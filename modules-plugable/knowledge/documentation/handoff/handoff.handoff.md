### Where a project's sessions live
- State: owner ruling (2026-10-13), implemented in `memar task`: a project with no `sessions` key in its preferences (since 2026-10-19 the `memar:` block of its `manifest.yaml`, before that `.agents/memar/preferences.md`) keeps its tasks in `.agents/tasks/` inside itself, which its VCS does **not** ignore (owner ruling, 2026-10-22, replacing the ignoring of 2026-10-13: an ignored folder can be lost to a clean, a reset or a re-clone, and a task folder holds work not yet archived); keeping the records is the job of the project's records branch (`archive`), and they are never committed to the main branch, so the folder shows as untracked there on purpose; `new` has no ignoring note for this default and so changes nothing; the `tasks` key still overrides, and a custom location git does not ignore still gets the note; only the Memar checkout keeps them in its own `.agents/tasks/`. Memar's daily sweep reaches only that last folder. No task verb has a default project or reads the calling folder: `--project NAME` (a registered name) or `--project-path PATH` (a folder) is always given, a name is resolved through `temp/projects.log` (`memar project find`), and a project's task folders are recorded on its entry there, wherever they lie. A missing tasks folder, in Memar's temp or a project, is created and blocks nothing. The `organization` project's existing sessions were moved out of Memar's `.agents/tasks/` into its own. Wherever a task's folder lies, its records are kept apart from it, in the project's `.agents/tasks/` (next entry).

### Who writes a plan's AIModelName, and when?
- State: the owner asked (2026-10-14) that a plan name the AI model that is to run the session, in a key called `AIModelName` (not `Model` nor `ModelName`), written as `CONTRIBUTORS.md` names a model. Which models can be started depends on the runtime and the account: in conversation `20261013T034406Z-30084-0`, Fable was refused for want of usage credits and Opus-5.5 is the strongest a sub-agent can run. A queued plan may be claimed later by another runtime. The model that actually ran is provenance, recorded in the changelog entry's Contributors bullet. The record's key spelling (`RecordKey.written`, a capitalized one-word key) cannot write `AIModelName`, so the key's written form must be declared with it.
- Options: (1) the delegator writes it when it hands the session to an agent (`new` for one delegated at once, `claim`/`claims` for a queued one), choosing by the `TaskKind` tier; `start` prints it and a runner that is not that model ends Blocked naming its own; a queued plan carries none, recommended: the value is known only where the runtime is. (2) written at `new` for every plan, queued ones too; cost: a queued plan names a model the claiming runtime may not have. (3) not in the plan, only the tier, the runner reporting its model; cost: no check that the assigned model ran.
- Anchor: `modules-plugable/ai/services/get_task_init_context.py` (model part), `session_claim.py`, `session_claims.py`, `session_new.py`; `docs/labels-design.md` of task `20261014T120306Z-20292-0`, AIModelName.

The `ModelName` is a suggestion: an agent that takes a session and lacks that model decides from the other two which model it gives the task, and the `memar` command says so. ### Do Effort and ReasoningLevel read as how much work the task needs and how hard its hardest judgment is?
- State: the owner named them "needed effort" and "needed level of reasoning" (2026-10-15). The design reads ReasoningLevel as the depth of reasoning the task's most demanding step needs, which an agent reads to choose how capable a model it gives the task, and Effort as how much the task reads, writes, checks and repeats before its acceptance check passes, which an agent reads to choose how much it lets the model spend. The two are independent: a migration over many files is high Effort, low ReasoningLevel; a short critique of a definition others consume is the reverse.
- Options: (1) the readings above, recommended: each number chooses one thing, so an agent never has to split one number into two decisions. (2) Effort as the app's own effort setting (how long the model thinks) and ReasoningLevel as model strength; cost: Effort then describes an app's knob rather than the task, which the owner's "the task's difficulty chooses" argues against. (3) other readings the owner states.
- Anchor: `docs/labels-design.md` of task `20261015-T103826Z-16432`, AIModel.
- Blocks: the help text of the `AIModel` flags and `start`'s model part. Assumption meanwhile: option 1 (Tentative).

### Does a claim record the model the claiming agent chose, and when does a started session end Blocked on its model?
- State: under the owner's ruling (2026-10-15) the agent that takes a session chooses its model from `AIModel`. Today `start` tells a runner to end Blocked if it runs on a weaker model "or cannot tell"; under a suggestion no runner can ever tell for certain, so that sentence would block every run. The claim file (`claim`, written by `memar task claim`) names who holds the session and not the model.
- Options: (1) the claiming agent may record the model it gives the task in the claim; `start` then says "you were handed this to run on X", and a runner that is not X ends Blocked naming its own; without that record a runner ends Blocked only when it can tell it falls short of `ReasoningLevel`, recommended: a check against a fact where one exists, a self-judgment only where none does. (2) no record; a runner ends Blocked only when it can tell it falls short; cost: no check that the chosen model ran. (3) no Blocked rule at the runner at all, the choice being wholly the claimer's; cost: a sub-agent started on a weak model by mistake runs a design task.

### May a plan carry more than one Topic label, and is a claims batch bounded by model tier as well as by topic?
- State: today a plan has one topic, so that a batch's membership is a plain equality and a task with two subjects is two tasks; `claims` gives one sub-agent the first task's topic. With labels a plan could carry several. A sub-agent runs on one model, so a batch that mixes a design task with mechanical ones runs one of them on the wrong model; `claims` today does not look at `Kind`.
- Options: (1) at most one Topic per plan, and a batch takes only tasks of the first task's `TaskKind` tier (or none stated) as well as its topic, recommended: one context and one model per sub-agent; cost: fewer tasks per batch. (2) several topics per plan, batching by overlap; cost: membership becomes a judgment of overlap, and one task may pull two subjects into one context. (3) bound the batch by the same `AIModelName` instead of tier; cost: queued plans carry no `AIModelName` under the recommendation above.
- Ruling: owner (2026-10-15): no limit on labels, Topic among them, but none assigned needlessly. The revised design keeps membership a plain test: a batch's topic is `--label Topic=T` or the first task's first `Topic` label, and its members are the queued tasks that carry that label, so several topics on one plan do not turn membership into overlap. The model bound is still open, and is now asked against `AIModel`, tiers being gone: (1) a batch takes only tasks whose `AIModel` equals the first one's, an absent one counting as a value, recommended: one sub-agent, one model choice, no design task run on a model chosen for mechanical ones and no mechanical one on the expensive model; cost: fewer tasks per batch. (2) tasks whose `ReasoningLevel` is no higher than the first one's; cost: cheap tasks ride on the expensive model. (3) no model bound; cost: one of the batch runs on a model chosen for another.
- Anchor: `modules-plugable/management/task/services/claims.py` (`take`, `batch_report`); `docs/labels-design.md` of task `20261015-T103826Z-16432`, Commands.
- Blocks: the `claims` change. Assumption meanwhile: ruling as above and bound (1) (Tentative).
- Asked: 2026-10-15, Claude (task `20261014T120306Z-20292-0`), for Omid Hekayati; the bound re-asked by task `20261015-T103826Z-16432`.
