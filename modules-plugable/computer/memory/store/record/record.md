# Memory Record

## Abstract
The record contract, the port that the memory module offers and its adapters realize, is the one contract through which a domain, a service or an agent's verb reaches the nodes a project keeps in non-volatile memory. A node is named by an id and holds one value per domain, its parts; a node may carry labels, and a label is an id attached to it so that nodes can be found by it. The port has five operations: `get`, `parts`, `list`, `scan` and `batch`, the last being the only one that writes, and it writes atomically under expectations about what the parts held when they were read. The port knows ids and batches and nothing about how a medium keeps them: windows, branches, folders, packs and paths belong to the adapter that serves a class of nodes, an adapter is a pluggable module, and which adapter serves which class is the project's choice, made once in the `memar:` block of its manifest and never in a service. Whether an adapter conforms is decided by one contract suite, specified here by its cases and run against every adapter.

Correction of 2026-10-24, from the owner's rulings and the model in [Memory Store → The contract](../../../../../modules/computer/memory/store/store.md#the-contract): this document was written as if the record were the one abstraction of retention. It is not. The contract (an address, `get`, `list`, the atomic `batch` under expectations, `state` and `changes`, the guarantees, the capabilities and the suite) belongs to the memory module and is realized by every capsule; `record` is one such capsule, pluggable, whose address is a 16-byte id followed by the ASCII bytes of a domain key, with no separator (the key charset makes the join unambiguous), and which adds the node, the part and the label; the token (the SHA-256 of a value) stays in the contract, which returns it with a value found and takes it in an expectation, so an adapter that knows addresses only can serve it. Where this document says the port, read the memory contract for what it states of `get`, `list`, `batch`, the answers, the guarantees, the capabilities and the cases that name no id, part or label, and read this capsule for the rest. Those statements were moved to [Memory Store](../../../../../modules/computer/memory/store/store.md) and [Memory Conformance](../../../../../modules/computer/memory/conformance/conformance.md) on 2026-10-26, with the contract's protocol; what stays here is what `record` adds, and it is Tentative where it conflicts with them. On 2026-10-26 `record` was built in [`record.py`](record.py), and the first design's `list` of ids became `nodes`.

## Introduction

### Motivation
A service that reaches its records through a folder, a version-control command or a database call carries what that medium costs and what it can lose. Work records kept as files in the working tree are scanned by antivirus software at every create and edit, are lost by a stash or a branch switch, and can be edited by any tool; a second store would repeat each of those with its own exceptions in the services. One port with the adapter chosen outside the services removes the exceptions, lets the medium change without a service changing, and makes a claim about the medium (atomic, durable, not in the working tree) a claim a test can decide.

## Explanation

### Definition
- **Node.** A thing a project keeps, named by an id; it is a record in the sense of the memory module's Record model, and this document says node for a record together with its parts and labels. A node exists once it has a part, and it is not a file, a row or a record: how an adapter shows it is the adapter's.
- **Id.** Sixteen bytes forming a UUID version 7, the record refusing any 16 bytes whose version and variant bits are other, the form [Label](../../../../../modules/knowledge/label/label.md#a-name-is-one-label) already gives its identifiers. The port requires of an id three things: equality; an existence instant, the milliseconds since the Unix epoch the id carries; and a total order, the byte order, which for this form is the order of existence instants and then of the remaining bytes. The port reads the instant to answer `list` and `scan`, never checks it against a clock, and mints no id: whoever names a node mints its id, and a collision is caught by writing the first part with an expectation that the part is absent. An id names no class: a caller that holds an id knows its class from where it got it, and a reference from a node of one class to a node of another carries the class name beside the id.
- **Domain key.** The name under which a domain keeps its part on a node: lowercase letters and digits, groups separated by single hyphens, at most 64 characters, issued by the domain's own module in code and compared by equality alone. The key `labels` is reserved to the port.
- **Part.** The value, a byte string of any length including none, that one domain keeps on one node. A node has at most one part per domain key at any instant. An empty part is a value and differs from an absent one. The encoding of a part is its domain's, and it is canonical: equal values encode to equal bytes, because the token below is taken over the bytes.
- **Token.** The SHA-256 of a part's bytes. A token is a function of the value alone, so it is the same in every adapter and can be recorded outside the store; it is not an order, and a value that returns to an earlier value returns to its token.
- **Label.** An id attached to a node. The `labels` part of a node is the labels as the concatenation of their ids in ascending order without repetition, and the port refuses a write to it in any other form. What a label means is its own domain's ([Label](../../../../../modules/knowledge/label/label.md)): the port treats it as an id, so any id a writer attaches, such as the id of another node, serves to find the nodes that carry it, and the choice of what to attach is the writer's.
- **Class.** A name a composition gives to the nodes one group of services reads and writes, so that one adapter serves them all. A node belongs to exactly one class, hence to one store, and a batch never spans two.
- **Batch.** A set of expectations and a set of writes applied as one step, as the operations below say.

### The operations
Each operation is stated by what it answers for a given input, so that any party can decide whether an adapter does. Their exact signatures are code, written once in [`record.py`](record.py), and this document names them. `record` is itself a store of the contract whose address is a key, the 16 bytes of an id then the ASCII bytes of a domain key, so the contract's `get`, `list`, `batch`, `state` and `changes` are its operations over keys, and it adds `parts`, `nodes` and `scan`.

- **`get(keys)`** is the contract's `get` over keys: one result for each key, in the order given, Found with the value and its token, Absent, or Unavailable.
- **`parts(ids)`** answers, for each id, the domain keys the node holds with the token of each, or Absent when it holds none, or Unavailable. It is a `list` over the keys that begin with the id, read from one committed state.
- **`nodes(from, to, after, limit, descending)`** answers the first `min(limit, n)` ids, `n` being the number of ids whose existence instant, a whole number of milliseconds, lies in `[from, to)` and which come after the id `after`, in ascending id order, or, when descending is asked, the last `min(limit, n)` ids of the range that come before the id `after` (`after` bounds from above), in descending order; or Unavailable when the adapter cannot answer the whole range. A page shorter than `limit` is therefore the end of the range, and no adapter returns a short page for any other reason. `nodes` with no bounds answers every node. A bound on instants is a range over the six-byte millisecond prefix of a key, so an adapter's windows, shards and directories never show: the answer is the same for any adapter holding the same nodes. The first design called it `list`; the contract's `list` answers keys and keeps the name.
- **`scan(all_of, from, to, after, limit, descending)`** answers as `nodes` does, only the ids of nodes whose labels include every id in `all_of`, a set of at least one. Paging by `after` visits every id that matches throughout the paging exactly once and any other id at most once, even while other nodes are written, and `scan` too is Unavailable when it cannot answer the whole range.
- **`batch(expect, write)`** is the contract's batch over the addresses of the keys, with its expectations (a token or `absent`) and its answers in their order ([Memory Store → The contract](../../../../../modules/computer/memory/store/store.md#the-contract)); a write creates the node when it is its first part. `record` adds to what is malformed and Refused: a key with an invalid domain key or an id not of the form above, and a write to `labels` in a form other than the one above.

  A call of `get`, `parts`, `nodes` or `scan` with an invalid domain key or id, an empty `all_of`, a `limit` below one or a `from` after a `to` is Refused as a whole, and answers nothing. `put` is a batch of one write and adds no semantics of its own.

### What every adapter guarantees
The guarantees are the contract's ([Memory Store → The contract](../../../../../modules/computer/memory/store/store.md#the-contract)); `record` reads them for nodes as follows.
- **Atomic and isolated.** A call of `get`, `parts`, `nodes` or `scan` answers from a state between two batches, so a node's parts and labels written by one batch are seen together.
- **One place orders the writes.** A held range is a range of existence instants, the six-byte millisecond prefix of an id; because the writer mints the id, an adapter with a shared store also holds every instant after the last range a fetch gave it, where new ids are minted, and decides an `absent` expectation there alone. The shared store is asked through `get`, `parts`, `nodes` and `scan` by id.
- **Absent is not unknown.** A part never written reads Absent only when the adapter has answered that it is not there, and a `scan` that could not look at part of its range answers Unavailable.
- **Nothing is removed.** No operation removes a part, a label or a node, though a medium others can change, such as files, may lose one; what a domain shows is its own matter, and no service offers erasure until the owner rules.
- **Derived structures are rebuildable and never stale.** The index that answers `nodes` and `scan` (the ids of the nodes and the labels of each) is derived from the nodes alone and kept in the memory of the process, one for each open `record`, never in the store's medium nor on disk; it records the `state()` it reflects and, before it answers, applies `changes` since that state, so that a batch committed by another handle or process shows in the next `scan`. Dropping it costs one rebuild from `list` and `get`, and changes no answer.

### Capabilities and limits
The capabilities, the limits and `stats` are the contract's, written once in [`store/protocol/store.py`](../../../../../modules/computer/memory/store/protocol/store.py) ([Memory Store → The contract](../../../../../modules/computer/memory/store/store.md#the-contract)). For `record`, a batch whose expectations are on more than one key needs `atomic_batch`, and a class that records state changes needs it when it is opened.

### What the port does not know
The port does not know how a medium keeps nodes: no window, branch, reference, folder, pack, object, path, file name or fan-out is part of its contract, and the rule that places a node in a window is the git adapter's private detail: since 2026-10-24 the adapter knows addresses only and shards by a fixed-length prefix of the address, which for this capsule's ids is a window of time, so the adapter reads no id. It does not know what a value encodes, what a domain key or a label means, which class a node belongs to, who wrote, or what a node's history was. It enforces no access: whoever can run an adapter on a store can read and write it, and who may do what is the authorization above it, so `list` and `scan` hide nothing. It stamps no time on a write and mints no id, and it accepts a node whose id has any existence instant, so a node named long before it is first written lands where its id says. History is the Request chain ([Request → Recording a change of state](../../../../../modules/computer/request/request.md#recording-a-change-of-state)), and a domain that wants an old value reads it there.

### Placement
[Kernel Neutrality](../../../../../modules/knowledge/modularity/rules/kernel-neutrality/kernel-neutrality.md#the-rule) puts to each part of this design the question whether a second organization could choose it otherwise without the subject meaning something else.
- The atomic batch under expectations, the difference between Absent and Unavailable, and the guarantees above are the subject of the memory module, and stay in it as its contract (`modules/computer/memory/store/`). The nodes, ids, parts, labels and tokens are this capsule's: they are a form of address and of value, and a second organization could take another form (an id of another kind, no labels) without a store meaning something else. Other kernel modules that refer to a node (Task, timeline, Request) refer to an address through the memory contract and depend on nothing here, so the capsule is pluggable and stands at `modules-plugable/computer/memory/store/record/` (owner's rulings of 2026-10-24).
- The contract suite is the decision procedure of the contract and stays with it in the memory module; the cases that name ids, parts or labels are this capsule's.
- The media and their mechanics, git branches, the shard rule, packs, folders, a reference in memory, are choices. Each adapter is a pluggable module attached to this contract ([Pluggable → Operational rules](../../../../../modules/knowledge/modularity/labels/pluggable.md#operational-rules)), and carries its capability's name. Where each stands is ruled: `git` and `files` are modules of their own at `modules-plugable/computer/memory/`, they realize the memory contract and know nothing of this capsule, and this capsule is laid over whichever store a class is bound to (2026-10-24). `git` keeps work records and uses git plumbing only; `files` stands for a project's source tree until the editing surfaces that replace it exist, and rests on the contract and on the file system module, which moves beside them; neither redoes the existing modules for git and for the file system. Because `files` and `git` know no label, a path is a thing this capsule's caller attaches (a label of a node), not something `files` keeps. The reference adapter that keeps nodes in the process, `volatile`, is the model the suite compares others with, so it is part of the decision procedure and sits in the memory module beside the suite, address-generic; each adapter's own tests run the contract's suite, a dependence toward the foundation. The view is a consumer of this capsule and a pluggable module of its own, [Memory View](../view/view.md), whose home beside it the move of the modules settles.
- Which adapter serves which class is a choice of the project and sits in its preferences, below. The name of a class is its services' own, the subject of the group of services that use it, and a project binds the name it finds.
- The limits and the capabilities are values the subject requires, so they are exposed as parameters above and a class states what it needs of them; no adapter and no port document fixes a floor.
- Every dependence runs toward the foundation: the port depends on the identifier it reads and on nothing under `modules-plugable/` or `bundles/`, and the module-graph test fails any import that runs the other way ([Kernel Neutrality → How a check runs](../../../../../modules/knowledge/modularity/rules/kernel-neutrality/kernel-neutrality.md#how-a-check-runs)).

### The Go-era Record model this contract replaces
The record folder holds a draft written for a database node: `Records` (named `Record_Model` before 2026-10-25) with `Get`, `Save`, `Read`, `Write`, `Append`, `Prepend`, `Extend`, `Lock`, `Unlock`, `Delete`, `Erase` and a count, a 16-byte `RecordUUID` (named `Storage_UUID` before 2026-10-25), and versions in `protocol/version.kh`. This contract is that model made decidable, and it stands where the draft stood so that the memory module has one record abstraction and no second. Each operation of the draft has a place in it, or a stated absence:
- `Get`, `Save` and `Read` are `get` and `batch`; `Count` (named `RecordsNumbers` before 2026-10-25) and the listing are `nodes` and `scan`.
- `Lock` and `Unlock`, which reach strict consistency by holding a record, are the expectations of a batch: a writer reads a token and writes under it, and no lock outlives a process.
- `Write` at an offset, `Append`, `Prepend` and `Extend` are not offered. The draft itself advises saving a large record in several small ones, and a part is replaced whole; a larger value is several parts or several nodes.
- `Delete` and `Erase` are the erasure question the port leaves open: the draft distinguishes making a record invisible from zeroing its place, and the owner's ruling on retention and erasure chooses between them.
- The versions of one record, `Versioned` and `MaxVersion`, are not a property of this contract: the history of a value is the chain of its Requests ([Request → Recording a change of state](../../../../../modules/computer/request/request.md#recording-a-change-of-state)).
- The draft's id was a 16-byte hash of the data, suggested so that a collision is improbable; this contract's id is a UUID version 7 so that `list` can order by time, and a content hash may fill the random bits of one when a node is content-addressed.
- Ranged `Read` and `Length` are not offered: a part is read whole, and a size is the domain's field when it needs one. The subscriptions `listen-to-key` and `listen-to-mediatype` are not offered: a consumer polls `scan`, and a change feed is a later capability recorded in the handoff. The draft's per-object metadata is not kept by the contract: the media type is in the `content` part, and length and compression are gone. The record's own request identity and time are the Request's. Broadcast replication on save is outside, since one writer location orders the writes.

The draft's declarations in `protocol/` and `services/` stay as they are until the build task replaces them with the protocol this contract owes. The owner ruled on 2026-10-25 that `Lock` and `Unlock` are an optional capability `lockable` of a store, outside the core operations, and that `Record_Model` becomes `Records` ([Memory Record Handoff](record.handoff.md#decisions)); the upgrade of the Go-era files is task `20261024-T052938Z-22844`, which gave them their names (`Records` with its methods unprefixed, `Lock` and `Unlock` on the `Lockable` of `protocol/lockable.kh`, `RecordUUID` and `Observer_RecordUUID`), and the build task of the contract does not edit or remove any file under `record/protocol/` or `record/services/`. the build task of the contract does not edit or remove any file under `record/protocol/` or `record/services/`; their fate is that task's and the moves task's. The text that follows is the first design's and is Tentative: the declarations the contract replaces (`model.kh`, `save-options.kh`, `data_model.kh`, the `service-*` files and the other `services/` drafts) are removed with a changelog record, and a declaration other modules import (`uuid.kh`, `uuid.observers.kh`, `data.kh`) stays and is repointed, so that the folder holds one record abstraction.

### Binding adapters to classes
A project says which adapter serves which class in the `memar:` block of its `manifest.yaml`, the block the tools read and no agent loads, in the key `memory`, whose form is declared once in [project preferences](../../../../../modules/process/project/services/preferences.py): a `class=adapter` pair for each class, an adapter named by its module's capability name. The example is illustrative; the class names are the composition's, and Memar's own choice is written in its manifest and nowhere else.

```
memar:
  memory: work-records=git-store, sources=files
```

- **A service asks for a class, never for an adapter.** It calls one function, `open(project, class_name, needs)`, declared in the entry point of Memar's tooling, [`bundles/memar/memar`](../../../../../bundles/memar/memar) (a bundle may import pluggable modules and a kernel module may not), where the needs (`Needs` in [`record.py`](record.py)) are `atomic_batch` for a class that records state changes and the least limits it uses; it returns `record` laid over the adapter bound to the class. The entry point reads the key and turns an adapter name into its module, the module of that name at `modules-plugable/computer/memory/store/<capability>/`, which offers `bind(project, class_name)`: the adapter that serves the class, naming the store it keeps the class in. So a kernel module imports no adapter and no bundle, and no service holds a branch for a class or an adapter. Opening is refused when the key does not name the class, when the adapter declares less than the needs or keeps a store `record` cannot be laid over, and when two classes are bound to one store; and, as malformed, when the key's form is broken or names an adapter no module offers. Each refusal says which, and names the class and the line to add or mend.
- **A group of services names its class.** The task verbs name the class of the work records they keep, in their own module, and the port fixes no name. A class the key does not name is refused when it is opened, with a message that names the class and the line to add; the port has no default adapter, because a default would be a choice the kernel makes.
- **A class states what it needs.** The service that opens a class says whether it records state changes, which needs `atomic_batch`, and the limits it uses; opening it on an adapter that declares less is refused when the class is opened.
- **An adapter's own parameters** are keys of the same block named after the adapter and declared by the adapter's module; the port declares none.
- **Two adapters never write one store.** A node's class decides its store, and a class has one adapter.

### The contract suite
The cases that name no id, part or label are the contract's and are code, in [`conformance.py`](../../../../../modules/computer/memory/conformance/conformance.py) ([Memory Conformance](../../../../../modules/computer/memory/conformance/conformance.md) says which moved and why). `record`'s own cases, those that name an id, a part or a label, are code too, one function each in [`tests/record.py`](tests/record.py) whose docstring states the case, with the halves of the contract's cases that stayed here under the contract case's name; each holds for `record` over any store, and an adapter's own tests run them on `record` laid over it. `python modules-plugable/computer/memory/store/record/tests/record.py` runs them, and the contract's suite, on `record` laid over `volatile`.

The contract's suite makes its addresses from the store's parameters alone, and an address it makes is not a key, so it reaches `record` through a translation in the tests: each of its addresses is one key of one fixed id, whose domain key spells the address in hexadecimal after a letter, which keeps equality and the byte order; every call still goes through `record` and its checks. The cross-process half of `one-process-sees-the-others-commit` runs only on a store declaring `shared_between_processes`, and runs on `record` laid over [`git-store`](../git-store/git-store.md) in that adapter's tests.

### The view
A read-only folder built from a class's committed state, for a person's editor, is a consumer of the port and is specified in [Memory View](../view/view.md). The port offers it nothing beyond `get`, `parts`, `nodes` and `scan`.

### Adapters state themselves
What an adapter's document states is the contract's ([Memory Store → The contract](../../../../../modules/computer/memory/store/store.md#the-contract)). For `record`, the 30-day window of the first design is a parameter of `git-store` for a class of ids of version 7, a prefix of the address, not a rule of the contract.
