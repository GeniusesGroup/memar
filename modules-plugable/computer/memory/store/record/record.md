# Memory Record

## Abstract
The record contract, the port that the memory module offers and its adapters realize, is the one contract through which a domain, a service or an agent's verb reaches the nodes a project keeps in non-volatile memory. A node is named by an id and holds one value per domain, its parts; a node may carry labels, and a label is an id attached to it so that nodes can be found by it. The port has five operations: `get`, `parts`, `list`, `scan` and `batch`, the last being the only one that writes, and it writes atomically under expectations about what the parts held when they were read. The port knows ids and batches and nothing about how a medium keeps them: windows, branches, folders, packs and paths belong to the adapter that serves a class of nodes, an adapter is a pluggable module, and which adapter serves which class is the project's choice, made once in the `memar:` block of its manifest and never in a service. Whether an adapter conforms is decided by one contract suite, specified here by its cases and run against every adapter.

Correction of 2026-10-24, from the owner's rulings and the model in [Memory Store → The contract](../../../../../modules/computer/memory/store/store.md#the-contract): this document was written as if the record were the one abstraction of retention. It is not. The contract (an address, `get`, `list`, the atomic `batch` under expectations, `state` and `changes`, the guarantees, the capabilities and the suite) belongs to the memory module and is realized by every capsule; `record` is one such capsule, pluggable, whose address is a 16-byte id followed by the ASCII bytes of a domain key, with no separator (the key charset makes the join unambiguous), and which adds the node, the part and the label; the token (the SHA-256 of a value) stays in the contract, which returns it with a value found and takes it in an expectation, so an adapter that knows addresses only can serve it. Where this document says the port, read the memory contract for what it states of `get`, `list`, `batch`, the answers, the guarantees, the capabilities and the cases that name no id, part or label, and read this capsule for the rest. The build task that writes the protocol moves each of those statements to the memory module and leaves here only what `record` adds; until then this text stands as the source of both, and it is Tentative where it conflicts with the memory module.

## Introduction

### Motivation
A service that reaches its records through a folder, a version-control command or a database call carries what that medium costs and what it can lose. Work records kept as files in the working tree are scanned by antivirus software at every create and edit, are lost by a stash or a branch switch, and can be edited by any tool; a second store would repeat each of those with its own exceptions in the services. One port with the adapter chosen outside the services removes the exceptions, lets the medium change without a service changing, and makes a claim about the medium (atomic, durable, not in the working tree) a claim a test can decide.

## Explanation

### Definition
- **Node.** A thing a project keeps, named by an id; it is a record in the sense of the memory module's Record model, and this document says node for a record together with its parts and labels. A node exists once it has a part, and it is not a file, a row or a record: how an adapter shows it is the adapter's.
- **Id.** Sixteen bytes forming a UUID version 7, the record refusing any 16 bytes whose version and variant bits are other, the form [Label](../../../../../modules/knowledge/label/label.md#a-name-is-one-label) already gives its identifiers. The port requires of an id three things: equality; an existence instant, the milliseconds since the Unix epoch the id carries; and a total order, the byte order, which for this form is the order of existence instants and then of the remaining bytes. The port reads the instant to answer `list` and `scan`, never checks it against a clock, and mints no id: whoever names a node mints its id, and a collision is caught by writing the first part with an expectation that the part is absent. An id names no class: a caller that holds an id knows its class from where it got it, and a reference from a node of one class to a node of another carries the class name beside the id.
- **Domain key.** The name under which a domain keeps its part on a node: lowercase letters and digits, groups separated by single hyphens, at most 64 characters, issued by the domain's own module in code and compared by equality alone. The key `labels` is reserved to the port.
- **Part.** The value, a byte string of any length including none, that one domain keeps on one node. A node has at most one part per domain key at any instant. An empty part is a value and differs from an absent one. The encoding of a part is its domain's, and it is canonical: equal values encode to equal bytes, because the token below is taken over the bytes.
- **Token.** The SHA-256 of a part's bytes. A token is a function of the value alone, so it is the same in every adapter and can be recorded outside the store; it is not an order, and a value that returns to an earlier value returns to its token.
- **Label.** An id attached to a node. The `labels` part of a node is the labels as the concatenation of their ids in ascending order without repetition, and the port refuses a write to it in any other form. What a label means is its own domain's ([Label](../../../../../modules/knowledge/label/label.md)): the port treats it as an id, so any id a writer attaches, such as the id of another node, serves to find the nodes that carry it, and the choice of what to attach is the writer's.
- **Class.** A name a composition gives to the nodes one group of services reads and writes, so that one adapter serves them all. A node belongs to exactly one class, hence to one store, and a batch never spans two.
- **Batch.** A set of expectations and a set of writes applied as one step, as the operations below say.

### The operations
Each operation is stated by what it answers for a given input, so that any party can decide whether an adapter does. Their exact signatures are code, written once in the port's protocol when the port is built, and this document names them.

- **`get(keys)`** takes any number of keys, a key being an id and a domain key, and answers one result for each key, in the order given: Found with the value and its token; Absent; or Unavailable. Unavailable is answered when the adapter cannot decide between the first two, as when the shared store it asks for an object it lacks cannot be reached. A call of many keys does not cost a process or a file per key where the medium allows it, and an adapter reports the processes it starts and the files it opens through `stats`.
- **`parts(ids)`** answers, for each id, the domain keys the node holds with the token of each, or Absent when it holds none, or Unavailable.
- **`list(from, to, after, limit, descending)`** answers the first `min(limit, n)` ids, `n` being the number of ids whose existence instant lies in `[from, to)` and which come after the id `after`, in ascending id order, or, when descending is asked, the last `min(limit, n)` ids of the range that come before the id `after` (`after` bounds from above), in descending order; or Unavailable when the adapter cannot answer the whole range. A page shorter than `limit` is therefore the end of the range, and no adapter returns a short page for any other reason. `list` with no bounds answers every node. An adapter's windows, shards and directories never show: the answer is the same for any adapter holding the same nodes.
- **`scan(all_of, from, to, after, limit, descending)`** answers as `list` does, only the ids of nodes whose labels include every id in `all_of`, a set of at least one. Paging by `after` visits every id that matches throughout the paging exactly once and any other id at most once, even while other nodes are written, and `scan` too is Unavailable when it cannot answer the whole range.
- **`batch(expect, write)`** applies the writes only if every expectation holds. An expectation is one of two: the part under a key holds the value of a given token, or the part under a key is absent. A write puts a value under a key, creating the node when it is the first. A batch is one of the following in its result, and when more than one applies the first in this order is the answer:
  - Refused: the batch is malformed, and nothing is applied. It is malformed when it holds no write, writes one key twice, holds two expectations on one key, names an invalid domain key, writes `labels` in a form other than the one above, exceeds a limit the adapter declares (TooLarge), or needs atomicity the adapter does not declare (NotAtomic).
  - Unavailable, with its reason: NotHeld, the batch has an expectation of a value on a part of a node the adapter does not hold, or writes one ([One place orders the writes](#what-every-adapter-guarantees)); Unreachable, the adapter cannot decide an expectation, as when a shared store it must ask cannot be reached; or Failed, the adapter could not finish and has made sure the batch can no longer commit. Nothing is applied. An adapter answers a batch only when its fate is settled: one that cannot tell whether a write it started has finished makes sure that write can no longer commit before it answers Unavailable.
  - Conflict: an expectation failed, the first in the order given is named, and nothing is applied.
  - Committed: every write is applied.

  A call of `get`, `parts`, `list` or `scan` with an invalid domain key, an empty `all_of`, a `limit` below one or a `from` after a `to` is Refused as a whole, and answers nothing. A write to a key with no expectation on it replaces the part whatever it held. `put` is a batch of one write and adds no semantics of its own.

### What every adapter guarantees
- **Atomic and isolated.** A committed batch is visible whole to every reader of the store and no reader sees part of it, whether the reader is a thread, another process, or the same process after a restart. A call of `get`, `parts`, `list` or `scan` answers from a state between two batches.
- **Linear.** The batches of one store are in one order, and a call that begins after a batch has returned sees it.
- **One place orders the writes.** A store has one writer location, the place where its batches are ordered, and every process that writes it goes through an adapter at that location. An adapter declares the ranges of existence instants it holds: for these ids it is the writer location and decides alone. An adapter with no shared store holds every id; one that keeps a copy of what a shared store holds holds the ranges it was given whole by a fetch the user asked for, and always the instants after the last of them, where new ids are minted. The shared store is asked through the port's own reads, `get`, `parts`, `list` and `scan` by id, which answer Found, Absent or Unavailable. A node outside the held ranges is read by asking the shared store, and the answer is as fresh as the asking; what the adapter learns that way it does not write into its own store. Inside a held range an `absent` expectation and a write are decided at the adapter, because the writer mints the id; outside it, an expectation of a value and a write are Unavailable with the reason NotHeld, and an `absent` expectation is Unavailable with the reason Unreachable until the shared store has answered. Writing the same nodes from several places is a design the port does not offer.
- **Durable as declared.** An adapter that declares `durable` keeps a committed batch through the abrupt end of the process that wrote it. Survival of the loss of power is not a port capability; an adapter that gives it says so in its own document.
- **Absent is not unknown.** An expectation that a part is absent is never satisfied by an adapter that could not look. A part never written reads Absent only when the adapter has answered that it is not there, by looking in a held range or by asking the shared store. A `list` or `scan` that could not look at part of its range answers Unavailable and never a shorter answer given as complete.
- **Nothing is removed.** The port has no operation that removes a part, a label or a node, though a medium others can change, such as files, may lose one. A value is replaced by writing another, and what a domain shows is its own matter. Erasure, which a legal purge or a secret requires, is not decided: the question is open in [Memory Handoff](../../../../../modules/computer/memory/memory.handoff.md#what-is-the-retention-and-erasure-rule-for-preserved-history-and-where-do-a-records-versions-live), and until the owner rules, no adapter and no service offers it.
- **No file in the working tree, where declared.** An adapter that declares `leaves_working_tree_untouched` keeps whatever it needs outside the project's working tree, in the store's own medium or in the user's data area, and its writes never change a file the working tree tracks or shows. An adapter whose medium is the working tree, as `files` is, declares it false.
- **Derived structures are rebuildable and never stale.** An index an adapter keeps to answer `list` or `scan` fast is derived from the nodes alone, is never written into the store's medium, and is rebuilt from the nodes when lost. It records the committed state it reflects and is brought up to date before it answers, so that a batch committed by another process shows in the next `scan`. Deleting every derived structure changes no answer.

### Capabilities and limits
An adapter declares, in code and once, what it is, and the port exposes it. `atomic_batch`: whether a batch of more than one write, or with expectations on more than one key, can be applied atomically; an adapter that declares it false refuses such a batch as NotAtomic and applies a one-key write with an expectation atomically. `durable`: a committed batch survives the abrupt end of the process that wrote it. `shared_between_processes`: several processes may use one store at once. `fallback`: the adapter asks a shared store for an object it lacks. `leaves_working_tree_untouched`. The limits: writes per batch, bytes per batch (the sum of the lengths of the values written), bytes per value. And `stats`: the number of processes started and of files opened since the store was opened, for an adapter whose medium costs either. What a class needs of its adapter, the least limits and the capabilities, is stated by the service that opens it and checked when the class is opened, as `atomic_batch` is; the port fixes no floor.

### What the port does not know
The port does not know how a medium keeps nodes: no window, branch, reference, folder, pack, object, path, file name or fan-out is part of its contract, and the rule that places a node in a window is the git adapter's private detail: since 2026-10-24 the adapter knows addresses only and shards by a fixed-length prefix of the address, which for this capsule's ids is a window of time, so the adapter reads no id. It does not know what a value encodes, what a domain key or a label means, which class a node belongs to, who wrote, or what a node's history was. It enforces no access: whoever can run an adapter on a store can read and write it, and who may do what is the authorization above it, so `list` and `scan` hide nothing. It stamps no time on a write and mints no id, and it accepts a node whose id has any existence instant, so a node named long before it is first written lands where its id says. History is the Request chain ([Request → Recording a change of state](../../../../../modules/computer/request/request.md#recording-a-change-of-state)), and a domain that wants an old value reads it there.

### Placement
[Kernel Neutrality](../../../../../modules/knowledge/modularity/rules/kernel-neutrality/kernel-neutrality.md#the-rule) puts to each part of this design the question whether a second organization could choose it otherwise without the subject meaning something else.

The nodes, ids, parts, labels and tokens are this capsule's: they are a form of address and of value, and a second organization could take another form (an id of another kind, no labels) without a store meaning something else. Other kernel modules that refer to a node (Task, timeline, Request) refer to an address through the memory contract and depend on nothing here, so the capsule is pluggable and stands at `modules-plugable/computer/memory/store/record/` (owner's rulings of 2026-10-24).
- The contract suite is the decision procedure of the contract and stays with it in the memory module; the cases that name ids, parts or labels are this capsule's.
- The media and their mechanics, git branches, the shard rule, packs, folders, a reference in memory, are choices. Each adapter is a pluggable module attached to this contract ([Pluggable → Operational rules](../../../../../modules/knowledge/modularity/labels/pluggable.md#operational-rules)), and carries its capability's name. Where each stands is ruled: `git` and `files` are modules of their own at `modules-plugable/computer/memory/`, they realize the memory contract and know nothing of this capsule, and this capsule is laid over whichever store a class is bound to (2026-10-24). `git` keeps work records and uses git plumbing only; `files` stands for a project's source tree until the editing surfaces that replace it exist, and rests on the contract and on the file system module, which moves beside them; neither redoes the existing modules for git and for the file system. Because `files` and `git` know no label, a path is a thing this capsule's caller attaches (a label of a node), not something `files` keeps. The reference adapter that keeps nodes in the process, `volatile`, is the model the suite compares others with, so it is part of the decision procedure and sits in the memory module beside the suite, address-generic; each adapter's own tests run the contract's suite, a dependence toward the foundation. The view is a consumer of this capsule and a pluggable module of its own, [Memory View](../view/view.md), whose home beside it the move of the modules settles.
- Which adapter serves which class is a choice of the project and sits in its preferences, below. The name of a class is its services' own, the subject of the group of services that use it, and a project binds the name it finds.
- The limits and the capabilities are values the subject requires, so they are exposed as parameters above and a class states what it needs of them; no adapter and no port document fixes a floor.
- Every dependence runs toward the foundation: the port depends on the identifier it reads and on nothing under `modules-plugable/` or `bundles/`, and the module-graph test fails any import that runs the other way ([Kernel Neutrality → How a check runs](../../../../../modules/knowledge/modularity/rules/kernel-neutrality/kernel-neutrality.md#how-a-check-runs)).

### The Go-era Record model this contract replaces
The record folder holds a draft written for a database node: `Records` (named `Record_Model` before 2026-10-25) with `Get`, `Save`, `Read`, `Write`, `Append`, `Prepend`, `Extend`, `Lock`, `Unlock`, `Delete`, `Erase` and a count, a 16-byte `RecordUUID` (named `Storage_UUID` before 2026-10-25), and versions in `protocol/version.kh`. This contract is that model made decidable, and it stands where the draft stood so that the memory module has one record abstraction and no second. Each operation of the draft has a place in it, or a stated absence:
- `Get`, `Save` and `Read` are `get` and `batch`; `Count` (named `RecordsNumbers` before 2026-10-25) and the listing are `list` and `scan`.
- `Lock` and `Unlock`, which reach strict consistency by holding a record, are the expectations of a batch: a writer reads a token and writes under it, and no lock outlives a process.
- `Write` at an offset, `Append`, `Prepend` and `Extend` are not offered. The draft itself advises saving a large record in several small ones, and a part is replaced whole; a larger value is several parts or several nodes.
- `Delete` and `Erase` are the erasure question the port leaves open: the draft distinguishes making a record invisible from zeroing its place, and the owner's ruling on retention and erasure chooses between them.
- The versions of one record, `Versioned` and `MaxVersion`, are not a property of this contract: the history of a value is the chain of its Requests ([Request → Recording a change of state](../../../../../modules/computer/request/request.md#recording-a-change-of-state)).
- The draft's id was a 16-byte hash of the data, suggested so that a collision is improbable; this contract's id is a UUID version 7 so that `list` can order by time, and a content hash may fill the random bits of one when a node is content-addressed.
- Ranged `Read` and `Length` are not offered: a part is read whole, and a size is the domain's field when it needs one. The subscriptions `listen-to-key` and `listen-to-mediatype` are not offered: a consumer polls `scan`, and a change feed is a later capability recorded in the handoff. The draft's per-object metadata is not kept by the contract: the media type is in the `content` part, and length and compression are gone. The record's own request identity and time are the Request's. Broadcast replication on save is outside, since one writer location orders the writes.

The draft's declarations in `protocol/` and `services/` stay as they are until the build task replaces them with the protocol this contract owes. The owner ruled on 2026-10-25 that `Lock` and `Unlock` are an optional capability `lockable` of a store, outside the core operations, and that `Record_Model` becomes `Records` ([Memory Record Handoff](record.handoff.md#decisions)); the upgrade of the Go-era files is task `20261024-T052938Z-22844`, which gave them their names (`Records` with its methods unprefixed, `Lock` and `Unlock` on the `Lockable` of `protocol/lockable.kh`, `RecordUUID` and `Observer_RecordUUID`), and the build task of the contract does not edit or remove any file under `record/protocol/` or `record/services/`. the build task of the contract does not edit or remove any file under `record/protocol/` or `record/services/`; their fate is that task's and the moves task's. The text that follows is the first design's and is Tentative: the declarations the contract replaces (`model.kh`, `save-options.kh`, `data_model.kh`, the `service-*` files and the other `services/` drafts) are removed with a changelog record, and a declaration other modules import (`uuid.kh`, `uuid.observers.kh`, `data.kh`) stays and is repointed, so that the folder holds one record abstraction.

### Binding adapters to classes
A project says which adapter serves which class in the `memar:` block of its `manifest.yaml`, the block the tools read and no agent loads ([project preferences](../../../../../modules/process/project/services/preferences.py)), in the key `memory`: one `class=adapter` pair for each class, pairs separated by commas, an adapter named by its module's capability name. The example is illustrative; the class names are the composition's, and Memar's own choice is written in its manifest and nowhere else.

```
memar:
  memory: work-records=git, sources=files
```

- **A service asks for a class, never for an adapter.** It calls one function, `open(project, class_name, needs)`, declared in the entry point of Memar's tooling in `bundles/memar` (a bundle may import pluggable modules and a kernel module may not), where the needs are `atomic_batch` for a class that records state changes and the least limits it uses; it returns `record` laid over the adapter bound to the class. The entry point reads the key and turns an adapter name into its module, so a kernel module imports no adapter and no bundle and no service holds a branch for a class or an adapter. Opening is refused when the key does not name the class, when the adapter declares less than the needs, and when two classes are bound to one store.
- **A group of services names its class.** The task verbs name the class of the work records they keep, in their own module, and the port fixes no name. A class the key does not name is refused when it is opened, with a message that names the class and the line to add; the port has no default adapter, because a default would be a choice the kernel makes.
- **A class states what it needs.** The service that opens a class says whether it records state changes, which needs `atomic_batch`, and the limits it uses; opening it on an adapter that declares less is refused when the class is opened.
- **An adapter's own parameters** are keys of the same block named after the adapter and declared by the adapter's module; the port declares none.
- **Two adapters never write one store.** A node's class decides its store, and a class has one adapter.

### The contract suite
The cases below are the stated inputs against which the port's requirements are decided. They are specified and not coded: the tests are written in the port's own `tests/` by the task that builds the port, each pending case carrying `owed:memory.port.contract-suite` in its title ([Test Practice → The Cycle](../../../../../modules/process/test/test.practice.md#the-cycle)), and when they run this list is replaced by a pointer to them. The suite reaches an adapter through a seam every adapter exposes for tests: to pause or fail it at the point after a batch's expectations are checked and before it commits, and to make the shared store unreachable or hold given nodes. Every adapter is run against the whole core group; the other groups run for an adapter that declares the capability. The model group compares an adapter with `volatile`.

Owed: memory.port.contract-suite

The operations' signatures, the domain key charset, the capability names and the limits are named in this document and written once, in code, when the port is built.

Owed: memory.port.protocol

Core, for every adapter:
- `get-absent`: a key never written reads Absent, and an empty value written reads Found with an empty value.
- `put-get-roundtrip`: values of length 0, 1, 255, a megabyte, every byte value, and bytes that are not valid text come back identical.
- `put-replaces`: a second write replaces the first, and the token changes with the value.
- `token-is-value-hash`: equal bytes under two keys have equal tokens, one changed byte changes it, and the token equals the SHA-256 of the bytes.
- `parts-are-independent`: writing one domain key leaves the node's other parts and other nodes unchanged.
- `parts-lists-keys-and-tokens`: `parts` names every key the node holds with its token and answers Absent for a node holding none.
- `expect-holds-pass-and-conflict`: an expectation on a current token commits; on a stale token conflicts, names that expectation, and leaves every part and label as it was.
- `expect-absent-pass-and-conflict`: an absent expectation commits for a never-written key and conflicts for a written one.
- `batch-all-or-nothing`: of three writes with the last expectation failing, or the second malformed, none is applied.
- `batch-malformed-refused`: an empty batch, a key written twice, an invalid domain key, a `labels` value unsorted or with a repeated id, and a batch over a declared limit are each refused with nothing applied.
- `batch-at-the-limits`: a batch at each limit the adapter declares, in writes, in bytes and in the size of one value, is committed, and a batch one over each is refused as TooLarge.
- `batch-answer-order`: a batch that is malformed and also holds a stale expectation is Refused, one with two failing expectations names the first in the order given, one with two expectations on a key is Refused, and one with a stale expectation on a node the adapter does not hold is Unavailable and not Conflict.
- `not-atomic-refused`: an adapter declaring `atomic_batch` false refuses a two-key batch and a one-key batch with an expectation on a second key, and commits a one-key write with an expectation.
- `batch-visible-whole`: while one thread commits batches that write two parts together, another reading them in one `get` call, in one `parts` call and by `scan` on a label the same batch sets, never finds them inconsistent, over 10,000 rounds.
- `concurrent-writers-no-lost-update`: N writers each add one to a counter part by reading it and writing with an expectation on the token, retrying on conflict, and the final value is N.
- `labels-set-and-scan`: a node with labels is found by `scan` for each and for any subset of them, not for an id it lacks, and not after its label set is rewritten without it.
- `scan-pages-complete`: paging with a small limit visits each matching id once while other ids are written, ascending and descending.
- `list-order-and-range`: ids come back in id order, the range is half open, `after` excludes its id, and descending paging by `list` and by `scan` with `after` set to the last id returned visits every id once and never repeats a page.
- `list-ignores-adapter-boundaries`: with ids whose instants are the Unix epoch, the instant before and after a month, a leap day, the turn of a year, the year 2100, and many ids within one second, any range and paging answers as the model does.
- `many-nodes`: 10,000 nodes are written in batches and read back by `get`, `list` and `scan`, equal to what was written.
- `id-form-refused`: 16 bytes whose version or variant bits are not those of a UUID version 7 are refused in a key, a label and an expectation.
- `domain-key-charset`: keys at the edge of the charset are accepted, and a key that is empty, has an upper-case letter, a hyphen at an end, a slash, a dot, a control character or 65 characters is refused.
- `derived-structures-droppable`: dropping every derived structure and repeating a sequence of `list` and `scan` calls changes no answer.
- `many-keys-one-pass`: for an adapter that reports `stats`, a `get` of 1,000 keys starts the same number of processes and opens the same number of files as a `get` of one.
- `read-inputs-refused`: a `get`, `parts`, `list` or `scan` with an invalid domain key, an empty `all_of`, a `limit` of zero or a `from` after a `to` is Refused and answers nothing.

Durable, for adapters declaring `durable`:
- `reopen-sees-committed`: after the store is closed and opened again by a new process, everything committed is there, with the same tokens.
- `kill-during-batch-is-atomic`: a child process commits batches each writing a pair of parts and a label, reports each commit on a pipe, and is killed at random moments, 200 times; on reopening, every batch the child reported is present, and every other batch is present whole or absent whole.
- `killed-writer-leaves-no-lock`: after the kill above, a new process commits without waiting for the dead one.
- `paused-live-writer-is-not-overtaken`: two writers hold the same expectation on one key and the first is paused at the commit point for 60 seconds; the second waits or conflicts, and exactly one commits.
- `unknown-fate-settles-first`: a batch made to fail at the commit point is answered Unavailable with the reason Failed, and when the pause ends the batch is not applied.

Shared, for adapters declaring `shared_between_processes`:
- `two-processes-lose-cleanly`: two processes write the same part with the same expectation; one commits, the other conflicts, and the store is readable.
- `one-process-sees-the-others-commit`: a call of `get`, `parts`, `list` and `scan` that begins after another process's batch returned sees it, including a label that batch set, whatever derived structure the first process held before.

Fallback, for adapters declaring `fallback`:
- `unavailable-is-not-absent`: with the shared store unreachable, a key of a node the adapter does not hold reads Unavailable and not Absent.
- `list-unavailable-is-not-short`: with part of the nodes unreachable, a range that covers them answers Unavailable, and a range that does not answers completely.
- `held-only-updates`: with the held ranges set by the seam, an expectation of a value on a part of a node outside them, and a write to one, are Unavailable with the reason NotHeld; an `absent` expectation outside them is Unavailable with the reason Unreachable until the shared store has answered; and inside them a creation commits without asking.
- `fallback-not-found`: a key of a node outside the held ranges, which the shared store answers is not there, reads Absent.
- `fallback-found`: a key of a node the shared store holds reads Found with the shared store's value as of the asking, and a read after the shared store's value changed reads the new value.

Working tree, for adapters declaring `leaves_working_tree_untouched`:
- `working-tree-unchanged`: after any sequence of the operations above, a listing of the project's working tree, its tracked files and its index are as they were.

Model, for every adapter:
- `model-equivalence`: random sequences of the five operations, from a recorded seed, give the same results on the adapter and on `volatile`, for at least 100,000 operations, the model built with the limits the adapter declares and the sequences kept within them.

### The view
A read-only folder built from a class's committed state, for a person's editor, is a consumer of the port and is specified in [Memory View](../view/view.md). The port offers it nothing beyond `get`, `parts`, `list` and `scan`.

### Adapters state themselves
Each adapter's module has a document that says, once: its capabilities and limits; where it keeps anything outside the store's medium; the derived structures it keeps and what invalidates them; how it meets each case; and what it cannot do. The `git` document states its first configuration, one reference or several, with the consequence of each for a batch that touches two, and what it does with a lock a killed writer left. It also states the plumbing it uses and the constraints that follow from the owner's ruling that git is a sink to be left: only `hash-object`, `mktree`, `commit-tree`, `update-ref`, `fast-import`, `cat-file --batch`, the read-only `for-each-ref`, `ls-tree` and `diff-tree`, `repack` and `multi-pack-index` (or the host's `git maintenance`) to keep the number of packs bounded, and `fetch` with an explicit refspec; no worktree and no index; a batch written as objects and made visible by one compare-and-swap of a private reference, never a worktree commit; references under a private namespace, fetched only by explicit refspec and never checked out; and the shard rule private (a prefix of the address; the 30-day window of the first design is a parameter of the adapter for a class of ids of version 7, not a rule of the contract).
