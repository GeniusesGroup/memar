## Decisions
Each is **Tentative**: taken by the design task so that the build tasks ask the owner nothing, open to the owner's ruling, and each says what changing it costs.
- **A node's id is a UUID version 7, and an id made from an old name is derived, never drawn.** [Label](../../../../../modules/knowledge/label/label.md#a-name-is-one-label) already uses the form. The layout: 48 bits of Unix milliseconds, the version, twelve bits zero, the variant, then 62 bits whose first two are the kind (00 a task, 01 a conversation, 10 any other node of a migrated task, 11 a node drawn at random) and whose remaining sixty are the first sixty bits of the SHA-256 of the name the id is derived from: for a task or a conversation its legacy id exactly as written, for another migrated node the task id and its role joined by a newline, the role being `request:create`, `content:<path>`, `text:<path>`, `blob:<path>` or `placement:<path>`, with the path relative to the task folder and written with forward slashes. The milliseconds are the instant the name carries, the legacy time times 1,000, and for a name that carries none the Start Date of its plan. A node drawn at random has kind 11 and random bits in all the rest, the twelve bits after the version included. Because the derivation is a function, a node is found by its legacy id with no index; the verbs accept the legacy text wherever they accept an id and print it for task nodes, which keep it in the field `legacy_id` of the `task` part; a new task is named by the tool as it is today and its node's id is derived from that name; and the kind keeps a conversation and the task of the same name apart. One function in the task module derives them, for every kind, and the migration calls it; legacy names are not renamed after the migration, so a node stays found by its legacy name, and the port requires nothing of an id beyond its form. Changing it costs every id.
- **`Lock` and `Unlock` are an optional capability of a store, outside the core operations; the declaration `Record_Model` becomes `Records` (owner, 2026-10-25).** The default control of concurrent writers is the expectation on a token. A store that can hold an address exclusively declares `lockable` beside `durable`, and offers `Lock` and `Unlock` built on the `Locker` of `modules/process/sync/` with a lease, so a holder that dies releases it; the contract suite gets a group for the capability. The name `Record_Model` named one record while the concept is the collection of records, and `Model` adds nothing: the collection is `Records`. `Storage_UUID` is `RecordUUID`. This replaces the first design's "no lock outlives a process", which was a design choice and not a necessity. Changing it costs the capability and its group.
- **The token is the SHA-256 of the part's bytes.** It is the same in every adapter and can be recorded in a Request. A value that returns to an earlier value returns to its token, which is harmless because a transition is guarded by the state it starts from and not by history.
- **The port has no removal.** The erasure rule is the owner's open question below. Contents labelled `temp` are therefore kept, and the view hides them. The cost is growth of the store without bound until the rule is made.
- **The port is blind to encodings.** The change plan said the port refuses invalid text; the design has the service that places a text run the text domain's check as part of the batch, so the port keeps opaque values ([Content → Checking text](../../../../../modules/knowledge/content/content.md#checking-text)). The effect is the same refusal.
- **The view is built above the port.** The change plan called building a view the adapter's duty. A view needs the path of a content and the text it points to, which are domain knowledge, so the builder works over any adapter through the port and a domain's declared presentation, and an adapter may offer a faster one behind the same verb. No service or agent builds a view of its own accord.
- **One place orders the writes.** A store has one writer location and a copy reads the shared store through its fallback but writes only what it holds, as [What every adapter guarantees](record.md#what-every-adapter-guarantees) says. Several users writing the same nodes is a design the port does not offer, and it needs its own: it is the first of the Anticipated Work below.
- **The first `git` configuration is one reference.** The change plan allows it and a later split into windows is a migration by id. A batch then touches one reference and its atomicity is one compare-and-swap; with several references, a batch touching two is not atomic against a kill in git's files backend, and the suite's case `kill-during-batch-is-atomic` decides. The adapter's document says which was chosen.
- **The migration is one creation Request per task, and no Status history is recovered.** The old logs hold events (opened, recorded, reaped, closed, renamed, moved, swept, blocked and released by dependency) and no Status values, so no Request chain of Status changes can be recovered from them. Each migrated task gets one Request that creates every one of its parts from absent, writing the Status its plan states, noted as migrated; a task's claim file becomes the holder and `claimed_at` in it. Names are made one per thing before ids are derived: the `renamed` lines of the log are applied so that a task is named by its current folder, every `Parent`, `Conversation` and `Depends_on` is resolved through them, and the several written forms of one name (`20261013T034406Z-30084-0` and `20261013-T034406Z-30084`) are normalized by a table the migration prints and `check_migration.py` compares for Conversation, Parent and Depends_on as well. A folder with no `plan.md` is a record of no task and is skipped, and the migration lists it. A migrated placement has the placer `unrecorded` and, for `placed_at` and `occurred_at`, the last write time of the file. A text that fails the check is stored byte for byte with the label `legacy-unchecked` by the legacy mode of the text function. What `archive` excludes (caches, binary files, files over 256 KB that are not documents) is not migrated, and a task's `temp` files are, minus those. Tasks archived on the records branch and absent from the working tree are migrated too, since the old layout is dropped.
- **No default adapter.** A class the manifest does not name is refused, naming the class and the line to add. Memar's own manifest gets `memory: work-records=git` when the adapter exists, and `sources=files` when that exists; the build task writes the line, because a line naming an adapter that does not exist would say what is not yet true.
- **The adapters are pluggable modules, and `git` keeps each class in a reference of its own.** Superseded in part on 2026-10-24: they stand at `modules-plugable/computer/memory/` beside `record`, not under it, and realize the memory contract ([Memory Handoff](../../../../../modules/computer/memory/memory.handoff.md#the-model-of-the-memory-layer-2026-10-24-decided-by-the-owner-in-task-20261024-t052936z-22844)); the rest of this entry stands. The adapter is named by its capability, `git-store` (the module `modules-plugable/computer/git` exists), so the manifest line is `memory: work-records=git-store` and its parameter, `git-store-reference` (written `git-reference` below and in the Brief of the build task, which the Addendum corrects), is written `class=reference` and defaults to `refs/memory/<class>`, so two classes bound to it never share a store. The owner's ruling that the adapter is chosen among the ways under `modules/computer/memory/` reads as the pluggable modules attached to the port, as the task asked.
- **The class of source files stays unbound.** The path-based services stay as they are, outside the port, until the files adapter exists; that is not an exception coded into the port or the task verbs.
- **An adapter may declare that it cannot apply a batch atomically.** It then refuses a multi-key batch as NotAtomic, which lets a files adapter exist without a silent non-atomic write; a class that records state changes refuses such an adapter when it is opened.
- **A reverse lookup is a scan by label.** A writer may attach the id of another node as a label, which gives the lookup of Requests by the node they changed and of placements by their timeline from the adapter's derived index, never committed.
- **Every committed batch is published to the shared store soon after it commits (owner, 2026-10-26; Tentative).** The owner asked whether the design says that each record written on a task reaches the shared store at once, now that there is no archiving step. It did not: the contract names a shared store only as a fallback for reading and says one place orders the writes, and the change plan keeps records in references that no command pushes. With the old folders, `archive-task-records` moved a task to the records branch; with the verbs re-based nothing moves a record off the machine, so a record written and not published is lost with the machine. The decision: a store that has a shared store declares the capability `replicated`; after a batch commits at the local compare-and-swap, the adapter pushes the reference by explicit refspec soon after, in the background, and keeps the last tip the shared store acknowledged in a private reference, so that "ahead of the shared store" is known after a restart. An unreachable shared store never fails or delays a batch; the push is retried, and the lag is visible through `state()` and a verb. A class's parameter `publish` says `now` (the batch is answered after the push) or `soon` (default). The suite gets a group for the capability. A write that must be ordered across machines, such as a claim, is not solved by this: it needs the shared store to be the writer location, which is the first of the Anticipated Work below. Changing it costs the capability, its group and the parameter.
- **A reference points to a commit per batch, not to a bare tree (owner's question, 2026-10-26; Tentative).** Git lets a reference outside `refs/heads` point to any object, so a commit is not required by git. It is kept for three reasons the contract needs: a fetch and a push negotiate by the commits each side has, so a reference to a bare tree makes every transfer resend whatever the other side cannot be shown to hold, growing with the store; the compare-and-swap of `update-ref` and the shared store's refusal of a non-fast-forward push both rest on a chain of tips, which is how a lost update is refused at the shared store; and `state()` is the tip and `changes(since)` is `diff-tree` between two tips. The cost is one small commit object per batch. Measured by [git-store Research 001](../git-store/git-store.research.001.md#findings) (task `20261026-T192807Z-36152`, local shared stores): after one more batch of one node, a push sends 647 and 669 bytes and a fetch 774 and 796 bytes at 1,000 and 100,000 nodes with a commit per batch, while with a bare tree a push sends 979 and 1,833 bytes and must be forced (git refuses an unforced push of a reference to a non-commit, so a lost update can no longer be refused), and a fetch resends the whole store, 68,423 and 6,992,144 bytes; a first, full transfer of a bare tree is about 2 % smaller. The numbers support the decision; it stays Tentative. Changing it costs the realization of `state()` and `changes`.
- **A heartbeat is not in the store.** No task has one; if one is introduced it is held in volatile memory with a lease, and the takeover of a lapsed claim is what a Request records.
- **Cutover is bounded and not a coexistence.** The task verbs read the store first and a task folder second until the migration's check passes and the old folders are removed, so that the queued tasks of the programme itself can still be claimed and read between the task verbs' change and the migration; the migration task then removes the folder path from the verbs.
- **The listing of ids is `nodes`, not `list` (build of 2026-10-26; Tentative).** `record` is a store of the contract over keys, so the contract's `list` answers keys and keeps its name; the first design's `list` of ids by existence instant needed another, and no abstraction of Memar names it. `nodes` is taken from this document's own word for what it answers, a node. Changing it costs one name in `record.py`, its cases and this document.
- **An adapter module offers `bind(project, class_name)`, and the adapter names its store as `store` (build of 2026-10-26; Tentative).** `open` must turn an adapter's name into an adapter for one class and must tell when two classes share a store; neither the store contract nor `conformance`'s `Adapter` (an object whose `open()` opens a store) says how a module is asked for the adapter of a class or what names the store it keeps. The decision: the module named by the capability, at `modules-plugable/computer/memory/store/<capability>/<capability>.py`, has `bind(project, class_name)`, which reads the adapter's own keys of the `memar:` block, does no work on the medium and returns an `Adapter` with a `store` attribute, any value whose equality is the sameness of the store (for `git-store`, the reference). `volatile`, which is kernel and no class's adapter, offers none. Changing it costs `open`, its tests and `bind` in each adapter.
- **`Needs` is declared in `record.py` (build of 2026-10-26; Tentative).** What a class needs of its adapter is stated in the contract's words (its capabilities and least limits) and checked by `open`, which returns `record`; the store contract declares no type for it. While `record` is the one capsule a class is opened as, the type is `record`'s; when another capsule is opened by class, it moves to `store/protocol/store.py`. A limit is met when the adapter declares none or one at least as large.
- **The contract's suite reaches `record` through a translation of its addresses (build of 2026-10-26; Tentative).** `conformance.py` makes its addresses from a store's parameters alone (`address(store, i)`), and none it makes for a store of any address length is a key, so the suite cannot run on `record` as it stands. `record`'s tests map each of its addresses to one key of a fixed id, whose domain key is `k` and the address in hexadecimal, which keeps equality and the byte order, and map the keys `record` answers back; addresses longer than 31 bytes have no key, and the suite makes none. The alternative, a way for an instantiation to give the suite addresses it takes, is a change to the conformance module and is not this capsule's to make.
- **`open` is written in `bundles/memar/services/memory/memory.py`, and the entry point declares it by one line (build of 2026-10-26; Tentative).** The entry point's docstring says it routes and nothing else, and its test `RouterNamesNoVerb` refuses a verb word (`project`, `add`, `list`) in any string or name it holds, which `open` cannot avoid; so `memar` binds `open` to that module's, and a service is handed the same function. Changing it costs one line and the module's place.
- **A task's Status is a field of the `task` part, holding the word of the Status vocabulary.** [Label](../../../../../modules/knowledge/label/label.md#a-name-is-one-label) says the values of Status are labels, which would let `scan` answer which tasks are queued; at this scale `claims` reads the `task` parts of the tasks in one call, and moving the Status to a label later is a change recorded like any other.

## Open Questions
### What is the retention and erasure rule, now that the port offers none?
- State: recorded in [Memory Handoff](../../../../../modules/computer/memory/memory.handoff.md#what-is-the-retention-and-erasure-rule-for-preserved-history-and-where-do-a-records-versions-live) before the port existed. The port has no operation that removes a part, a label or a node, and the git adapter keeps every object in history and packs, so a legal purge, a secret, or the contents labelled `temp` cannot be removed by any verb.
- Options: rule first, then add an erase operation whose contract case every adapter declares or refuses (recommended: the port's contract changes once, in the open); or let `git` rewrite history behind an operator verb outside the port, cost: an exception in the one door.
- Anchor: [What every adapter guarantees](record.md#what-every-adapter-guarantees), the bullet "Nothing is removed".
- Blocks: erasure and the disposal of `temp` contents. Assumption meanwhile: nothing is removed (Tentative).
- Asked: 2026-10-23, Claude (task `20261023-T074641Z-5420`), for Omid Hekayati.
