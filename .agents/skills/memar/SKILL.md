# Memar
This file holds only what is the agent's own: how an agent's runtime — its context window, its sub-agents, its tools — carries out work the Memar way. Memar's knowledge is in its documents, and how its tools are used is declared by `memar` and the tools it leads to; neither is repeated here. This file is not complete: what it does not say may still be in Memar, so look it up. Where this file disagrees with a document or with `memar`, the document or `memar` wins, and the disagreement is reported.

## Scope
Memar is the framework the work is conducted within ([Framework](/docs/framework.md)), not a library to consult. The work is usually the person's own project — not necessarily software — and [GeniusesGroup/memar](https://github.com/GeniusesGroup/memar) is its reference; do not assume the project is Memar. "Write this in Khayyam" engages this skill without the word Memar.

## Reaching Memar Server
Memar is reached by one of two routes.

- **The `memar` command.** Run `memar commands` once: it prints every command with its call shape and a line on what it is for, so no command is found by descending `--help` level by level; take one command's reasons and words from its own `--help`. Then `memar --help` says: it leads to opening the session, to finding, reading, and writing Memar's content, and to resolving a reference. Take each named thing's interface from that thing each time it is used, not from memory. Find and read content the ways it offers, in preference to resolving links by hand or reading whole documents. Resolve a link in this file that begins with `/` the way it offers, never into the folder this copy sits in nor into the project being worked on.
- **Where `memar` is absent**, read [Scripts](https://github.com/GeniusesGroup/memar/blob/main/.agents/scripts/README.md) and decide from it. If it cannot supply what the work needs, stop and say so.

## Consult the governing document before each act
- Each step reads, in this context and not as a delegate's summary, the passages that govern its act and its subject. What an act requires is declared once, by kind, in the lists of [Normative References](/modules/knowledge/content/rules/normative_references/normative_references.md), which owns that claim, and `memar` prints them: open a session with its act's kind (`memar content context --help` names the kinds), take it up with `memar session start --session-id ID --without-skill` (without the flag where the runtime has not loaded this file), and read every part it prints before acting. A question answered in chat opens no session: run `memar content context --kind answer` and read every part first.
- The trigger is the step, not the session. When the act changes — asking the human (`answer`), critiquing (`critique`), delegating or asking for a review (`plan`), or another kind than the plan's — run `memar content context --kind K --after K0 --session-id ID` (K0 each kind already read, ID the session: `--after` leaves out only what that session's record shows printed as it reads now, and is refused without it) and read what it prints first; after a compaction, without `--after`. Thinking runs in every step, and no step names it as its act: every kind prints its passages.
- A section printed marked `changed since reviewed` is read as it reads now, and the report's Left open says `<list>:<line> changed since reviewed; read as it reads now`. An entry printed marked `anchor gone` names a section that is not there: search for its label (`memar content find`, or `memar content search` for where a term occurs), read the section judged to be the one meant, and say under Left open which was read, or that none was.
- A subject is not a kind: its governing documents are found by searching, with `memar content search` for where a term occurs and `memar content find` for the sections most like the subject (informative only: it ranks by word similarity and binds nobody), for the subject's term and each other term the step uses, `docs/` hits first; read the governing document it surfaces at the section that governs the step, and follow its links where the act depends on them. A subject that enters the work midway is consulted when it enters. A step on a Khayyam construct reads this way [Khayyam](/docs/khayyam/khayyam.md#abstract)'s Abstract, [Separation of Syntax and Governance](/docs/khayyam/khayyam.md#separation-of-syntax-and-governance-a-principle), and [Minimal Legislation](/docs/khayyam/khayyam.md#minimal-legislation-a-principle).
- Read each as [Reading guidance](/docs/README.md#reading-guidance) says, and act from the section that governs the act — not from memory, from training, or from this file; the act's own document says what has to come before it. Where it links a Practice for the act, do the act as that Practice says. A proposal that departs from a passage cites it.
- Where the search finds nothing, proceed as [Cognition Practice → Norm Application Points](/docs/cognition.practice.md#norm-application-points) says for a lookup that matches nothing.

## Session and plan
- Before any other work, open a session through Memar ([Reaching Memar Server](#reaching-memar-server)) with the kind of its act ([Consult the governing document](#consult-the-governing-document-before-each-act)) — or, when your brief hands you one, take that one up and open none — and keep all scratch in its folder — not the OS temporary directory nor a runtime's scratch place.
- A session exists so that a task's decisions outlive the context. A task whose outcome is just that it was done — committing, staging, a rename, one edit, a lookup, a handful of tool calls — opens no session and starts no sub-agent: do it in place. Opening a session or a sub-agent costs a plan, a brief, a start reading and a report; spend it only where a later session would need what was decided.
- One session holds one task, and its plan holds that task's own acceptance check; a further task — another request, or one delegated — gets a session of its own, linked to the session it came from. A conversation is not a task: one conversation holds several sessions, and a question answered in chat opens none. A session names its project with the flag for what it has — `--project NAME` for a name, which `memar project find` resolves, `--project-path PATH` for a folder — never one in the other's place, and a name told by a word is never reasoned about nor turned into a guessed path.
- A session is for work to be done: its acceptance check is a change applied or a decision recorded. A request to investigate and apply nothing opens no session; the investigation is the first step of the session of the work it improves, and its finding revises that plan, or it is a question in the handoff of the document it concerns, or a Research facet file where it meets that facet's criterion ([Research](/modules/knowledge/documentation/research/research.md)). A proposal waiting for approval leaves its session Blocked, never Complete. The rule is [A session is for work](/modules/knowledge/documentation/handoff/handoff.practice.md#a-session-is-for-work); it is not restated here.
- Add nothing new to Memar's session, commit, or host tooling unless it is indispensable, and say in one line why; the owner holds git to be a sink to be removed, and the session id in a commit message stays as it is. Memar's session is not developed further: organization's Task replaces it, and what exists is kept, not built on.
- Judge a step by what its development costs over the whole work, rework it prevents included, not by the tokens of its session alone.
- A runtime's to-do list or plan mode is not the session's plan: it ends with the context; the plan outlives it.
- Intake binds before work ([Cognition Practice → Norm Application Points](/docs/cognition.practice.md#norm-application-points)) and ends in the written plan, made before reading the material the work is about. Decide each step in it local or delegated by the test under [Delegation](#delegation); a step the plan did not foresee takes the same test before it starts.
- Each step in the plan names the paths of the governing documents it reads ([Consult the governing document](#consult-the-governing-document-before-each-act)) and of the tests it adds or runs; a step that names no document cannot start.
- The coordinating session runs on the strongest model the runtime offers for judgment, not the smallest one: writing the plan and its critique run on the strong tier; a small model runs only the mechanical steps — search, count, moves — after the plan is written and reviewed. A delegated step of ideation, design, or critique runs on that tier too: name the model explicitly when starting its sub-agent, since a runtime's default may be weaker; a sub-agent given such a step on a weaker model ends Blocked, naming the model it runs on.

## Context window and compaction
- After any compaction or summary of the context — announced or not; a context that opens with a summary has been compacted — re-read this file and the session's plan, and run `memar content context` for the current act's kind without `--after`: a summary drops rules and decisions that still bind. What was read before a compaction and not since is unverified reading ([What Implementation Asymmetry Obliges](/docs/cognition.md#what-implementation-asymmetry-obliges)).
- The session's context is a budget as well as each step's: tool output, reports, and the conversation accumulate across steps that each passed the test. Ask a command for the least output that answers — a test run's summary line, a diff's stat.
- Once the context is past about half the window (reported or estimated), take no further step locally: hand what remains of this session's task to a new chat on a session linked to this one, or delegate it where [Delegation](#delegation) allows a sub-agent.
- A prompt cache reuses only an unchanged prefix, and it lasts about an hour. So the skill, the context its kind printed, and the plan stay unchanged within a session; a new session, or a changed prefix, pays the whole context again. Keep a task's work in its own session rather than extending a long one.

## Blocking and independent sessions
- A session this chat creates, or finds queued, that the chat's work cannot go on without — a step still to come reads its Result, or its Result could change the plan — is a blocking session. The coordinator lists it in the `Depends_on` of its own plan (`memar session depends-on ID --add BLOCKING`), sets that plan Blocked, and tells the owner at once that the work waits ([Queued Work and Its Hand-Back](/modules/knowledge/documentation/handoff/handoff.practice.md#queued-work-and-its-hand-back)).
- Where a session runs is decided by two questions about it: does this chat need its result, and does it need the owner (questions, critique, back-and-forth)? A session this chat needs the result of, that needs no owner, is carried out by a sub-agent, which returns only its hand-back ([Delegation](#delegation)): no new chat, since the chat that needs the result reads it either way and a sub-agent costs it only the hand-back. A session that needs the owner, whether or not this chat waits for it, is carried out in a new chat: with the present agent apps a chat that takes in several sessions' reading and its questions and answers with the owner grows past 500K tokens, and every later turn pays for all of it.
- **A new chat is never the way to reach a stronger model, and a session whose result the coordinator reports is a session it needs the result of.** The runtime's tool that starts a chat gives the new chat at most the coordinator's own model and ignores, without refusing, a request for a stronger one, so a research, design or review session that needs the strongest tier the coordinator is not running on is a sub-agent with the model named, never a new chat. This holds whatever the session is called and whether or not the owner asked for it by name: the test is only whether the session needs the owner during its work. A step the owner asked to be researched and whose answer the coordinator then brings back is such a session; a new chat is for a session that needs the owner, or whose result no step of the coordinator reads.
- To open a new chat, where the runtime has a tool that starts one, the coordinator starts one per session, hands it the text `memar session hand-session-plan-to-carry-out ID` prints and nothing else, and shows the owner `memar session ask-for-new-chats --coordinator ID ID...`, ID the coordinator's own session, which marks as blocking the sessions its `Depends_on` cites. Where it has no such tool, it prints that text and says in one line that it cannot start a chat. For blocking sessions it also says that it cannot learn by itself that those chats ended, asks the owner to tell it when each of them is done, does only the work no waiting session touches, and ends its turn when none is left.
- A session whose result this chat does not need — a requirement found on the way, such as B found while developing A — is independent: this chat creates its session with the whole plan, opens its chat (or lists it for the owner to open) so it runs in parallel, and is then done with it: it does not track the session's interactions with the owner, its result, or when it ends. Two that change the same files are listed as one after the other. The coordinator says how many chats it opened.
- The coordinator resumes when the owner says a session is done, or when `memar session list` says that every session its `Depends_on` cites is Complete and it can resume. It reads `memar session show --session-id ID --hand-back` — Status, path, `Decisions needed` — and no more of the report unless a step names a part; a session that is not Complete, or that holds decisions, goes to the owner before the plan goes on. A blocked chat consumes the decisions made and does not re-enter their reasons, unless its own work meets a problem.
- A problem found later in a finished session's work goes back to that session's chat with a prompt that states the problem and the new ask, not to a new session; a new session is for work that is new in itself.
- A chat started for a session is that session's coordinator: it takes this skill, the session's Closing, and these same bullets for what it meets.

## Delegation
- Delegate a step, with its acceptance check, when what it reads would take a large share of the context and the session needs only its conclusion — measured in bytes, not in files — or when it reruns a script until it comes out clean; keep only the report. Measure before reading; about 20 KB of output or of a single file, and about a quarter of the window for a step's whole reading, are the working marks, not laws. How large a task is, and when tasks are split or merged, is set by [Sizing a Task and Recording Follow-Ups](/modules/knowledge/documentation/handoff/handoff.practice.md#sizing-a-task-and-recording-follow-ups); read it before splitting, merging, or queuing work. The sections this file links and the passages a report cites, read at the cited lines, do not count; nor does what `memar session start` and `memar content context` print, whatever its size: it is read whole, every part, in this context. A step that crosses the line midway is delegated from there.
- A sub-agent is used for a session whose result this chat needs and that needs no back-and-forth or critique with the owner ([Blocking and independent sessions](#blocking-and-independent-sessions)), and for a read-only or mechanical step; it returns only its hand-back (Status, path, at most ten lines): it writes its report.md and its final text is that hand-back, never the report. Sub-agents run one at a time, each to its end, unless the owner asks otherwise: several at once spend the owner's usage limit together and are all cut off midway, leaving half-made edits; and a sub-agent starts no sub-agents of its own.
- Editing a file exempts no step: an edit that carries out a decision already taken — code and its tests, a document change whose content is settled — is delegated by the same test, and only an edit that is itself the decision stays local.
- Keep local the target's structure — built from reports, not from a survey — the decisions over findings, and the merge. Judgment exercised while producing a finding is delegable with its criteria, so calling a step judgment never keeps it local.
- Do not delegate work whose intermediate context is the deliverable, or work that needs the session's decision between its steps; where such work exceeds the size test, split it at those decisions and delegate the parts between.
- A tangent the session will not otherwise need is not a step to delegate; it is handled per [Mid-session tangents](/modules/knowledge/documentation/handoff/handoff.practice.md#mid-session-tangents).
- What a delegation must establish: [Interaction With an Agent](/docs/agency.md#interaction-with-an-agent).
- A runtime that starts a sub-agent as a fork of this context at a marked point, not as a cold start, changes what a delegation costs; Memar's expectation of it, and what this section does until a runtime offers it, is [Forked Sub-Agent](/modules-plugable/process/forked-subagent/forked-subagent.md).

## Sub-agents, briefs, and reports
- A sub-agent's first command is `memar session start --session-id ID` (the brief says so): it prints the plan, this skill, the passages the plan's Kind requires, the documents the plan's Steps name and the help of the commands it names, in ordered parts when too long for one output, and says which model tier the plan's Kind needs. A sub-agent loads nothing before it and reads every part. A read-only step takes no development or modeling act, so beyond what `start` prints it reads only what its step needs.
- A sub-agent starts with none of the session's context: what its session's plan does not carry, it does not know. The delegating session opens the sub-agent's session itself, linked to its own, and writes the whole task into that session's plan.md — the paths and passages to judge, the criteria, the acceptance check, and the report shape, restating no rule — then hands the sub-agent only the brief that opening the session prints (`memar session hand-session-plan-to-carry-out ID` prints it again), the same text for every sub-agent, to which nothing is added: what else it needs is in the plan, and its `TaskKind` label (`--label TaskKind=K`) says the model it needs. The sub-agent does not rewrite the plan's Request; its report.md is read against the plan's check. The sub-agent declares unverified reading and context limits per [What Implementation Asymmetry Obliges](/docs/cognition.md#what-implementation-asymmetry-obliges).
- A sub-agent that may write files writes its report.md; one that may only return text returns the hand-back and nothing else, and the delegating session writes the report.md it can from it, marking what it could not. A delegated step is done only when its report.md exists.
- Start a new sub-agent rather than resume a long one.
- Sub-agents running at the same time write disjoint files, or write a shared one only through Memar's writing tool.
- A report is a claim: read the passages it cites at the cited lines before building on it ([Treat shared artifacts as claims](/docs/cognition.md#treat-shared-artifacts-as-claims-under-the-same-evaluation-not-as-absolute-authority)). Keep each report in the session folder for the [debrief](/docs/cognition.practice.md#debriefing-runs).
- Each pass, local or delegated, has a finite boundary, the same acceptance check, and a named end, the Status its report states: Complete, Blocked, or Active ([Status](/modules/knowledge/documentation/documentation.md#status)). Errors and exhausted budgets are never reported as Complete ([Acceptance Criteria](/docs/agency.md#acceptance-criteria)).

## Reviewers
- Ask for a critique or approval as [recording an approval](/modules/knowledge/documentation/changelog/changelog.practice.md#recording-an-approval) says. In this runtime the reviewer is a newly started sub-agent that has not seen the work — never the session itself, nor a sub-agent resumed from the work — preferably on a different model from the session's where the runtime offers one ([choosing who reviews](/modules/knowledge/documentation/changelog/changelog.practice.md#choosing-who-reviews)).

## Asking the human
- Ask as [Cognition Practice → Norm Application Points](/docs/cognition.practice.md#norm-application-points) says — what to settle first, and the shape of the question; an act beyond the instance is confirmed first ([Confirm before large-scope changes](/docs/cognition.md#confirm-before-large-scope-changes)).
- Before a coordinator brings the owner a question — a line under a report's `Decisions needed`, its own written there first — it hands it to a newly started agent on the strongest model with the text `memar session hand-session-questions-to-answer ID` prints, the same for every session, nothing added; that agent's first command is `memar session answer-session-questions`, not `start`, and it opens no session, writes nothing, and returns its answers as text: what it is sure of is recorded as Tentative with its reasons, and only what it is unsure of, or what reaches the owner however settled, goes to the owner.
- A question only the owner can answer, found during a task, is written as an entry in the handoff of the document it concerns ([Questions Found During a Task](/modules/knowledge/documentation/handoff/handoff.practice.md#questions-found-during-a-task)); the conversation and the report hold at most a pointer to it, and recording a question never needs a session of its own. A question about this skill or Memar's scripts is the exception that section names: it is queued at once as a session that studies and decides it.
- When the runtime's sandbox or permissions refuse a command, report the refusal or ask for the permission; do not reach the same act by another route.
- A sub-agent has no human to ask: what it would ask, it ends on as blocked or approval-required, with the question stated, and the session that delegated it asks.

## Closing
- Before ending work on a task — finished or not — write its session's report, with its Status, and set its plan's Status to agree, as `memar session --help` says: a session left Active after its check passed reads to every later session as work still owed.
- Commits follow the whole piece of work, not each session or chat: a chat started for one session of a larger work leaves its changes uncommitted and says so in its hand-back, and the chat that holds the whole work commits once, after the human approves; sub-agents never commit. That commit names every session the work carried out, each by its id with `--session-id` of `host/git.py commit`, which refuses a commit that names none unless it says it carries out none ([Scripts → Deleting, moving, restoring, and committing](/.agents/scripts/README.md#deleting-moving-restoring-and-committing)).
- Run `memar content check` on the files the task changed **before** the commit, not only after it, and make the commit only when it reports no problems. The reason is the cost of a late finding: encoding or newline damage, a broken link and an undischarged propagation that reach history can be removed only by folding another change into the commit, which rewrites history the task's records already cite; found before, each costs one edit. A check after the commit finds nothing a check before it would not have, except what changed in between.
- Each commit has a cost: history to read, to review and to fold. Commit by area — usually the top folder a change lies in (`.agents`, `docs`, one module) — a few commits for a large batch, not one per topic or per file. Split an area only where two changes would be reviewed or reverted apart. Staging, grouping and committing a batch is done in place, from `git status` and `git diff --stat`, never delegated.
- Close by type per [Handoff Practice](/modules/knowledge/documentation/handoff/handoff.practice.md), each durable result in the home [Results routing](/modules/knowledge/documentation/documentation.md#results-routing) gives it.
