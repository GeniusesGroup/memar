# Memar

## Purpose
This skill defines how an agent discovers and applies Memar (and its sub-projects, including Khayyam). It does **not** duplicate project documentation: for duplication versus linking see [Documentation → Content Rule](/docs/documentation.md#content-rule-no-fabricated-or-redundant-provenance). This skill only explains how to find, navigate, and use that knowledge.

## Scope
Memar and Khayyam are meant to be *used*, not only maintained. Most people who trigger this skill are working on **their own** project — code, hardware, an organization, etc. — and want Memar's approach. Treat `GeniusesGroup/memar` as **reference documentation**; do the actual work in the person's project. Do not assume that project *is* Memar, do not assume it is software, and do not wait for the word "Memar" — phrases like "write this in Khayyam" are enough.

Memar is the **framework the development is conducted within**, not a passive library. For what a framework is see [Framework](/docs/framework.md). This skill stays loaded while work is conducted within it.

## Separation of knowledge
1. **Repository documentation** — the source of truth: the facet system of [documentation.md](/docs/documentation.md) and the protocol contracts of [protocol.md](/docs/protocol.md), living in [`docs/protocols/`](/docs/protocols/). For where state worth persisting goes, see [Documentation](/docs/documentation.md) and [Protocols](/docs/protocols/README.md); for procedure, see the facet Practice. This skill enumerates nothing.
2. **Agent configuration** — how *this* agent, with *its* tools, discovers and applies the above. Organizational ways of working belong in the repository's Practice-facet documents, never here; only tool-dependent content lives in this skill.

## Working rules
- Before reasoning about ideas, architecture, modeling, terminology, or critique, read [**Cognition**](/docs/cognition.md) and follow [its discourse norms](/docs/cognition.md#discourse-norms-derived-from-this-model).
- Before enacting any development step, read [**Test**](/docs/protocols/process/test.md) and follow [Test Practice](/docs/protocols/process/test.practice.md) for the procedure.
- Before enacting work that commits to a module, read [**Modeling**](/docs/modeling.md#modeling-before-implementation) and follow [Modeling Practice](/docs/modeling.practice.md#the-modeling-workflow) for the gate.
- For documentation — finding, reading, writing, retiring a thread — heed [Documentation](/docs/documentation.md) and the facet Practice: [Documentation Practice](/docs/documentation.practice.md) for procedure, [mid-session tangents](/docs/documentation-handoff.practice.md#mid-session-tangents) for live threads. Discover from the repository and read only what the task needs ([No derivative inventories](/docs/documentation.practice.md#no-derivative-inventories)).
- Text reaches a file through a file-write tool or through `memar content` — `write`, `edit`, `check` — never through a shell's own text handling. Why a shell damages the files it reads is in [Scripts → Putting text into a file](/.agents/scripts/README.md#putting-text-into-a-file).
- For load-bearing terms follow [Terminology Authority](/docs/terminology.md#terminology-authority-and-governance); general domain background is fine, Memar behavior invented from it is not.
- For protocols versus implementations see [Where implementations live](/docs/protocols/README.md#where-implementations-live).
- Canonical repository: https://github.com/GeniusesGroup/memar

## Agent workflow in sessions
This section is agent-specific (tool-dependent), so it lives here rather than in a repository Practice. Norms live in [Cognition](/docs/cognition.md) and the facet Practices ([Agency](/docs/agency.md) for acceptance only); this section states only what varies by runtime — session container, delegation mechanics, reviewer identity.
- Begin every shared-tree session with `memar session new` and write only inside the folder it prints — reading another session's folder is fine — and never spend a message asking anyone to close one — `memar session --help` says when a folder is closed. That folder is the only scratch: no OS temporary directory, which other applications wipe while a session is still alive.
- An act that cannot be undone is not an act to take. A file that holds work is never deleted for good: move it to the platform trash through [`host/fs.py`](/.agents/scripts/host/fs.py), and move a tracked path through [`host/git.py`](/.agents/scripts/host/git.py) so the history follows. If those are not at hand, stop and say so. Do not fall back to the host's own delete or move. That shelf is deliberately not under `memar`: it constrains the host's tools, which is not a thing Memar offers.
- Treat intake as binding before work; for checkpoints and question shape see [Cognition Practice](/docs/cognition.practice.md#norm-application-points). For what a delegation must establish see [Interaction With an Agent](/docs/agency.md#interaction-with-an-agent).
- Keep local what requires the session's held model — target structure, judgment, final merge. Delegate what is bounded and answerable: exploration whose raw material the session will not need after integration, a second opinion on a deep claim, and the independent review an `approved` tag requires.
- Do not delegate work whose intermediate context is itself the deliverable, or work needing continuous back-and-forth judgment; delegation is lossy and has coordination cost. A tangent the current session will not otherwise need is not delegation — handle per [Mid-session tangents](/docs/documentation-handoff.practice.md#mid-session-tangents).
- Brief a sub-agent in one short clause: name this skill and say to load it first, name paths plus the passages it must judge, state acceptance criteria and the structured report shape. Do not restate this skill's rules in the brief; do not carry a content dump. Treat context exhaustion as the signal that triggers delegation; declare unverified reading and context limits per [What Implementation Asymmetry Obliges](/docs/cognition.md#what-implementation-asymmetry-obliges).
- Before asking the human who started the session, exhaust what agents can settle: re-read the owning documents, delegate bounded discovery to a sub-agent, and seek critique from another sub-agent, preferably a different model. Bring the human only what survives, with what was tried; the main session holds the review and merge.
- Execute delegated and local work the same way: finite boundary, same acceptance check each pass, named stop (success, clean no-op, blocked, approval-required, exhausted, no progress). Errors and exhausted budgets are never reported as success. For what acceptance is see [Agency → Acceptance Criteria](/docs/agency.md#acceptance-criteria).
- Request critique and review with the same four things: the claim quoted, the evidence (command to run or passages to read), the boundaries not to consider, the verdict asked for. Read either verdict as a finding, not as a gate; do not re-ask the same reviewer after material change. Procedure per [recording an approval](/docs/documentation-changelog.practice.md#recording-an-approval); only the reviewer's identity per [choosing who reviews](/docs/documentation-changelog.practice.md#choosing-who-reviews) is runtime-dependent.
- Prefer a **new** sub-agent with a short brief over **resuming** a long prior sub-agent thread: resume replays that thread's history into the bill again. Name needed sections by path and anchor per [No derivative inventories](/docs/documentation.practice.md#no-derivative-inventories).
- Close by type: decisions and open state into the per-topic handoff, observed changes into the paired changelog, stabilized conclusions graduated into the governing document. Preserve each delegation's report (what ran, the check, the boundary, the stopping reason) beside the session; the debrief reads them, not memory. See [Handoff Practice](/docs/documentation-handoff.practice.md) and [Documentation Practice](/docs/documentation.practice.md).

## Content navigation
Reach Memar's content through **`memar`** first, by that bare name. Run `memar --help` for what Memar is and what it does, and `memar <verb> --help` for one verb's interface; each tool declares its own, and this document does not repeat them.
- `memar content` is the whole of Memar's written content under one word: the model definitions, the rule catalog, the protocol implementations and their sources, and the configuration a session is driven by, as well as the documents under `docs/`. `memar content --help` lists what it holds. "Documentation" is the narrower word and it is not the boundary here — a reader who treats it as one looks in `docs/` and concludes the rest was never written.
- Where the command is not installed, run `python $MEMAR_ROOT/.agents/scripts/memar-content.py --help` from a Memar checkout instead.
- Where no checkout exists on the machine, fetch the bootstrap first — `https://raw.githubusercontent.com/GeniusesGroup/memar/main/.agents/scripts/install.sh` on POSIX, `https://raw.githubusercontent.com/GeniusesGroup/memar/main/.agents/scripts/install.ps1` on Windows — and run it with `--help` (`-Help` on Windows) for its interface. It clones the repository and then hands the run to the installer, whose own `--help` declares what a bare `memar install` settles: the machine, the project it is run from, and the agent apps. Inside a checkout the command finds the repository it is in and the variable is not needed. The skill copy a consuming project holds carries no scripts beside it.
- The `/docs/...` paths in this skill resolve inside a checkout or through `memar` — never as files beside this copy.
- When passing a document to that tool on shells that rewrite a leading `/` (Git Bash/MSYS), pass a bare repo-relative name (`docs/cognition.md`). Prefer the tool to hand-resolving document links or reading whole documents.
- If Python is absent, install it, then read the script source for the needed step only; inventing a parallel recipe catalog here is not the fallback.
