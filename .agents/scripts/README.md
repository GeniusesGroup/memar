# Scripts
Executable helpers for recurring host-tool work where Memar sessions need a constraint free-form shell habits keep violating. A need earns a file here when it is worth a small script with a stable interface, and when it serves one of the kinds below — as the entry point, as one of the concerns that entry point asks rather than repeats, or as the suite that checks them; a need that serves none of them does not belong here. Each file in this folder documents itself, and each of those declarations is the authority: `-Help` for [`install.ps1`](./install.ps1), and `--help` for [`install.sh`](./install.sh) and for every Python file that has a command line, and each Python module's own docstring for what it provides and how it is invoked. A module with no command line declares no help, because it is reached by an import rather than by a command; this document does not repeat a name, path, command, or default a script already declares — where a reader needs one of those, the script is run or read, not this page. Discover what exists in this folder by listing it: the grouping below states a criterion, not an inventory ([Documentation → Content Rule](../../docs/documentation.md#content-rule-no-fabricated-or-redundant-provenance)).

Installation and location material lives here rather than in the entry document, because all of it is about these files.

## How a file is named
A name in this folder states its domain before its subject: the surface the file acts on, then what it does on that surface. A bare name that is only a role or a mechanism — a lock, a target, a decision about what a copy leaves out — states no domain at all, and a reader who has just listed this folder is owed one; the domain comes first because that is what says whether the file is worth opening. One domain carries one prefix and several files may sit under it, while a domain with a single file is named by the domain alone.

The boundary between the two is the hyphen, as [Documentation → File Naming](../../docs/documentation.md#file-naming) sets it for the rest of this repository, and a file Python imports as a module cannot carry one: a hyphen is not a legal module name. Which form a name takes is therefore settled by how the file is reached rather than by taste — one that is only ever run is hyphenated, and one that a sibling imports states the same two parts with an underscore in the same domain-first order, because that is the form the interpreter accepts. The underscore elsewhere in this repository joins the words of one term, so in an imported file's name the boundary is carried by the order of the words rather than by the separator; the words are the same either way, and no file here is made loadable by a trick that would let a hyphen stand. Which is which is discoverable from the file itself: a command line is how a run-only file is reached, and an import of a sibling is how the rest are.

## Three kinds of file
**Installing Memar — onto a machine, then into a project.** [`install.ps1`](./install.ps1) on Windows and [`install.sh`](./install.sh) on POSIX are the bootstrap, and they are only a bootstrap: each makes sure git and Python are present, then obtains a git checkout — the repository is a checkout, so obtaining Memar is cloning it, pulling one that is already there, or using one this run is already standing in — and runs the installer from that checkout, with its siblings on disk beside it. Nothing of the set is fetched file by file over the network and nothing is run from memory, because a program that had one file alone would have no siblings to import. Neither decides anything about Memar, least of all whether a folder is one: the test for that is the one the installer asks. [`install.py`](./install.py) is the installer and the resolver, and the one place that decides: what a Memar repository is, what the location variable says, and what to do when it says nothing usable. It also settles what a machine has besides the checkout — the desktop shortcut, and the editor extensions that checkout ships, copied in under the names their own manifests give and written over the copy a previous run put there, so the editor follows the checkout rather than the first version of it. An extension without Memar resolves nothing, so it is part of this step rather than a separate errand; when extensions reach a marketplace, that step becomes a network install into somebody's editor and must be asked for rather than done silently. [`install-agents.py`](./install-agents.py) installs Memar into a project, and [`install-apps.py`](./install-apps.py) copies the skill into the agent apps it detects.

**Navigating Memar's documentation.** [`memar-documentation.py`](./memar-documentation.py) resolves, reads, and searches the doc set: one reference, one section, a regex search across the explanatory surface, a changelog entry appended. It is not carried beside the Memar skill: it is general-purpose, so it lives here and the skill names this folder.

**Constraining an operation a host tool already offers.** [`fs.py`](./fs.py) and [`git.py`](./git.py) exist for the constraints a session would otherwise improvise past — recoverable deletion, history-preserving moves, a guarded restore — not for the capability, which the host tool already has.

The Python files in this folder import each other directly, and the run of the installer is the one that settles where those imports are answered from: a file on disk inside the checkout the bootstrap obtained, beside the file that imports it. What that buys is one implementation of each concern: the sibling a file imports is the one on disk in the checkout the run is in, and a bootstrap does not assemble a second copy of the set to answer an import. What a bootstrap does *not* do is ask a peer's question itself: whether a folder is a Memar repository is asked through the module that holds the test, so a shell cannot answer it differently from the installer.

## Putting text into a file
A file's encoding and line endings are decided when it is written, and on Windows they are decided by whatever shell does the writing. `memar-documentation.py` carries the three subcommands that decide them instead: `write`, `edit`, and `check` — read them from its `--help`, which is this folder's authority, and prefer them to any shell's own text handling.

The reason is specific rather than general. A shell that reads a file without being told its encoding will fall back to the console codepage when the file carries no byte-order mark, and a document that is correctly encoded carries no mark — a mark would become part of the first line for every tool that reads the file as text rather than as bytes. So the files this repository cares most about not damaging are the ones such a shell cannot read, and a read-then-write round trip through one loses every non-ASCII character it contains: an em dash, an arrow, a right single quote, a Persian word. The result is still valid UTF-8, so nothing downstream reports an error, and the damage is discovered by a reader rather than by a tool.

`check` exists because the damage is otherwise invisible, and it reports what can be known: a byte-order mark, invalid UTF-8, a replacement character left by a decoder that substituted instead of failing, mixed line endings, the fingerprints of a mis-decode, and for Markdown the written-surface rules and the links the document makes. Mojibake cannot be detected exhaustively, since it is still valid UTF-8, which is why the command is shaped around never producing it rather than around finding it.

A link is judged in both halves, because both break the same way and moving a document breaks both at once: the file the link names, and the heading inside that file. A relative link is the only kind judged — one with a scheme, and one written site-root, name something this run cannot resolve, and are left alone. The links inside code spans and fenced blocks are text about links and are read as none. What a check cannot do is tell a broken link from a link that was always meant to name something that no longer exists; a changelog entry citing a document that was deleted is reported like any other, and deciding it is a call about history rather than about the tree.

A file that checks another file in this folder is not beside what it checks and is not another angle on it: a check states the expectations of a process, and the installer's process is not its file. Such a file therefore goes in a `tests/` folder inside the folder that owns what it checks, named for that subject and carrying no marker, per [Test Placement](../../modules/process/test/rules/test-placement/test-placement.md) and [Test Naming](../../modules/process/test/rules/test-naming/test-naming.md). The folder states the role, so the name does not have to, and every file in this folder stays a file this folder is for. Nothing here depends on that arrangement, and a script that wants its checks run asks for them the way it asks for anything else here.

## A consuming project receives no copy of these files
[`install-agents.py`](./install-agents.py) writes what a project's instructions are read from: a one-line `## Memar` section in its `AGENTS.md` naming the file to read, the substance in the `.agents/memar/README.md` that line points at, and the index of the folder they sit in when the project has none. It places no script there and no Python file anywhere in the project, and `update` does not add one later. The bootstrap for the machine is fetched from this repository at the point of use, and that README says so in full: a copy per repository is unmaintainable, because it goes stale on every change here and re-reaching every project by hand is the only way to update it. One fetch, one update, every consumer.

The same rule holds for the skill: [`install-apps.py`](./install-apps.py) copies the skill document, not the scripts it names. A consumer that wants these files on disk clones this repository and points the variable at the clone; it does not receive them second-hand through another project or another app's skill folder.

## Getting Memar into a project
From the project you want Memar in, a subdirectory being fine, run [`install-agents.py`](./install-agents.py) for [AGENTS.md](https://agents.md/) instructions and [`install-apps.py`](./install-apps.py) for the skill in the agent apps it detects. Both are run from a Memar checkout, with their neighbours beside them; neither needs a clone of this repository beyond that, nor a local IDE. Refreshing an install instead of creating one is a variant of the same call rather than a second procedure, and each script's help names it.

A web chatbot is still an agent-app target, with a weaker interface: only if that app lets you add a skill, and only as a skill file or pasted text. No script covers that case, because a script can only write where it can see; the folder to hand it is [`../skills/memar/`](../skills/memar/). Check that app first. Workspace and local agent apps are the better fit — Memar adds substantial cognitive load to the process and is not equally appropriate in every interface.

Memar is a development framework, not a host-tool plugin: its model lives in `docs/`, so what a host tool could install from this repository is the agent configuration under [`.agents/`](../), not the model.

## Where Memar lives
One environment variable, **`MEMAR_ROOT`**, holds the path of a Memar checkout on this machine. The installer writes it for the current user and prints what it wrote and where, on whichever platform reached it; everything that needs Memar reads it through [`install.py`](./install.py), and nothing guesses a location or keeps a second copy of the repository. Which folder an install lands in by default, the modes offered for naming a folder or reusing one that already exists, and the check that refuses a folder which is not a Memar repository belong to the installer and to the bootstrap that runs it, and their own help declares them.

Run the bootstrap for your platform with no arguments to take the location it chooses, or tell it where Memar should live. With no arguments and Memar already registered, the run it starts says where Memar is and stops, so re-running costs nothing; naming a destination is a deliberate act and is carried out. Because a running program does not read a new value, the run names the programs that must be restarted — that reminder belongs to the moment it matters, which is why this page does not repeat it.

A session that finds `MEMAR_ROOT` unset is not left with instructions to follow: the bootstrap is one command, and the README beside a project's `AGENTS.md` pointer carries it. What the variable says is asked of [`install.py`](./install.py), the one place that reads it; it does not install, because a session that quietly puts a repository on the machine produces a location nothing else was told about. The record is the record, and the copy of it a running process holds is not: where the platform's own record of the variable — the current user's environment, or the managed block of the shell profile — holds an answer, that answer is what is used, and a process environment that disagrees with it is reported rather than obeyed. A value set for one run and written nowhere is read where the record says nothing, and nowhere else. None of these scripts resolves Memar by copying the repository elsewhere, each declaring that in its own interface, because a copy outside the registered location is machine-local and does not survive — and a destination under a temporary directory is refused outright, for the same reason.
