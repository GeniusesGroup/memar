# Scripts
> **Warning: this folder's CLI surface is provisional.** Memar is moving toward a knowledge-graph server that agents converse with, not a command line they invoke — every sentence here describing today's CLI behavior will rot on that move. This file therefore states only how Memar is installed and how its entry command is used, and points at each tool's own `--help` for everything else. Do not add usage text, per-file rationale, or anything a file or a `--help` already says: the owning file carries its own why, `--help` carries usage, and a second copy here is guaranteed to drift. One need is met by one method: when two implementations serve one need, unify them or record why they differ — never keep both silently.
Executable helpers for recurring host-tool work where Memar sessions need a constraint free-form shell habits keep violating. A need earns a file here when it is worth a small script with a stable interface, and when it serves one of the kinds below — as the entry point, as one of the concerns that entry point asks rather than repeats, or as the suite that checks them; a need that serves none of them does not belong here. Each file in this folder documents itself, and each of those declarations is the authority: `-Help` for [`install.ps1`](./install.ps1), and `--help` for [`install.sh`](./install.sh) and for every Python file that has a command line, and each Python module's own docstring for what it provides and how it is invoked. A module with no command line declares no help, because it is reached by an import rather than by a command; this document does not repeat a name, path, command, or default a script already declares — where a reader needs one of those, the script is run or read, not this page. Discover what exists here by listing it: the shelves and the criteria that separate them are named below, and this page does not inventory them ([Documentation → Content Rule](../../docs/documentation.md#content-rule-no-fabricated-or-redundant-provenance)).

## Three shelves, and what separates them
A file's shelf is decided by **what the file belongs to**, not by who calls it. That question has one answer per file, and answering it any other way is how a folder fills with files whose names say nothing about what they do.

**The top of this folder is Memar's own.** The launcher, the tools it routes to, and the modules only Memar's own tools use. A file here either declares a command line — in which case its name carries the hyphen that separates its domain from its subject, because that is how a caller types it — or declares none, and is then reached by an import, which is the only form the interpreter accepts.

**[`machine/`](./machine/) is the machine's, not Memar's.** The filesystem and the environment, and the one place a session's identity is minted: the interfaces Memar has to reach the machine through, none of which it owns. [`host/`](./host/) is the same idea for tools rather than interfaces — tools the machine already has, wrapped in the constraints a session improvises past. Both paths carry that claim; read [`host/README.md`](./host/README.md) for why neither of them is under `memar`, which is the point of naming them at all.

## How a file is named
A name states its domain before its subject: the surface the file acts on, then what it does on that surface. A bare name that is only a role or a mechanism — a lock, a target, a decision about what a copy leaves out — states no domain at all, and a reader who has just listed this folder is owed one. The domain comes first because that is what says whether the file is worth opening.

**The domain is a shelf wherever a domain has more than one file, and an underscore-prefixed module wherever it has exactly one.** `machine` carries seven files, so it is a shelf and each of its files says what it acts on and what it does: [`env_location.py`](./machine/env_location.py), [`env_path.py`](./machine/env_path.py), [`fs_lock.py`](./machine/fs_lock.py), [`fs_memar.py`](./machine/fs_memar.py), [`fs_target.py`](./machine/fs_target.py), [`fs_trash.py`](./machine/fs_trash.py), [`editor_extension.py`](./machine/editor_extension.py). The prefix inside a shelf is a second domain, not a repetition of the first — a reader listing the shelf sees `fs_` and `env_` and knows which machine interface each answers before reading a word of it. A domain with a single file has no second word to put in a folder name, so it stays at the top as `memar_console.py`, `memar_copy_excluded.py`, `memar_repository.py`, `memar_session.py` — the prefix there is a complete name rather than a truncation, which is why those read as one phrase and the shelf's files do not.

**Which form a name takes is settled by how the file is reached, not by taste.** One only ever run is hyphenated: a hyphen is what a caller types and a shell splits on, and no interpreter will accept it as a module. One a sibling imports is a module path — `memar_console`, `machine.fs_lock`, `machine.env_location` — because that is the form the interpreter resolves. A file that would be both has no legal spelling, so **no file here is both**, and that is the condition the rule rests on rather than a coincidence: `memar-install.py` asks the other two installers as child processes — the composition [`host/git.py`](./host/git.py) already used with [`host/fs.py`](./host/fs.py) — which is what lets all three keep the hyphen naming their domain first. Two names that differ by one separator are the sanctioned form of this split, not an accident of spelling: [`memar-session.py`](./memar-session.py) is run and [`memar_session.py`](./memar_session.py) is imported, and the separator is the only thing that says which. An underscore is never a hyphen in disguise: in an imported name the boundary is carried by the shelf or the prefix and by the order of the words, and no file here is made loadable by a trick that would let a hyphen stand.

**Where a name or a path is decided is itself one file's business, and it is stated there.** `INSTALL_DIRNAME` belongs to [`machine/fs_target.py`](./machine/fs_target.py) because that is the module that answers which folder a run would use. The layout inside a checkout — the scripts folder, the skill, the extensions folder, the consumer README — belongs to [`machine/fs_memar.py`](./machine/fs_memar.py), which had three copies of it in three files. Both lock families name themselves in [`machine/fs_lock.py`](./machine/fs_lock.py) and derive their names from nothing: the install lock was built from the installer's folder name, which made the lock module import the module that decides a destination folder for one string literal, and a rename there would silently orphan every lock this one had written. A name or a path borrowed across modules is one two modules can disagree about.

## Installing Memar — onto a machine, then into a project
[`install.ps1`](./install.ps1) on Windows and [`install.sh`](./install.sh) on POSIX are the bootstrap, which obtains the checkout. [`memar-install.py`](./memar-install.py) is the installer: it records where the checkout is, settles the machine around it, and asks the other two — [`memar-install-agents.py`](./memar-install-agents.py) puts Memar into a project, [`memar-install-apps.py`](./memar-install-apps.py) copies the skill into the agent apps it detects — so that one bare run installs all three layers and each stays separately runnable. What each accepts is declared by its own help, which is this folder's authority for it.

**Reaching Memar by one word.** [`memar`](./memar) is the command a person or an agent types, with [`memar.cmd`](./memar.cmd) beside it for a shell that will not run a file without a known extension. The launcher routes and adds nothing, and the file states its own design; run `memar --help` for what it routes to and `memar <verb> --help` for a verb's interface, declared by the tool that implements it.

**Memar's content.** [`memar-content.py`](./memar-content.py), reached as `memar content`, is one subject under one word: the written content of a checkout, read, related, audited, and written. It is general-purpose rather than part of the skill, so it lives here and the skill reaches it through `memar`, which is how a caller reaches it without knowing that name. Its boundary is the whole checkout — `docs/`, `modules/`, `.agents/` — rather than only the Markdown under `docs/`, because the model definitions, the rules, and the sources are content too, and a tool named for content that could not search code would be a tool for documents.

The Python files in this folder import each other from disk, inside the checkout the bootstrap obtained: one implementation of each concern, no assembled second copy. **Running a file puts its own folder on the module search path, so no file in this folder declares one.** A module inside a shelf is only ever imported, and its importer already put this folder there. The two files that do declare one are the two that are run from *inside* a subfolder — [`host/fs.py`](./host/fs.py) and [`host/git.py`](./host/git.py), whose names carry a hyphen and so cannot be run as `-m` — and the test suites, which are run from their own `tests/` folder. Whether a folder is a Memar repository is asked through [`memar_repository.py`](./memar_repository.py), so no shell answers it differently from the installer.

**Everything this project has developed as a script is provisional and is eventually to become real code in modules.** That is not a demotion of these files — a need earns one here when a script is the right shape for it, and a need that has outgrown a script is not served by a better script — but it is the direction of travel, and it is why a folder under [`modules/`](../../modules/) rather than a `.py` file here is where a concern comes to rest once its subject is settled. The scripts this most affects are the ones inside a module: every `.py` file under [`modules/khayyam/targets/go/`](../../modules/khayyam/targets/go/) is provisional in that standing, and the mechanism that read the Go residue moved out of that folder for want of a subject to match it, while the Rule documents it applied stayed where their subject was ([`declaration-rename.md`](../../modules/khayyam/rules/declaration-rename/declaration-rename.md):89). Nothing here is permanent either; what is permanent is the standing, not the file.

## Putting text into a file
A file's encoding and line endings are decided when it is written, and on Windows they are decided by whatever shell does the writing. [`memar-content.py`](./memar-content.py) carries the verbs that decide them under `memar content` — its write, its edit, and its check — each declaring what it accepts through `--help`, which is this folder's authority. Prefer them to any shell's own text handling.

The reason is specific rather than general. A shell that reads a file without being told its encoding falls back to the console codepage when the file carries no byte-order mark — and a correctly encoded document carries none, since a mark would become part of the first line for text readers. A read-then-write round trip through such a shell therefore loses every non-ASCII character it contains while staying valid UTF-8, so nothing downstream reports the damage and a reader discovers it.

Those verbs also take the per-file lock in [`machine/fs_lock.py`](./machine/fs_lock.py) and write an intent note beside it, so two cooperating sessions writing one file are serialized rather than interleaved, and a session that takes over a stale lock can read what the dead one meant. The lock is advisory: a file-write tool does not take it, which is why the skill carries the rule and not the mechanism.

A file that checks another file in this folder is not beside what it checks and is not another angle on it: a check states the expectations of a process, and the installer's process is not its file. Such a file therefore goes in a `tests/` folder inside the folder that owns what it checks, named for that subject and carrying no marker, per [Test Placement](../../modules/process/test/rules/test-placement/test-placement.md) and [Test Naming](../../modules/process/test/rules/test-naming/test-naming.md). A shelf owns its own `tests/`, so [`machine/tests/`](./machine/tests/) sits beside the concerns it checks rather than in one folder at the top whose owner would have to be decided per file. The folder states the role, so the name does not have to, and every file in this folder stays a file this folder is for.

## A consuming project receives no copy of these files
[`memar-install-agents.py`](./memar-install-agents.py) writes what a project's instructions are read from: a one-line `## Memar` section in its `AGENTS.md` naming the file to read, the substance in the `.agents/memar/README.md` that line points at, and the index of the folder they sit in when the project has none. It places no script there and no Python file anywhere in the project. The bootstrap for the machine is fetched from this repository at the point of use, and that README says so in full: a copy per repository is unmaintainable, because it goes stale on every change here and re-reaching every project by hand is the only way to update it. One fetch, one update, every consumer.

The same rule holds for the skill: [`memar-install-apps.py`](./memar-install-apps.py) copies the skill document, not the scripts it names. A consumer that wants these files on disk clones this repository and points the variable at the clone; it does not receive them second-hand through another project or another app's skill folder.

## Getting Memar into a project
One bare `memar install` settles the machine, this project, and the agent apps, in the only order that works — the app layer needs the location the machine layer records, so a directory that is not a project is reported and skipped while the rest still runs. Each script's help names what it accepts and how to narrow the run to one layer.

A web chatbot is still an agent-app target, with a weaker interface: only if that app lets you add a skill, and only as a skill file or pasted text. No script covers that case, because a script can only write where it can see; the folder to hand it is [`../skills/memar/`](../skills/memar/). Check that app first. Workspace and local agent apps are the better fit — Memar adds substantial cognitive load to the process and is not equally appropriate in every interface.

Memar is a development framework, not a host-tool plugin: its model lives in `docs/`, so what a host tool could install from this repository is the agent configuration under [`.agents/`](../), not the model.

## Where Memar lives
One environment variable holds the path of a Memar checkout on this machine. Everything that needs Memar reads it through [`machine/env_location.py`](./machine/env_location.py), and nothing guesses a location or keeps a second copy of the repository. Which folder an install lands in by default, the modes offered for naming a folder or reusing one that already exists, and the check that refuses a folder which is not a Memar repository belong to the installer and to the bootstrap that runs it, and their own help declares them.

Run the bootstrap or the installer with `--help` for what a no-argument run does, what naming a destination does, and what restart is owed. What the variable says is asked of the module that reads it, and `memar install --root` prints it for a program that needs to find it. None of these scripts resolves Memar by copying the repository elsewhere, because a copy outside the registered location is machine-local and does not survive.
