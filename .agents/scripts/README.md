# Scripts
This file is the work instruction for a session that reaches Memar without the `memar` command: how Memar is installed, and the rules a session follows when it deletes, moves, restores, or commits anything, or puts text into a file. A session that has `memar` needs it only for those acts. Each file in this folder declares its own interface — `-Help` for [`install.ps1`](./install.ps1), `--help` for [`install.sh`](./install.sh) and for every command a Python file here declares — and that declaration, not this page, is the authority for what it accepts; ask it each time it is used. What a file is for and why it is built as it is sits in its own opening docstring or comment, and how this folder is organized is under [Maintaining this folder](#maintaining-this-folder).

## Installing Memar — onto a machine, then into a project
1. Fetch the bootstrap into a file: [install.sh](https://raw.githubusercontent.com/GeniusesGroup/memar/main/.agents/scripts/install.sh) on POSIX, [install.ps1](https://raw.githubusercontent.com/GeniusesGroup/memar/main/.agents/scripts/install.ps1) on Windows. In a Memar checkout the same two files sit beside this README.
2. Read its opening comment before running it, and ask it for its help — `install.ps1 -Help`, `install.sh --help` — for what a run with no argument does, what naming a destination does, and what restart is owed.
3. Run it only as that comment and that help say.

The bootstrap obtains the checkout and hands it to `memar install` inside it, the [installer](./services/install.py): it records where the checkout is, settles the machine around it, then puts Memar into the project it is told with `--project NAME` or `--project-path PATH` (the bootstrap, which runs before any registry exists, takes only a folder, `--project-path`/`-ProjectPath`, and passes it on as `--project-path`) and copies the skill into the agent apps it detects. `memar install --project NAME` or `--project-path PATH` therefore settles the machine, that project, and the agent apps, in the only order that works — the app layer needs the location the machine layer records, so a project not named or not a project is reported and skipped while the rest still runs; the folder the command runs in is never read, and a path needs no earlier `memar project add`. Installing is declaring that the project follows Memar, so the project layer also registers the project, once, under its folder's name (what `memar project add` does; a person gives it another name later with `--alias`): a project already registered is left as it is, and a name another project holds is reported with the holder, with nothing renamed and the install going on.

Whatever else Memar needs and the machine lacks — Python, git — comes through the bootstrap as well; a hand-made recipe in its place is not the fallback. If the bootstrap cannot supply it, stop and say so.

Once installed, [`memar`](./memar) is the one word a person or an agent types, with [`memar.cmd`](./memar.cmd) beside it for a shell that will not run a file without a known extension; `memar --help` says what it routes to, and each verb's own `--help` says what that verb accepts.

A web chatbot is an agent-app target with a weaker interface: only if that app lets you add a skill, and only as a skill file or pasted text. No script covers that case, because a script can only write where it can see; the folder to hand it is [`../skills/memar/`](../skills/memar/). Check that app first. Workspace and local agent apps are the better fit — Memar adds substantial cognitive load to the process and is not equally appropriate in every interface.

## Where Memar lives
One environment variable holds the path of the Memar checkout on this machine, and everything that needs Memar reads it; nothing guesses a location or keeps a second copy of the repository. `memar install --root` prints it for a program that needs to find it. A copy of the repository outside the registered location is machine-local and does not survive, so no script resolves Memar that way. Where a checkout exists but `memar` is not on the path, run the checkout's own launcher with Python by its path — `python <checkout>/.agents/scripts/memar <verb>` — which is the same command under its full name. The default install folder, the modes for naming or reusing a folder, and the refusal of a folder that is not a Memar repository are declared by the bootstrap's and the installer's own help.

## Deleting, moving, restoring, and committing
The [`host/`](./host/) shelf wraps tools the machine already has with the constraint a session improvises past: [`host/fs.py`](./host/fs.py) for the filesystem, [`host/git.py`](./host/git.py) for version control. A session that touches files or history takes no act that cannot be undone, and follows these rules:

- Deleting, moving, discarding, stashing, restoring, and committing go through those two files, each asked for its own `--help`, so the act stays recoverable — a deletion goes to the OS recycle bin, a tracked path moves with its history, uncommitted work is not discarded unasked, and a commit takes only the paths it names.
- Never the host's own command for those acts — `rm`, `Remove-Item`, `git rm`, `git restore`, `git checkout` of paths, `git clean`, a plain `git commit` — and never a command a runtime rewrites: a runtime that rewrites commands can turn a safe one into the host's own, and what it actually ran is what is judged.
- In a working tree other sessions share, commit only this session's paths, through `host/git.py`. The records of the task's sessions are not among those paths: `memar session archive` keeps them on the project's records branch in a commit of its own, made through `host/git.py record` without moving HEAD, the index or the working tree, and names them for the task's commit to cite.
- One session task gets one commit, made by the coordinating session only after the human approves the result, never before: a finding after that commit is folded into it, not added as a commit of its own. A sub-agent never commits; its edits reach history through the coordinating session's commit. A one-character or other small edit folds into the task's single commit, never a commit of its own — and that holds for such an edit another session left uncommitted on purpose, since that is how a small edit is meant to reach history: alongside a larger change. A move rides with the task's commit too, as long as each moved file stays above git's rename threshold (50% similarity by default) so git still reports it as renamed and history follows it; a move keeps a commit of its own only where the task's edit to the moved file would push it below that threshold — the move is committed first, alone, and the edit folds into the task's commit. Before the session closes, it folds any further unpushed commits of its own into that one.
- When a commit stops partway — another git process held a lock past the wait — do what its message says: finish, or undo, with one of the two commands it prints — never with a host `git update-ref` or `git reset` in their place. Never delete a lock file to get past one; the message says whether the lock looks stale, and deleting one is a person's call.
- Every `host/git.py` verb that acts on a repository (`commit`, `uncommit`, `reindex`, `record`, `rename`, `remove`, `stash`, `restore`, `undelete`) takes the repository it acts on with `--repository PATH`, and never reads the folder it is run from; a relative path it is given is relative to that repository.
- If those files are not at hand or do not cover the act, stop and say so.

Both are run with Python by their path inside the checkout the location variable names; neither is a `memar` verb, and [`host/README.md`](./host/README.md) says why.

## Putting text into a file
Text reaches a file through a file-write tool or the write and edit verbs under `memar content`, each declaring what it accepts through `--help` — never through a shell's own text handling: redirection, `echo`, `Set-Content`, a here-string piped to a file, or a read-then-write round trip through a shell. Where another session may be writing the same file, use those verbs.

The reason is specific rather than general. A shell that reads a file without being told its encoding falls back to the console codepage when the file carries no byte-order mark — and a correctly encoded document carries none, since a mark would become part of the first line for text readers. A read-then-write round trip through such a shell therefore loses every non-ASCII character it contains while staying valid UTF-8, so nothing downstream reports the damage and a reader discovers it.

The verbs under `memar content` also take a per-file lock and write an intent note beside it, so two cooperating sessions writing one file are serialized rather than interleaved, and a session that takes over a stale lock can read what the dead one meant. The lock is advisory: a file-write tool does not take it, which is why a shared file is written through those verbs.

## A consuming project receives no copy of these files
Installing Memar into a project writes only the instructions its agents read — a one-line section in its `AGENTS.md` and the file that line points at — and places no script and no Python file there; installing into an agent app copies the skill document, not the scripts. The bootstrap is fetched from this repository at the point of use: a copy per repository goes stale on every change here, and re-reaching every project by hand is the only way to update it. One fetch, one update, every consumer. A session in a consuming project reaches these files in the checkout the location variable names, or clones this repository and points the variable at the clone; it does not take them second-hand from another project or another app's skill folder.

Memar is a development framework, not a host-tool plugin: its model lives in `docs/`, so what a host tool could install from this repository is the agent configuration under [`.agents/`](../), not the model.

## A script is told its project
No script has a default project, and none reads the folder it was started in: not `Path.cwd()`, not `os.getcwd()`, not a relative path taken as "here". Both are guesses that are right on the day they are written, and an agent working across projects is wrong the first time the guess is. A verb that acts on a project takes it as an argument, always, and the flag says which kind it is: `--project NAME` is a name, turned into a folder by `memar project find` (the registry is `temp/projects.log`), and `--project-path PATH` is a folder, taken as given; the two are one mutually exclusive pair declared once, by `add_project_flags` in [project_find.py](./services/project_find.py), with `project_from_args` turning what was given into the folder, so no verb declares the flags or resolves names itself. Neither stands in for the other: a name written like a path, or a path that is no folder, is refused with the flag to use. An empty or missing project is refused, never filled in. A relative path the person typed is theirs and is taken as given; the rule is against a default, not against a path. An agent told a project by a word asks `memar project find WORD` and never reasons about the name or guesses a path. A script that cannot find a project asks `memar project find`, which also looks for a few seconds beside the Memar checkout, and never writes a search of its own. A new verb that reads the calling folder, or assumes a project, is a defect: fix it before adding another.

**Constraint: the project registry and Khayyam's dependency management are developed only together, and nothing is added to either until they are one.** Khayyam needed a dependency management matching what `memar project` and `temp/projects.log` do for projects, and it is still not done. Until the two are unified, no new field, verb or lookup is added to the registry, and no new resolution rule to Khayyam's `in` addresses or module manifests. The reason is that there is no magic in code: accepting an implicit path is magic the user may not expect, and anything not documented must be written down. The open question, with its options, is in [documentation-handoff.handoff.md](../../docs/documentation-handoff.handoff.md#khayyams-dependency-management-and-memars-project-registry-one-design-and-nothing-added-to-either-before-it-exists).

## Maintaining this folder
This section is for whoever adds, renames, or removes a file here; a session doing other work does not need it.

**This folder's CLI surface is provisional.** Memar is moving toward a knowledge-graph server that agents converse with, not a command line they invoke, and every sentence here describing today's CLI behavior will rot on that move. That server is reached through Memar's own protocols — [sRPC](../../docs/modules/net/sRPC.md) with a [delivered SDK](../../docs/modules/process/service-sdk.md) — and through MCP, where an agent app requires it, only by the [guest adapter](../../modules/lib/lib.handoff.md#mcp-as-a-guest-adapter) under `modules/lib/`, never as the server's model. Do not add usage text, per-file rationale, or anything a file or a `--help` already says: the owning file carries its own why, `--help` carries usage, and a second copy here is guaranteed to drift. One need is met by one method: when two implementations serve one need, unify them or record why they differ — never keep both silently.

A need earns a file here when it is a recurring piece of host-tool work where sessions need a constraint free-form shell habits keep violating, worth a small script with a stable interface, and when it serves one of the kinds below — as the entry point, as one of the concerns that entry point asks rather than repeats, or as the suite that checks them. Discover what exists by listing the folder: the shelves and the criteria that separate them are named below, and this page does not inventory them ([Documentation → Content Rule](../../docs/documentation.md#content-rule-no-fabricated-or-redundant-provenance)). A module with no command-line face declares no help, because nothing reaches it but an import; each module's docstring says what it provides.

**A one-time migration is never a file here.** A script that changes once what an earlier Memar left — plans or reports in an earlier shape, folders named in an earlier form, a record another has replaced — does its change and is of no use afterwards, so it is not a recurring need and earns no file on any shelf. It lives in the `services/` folder of the session that does the change, its test in that session's `tests/`, and it reaches this folder's modules by being run with this folder on `PYTHONPATH`, which whoever runs it sets. Nothing here names such a script: a message about something in an earlier shape says that only today's shape is read and where that shape is shown, never which script converts it, because the script is gone once its work is done.

**Everything this project has developed as a script is provisional and is eventually to become real code in modules.** That is not a demotion of these files — a need earns one here when a script is the right shape for it, and a need that has outgrown a script is not served by a better script — but it is the direction of travel, and it is why a folder under [`modules/`](../../modules/) rather than a `.py` file here is where a concern comes to rest once its subject is settled. The scripts this most affects are the ones inside a module: every `.py` file under [`bundles/khayyam/targets/go/`](../../bundles/khayyam/targets/go/) is provisional in that standing, and the mechanism that read the Go residue moved out of that folder for want of a subject to match it, while the Rule documents it applied stayed where their subject was ([`declaration-rename.md`](../../bundles/khayyam/rules/declaration-rename/declaration-rename.md):89). Nothing here is permanent either; what is permanent is the standing, not the file.

**Python written here still follows Memar's way, because it will be converted to Khayyam.** Where a script must be written in Python anyway, it is written as Memar would write it: one service is one file, a type is declared once and used by the services, a fact that belongs in a type is not copied into a help text or a comment but obtained by calling the type's methods, and nothing is implicit. Done this way, converting a script to Khayyam later is a change of syntax only, not of the frame of the code; the one-service-per-file rule was not kept from the start and fixing it afterwards cost a great deal.

## A growing file is a sign of a problem
A script or service file that grows large means a concern is missing a place of its own: one file for a family of commands grew quickly until it was split into one file per single-purpose command. When a file passes the mark, split it by concern rather than raising the mark. [`services/tests/script_size.py`](./services/tests/script_size.py) holds the mark and names the files over it with what each should split into.

### The shelves, and what separates them
A file's shelf is decided by **what the file belongs to**, not by who calls it. That question has one answer per file, and answering it any other way is how a folder fills with files whose names say nothing about what they do.

**The top of this folder is what is reached from outside it, and nothing else.** The router, [`memar`](./memar) with `memar.cmd` beside it, the two bootstraps, and this README are reached from outside. The router routes and nothing else: it knows no verb, no argument, and no help text, so none of them has a second copy that could drift from the service that answers it. No module sits at the top: one that more than one shelf imports goes to the shelf its nature belongs to — what answers about the machine to `machine/`, whoever imports it — and one with two natures is split along them, each part on its own shelf.

**[`services/`](./services/) is where every verb lives, and it is what Memar itself does.** One file per service — one capability, such as opening a session or finding one — imported by the router and by other services, never run. Each service with a command-line face declares that face itself, through the one function the router calls; the contract is stated in the router's own docstring, which owns it. The shelf owns the domains on it, so a domain gets no folder of its own there: a domain is a file named for the domain, each of its capabilities is a file named `<domain>_<capability>`, and what several capabilities of a domain share is a file of that domain named for what it is. This mirrors Memar's own module and service — the module owns the domain, and each service is one capability of it — and Memar's types, each of which introduces itself so that its consumer calls only the method it needs.

**[`machine/`](./machine/) is the machine's, not Memar's.** The filesystem and the environment: the interfaces Memar has to reach the machine through, none of which it owns. [`host/`](./host/) is the same idea for tools rather than interfaces — tools the machine already has, wrapped in the constraints a session improvises past. Both paths carry that claim; read [`host/README.md`](./host/README.md) for why neither of them is under `memar`, which is the point of naming them at all.

### How a file is named
A name states its domain before its subject: the surface the file acts on, then what it does on that surface. A bare name that is only a role or a mechanism — a lock, a target, a decision about what a copy leaves out — states no domain at all, and a reader who has just listed this folder is owed one. The domain comes first because that is what says whether the file is worth opening.

**A file whose whole subject is its surface is named by that surface alone.** Each of the two files under [`host/`](./host/) acts on every operation the tool it wraps has — a directory tree, a link, the recycle bin on one side, a rename, a stash, a commit on the other — so no single act is left to name after the surface, and a subject standing in for all of them would be an adjective about how safe the file is rather than a statement of what it does. What says whether such a file is worth opening is the surface itself, so the surface is the whole name and the shelf above it carries the rest of the claim.

**Inside a shelf the domain is the prefix.** The prefix is a second domain, not a repetition of the shelf's — a reader listing `machine/` sees `fs_` and `env_`, and listing `services/` sees `session_`, and knows which interface or domain each answers before reading a word of it.

**A domain with one file inside a shelf keeps its bare name there.** That last sentence is a claim about Memar's own domains, and it stops where Memar's own stops: a machine interface is not Memar's, and a `memar_` name on one would assert the ownership the shelf exists to deny. So a file that alone answers for another interface — the editor's extensions, the console — keeps the whole of its domain in its own name, and a reader listing the shelf reads it beside the `fs_` and `env_` prefixes and knows what it answers for before opening it.

**Which form a name takes is settled by how the file is reached, not by taste.** No file here except the router is run by its name, and the router's name is the one word a caller types. The files under `host/` and the test suites are run by their path, which asks nothing of the name. Everything else is imported, by the router or by a sibling, so its name is a module path, because that is the form the interpreter resolves; a hyphen is what a shell splits on and no interpreter accepts in a module, so no file here carries one. An underscore is never a hyphen in disguise: in an imported name the boundary is carried by the shelf or the prefix and by the order of the words, and no file here is made loadable by a trick that would let a hyphen stand.

**Where a name or a path is decided is itself one file's business, and it is stated there.** A name or a path borrowed across modules is one two modules can disagree about, so each is owned by the module that answers the question it belongs to, and that module's docstring says so. A name the outside holds is the same question with the owner elsewhere: the two bootstraps are fetched by raw URL ([Installing Memar](#installing-memar--onto-a-machine-then-into-a-project)), so each one's name is held by the projects that fetch it, and changing it here changes what they hold — which is asked of them, not taken here.

### How the files reach each other
The Python files here import each other from disk, inside the checkout the bootstrap obtained: one implementation of each concern, no assembled second copy. **The router puts this folder on the module search path, so nothing it reaches declares one.** A service, and any module on a shelf, is only ever imported, and its importer already put this folder there. The files that do declare one are those run by their path from *inside* a subfolder — the two under `host/` and the test suites, each run from where it sits. Whether a folder is a Memar repository is asked through [`machine/fs_memar_repository.py`](./machine/fs_memar_repository.py), so no shell answers it differently from the installer.

### Where a check goes
A file that checks another file in this folder is not beside what it checks and is not another angle on it: a check states the expectations of a process, and the installer's process is not its file. Such a file therefore goes in a `tests/` folder inside the folder that owns what it checks, named for that subject and carrying no marker, per [Test Placement](../../modules/process/test/rules/test-placement/test-placement.md) and [Test Naming](../../modules/process/test/rules/test-naming/test-naming.md). A shelf owns its own `tests/`, so [`services/tests/`](./services/tests/), [`machine/tests/`](./machine/tests/), and [`host/tests/`](./host/tests/) sit beside the concerns they check rather than in one folder at the top whose owner would have to be decided per file; the top's own [`tests/`](./tests/) checks what sits at the top — the router. The folder states the role, so the name does not have to, and every file in this folder stays a file this folder is for.
