# Scripts
> **Warning: this folder's CLI surface is provisional.** Memar is moving toward a knowledge-graph server that agents converse with, not a command line they invoke — every sentence here describing today's CLI behavior will rot on that move. This file therefore states only how Memar is installed and how its entry command is used, and points at each tool's own `--help` for everything else. Do not add usage text, per-file rationale, or anything a file or a `--help` already says: the owning file carries its own why, `--help` carries usage, and a second copy here is guaranteed to drift.
Executable helpers for recurring host-tool work where Memar sessions need a constraint free-form shell habits keep violating. A need earns a file here when it is worth a small script with a stable interface, and when it serves one of the kinds below — as the entry point, as one of the concerns that entry point asks rather than repeats, or as the suite that checks them; a need that serves none of them does not belong here. Each file in this folder documents itself, and each of those declarations is the authority: `-Help` for [`install.ps1`](./install.ps1), and `--help` for [`install.sh`](./install.sh) and for every Python file that has a command line, and each Python module's own docstring for what it provides and how it is invoked. A module with no command line declares no help, because it is reached by an import rather than by a command; this document does not repeat a name, path, command, or default a script already declares — where a reader needs one of those, the script is run or read, not this page. Discover what exists in this folder by listing it: the grouping below states a criterion, not an inventory ([Documentation → Content Rule](../../docs/documentation.md#content-rule-no-fabricated-or-redundant-provenance)).

Installation and location material lives here rather than in the entry document, because all of it is about these files.

## How a file is named
A name in this folder states its domain before its subject: the surface the file acts on, then what it does on that surface. A bare name that is only a role or a mechanism — a lock, a target, a decision about what a copy leaves out — states no domain at all, and a reader who has just listed this folder is owed one; the domain comes first because that is what says whether the file is worth opening. One domain carries one prefix and several files may sit under it, while a domain with a single file is named by the domain alone.

The boundary between the two is the hyphen, as [Documentation → File Naming](../../docs/documentation.md#file-naming) sets it for the rest of this repository, and a file Python imports as a module cannot carry one: a hyphen is not a legal module name. Which form a name takes is therefore settled by how the file is reached rather than by taste — one that is only ever run is hyphenated, and one that a sibling imports states the same two parts with an underscore in the same domain-first order, because that is the form the interpreter accepts. The underscore elsewhere in this repository joins the words of one term, so in an imported file's name the boundary is carried by the order of the words rather than by the separator; the words are the same either way, and no file here is made loadable by a trick that would let a hyphen stand. Which is which is discoverable from the file itself: a command line is how a run-only file is reached, and an import of a sibling is how the rest are.

## Three kinds of file
**Installing Memar — onto a machine, then into a project.** [`install.ps1`](./install.ps1) on Windows and [`install.sh`](./install.sh) on POSIX are the bootstrap; [`install.py`](./install.py) is the installer and the resolver, and the one place that decides what a Memar repository is and what the location variable says. [`install-agents.py`](./install-agents.py) installs Memar into a project, and [`install-apps.py`](./install-apps.py) copies the skill into the agent apps it detects. What each accepts is declared by its own help, which is this folder's authority for it.

**Reaching Memar by one word.** [`memar`](./memar) is the command a person or an agent types. The launcher routes and adds nothing, and the file states its own design; run `memar --help` for what it routes to, and `memar <verb> --help` for a verb's interface, which is declared by the tool that implements it.

**Navigating Memar's documentation.** [`memar-documentation.py`](./memar-documentation.py) resolves, reads, and searches the doc set; run it with `--help`, or `memar <verb> --help` for one verb, for what each verb accepts. It is not carried beside the Memar skill: it is general-purpose, so it lives here and the skill names this folder — through `memar`, which is how a caller reaches it without knowing that name.

**Constraining an operation a host tool already offers.** [`fs.py`](./fs.py) and [`git.py`](./git.py) exist for the constraints a session would otherwise improvise past — recoverable deletion, history-preserving moves, a guarded restore — not for the capability, which the host tool already has.

The Python files in this folder import each other directly from disk, beside the file that imports them, inside the checkout the bootstrap obtained: one implementation of each concern, no assembled second copy. Whether a folder is a Memar repository is asked through the module that holds the test, so no shell answers it differently from the installer.

**Everything this project has developed as a script is provisional and is eventually to become real code in modules.** That is not a demotion of these files — a need earns one here when a script is the right shape for it, and a need that has outgrown a script is not served by a better script — but it is the direction of travel, and it is why a folder under [`modules/`](../../modules/) rather than a `.py` file here is where a concern comes to rest once its subject is settled. The scripts this most affects are the ones inside a module: every `.py` file under [`modules/khayyam/targets/go/`](../../modules/khayyam/targets/go/) is provisional in that standing, and the mechanism that read the Go residue moved out of that folder for want of a subject to match it, while the Rule documents it applied stayed where their subject was ([`declaration-rename.md`](../../modules/khayyam/rules/declaration-rename/declaration-rename.md):89). Nothing here is permanent either; what is permanent is the standing, not the file.

## Putting text into a file
A file's encoding and line endings are decided when it is written, and on Windows they are decided by whatever shell does the writing. `memar-documentation.py` carries the three subcommands that decide them instead: `write`, `edit`, and `check` — read them from its `--help`, which is this folder's authority, and prefer them to any shell's own text handling.

The reason is specific rather than general. A shell that reads a file without being told its encoding falls back to the console codepage when the file carries no byte-order mark — and a correctly encoded document carries none, since a mark would become part of the first line for text readers. A read-then-write round trip through such a shell therefore loses every non-ASCII character it contains while staying valid UTF-8, so nothing downstream reports the damage and a reader discovers it.

What `check` reports, how it judges links, and how it lists undischarged propagations are declared by that tool; run `memar check --help` for them, and `memar write --help` and `memar edit --help` for the commands that put text into a file.

A file that checks another file in this folder is not beside what it checks and is not another angle on it: a check states the expectations of a process, and the installer's process is not its file. Such a file therefore goes in a `tests/` folder inside the folder that owns what it checks, named for that subject and carrying no marker, per [Test Placement](../../modules/process/test/rules/test-placement/test-placement.md) and [Test Naming](../../modules/process/test/rules/test-naming/test-naming.md). The folder states the role, so the name does not have to, and every file in this folder stays a file this folder is for. Nothing here depends on that arrangement, and a script that wants its checks run asks for them the way it asks for anything else here.

## A consuming project receives no copy of these files
[`install-agents.py`](./install-agents.py) writes what a project's instructions are read from: a one-line `## Memar` section in its `AGENTS.md` naming the file to read, the substance in the `.agents/memar/README.md` that line points at, and the index of the folder they sit in when the project has none. It places no script there and no Python file anywhere in the project. The bootstrap for the machine is fetched from this repository at the point of use, and that README says so in full: a copy per repository is unmaintainable, because it goes stale on every change here and re-reaching every project by hand is the only way to update it. One fetch, one update, every consumer.

The same rule holds for the skill: [`install-apps.py`](./install-apps.py) copies the skill document, not the scripts it names. A consumer that wants these files on disk clones this repository and points the variable at the clone; it does not receive them second-hand through another project or another app's skill folder.

## Getting Memar into a project
Run [`install-agents.py`](./install-agents.py) for [AGENTS.md](https://agents.md/) instructions and [`install-apps.py`](./install-apps.py) for the skill in the agent apps it detects; each script's help names its variants, including refresh.

A project is left holding the entry point this repository reaches itself through, not a path into a scripts folder.

A web chatbot is still an agent-app target, with a weaker interface: only if that app lets you add a skill, and only as a skill file or pasted text. No script covers that case, because a script can only write where it can see; the folder to hand it is [`../skills/memar/`](../skills/memar/). Check that app first. Workspace and local agent apps are the better fit — Memar adds substantial cognitive load to the process and is not equally appropriate in every interface.

Memar is a development framework, not a host-tool plugin: its model lives in `docs/`, so what a host tool could install from this repository is the agent configuration under [`.agents/`](../), not the model.

## Where Memar lives
One environment variable, **`MEMAR_ROOT`**, holds the path of a Memar checkout on this machine. Everything that needs Memar reads it through [`install.py`](./install.py), and nothing guesses a location or keeps a second copy of the repository. Which folder an install lands in by default, the modes offered for naming a folder or reusing one that already exists, and the check that refuses a folder which is not a Memar repository belong to the installer and to the bootstrap that runs it, and their own help declares them.

Run the bootstrap or the installer with `--help` for what a no-argument run does, what naming a destination does, and what restart is owed. What the variable says is asked of [`install.py`](./install.py), the one place that reads it. None of these scripts resolves Memar by copying the repository elsewhere, because a copy outside the registered location is machine-local and does not survive.
