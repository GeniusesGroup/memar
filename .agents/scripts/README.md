# Scripts
This file is the work instruction for a session that reaches Memar without the `memar` command: how Memar is installed, and the rules a session follows when it deletes, moves, restores, or commits anything, or puts text into a file. A session that has `memar` needs it only for those acts. Each file in this folder declares its own interface — `-Help` for [`install.ps1`](./install.ps1), `--help` for [`install.sh`](./install.sh) and for every Python file that has a command line — and that declaration, not this page, is the authority for what it accepts; ask it each time it is used. What a file is for and why it is built as it is sits in its own opening docstring or comment, and how this folder is organized is under [Maintaining this folder](#maintaining-this-folder).

## Installing Memar — onto a machine, then into a project
1. Fetch the bootstrap into a file: [install.sh](https://raw.githubusercontent.com/GeniusesGroup/memar/main/.agents/scripts/install.sh) on POSIX, [install.ps1](https://raw.githubusercontent.com/GeniusesGroup/memar/main/.agents/scripts/install.ps1) on Windows. In a Memar checkout the same two files sit beside this README.
2. Read its opening comment before running it, and ask it for its help — `install.ps1 -Help`, `install.sh --help` — for what a run with no argument does, what naming a destination does, and what restart is owed.
3. Run it only as that comment and that help say.

The bootstrap obtains the checkout and hands it to [`memar-install.py`](./memar-install.py), the installer: it records where the checkout is, settles the machine around it, and asks [`memar-install-agents.py`](./memar-install-agents.py) to put Memar into the project and [`memar-install-apps.py`](./memar-install-apps.py) to copy the skill into the agent apps it detects. One bare `memar install` therefore settles the machine, this project, and the agent apps, in the only order that works — the app layer needs the location the machine layer records, so a directory that is not a project is reported and skipped while the rest still runs. Each script's help names how to narrow a run to one layer.

Whatever else Memar needs and the machine lacks — Python, git — comes through the bootstrap as well; a hand-made recipe in its place is not the fallback. If the bootstrap cannot supply it, stop and say so.

Once installed, [`memar`](./memar) is the one word a person or an agent types, with [`memar.cmd`](./memar.cmd) beside it for a shell that will not run a file without a known extension; `memar --help` says what it routes to, and each verb's own `--help` says what that verb accepts.

A web chatbot is an agent-app target with a weaker interface: only if that app lets you add a skill, and only as a skill file or pasted text. No script covers that case, because a script can only write where it can see; the folder to hand it is [`../skills/memar/`](../skills/memar/). Check that app first. Workspace and local agent apps are the better fit — Memar adds substantial cognitive load to the process and is not equally appropriate in every interface.

## Where Memar lives
One environment variable holds the path of the Memar checkout on this machine, and everything that needs Memar reads it; nothing guesses a location or keeps a second copy of the repository. `memar install --root` prints it for a program that needs to find it. A copy of the repository outside the registered location is machine-local and does not survive, so no script resolves Memar that way. Where a checkout exists but `memar` is not on the path, run the checkout's own launcher with Python by its path — `python <checkout>/.agents/scripts/memar <verb>` — which is the same command under its full name. The default install folder, the modes for naming or reusing a folder, and the refusal of a folder that is not a Memar repository are declared by the bootstrap's and the installer's own help.

## Deleting, moving, restoring, and committing
The [`host/`](./host/) shelf wraps tools the machine already has with the constraint a session improvises past: [`host/fs.py`](./host/fs.py) for the filesystem, [`host/git.py`](./host/git.py) for version control. A session that touches files or history takes no act that cannot be undone, and follows these rules:

- Deleting, moving, discarding, stashing, restoring, and committing go through those two files, each asked for its own `--help`, so the act stays recoverable — a deletion goes to the OS recycle bin, a tracked path moves with its history, uncommitted work is not discarded unasked, and a commit takes only the paths it names.
- Never the host's own command for those acts — `rm`, `Remove-Item`, `git rm`, `git restore`, `git checkout` of paths, `git clean`, a plain `git commit` — and never a command a runtime rewrites: a runtime that rewrites commands can turn a safe one into the host's own, and what it actually ran is what is judged.
- In a working tree other sessions share, commit only this session's paths, through `host/git.py`.
- If those files are not at hand or do not cover the act, stop and say so.

Both are run with Python by their path inside the checkout the location variable names; neither is a `memar` verb, and [`host/README.md`](./host/README.md) says why.

## Putting text into a file
Text reaches a file through a file-write tool or the write and edit verbs under `memar content`, each declaring what it accepts through `--help` — never through a shell's own text handling: redirection, `echo`, `Set-Content`, a here-string piped to a file, or a read-then-write round trip through a shell. Where another session may be writing the same file, use those verbs.

The reason is specific rather than general. A shell that reads a file without being told its encoding falls back to the console codepage when the file carries no byte-order mark — and a correctly encoded document carries none, since a mark would become part of the first line for text readers. A read-then-write round trip through such a shell therefore loses every non-ASCII character it contains while staying valid UTF-8, so nothing downstream reports the damage and a reader discovers it.

The verbs under `memar content` also take a per-file lock and write an intent note beside it, so two cooperating sessions writing one file are serialized rather than interleaved, and a session that takes over a stale lock can read what the dead one meant. The lock is advisory: a file-write tool does not take it, which is why a shared file is written through those verbs.

## A consuming project receives no copy of these files
Installing Memar into a project writes only the instructions its agents read — a one-line section in its `AGENTS.md` and the file that line points at — and places no script and no Python file there; installing into an agent app copies the skill document, not the scripts. The bootstrap is fetched from this repository at the point of use: a copy per repository goes stale on every change here, and re-reaching every project by hand is the only way to update it. One fetch, one update, every consumer. A session in a consuming project reaches these files in the checkout the location variable names, or clones this repository and points the variable at the clone; it does not take them second-hand from another project or another app's skill folder.

Memar is a development framework, not a host-tool plugin: its model lives in `docs/`, so what a host tool could install from this repository is the agent configuration under [`.agents/`](../), not the model.

## Maintaining this folder
This section is for whoever adds, renames, or removes a file here; a session doing other work does not need it.

**This folder's CLI surface is provisional.** Memar is moving toward a knowledge-graph server that agents converse with, not a command line they invoke, and every sentence here describing today's CLI behavior will rot on that move. Do not add usage text, per-file rationale, or anything a file or a `--help` already says: the owning file carries its own why, `--help` carries usage, and a second copy here is guaranteed to drift. One need is met by one method: when two implementations serve one need, unify them or record why they differ — never keep both silently.

A need earns a file here when it is a recurring piece of host-tool work where sessions need a constraint free-form shell habits keep violating, worth a small script with a stable interface, and when it serves one of the kinds below — as the entry point, as one of the concerns that entry point asks rather than repeats, or as the suite that checks them. Discover what exists by listing the folder: the shelves and the criteria that separate them are named below, and this page does not inventory them ([Documentation → Content Rule](../../docs/documentation.md#content-rule-no-fabricated-or-redundant-provenance)). A module with no command line declares no help, because it is reached by an import rather than by a command; each module's docstring says what it provides.

**Everything this project has developed as a script is provisional and is eventually to become real code in modules.** That is not a demotion of these files — a need earns one here when a script is the right shape for it, and a need that has outgrown a script is not served by a better script — but it is the direction of travel, and it is why a folder under [`modules/`](../../modules/) rather than a `.py` file here is where a concern comes to rest once its subject is settled. The scripts this most affects are the ones inside a module: every `.py` file under [`bundles/khayyam/targets/go/`](../../bundles/khayyam/targets/go/) is provisional in that standing, and the mechanism that read the Go residue moved out of that folder for want of a subject to match it, while the Rule documents it applied stayed where their subject was ([`declaration-rename.md`](../../bundles/khayyam/rules/declaration-rename/declaration-rename.md):89). Nothing here is permanent either; what is permanent is the standing, not the file.

### Three shelves, and what separates them
A file's shelf is decided by **what the file belongs to**, not by who calls it. That question has one answer per file, and answering it any other way is how a folder fills with files whose names say nothing about what they do.

**The top of this folder is Memar's own.** The launcher, the tools it routes to, and the modules only Memar's own tools use. A file here either declares a command line — in which case its name carries the hyphen that separates its domain from its subject, because that is how a caller types it — or declares none, and is then reached by an import, which is the only form the interpreter accepts. [`memar-content.py`](./memar-content.py), reached as `memar content`, is general-purpose rather than part of the skill, which is why it sits here and the skill reaches it only through `memar`.

**[`machine/`](./machine/) is the machine's, not Memar's.** The filesystem and the environment, and the one place a session's identity is minted: the interfaces Memar has to reach the machine through, none of which it owns. [`host/`](./host/) is the same idea for tools rather than interfaces — tools the machine already has, wrapped in the constraints a session improvises past. Both paths carry that claim; read [`host/README.md`](./host/README.md) for why neither of them is under `memar`, which is the point of naming them at all.

### How a file is named
A name states its domain before its subject: the surface the file acts on, then what it does on that surface. A bare name that is only a role or a mechanism — a lock, a target, a decision about what a copy leaves out — states no domain at all, and a reader who has just listed this folder is owed one. The domain comes first because that is what says whether the file is worth opening.

**The domain is a shelf wherever a domain has more than one file, and an underscore-prefixed module wherever it has exactly one.** Inside a shelf the prefix is a second domain, not a repetition of the first — a reader listing `machine/` sees `fs_` and `env_` and knows which machine interface each answers before reading a word of it. A domain with a single file has no second word to put in a folder name, so it stays at the top with a `memar_` prefix, which there is a complete name rather than a truncation.

**Which form a name takes is settled by how the file is reached, not by taste.** One only ever run is hyphenated: a hyphen is what a caller types and a shell splits on, and no interpreter will accept it as a module. One a sibling imports is a module path, because that is the form the interpreter resolves. A file that would be both has no legal spelling, so **no file here is both**, and that is the condition the rule rests on rather than a coincidence: a run file that needs another run file asks it as a child process, which is what lets both keep the hyphen naming their domain first. Two names that differ by one separator are the sanctioned form of this split, not an accident of spelling: [`memar-session.py`](./memar-session.py) is run and [`memar_session.py`](./memar_session.py) is imported, and the separator is the only thing that says which. An underscore is never a hyphen in disguise: in an imported name the boundary is carried by the shelf or the prefix and by the order of the words, and no file here is made loadable by a trick that would let a hyphen stand.

**Where a name or a path is decided is itself one file's business, and it is stated there.** A name or a path borrowed across modules is one two modules can disagree about, so each is owned by the module that answers the question it belongs to, and that module's docstring says so.

### How the files reach each other
The Python files here import each other from disk, inside the checkout the bootstrap obtained: one implementation of each concern, no assembled second copy. **Running a file puts its own folder on the module search path, so no file in this folder declares one.** A module inside a shelf is only ever imported, and its importer already put this folder there. The files that do declare one are those run from *inside* a subfolder — the two under `host/`, whose names cannot be run as `-m` — and the test suites, which are run from their own `tests/` folder. Whether a folder is a Memar repository is asked through [`memar_repository.py`](./memar_repository.py), so no shell answers it differently from the installer.

### Where a check goes
A file that checks another file in this folder is not beside what it checks and is not another angle on it: a check states the expectations of a process, and the installer's process is not its file. Such a file therefore goes in a `tests/` folder inside the folder that owns what it checks, named for that subject and carrying no marker, per [Test Placement](../../modules/process/test/rules/test-placement/test-placement.md) and [Test Naming](../../modules/process/test/rules/test-naming/test-naming.md). A shelf owns its own `tests/`, so [`machine/tests/`](./machine/tests/) sits beside the concerns it checks rather than in one folder at the top whose owner would have to be decided per file. The folder states the role, so the name does not have to, and every file in this folder stays a file this folder is for.
