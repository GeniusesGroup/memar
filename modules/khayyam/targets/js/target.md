# Khayyam JavaScript Target
## Abstract
This document is the JavaScript emit target of the Khayyam toolchain: what a `.kh` unit becomes when it is compiled for a JavaScript host, how a name in a method body is read, how a body-less method reaches an implementation, how the link-first rule decides between a linked implementation and a compiled unit, what a build repeats and what it does not, and what a host is asked for when it runs a program. Three claims hold the target. The artifact decides nothing: every name, type, and call in an ES module is read out of the target-independent representation, and the one place where a body is read into commands is stated here as part of that representation rather than as a private step of this backend. A question the language owns is answered in the language: where the compiler needs a behaviour, the library that carries it is written in Khayyam and compiled by this backend, and the host supplies only the mechanism underneath it. And the distance between the language as it stands and a compiler written in Khayyam is measured here rather than argued.

## Introduction
### Motivation
The target is where the toolchain's two disciplines become checkable or fail: a JavaScript backend that never becomes the hidden specification of Khayyam's semantics, and a frontend that never treats a library name as an intrinsic ([execution.md → Disciplines binding every milestone](../../execution.md#disciplines-binding-every-milestone)). A backend that can lower anything is exactly the failure those disciplines name, so what this target is allowed to read and what it must refuse is stated as its contract rather than discovered in its code.

### Methodology
Each claim below is stated with the document section it comes from, and each output shape was fixed by a test written before the code that produces it: the commands a body may hold ([body.test.ts](../../core/test/body.test.ts), beside the module it belongs to), the shape of an ES module ([emit.test.ts](./test/emit.test.ts)), the shape and the resolvability of a link-map entry ([link.test.ts](./test/link.test.ts)), and the two facts that a program runs ([run.test.ts](./test/run.test.ts) under Node, [browser.check.ts](./test/browser.check.ts) in a browser). Where the language states nothing, this document says so and the question is carried in the paired [handoff](./target.handoff.md) rather than answered here. Where the compiler needs a behaviour, the answer is an abstraction in Khayyam, modelled under [`modules/process/`](../../../process/) before it is written anywhere, and the host supplies the mechanism it is built on.

## Explanation
### What this target owns
The toolchain's pipeline is source → frontend → semantic representation → target → artifact → host ([execution.md → Pipeline](../../execution.md#pipeline)). This target holds everything from the representation to the host: reading a method body's commands, resolving the names a body reaches for, writing one ES module per unit, the map that decides what is linked instead of compiled, and the request a host makes to run a program. The frontend and the shared representation are not this target's, and neither is the host: the runtime is configuration plus the host JavaScript engine, and entry and lifecycle are not grammar ([Compiler → Entry and lifecycle are not grammar](../../../../docs/protocols/computer/compiler.md#entry-and-lifecycle-are-not-grammar)).

### The program a target is given
A compiled program is a set of units and nothing else. For each unit it carries the URI, whether the unit is compiled or linked, the types the unit can name and the unit that declares each, each capsule's fields, each method's three call groups, its commands, and what kind of method it is, the exports the unit is known by outside itself, the modules its artifact imports with the local name each import is known by inside it, and the methods whose implementation the link phase supplies. The compiler builds that from [`analyze`](../../core/src/frontend.ts) plus the commands read from each body; the backend reads nothing else.

A body's text is read into commands by [`readCommands`](../../core/src/body.ts), which uses the same scanner as the frontend and reports a fault with the same labels a `.kh` unit is refused with. The commands are part of what the backend is given rather than something it derives, which is what keeps the backend a translation: a name it cannot resolve is a refusal, never a guess.

### The commands a body may hold
The grammar ships no control-flow keyword, no operator, and no literal of its own, so the set of forms a body may contain is small and every one of them is a document's own claim:

| Command | Form | Stated by |
| --- | --- | --- |
| `declare` | `vr {name} {type}` | [Variable in Khayyam](../../../../docs/khayyam/variable.md) — variables may be declared in files and in method bodies |
| `scope` | `tp {name} sc { … }` | [Khayyam → Scope](../../../../docs/khayyam/khayyam.md#scope) — a code scope is inert until a library method drives it |
| `invoke` | `recv.Name(a, b)(c)` | [Khayyam → Method Invocation Rules](../../../../docs/khayyam/khayyam.md#method-invocation-rules) — one dot, both call groups written |
| `return` | `return` | [Khayyam → Scope](../../../../docs/khayyam/khayyam.md#scope) — an IR marker that ends with a line break and carries nothing on its line |

`sc` is the one subtype a body admits; the other four are declarations of a file. A body carrying anything else is refused at the point it stands, under the frontend's own labels, so a compiler never lowers a body it only partly understood. The three call groups of a method and the two groups of a call are both mandatory, and a body that writes a call with one group is refused the same way — which is why the library below writes `self.Revise(condition)(reversed)` rather than what looks like the shorter spelling.

Two readings the documents leave open are taken here, and both are recorded in the paired handoff: a body is read in two passes, so a driver may name a scope declared below it, and a name a body reaches that no declaration binds is a refusal rather than a type.

### A field is a variable
A capsule field is what a `vr` is - a slot the program writes through and a call hands over. It is reached the only way a body may reach its own capsule state: `self.field`. The privacy the language states is about a *passed* capsule fields ([Encapsulation -> Capsule Structure and Privacy](../../../../docs/khayyam/encapsulation.md#capsule-structure-and-privacy)), and a method reaching its own capsule state is what that rule leaves to the capsule own methods. So a field may be the receiver of a call and it may be handed to a method; the emitted class holds one cell per declared field, and the host still creates every value (it hands the values over, not the slots).

A call writes into a name the body binds, and a field is not one: [bootstrap/write-field.kh](./bootstrap/write-field.kh) is refused for reaching for one, and it is refused on purpose rather than held open. A capsule state changes through a method of that capsule, and every other method goes through that one - so the endorsed shape is a method that hands its field to the method that writes it, which needs nothing more than a field read and a variable handed over ([bootstrap/state.kh](./bootstrap/state.kh), and the write landing is held by [run.test.ts](./test/run.test.ts)). What makes that shape work is that a call hands over the slot and not what is in it, which is the language own statement that a call passes every variable of a call strictly by reference and that the three groups are one list of variable references; [run.ts](./src/run.ts) is where the host entry becomes one, and a supplied implementation is handed the same slots, because the owner of a body-less method is the callee of last resort.

### The artifact of one unit
Each compiled unit is one ES module. The module exports a class per capsule, a marker per abstraction, and a function per method; a method's exported name joins the owner type's name and the method's name with a `$`, and every other name the module writes for itself begins with one — no identifier in the language can hold a `$` (the Identifiers paragraph of [Khayyam](../../../../docs/khayyam/khayyam.md)), so a generated name can never collide with a name the author wrote. Imports are relative and named, never bare, so a browser resolves the artifact's whole graph without a bundler.

A variable is a cell. The language passes every variable of a call strictly by reference ([Khayyam → Method](../../../../docs/khayyam/khayyam.md#method)), so what a call writes into is a slot: the caller declares `{ value: undefined }`, hands the slot over, and the callee writes through it. An influencing variable is handed over as the value the slot holds, and the influenced group is handed over as the slot itself. The three groups of a signature are one call in the artifact, because the language states that in the underlying layer they are one list of variable references and the three groups exist so a reader can see which variables influence and which are influenced ([Method in Khayyam → Key Rules](../../../../docs/khayyam/method.md#key-rules)).

A scope is emitted as a function declared inside the method that holds it, before the statements of that method. That is the lowering the language describes — a compiler of this language lowers `sc`-driven branches to internal jumps, and `return` is an IR marker rather than a keyword ([Khayyam → Scope](../../../../docs/khayyam/khayyam.md#scope)) — and it is why a driver may name a scope declared below it.

### The three kinds of body-less method
A body-less method is the language's own signal that something comes from outside the method, and what comes from outside depends on the method's owner ([Khayyam → Method, Body-less Methods](../../../../docs/khayyam/khayyam.md#method)):

- On a **capsule** it is the foreign-function-interface form, and the implementation arrives when the program is linked and run. The module exports a `supply` function for that, and the host hands each unit the implementations of its own.
- On an **abstraction** it is the contract form, and it asks of an implementing capsule rather than of the link phase. No artifact carries one, and a call whose receiver is typed as an abstraction is refused where it stands: this target resolves a call by the receiver's declared type and has no dispatch over capsules it did not see, which is the boundary the [Compiler → Designated pure operations](../../../../docs/protocols/computer/compiler.md#designated-pure-operations-may-run-at-compile-time) line between compiling and dispatching points to and this milestone has not reached.

### The link phase
The map that decides what is linked is [`link_map.json`](./link_map.json), a table keyed by a unit's URI. An entry names the JavaScript module that provides the unit, the protocol document the implementation was checked against, what was checked with the section of that document each check was read at, the unit's declarations as the map states the module has them, and the exports that provide them. Two things follow from that shape. A link is never silent: an entry that names no protocol document, records no check, provides nothing, declares nothing, or records a check at a section the document does not have is refused before anything is compiled. And a linked unit is never thinner than the unit it replaces: its declarations stand in for the `.kh` file's, so an abstraction's methods keep a stated signature even though no source declares them here.

The rule the map is read under is link-first: a unit with a conformant equivalent is not compiled, and a unit without one is compiled from its own source. An entry whose module cannot be read is not a link, and the unit falls back to its own source. What a linked module must look like is this target's convention and not the language's: a method is reached as `exported(owner, …influencing, …influenced)`, the owner first — the parent type itself where a call is made on the parent type — the influencing variables as the values the caller holds, the influenced variables as the slots the caller declared, and a scope as the function the compiler emitted for it.

The map holds no entry, and that is its state rather than a gap in the rule: the archived sources the link-first decision rests on are not in this repository, and a conformant implementation written here instead would answer a language question in another language. The rule, the entry's shape, and the fallback are held by the tests over fixtures; what an entry is checked against is the map's own record, and the protocol document it names.

### Running a program
A host is asked for one entry, and the request is configuration rather than grammar: which unit declares the entry method, which method it is, what the call is made on, the influencing values, and the implementation of each body-less method keyed by the unit that declares it. [`run`](./src/run.ts) loads every unit the program stands on, hands each the implementations its own body-less methods are waiting for, builds the owner, and makes the call. It reads no `.kh` and holds no opinion about what the program means.

What a host supplies is what the program did not write, and the language owns everything above it. The language has no primitive types, no literal, and no construction form ([Khayyam ? Type Principles Realized](../../../../docs/khayyam/khayyam.md#type-principles-realized)), so every value a program handles was produced outside it � by a method whose implementation the host supplied, which is the link form the language names for a body-less method on a concrete capsule. What belongs above that � a conditional, a text, anything a program composes out of � belongs to a Khayyam library, and a Khayyam library belongs with the rest of the library under [`modules/`](../../), not in this target's folder: the module README states that language-wide library source lives in the other module folders, and the architecture's own method says a model settles before code is written. Which is where the control-flow library is: modelled at [modules/process/control-flow/model.md](../../../process/control-flow/model.md), and not written, because that model carries the questions its writing waits on.

### What the demo
[`demo/greeting.kh`](./demo/greeting.kh) is the program: a capsule that holds a value, and a method that calls a behaviour of the owner and a behaviour of the value it was given. It needs no library control flow, which is what the plan's third goal asks for. [`demo/node-host.js`](./demo/node-host.js) is the host on Node and [`demo/browser.html`](./demo/browser.html) is the same host in a browser, which loads what the build wrote as an ES module and runs it with no bundler and no build step of its own.

### Unchanged work is not repeated
A build is [`build`](./src/cache.ts), and it keeps what the last build left beside the artifacts under `build/.cache/`. A unit's key is the hash of its own source, this target's three versions, the host profile, the link map's own text, and the keys of the units it names — the key list the plan states. A unit is still the same unit when its source is the same and every unit it names is, and a unit that is stands in for itself: it is not read, not analysed, and not emitted, and a caller resolves names against the declarations the stored record carries. So a build over unchanged sources compiles nothing and writes nothing; a change to one file compiles that file and the units that name it and no other; and a change to a version, to the host profile, or to the map reaches every unit.

Two things about a build are the build's own and are reported rather than inferred: a file is written only when the text it would hold is not what it already holds, so a source change that no artifact shows writes nothing; and a unit that names itself, directly or through another, has no key and is compiled every time, which is the conservative answer rather than a wrong one.

### What a compiler written in Khayyam would need
The direction this target exists for is a compiler written in Khayyam, and the language as it stands is measured against that in [`bootstrap/`](./bootstrap): a unit per need, each naming the document section it depends on, each compiled by this target so that what it does is a measurement rather than an argument. The probes and what they show are in the paired [handoff](./target.handoff.md); what belongs to the language's documents and not to this target is carried there as an open question.

### What the target may not do
The backend recognizes language primitives only, and no library name is an intrinsic of it: a conditional would be a unit the program includes, not a name the compiler knows ([Compiler ? The compiler recognizes language primitives, not library names](../../../../docs/protocols/computer/compiler.md#the-compiler-recognizes-language-primitives-not-library-names)). Nothing under `build/` is read as if it were a representation; only the backend writes it and only the host executes it ([execution.md ? Compile cache](../../execution.md#compile-cache)). And where the target needs a behaviour the language does not have, the answer is a Khayyam library modelled where that concept belongs and written after the model settles � not a JavaScript module beside it, and not a `.kh` file in this folder.
