# Khayyam JavaScript Target Handoff
Open work for [target.md](./target.md). Entries are mutable current state — revised as each item moves, removed when it resolves or is dropped. Every open question below names the file and the line it can be read at, so a session that starts cold can go straight to it. See the repository's [documentation-handoff.md](../../../../docs/documentation-handoff.md) for what a handoff is.

## Topic & Purpose
The JavaScript emit target of the Khayyam toolchain: what a `.kh` unit becomes when it is compiled for a JavaScript host, and where the language's own libraries sit between the two. The plan that governs the order is [execution.md](../../execution.md); this file carries the state a continuing session needs and nothing it can re-derive from the tree.

## Status
Active

## What the toolchain is asked to do, and what it does now
- **`core/`** reads a file for a compiler and holds the semantic representation a target is given ([core/src/sr.ts](../../core/src/sr.ts)). A method's body is carried there as text, so the commands a body holds are read here.
- **`targets/js/bootstrap/`** holds one probe per thing a compiler written in Khayyam needs, each compiled by this target, so that the distance between the language and that compiler is measured rather than argued.
- **`modules/process/control-flow/`** holds the model of the control-flow library a compiler written in Khayyam reaches for, produced with the architecture's own method before any of it is code ([model.md](../../../process/control-flow/model.md), [model.handoff.md](../../../process/control-flow/model.handoff.md)). No library is written there yet: the model carries the questions its writing waits on. A Khayyam library belongs with the rest of the library under `modules/`, not in a target's folder, so none is written here.
- **`core/src/body.ts`** reads a body's commands and refuses anything outside the four forms the language documents admit, under the frontend's own labels. It was a module of this target and the owner moved it to the frontend, since the reading is the same for every target and the module's own rule is that target-independent code does not live inside a target folder.
- **`targets/js/src/program.ts`** reads a unit and everything it reaches, asks the link map before a unit's own source, tells the three kinds of body-less method apart, and holds what the backend translates.
- **`targets/js/src/emit.ts`** writes one unit as one ES module, resolving every name before it emits anything.
- **`targets/js/src/cache.ts`** is the build: what the last one left beside the artifacts, what a key is made of, and what this build compiled, stood in for, and wrote.
- **`targets/js/src/link.ts`** and **`link_map.json`** decide what is linked instead of compiled, and hold the record that lets a link stand in for compiling a unit. The map holds no entry.
- **`targets/js/src/run.ts`** runs one entry of a program on a host. Entry and lifecycle are the host's configuration, not the language's.
- **`demo/`** is the program and the two hosts it runs under: Node and a browser that loads the artifact as an ES module with no bundler.

## The goals this target answers, and what each still owes
The goals and their checks are [execution.md → The goals, in the order they come](../../execution.md#the-goals-in-the-order-they-come).

1. **Goal 3 — a `.kh` source runs on a JavaScript host.** Owed: nothing further for the check as written. `demo/greeting.kh` compiles to an ES module, the module runs under Node ([run.test.ts](./test/run.test.ts)), and the same artifact loads in a real browser with no bundler and runs there ([browser.check.ts](./test/browser.check.ts)). What the answer rests on is stated under the Open Questions below: a program cannot create any value of its own, a body cannot read a field of its own capsule, and the reading of a body belongs to the frontend but is still not carried by the representation.
2. **Goal 4 — the `.kh` library is reachable, link-first.** Owed: the map's entries. What is answered: the rule is in the compiler — a unit with a conformant equivalent is not compiled, a unit without one is compiled from its own source, and an entry whose module cannot be read falls back — with the entry's shape and every check an entry must answer held by [link.test.ts](./test/link.test.ts) over fixtures, and a program that includes a unit the map stands in for is what the rule is about. What is not: the map holds no entry. The owner's direction for that half is a module that names the interfaces a program may call, so that a host picks an interface and a call in Khayyam becomes the same call in JavaScript; an entry written here before that module exists would answer a question the language owns.
3. **Goal 5 — a reader runs a `.kh` file without a bundler.** Owed: the page that takes a file. What is answered: an artifact loads and runs in a browser with no bundler and no build step on the page ([browser.html](./demo/browser.html)). What is not: nothing in this target compiles inside a browser, which is the goal's own subject.
4. **Goal 6 — unchanged work is not repeated.** Owed: nothing for the check as written. [cache.test.ts](./test/cache.test.ts) holds all three of it: a second build over unchanged sources compiles nothing and writes nothing; a change to one file compiles that file and the units that name it and no other; and a change to a version, to the host profile, or to the map reaches every unit. What the cache does not yet cover is the key the plan names for a change to the frontend or the backend *as code*: the versions are named constants of this target, so a change to them is a change to the constant and a change of the constant is a change of the toolchain.

## Decisions
- **The command set is what the language admits, and nothing else** — Decided. A body may hold a variable declaration, a scope, a method invocation, and the `return` marker, and every other form is refused at the point it stands. Reason: the grammar ships no control-flow keyword, no operator, and no literal, so a body that carried anything else would be carrying something the language does not have; a backend that lowered it would be deciding what the program means.
- **Where the target needs a behaviour, the answer is a Khayyam library, and the library is modelled where the concept belongs before it is written anywhere** - Decided (owner, 2026-09-28; revised 2026-09-29). What the target needs is modelled at [modules/process/control-flow/](../../../process/control-flow/) and no `.kh` library is written in this folder: the module README places language-wide library source in the other module folders, and the architecture's method says a model settles before code is written. Reason: a question the language owns is answered in the language, and the two answers are at different heights - the library prepares the Khayyam compiler that will later compile itself, while this target takes what the model settles and no more.
- **A body is read in two passes: what a block binds, then what it does** — Decided. A block's cells and its scopes are lifted out of its command order before its statements, and a scope is emitted as a function declared before them. Reason: the language terminates a command with its line's break and orders nothing else, and the control-flow protocol's own example names a scope on the line above the `tp … sc` that declares it. This is the toolchain's own reading; whether the language says anything about it is a question for the language handoff.
- **Every variable is a cell, and a field is a variable** - Decided (owner, 2026-09-28; the field half 2026-09-29). A `vr`, every parameter of a call, and every field of a capsule are one object the caller hands over and the callee writes through; a field is reached as `self.field` and nothing else. Reason: the language passes every variable of a call strictly by reference, so one representation covers every role a slot plays; and the privacy the language states is about a passed capsule's fields, which leaves a method reaching its own capsule's state to the capsule's own methods. The one position this leaves open is a call *given* a field to write, and that is a rule of this level rather than a claim about the language.
- **The three call groups are one call in the artifact** — Decided. Reason: the language states that in the underlying layer the three groups are the same thing and the separation exists so a reader can see the roles. Both groups of a call are still written in the source, because the language says the call writes both.
- **A generated name begins with a `$` and joins a method's owner and name with one** — Decided. Reason: no identifier in the language can hold a `$`, so a name the artifact writes for itself can never collide with a name the author wrote, and a collision needs no rule to avoid it.
- **A body-less method is one of three things, told apart by its owner** — Decided. A body with commands is compiled; a body-less method on a capsule is the link form and is supplied when the program is run; a body-less method on an abstraction is the contract form, no artifact carries one, and a call whose receiver is typed as an abstraction is refused where it stands. Reason: the language names the two forms separately, and a contract asks of an implementing capsule rather than of the link phase, so treating it as a missing implementation would both invent an obligation and refuse a well-formed unit.
- **This target has no dispatch over capsules it did not see** — Decided for the first target. A call is resolved by the receiver's declared type. Reason: a call on an abstraction is the form the language leaves to the compiler's choice between monomorphization and dynamic dispatch, and nothing in this milestone is a dispatch table.
- **A link-map entry states the unit's declarations as well as its exports** — Decided. Reason: a linked unit is not compiled, so nothing else states its abstraction's method signatures; a link that carried only runtime values would leave the contracts of the unit it replaces stated nowhere.
- **An entry that cannot be checked is refused before anything is compiled** — Decided. An entry naming no protocol document, recording no check, providing nothing, declaring nothing, or recording a check at a section its document does not have is refused, and the repository's own map answers the same check as any other map. Reason: the per-entry record is the only thing that keeps linking from silently replacing the representation as the source of truth.
- **An entry whose module cannot be read is not a link, and the unit falls back to its own source** — Decided, following the link-first decision. Reason: the decision keeps a failing entry falling back to compiling, and a module that is not there cannot be conformant to anything.
- **A body-less method on a capsule reaches its implementation through a `supply` function the module exports** — Decided. Reason: the language says the implementation is provided externally at link time and says nothing about the mechanism; the mechanism is this target's, and a second target will have its own.
- **The browser load check runs in its own `node --test` invocation** — Decided. Reason: it spawns a real browser, and running it beside the language server's process tests made one of those fail on timing that is not its own. The file carries `.check.` so the ordinary glob does not pick it up, and the module's test script runs it second.
- **A standing unit is not read at all, and a build reports what it did** — Decided. A build's driver is offered the units an earlier build left before it reads any source, so a build over unchanged sources parses nothing; and a build answers with the units it compiled, the units it stood in for, and the artifacts it wrote. Reason: the plan's check is about what a build repeats, and a check that can only be read out of a stopwatch is a check a reader has to trust.
- **A file is written only when its text would change, and a unit that names itself has no key** — Decided. Reason: the first is what "unchanged work is not repeated" means on disk, and the second is the conservative answer where a key cannot be computed rather than a wrong one.

## Ambiguities Resolved
- **Where a branch body's driver stands.** A driver is a statement of the enclosing method and the scope it drives is a declaration of that same method, so the artifact emits both inside one function with the scope ahead of the statements. A body read in one pass would refuse the program, because a driver names a scope it has not met yet.
- **A call written on the parent type has no value to call on.** The parent type itself reaches the implementation as the owner, which is what the language's own two call shapes say — `W32.Sum(a, b)(total, err)` names the parent type before the dot, and the body does not invoke `self`.
- **The type of a scope argument is unstated in the documents, so the model declares one.** The control-flow model declares the scope as the shape the compiler emitted and carries the open question of what a scope is in the language itself; the protocol allows a realization to express the rule through named scopes or explicit closures.
- **Which group a variable a method writes belongs in.** The three groups of a signature and the two of a call are both mandatory, and writing a variable a callee writes into the influencing group compiles into a call that hands over the wrong thing. The language's rule caught two such mistakes in the library this work wrote, and the tests keep both.

## Open Questions
Each entry names the file and line it can be read at. What is open in an entry is that nothing has answered it yet, not that the answer is hard to reach.

### A body is read by the frontend, but the shared representation does not carry the commands
- State: the reading is a module of `core/` now, so a second target reads a body the same way this one does. What is left is the other half: the representation still hands a target a method body as text, and the target is the one that asks for the commands. Nothing in the tree says whether a body belongs in the representation as a list of commands or as text a target reads, and the toolchain category for host-independent work is an open question in the parent handoff. It is also the first thing the self-hosting phase needs.
- Anchor: `modules/khayyam/core/src/sr.ts:78` (the body as text) against `modules/khayyam/core/src/body.ts:13` (the commands it is read into).
- Blocks continuation: no for a second target, whose reading is this one; yes for a compiler written in Khayyam, which would have to read a body through the representation rather than through a module of its own host.
- Path: the owner of `core/` decides whether `analyze` returns commands. If it does, a target is handed what it translates and the frontend owns the refusal labels outright; if it keeps the text, a target keeps asking for the reading and the module stays a frontend utility every target imports.

### A link cannot stand in for a `.kh` file that is not there
- State: the frontend resolves every `in` URI through the injected file system before this target is asked anything, and refuses a unit whose URI resolves to nothing. So a link can only replace a unit that exists as source: the map is asked before the source is read, and a unit whose file is missing is refused by the frontend's own label before the map is consulted. Link-first as the parent decision states it is therefore bounded by the frontend's import resolution.
- Anchor: `modules/khayyam/core/src/frontend.ts:42` (the frontend reading every inclusion) against `modules/khayyam/targets/js/src/program.ts:145` (the map asked before the source).
- Blocks continuation: no for the demo; yes for filling the map with implementations whose `.kh` source is absent, which is the case the archived library would have been.
- Path: the toolchain's ruling, because it changes what `analyze` is for — whether a resolvable URI is a question the frontend answers or a question a resolver answers, which is where dependency resolution and the rule engine's work already point.

### The archived memar-js sources the link-first decision rests on are not in this repository
- State: the decision records that conformant JavaScript for much of the library already exists in archived memar-js sources, and its assumption carries the stability Unexamined. Nothing in the tree holds them: no directory, no vendored copy, no URL. The map therefore holds no entry, and the rule is held by tests over fixtures rather than by a link in the repository.
- Anchor: `modules/khayyam/execution.handoff.md:40` (the decision naming the archive) against `modules/khayyam/targets/js/link_map.json`.
- Blocks continuation: yes for goal 4's first half, since the map is meant to be filled from that archive.
- Path: the archive is located and read. Filling the map with implementations written here is the alternative, and the reading behind this target's work is that an entry is a conformant implementation that already exists rather than one produced to fill the table.

### The corpus under `modules/` is not yet reachable

The corpus's method bodies are carried the same way, but the corpus carries what the parent handoff lists — a qualified type reference nothing resolves, and one URI that resolves to nothing. A corpus file with a qualified reference is refused here, at the point the reference stands, because the representation does not say what a qualifier denotes.
- Anchor: `modules/khayyam/targets/js/src/emit.ts:231` (resolution refusing a name no type answers) against the qualified-reference question in [execution.handoff.md](../../execution.handoff.md).
- Blocks continuation: yes for goal 4's second half over the corpus, and for the M2 scope boundaries the parent handoff records.
- Path: the parent handoff's rulings on a qualified reference and on a body read in one or two passes, then the matrix rows that fix them here.

### What a compiler written in Khayyam lacks, measured
- State: seven probes under [`bootstrap/`](./bootstrap), each a unit a Khayyam-written compiler would need, each compiled by this target so that what it does is a measurement ([bootstrap.test.ts](./test/bootstrap.test.ts)). The order below is the order a compiler needs them, and the last two are what it can already do.
  1. **The characters of its own input** — [character.kh](./bootstrap/character.kh). Nothing is refused: the unit reads, and the only route to a character is a method with no body, which the language's link form exists to arrange. A compiler that cannot see the text it is handed cannot begin.
  2. **A place to put what it has read** - [state.kh](./bootstrap/state.kh). Compiled, after the owner settled what a field is for: a capsule declares a field, a method of that capsule reaches it as `self.field` and makes a call on the value it holds. The slot is the language's and what is in it is the host's, so a compiler can hold a position and move it.
  3. **An instance it made itself** — [construct.kh](./bootstrap/construct.kh). Nothing is refused, and that is the finding: a body declares the slot and calls a method that writes it, and what fills the slot is still the host's.
  4. **Repetition** — [repeat.kh](./bootstrap/repeat.kh). The probe's only command is a scope, and what it can drive is nothing. There is no repetition in the grammar, which is settled; what is open is that the library which would supply it does not exist yet, and the one that does is the jump this target's control-flow unit is built on.
  5. **A behaviour as a value** — [behaviour.kh](./bootstrap/behaviour.kh). Refused by the frontend's own label: `unbound-type-name`. The language admits a method in an argument position, and no unit can declare the type that holds one.
  6. **What a body already does** - [compose.kh](./bootstrap/compose.kh). Compiled: a scope, a driver that drives it, a call that carries a value into an argument and receives what the call wrote into a slot, and an early return. Everything a library in this language is made of is here, which is what makes the five above findings rather than a blanket refusal. The probe needed no library, and it answered two questions by the way: the parameters of the method itself are not slots a call may write (a body binds them with `vr`), and a signature is not followed by a body.
  7. **The one question this level holds open** - [write-field.kh](./bootstrap/write-field.kh). Refused, and the refusal is the finding: a call may be given a name the body binds to write, and a field is the same slot, and whether a field is one of those names is a rule of this level rather than a claim the documents make. The probe carries both calls so that the difference is one line.
- Anchor: `modules/khayyam/targets/js/test/bootstrap.test.ts` and the seven units beside it.
- Path: items 1 and 3 are the boundaries of the language itself and are measured rather than argued: the first wants a text capability in the language or a library over one, the second a construction form. Item 2 is the field-access question below and is the one on the critical path - a library that holds a cursor, which is what a reader is, needs it, and the owner has since narrowed what reading a field is for (a variable handed to a method), which settles the use and leaves the write open. Item 5 is the method-as-value question below and is *not* on that path, because a scope already carries a body to a method that takes one. Item 4 wants the control-flow library the model already is, and a collection type the language does not have; the collection abstractions of the corpus are declarations with no bodies.

### A capsule's own fields are not readable in a body
- State: settled, in two rulings rather than one. What a field is *for* is settled: a field is a variable, and a variable is handed to a method, so a body reaches `self.field` as the receiver of a call and as an argument. Whether a *call may be given a field to write* is settled too, and against it: a capsule state changes through a method of that capsule and every other method goes through that one, so nothing a method could be given to write directly is worth admitting - a body that reaches for one is a body whose logic is written badly. The language states the privacy it intends (docs/khayyam/encapsulation.md -> Capsule Structure and Privacy, and docs/khayyam/khayyam.md -> Method), and what it does not state is what a body statement may write, which is this toolchain rule and not the language claim. The measurement that made the endorsed shape possible is in the same pair: a call hands over the slot rather than what is in it, which the language states and this target was not doing.
- Anchor: `modules/khayyam/lsp/src/semantic.ts:319` (the role at the declaration) against [Encapsulation → Capsule Structure and Privacy](../../../../docs/khayyam/encapsulation.md#capsule-structure-and-privacy).
- Blocks continuation: no. Nothing in the language, nothing in this target, and nothing the control-flow model is waiting on.
- Path: none, and that is the point of the ruling: the field is not a gap to be closed but a shape to be written. What a library still cannot do is hold a value it was never handed ([construct.kh](./bootstrap/construct.kh)) or reach a character of a text ([character.kh](./bootstrap/character.kh)), and those are the language boundaries above this one.
- Blocks continuation: no for this target program; no for a library that is handed its state; no for a compiler written in Khayyam, whose every loop over what it has read is now a method of its own capsule handing its field on.
- Path: none. The endorsed shape is measured by [run.test.ts](./test/run.test.ts), where a host supplies the method that writes and the test reads the field back.
- State: the language admits a method in an argument position and nothing states how a bare name writes one, so a body that passed a method as a value is refused here. A method attached to a capsule is written with the receiver name in front of the dot, and whether a bare name may stand for one is what is unstated. The control-flow model did not need it and says so: the conditional above a scope is the scope own value, so nothing that model proposes takes a method as a value - but a library whose behaviour takes another behaviour cannot be called from a program.
- Anchor: `modules/khayyam/targets/js/src/emit.ts:231` against [Method in Khayyam → Type-level arguments for `sc` and `mt`](../../../../docs/khayyam/method.md#type-level-arguments-for-sc-and-mt).
- Blocks continuation: no for this target; yes for a higher-order library.
- Path: the same question as the previous one, and the owner of the receiver-method-names rule may hold part of it.

### The browser load check needs a browser

On this machine both are installed and the check runs, and it is the only check in this target that depends on anything outside the toolchain.
- Anchor: `modules/khayyam/targets/js/test/browser.check.ts:58`.

## Assumptions
- **A body the documents do not show is refused rather than guessed** — Stability: Strong. Every command form is a document's own claim, and the refusal names the frontend's label at the line it stands on.
- **A host that supplies body-less implementations can create the values a program handles** — Stability: Strong. The language has no primitive type, no literal, and no construction form, so every value a program handles was produced outside it; what varies is only how the host produces one.
- **Relative specifiers are enough for a browser to load the artifact's whole graph** — Stability: Strong for this target (checked, in a real browser, with no bundler and no build step on the page); revisit if a host needs a bare specifier resolved by an import map.
- **The language's command set is complete as it stands** — Stability: Weak. Nothing in the documents forbids a new command form, and a form this target refuses today may be added to the language tomorrow. What changes it: a change to [Khayyam](../../../../docs/khayyam/khayyam.md) or [Method in Khayyam](../../../../docs/khayyam/method.md); the refusal is a label from the frontend's own list, so adding a form means a new label there first.
- **`core/`'s accept/refuse matrix and this target agree on what a unit is** — Stability: Strong for the forms this target reads; the corpus is not yet in that set.
- **A library written in Khayyam states the protocol it realizes in its own header, and its model states it before that** - Stability: Tentative. The comment policy sanctions prose in a `.kh` file where a documentation method does not exist yet, and a rule catalog is where a normative claim about such a library would belong; the owner of the rules catalog may say where such a record lives, and whether the model is the record or the header is.

## Proposed Next Steps
Ordered; each begins with a goal and a test, in the order [execution.md → How work in this toolchain proceeds](../../execution.md#how-work-in-this-toolchain-proceeds) fixes.

1. **Rule on the influenced group, in the language first, and the field-access one first.** The goal is that a call may hand a field on as a reference to write, which is what every library that holds state between two calls needs; the test is `self.field` in an argument position, and `self.field` in the influenced group of a call whose parameter is declared as a reference rather than as a name. The owner has settled the use of a field (a variable is handed to a method) and the reading is what is open, and it is the one question a compiler written in Khayyam waits on, because every loop over what it has read is a field.
1. **Model the control-flow concept, then write the library it settles.** The goal is that a program can branch and repeat in this language; the test is the model own open questions each closed with the document section it comes from, and a unit under [modules/process/control-flow/](../../../process/control-flow/) that compiles here. The field question is no longer among them. The model is [model.md](../../../process/control-flow/model.md) and its [handoff](../../../process/control-flow/model.handoff.md) names what it waits on; a model is not written into a target folder, and the questions in it are the language own, so they go to the language documents first.
3. **Write the first Khayyam library a reader needs: a text with a cursor.** The goal is that a program's own code can reach a character and hold a position; the tests are the two probes this folder already holds, asserting what they show today and what they would show after the ruling. Depends on (1) and (2).
4. **Model the module that names the interfaces a program may call, and fill the map from it.** The goal is that a host picks an interface and a call in Khayyam becomes the same call in JavaScript, which is the form the link map takes; the test is an entry whose checks name a protocol document and whose module implements what a Khayyam unit would have, for one interface. Depends on the model, and on a decision the owner has not yet made: the language admits no literal, so `Beep(500, 100, 5)` is not writable as it stands, and a primitive argument needs either a named capsule for it or a ruling that a literal may stand in an argument.
5. **Make the browser page take a file.** The goal is that a reader runs a `.kh` file without a bundler, not only an artifact this toolchain wrote; the test is a page that takes a pasted unit, compiles it through this build, runs it, and shows its output. Depends on the toolchain running in a browser, which is the step after it.
