# Khayyam Rule — Import Address Handoff
Open state for [import-address.md](./import-address.md). See the repository's [documentation-handoff.md](../../../../docs/documentation-handoff.md) for what a handoff is.

## Status
Active — ruled 2026-09-26 (owner) that the form of the value is a tool's rule rather than the grammar's, which is where the toolchain already stood.

## Decisions
- **The value is a URI, and the term stays** — Decided (2026-09-27, owner). A ruling the same session had the toolchain's records replace the word *URI* with *address*; that was overreach, and the term is restored. The position, stated in the owner's form: the value an `in` declaration carries is a URI, the language fixes no scheme for it, and the scheme is dependency management's choice — several schemes exist, and the one this repository writes (a repository-root-relative path) is its resolver's choice, not a requirement of the language. The language document's own import section is where the term stands ([Khayyam → Import Mechanism (`in`)](../../../../docs/khayyam/khayyam.md#import-mechanism-in): the file URI system is the source of truth, and which file URI resolves to which version is a build/tooling-layer concern). Restored in the rule, here, the rules index row, the [unresolved import rule](../unresolved-import/unresolved-import.md), the [toolchain handoff](../../execution.handoff.md), and the matrix's rows and comments. The rule's own name and folder are unchanged: the ruling settles the term the records speak in, and renaming the rule would move every link to it.
- **The grammar does not grade the URI's shape** — Decided (2026-09-26, owner). An earlier entry the same day ruled the extension mandatory in the grammar; that entry is reversed, and the language document's import section states only what is — the value is a URI, and the grammar states no spelling for it — with the enforcement where it belongs.
- **The base is the manifest of the module that wrote the URI, and it is a default rather than a fact** — Ruled (2026-09-29, owner), replacing the 2026-09-26 entry this line stood as. A URI is written relative to the module whose file carries it, not to the repository and not to the file's own directory. The reason is that a Module is not a directory: one repository holds a hundred modules and a hundred manifests, and there is no one place they all resolve from, so "the base" is a thing each module has rather than a thing a project has. What it replaced was not a fact that turned out to be wrong but one that was right for a day and then answered the wrong question — this toolchain implemented the repository root with a walk up for a version-control directory, which made the storage engine decide what a reader's file meant. [Knowledge → Identity Must Be Independent of Location](../../../../docs/knowledge.md) is the sentence that says so, and the walk is deleted with `lsp/src/root.ts`. **The default half is the part that matters for how this rule is written:** the earlier version stated the base as a plain fact and this toolchain read that as licence, so a reader is now told what it may assume *and* that a project may resolve from somewhere else provided it says so. What no project may do is resolve from something undeclared — a program's declarations must not mean different things in two directories with nothing on the screen telling a reader which.
- **The toolchain's behavior did not change with the ruling** — State. The strict check the earlier entry described is not in the toolchain: [core/src/frontend.ts](../../core/src/frontend.ts) resolves a URI and refuses only when nothing is behind it, and the matrix's two URI rows are accepts — one for a URI carrying no extension, one for a foreign extension — each naming dependency management and the resolver as what a URI is for.

## Open Questions
- **Whether a resolver may complete a URI.** Nothing in the toolchain forbids it, and the [manifest handoff](../../../../docs/khayyam/modularity.handoff.md) proposes exactly that for the `memar/` root. Whether completing a root or a stem is a *resolver's* power or a rule a resolver must hold is undecided, and it is the question that made the extension look like grammar in the first place.
- **What a URI may carry.** Directory segments and a file name are settled. A query, a fragment, a version marker — nothing raises them, and the rule does not introduce any.
- **Qualified references.** The resolver skips a reference containing `.` (`pkg.Type`) without a binding check, so a qualified name is currently unverified. Whether qualification is an addressing concern of this rule or a separate resolution rule is undecided, and it is entangled with the qualified-name resolution semantics the [toolchain handoff](../../execution.handoff.md) carries.
- **Whether the rule should grade anything at all.** If an organization wanted a repository-wide URI convention — one extension, one directory depth — that is a governance rule over the same subject rather than a gate, and the two classes would then share a subject and need distinguishing.
