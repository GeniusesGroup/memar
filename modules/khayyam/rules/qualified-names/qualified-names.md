# Khayyam Rule — Qualified Names
Khayyam's rules live one rule per folder under [`modules/khayyam/rules/`](../README.md), and this is the rule for declarations whose names would collide with another module's. It is a governance rule of this repository, and it is the mechanical half of a claim the language makes: [Khayyam → Import Mechanism (`in`)](../../../../docs/khayyam/khayyam.md#import-mechanism-in) holds that a name collision is an architecture error rather than a disambiguation problem, that the correct fix is one abstraction being the single owner of one concept, and that the language supplies no `as` alias to defer the question.

## The rule
A declaration carries its module's path at its definition site when its plain name would collide with another module's. `Stringer` in `codec/string/utf8` is declared `UTF8_Stringer`; `Duration` in `time/duration`, which already carries its module, is declared `Time_Duration` instead of being shortened. A collision found anywhere in a module is reported, not silently renamed at the import site.

A bare method name is a plain name too. A method keeps its bare name under the [receiver method names rule](../receiver-method-names/receiver-method-names.md), so a declaration whose plain name is also a bare method name anywhere in the repository carries its module's path exactly as it would for another module's declaration. `Domain` in `app/protocol` is both an abstraction and the method of `BS_Init_Request` that returns one; the abstraction is `App_Domain` and the method is `Domain`. The method side does not yield, and the reason is in that rule.

A module prefix is kept only when the bare name is ambiguous in the corpus. The owner's ruling on `modules/computer/datatype/protocol/detail.kh` (2026-09-29) is the example: `Computer_Detail` is `Details`, `Datatype_Quiddity` is `Quiddity`, and nothing else in the corpus claims those plain names — the qualifier only repeats where the file lives. A name that already carries its module steps up rather than shortening (`Time_Duration` in `time/duration`) is not stripped. A bare name that equals another declaration, a `_2` counter, or the Record/Storage UUID pair is left as written and reported.

Observer and mutator abstractions (`Observer_X`, `Mutator_X`) — spelling, composition, and accessor naming — are governed by the [observer and mutator rule](../../../computer/adt/rules/observer-mutator/observer-mutator.md). This rule still applies when an `Observer_*` or `Mutator_*` name would collide with another module's declaration.

### When qualification cannot separate two declarations
Qualification separates declarations of different modules. It cannot separate two declarations that the same module path would give the same name, and a tool that meets such a pair and falls back — to a counter such as `GUI_Event_2`, or to a step up the path that the name itself does not call for, such as `Storage_UUID` beside `Record_UUID` — has produced a report, not a name. No fallback of either kind is kept as a name. The step up that `Time_Duration` takes is not a fallback: it is how qualification spells a name that already carries its module, not a way out of a name something else has taken. A pair that qualification cannot separate is one of three things, and each has its own answer:

- **One concept declared twice.** `Observer_RecordUUID`, `Observer_RecordsUUID`, and `UUID` are declared identically in `identifier/record` and in `memory/record`, down to the comment. This is the case [Khayyam → Import Mechanism (`in`)](../../../../docs/khayyam/khayyam.md#import-mechanism-in) names — two abstractions claiming one concept — and its answer is one declaration that the other module includes, not a second name. The surviving declaration then takes the name this rule gives it with the duplicate gone: `Record_UUID`, because `UUID` is still claimed by other modules' concepts; `Observer_RecordUUID` and `Observer_RecordsUUID` bare, because nothing else claims them. Which module keeps the declaration is a question of which one owns the concept, and it is not answered by naming. `Stringer`, `Stringer_To`, and `Stringer_From` in `codec/string` and `Codec_Stringer`, `Codec_Stringer_To`, and `Codec_Stringer_From` under `lib/codec/string` have the same signatures and the same comment, and both paths end in `codec/string`, so qualification cannot separate them either. They are this case unless the [lib handoff](../../../lib/lib.handoff.md)'s open question finds the two contracts distinct.
- **An abstraction and a capsule that one module's path names alike.** `GUI_Event` is an abstraction in `gui/protocol` and a capsule in `gui`; `GUI_Application`, `GUI_Page`, and the other capsules of `gui` beside their `gui/protocol` abstractions are the same pair. The abstraction keeps the name. An abstraction is the language-level counterpart of a protocol's declared requirements ([Abstraction in Khayyam](../../../../docs/khayyam/abstraction.md)), and an abstraction's method signatures and composition may name only abstractions ([Abstraction → What You Cannot Do](../../../../docs/khayyam/abstraction.md#what-you-cannot-do)), so the abstraction's name is the one the rest of the corpus has to write; a capsule is named where a realization is chosen. [Abstraction → Satisfying an Abstraction](../../../../docs/khayyam/abstraction.md#satisfying-an-abstraction) shows the shape — `FileReader` satisfies `Reader`, and the capsule's name says which realization it is. What the capsule is called is its author's choice; this rule supplies no suffix for it.
- **One source declaration emitted twice.** `modules/net/protocol/socket.kh` holds `Net_Socket_2` and `Socket` for one Go `Socket` interface, and `modules/net/protocol/packet.kh` holds `Net_PacketTarget_2` beside `PacketTarget` and `Net_PacketListener_2` beside `PacketListener`. One of the two copies is removed; the other takes the name the abstraction case above gives it. There is no naming question here, only a duplicate.

A pair that is none of these — two distinct concepts in one module claiming one word — is the redesign the language document asks for, and its names are chosen by its author, not produced by a rule.

## Why it exists
With no package qualifier and no alias, a name has to say where it lives at the place it is declared, or two modules' names meet with nothing to tell them apart. A name must also carry domain meaning without relying on a directory or package prefix to supply missing context — that discipline is the [identifier naming rule](../identifier-naming/identifier-naming.md); this rule handles collisions and module qualification when the plain name is not enough. The language's answer to a collision is a redesign, and a redesign is expensive to apply one name at a time; qualification is the bridge that makes the redesign possible — every collision becomes visible at a declaration site an author can change, rather than at an import site a reader has to interpret. The port is the evidence: 1021 declarations and methods were renamed this way, 0 cross-file collisions remain, and every collision the bridge found was reported as the architecture error the language says it is.

## Keep it or drop it
An organization may keep this rule, replace it with a package qualifier or an alias if the language ever grows one, or drop it and take the redesign cost directly. Dropping it is a legitimate choice for a small codebase where collisions are rare enough to redesign on sight; it is a poor choice for a library that is meant to be included by others, because the collision then surfaces in someone else's file.

## What this rule does not claim
- It does not claim the language requires module-qualified names, nor that a qualified name is a language form. `pkg.Type` is a reference this toolchain accepts without resolving it — see the [unbound type name rule](../unbound-type-name/unbound-type-name.md)'s open questions — and nothing in the grammar requires a name to carry its module.
- It does not claim qualification is the right remedy. The language document's position is that the remedy is a redesign, and this rule is the bridge to it, not the destination.
- It does not claim a name is good because it is qualified. The [identifier naming rule](../identifier-naming/identifier-naming.md) is where style lives, and the two are independent.
- It does not claim which module owns a concept declared twice, and it does not name a capsule that gives up a name to an abstraction. Both are judgments about the corpus; the rule states only that no counter or fallback step stands in for them.
