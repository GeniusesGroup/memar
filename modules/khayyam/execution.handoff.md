# Khayyam JS Execution Handoff
Open work for [execution.md](./execution.md). Entries are mutable current state — revised as each item moves, removed when it resolves or is dropped. Every open question below names the file and the line it can be read at, so a session that starts cold can go straight to it. See the repository's [documentation-handoff.md](../../docs/documentation-handoff.md) for what a handoff is.

## Topic & Purpose
Establish a fast, principled path to run Khayyam source on any JavaScript host, with durable placement rules within this repository and an incremental compile cache, and to give a reader of a `.kh` file a display that answers with the same role for the same name everywhere. The plan governs the order; this handoff carries the state a continuing session needs and nothing it can re-derive from the tree.

## Status
Active

## What the toolchain is asked to do, and what it does now
The toolchain is asked to read a `.kh` file, say what it declares and what it refuses, and tell whoever is reading the file what every name in it *is* — never merely where it stands. Three things answer that today, and they are three separate pieces:

- **`core/`** reads a file for a compiler. [`analyze(path, source, fileSystem)`](./core/src/frontend.ts) takes the text and an injected file system, parses the ruled `tp`/`vr`/`in` forms through [`parseUnit`](./core/src/gate.ts), and resolves every inclusion — refusing `unresolved-import`, `name-not-declared`, `kind-mismatch`, or `unbound-type-name`. Its only callers are the tests in [`core/test/`](./core/test/).
- **`core/src/reader.ts`** offers [`readUnit`](./core/src/reader.ts), which is a *reader* rather than a gate: it recovers per declaration and returns every fault beside the declarations it did read, so one unreadable declaration costs the file that declaration and nothing else. Its only production caller is the language server.
- **`lsp/`** serves those roles over LSP. [`server.ts`](./lsp/src/server.ts) holds open documents, declares full-document synchronization, publishes a diagnostic for every fault, answers `textDocument/semanticTokens/full` with one token per role, and refuses a change payload that contradicts the capability it declared. [`semantic.ts`](./lsp/src/semantic.ts) resolves each occurrence to a binding and reports the role that binding carries, and the legend it advertises is the contract's twenty-one roles in the contract's own order — one of which it answers and no grammar can, because a declaration's block is a fact about the document and not about a line.

The editor side is one realization of the display contract: a TextMate grammar for what syntax can answer, the language server for what only analysis can, and a language-scoped `editor.tokenColorCustomizations` default for the values. See [display.handoff.md](./display/display.handoff.md) for that half and [Ambiguities Resolved](#ambiguities-resolved) for the questions the display work closed.

## The goals still owed, and the shape each output must have
The goals and their checks are [execution.md → The goals, in the order they come](./execution.md#the-goals-in-the-order-they-come). What each one still owes, and the shape its output must have:

1. **Goal 1 — placement and open state before code.** Owed: the readiness record is written and the repository's placement governance knows where the shared rule engine and the toolchain category go. The output shape is a written home for each — a directory a second contributor can find without asking — plus this file's open questions, each already carrying a file and a line.
2. **Goal 2 — the frontend accepts and refuses the core grammar.** Owed: the qualified-reference gap, and the accept/refuse matrix's coverage of `mt` bodies once M3 parses them. The output shape is a matrix row per form, naming the document section the form comes from, and a `RefusalReason` per refusal in [core/src/sr.ts](./core/src/sr.ts).
3. **Goal 3 — a `.kh` source runs on a JavaScript host.** Owed: the JS backend and the runtime glue, neither of which exists. The output shape is an ES-module artifact plus the fact it runs: a `.kh` program needing no library control flow, run under Node and loaded in a browser, with no layer between the representation and the artifact deciding what the program means.
4. **Goal 4 — the `.kh` library is reachable, link-first.** Owed: the URI→JS-module link map against the archived memar-js sources. The output shape is a map whose every entry resolves and records the protocol document it was checked against, with a compiled program that uses library control flow as the thing that runs.
5. **Goal 5 — a reader runs a `.kh` file without a bundler.** Owed: the demo page. The output shape is one page that takes a file, resolves and compiles it through the cache, runs it, and shows its output with no build step.
6. **Goal 6 — unchanged work is not repeated.** Owed: the cache. The output shape is a second build that compiles nothing, and a one-file change that compiles that file and its dependents and no other.

## Decisions
- **Placement of protocol implementations vs. Khayyam toolchain** — Decided. Language-agnostic protocol code (Lexer, …) belongs in the shared implementation modules under `modules/`; Khayyam-host toolchain work belongs under `modules/khayyam/`; language-wide design lives in the repository's `docs/khayyam/` and `modules/` tree; host-independent protocol design lives in `docs/protocols/`. Reason: the repository's local placement keeps general claims at the root, language-specific material with the language, and host-specific work with the toolchain.
- **Scope: bootstrap path (option A)** — Decided. Core grammar → first JS run → bootstrap the `.kh` libraries under `modules/` with the same toolchain → then library control flow. Reason: the `.kh` library is not yet executable; control flow is library-defined; a demo that simulates control flow in the backend would violate the "JS backend is not the hidden specification" discipline. Rejected: demo-only with backend-simulated control flow (violates discipline); full language + library up front (too slow for first running feedback).
- **Lexer implementation deferred** — Decided. M0–M5 do not implement `modules/computer/lexer/`; the frontend may consume source directly until a separate lexical layer is justified. Reason: semantic representation is the higher-leverage layer for Khayyam now; Lexer protocol remains Draft. Placement `modules/computer/lexer/` is reserved by the placement decision above for when this is picked up.
- **Semantic representation is the priority layer** — Decided. Design and freeze the Khayyam semantic representation before investing in backend breadth; language simplicity makes this the right order. Reason: one representation behind JS (now) and WASM (later) is the implementation-independence test in the repository's compiler handoff.
- **Compile cache is git-ignored build output** — Decided. Artifacts under `modules/khayyam/targets/js/build/`, content-hash keys, transitive invalidation via `in` imports; never committed. Reason: avoid recompiling unchanged files; keep git history free of generated JS; build products are not a source of truth.
- **memar-go abstractions are the primary design reference** — Decided (2026-09-24, owner). The archived memar-go repository carries years of deliberate categorization and abstraction work whose critique-into-documents pass has not happened yet, so the code is currently their carrier — one promoted example already lives in [error.md](../../docs/protocols/process/error.md). Every toolchain or `.kh` library design question reaches for memar-go's abstractions first, not Go-standard-library or other ecosystem idioms. When a memar-go abstraction is wrong for Khayyam, the critique and its replacement are recorded in this handoff or the owning document's handoff — never applied as a silent substitution. Reason: owner directive at the bootstrap gate; ecosystem defaults would reintroduce exactly the inherited-layer assumptions that are expensive to remove later.
- **Plan parameters confirmed by the owner** — Decided (2026-09-24). Bootstrap scope A, milestone order M0–M5, the deferred lexer, and the link-first rewrite of M3/M4 below are owner-confirmed, not tentative. Reason: owner review at the readiness gate.
- **Milestone order M0–M5** — Decided (2026-09-24, owner confirmation). Order is default; M2/M3 may interleave when a library construct blocks an earlier sample. A later reordering would be a revision of this entry, not an open state.
- **Toolchain implementation language: TypeScript** — Decided (2026-09-24). M1–M5 toolchain code is TypeScript developed on Node, emitting plain ES-module JavaScript artifacts; the artifact stays host-neutral. Reason: the session's self-hosting roadmap puts a TypeScript→JavaScript phase before any self-hosting phase, and static checking applies exactly where the semantic representation is built. Alternatives considered: plain JavaScript (rejected — no checking at the layer where meaning is encoded); writing the toolchain in Khayyam now (rejected — the toolchain that would run it is what does not exist yet; that is the self-hosting phase's job).
- **Link-first bootstrap (M3/M4)** — Decided (2026-09-24). Before compiling a `.kh` library unit, resolve its `in` imports through a URI→JS-module link map pointing at existing implementations conformant to the protocol documents; compile a unit only when no conformant equivalent exists — library-driven control flow is the expected compile set. Each map entry records the protocol document it was checked against, and a failing entry falls back to compiling the `.kh` source. Reason: the readiness inventory ([execution.research.001.md](./execution.research.001.md)) found the archive's sources — transferred unreviewed from memar-khayyam, never committed even there, to preserve ideas — include 16 files with no code and 2 in Go-draft, so compiling them yields nothing runnable while conformant JavaScript for much of the library already exists in the archived memar-js sources. The per-entry conformance record is what keeps discipline #1 intact — linking may never silently replace the semantic representation as the source of truth. Alternative considered: compile every `.kh` unit regardless (rejected — M3 would spend itself on an unfinished idea archive).
- **M1 acceptance inputs selected** — Revised (2026-09-24, owner). The archive's `.kh` files are not a syntax yardstick: they may originate from different periods of Khayyam's development while the syntax is only now considered final — `docs/khayyam/` is the permanent evaluation ground, and the archive can neither support nor refute a language rule. Positive inputs are therefore fixtures derived from the documented forms (the examples in `docs/khayyam/`), to live under `modules/khayyam/core/test/fixtures/` when M1 starts; the archive supplies only negative/diagnostic/stress inputs: `if.kh` (dangling import, unbound identifiers, empty `mt` body), `mutable.kh` (import written without `in`), and `life_cycle.kh` as the mixed-dialect stress case (expected refusal), `mem.kh` excluded as Go-draft, the 16 placeholder files as smoke inputs (expected acceptance — a file with no declarations violates no rule). Amendment (2026-09-25): `panic-recovery.kh` moves from negatives to accepted smoke — the documentation imposes no emptiness constraint on a capsule (encapsulation.md → Capsule Structure and Privacy: fields are what a capsule *can* contain), so an empty `cp` is well-formed and the original "empty `cp`" negative basis is unsupported by the docs. This supersedes the earlier selection of `weak.kh`, `concurrency.kh`, `blocking.kh` as positives: their method declarations (`tp mt ReferenceAlive …`; `tp IsAsync …` with no `mt`) match no documented form — a pre-final-syntax artifact, not a language ruling in either direction. Reason: owner directive 2026-09-24; the mismatch is recorded in [execution.research.001.md](./execution.research.001.md) → Notes.

- **The specification states no diagnostics contract; the toolchain has its own** — Revised (2026-09-27). M1 acceptance asserts accept/refuse outcomes only, and nothing pins a message format, a diagnostic code, or a recovery behavior to the specification, because no document states one. The toolchain is not silent any more and does not need the specification to say so: [server.ts](./lsp/src/server.ts) publishes one diagnostic per fault, carrying a range on the line the fault stands on, a severity, a code equal to the refusal label, a sentence saying what the language has in place of the thing refused, and — where the fault is a consequence — the fault it follows from, its line, and what that fault cost. Reason: a reader who is shown a confidently wrong file is worse served than one shown a refusal, and the labels are this toolchain's own.

- **Module internal structure: plan, rules, and core at the root, targets under `targets/`** — Revised (2026-09-25, owner). `modules/khayyam/` organizes by kind: the governing plan `execution.*` at the root, `core/` (the target-independent frontend + semantic representation), `rules/` (Khayyam's rules — the owner's own folder and idea), and `targets/<emit>/` for every emit target (`js` first, then `wasm`, `c`/`asm` as taken up; per-arch subfolders under `asm/` when real). There is deliberately **no** `modules/khayyam/linter/`: even holding only rules, that name carries the wrong concept — "linter" and "formatter" are labels attached to rules, not places. Names are by emit output, never by implementation language. Empty folders that name an accepted responsibility stay; none of this is final. `lsp/` and `display/` have since been added beside `core/` as the realization that answers a reader and the contract that governs it.
- **Language-independent mechanisms are shared, not Khayyam-owned** — Revised (2026-09-25). The Linter protocol is language-independent by its own text ([linter.md → Abstract](../../docs/protocols/computer/linter.md)), and the general mechanism a language-independent tool runs on belongs in the shared implementation modules, following the Lexer precedent ([execution.md → Pipeline](./execution.md)) — `modules/computer/lexer/`, whose language-specific model stays with the toolchain. What that mechanism is called and where it sits is the open question below: the owner's model makes it a general **rule engine**, not anything named "linter".
- **Khayyam's rules live in `modules/khayyam/rules/`; their normative claims stay in the subject documents** — Decided (2026-09-25, owner). The folder is the owner's own: it says "here are Khayyam's rules". A rule's normative claim — what the language means — stays in the document that owns the subject ([linter.md → A rule's home is its subject's document](../../docs/protocols/computer/linter.md)); the executable rule lives in this catalog and cites that claim. This answers the Khayyam instance of the catalog question in [linter.handoff.md](../../docs/protocols/computer/linter.handoff.md) — a cross-language catalog is not wanted for Khayyam. Beside the folder stands a general rule engine (placement open below) that applies rules by each rule's stated condition; a formatter is then a rule that rewrites source, not a separate tool concept — which is why no `linter/` folder is needed.
- **Rule model: one authored rule, two request paths, and a compile-time gate** — Accepted in principle (2026-09-25, owner), with the protocol work explicitly unfinished. The model: every rule declares identity, subject, condition, consumes, produces, enforcement (`compiler-gate` / `governance` / `source-rewrite`), and scope (`unit` / `repository`); a *check* is one evaluation of one rule against a conforming input; a diagnostic identifies the rule that produced it. The same authored rule then serves both paths — the memar server asks for diagnostics without invoking any target, and the compiler gates target invocation on the compiler-gate rules. Under this, the compiler does not reimplement a rule's condition: it builds the target-independent analysis input, asks the engine, and invokes the target only when every mandatory rule passes; a lexical or syntactic failure that prevents building that input stays a direct frontend diagnostic that also blocks the target. The frontend's four import-resolution refusals are cataloged as compiler-gate rules, one folder each: [unresolved-import](./rules/unresolved-import/unresolved-import.md), [name-not-declared](./rules/name-not-declared/name-not-declared.md), [kind-mismatch](./rules/kind-mismatch/kind-mismatch.md), and [unbound-type-name](./rules/unbound-type-name/unbound-type-name.md). The documents establish the classification (ontology versus governance) but not this mechanism: [compiler.md](../../docs/protocols/computer/compiler.md) states acceptance, refusal, and target production without the analysis-event schema, so this was the question. The owner answered (2026-09-25): the model stands, and question B is settled as described — the compiler builds the target-independent analysis input, asks the engine, and invokes the target only when every mandatory rule passes; only a lexical or syntactic failure that prevents building that input stays a direct frontend diagnostic, and it too blocks the target. What remains open is the protocol members the model cannot stand without, which each rule's own handoff records.
- **No CLI or TUI: toolchain components are apps that receive requests** — Decided (2026-09-24, owner). Nothing in this toolchain is designed as a command sequence over argv that exits after running; each component (compiler, linter, inspector, demo) starts as an app and then receives requests, consistent with [os.md](../../docs/protocols/computer/os.md) and [immutable_infrastructure.md](../../docs/protocols/runtime/immutable_infrastructure.md) and the unikernel stance. Build tooling (Node scripts, test runner) is is developer-side and is not the product's interaction surface. The editor extension is a second instance of the same shape: it starts a process and then speaks LSP to it over stdio. Reason: owner directive; the same mental path as Memar's OS modeling.

Applied case: `khayyam/compiler/{ast,keywords,parser}` stays deleted, because the structure M1 builds under `core/` supersedes it; the principle governs future restructuring, including lifting shared frontend/SR material into `core/` when a second target starts. Reason: owner directive on folder critique.

A rule belongs to the language only if changing it would change what programs mean — their existence, resolution, or observable behavior. Anything whose handling may vary by realization — naming style, transliteration, script repertoire, refusal wording — belongs to the rule catalog, linter, or compiler, never to the grammar. - **Ported corpus fidelity: names qualified at the definition site, imports file-level, license header mandatory** — Decided (2026-09-25). The corpus ported from memar-go now carries the reference's doc comments, and its declarations carry module-qualified names under the [qualified names rule](./rules/qualified-names/qualified-names.md) — with no package qualifier and no `as` alias in the language, a name must be self-describing where it is declared (the owner's example: `Stringer` in `codec/string/utf8` becomes `UTF8_Stringer`; a name that already carries its module steps up instead, `Duration` in `time/duration` becoming `Time_Duration`): 1021 declarations and methods renamed, 0 cross-file collisions, every collision reported as the architecture error the language says it is. Imports are file-level URIs and all 141 resolve to a real file — which also retired the archive's dangling `memar/math/boolean` / `Bool` in favor of `Boolean` at its real path; the shape of a URI is the [import address rule](./rules/import-address/import-address.md)'s subject, not the grammar's. - **A transferred abstraction is reviewed and cleaned before it is committed; the bridge's output is not a finished library** — State (2026-09-26, owner). The procedure is: transfer, then review the abstractions against [Abstraction in Khayyam](../../docs/khayyam/abstraction.md) and [Polymorphism in Khayyam](../../docs/khayyam/polymorphism.md) against the two naming rules, and only then commit. The review is four checks — each contract is stated once, in the file that owns it; a refinement is written as abstraction composition (`tp … ab { … }`) rather than as a second interface beside the general one; a declaration that exists only because the reference instantiated a generic is removed; a name that repeats its owner is dropped — and each change is recorded as a before/after with the document that justifies it. Worked example, the first file through it: `modules/time/timer/`, cleaned 2026-09-26. The port had written `tp Timer_Time_Timer_Status ab` beside `tp Timer ab`, repeating `Init`, `Start`, `Reset`, and `Stop` under a second owner; it is removed — no contract in the corpus named it, its status half is already `Timer_Status`, and the Go type parameters it carried have no Khayyam form ([Polymorphism → What You Will Not Do](../../docs/khayyam/polymorphism.md#what-you-will-not-do-in-khayyam)). The same pass found the timer's status stated twice — once as an orphan `tp TimerStatus ab` in `timer-status.kh` with no methods and no importer, once as `Timer_Status` in the listener file beside it — and settled it once in the file that owns it, `timer-status.kh`, under the qualified name the [qualified names rule](./rules/qualified-names/qualified-names.md) gives it; the four owner-prefixed method names became bare under the [receiver method names rule](./rules/receiver-method-names/receiver-method-names.md), which says the receiver supplies the context the name would otherwise carry. No second file has been through the review.
- **The display realization states the contract's roles, and reaches the editor additively** — Revised (2026-09-28). Three decisions, all checkable in the extension. (a) A legend entry is a **token type**, read whole, and not a TextMate scope and not a selector — so the server advertises the contract's own role name for each of the twenty roles, and the extension bridges each of those names that a TextMate scope reaches to the role's own TextMate scopes through the `semanticTokenScopes` contribution, one value per role, stated once, with the language in the bridge's own `language` field and in the provider's document selector (the one role the contract declares server-only names no scope, so the bridge carries no entry for it and the colour rules are the only mechanism that styles it). The grammar needs no change: the editor's merge only requires that the grammar tokenise the line. (b) The extension's colour rules were a list where the editor reads a map, so they matched nothing; they are now a map, and its keys are the same twenty names the legend gives. (c) The themes are deliberately **not** contributed as selectable themes, so the values reach the editor additively as a language-scoped `editor.tokenColorCustomizations` default layered over whatever theme the reader has chosen, and the owner's stale selection of a theme that is not offered is gone. Rejected: naming each legend entry `<role>.<language>`, which this entry decided on 2026-09-27 and which is now reversed deliberately — the editor reads a separator in a **rule's** key as the boundary between a token type and a language, and matches that type against the token's own type hierarchy, which for a name this extension does not declare under `semanticTokenTypes` is the name and nothing else, so a legend entry carrying a language of its own matches nothing and every token of it is dropped. Reason: the editor's own product was read to settle each of these; the display contract governs the roles and never a value, and this is where the values go.
- **The client sends whole text; the server refuses a payload that contradicts what it declared** — Decided (2026-09-27). The server declares `textDocumentSync.change = 1` (Full), the client sends the whole document's text once per change with no range, and the server measures every payload against the capability it declared and refuses a contradiction by name — one content change, no range — publishing the refusal on the document it is about. The accepting path is gone. Reason: a ranged change is a payload the client never agreed to, and applying it applies rules no client promised to follow, so the server then holds a document the editor does not have: every fault and every role it answers is about that text, and the editor shows it as though it were about the file on screen.
- **The installer writes over the extension folder it installed before** — Decided (2026-09-27). Every run copies the checkout's extension over the target folder, including a run that only reports. Reason: a run that refuses to overwrite leaves the editor serving the first code it was given, and a change in the checkout never reaches the reader while the editor keeps looking correct.
- **The language server does not take its vocabulary from an outside protocol; the adapter in the client carries the translation** — Decided (2026-09-28, owner). The server answers in its own abstractions — the display contract's roles, this toolchain's refusal labels, the document it holds, the reader, the gate ([execution.md → The language server answers in its own abstractions](./execution.md#the-language-server-answers-in-its-own-abstractions)) — and a client that can only speak something else translates in its own files. ## Ambiguities Resolved
- **Does a refusal reach the reader, and is a file that could not be parsed answered from position?** — Answered. A refusal reaches the reader as a diagnostic in the editor's own collection, and a file the frontend could not read in full is **not** answered from position: it is read with recovery per declaration, and roles are answered only for what was read. The unit of recovery is the declaration because the language's unit is the line — [khayyam.md → Declaration separator](../../docs/khayyam/khayyam.md) states that a declaration occupies one line and the line's break terminates it — so one unreadable declaration costs the file that declaration and the lines around it still answer. A fault that follows an earlier one names the fault it follows from and its line, because standing alone it says nothing actionable: a closing brace with nothing to close reads as a stray form no declaration takes, and the brace that went missing is ten lines up. What was not asked and is not claimed: the specification states no diagnostics contract, so the messages, the codes, and the severities are this toolchain's own.
