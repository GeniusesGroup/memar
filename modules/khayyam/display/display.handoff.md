# Khayyam Display Handoff

Open work for the display contract in this folder — `display.json` (the contract) and [`display.md`](./display.md) (its prose). Entries are mutable current state: revised as each item moves, removed when it resolves or is dropped. What remains is per target, recorded as open state, not as a plan to be executed in order. See the repository's [documentation-handoff.md](../../../docs/documentation-handoff.md) for what a handoff is.

## Topic & Purpose
The display contract is stated and realized in one editor. The owner's subject is everything outside it — a `.kh` file on a code-hosting page, a fenced block in a rendered document, another editor — where a reader of Khayyam is still owed the same roles. This handoff carries what the contract owes, how the one shipped realization delivers it, the two questions this folder owns that nothing has answered, and what an owner looks at to know the colouring works.

## What the display contract owes
A person reading Khayyam is a consumer of the contract wherever they read it, and the contract is a property of the language rather than of any one tool. What it owes a reader, in the form the realization has to discharge it:

- **Every name carries the role of what it IS, at every position in every file.** A Method looks like a Method at its declaration and at its call site; an included name looks like an included name at its inclusion and at every use; a parameter looks like a parameter in a signature and in the body it is used in. This is the load-bearing rule, and it is the one the grammar cannot discharge on its own.
- **Twenty-one roles, and no scope the contract does not name.** A realization that invents a scope has left the contract; one that never emits a role has abandoned it. `identifier-reference` is part of the obligation and not a fallback: its job is to stop a use site reading as a local declaration. One role, `method-local`, is declared **server-only** and names no scope at all, because a TextMate grammar cannot tell a name declared in a method body from one declared at file level — the line that opens the body is not on the line the name stands on. That is a property of the mechanism and not a gap in a realization, so the contract states it on the role (Decisions below) and `verify-roles.mjs` reports it in its verdict.
- **Every theme supplies a value for every role-attribute pair**, keyed `khayyam.<role>.<attribute>`; a missing value and an unknown role are both errors, and `fontSize` is not an attribute. The contract never states a value.
- **The same contract governs the editor, a code-hosting page, and a rendered document.** What differs between them is the realization and the theme, never the roles.

The two mechanisms the contract knows discharge that in different widths, and the boundary between them is the reason the contract outlives any one highlighter: a TextMate grammar matches one line at a time and holds no symbol table, so a role can be assigned only where syntax determines the identity; a language server resolves each identifier to its declaration, so it can answer at a use site.

## What a Host's Own Mechanism Costs a Realization
The editor is not a neutral consumer of a role and a value: four of its own rules decide what a reader sees, and a reader debugging this side should not have to re-derive them. Each was read out of the editor's own bundled source — VS Code 1.139.1, `resources/app/out/vs/workbench/workbench.desktop.main.js` in the installed product. That file is minified, so each entry names the identifier that survives in it, and a reader finds it by searching for that name. These are facts about this host, not about the contract. `verify-roles.mjs` transcribes two of the four into its own checks — the selector rule, and the highlighting gate it refuses to let a manifest or a theme leave unset — and takes the third as the rule about what the manifest may not contain outside `[khayyam]`. The first is the reason its refusals matter rather than a check of its own, since no run from here can watch the editor merge. The architecture states them as constraints a realization is designed against at [docs/content.md → Theme / Role-to-Rendering Mapping](../../../docs/content.md#what-a-hosts-own-mechanism-costs-a-realization).

- **The merge is field by field, and a semantic token supplies one for every token it emits.** Read out of `addSparseTokens`, the model's semantic-token part: over one line the host walks the grammar's tokens, and across the span a semantic token covers the result is `(grammar & ~mask) | (semantic & mask)` — every field the semantic token supplies wins, every field it does not stands, and a position no semantic token covers keeps the grammar's own metadata. The discard is one layer earlier, in the computer that writes a line's tokens: a token whose resolved metadata is the no-style value `2147483647` is never written into the line, and `SemanticTokensProviderStyling.getMetadata` returns exactly that value when the theme resolves no style for the type/modifier pair or the type is not in the legend. **What it costs a debugger:** a role with no resolvable value does not look unstyled — it looks like the grammar's colour, which is a plausible wrong answer rather than a gap; and a role whose token was discarded is indistinguishable, on screen and in the line, from a token the server never sent.
- **A token type may not carry a separator.** Read out of the registry's `parseTokenSelector` and the `match` it returns, beside `getTypeHierarchy`: a rule's key is split at its first separator, what precedes it is the type, what follows is modifiers, and a `:` part is the language — and the parsed type must then be found in the token's own hierarchy, which is `[type, superType, …]` built from the super-types the extension declared in `semanticTokenTypes`. `registerTokenType` refuses any id that is not `^\w+[-_\w+]*$`, and the host's own standard types (`comment`, `string`, `keyword`, `type`, `variable`, …) are single segments. **What it costs a debugger:** a type name carrying a separator can never be matched by a rule keyed the same way, and nothing reports it — the token resolves no style and is then discarded by the entry above, so the editor asks for tokens, receives them, and draws the grammar's colours alone.
- **A `[name]` key in the colour customizations is a theme key, not a language key.** Read out of `getThemeSpecificColors` with `isThemeScope` and `isThemeScopeMatch` on the colour provider: every key of the setting that looks like `[…]` and holds an object is matched against the **active theme's** own `settingsId` (`o === this.settingsId || …`), and a key that matches no theme contributes nothing; `readSemanticTokenRules` separately skips a `[…]` key while walking `rules`, so a theme block is never read as a selector. **What it costs a debugger:** this extension contributes its values inside the `[khayyam]` language-scoped default in `package.json`, so a `[khayyam]` key nested inside that block is inert — present in the manifest, matched against no theme, and skipped as a rule. The same reading is why a value that has to vary with the reader's theme cannot be written on this axis at all: a per-theme value needs a mechanism of its own, and the one this extension found is a theme the reader selects. What is left of that axis — the reader who selects none — is the open question below.
- **Whether semantic highlighting is computed at all follows a setting whose default defers to the theme.** Read out of the editor's own configuration schema — `editor.semanticHighlighting.enabled`, `enum: [true, false, "configuredByTheme"]`, `default: "configuredByTheme"` — and out of the gate that consumes it before the editor asks a provider for tokens at all: `typeof value === "boolean" ? value : themeService.getColorTheme().semanticHighlighting`. **What it costs a debugger:** a realization that satisfies the contract can still be invisible, and visibility follows the reader's theme, so no observation made under one theme settles it. The extension therefore sets the language-scoped default to `true` in its manifest and each offered theme opts in with its own `semanticHighlighting`, and `verify-roles.mjs` refuses the manifest without the default and refuses a theme that declares no opt-in, because a theme that declares no `semanticHighlighting` discards every role with no error — and that opt-in is the whole of what a theme's own `semanticTokenColors` map needs beside it.

**Standing item:** these four are why the realization is an adapter and not a definer. The roles and the values belong to the contract; where this host's mechanism is incomplete or awkward, the translation belongs in the host's own files — the manifest, the themes, the colour rules, the settings — and never in what the contract says a role is called or what a theme must supply. Every future change to this extension's colouring is measured against [`display.json`](./display.json), not against the editor.

- **The client sends the whole text, and the server refuses a payload that contradicts what it declared** — Decided (2026-09-27, owner). The server declares `textDocumentSync.change = 1` (Full) and holds one text per document, re-reading all of it on every change, so there is no state an incremental update would keep up to date. Full also states what the client must send: the whole document's text, once, with no range. The client sends exactly that. The server measures every payload against the capability it declared and refuses a contradiction by name — more than one content change, or a change carrying a range — publishing the refusal as a diagnostic on the document it is about and leaving the text it holds untouched; the accepting path is gone. Reason: a ranged change is a payload no client agreed to send, and applying one applies rules the client never promised to follow, so the server then holds a document the editor does not have. One ranged edit happened to apply; two in one notification — which is what the editor sends for a multi-cursor edit or a fix-all-on-save — landed the second edit where the first one had moved the text, and the result was a corrected fault that did not clear and tokens that never refreshed after an edit, with nothing saying why.
- **The installer writes over the extension folder it installed before** — Decided (2026-09-27, owner). Reason: a run that refuses to overwrite leaves the editor serving the first code it was given, so a change in the checkout never reaches the reader while the editor keeps looking correct — the hardest shape a defect takes, because the tool appears to work.

Reason: a file carrying one lexical or syntactic fault used to reach the reader as though it were well-formed — a handful of confidently wrong roles and nothing marking it as degraded — and a corrected fault used to stay on the line. - **Roles are measured over the wire, because no editor is available to the writing agent** — Decided (2026-09-27, owner). ### The four roles a super type cannot express, and what the contract does with them - owner ruling

## Key Definitions Established
- **Realization** — anything that assigns the contract's roles to text (a TextMate grammar, a language server, any other engine). **Theme** — anything that supplies a value for a role-attribute pair. A theme never declares a language to a host; the two are separate acts, and conflating them is what the Linguist entry is about.
- **Token type** — what a semantic token legend entry means to a host, and the whole of it: a token's type is its legend entry, and its language is the language of the document it stands in. Neither is read out of the name. A **selector** is the other half of the vocabulary: a rule's key, which a host splits at its first separator into a type and a language, and matches against the token's type hierarchy. It is not a TextMate scope, and a host keeps the two apart: a theme's `tokenColors` reaches a token by its scope and a theme's `semanticTokenColors` reaches it by its type, so one theme file delivers the contract's scopes and the contract's roles in two different blocks and a host reads each in the block that suits it.
- **Role, over position** — the display rule that a name carries the role of the identity it denotes, so that the same name answers with one role wherever it stands. It is the rule the grammar cannot discharge and the server exists to discharge.
