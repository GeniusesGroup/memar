# Khayyam Display

How a Khayyam source is displayed to whoever reads it, and what each reader is owed. The contract itself is [`display.json`](./display.json) — the authoritative statement of the roles, the attributes, and what a theme must supply. This document is the prose around it: what the contract claims, how a consumer implements it, and which consumers exist. Unfinished work on reaching the consumers outside this repository is in the paired [handoff](./display.handoff.md).

The display contract is a property of the language, not of any one tool. The same roles govern the same identities whether the reader is looking at a file in this repository's editor, at a `.kh` file on a code-hosting page, or at a rendered document. **A person reading Khayyam is a consumer of this contract, and a person reading it on someone else's web page is a consumer too** — a highlighter that cannot honor the roles fails the reader, and no amount of correctness elsewhere repairs that.

## The contract
- **A role names what an identifier IS, never where it appears.** The same identity carries the same role at every position in every file. This is the load-bearing rule: a Method looks like a Method at its declaration and at its call site, an included name looks like an included name everywhere it is used.
- **A role also states its KIND — what kind of thing it is — and the kind is a separate question.** The editor already publishes a classification of its own: twenty-four standard token types and eight standard modifiers. A provider tells it a kind of its own by contributing a **super type**, and a type with no super type has a hierarchy of exactly itself, so no rule keyed on a standard type ever reaches it. Every role therefore states one of exactly three answers: the standard type it is a kind of; **this language's own root**, with the reason there is no counterpart; or the host's own standard type under the role's own name, which is registered nowhere. A root is a real result, not a failure — it is what the language adds to the host's vocabulary — and it is visible in the contract and in the verifier's verdict so a reader can see it.
- **What a super type does not carry is named, not hidden.** A super type expresses *kind* and nothing else. **Origin** (a name that arrived by inclusion against one declared here) and **validity** (a name valid for a whole file against one valid for a method body) are the residue: the host's eight modifiers have nothing for either, so they are carried by the palette's lightness and chroma and by the `fontStyle` channel, and the contract names them as residue rather than spreading them across new kinds.
- **The specification names roles, kinds, attributes, and variable names; a theme supplies values.** The specification never states a color. This is the separation CSS custom properties make — the name is declared once, the value is provided by whoever renders.
- **Attributes are the channels.** `color` is the first and is required; `fontStyle` is the second and is required. An attribute is either a real channel for every role or it is not in the schema, and the schema is a map so a further attribute can be added without reshaping a role. `fontSize` is a **deliberate exclusion**, recorded with its critique in the contract: size destroys the monospaced alignment the language depends on to be read, and it makes a role's presence depend on a difference a reader may not notice.
- **Two roles are two identities.** A theme is expected to give each its own value; how far apart two values must be is a question about the roles' distinctness, not something a theme can be asked to enforce.
- **Every role says which mechanism implements it.** `implementedBy` is one of two words: `grammar-scope`, meaning a scope carries the role, or `server-only`, meaning no scope can. A role that says neither is an error, and so is one that says one and contradicts it. This is the one thing a consumer has to know before it can tell whether it is able to answer a role at all.
- **Every value a theme states meets a floor.** No role holds an exemption from it, and a comment is a value like any other: a comment that recedes by being hard to read is not receding, it is missing.
- **A theme's values are derived, not chosen.** The contract states the *rule* a value comes from, so that a check can fail a value that breaks a rule and not only a value that is missing.

## The kinds, and what a super type reaches

| | How many | Which |
| --- | --- | --- |
| Declare a super type | 12 | `subtype` : `keyword` · `included-type`, `type-reference`, `method-argument-type`, `method-owner-type` : `type` · `included-variable`, `method-local` : `variable` · `file-uri` : `string` · `capsule` : `class` · `abstraction` : `interface` · `method-argument` : `parameter` · `capsule-field` : `property` |
| This language's own root | 4 | `scope` · `identifier-reference` · `invalid-number` · `invalid-operator` |
| The role's own name **is** the host's standard type | 5 | `keyword` · `method` · `variable` · `comment` · `string` |

**Why the last row is declared nowhere.** `registerTokenType` *overwrites* the entry for the name it is given, renumbers the type, and gives the token-styling schema a property of our own for it. And declaring `keyword` a kind of `keyword` makes the host's `getTypeHierarchy` walk a cycle that never ends: it starts at the name, pushes the super type, looks the super type up, and finds the same entry again. So a role whose own name is already the host's type for that kind needs no declaration, and the verifier refuses one.

**Why a root declares nothing.** A root has no standard type to declare under, and a super type is the only thing that would make it reachable by a rule keyed on a standard type. Its hierarchy is exactly itself, which is what makes a theme's value for it **mandatory** rather than a formality — the fact a consumer needs before it decides whether a foreign theme must be extended at all.

**What the declaration buys, proved from the host's own code.** A host matches a rule's key against the token's whole type hierarchy, and the score is `100 − depth` (plus 10 when the key names a language), with a style written when a rule's score is **≥** the one already held. For `subtype`, declared under `keyword`: the hierarchy is `['subtype', 'keyword']`; our rule keyed `subtype` sits at depth 0 and scores **100**; a reader's rule for `keyword` sits at depth 1 and scores **99**. Ours wins. And because the declaration exists, a theme that has never heard of Khayyam still reaches our roles through their declared kind. `verify-roles.mjs` states this arithmetic in the host's own numbers on every run, and **stops the build** if the score ever came out the other way.

## The palette, derived rather than chosen

- **One hue per kind**, so a reader sees a family. Two roles of one kind carry the same hue; two kinds are told apart by at least 20° of hue or at least 12 L\*, and never by both failing. The kinds whose values sit below 0.05 of chroma have no hue a reader can resolve at all, and form a neutral lane separated by lightness.
- **The two sheets are two designs, and the rule holds in each of them.** Nothing obliges a light sheet and a dark sheet to agree in hue — only to agree in what a hue is *for* — and a value chosen for one background and adjusted for the other is a design for the first. The dark sheet walks the whole arc in short steps and leans on lightness upward, into the pale half sRGB has most of. The light sheet cannot: its floor against `#FFFFFF` caps every value at CIE L\* 49.9, and a measurement of the gamut says where sRGB has chroma to give on white at all — green, about 125° to 175°, and blue through violet to magenta, about 250° to 350°; the cyan and blue-cyan arc from 175° to 245° holds almost none at any lightness dark enough to read. So the light sheet spends its arc where the gamut has colour, and spends the cyan arc on the one value that is **bold** and so does not need its colour found. It puts its kinds on a fifteen-rung lightness ladder, so hue and lightness both tell two kinds apart rather than one of them carrying the whole weight; its top rung holds four kinds 37° to 85° apart, and its seventeen chromatic values carry a mean chroma of 0.140 against the 0.113 of the sheet it replaces, whose four kinds sat on a single lightness level 33° to 45° apart. **That is the difference the owner saw**: a set of mid tints a few degrees of hue apart reads as one colouring with the lights on, and a set of deep, saturated values spread over a lightness ladder does not.
- **Origin, and declaration against use, are carried by lightness and saturation and never by hue.** A name that arrived by inclusion sits further from the sheet's background than one declared here, and is the less saturated of the two. So `included-type` and `type-reference` are one kind told apart by lightness and by the italic, and so are `included-variable` and `variable`; and `variable`, `method-local` and `included-variable` are one kind on a three-step ladder. On white "further from the background" is *darker*, so the direction inverts with the background and the rule is the same rule.
- **The warm band — 15° to 120° of OKLCH hue — belongs to the two refusals and to nothing else.** Warm means error and nothing else, and the band is an interval the check reads, so a warm value on an ordinary role is a refusal with its measured hue named.
- **Every value is measured against the background *that theme* states for itself**, read from that theme's own base chain. The floor is the owner's **4.5:1** and the lowest value in either sheet is **4.54:1** (dark `comment`); the light sheet's own lowest is **4.83:1** (light `comment`) and its values run to 15.3:1, so its contrast is a ladder too rather than a crowd at the floor.
- **What is kept from [display.research.001.md → F3](./display.research.001.md#f3--a-proposed-value-per-role-per-theme-with-its-measured-contrast):** the method, the floor, the two backgrounds, and the **two dark refusal values** — `#ED5350` and `#FEB98B` — which the warm lane leaves untouched. **What changes: every other value in both sheets.** That is not a preference: hue now follows the kind, and under the earlier proposal the four declared Type categories shared one blue by a different argument, `variable` and `capsule-field` shared one green, and `method-local` had a hue of its own although it is the same kind as `variable`.
- **What each sheet's derivation could not do, recorded rather than hidden.** The dark sheet carries four pairs of roles in one family under ΔE76 10 under one of the three dichromacy simulations, and `palette.recordedDichromacyPairs` names each pair, its worst figure, and the reason. **The light sheet carries none**: measured, its weakest pair the contract measures is `variable` against `method-local` at ΔE76 10.8 under deuteranopia, its `abstraction` against `type-reference` — the pair this contract named as the weakest in either sheet, at protanopia 5.6 — is now 33.9, and the ten closest pairs of any kind are all at ΔE76 11.1 or more, of which the three closest are the neutral lane's own steps and the next three are steps of the `variable` ladder. A pair that fails with a stated reason is a decision; a pair that fails silently is a defect, and the check refuses the second.

## The roles
Twenty-one roles. Each names what a reader must be able to tell apart; the scope column is what a realization emits for it, and a role with no scope is one no grammar can answer at all.

| Role | What it names | Scope |
| --- | --- | --- |
| `keyword` | A reserved word of the language: `tp`, `vr` | `keyword.control.khayyam` |
| `subtype` | The subtype keyword that names a Type's category or routes an inclusion: `in`, `cp`, `mt`, `ab`, `sc` | `keyword.control.subtype.khayyam` |
| `included-type` | A Type whose name arrived here through Type Inclusion | `entity.name.import.khayyam` |
| `included-variable` | A Variable whose name arrived here through Variable Inclusion | `variable.other.import.khayyam` |
| `file-uri` | The source-level path an inclusion routes to | `string.quoted.double.file-uri.khayyam` |
| `capsule` | A Capsule declared in this file | `entity.name.class.khayyam` |
| `abstraction` | An Abstraction declared in this file | `entity.name.interface.khayyam` |
| `method` | A Method, at its declaration and at every call site | `entity.name.function.khayyam` |
| `scope` | A Scope declared in this file | `entity.name.scope.khayyam` |
| `type-reference` | A Type in a type position whose category and origin this file does not state | `entity.name.type.khayyam` |
| `variable` | A Variable this file declares at **file level** | `variable.other.khayyam` |
| `method-local` | A Variable a method body declares, of no wider validity than that body | **none — `server-only`** |
| `method-argument` | An influencing or influenced variable named in a method signature | `variable.parameter.khayyam` |
| `method-argument-type` | The declared type of a method argument | `entity.name.type.parameter.khayyam` |
| `method-owner-type` | The owner type in `(self {owner})` | `entity.name.type.owner.khayyam` |
| `capsule-field` | A Capsule's field, private to the Capsule | `variable.other.field.khayyam` |
| `identifier-reference` | A bare identifier whose binding the realization cannot state | `variable.other.reference.khayyam` |
| `comment` | Text the author marked as not code | `comment.line.double-slash.khayyam`, `comment.block.slash-star.khayyam` |
| `string` | A quoted literal that is not a file URI (reserved — the language has no string literal) | `string.quoted.double.khayyam` |
| `invalid-number` | A bare number, which the language does not admit | `invalid.illegal.numeric.khayyam` |
| `invalid-operator` | An operator character the language does not admit | `invalid.illegal.operator.khayyam` |

`identifier-reference` is negative and load-bearing: its job is to ensure a use site does not read as a local declaration, so a reader is never told that an included name or an argument is this file's own. A realization that can resolve the binding replaces it with the resolved role. `subtype` is a distinct role from `keyword` so a theme may style it apart, while its scope sits under `keyword.control` so a theme that styles keywords generically still reaches it.

`variable` and `method-local` were one role until the owner ruled, on 2026-09-28, that a method's local variable and a file-level one are different things: two declarations with two different scopes of validity are two identities, and the load-bearing rule above says one role cannot hold both. `method-local` is the **only** role with no scope, and the reason is a property of TextMate rather than of this repository's grammar: a `vr` in a body and a `vr` at file level are the same line of text, and the line that opens the body is not on it. A resolver holds the whole document and can tell; a one-line matcher cannot, at all.

## How a consumer implements it
A **realization** assigns the roles to text, and a **theme** supplies the values.

1. **A realization emits every role's scope for the parts the role describes, and emits no scope this contract does not name.** A realization that invents a scope has left the contract; a realization that never emits one has abandoned a role. **A role declared `server-only` names no scope, because none can carry it** — the realization that answers it is the one that can see the whole document, and one that cannot must leave it to that realization rather than guess a scope. Leaving a role's scope unemitted is not the same as abandoning the role: a grammar answers every use site with `identifier-reference` and is not expected to answer a `server-only` role at all.
2. **A theme supplies a value for every role-attribute pair**, keyed `khayyam.<role>.<attribute>` — role first, because the role is the identity being displayed, and attribute second, because the same role may be rendered differently on each channel. A role carrying two attributes therefore has two independent variables.
3. **A missing value is an ERROR, not a fallback to a default.** A theme that omits a value leaves the reader unable to tell an unstyled role from an unrecognized one. The one legitimate "nothing to say" is written out explicitly as the empty value — which is why `fontStyle` is a real value for most roles, not a missing one.
4. **An unknown role is an ERROR, and so is an unknown attribute.** In particular a value for `fontSize` is an error, because size is a discouraged channel for code.
5. **A value below the floor is an ERROR.** Every `color` value meets or exceeds **4.5:1** against the background that same theme states for itself, and no role holds an exemption — `comment` among them.
6. **Two roles may share a value for the same attribute.** Nothing in the contract forbids it.
7. **A theme mirrors a value onto a scope only where a scope exists.** A `server-only` role has none, so its value reaches a host that styles semantic tokens directly, and no TextMate scope carries it.

A theme is a value sheet and nothing more. It never declares a language to a host, and it never adds support for Khayyam anywhere — registration with a highlighter or a code-hosting site is a separate step, tracked in the [handoff](./display.handoff.md).

## The two mechanisms, and where each stops
The contract names what must be true of the display; it does not say how a given engine can achieve it. `display.json` records the two profiles it knows:

- **TextMate** — a grammar assigns a scope name to each part of a line, and a theme maps scopes to values. Identity is available only where the *syntax* determines it: at a declaration site, where the subtype keyword names the category, and in a method signature. At a use site the binding of a bare identifier is not recoverable, so the role collapses to `identifier-reference` — under this profile an argument, a declared variable, and an included name are indistinguishable once used. A captured back-reference cannot be re-matched inside the same construct in `vscode-textmate` (verified: a nested rule using one silently disables the construct's whole pattern list), so an identity cannot be carried from a signature into a body, or from an inclusion into a body. **And the same limit takes a whole role away where the only difference is the block a declaration stands in**: `method-local` is the one role this profile cannot answer at all, at a declaration or at a use, because the line that opens a body is not on the line the name stands on. That is a limit of the mechanism rather than of any grammar file, and the contract says so on the role rather than leaving a consumer to discover it.
- **LSP semantic tokens** — a language server resolves each identifier to its declaration and emits the role of what it resolved to, which is exactly what the TextMate profile cannot do, and it is the only profile that can answer a role no scope can carry, because a declaration's block is a fact about the document and not about a line. The standard semantic token types are a subset of what this contract needs, and **a role's kind is only usable once a realization declares it**: a host matches a rule's key against the token's whole type hierarchy, and a type that declares no super type has a hierarchy of exactly itself, so a reader's rule for the standard class never reaches a role that was not declared under it. The extension therefore contributes `contributes.semanticTokenTypes` with one entry per role whose kind is a standard type, and those twelve entries are what make a theme that has never heard of Khayyam reach our roles anyway. Where a role has no standard counterpart, this contract is authoritative and the role is declared nowhere. The list the host registers is not the list the protocol's specification names — this host registers `member` and not `modifier`, and no `defaultLibrary` — so a decision about which names exist is made against the host's own list, read out of the host's own product. The token type a realization announces for a role is the **role's own name, spelled as the contract spells the role**; the language is stated where the host reads it — in the host's own field for it, and in what the realization serves — and never welded into the name. A realization's vocabulary is its own, and a host that reads a different form carries the translation in its own files ([execution.md → The language server answers in its own abstractions](../execution.md#the-language-server-answers-in-its-own-abstractions)): a host that splits a name at a separator into a type and a language matches the type against a name that is the whole of it, and matches nothing, which is that host's own cost to carry — the role keeps the name the contract gives it.

## The worked example: this repository's editor
The VS Code extension under [`.agents/vscode/extensions/khayyam-language/`](../../../.agents/vscode/extensions/khayyam-language/) is the one realization this repository ships, and it shows three things a consumer outside a repository has to decide for itself:

- **How the values reach a renderer.** A contributed colour theme *replaces* the active theme outright, so one covering only Khayyam scopes would strip every other language's colours — measured with the real highlighter, 0 of 26 Python tokens kept a colour, against 26 of 26 under Dark+. The extension therefore contributes two selectable themes, `Memar Dark` and `Memar Light`, and each states the contract's twenty-one roles in its own `semanticTokenColors` — the map a host resolves a semantic token's colour out of, keyed by the token type and valued from that theme's own sheet — opts into semantic highlighting, and states no colour outside the contract's roles: no `colors` block at all, and `tokenColors` naming only this language's scopes. What a reader keeps of everything else is a base, and a base is not named by identity: a host resolves an `include` by a path relative to the file that states it, so naming a theme the host already ships reaches a file inside this extension that does not exist, and the base is the shipped theme files copied into this extension's own `themes/` folder. Dark Modern and Light Modern are the bases, chosen because their own backgrounds are the ones the contract's contrast was measured against. A consumer whose host resolves an `include` that way can do this; one that does not has a different problem, and a theme that states a workbench colour itself answers none of it. The language-scoped `editor.tokenColorCustomizations` and `editor.semanticTokenColorCustomizations` defaults stay beside the themes and carry the dark sheet, because that setting has no theme dimension; whether they serve a reader who selects no Memar theme is the one question left open here ([handoff](./display.handoff.md) → Open Questions).
- **How the two sides are kept from drifting.** [`scripts/verify-roles.mjs`](../../../.agents/vscode/extensions/khayyam-language/scripts/verify-roles.mjs) checks both directions — every role implemented and every scope the grammar emits named by the contract, every role-attribute pair valued in every theme and every value naming a known role and attribute, and the theme's host-format rules agreeing with the values it declares. It also checks the third side, the one a host reads the roles through: the legend the language server actually advertises is read out of the server's own module, a legend entry carrying a separator is refused, and every role's name must appear as a key in the `editor.semanticTokenColorCustomizations` rules with the same spelling the legend gives it, and in each contributed theme's `semanticTokenColors` under that same spelling carrying that theme's own sheet's value. The themes the manifest offers and the theme files the extension ships are counted against each other in both directions — a contribution naming no file, a file nothing offers, a label disagreeing with the file's own name, a `uiTheme` disagreeing with the file's `type` — and each offered theme must rest on a base the extension ships, read the way the host reads it, and state no workbench colour of its own. A `contributes.semanticTokenScopes` bridge is **refused** outright, and the ground is that a bridge decides the value for every reader whose theme is not ours: it probes a TextMate scope against whatever theme is active, so a reader who selects a theme that has never heard of Khayyam is given that theme's value for `variable` or `keyword.control` instead of the contract's. And it checks the two-way split the contract now states per role: a role is either implemented by a scope the grammar emits or **declared `server-only` with its reason stated in the contract**, and a role that says neither — or says one and contradicts it — is refused, so a consumer that cannot answer a role finds out from the contract rather than from a missing colour. Its own last line is the verdict, and that line is fixed by a test before the check says it ([`display/test/report.test.ts`](./test/report.test.ts)); the verdict carries the count each of the contract's two mechanisms answers, because the two are not the same set. A consumer outside this repository has no such check; the contract is then the only thing preventing the two sides from diverging silently.
- **Whose name a theme carries.** The display contract is Khayyam's and the theme is Memar's, and each name is kept where it belongs. The sheet inside a theme file is keyed `khayyam.<role>.<attribute>`, because the contract is what the theme realizes and the contract fixes the key; the name a reader's picker shows is `Memar Dark` or `Memar Light`, because that label is what says whose choice of colours they are looking at. The check holds both halves: a label that disagrees with the name the file it points at declares, a label that names no Memar theme, and a sheet keyed by anything but the contract's own role names.

## Authority and drift
The roles are not invented here. `display.json` cites the language document each role comes from — [Type and its four categories](../../../docs/khayyam/khayyam.md#type), [Capsule Structure and Privacy](../../../docs/khayyam/encapsulation.md#capsule-structure-and-privacy), [Inclusion Is Not Module Definition](../../../docs/khayyam/modularity.md#inclusion-is-not-module-definition) — and the identity vocabulary the toolchain already uses in [`core/src/sr.ts`](../core/src/sr.ts). `display.json` wins any disagreement: when a realization and this file differ, the realization is corrected, and a new display distinction is added as a role in the contract first, never smuggled in through a grammar or a theme.

**What is not this repository's to decide is what a role is *called*, when the role is a claim about the language.** The name of the twenty-one roles here is this toolchain's own vocabulary, reached from the contract's own words and not from any consumer's constraint ([execution.md → The language server answers in its own abstractions](../execution.md#the-language-server-answers-in-its-own-abstractions)); whether the *language* names a variable declared in a method body differently from one declared at file level — and whether it draws that distinction at all — is a question for [docs/khayyam/](../../../docs/khayyam/) and for the owner, and no file in this repository answers it. The role's `origin` field says which names are the owner's and which are this toolchain's, so a later reader can tell a claim about the language from a claim about how it is read.

## Membership criterion
Material belongs in this folder when its subject is **how a Khayyam source is read** — the roles, the attributes, the theme contract, the checks that keep a realization honest about them, and the work of reaching the consumers outside this repository. It does not belong here: the grammar of the language (that is [`docs/khayyam/`](../../../docs/khayyam/)), a host's own mechanism (that is the host's), or a theme's aesthetic choices (a theme supplies values; the contract never states them).

Whether this folder is this material's long-run home is open — see the [handoff](./display.handoff.md) → Open Questions. It is language-owned material, and [the module README](../README.md) places language-owned material under `docs/khayyam/`.
