# Khayyam Language Server Handoff
Open work for the language server, [`modules/khayyam/lsp/`](.), which realizes the [display contract](../display/display.json) and the toolchain's own reading over LSP. The plan that governs the module's order is [execution.md](../execution.md); the open state of the toolchain as a whole, and of the milestone this folder's work belongs to, is [execution.handoff.md](../execution.handoff.md) — this file carries only what a session working inside `lsp/` needs and cannot re-derive from the tree. It was opened on 2026-09-29 for the work that makes definitions followable, because that work raised a boundary question the module handoff does not answer and a session cannot answer for it.

## Topic & Purpose
Make a reader of a `.kh` file able to ask where a name is declared and be sent there, over the same server that already answers what every name in the file is. The server's answers are its own — the display contract's roles, the toolchain's refusal labels, the document it holds, the reader, and the gate — and a definition is an answer in the same terms: a place in a document, named by a URI, a line, and the extent of the declared name. The order is the module's ([execution.md → How work in this toolchain proceeds](../execution.md#how-work-in-this-toolchain-proceeds)): the abstraction first, then a test that fixes what comes out, then the code.

## Status
Active

## What the reader reaches today
The whole path, and each part of it has a check: the server answers `textDocument/definition` over its own stdio, and [test/goal-definition.test.ts](./test/goal-definition.test.ts) states the goal in one document from the running server — the three names the document declares reaching the places they are declared at, and the two that arrived by an address reaching no place and being told which root was found and which manifest is not there. A fourth check in the same file pins the ends of a name, so a caller that aims one character past one is caught by a test rather than by a reader's log. The extension this repository ships builds its own LSP client rather than a library one, so the editor is given a definition only if the extension registers a provider for it — which it now does, reading the server's own `definitionProvider` at the handshake and registering one when the server says it answers. [test/client-definition.test.ts](./test/client-definition.test.ts) holds the other end: the request the extension sends, the reading of what comes back, that a provider is registered at all, and the two halves together over the real server. **What no check can reach from here**: a reader's own go-to-definition in a live editor, because no editor was run — the same limit the roles carry.

## What the server answers today
It holds the open documents, re-reads one whole on every change under the Full capability it declared, publishes one diagnostic per fault the reader met, answers `textDocument/semanticTokens/full` with the contract's twenty-one roles in the contract's own order, and answers `textDocument/definition` with the place a name is declared at. **A definition that would leave the document is not answered at all**, because an address is resolved by what a manifest declares and no manifest says how — the refusal names the root it found and the manifest that is not there, and the same sentence stands behind every `in` in every file. The reader behind those answers is the one that recovers per declaration, so a file with one fault still has the rest of itself displayed. The folder is split by what each piece answers — the transport, the documents it holds, the capabilities it declares, the root a document is placed in, the reader's tables, and the answers themselves — and `server.ts` is the process that wires them; a reader looking for one of them starts from [definition.ts](./src/definition.ts) or [semantic.ts](./src/semantic.ts), which is where either answer is stated.

## Decisions
- **A definition is a place a name is declared at, and a place is a document, a line, and an extent** — Decided (2026-09-29). A role says what a name *is*, and one name is one thing at every position, so a definition is a different kind of answer from a role: a position in a document rather than a class. The three parts are the document the declaration stands in, the line, and the extent of the declared name itself rather than of the whole declaration — a reader who asks about `err` is sent to `err`, and the surrounding signature is still there to be read around it. The line is not new state: [`core/src/sr.ts`](../../core/src/sr.ts) already carries it on every declaration, and it carries it for exactly this purpose (a reader that recovers per declaration pairs a declaration with the line it stands on). What the representation does not carry is the column, so the extent is found by the scanner the server already runs.
A definition asked at any position stands on the one binding, and a binding this document does not make reaches nothing
- **The four names the goal names stand on the one binding, and a binding this document does not make reaches nothing.** A name used in a method body reaches its parameter, its body-local, or the file-level or included declaration it resolves to; a parameter named in a signature reaches that slot, which is its own declaration; and a declaration's own name reaches itself. Those three follow from one claim rather than being cases of it: a name is one binding at every position it stands in, so asking at the declaration and asking at a use cannot disagree. The fourth — a type or variable that arrived by an address — is the one the owner's ruling of 2026-09-29 answers as *nothing*, because nothing declares how an address resolves; see the decision *What a root resolves an address by is the root's manifest to declare*, below.
- **A document's claims on other files are looked for from the root its own place walks up to, and one this toolchain cannot account for is a fault where it stands.** The reader does not resolve addresses, so a name the file says arrived by one is bound by the file's own word: `tp Bool in "..."` makes `Bool` an `included-type` on this machine and on any other, because a role says what the file says a name is, and a role that changed with the filesystem would make one file read differently in two directories with nothing saying why. Whether the address resolves is a separate fact about the file, and until the decisions above nothing in the server said it. So the server asks — from the root it found — and reports one fault per claim it cannot account for, under the labels the toolchain already has: an address that resolves to nothing is `unresolved-import`, a file that declares no such name is `name-not-declared`, and a file that declares it as the other kind is `kind-mismatch`, each with a rule folder of its own ([unresolved-import](../rules/unresolved-import/unresolved-import.md), [name-not-declared](../rules/name-not-declared/name-not-declared.md), [kind-mismatch](../rules/kind-mismatch/kind-mismatch.md)), and the gate has refused a unit on exactly those three since M1. Decided (2026-09-29). What is decided here and what is not: that a reader is owed this is the toolchain's own ruling, and the two analysers the [module handoff](../execution.handoff.md#two-analysers-analyze-and-the-servers-own-binding-table) carries are untouched by it — the server still answers roles from its own table and still resolves nothing an address brings, so a name whose claim nothing accounts for still carries `included-type`. The three labels are what *would* be asked, and today the walk stops at the first: no manifest declares how, so the other two questions are not reached.
- **A claim's fault carries the reason resolution gave, verbatim, because three different faults answer not-found alike.** A file that is not in the repository, a repository whose root this toolchain could not find, and a repository whose manifest declares nothing about how an address resolves all answer "not found", and only the sentence tells a reader which one happened — writing the file fixes one, opening the repository as a folder fixes the second, and writing a manifest fixes the third. So the reason resolution gave is in the finding as it stands, not summarised, and the address the claim names is in it too: a reader told a claim cannot be accounted for, and not which claim, has a line to look at and nothing to read on it. Decided (2026-09-29), with the decisions above.
- **A name nothing declares has no definition, and that is an answer** — Decided (2026-09-29). A reserved word, a quoted literal, punctuation, a name no binding in the file answers, and a name that arrived by an inclusion whose URI addresses nothing all answer with no definition. The last is stated rather than worked around because the alternative is a place that does not exist: a server that answered the inclusion line instead would be sending a reader to a declaration the file does not have. This is the same refusal discipline the diagnostics carry — a reader is better served by nothing than by a confident place that is wrong.
- **This folder's first production resolver is the one that now has no base at all.** State, 2026-09-29 and revised 2026-09-30. It was worth recording that the server is the toolchain's first production resolver of an address, because [`analyze`](../../core/src/frontend.ts) has never been called outside the tests over it in [`core/test/`](../../core/test/) — so whatever a resolver decides, the server is where it is decided first, and there is no earlier implementation whose behaviour constrains it. That entry originally stood as the decision that the base is the repository root; that half was retired the next day when the owner ruled the base is the writing module's manifest, and the sentence that remains is the part the retirement did not touch.
- **A body is read in two passes: what it declares, then what it uses.** The language fixes a declaration's line and states nothing about the order of a body's statements, so a single forward walk knows only the names a use is preceded by, and then a name is two things, which is the one thing the display contract's first principle and a definition both refuse. Binding every name the body declares first and then resolving every use against the whole is the reading that makes a name one thing wherever it is used. Decided (2026-09-29). What is decided here and what is not: the choice of two passes over one is this toolchain's, because both readings are consistent with the language; whether a use standing before its declaration is an unbound name **by design** is a claim about the language, and it is carried as an open question in [khayyam.handoff.md](../../docs/khayyam/khayyam.handoff.md).
- **A declaration is bound in the block that contains the statement, and in no other.** The block is the whole of what makes a name declared in a body the `method-local` it is rather than the file-level `variable` (display.json -> `method-local`), and the block holding a declaration statement is the one the name belongs to. For a `tp {name} sc` written in a method body that is the method body, which is what lets a driver name the scope it is about — the `CF.ELSE(elseProcess)` a line above the `tp elseProcess sc` that declares it — so the scope's name is answered throughout the method, inside the scope's own statements and inside a block beside it. For a `vr` written inside a scope it is that scope, and the name reaches that scope's statements and nothing beside them. Decided (2026-09-29), with the two-pass reading above: two passes change the order of the uses and not the reach of the names.
- **A call site names a Method, and the declaration says which one.** The dot operator is the language's only invocation form, so the name before an opening parenthesis is a Method; when this file declares a Method by that name, the call is resolved against that declaration and carries the place it is declared at, and when it does not, the Method belongs to something else, is named by nothing here, and the call carries the role with no place. Decided (2026-09-29). The reason is the contract's first principle rather than a preference: a role follows the binding and never the position, and taking the role from the parenthesis while taking nothing else from the binding is a role that came from where the name stands.
- **A receiver named in a signature's owner slot has no role and no definition, and the two absences are one decision.** The owner group says which type a method belongs to, and what stands in front of that type is the receiver, whose meaning is supplied by the type beside it rather than by anything it says itself. The display contract gives the type a role and the receiver none, and a role the contract does not recognise is not an identity this toolchain may follow: the receiver is not bound, and a definition asked at it answers nothing. Decided (2026-09-29). What is left is the contract's own: a display distinction is added as a role in [display.json](../display/display.json) first and never smuggled in through a grammar or a theme, so a receiver that should be followable is a change to the contract, which is the owner's file.

- **A definition into a document this server holds is read against that document's own text, not against the file on disk.** A `Location` is read by the editor against the text the editor holds, and the text this server holds of an open document is the editor's own — the Full capability means one whole text per change — so a definition that went to disk for a document the editor has open with unsaved edits would name a line the reader is not on. The held text therefore comes before the file system, and a document this server holds no text for is read from where it is. Decided (2026-09-29). What this costs: a definition can name a place that is not yet saved, which is the place the reader asked about, and a reader who wants the file on disk has the file.

- **This server walks up for a module manifest, and the boundary is a fact rather than a name.** Ruled (2026-09-29, owner) and built on 2026-09-30. An address is resolved through the manifest of the module whose file wrote it, the manifest is looked for upward from that file's own directory one directory at a time, the nearest one answers, and the walk ends at a boundary this project states rather than at a directory called something. **What the boundary is and is not** is the part that took two rounds: it began as the directory holding `.agents`, and the owner's objection was that naming a directory makes the walk's end depend on a spelling — and, more deeply, that a filesystem realization is not what a protocol is built on, so finding directories is the one thing a filesystem-based dependency management has to do rather than the right method. And then that was struck out too: **the criterion is a statement the project being worked on makes, not one this framework makes.** `MEMAR_ROOT` says where *Memar's source* sits on a machine, so in a project that merely uses Memar it says nothing about that project — and a criterion that answers for the framework instead of for the project is the storage engine's mistake in a project's clothes, which is the same mistake this folder made with `.git` and then nearly made again. So `MEMAR_ROOT` is this repository's instance of the criterion and not the criterion, a foreign project states its own somewhere this folder does not know, and until it does the walk ends at the filesystem's own root **and says that a manifest found that way was found by leaving the project** — on a machine holding several projects that is another project's module, and a resolver that took it as its own would be wrong in a way nothing afterwards could explain. All three endings are named in the answer, because they are three different facts with three different remedies. [manifest.ts](./src/manifest.ts) is the walk; [workspace.ts](./src/workspace.ts) is what a reader is told.
- **A format is a registry entry, so "JSON was simpler" cannot harden into "JSON only".** Decided (2026-09-30, toolchain), carrying the owner's ruling that the objection "YAML would have been better" is one a reader is entitled to make and that the answer has to be true rather than promised. A format is an extension, a name for a sentence, and a parse; adding one is one entry. A manifest in a format this server does not read is **found**, named, and refused with the work to add it stated — a different answer from no manifest being here, because one wants a file written and the other an issue opened. Three cases are told apart because three things can happen: no manifest, a manifest in a format it cannot read, and a manifest it read. Two manifests in one directory is a fourth and it is a fault rather than a choice, since a reader that picks one has invented a precedence nothing stated.- **A definition this toolchain cannot account for is an error rather than nothing.** Decided (2026-09-29, toolchain), and it is the whole of what a refusal is for: a reader told "nothing there" cannot act, while a reader told which manifest would answer has one thing to go and write. So the answer to a request that would leave the document is nothing rather than a guessed place, and the publication beside it carries the reason. The three labels the toolchain already refuses a unit under — `unresolved-import`, `name-not-declared`, `kind-mismatch` — are what *would* be asked once a manifest is consulted, and the walk stops at the first question, so only the first is ever reached. What a *resolver* is, and what it costs to have one that refuses a name by no place, is stated once here and the refusal is what is built.
- **The manifest's own content is not this folder's to state.** The name of the manifest, what a module claims, how one reaches it, and which other modules it uses are [dependency management's subject](../../docs/protocols/modules/dependency-management.md) and live there. This folder holds one line of it — that a base is a module's manifest and not a root — because that line is what deleted a file of its own, and the rest it cites rather than repeats: a later session that finds manifest design in a language-server handoff has found a mistake, because this folder realizes the protocol and does not state it.
- **Every misstep on the way is recorded as a question about whether the protocol has a better method.** Ruled (2026-09-29, owner). The rule is not a place for complaints; it is a place for the questions this work raises about the protocols themselves, so that a later session answering a protocol question knows which live facts of the tree pushed on it. See [Missteps this work found](#missteps-this-work-found).
## Missteps this work found
Each is a mistake met on the way that is a question about a protocol rather than about this code, kept so that the protocol question is answered against the fact that raised it rather than in the abstract.19068- **A framework cannot be its own first case.** Two boundary criteria for the same walk failed the same way, an hour apart, and the second failure was subtler than the first: the directory holding `.agents`, then this repository's own `MEMAR_ROOT`. Both were true of *this repository* and neither was true of a project that merely uses Memar — and Memar is a framework, so a project that uses it is the ordinary case and this repository is the special one. A criterion that answers for the framework rather than for the project is the storage engine's mistake wearing a project's clothes, which is what the `.git` walk was and what I rebuilt one level up without seeing it. **What the question should have been, and was not**: not "what directory ends this walk" but "who says where the walk ends, and is that someone other than me" — a question about the *subject* of a criterion rather than its spelling, and answering it would have retired both attempts at once. The protocol's own sentence is the one that settles it: [Modularity → Modularity Is Not Deployment](../../docs/modularity.md#modularity-is-not-deployment) is about a Module, and the same refusal applies to a criterion. **What this costs in the toolchain**: nothing is lost and one thing is gained — the walk reports *how* it ended in every case, so a project with no statement of its own gets a warning instead of another project's answer.

- **A URI is not a path, and a resolver that conflates them reports a file that is there as one that is not.** Reading a `file:` address as a string reads it as a path on disk and finds nothing, and the failure is indistinguishable from the file's absence — a `refused` that a reader would repair by writing a file that is already there. Whether the protocols distinguish an address that is not an address from one that is not resolvable, and require a resolver to say which, is unasked in every protocol this work touched. `docs/protocols/` and the Language Server Protocol's own URI rules are the places to answer it.
- **A client's notification stream and its own requests have no stated order, so a client cannot tell which notification answers the change it just sent.** A publication counted as "the next one" from whatever had arrived by the time it was looked for is the next one only when nothing is in flight, and a server answering two changes in order can have both publications outstanding. The race is invisible in a test that sends one change and visible only under a whole suite running at once, which is the worst way for a defect to appear. Whether the protocols state an ordering guarantee between a client's request and the server's notifications — and what a client may rely on when it has sent two — is unasked, and [compiler.handoff.md → The analysis-event schema](../../docs/protocols/compiler.handoff.md) already carries ordering guarantees as part of an undecided schema.
- **Two answers about one document, one cached and one not, with nothing saying they may differ.** Roles are cached per document and dropped on a change; a definition is asked for every time. Both are correct, and a reader sees a name coloured from a text that a definition beside it was read against a later one. Whether a protocol may let a client answer one request from a cache and not another, and if so on what the client is then asserting, is unasked.
- **A protocol cannot say what a resolver does when the thing it depends on is undesigned, and the code then fills the silence with its own default.** The import address rule's "the base is the repository root" was read for a day as a base the toolchain could use on its own, and every cross-file answer in this folder rested on that reading until the owner's ruling made the base manifest-declared. A rule that states a default as a plain fact is read as a licence; stating that it is a default nothing has yet overridden would not have been. That is a question about how a rule states a default, and it belongs to [Documentation → Normative language](../../docs/documentation.md) rather than to any of the protocols.
- **A delta stream states an absolute position and a difference in the same field, and the protocol says which in a clause a reader reads once.** Semantic tokens arrive as five numbers per token, and the second is how far along the line — from the token before it when the token is on the same line, and from the start of its line when it is not. The client that walks the stream got it wrong in the one way that stays wrong quietly: it treated the field as a difference everywhere except the first token, so every token that opened a line was placed at its absolute character *plus* the last token's, drifting one line further with every line of the file. The extension's self-test asked where a name on [`main.kh`](../../main.kh)'s eighth line was declared and was told nothing, because the position it asked at — character 42 of an eighteen-character line — was not a position the server had ever heard of, and nothing is also what a provider that was never registered answers. Two more mistakes rode the same walk and were found with it: asking one character *past* the end of a name, which is where the next character begins and is not inside that name; and taking the first name in the stream, which on any file that starts with `in` declarations is a name that arrived by an address and is therefore declared in a file no manifest here says how to reach — so the self-test asked about the one kind of name that cannot have a definition and printed the answer it prints when nothing works. The protocol question, which is the one worth putting to it: **a positional stream that changes the meaning of a field on the value of the field before it should say so at the field**, and a client that walks it has no way to detect its own mistake except by checking a position against the text it already holds. See [Language Server Protocol → Semantic tokens](https://microsoft.github.io/language-server-protocol/specifications/lsp/3.17/specification/#textDocument_semanticTokens) and the self-test in [`client.js`](../../../../.agents/vscode/extensions/khayyam-language/scripts/client.js) as it now stands.
- **A rule that states a default as a plain fact is read as a licence, so stating that it is a default nothing has yet overridden would not have been.** Kept as its own entry because the one above found it by a protocol's silence and this one is about this repository's own documents, and the two fail the same way. [import-address.md](../rules/import-address/import-address.md) said the base is the repository root as a fact, and the toolchain read it for a day as permission to use that base. **It says *by default* now**, with the sentence that a project may resolve from elsewhere provided it says so, so this repository's own reader is no longer at risk of the same reading — and the misstep is not a closed subject for a reason that is the rule's own: the same wording will be needed in every rule that names a default, and nothing in the documentation system yet says a default must be marked as one. That belongs to [Documentation → Normative language](../../docs/documentation.md), and the rule is the worked example rather than the fix.

## Ambiguities Resolved
- **Is a definition a role, a binding, or a position?** — Answered: a position, and the role is a separate answer about the same occurrence. Conflating them would make the answer to "where is this" a class name, which sends a reader nowhere; the server already answers the class through `semanticTokens`, so the two together are what one occurrence is and where it came from, and each is asked for separately.
- **Does following an inclusion mean the server opens a file, and does that settle the two-analyser question?** — Answered in part, and the rest is carried below. Reaching the declaration of an included name needs the file behind the URI, and the server now reads it — but it does so through [`readUnit`](../../core/src/reader.ts), the reader that recovers per declaration, and not through [`analyze`](../../core/src/frontend.ts), the gate that refuses a unit whose closure it cannot account for. So the display question the [two analysers entry](../execution.handoff.md#two-analysers-analyze-and-the-servers-own-binding-table) carries is untouched: the server still answers roles from its own table and does not know whether an inclusion resolves, and a name whose inclusion resolves to nothing still carries `included-type` at its use. What is new is that such a name now also has no definition, which is a statement about a place and not about a role.

  - Blocks continuation: no for a claim; yes for any fault inside a body, which is M3's subject and is listed below.
  - Path: reading a method body, which is the control-flow library's subject and not a diagnostic decision.
## Assumptions
- **The column of a declared name can be found by scanning the line the representation says it stands on** — Stability: Strong for a language whose declaration occupies one line; the scanner's columns are string indices, which is what a client counts characters in, so the two agree without a conversion. What changes it: a language in which a declaration spans lines, which [khayyam.md → Declaration separator](../../../docs/khayyam/khayyam.md) does not permit.
- **A file named by an inclusion URI can be read whole when a reader asks for a definition** — Stability: Weak. Nothing in the toolchain has done this in production, and the corpus behind those URIs is an unreviewed archive (the module handoff's own assumption). What changes it: a target file the scanner refuses at the file extent, where reading stops and the definition is whatever was read before the fault.
