## Open Questions — the first-level tree
- **`runtime/` against `computer/runtime/`.** Both exist. `modules/computer/runtime/` holds `protocol/`, `scheduler/` and `thread/`; `modules/runtime/` holds one folder, `flow/`, whose README states a question rather than a subject ("`## [{panic, recover}, {try, catch}, ...]`" under the title Flow). README.md places "the runtime and its mechanisms" under `modules/computer/runtime/`, which `modules/lib/lib.md:25` also does. Is `modules/runtime/` the general runtime and `computer/runtime` its mechanisms, or is one of them misfiled?
- **Where the type categories are realized.** `modules/computer/datatypes/` and `modules/computer/datatype/` both exist, beside `modules/computer/datatypes/protocol/data-types.kh` and `modules/computer/datatype/protocol/*.kh`. One of the two spellings is wrong, and the choice of which is a decision about the layer's vocabulary.
- **The registry folders.** `modules/modules/` holds the module system itself — `module/`, `service/`, `app/`, `error/`, `impl/`, `locale/`, `data-type/`, `gui/`, `validators/`, `syllab/` — and its own `____bug/`, `____json/`, `____storage/` scratch trees, which `.gitignore`'s `*____` keeps out of version control. Which of these are members and which are scratch is not stated anywhere.
- **`modules/modules` as a name.** The folder's subject is the module system, inside a folder already named `modules`. Whether it is `modules/modules`, `modules/module-system`, or something else is undecided.
- **Identity's ownership.** `modules/identifier/` holds identity, per `modules/lib/lib.md:25`, but the `UUID` name is claimed by four modules at once — `computer/datatype/protocol`, `identifier/record/protocol`, `memory/record/protocol`, `process/request/protocol` (live `reemit --dry-run`, 2026-10-01). The qualified-names rule records the two-module form of this question; the four-module form is wider.
- **Where the concurrency primitives live.** `modules/computer/runtime/` holds `thread/` and `scheduler/`; `docs/protocols/runtime/immutable_infrastructure.md` and `docs/protocols/computer/concurrency.md` both reach into this area. No document states which of runtime, process, or computer owns a primitive.
- **`lib/`'s membership.** See its own questions below.
- **The `computer/` against `hardware/` boundary.** `modules/hardware/` holds one folder, `cpu/`, with three files: `core.kh` (a capsule whose Go clue block records a body-less assembly function), `core.s` (that assembly, 123 bytes), and `cache.txt` (a Go snippet for `cache_line_size`). Whether a CPU is hardware, a computer, or neither is stated nowhere.
- **`time/`'s mixed axes.** `modules/time/` holds `astronomy/`, `earth/`, `mars/`, `unix/`, `utc/`, `epoch/`, `monotonic/`, `duration/`, `protocol/`, `timer/`, `timing-wheel/` — calendar systems, epoch families, monotonic clocks, timers and a wheel in one folder. `docs/protocols/time/time.handoff.md` carries the open question about `time/monotonic.Time` having no declaring protocol file.
- **Minor naming inconsistencies.** Several, recorded only as a category: `datatype` against `datatypes` above, `____gen.kh` and `____make-error-js-sdk.kh` beside conventional siblings, `sRPC` and `immutable_infrastructure` against kebab-case and snake_case neighbours. None is worth a decision on its own; the question is whether one convention is chosen for the layer and applied.
- **Three questions the notes counted but did not name.** The session record says fourteen and preserved eleven. The remaining three are not recoverable from anything in this repository, so they are absent here rather than reconstructed. Anyone who remembers them should add them.

## Open Questions — `lib/`
`modules/lib/lib.md` is the only document that governs this folder, and it is an implementation-layer document at Status Draft; `docs/` does not mention `lib/` at all. Three findings, measured on 2026-10-01:
- **"The module holds no Go and claims no Go" against 209 of its 233 `.kh` files carrying a Go clue block.** `lib.md:27` says it. The blocks are the port's archive and are committed deliberately (see [go-clue-residue.handoff.md](khayyam/rules/go-clue-residue/go-clue-residue.handoff.md)), so the sentence is now a claim about intent that the tree contradicts on its face. Either the sentence is reworded to name the archive, or the folder's claim is withdrawn.
- **Three second-level folders the document does not account for.** `lib.md:32` says three protocol families are held; on disk `modules/lib/` has six second-level folders — `adaptors/`, `codec/`, `identifier/`, `net/`, `parser/`, `process/` — of which `adaptors/`, `identifier/` and `parser/` appear in no table row and in no argument. Their own READMEs are absent. Which of them earns the folder is undecided.
- **`libgo` surviving in the corpus is not a defect.** The port record noted that six files still carry the old module name. Measured: 52 tracked, non-scratch `.kh` files contain the string, and in 50 of them every occurrence is inside a `/* … */` Go clue block, which is archive text. The two exceptions are a leftover port note (`modules/lib/net/http/protocol/handler.kh:58`) and a `TODO(go-migrate)` marker naming its own source path (`modules/lib/process/command/flag.kh:3`). No import resolves to `libgo` anywhere.

## Live problems the two archives jointly expose
Each of these is a fact about the current declarations, verified on 2026-10-02, not about either archive.
- **`modules/time/unix/` declares nothing at all** — zero `tp`, `cp`, or `vr` lines across `now.kh`, `atomic.kh`, `epoch.kh`, `const.kh` and `time.kh`. `modules/time/protocol/time.kh:9,15,19,22` therefore has no implementer.
- **`Datatype_LifeCycle` has no live state set.** `modules/computer/datatype/protocol/life-cycle.kh:2` is an empty abstraction; the constants live only inside the archived Go comment at `:13-35`, and 33 corpus files reference `LifeCycle_*`, `Software_PreAlpha`, or `ServiceStatePreAlpha`. `software-life_cycle.kh:4`'s `SoftwareLifeCycle ab` is a second empty abstraction, imported by nothing.
- **`Event_Methods` is declared in one place and referenced in another that has no such declaration.** Declared at `modules/gui/protocol/event.kh:40`; `modules/gui/event.kh:18,56` name `memar/process/event/protocol.Event_Methods` as the realization target, and no `process/event` protocol file declares it.
- **`TAGS` is documented and archived but declared nowhere.** `docs/protocols/process/error.md:208,210` lists it as a `Detail` member; `modules/computer/datatype/protocol/detail.kh:61` archives it; no `.kh` file declares it. The corpus's `Details` at `detail.kh:19-41` carries the other five and not this one, so the document's list of six matches neither archive.
- **The HTTP status vocabulary has no live home.** Both archives carry it; `modules/lib/net/http/const.kh` holds zero live declarations, `protocol/version.kh` is one line, and `protocol/status.observers.kh:6,9` demands `GetStatusCode` and `GetReasonPhrase` with nothing to answer them.
- **`Error-ID` is a named contract with no header key.** `docs/protocols/net/sRPC.md:138` makes it a consumed HTTP adapter; every `Key_*` in both archives is comment-only.
- **All nine `modules/math/per/` types are bare `tp X ab`.** Both archives hang their behaviour off a `Calculate` receiver and a symbol method (`%`, `‱`) that no live declaration has; the sign survives only in a comment at `cent.kh:3` and `myriad.kh:3`.
- **`maxWhen`, `verifyTimers` and `heapAry` have no live declaration** (`modules/time/timer/const.kh:12-20`) and are referenced only from archived code, so nothing is broken today and nothing carries the heap's even-arity invariant forward.

## The archived JavaScript, and what it did not carry
`memar-js` was archived on 2026-10-01 and 102 of its 113 files were transferred into 33 `.kh` files across 19 folders as `//` comment blocks. Each block names its source — 115 `// source: memar-js/<path>` lines naming 102 distinct paths, so the placement record is in the tree and needs no ledger beside it.
- **Its format is stated nowhere.** The marker reads `// TODO(js-idea): archived memar-js source, not Khayyam and not a migration`, and a variant reads `archived memar-js JavaScript`; beneath it, `// Unverified idea from the retired memar-js repository (archive commit 27e013d, last pushed 2026-01-06). Kept as a thought only: the architect has moved on since, so this may contradict the current design.` then `// source: <path>`. This is the same gap [go-clue-residue.handoff.md](khayyam/rules/go-clue-residue/go-clue-residue.handoff.md) already records for the Go block, and it is the owner's to settle for both at once: where an archived block's format is governed. The Go block's format is at least read by a rule; this one is read by nothing.
- **Two spellings of one marker.** `modules/identifier/mediatype/protocol/media-type.kh:15` says "archived memar-js JavaScript" where the other 32 say "archived memar-js source". One of the two is the form; nothing says which.
- **Eleven files were deliberately not carried.** Eight are third-party and not the architect's work: `widgets/barcode/storage/*` — `axenfox/onscan.js` and the source and bundles of `samsam2310/zbar.wasm` — plus `widgets/barcode/zbar.c` (C) and `widgets/barcode/zbar-v0.wasm` (a compiled binary). Three are the retired repository's own plumbing: `.gitignore`, `LEGAL`, `LICENSE` (Apache-2.0, while this repository carries its own). The barcode reader's *idea* is in the corpus at `modules/gui/protocol/element.kh:428-444` as archived JavaScript; its scanner implementation is nowhere, and no document records that a decision was made to leave it out.
- **The owner's condition on a replacement scanner**, recovered from the retired repository's README, which was never committed there: a replacement library must be readable, light and dependency-free, and should preferably be implemented in this project's own Khayyam so that it serves any language rather than one.
- **The rule that governed the retirement**, from the same README: a full Go, C, or Rust rewrite comes after writing something in Khayyam; whatever Khayyam lacks gets rewritten in Go; once Khayyam has everything, the Go repository is a full rewrite. The README states the shift in its own terms — `memar-go` began with transfer and simplification, dropping `R&D` functions and conditions, and `memar-c` and `memar-rust` shared that aim — and that the emphasis is now on implementation quality. It also states that `memar-js`, which could have served a faster crossing, is retired, while `memar` was implemented in `memar-khayyam` and `memar-organization`.
- **What the transfer did not reach.** The same README records that the complete rewrite of `memar-go` in Khayyam had been done, but that those writings were a smaller subgroup which did not survive into the current archive — present in `memar-go`, `memar-js` and `memar`, and absent from `memar-khayyam`. The README itself was recovered by the owner from a real address on 2026-10-01, moments before it was deleted from disk; nothing in either repository holds it.
