## Decisions
### What a site's release is designed on (Tentative, 2026-10-24; owner's working answers of 2026-10-25)
- The release is designed on the three working answers below, site secrets outside the release, only the builder's key installed, and custody in an offline token with a recovery key, and on the decision on rotation and revocation. Each is replaced if the deeper task 20261025-T140521Z-16944 changes it.
- Reason: the release task can be planned without waiting, and each answer is the option that keeps every release vouched for by one party.

### A site's secrets are key material the site owns, generated on the site and kept outside the release (Tentative, owner's working answer, 2026-10-25; deeper task 20261025-T140521Z-16944)
- Decided: secrets are not configuration but key material the site owns: the private key of its TLS certificate, the credentials between its own processes, the key that signs its sessions and the keys of its people are generated on the site when it is commissioned, kept in the site's own secret store outside the release, rotated by a recorded procedure, and named by the release only by the name under which it asks for each. Cost: one class of input outside the artifact, which [immutable_infrastructure.md](immutable_infrastructure.md) must then state as the single exception.
- Reasons: [A change carried to a site with no network](immutable_infrastructure.md#a-change-carried-to-a-site-with-no-network) puts a site's configuration inside the signed release, but a release is built and signed by its builder, so a secret inside it is known to the builder and travels on every carried medium, and a secret in the repository is worse.
- Rejected: sealing secrets in the release, encrypted to a key the site generated, which has the builder handle every secret's plaintext when it seals it; administrators entering secrets on the server as files, a configuration change outside any artifact, which the principle refuses.
- Standing: the owner accepted the recommended option on 2026-10-25 as a working answer, to be studied in depth in task 20261025-T140521Z-16944, which may change it. It is an exception to a premise, The Principle's "any change to configuration is a change to the artifact itself", and stays visibly a working answer until that task settles it. It replaces the open entry "Are a site's secrets configuration that must be in the release, or key material kept outside it?".

### Only the builder signs a release a site installs; the site's owner verifies its own builds and does not install them (Tentative, owner's working answer, 2026-10-25; deeper task 20261025-T140521Z-16944)
- Decided: only the builder's key is installed; the site's owner can rebuild from delivered source and compare its build with the builder's release digest by digest, which proves the source is the release's, and installing its own builds stays outside this design unless the licence grants a key. Cost: "no lock-in" is given as verifiable builds, not as independent releases.
- Reasons: [A change carried to a site with no network](immutable_infrastructure.md#a-change-carried-to-a-site-with-no-network), bullet "The site verifies before it loads", refuses a release whose signature does not verify against a key installed at commissioning, so a release the site's owner builds installs only if the site also trusts a key the owner holds, and the release design signs every release with the builder's key.
- Rejected: the site also trusting a key the site's owner generates at commissioning, so that the builder stops vouching for every release the site runs and support and warranty must say which releases they cover; installing the site owner's key only when a licence condition releases it, as an escrow release, a key ceremony kept for an event that may never come.
- Standing: the owner accepted the recommended option on 2026-10-25 as a working answer, to be studied in depth in task 20261025-T140521Z-16944, which may change it; it is tied to the licence task 20261024-T074259Z-16944, which decides with it. It replaces the open entry "Who may sign a release that a site installs: only its builder, or also the site's owner?".

### A release-signing key is held offline in a hardware token, with a recovery key (Tentative, owner's working answer, 2026-10-25; deeper task 20261025-T140521Z-16944)
- Decided: the signing key is held offline by the builder in a hardware token, with a second token holding a recovery key whose verification key is also installed at commissioning; loss is answered by signing with the recovery key, compromise by a release signed with the recovery key that removes the compromised verification key. Cost: two keys kept, one never used in normal work.
- Reasons: [A change carried to a site with no network](immutable_infrastructure.md#a-change-carried-to-a-site-with-no-network) names a signing key and a verification key installed at commissioning and says nothing on who holds the signing key, where, under what control, and what a site does when that key is lost (no new release can be signed) or compromised (a stranger's release would verify); a site no network reaches cannot be told of a compromise except by a person carrying the news, so a recovery path must already be installed.
- Rejected: one key, its loss answered by recommissioning every site by hand, a site visit per site at the worst time; a threshold of several holders who must sign, so that a release needs several people present.
- Standing: the owner accepted the recommended option on 2026-10-25 as a working answer, to be studied in depth in task 20261025-T140521Z-16944, which may change it. The owner holds that the key model must be made exact and independent of any adopting organization, and judges bearer-token practice such as JWT a security disaster; the deeper task tests that premise. The release task 20261024-T161049Z-20560 builds its tests of key loss and compromise on this answer. It replaces the open entry "Who holds a release-signing key, and what is done when it is lost or compromised?".

### A key change is itself a release (Tentative, 2026-10-24; task 20261024-T164111Z-16944)
- Decided: a site's trusted verification key is rotated and revoked by a release. A release signed by a key the site currently trusts adds the new verification key, and a later release removes the old one; a revocation is the same kind of release, removing the compromised key. The site's administrators record each key change as a change with its Request. Cost: a release cycle per rotation. The release task 20261024-T161049Z-20560 builds its key procedures on this.
- Reasons: [A change carried to a site with no network](immutable_infrastructure.md#a-change-carried-to-a-site-with-no-network) says that the only way a change reaches the running system is a new artifact, and that a release is verified against the keys the site trusts; a key change carried as a release is that rule applied to the keys. A separate signed key file installed outside the release was not taken: it is a second artifact kind, which [The Principle](immutable_infrastructure.md#the-principle) does not name. Never rotating a key and revoking it only by recommissioning the site was not taken: it leaves a key to live as long as the site.
- Which key signs the release that revokes a compromised key follows the custody decision above, the owner's working answer of 2026-10-25: the recovery key.
- Settled from the owning document by the agent that answered the questions of task 20261024-T074257Z-16944: it is none of the four kinds that always reach the owner, so it is recorded Tentative and the owner may revise it. It replaces the open entry "How is a site's trusted verification key rotated or revoked without a network?".

## Open Questions

### Position within the deployment and change lifecycle
The document now states Memar's deployment-domain rule (infrastructure immutability; no runtime logic addition), but its position within the broader change lifecycle — release, versioning, environment promotion, rollback — has not been discussed. The base-layer concept document founding that direction now exists: [Software](../../../process/software/software.md) records the settled definition (the objective manifestation of a system of aggregated processes; not limited to the computer world) and carries the lifecycle positioning as open work. Configuration-management practice (configuration identification, baselines, change control, status accounting, audit) is the comparative prior art to examine. Separately, the term "ecosystem" — used loosely across documents for technology and AI environments — has no Memar definition; a terminology decision is owed before it carries weight here.

### Does immutable infrastructure eliminate the need for Profile-Guided Optimization in the Khayyam compiler?
- State: settled in direction, not in inventory. [The Principle](immutable_infrastructure.md#the-principle) states that Khayyam's compiler and runtime are expected "to benefit directly — for example, by reducing or eliminating the need for runtime profile-guided optimization wherever configuration-driven behavior can instead be resolved at compile time". So the whole-elimination reading is refused and the subset reading is taken, and the criterion is named: behavior resolvable at compile time because the configuration it depends on is fixed by the redeploy rule loses its runtime-data dependence and with it the reason for PGO; per-request and per-connection behavior does not, because a redeploy does not fix it. Residue: the passage is illustrative ("for example") and names no inventory, so which currently PGO-addressed cases fall in which class is unstated — that is the whole of the decision the entry was holding.
- Next: enumerate the PGO-addressed cases against the compile-time-resolvable criterion during the dedicated chat; nothing about the direction or the criterion is left to decide.
