# Immutable Infrastructure

## Abstract
Immutable infrastructure is Memar's deployment-domain position: the infrastructure a system runs on — hosts, runtime environments, configuration delivery, and the build/deploy pipeline — is part of what delivers the system's definition to execution, and like that definition it is not a site of runtime change. Any change to configuration is a change to the artifact itself, requiring a rebuild/redeploy, rather than a runtime-interpreted change to an already-running instance. A closely related governance rule holds that every capability a running Memar application can reach is present in the artifact it was built from, so that every capability increase must go through recompilation, addressed once as "what code may enter the repository" rather than duplicated across source review and a separate runtime-loading mechanism. Both rules are the deployment face of the base layer's [Structure Is Fixed by Definition](../../../../docs/type.md#structure-is-fixed-by-definition) principle, stated here — where deployment governance belongs — so that any language or stack realizes them identically. The document also records what rebuild speed alone does not settle — an emergency-halt design thread and a connection-continuity thread — and its relationship of convergence without interdependence to [Type](../../../../docs/type.md)-level identity.

## Explanation

### The Principle
Memar treats deployed infrastructure as immutable: any change to configuration is a change to the artifact itself, requiring a rebuild/redeploy, rather than a runtime-interpreted change to an already-running instance. The scope is deliberately deployment-specific. Infrastructure names the base a system runs on — the platform layer whose capacity a deployed system's operations ride on — and the rule governs that base and the configuration reaching it; it does not answer the general question of when a system's [Structure](../../../../docs/system.md#structure) may come into being, which the base layer owns ([Type → Structure Is Fixed by Definition](../../../../docs/type.md#structure-is-fixed-by-definition)). Khayyam's compiler and runtime are expected to benefit directly — for example, by reducing or eliminating the need for runtime profile-guided optimization wherever configuration-driven behavior can instead be resolved at compile time.

A closely related principle, raised in discussion and worth recording alongside immutable infrastructure itself: every capability a running Memar application can reach is present in the artifact it was built from — a runtime signal selects among capabilities so compiled and introduces none, and a capability increase goes through recompilation. The check is per capability: name the capability and the artifact that carries it, and a capability with no such artifact is what this principle refuses; source review is where it is caught, one control point rather than a second one in a runtime-loading mechanism. A narrow, explicitly pre-compiled emergency shutoff — disabling an already-known feature rather than adding logic — is compatible with this principle rather than an exception to it, because its halt path and its run path are both in the built artifact and the signal that chooses between them is not code ([Emergency halt](#emergency-halt-god-halt-service)); what that service still needs is recorded under [Open Design Threads](#open-design-threads).

This document lives in [`modules/`](../../../README.md) rather than among the concept documents at `docs/` root: it does not define the general concept of immutable infrastructure — its full scope within the deployment domain remains an open question in the paired [handoff](immutable_infrastructure.handoff.md) — it states Memar's own rule set governing the change processes of deployed systems, realizable in any language or stack, which is the question shape of the modules (see their [membership criterion](../../../README.md#membership-criterion)).

### A change carried to a site with no network
The rule holds unchanged where a system runs on a site with no network to its builder, as an isolated industrial site is: the only way a change reaches the running system is a new artifact, and there the artifact is carried in (Tentative, 2026-10-24, from the delivery design of a Memar-built system on an isolated industrial site).

- **The artifact is one release, whole.** Everything the system runs from is in it: every image, every pinned dependency, the scripts that convert the stored shapes of the version it replaces, and the site's configuration. A manifest names each file with its digest and the version the release replaces, and a party the site trusts signs the manifest. Nothing is fetched while it is installed.
- **The site verifies before it loads.** The release is checked against the verification keys installed on the site when it was commissioned, one for each party the site trusts to sign; a release whose signature or any digest does not hold is refused whole, and nothing of it runs. Two cases follow, and which a site has is chosen at its commissioning, not by this rule. Where only the builder's key is installed, only the builder's releases install, and a release the site's owner builds itself from delivered source can be compared with the builder's, digest by digest, but not installed. Where the site's owner also holds a signing key whose verification key is installed, its own releases install too, and the builder no longer vouches for every release the site runs. Who may sign for a site, and how a signing key is held, rotated and revoked on a site no network reaches, are open ([handoff](immutable_infrastructure.handoff.md#open-questions)).
- **Configuration is part of the release.** Changing a parameter of the site is building a release of a new version, not editing a file on the running server. Whether a site's secrets are such configuration is open ([handoff](immutable_infrastructure.handoff.md#decisions)).
- **An old shape is converted, not kept readable.** A release that changes how something is stored carries the script that converts the old shape to the new one, and the system reads only the new ([Software → No Hidden Inputs](../../../process/software/software.md#no-hidden-inputs)). A release that skips versions carries every conversion between them, in order. A past Request is written once, never edited, and signed over its data, so converting the shapes inside it would break its signature; how a conversion treats the payloads of past Requests is open ([Request Handoff](../../request/request.handoff.md#decisions)).
- **Going back is redeploying the release before.** The previous release stays on the site. Since a conversion changes stored data, an update first stops every service that writes, then takes a backup, and only then runs its first conversion, so the backup holds every record committed before the update and nothing is written between the two. Going back after a conversion is a restore of that backup and the previous release together.
- **A restore loses what was written after the update.** Every record committed under the new release, a permit or an approval among them, is absent from the backup, so a restore made days after an update loses days of records. Going back is therefore lossless only until the new release takes its first write. After that, going back needs those records carried back: the Requests committed since the update name every one of them ([Request → The Request node](../../request/request.md#the-request-node)), and applying them again under the previous release needs a conversion of their shapes back to the previous one. A release that carries no such reverse conversion can be left, once it has taken writes, only by a new release that fixes it forward.
- **Data edited at runtime selects; it does not add.** A rule, a workflow or an approval matrix that people edit from a console while the system runs is data that selects among the capabilities the artifact carries. The console therefore accepts no code and no expression that names an operation the artifact lacks; an operation a rule needs that the artifact lacks is a new release. This is the governance rule above, applied to rules kept as data.

### Open Design Threads
Sub-minute unikernel image rebuild+redeploy was proposed as sufficient to remove the practical need for Erlang/BEAM-style hot code swapping. The two threads below record what that speed alone does not settle; they are preserved from a context note so the reasoning survives until the dedicated chat. Nothing here is designed or decided yet.

#### Emergency halt ("God-halt") service
For reaction times faster than even a sub-minute redeploy (down to network-speed reaction), a dedicated, pre-compiled monitoring service that can halt all processes system-wide until re-authorized was proposed. This is **not** an exception to this document's governance rule — it selects between pre-compiled run/halt paths based on a runtime signal; it does not inject new code. Needs dedicated design for:

- Where this service lives in the graph model (Code vs. Rule distinction — is the halt condition itself a Rule node, evaluated dynamically, while the halt/run branches are fixed Code?).
- Single-point-of-failure and security-surface concerns: whoever controls this service can paralyze the whole system.
- Distributed-system propagation: whether "halt" is scoped per-instance/per-node or must reach an entire multi-node/multi-datacenter deployment, and what consistency guarantee (if any) applies to signal propagation — a distributed-coordination problem independent of how fast the halt logic itself executes locally.

#### Connection continuity across a sub-minute redeploy
Per the existing sRPC Connection/Session model, a Connection is a persistent identity between two `ApplicationInstanceID`s that must NOT be resumed if `ApplicationInstanceID` changes. Open question: does a sub-minute unikernel rebuild+redeploy preserve the same `ApplicationInstanceID` (allowing in-flight Connections to survive), or does every redeploy constitute a new instance identity (meaning long-lived Connections/streams are necessarily dropped on every redeploy-driven update)? If the latter, sub-minute rebuild speed alone does not replicate what Erlang's hot code swapping was originally built to guarantee (call/session continuity in telecom systems) — a distinct concern from *how fast* the swap happens. Needs a decision on whether a graceful-draining/handoff mechanism is required as a companion piece to this document's principles, and if so, where it's modeled (deployment layer vs. framework layer).

### Relationship to Type-Level Identity
Two framework principles converge here and must not be conflated: this document's governance rule — every capability a running Memar application can reach is present in the artifact it was built from — and the [Type](../../../../docs/type.md) identity principle — a static concept MUST be carried as its own named entity, never demoted to runtime data ([Type → Stateless Types](../../../../docs/type.md#stateless-types)). The base layer now also states this document's own structural ground — [Structure Is Fixed by Definition](../../../../docs/type.md#structure-is-fixed-by-definition) — so the principles form a family: type-level structure fixity, its behavior corollary (Explicit Behavior Ownership), and this document's deployment face. They are **compatible** and share an architectural inclination toward compile-time fixedness, but they are **logically independent**: they are *convergent* (both push toward compile-time fixedness) yet not *interdependent* — neither logically requires the other.

Each can hold without the other. A closed, compile-time-fixed set of immutable sentinel values with numeric IDs satisfies this document completely while still carrying identity as data — compatible with immutable infrastructure, yet in violation of type-level identity. Conversely, a hypothetical runtime type registry could register new concept Types without full recompilation — satisfying identity-in-type while violating this document's governance rule. Whether such a registry is desirable, architecturally sound, or within either document's scope remains an open question; like configuration-driven behavior generally, it is an optional feature whose presence must be deliberately designed and justified, never an implicit backdoor around the default governance model.

What type-level identity adds beyond this document alone is compile-time-*typed* identity: concepts are not merely fixed at compile time — the type system itself carries and verifies their identity, a stronger guarantee than compile-time-fixed data.
