# Revision
## Abstract
A **Revision** is the application of a reviewable plan to sources: enumerate what the sources hold, turn the affected ranges into a plan a reader can review, write only under an explicit request, refuse a write that would newly break a file, and report everything found and left. This document states that contract once, so every language toolchain realizes the same engine instead of each module re-inventing it. It does not state how sources are enumerated for any one language, what a plan looks like on screen, or which exit codes a command returns; those are per-target decisions. It owns neither the identity of what is rewritten nor the truth of what the rewrite means: the first belongs to the Content model, the second to the language analyzer, and the refusal gate is where the two meet.

## Introduction
### Motivation
Three failures recur wherever a machine rewrites sources without a stated contract. The first is **the silent rewrite**: ranges change with no artifact a reader could have reviewed beforehand, so the run's judgment is unreviewable by anyone but its author. The second is **the write that breaks what it touched**: a file the run itself made newly ill-formed is left behind, and the damage is discovered later without evidence it was ever sound. The third is **the unreported leftover**: places the run saw and skipped, or could not read, vanish from the record, so the next run starts from no stated account of what remains. Each is a failure of the enactment's standing rather than of its content, and each is answered by stating the contract before the mechanism.

### Methodology
This document lifts only what is portable from the one mechanism examined in full: the declaration-rename engine, whose claims were classified as language-level, per-target, or neither in its managing record. Source shape, unit naming, residue modes, and second-language machinery stay per-target and do not travel here; what travels is the engine shape — enumerate, plan, explicit write, refuse-on-newly-broken, report — because none of those steps asks what a token is. Where the sources for these claims come from is recorded in the paired changelog; open limits live in the paired handoff.

## Explanation
### What a Revision Is
A **Revision** is **the enacted form of a reviewable decision about ranges in the sources, kept to the contract below.** Five commitments are inseparably in that definition. First, the engine **enumerates the sources** it will consider, and the sources are stated before the run rather than discovered mid-run. Second, it **turns affected ranges into a plan** a reader can review before anything is written; a plan no second participant could read is not a plan. Third, it **writes only under an explicit request**; a dry run is the default posture and a write is an opted act, never the absence of a flag. Fourth, it **refuses a write that would newly break a file**, judged by the language analyzer against the file as the run found it — nothing is written anywhere when one file would newly fail. Fifth, it **reports everything found and left**: what changed, what was seen and skipped, and what could not be read, each named. A run that satisfies all five is a Revision; a run missing any of them is something else with a shared name.

### The Twin Split
A Revision rewrites text, but the text is not what decides whether the rewrite is right. Two authorities meet at the refusal gate, and each owns a different half. **Identity, addressing, and versioning of the rewritten text belong to the Content model**: an occurrence is an addressable fragment carrying relations, independent of the path that locates it — identity independent of location is the Memar statement of the first half ([Knowledge → Identity Must Be Independent of Location](../../knowledge/knowledge.md#identity-must-be-independent-of-location)); [Content → Addressability](../../knowledge/content/content.md#addressability) of the second. **Binding truth belongs to the language analyzer**: whether a name at a place binds a declaration is settled by the reader and the scope rules, never by the spelling alone. The gate — refuse what would newly break — is where the two halves touch without merging: Content says what moved, the analyzer says whether the move holds. A Revision that contradicts the analyzer revises a different process than the one it claims; an implementation that satisfies the plan while breaking the file has satisfied the wrong thing. The same division already runs through the neighboring protocols: the [Lexer](../lexer/lexer.md#what-a-lexer-is) applies a lexical model to a source it references without owning, and the [Compiler](../compiler/compiler.md#what-a-compiler-is) accepts or refuses a source while emitting the events analysis subscribes to.

### Relation to Lexer, Compiler, and Linter
No claim here duplicates a neighboring protocol, and each neighbor is named once so the boundary is checkable. The Lexer owns **what is recognizable in a source and how** — tokens, prose, and the boundary between them — and this document consumes that ownership without restating it. The Compiler owns **acceptance**: whether a source is a well-formed program, and the events analysis tools subscribe to. The Linter owns **rule diagnostics over an accepted program**: where configured rules are violated, reported as errors, warnings, or suggestions. This document owns **enactment**: what happens after a decision about ranges exists. A Revision never lexes, never accepts, and never judges style; it moves text under a plan and refuses to move it when the analyzer newly objects. Where a Revision appears to need a token judgment — whole identifiers, comment extents, string boundaries — that need is a call on the Lexer, not a clause of this contract.

### What Narrowed Elsewhere
Stating this contract narrows two neighbors without changing their documents. The rename `Binding` keeps the binding-resolution contract — declaration identity, occurrence addressing, cross-unit edges — binding every language's toolchain: Khayyam's `core/` is its first realization, not its boundary. Source naming, plan shape, write gating, report shape, and exit codes move here; residue modes, second-language members, and prose classes stay per-target facts of the Go port and never enter a shared interface. The narrowing is by examined-versus-unexamined, never by language name: one requirement in one correct shape, not the same engine re-invented per module. Nothing in those documents is edited by this section; the narrowing is recorded where each narrowed claim lives.

### What This Document Does Not Define
This document states no structural rule: where a Revision mechanism lives, what its artifacts are named, and how a runner finds them are Rules carried beside their protocol, never clauses of it. It does not define per-target source shapes, plan renderings, or exit-code taxonomies. It makes no claim that would hold for a language this repository does not have; portability is bounded by examined mechanisms, and the bound is kept open in the paired handoff rather than argued here.
