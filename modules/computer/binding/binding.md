# Binding Model

## Abstract
On that test an **atomic** release of the ring's head or tail is expressible today as a declared method and as nothing else, because the language embeds no concurrency model and the memory protocol puts data races among relaxable governance; and **resizing** is expressible only as a declared capability whose length is a value from outside the language, which puts it in direct conflict with the same design's central property — the owner's own two sentences, that the driver is handed the capsule's address and that the buffer may be grown or shrunk, cannot both hold. Both findings rest on the documents and on the owner's account; neither was corroborated from the `.kh` sources, and an earlier form of this abstract cited the sources for both, which is withdrawn. It carries twenty-five open questions, each labelled language, protocol, toolchain, or naming, with what it blocks and what would close it, and it now carries the owner's own placement of that atomicity: **a method of the buffer module** obtains the indivisibility — and, this model now records, the order as well — from the synchronisation module modelled at [Synchronization Model](../../process/sync/sync.md), because a release that is indivisible but unordered does not free a region the other party may safely refill.

## Introduction

### Motivation
The owner's decision widens the subject this document models and changes its name. The previous shape was about a program reaching a facility its host provides, in a folder named for that; the decision is that the concern is wider than a host interface, and that `ffi` is limiting in its essence because it refers only to a function. The owner's own words set the three requirements:

> What is inside it and who uses it can be a module, probably at the compiler level (if we cannot conceive of another consumer for it), that allows binding operations from Khayyam to other languages — such as calling various web APIs, or functions of other languages like C.

> So in my view, for **each language** we should say separately what the abstraction must be and what the developer declares to make this need possible.

> the possibility of introducing a shared buffer capsule between, say, a network driver and an app that directly puts received packets into that buffer, where no code introduces it to it other than saying that this buffer is, for example, a ring with protocol abcde, on which both agree.

And a fifth fact, which is a design rather than a decision, and is the sharpest instance this concept has been given:

> It depends on the viewpoint. If both sides want to work as exactly the same code that a unikernel or exokernel describes — not merely at the level of abstraction, which in my view must also be identical at the level of implementation. That is, in the driver–app example: **both must have the same module**; on the app side that module is initialised and **the memory address of that capsule is given to the driver**, which hands it to the same module; and then on every call, that module writes the corresponding data into the corresponding buffer. That way the data goes straight from the hardware to the app's memory without having to go through the OS's memory and then be transferred. The OS's only duty is supervision — for instance correctly introducing a driver as an app to the others — so that an app does not appoint itself as an app of others' choosing and does not take control of the hardware.

And a sixth fact, which changes what the model is *for* rather than what it covers, and is the hardest thing this concept has been asked to hold:

> Both parties must agree on an **execution method**, because without an agreement concurrency cannot be implemented — both sides must know what the other side does. For example, when a packet has been read and processed, the app side must **atomically** change that buffer's head or tail so that the portion of the buffer is freed for the driver to give it a new packet. And it must also be agreed that the buffer will be grown or shrunk when necessary.
>
> So the idea of the same library is **not that the code is literally the same, but that the behaviour is the same.** This sameness of behaviour can come with small changes, but not as **breaking changes.**

A seventh fact removes a shape rather than adding one, and it governs where the guarantee in the fifth fact may be sought:

> Each module should do one thing and do it properly; that way modules really become simple. We no longer need a big umbrella concept like `os` where everything is dumped in without care and we call it a monolithic OS kernel with pride and say we have the best operating system in the world.

Three instances follow, and the model must carry all three: a foreign function in `C`; a Web API, which is an agreement about data and behaviour reached over a network; and a shared ring buffer a network driver writes received packets into while the application reads them, with no code introducing the buffer to either side. The third is the sharp one, because it needs a *place*, the language has no primitive types, no literal, and no construction form, and it needs more than a place: the two parties write into and read from the same region at the same time, so the agreement must carry a method as well as a subject. The owner's design above says how that instance actually works, which is worked out under [The sharpest instance](#the-sharpest-instance-one-module-on-both-sides) and which revises five things this document previously recorded: the crossing is not the one instance nothing crosses, the binding's two halves are one artifact rather than two statements, the place is holdable without being nameable, what the two parties agree about is a behaviour rather than a signature, and the party that guarantees a driver is introduced correctly is not an operating system.

A fourth fact is a decision, not a gap, and it changes what the model may claim. The language is **silent** about how a foreign function is reached: an earlier drafted intervention that would have put a sentence about a provision's name into `docs/khayyam/` was **withdrawn rather than deferred** ([Language Gaps → I-B](../../../bundles/khayyam/targets/js/language-gaps.md#i-b--whose-name-a-body-less-method-carries--withdrawn-by-the-owners-ruling), the ruling at `:76-77`), on the ground that "how a foreign function is reached depends on each organization's own modules". The consequence is precise and it is this model's: the separation of the two vocabularies is no longer carried by a sentence any rule may cite, and is carried instead by two keyspaces the run request already keeps apart. What is left for a rule is only the second half — that the correspondence be recorded as a declaration and not left as a coincidence of spelling.

### Methodology
The model was derived by the procedure in [Modeling Practice → Challenging a Proposed Concept](../../../docs/modeling.practice.md#challenging-a-proposed-concept): the candidates were taken from the owner's widened decision, from the language's own decomposition of the sentence that names the provision form, and from the sources' existing uses of that form, and each was then run against the challenge questions. Node-or-edge standing was decided by the audit in the same practice, and every surviving candidate was searched against the whole `.kh` sources for a declaration that already does its job under another name.

Three standing rules shape what follows. **A claim is recorded only where a document or a declaration states it**, with the section it comes from and, for a declaration in this repository's sources, the file and the line; where a `.kh` file is the only witness it is named as such and marked as a fact about the repository rather than about the language; where nothing answers, the silence is reported as the gap rather than smoothed. **Nothing here designs an implementation.** Where this document names a declaration it says what it must mean, never how it is written. **A concept is not narrowed to fit what the language admits today.** Where an instance is inexpressible, the model says so and says what it would cost — the previous shape of this model kept the third instance out because the language has no primitive types, and keeping it out is exactly the narrowing the owner's decision forbids.

Three measurements over this repository's `.kh` files are carried in the paired [handoff](./binding.handoff.md), all reproducible and none from a sample: **30** `.locale.<lang>.kh` companions beside **100** `.observers.kh` and **9** `.mutators.kh`; **63** retained Go generic `type X[…]` declarations, of which **8** state a union constraint; and the counts of body-less method declarations by their owner's kind. **None of them is the ground of a claim in this document.** The code under `modules/**` is the residue of an attempt to develop these ideas in another language that did not succeed, and the owner has ruled it neither evidence nor a premise: a conclusion that rested on what a declaration happens to say has been re-grounded on the documents or withdrawn, and what remains is a description of the repository's state and nothing more. That the counts may be described is not the same as their being used; the earlier form of this paragraph introduced them as "the measurements behind this revision", which made them that, and that wording is withdrawn.

The measurements behind this revision, all reproducible and none from a sample: the companion-file convention — **30** `.locale.<lang>.kh` files (23 `.locale.eng.kh`, 5 `.locale.per.kh`, 1 `.locale.en.kh`, 1 `.locale.fa.kh`) beside **100** `.observers.kh` and **9** `.mutators.kh`, over 1,281 `.kh` files; the Go generics the sources retain inside their clue blocks — **63** `type X[…]` declarations across **54** files, of which **44** declare a generic interface across **35** files, and **8** declare a union constraint, the one notion being `modules/math/integer/protocol/integer.kh:10` writes `Signed | Unsigned` and `modules/math/protocol/ordered.kh:10` writes `Integer | Float | ~string`; and the body-less declarations, whose count is carried from [language-gaps.md:19](../../../bundles/khayyam/targets/js/language-gaps.md) and `:33` rather than re-measured here — **728** body-less declarations, **669** on an `ab`, **59** on a `cp` declared in the same file, and **none** on an `mt`. The method for each is stated in the paired [handoff](./binding.handoff.md).

## Explanation

### What a binding is
A **binding** is an agreement two parties hold about something, with no third party introducing it. Each party states its half; the agreement holds because both stated it; nothing else has to say so.

That is the whole definition, and each clause of it does work this model depends on. "**Two parties**" is what makes the concept host-independent: the parties are named by the role they take in the agreement, not by what they are, so a program and a runtime, a driver and an application, and two languages' libraries are all the same shape. "**About something**" is what makes it wider than a call: what the parties agree about may be a route to a capability, a shape of data and behaviour, or a place in memory, and none of the three is a specialization of the other two. "**No third party introducing it**" is the clause that is easiest to lose and the hardest to keep, because the ecosystems this vocabulary comes from all have one: a service loader, a dynamic linker, a manifest, a registry, a container runtime. Under this definition there is none — which is a claim to be checked against [Foreign function interface](https://en.wikipedia.org/wiki/Foreign_function_interface) rather than asserted, and [Where the reference covers this and where it does not](#where-the-reference-covers-this-and-where-it-does-not) records what that check found.

A binding is also not a mechanism. It is a statement; what discharges it is someone else's business — a body-less method's implementation arriving at a supply table, a socket library's code running in another address space, a driver writing into a region both sides name. This model's subject is the statement and the agreement it is part of, which is why the run request's key and the side file's name appear in it at all and no implementation code appears in it anywhere.

**What the two parties agree about is a behaviour, and never a code.** That is the clause the owner's sixth fact adds, and it changes the model rather than completing it, because a binding stated as an agreement about a *signature* is answered by an interface and an agreement about a *behaviour* is not: two independent parties may reach the same behaviour by entirely different means, and the agreement is what holds while they do. The owner's sentence is explicit that "the idea of the same library is not that the code is literally the same, but that the behaviour is the same … This sameness of behaviour can come with small changes, but not as breaking changes." Two consequences run through the rest of this document. **A crossing of kind *route* inherits its method** — the far side's own signature says what a call to it does — **while a crossing of kind *place* inherits nothing**, because a region has no signature, so the method is part of what must be agreed and not a detail either party may choose. And **the subject of the agreement widens by one clause**: a place crossing is no longer only *which* region is shared but *what each party may assume the other does to it*, which is what the owner's atomic head-or-tail requirement and the resizing requirement are instances of.

**What makes this a binding rather than a contract one side imposes.** Three things, and each of them is a negative. **Neither party authored it alone** — a contract may be one organization's document that another party accepts or refuses, and this agreement holds because both parties state it ([Binding](#binding)). **No third party enforces it** — there is no principal, no arbiter, and nobody to escalate to, which is the sharpest difference from the repository's own nearest concept, below. **Neither party can be compelled to it** — a party that declines to state its half has not broken anything, and the crossing simply does not exist for it. An agreement one side imposes and the other may only accept or refuse is a contract this model does not claim; what makes this one different is that there is no authority in the picture to impose it.

**The repository already has a concept for an agreement between parties, and it is not this one.** [Agency → Contracts](../../../docs/agency.md#contracts) defines a **Contract** as "a structure establishing expectations between participants, which may define responsibility, authority, obligations, constraints, expected outcomes, acceptance criteria, failure conditions, and escalation procedures; not necessarily a legal document" ([:1006](../../../docs/agency.md#contracts), glossary at [:2007](../../../docs/agency.md#contract)) — which is the same subject this model needs, and the binding is a narrower kind of it. Three distinctions, each on the evidence: **a Contract has an escalation procedure and this model has no third party to escalate to**, so a Contract's terms are enforced from above while a binding's can only be *checked*; **a Contract sits inside an agentive relationship with a Principal** ([Agency → Trust](../../../docs/agency.md#trust) is a Principal's assessment of an Agent, and [Verification and Validation](../../../docs/agency.md#verification-and-validation) is how a Principal discharges it), while two independent parties hold this agreement between themselves with nobody above either of them; and **a Contract may define obligations, which are duties one party may fail**, while a binding's own test — below — admits no term one party cannot verify alone. The repository has already drawn the neighbouring line from the other side, twice and in the same words: [Protocol → Protocol vs Contract](../../../docs/protocol.md#protocol-vs-contract) says a Protocol "does not inherently require predefined parties … no negotiation needed", and [Abstraction in Khayyam → What Is an Abstraction in Khayyam?](../../../docs/khayyam/abstraction.md#what-is-an-abstraction-in-khayyam) at `:45` says an abstraction "is not a contract: it names required behavior, not parties, obligations, or commitments". So the two nearest concepts are each explicitly *not* bilateral, and the gap they leave is exactly what this model fills: a bilateral agreement with no principal and no escalation.

**The test a term of a binding must pass.** Since neither party can be compelled and no third party enforces anything, a term is worth stating only if one party can check it without the other's cooperation; anything else is a hope, and a hope between two parties that cannot be coordinated is not a rule. This test is what decides every requirement below. *The two sides hold the same artifact* passes it — a link or build step reads which artifact each side received, with no question to the other party ([What the language must say first](#what-the-language-must-say-first-what-the-toolchain-must-check)). *The head is advanced atomically* does not pass it, because atomicity is a property of a realization rather than of anything the other party declares, and it is therefore carried as a **provision** whose arrival is the evidence ([The execution method](#the-execution-method-an-atomic-head-or-tail)). *The buffer may be resized* passes it only as a declared capability — whether a party *may* resize is stated; what a resize does to the address the other side holds is not, and that is where the design's central property is at risk ([Resizing](#resizing-what-the-agreement-must-carry-about-the-places-size)).

### The three instances, and what each costs the language
A model that only names the first instance has narrowed the concept, so this section names all three and states for each what the language must already admit and what it does not.

**A foreign function — a route to a facility in another language.** This is the instance the language has a form for. [Khayyam → Method](../../../docs/khayyam/khayyam.md#method) at `:91` and [Method in Khayyam → Body-less Methods](../../../docs/khayyam/method.md#body-less-methods-ffi-and-contracts) at `:80` both say that when the receiver is a concrete capsule, "a body-less method signals to the compiler that the implementation will be provided externally during the linking phase". **What it costs the language: nothing further**, because the form exists and is stated. **What it costs the model: the shape the owner's design uses has no case.** The method that reaches a facility is a method, and it is that method's companion unit that holds the provision, so the design is built on a body-less method whose owner is a *method* — which the language admits as an owner ([Khayyam → Method](../../../docs/khayyam/khayyam.md#method); [Method in Khayyam → A method implements an abstraction by methods of its own](../../../docs/khayyam/method.md#a-method-implements-an-abstraction-by-methods-of-its-own) at `:74`) and which no sentence says is a provision or a contract. An earlier form of this entry also reported that the sources hold the form fifty-nine times on a concrete capsule and that none of the fifty-nine was written as one, and read the fifty-one arithmetic and text conversions among them as provisions nobody meant. Both figures remain true of the repository and are carried as such; neither is used here, because what a ported declaration was *meant* to be is not something its text can establish, and because the code under `modules/**` is residue of an attempt to develop these ideas in another language that did not succeed — which the owner has ruled neither evidence nor a premise. The gap is the language's silence about the method owner, and the silence is the whole of it.

**A Web API — an agreement about data and behaviour reached over a network.** The parties are a program and a service; the crossing is a shape rather than a route; the other party's name is a URL, a method verb, and a media type, none of which is a name in the language. **What it costs the language, on the evidence of this repository's own documents, is a text type that a program may write.** There are no primitive types ([Khayyam → Type Principles Realized](../../../docs/khayyam/khayyam.md#type-principles-realized)) and no literal — "a bare numeric literal `41` may not appear as a value without a named capsule" ([Khayyam → Separation of Syntax and Governance](../../../docs/khayyam/khayyam.md#separation-of-syntax-and-governance-a-principle) at `:162`) — and a `vr` "cannot carry an initializer inline" ([Variable in Khayyam → Variable Declaration Syntax](../../../docs/khayyam/variable.md#variable-declaration-syntax)), so the URL and the payload shape cannot be written in a Khayyam source even as data. A library can own them: [`modules/computer/buffer/string.kh`](../buffer/string.kh) and the error family's locale companions are the sources' own way of stating text this repository owns. **What it costs the model: a second crossing kind, and the refusal to treat "a binding" as "a call".** A program holding a Web API's shape is holding data, not a route, and nothing in the language says how data crosses a binding — [Method in Khayyam → Key Rules](../../../docs/khayyam/method.md#key-rules) says every variable of a call passes strictly by reference, which governs a call and says nothing about a value obtained over a network by anything but a call.

**A shared ring buffer — a place in memory.** A network driver writes received packets directly into a region; an application reads them; **no code introduces the region to either side**; only the agreement that it is a ring of a stated protocol. **What it costs the language is a type for a place, and the language has none.** Four separate statements bear on it and none of them yields a place. There are no primitive types, so nothing has an address. There is no literal, so no offset can be written. There is no construction form, so nothing produces the region — [The JavaScript target → Running a program](../../../bundles/khayyam/targets/js/target.md#running-a-program) records that "every value a program handles was produced outside it". And [Abstraction in Khayyam → What You Cannot Do](../../../docs/khayyam/abstraction.md#what-you-cannot-do) at `:100` states that an abstraction's signature may name only abstractions, while a construction's result is a concrete instance, so **no shared contract can name the region** — the sibling [construction model](../../process/construction/construction.md#what-neither-states-and-what-a-library-is-therefore-blocked-on) states the same consequence at `:154`, and [Type → What Is Not a Type](../../../docs/type.md#what-is-not-a-type) states that "the raw socket handle is not" a Type. So the honest answer, on the documents alone, is that **a shared place has no expression in a Khayyam source at all**: not as a literal naming an offset, not as a contract two parties share, and not as a construction a program performs. The thing that *is* expressible is the agreement — two declarations, one on each side, each stating "this is a ring of protocol abcde" — and the gap is not the agreement, which is two declarations and nothing more, but the *place*. **The owner's design then works around three of the four negations without removing any of them**, by making the place's address the one thing the two sides exchange rather than something a source states; that is worked out under [The sharpest instance](#the-sharpest-instance-one-module-on-both-sides), and what it leaves inexpressible is any statement of *where* a place is. What it costs the model is the sharper claim: widening the concept to bindings, plus a host that produces values, does widen what a program may hold — but not by one word in any language document. See [What a program may express afterwards](#what-a-program-may-express-afterwards-that-it-could-not-before).

**What this instance costs the language is now two things rather than one, and the second is the harder.** The first is the type for a place, above. The second is that a place crossing is the only one of the three with no signature to inherit a method from, so the agreement must state a **behaviour** as well as a subject: what the driver may assume the application does when it has finished with a portion, and what the application may assume the driver does when it takes the next one. Concretely the owner's design requires two: that the application's release of a portion is an **atomic** change of the ring's head or tail, and that the ring's **size may change** when necessary. Neither can be written as a value, neither can be computed by a source, and — this is the finding that decides both — neither can be *checked* by the party that depends on it. What a Khayyam program can say about each is a declaration whose execution arrives from elsewhere, which is the same shape the language already uses for every foreign operation. The costs are worked out under [The execution method](#the-execution-method-an-atomic-head-or-tail) and [Resizing](#resizing-what-the-agreement-must-carry-about-the-places-size).

One fact about the sources keeps the third instance from being exotic. The language has no union type, and the sources' retained Go generics carry the notion anyway: of 63 `type X[…]` declarations across 54 files, 8 declare a union constraint — `Signed | Unsigned` at [`modules/math/integer/protocol/integer.kh:10`](../../math/integer/protocol/integer.kh), `~int | ~int8 | ~int16 | ~int32 | ~int64` at [`signed.kh:24`](../../math/integer/protocol/signed.kh), `~uint | ~uint8 | … | ~uintptr` at [`unsigned.kh:10`](../../math/integer/protocol/unsigned.kh), `~complex64 | ~complex128` at [`modules/math/protocol/complex.kh:10`](../../math/protocol/complex.kh), `~float32 | ~float64` at [`float.kh:10`](../../math/protocol/float.kh), `Integer | Float` at [`number.kh:10`](../../math/protocol/number.kh), `Integer | Float | ~string` at [`ordered.kh:10`](../../math/protocol/ordered.kh), and `Ten | Cent | Mille | … | Quadrillion` at [`modules/math/per/____per.kh:12`](../../math/per/____per.kh). "One of these kinds" is therefore not an alien idea to the sources; it is a retired one, inside archived Go rather than in Khayyam, and that is a fact about the sources' history rather than about the language.

### The sharpest instance: one module on both sides
The owner's account of the driver and the application is the sharpest thing this model is asked to hold, so it is restated in the model's own terms before its seven parts are worked out. Both sides work as the same code a unikernel or exokernel describes — identical at the level of implementation, and not merely at the level of abstraction. On the application side that module is initialised and **the memory address of that capsule is given to the driver**, which hands it to the same module; and on every call that module writes the corresponding data into the corresponding buffer, so the data goes from the hardware into the application's own memory without passing through any other party's memory and being transferred. What the two sides agree is not the text of that code but the **behaviour** it has, and the agreement must carry an **execution method** besides the place itself: that a portion is released by an atomic change of the ring's head or tail, and that the ring's size may change when necessary. What is not in the picture is an operating system holding the two sides together.

Seven things have to be worked out, and each of them is a question the rest of this document answers in a different voice than it would have answered it before this design was stated.

#### One module, both an abstraction and an implementation
The claim is that one module is at once the specification both sides rely on and the code both sides run. **Nothing in this repository's language documents contradicts that**, and the reason is worth stating because it is not the obvious one. [Abstraction in Khayyam → What You Cannot Do](../../../docs/khayyam/abstraction.md#what-you-cannot-do) at `:99` and `:142` refuse a method body inside an abstraction and refuse default implementations — and both refusals are about *an abstraction supplying behavior*. The owner's module supplies none. Its abstraction-owned declarations stay body-less and its capsule-owned declarations carry the bodies, in one unit, which is exactly what [abstraction.md:136](../../../docs/khayyam/abstraction.md#abstraction-realization-implicit-satisfaction) makes satisfaction structural, and what the sources happen to do wherever a concept and one of its instances stand in one file — [`modules/math/integer/unsigned-32.kh:8`](../../math/integer/unsigned-32.kh) declaring `tp W32 cp` and [`:24`](../../math/integer/unsigned-32.kh) declaring `tp U32 ab` in the same unit.

What the design does is put its weight on the single asymmetry that document draws between a concept and a concrete instance ([abstraction.md:107](../../../docs/khayyam/abstraction.md#a-concept-is-an-abstraction-a-concrete-instance-is-a-capsule) at `:108`–`:109`): a signature owned by an abstraction may name only abstractions, while a signature owned by a capsule may name a capsule, including itself. An abstraction-owned method therefore cannot take a place at all — not even a wrapper capsule — and this repository's one target refuses a call whose receiver is typed as an abstraction outright ([target.md:60](../../../bundles/khayyam/targets/js/target.md#the-three-kinds-of-body-less-method)). **Two separate realizations would put the driver's calls on the abstraction side of that wall; one implementation does not.** The owner's insistence that the two sides be identical at the level of implementation is therefore not a preference for tidiness — under this language it is what makes the design writable. What it does not settle is the model's largest gap: whether a body-less method whose owner is a *method* is the provision form or the contract form is untouched by this and still open, and the sources' 728 body-less declarations contain no instance of it.

Two consequences follow, and the second is a cost the model should not round away. **The abstraction in that module stops being a substitution point between the two parties.** [abstraction.md:111](../../../docs/khayyam/abstraction.md#a-concept-is-an-abstraction-a-concrete-instance-is-a-capsule) says an implementation "is free to be more precise than what it is asked for"; this design does not withdraw that freedom, it simply does not exercise it, because there is one implementation and both parties hold it. And **one declaration's names now stand in two parties' namespaces at once.** The separation this model calls structural rests on the other party's name being outside the language, and a module both sides include does put one name in both — but there it is one declaration of one thing included twice rather than two claims on one spelling, so the collision the separation exists to prevent does not arise. What it does arise for is a party's own name appearing in a `.kh` source at all, which is the naming question this model carries as its twelfth.

**Language-level or per-target.** *Language-level:* that one unit may declare an abstraction and the capsule satisfying it, and that both parties may include that one unit — no target is required for either, and a second target admitting them is the language admitting them rather than a coincidence between two tools. *Per-target, and per-organization:* that the **identical** artifact is what the two sides receive. A target could legitimately link a separate build of the module to the driver, and the design's central property — hardware writing into the application's own memory — would be lost with nothing in the language objecting. That is a link-and-build obligation, and its home is a tool that applies it, not `docs/khayyam/`.

#### The place is the address, and the address is exchanged
The sharpest honest reading of this design is that **it resolves the place problem by making the address the one thing the two sides exchange, rather than something the language can express.** Every one of the four negations this model records is still true, and none is contradicted: there are no primitive types ([khayyam.md:206](../../../docs/khayyam/khayyam.md#type-principles-realized)), no literal ([khayyam.md:162](../../../docs/khayyam/khayyam.md#separation-of-syntax-and-governance-a-principle)), no construction form ([target.md:70](../../../bundles/khayyam/targets/js/target.md#running-a-program) — every value a program handles was produced outside it), and no shared contract that may name a concrete instance ([abstraction.md:100](../../../docs/khayyam/abstraction.md#what-you-cannot-do), with the same consequence at [construction.md:154](../../process/construction/construction.md)). What changes is what they forbid. The design never asks the language to **name** a place: no type for a region, no offset as a literal, no construction form producing one. It asks for a value to be handed from one party to another, and a value the host produced is the one kind of value this language has. A call carries it because every variable of a call is handed over by reference ([method.md:39](../../../docs/khayyam/method.md#key-rules)).

So the address is a value the host produces, and what that costs is three things, stated without softening. **A wrapper capsule, not an address.** The raw address is not a Type ([type.md:78](../../../docs/type.md#what-is-not-a-type): "the raw socket handle is not"), so what crosses is an instance of a declared capsule that wraps it — the pattern the sources already use for a host-owned value ([`modules-plugable/computer/ui/gui/protocol/application.kh:8-10`](../../../modules-plugable/computer/ui/gui/protocol/application.kh)), and the only one this language has for a value it did not make. **Every operation on the place is a provisioned method.** Reading, writing, and advancing within the region are that capsule's methods, whose implementations arrive from outside ([khayyam.md:91](../../../docs/khayyam/khayyam.md#method)), so no program computes with a place, compares two of them, or writes one down; it asks the capsule. **The wrapper's declaration is one of the module's**, included by both sides for the same reason the module is, which is what keeps it a single declaration rather than two spellings. What it does **not** cost is the copy the design exists to avoid: the buffer stays where the hardware put it and only a handle moves.

That last observation is not this model's finding, and the model had not read the document that already states it. [OS → Networking: frame delivery, not communication meaning](../os/os.md#networking-frame-delivery-not-communication-meaning) says the "same exclusive grant can map the NIC's own memory into the destination application's address space, so packet data lands directly in the application's buffers from the NIC — moved by the hardware, without the kernel copying it and without the kernel observing each packet at all", that "supplying security this way costs isolation, not mediation", and that the kernel-mediated copy path is "one implementation of the guarantee, not the guarantee itself". This repository had the owner's conclusion at the guarantee layer before this model had it at the crossing layer.

What the design therefore does not need is as important as what it does: **no grammar, and no shared construction contract** — which is the wall [construction.md:154](../../process/construction/construction.md) states. There is exactly one construction here, on the application's side; the driver constructs nothing and is handed the address of what the application built. A contract over constructions was never needed, because no second party constructs.

**Language-level or per-target.** *Language-level:* that a place is not nameable, literal, or constructible; that every variable of a call is handed over by reference; and that a capsule-owned signature may name a capsule while an abstraction-owned one may not. *Per-target:* what the host's address is, how the wrapper capsule's instance is produced, and how the handover is delivered — this target realizes one cell per variable ([`run.ts:75-86`](../../../bundles/khayyam/targets/js/src/run.ts)) and lets emitted source establish a file-level variable's initial state ([variable.md](../../../docs/khayyam/variable.md#variable-scope-and-visibility)).

#### The execution method: an atomic head or tail
The owner's requirement is exact: when a packet has been read and processed, the application must **atomically** change that buffer's head or tail, so that the portion is free for the driver to fill with the next packet. Three documents bear on it and one name collides with it, and the answer to "can a program say this?" is yes as a declaration and no as a computation.

**The language says nothing about it, and has already said where such things go.** [Agency in Khayyam → Concurrency](../../../docs/khayyam/agency.md) at `:13` states that "Khayyam embeds no concurrency model into its syntax — no `go` keyword, no `async`/`await`", that whether a method blocks or runs asynchronously is "an intrinsic property of the method's own definition (tagged via an abstraction, e.g. `tp Async ab`), not a choice made by the caller", and that how such a method is carried out "belongs to the library that implements it, and how that library's work is scheduled belongs to the framework and runtime above the language". At `:39`: "The grammar states nothing about how execution is scheduled or what substrate it runs on." And at `:44` the cost is priced in this document's own terms — without a privileged concurrency keyword, "the static guarantees a language like Rust derives from concurrency being baked into its type system … must be reconstructed elsewhere — by a rule or a tool's check rather than by the grammar", which "places the same opt-in/swappable trade-off discussed in [Memory → Safety enforcement is governance](../memory/memory.md#safety-enforcement-is-governance) onto concurrency safety as well". **The word itself collides.** [Khayyam → Syntactic Atomicity and Semantic Clarity](../../../docs/khayyam/khayyam.md#syntactic-atomicity-and-semantic-clarity) at `:234`–`:235` uses *atomic* of syntax: "each syntactic construct should correspond to a single semantic intent, and each semantic intent should preferably be represented by a single syntactic construct". That is a principle about grammar, and a reader following the owner's word into the language documents will land on it. The collision is recorded here so that neither document is read as contradicting the other, and the same word names a second concept in [Synchronization Model → Sequencing](../../process/sync/sync.md#sequencing) — the order in which one party's completed writes become the other party's next premise — which the head-or-tail requirement turns out to need.

**The concurrency protocol says nothing about atomicity, and its one load-bearing rule bears on this design directly.** [Concurrency Realization](../concurrency/concurrency.md) states the substrate (`:27`–`:30`), that channels are signals and not stores (`:32`–`:39`), and that execution units are pooled rather than spawned (`:41`). The rule that matters is that "a channel carries *signals* … Data to be conveyed travels in the system's storage or explicit message structures; the channel notifies of its availability" (`:33`, `:36`), and that a channel used to hold data "is a modeling error this framework treats as a defect" (`:37`). The ring in this design is precisely what that rule forbids a channel to be: a data store with a retention requirement. Two parties sharing it are sharing storage, and telling each other that a packet is there is a separate concern this model does not conflate with the crossing. The same document records at `:18` and `:35` that the fixed-capacity ring is what a channel's buffer is — the ecosystem's answer, which the owner's resizing requirement overrides rather than follows.

**The memory protocol places atomicity in governance, not in the language.** [Memory → Safety enforcement is governance](../memory/memory.md#safety-enforcement-is-governance) at `:85`: "Memory-safety checks — use-after-free, missing teardown, and data races insofar as they are memory — are policies about how already-typed instances flow. They are enforced by the [Linter](../linter/linter.md) and by compiler analyses the organization elects to run, and they are relaxable by configuration. They are not an unbypassable property of a language the way a mandatory borrow checker is. An organization that disables the checks has not forked a language; it has chosen a different governance posture, and it owns the resulting failures." And [Memory → Copy and ownership semantics are contract members](../memory/memory.md#copy-and-ownership-semantics-are-contract-members) at `:99`–`:102` gives the ring's terms their home: "A method's contract includes the memory semantics of its inputs and outputs … 'Treat any returned buffer as valid only until the next call' is a legitimate contract term — but it must be *written*, because it is exactly the term callers otherwise assume to be the opposite", and "every buffer-reuse, pooling, or zero-copy optimization they perform must be paired with an explicit, documented contract term". The owner's design is a zero-copy optimization in that document's own vocabulary, so this is the rule that obliges it to say what it does.

**The process concept settles that the requirement is a choice, before any mechanism is named.** [Process → Concurrency](../../process/process.md#concurrency) at `:196`: concurrency "is not, by itself, evidence that mutual exclusion is required"; at `:200`: "The important question is therefore not *'where should we add a lock?'* but *'what concurrency constraints does the process actually require …'*"; and at `:232`, pinning a bounded part of a process to one fixed Worker "can resolve a concurrency hazard without a lock, precisely because it removes the possibility of two activities touching the same state through two different Workers at once". The driver and the application are two Workers over one region, so the atomic advance is one admissible answer among several the repository's own concept allows, and the model records it as the owner's choice rather than as a requirement the process concept imposes.

**What a Khayyam program can actually say today.** Only a declaration whose execution arrives from elsewhere: [Khayyam → Method](../../../docs/khayyam/khayyam.md#method) at `:91` and [Method in Khayyam → Body-less Methods](../../../docs/khayyam/method.md#body-less-methods-ffi-and-contracts) at `:80` make a body-less method on a concrete capsule the form through which an implementation arrives externally, and nothing in the language computes, writes, or inspects one — [Agency in Khayyam](../../../docs/khayyam/agency.md) at `:13`, `:39` and `:44`, above, is why. So a program can say that advancing the ring's head is one indivisible operation and can say nothing about how it is done. Two facts about this repository are recorded here as what they are and are the ground of no claim in this document: the `.kh` sources declare an abstraction of atomic operations at [`modules/computer/adt/hash_table/protocol/atomic.kh:7`](../adt/hash_table/protocol/atomic.kh)–`:15` with body-less `Load`, `Store`, `Swap` and `CompareAndSwap`, and carries a pair of shareability flags at [`modules/computer/function/protocol/access.kh`](../function/protocol/access.kh); and the same sources raised and never declared a mutable reference safe to pass between threads at [`modules/computer/memory/reference/concurrent.kh`](../memory/reference/concurrent.kh). The code under `modules/**` is residue of an attempt to develop these ideas in another language that did not succeed and the owner has ruled it neither evidence nor a premise, so none of this is read as the language having found this shape — only as the language leaving it available, which is what the two documents above already say.

**The answer, plainly: an atomic head or tail update is expressible today as a declared method and as nothing else.** No source can write the update, name the region it applies to, or compute a new head; what a source can do is declare that advancing the head is one indivisible operation, which is a provision in this model's own terms. What that costs the design is four things, none of them a change to the grammar. **The guarantee is the same on both sides only because both sides run the same module** — which is the one obligation nothing checks (question 19 under [Open questions](#open-questions)), and the atomicity rides on it entirely. **It fails the checkability test stated under [What a binding is](#what-a-binding-is)**, because atomicity is a property of a realization and not of anything the other party declares, so the only evidence available is that a provision arrived. **It is relaxable by configuration** in the sense `memory.md:85` gives, so "atomically" is a property of an organization's posture rather than of the design, and an agreement can state the requirement without ever being able to guarantee it. **And it costs a contract term rather than a type**, which is the cheapest of the four and the only one the repository has already written down.

**The owner has ruled where the indivisibility lives, and the ruling adds a requirement the word "atomically" does not carry.** Asked who carries atomicity in this design, the owner answered that it is **a method of the buffer module, using a module similar to Go's `sync`**, and that the synchronisation module itself may be generated. So the indivisibility is a method of [`modules/computer/buffer/`](../buffer) — its receiver is a capsule, so it may name a capsule and take the region, which [Abstraction in Khayyam → What You Cannot Do](../../../docs/khayyam/abstraction.md#what-you-cannot-do) at `:100` would forbid an abstraction-owned signature to do — and the guarantee it rests on belongs to the module modelled at [Synchronization Model](../../process/sync/sync.md). Two consequences follow, and the second is the one the owner's sentence does not carry. **The cursor and the rule about when a portion is free are the ring's**, under [Modeling → Constraints Belong to the Constraining Concern](../../../docs/modeling.md#constraints-belong-to-the-constraining-concern); the sources' nearest is an empty `Buffer_Index` at [`index.kh:2`](../buffer/protocol/index.kh) that `Computer_Buffer` does not compose at [`buffer.kh:22`](../buffer/protocol/buffer.kh). **Indivisibility alone does not free the region**: the driver must also observe the application's earlier writes to it, so a release that is indivisible and unordered lets the driver refill bytes the application was still writing — which is why the synchronisation model carries **Sequencing** beside **Atomic Operation** and why the order is a second requirement rather than a property of the first. **What it costs:** one more declaration outside this folder, one more module both sides must include for the guarantee to be the same on both, and the same silent-loss risk under question 19 that already rides on the indivisibility. **What it awaits:** the protocol that would state the guarantee — [Concurrency Realization](../concurrency/concurrency.md) at `:11` claims to cover the synchronization primitives its body never names — and a document that owns the terms, question 24.

**Language-level, per-target, or protocol-level.** *Language-level:* that the update may be declared as one operation whose execution arrives from outside, and that nothing in a source may write, compute, or inspect it — the same arrangement as every other provision, and a second target could not make an indivisible update writable without adding a literal and a type it does not have. *Per-target:* whether a head is an index or a pointer, what the indivisible operation actually is on that substrate, and whether a method declared on an abstraction is supplied at all — this target's link map holds nothing (`link_map.json` is `{}`), so the guarantee is a fact about a host's runtime. *Protocol-level:* that a place crossing's release is indivisible **as a term of the agreement**, which is [Memory → Copy and ownership semantics are contract members](../memory/memory.md#copy-and-ownership-semantics-are-contract-members)'s subject and not the language's.

#### Resizing: what the agreement must carry about the place's size
The owner's second requirement: "it must also be agreed that the buffer will be grown or shrunk when necessary."

**The measure of a size would have to come from outside too.** The sources happen to declare one — [`modules/computer/adt/container/protocol/length.kh:15`](../adt/container/protocol/length.kh) writes `tp NumberOfElement ab`, its comment at `:12`–`:13` recording that a length "can present capacity, usage, buffer" — and that is recorded as a fact about the repository, not used: whether this repository writes a `NumberOfElement` capsule or names something else is a decision for whoever writes the library, and the language decides nothing about it. What the three sentences above decide is enough: so a size is a value from outside the language, exactly as the address is, and what a source may say is the *declaration* of a resize and nothing about how large.

**What the repository's own files show here, and what does not follow from them.** [`modules/computer/adt/container/protocol/resize.kh:7`](../adt/container/protocol/resize.kh) declares `Container_Resize ab` with `Container_Resize_Resize mt (self Container_Resize) (ln NumberOfElement) (e Error)` at `:11`, `Resized … (b Boolean)` at `:13`, and `Resizable … (b Boolean)` at `:16` — commented "Resizable returns true if the container(buffer, ...) can be resized, or false if not." Those lines are a description of the repository's state. An earlier form of this paragraph drew three conclusions from them — that resizability is a capability to be asked about rather than a promise, that a resize may fail, and that the operation is the container's own rather than a property of any crossing — and those conclusions are **withdrawn**, because they were read out of a declaration the language did not write and the language did not require. The first of the three survives on other grounds and is stated here on them: the model's own checkability test ([What a binding is](#what-a-binding-is)) leaves a bilateral agreement able to state a requirement it cannot compel, so "may the ring be resized" is the most a crossing's agreement can carry and asking the other party is the only form of that which either can check alone. Whether a resize may fail, and where a crossing's size may change at all, are open and are carried in the paired [handoff](./binding.handoff.md).

**What resizing costs this design is sharper than anything else in this revision, because resizing and zero-copy are two names for what happens to an address.** The trade-off is the owner's own, not the sources', and both halves of it are in the account at `:30` and `:80`: the application hands the driver **the memory address of the capsule** and the driver writes into the application's own memory without passing through any other party's memory, *and* the two sides must agree that "the buffer will be grown or shrunk when necessary". Those two sentences cannot both hold while the address keeps naming the same region. This design's central property holds exactly as long as that address keeps naming that region; a resize that moves the region invalidates the driver's address silently — the driver writes into memory that is no longer the ring, and nothing in the language, in the shared module, or in either party's declaration objects. Nothing here rests on what the `.kh` files say: [`modules/computer/buffer/zero-copy/buffer.kh:7`](../buffer/zero-copy/buffer.kh) carries a comment "It means buffer not reuse when need copy more data to it and **it can't be resized!**" and [`modules/computer/buffer/circular/buffer.kh:7`](../buffer/circular/buffer.kh) describes a circular buffer as one "that uses a single, **fixed-size** buffer as if it were connected end-to-end", and an earlier form of this paragraph read those two as the sources stating the trade-off and settling it. That reading is **withdrawn** twice over. The two comments are about two different kinds of buffer — one says a buffer that is zero-copy cannot also be resized, the other says a circular buffer is built on one fixed-size region — so they do not contradict each other and neither contradicts the owner's design; and in any case the code under `modules/**` is residue of an attempt to develop these ideas in another language that did not succeed, which the owner has ruled neither evidence nor a premise. The trade-off is the owner's, and it is live whether or not any file in this repository happens to have noticed it.

Three answers follow and the model does not choose among them, because the choice is the owner's. **The region never moves and "grown or shrunk" means the grant is renegotiated** — the size is then a one-time agreed fact of the agreement, the address stays valid for the ring's whole life, and this costs the design nothing. **The region moves and the driver is re-told** — then the crossing carries a second exchange after the first, and the design acquires a window in which the two sides disagree about where the ring is, which is a concurrency requirement the agreement must state and which "no breaking changes" cannot absorb, because it is not a change either party makes alone. **The address is an indirection that survives the move** — then it is not the region's address but a cell holding one, which is a place inside a place and reintroduces by another name the mediation this model refuses.

**Language-level, per-target, or protocol-level.** *Language-level:* that a size is not writable, that the measure of a size is a named capsule whose values come from outside, and therefore that a resize may be declared and never described. *Per-target:* whether a resize moves the region, whether it does so atomically with respect to the other side's operations, and what the other side's address becomes afterwards. *Protocol-level:* whether a crossing's size may change at all while a crossing is live — a term of the agreement, owned by [Memory → Copy and ownership semantics are contract members](../memory/memory.md#copy-and-ownership-semantics-are-contract-members) in the shape of "treat any returned buffer as valid only until the next call", with a ring whose size changes as the case where a caller must be told rather than left to infer.

#### The initialisation
The owner's account says the module "is initialised" on the application's side, and that word names a concept this repository already has which is **not** Construction's. [Construction Model → Initialization](../../process/construction/construction.md#initialization) defines it as the responsibility by which an obtained instance reaches a state in which its methods mean what they promise, and separates it from Construction on the evidence of [Variable in Khayyam → Overview](../../../docs/khayyam/variable.md#overview), which names "creation and initialization" as two, and on [Modeling → One Authoritative Location per Concern's Data](../../../docs/modeling.md#one-authoritative-location-per-concerns-data), which is why an instance's arguments are the domain's to state and the obligation is not. [construction.md:128](../../process/construction/construction.md#the-names-to-use-and-the-names-to-refuse) refuses `Init` as a shared name across types on that ground, and this document agrees with the refusal on it. The `.kh` files agree too — [`modules/computer/capsule/protocol/life_cycle_contract.kh:6-9`](../capsule/protocol/life_cycle_contract.kh) excludes `Init` and `Reinit` from the shared lifecycle contract because "Initialization and re-initialization are the capsule's own behavior, through its own named methods carrying its own domain arguments" — and that agreement is recorded as a fact about the repository, not as the reason. An earlier form of this paragraph made the sources' comment the reason and read the decision as already made; that is withdrawn, because a comment in the residue of the failed Go attempt is not a decision and cannot be one.

So the revision this model owes is precise: **`init` is Initialization; it is the capsule's own named method; and in this design it belongs to the application's side alone.** The driver holds the same instance and must not initialize it — a rule nothing in this repository states, and one the sources' own exclusion is what makes coherent. Had `Init` been a shared contract method, the driver would be the obvious caller of it on an instance it does not own, and the two sides would disagree about the instance's state at exactly the moment the hardware begins writing into it. [Compiler → Entry and lifecycle are not grammar](../compiler/compiler.md#entry-and-lifecycle-are-not-grammar) at `:41` puts `init` outside the grammar in any case: how a program boots and tears down is compiler configuration plus the selected Runtime.

**Does the model need a revision because of the construction model's finding?** Yes, in one place, and it is this one. The model recorded the application's side of a place-crossing as "a form any document provides" not at all — a method that writes into a region the program was handed, or a declaration that says which region. It is provided, by the construction model's two concepts in order and by the sources' own comment: obtain the instance, then initialize it through the capsule's own method, with the holder doing both. That is a revision of this document's claim, and it is why the shared place is no longer recorded here as unimplementable.

**Language-level or per-target.** *Language-level:* nothing — the language says nothing about initialization, and this is not a silence `docs/khayyam/` should close ([khayyam.md:177](../../../docs/khayyam/khayyam.md#minimal-legislation-a-principle)). *Per-target:* how a program boots and what drives initialization, which [compiler.md:41](../compiler/compiler.md#entry-and-lifecycle-are-not-grammar) assigns to configuration plus the selected Runtime. Neither, and this is the live part: **which party may call an instance's initialization at all**, which no document states and which the two sides of this design disagree about implicitly.

#### Each party is a module of an existing category, and there is no umbrella
The owner's account had an operating system supervising, its only duty introducing a driver as an application to the others so that "an application does not appoint itself as an application of others' choosing and does not take control of the hardware". The owner's seventh fact removes that shape rather than relocating it: "Each module should do one thing and do it properly; that way modules really become simple. We no longer need a big umbrella concept like `os` where everything is dumped in without care and we call it a monolithic OS kernel with pride and say we have the best operating system in the world."

**The umbrella was never load-bearing in the document the model leaned on, which says so twice.** [OS → The kernel is a layer concept, not an OS-exclusive one](../os/os.md#the-kernel-is-a-layer-concept-not-an-os-exclusive-one) at `:41` — "a system's kernel is the foundational layer carrying its non-removable domains, so a user-space application can have one". [OS → Networking: frame delivery, not communication meaning](../os/os.md#networking-frame-delivery-not-communication-meaning) at `:117` — "Even packet routing can be an application: a router is a service holding an entitlement to the network hardware, not a sanctified OS subsystem" — and at `:121` the driver is named in the same register ("if the driver, or even frame delivery, is itself an application"), together with the statement of this design's central property as that document's own finding: the "same exclusive grant can map the NIC's own memory into the destination application's address space, so packet data lands directly in the application's buffers from the NIC — moved by the hardware, without the kernel copying it". So the OS document had already de-privileged the driver before this model did. What this model did with it was make an umbrella the *warrant* for a guarantee, which is the one use of it the owner has refused; the guarantee itself was never the OS's to give, and [OS → Identity](../os/os.md#identity-principals-not-users) at `:126` had already narrowed identity to "a notion of **principal** that privilege boundaries can attach to" rather than a party.

**What replaces it: each party is a module of a category this repository already has, doing one thing.** The categories are named here as the owner named one of them and the sources named the rest, and they are **not settled**: [modules/README.md:11](../../../README.md) states that "no folder here is final" and that "names may be merged, split, moved, or retired whenever the responsibility they name is better served another way", so this is a reading of the categories as they stand rather than a decision about where they go.

- **The driver** — [`modules/computer/driver/`](../driver), named by the owner. It is empty, which [`modules/README.md:10`](../../../README.md) makes "a decision made visible" rather than an absence, and `:12` says a folder without a README "carries its intent in its name" until one is written.
- **The application** — the two categories that own what an application does with a region: [`modules/computer/adt/`](../adt), which owns `Computer_Queue`, `Container_Resize`, `HashTable_AtomicAccessor`, `List_Head` and `List_Tail`, and the presence abstractions `OnPresent`/`OnAbsent` ([`listeners.kh:4`](../adt/protocol/listeners.kh), [`:7`](../adt/protocol/listeners.kh)); and [`modules/computer/buffer/`](../buffer), which owns the region itself and states the trade-off this design runs into ([`zero-copy/buffer.kh:7`](../buffer/zero-copy/buffer.kh), [`circular/buffer.kh:7`](../buffer/circular/buffer.kh)).
- **What both sides rely on** — [`modules/computer/capsule/`](../capsule), which owns the lifecycle contract ([`life_cycle_contract.kh:5`](../capsule/protocol/life_cycle_contract.kh)) and, decisively, the authorization that answers "who may use this": [`authorization.kh:5`](../capsule/protocol/authorization.kh) declares `tp Authorization ab` with `Capsule_Authorization_LimitToUseBy` at `:7`, commented "LimitToUseBy or ImportableBy".
- **What each side may rely on about when the other side's effect has taken effect** - [`modules/process/sync/`](../../process/sync), modelled at [Synchronization Model](../../process/sync/sync.md), which owns exactly two guarantees and refuses a third: that an effect is indivisible, and that one side's completed writes become the other side's next premise in a stated order. This is a category this document names for the first time in this revision, on the same footing as the others rather than as a part of any of them, and it is a peer of the buffer rather than a part of it: the release is a method of [`modules/computer/buffer/`](../buffer) and the guarantee is obtained from here.
- **How the two sides' work is scheduled** — [`modules/computer/runtime/`](../runtime), which owns `Async` ([`concurrency.kh:7`](../runtime/protocol/concurrency.kh)), the thread protocols and the scheduler, and is the only one of these categories with a README.

**The guarantee moves with the categories, and it becomes three small things instead of one large one.** What the OS document named three times over — resource entitlements (`:93`), exclusive-access arbitration (`:117`), and a principal (`:126`) — was a single guarantee about *who may touch this hardware*, held by one party on behalf of every party. Under the categories it separates into three, each owned where it belongs: **who may use this capsule** is `Authorization`'s `LimitToUseBy`, stated on the one declaration both sides include; **what each side may assume the other does to the region** is the crossing's own contract terms under [Memory → Copy and ownership semantics are contract members](../memory/memory.md#copy-and-ownership-semantics-are-contract-members); **who may do the work at the same time** is a posture an organization configures, per [Memory → Safety enforcement is governance](../memory/memory.md#safety-enforcement-is-governance). So this document no longer claims the guarantee is named three times anywhere. It claims that each part of it has an owner in a category that does one thing, and that the largest part — admission — is a term on the crossing rather than a party ([The relations](#the-relations)).

**Language-level, per-target, or protocol-level.** *Language-level:* that a capsule's authorization is a declared abstraction whose value the module states, and that satisfaction is structural ([Abstraction in Khayyam → Abstraction Realization](../../../docs/khayyam/abstraction.md#abstraction-realization-implicit-satisfaction)) — nothing here mentions hardware, entitlements, or principals, and a second target admitting the same declaration learns nothing new. *Per-target:* what an authorization is checked against, and how a driver reaches a device at all, which no document states and which a second target may answer differently. *Protocol-level:* whether admission is a term of a crossing at all — with no umbrella to hold it, no document owns that question today, and it is carried below as an open question with these categories named as the candidates rather than as the answer.

### Where the reference covers this and where it does not
The owner supplied [Foreign function interface](https://en.wikipedia.org/wiki/Foreign_function_interface) as a reference, and asked how much of it this concept covers. Read in full, the honest answer is: **the concept covers the page's first instance and strictly widens past the page's second and third, and the page says so itself.**

What the page defines is narrow and exact: "a mechanism by which a program written in one programming language can call interoperable routines or make use of services written or compiled in another one", often into a dynamic-link library. That is this model's first instance, in this model's own words: a route to a facility in another language. The page's concerns are also the first instance's concerns — mating "the semantics and calling conventions" of two languages, the runtime environments and ABIs of both, glue code, wrapper libraries, and the cases that make an FFI hard (garbage collection on one side and not the other, objects that cannot be mapped, VMs that are not the same VM, cross-language inheritance). Every one of them is a concern about *a call*, and this model carries every one of them inside the first instance without adding anything.

Where the concept is wider than the page, the page marks two of the three boundaries itself. It says that "the term foreign function interface is generally not used to describe multi-lingual runtimes such as the Common Language Runtime", and that "many distributed computing architectures such as the Java remote method invocation (RMI), RPC, CORBA, SOAP and D-Bus permit different services to be written in different languages; such architectures are generally not considered FFIs" — which is this model's second instance, a Web API, placed by the reference itself outside the term it defines. And the page's own *Naming* section records that "Ada has *language bindings*" and that Java has JNI, JNA, and, since Java 22, the "Foreign Function and Memory API" — the last being the closest the reference comes to this model's third instance, since it admits memory alongside functions. What the page never describes is the property this model puts at the centre: **an agreement two parties hold with no third party introducing it.** The page's mechanisms all have one. An FFI has a dynamic linker resolving a symbol; a JNI has a JVM; a Web API has a resolver, a manifest, or a service registry; a CLR has a common substrate. Even the CLR case, which the page excludes by name, works because a common substrate introduces the services.

So the coverage runs the way the owner said it would and no further: this concept is **a kind** of what that page describes for its first instance, and is not a kind of it at all for the other two, because the reference's own exclusions and its own reliance on a mediating mechanism are what this model removes. What this model gains from reading it and what it does not: the page's list of what makes an FFI hard is the first instance's cost list, and it is carried here as such; the page's `extern "C"` and name-mangling material is a first-instance problem about spelling and is carried under [The names to use and the names to refuse](#the-names-to-use-and-the-names-to-refuse); and nothing on the page is evidence about a shared place.

### The concepts

#### Binding
The agreement two parties hold about something, with no third party introducing it.

Its distinguishing property is that **it is a statement, not a mechanism** — and that it holds by being stated twice rather than by being installed once. Nothing about it is dispatched, resolved, loaded, registered, or copied; those are the other party's business and are named elsewhere in this model or owned elsewhere in the repository. This is the sense in which the owner's requirement holds: the binding is not a comment beside a declaration, it is the declaration, and it is checkable because both halves are.

**What it agrees about is a behaviour.** The owner's sixth fact makes this the concept's second clause: the two parties agree what each may assume the other does, not what code either runs — "the idea of the same library is **not that the code is literally the same, but that the behaviour is the same**". A binding about a route inherits its behaviour from the far side's signature; a binding about a place inherits nothing, because a region has no signature, so the behaviour is part of what is agreed. This is what makes the concept a bilateral agreement rather than an interface: two independent parties may reach one behaviour by different means, and the agreement is what holds while they do.

**What "no breaking changes" means here, and what it cannot mean.** It cannot mean a commitment, because a commitment is enforced by somebody and this agreement has no third party: there is no principal, no arbiter, and no escalation path ([Agency → Contracts](../../../docs/agency.md#contracts) is where a term with those things is defined, and [Protocol vs Contract](../../../docs/protocol.md#protocol-vs-contract) is where the repository has already said that what it calls a Protocol is explicitly *not* that). It means one of two things instead, and which one depends on whether the parties run the same artifact. **Where they do**, a breaking change is not a promise either party could break but a fact about the deployment: both sides include one module, so a change to the behaviour reaches both at once and there is no window in which one side holds the old behaviour and the other the new — and the check is a link or build step, not a negotiation. **Where they do not** — a foreign function, a Web API — "no breaking changes" becomes an obligation the far party must publish, which is the price this document already records under [Implications](#implications) and the reason a binding's declaration has to state what the other side may rely on. **What "no breaking changes" excludes, in both cases, is a change to the *code* that leaves the behaviour identical**: that is the "small changes" the owner's sentence admits, and this repository's own measurement discipline ([Memory → Allocation claims are measurement claims](../memory/memory.md#allocation-claims-are-measurement-claims)) is the form such a claim must take — stated with the evidence, not asserted.

**The test any term of it must pass.** A term is worth stating only if one party can check it without the other's cooperation; anything else is a hope. This is what decides the difference between what the sharpest instance carries as a declaration, as a provision, and as an open question ([The execution method](#the-execution-method-an-atomic-head-or-tail), [Resizing](#resizing-what-the-agreement-must-carry-about-the-places-size)), and it is the sharpest available contrast with a Contract, whose terms are enforced from above rather than checked from below.

**What it owns.** That the agreement exists, is stated once per side, and holds by that statement. **What it does not own.** What either party means by what it states, whether the other party exists at run time, what discharges the agreement, whether the behaviour is the same in fact, and how either party is delivered.

**Node.** It has an independent lifecycle — one party can change or vanish and the agreement is the thing that is then broken — and it enforces rules no existing concern in this repository owns: that both sides state it and that nothing in between does. It survives [Modeling Practice → Challenging a Proposed Concept](../../../docs/modeling.practice.md#challenging-a-proposed-concept) because removing it leaves the two declarations with no relation between them.

**Collides with** `Adaptor`, with the opposite responsibility, and **is not declared** by any `.kh` file.

#### Party
Either of the two sides that hold a binding, named by the role it takes in the agreement rather than by what it is.

This is the concept that replaces the previous shape's *Host Facility*, and it exists because "host" is not a role: the program and the runtime are not in the same relation as a driver and an application, and neither is in the same relation as two libraries in two languages. What all three share is that each is one of two, each states its half, and each is reached by a name the other does not own. A party's own name, its own spelling, and its own rules about its own shape are that party's and not this repository's.

**What it owns.** Its own name, its own vocabulary, its own argument order and optionality, its own failure behaviour, and whether it exists at all in a given environment. **What it does not own.** How a program asks for it, whether any program does, what a program does with what it gets, and whether this repository has heard of it.

**Node.** It has an independent lifecycle — a party's release or replacement cycle, which this repository does not participate in — and it enforces rules nothing else owns: that its name belongs to it.

**Refuses the name `Host`** for itself, on the evidence in this repository. `Host` already has three owners here: the process that loads and runs an artifact ([Compiler → Entry and lifecycle are not grammar](../compiler/compiler.md#entry-and-lifecycle-are-not-grammar); [the JavaScript target](../../../bundles/khayyam/targets/js/target.md#running-a-program) says "a host is asked for one entry"), the display contract's editor and CSS ([`display.json`](../../../bundles/khayyam/display/display.json), where the `capsule` role reads "A class, in the host's sense of a stateful declared type"), and a URL authority at [`modules-plugable/computer/ui/gui/protocol/navigator.kh:173`](../../../modules-plugable/computer/ui/gui/navigator.kh). Where the environment as such is meant, [Runtime](../runtime/runtime.md#what-a-runtime-is) owns it, and that document refuses to be narrowed to a language's virtual machine.

#### Crossing
What the agreement is about: a route to a capability, a shape of data and behaviour, or a place in memory.

This is the concept that makes the widening structural rather than a broadening of vocabulary, and it is the one place the previous shape was wrong by omission: it had a route and nothing else, so a Web API and a shared buffer had nowhere to stand. A crossing is not the call and not the value — it is the thing the two parties agree on, which a call reaches and a value instantiates.

The three kinds are **classifications of a Crossing, not concepts**, and they are recorded here as loop-edges for the reason [Modeling → Classification Emerges From Rules and Relations](../../../docs/modeling.md#classification-emerges-from-rules-and-relations-not-from-intrinsic-labels) gives: a label earns a node only when it carries rules no other concern owns and opens a relation the model recognizes. None of the three does. `Route` and `Shape` and `Place` differ in what a crossing must have — a key, a shape, or an identity — and that difference is stated under each instance above and is a difference of what is required, not of what is owned. A fourth kind is left open rather than refused: what a crossing is when neither party is a program is not enumerated by this model, and the enumeration's criterion is carried as an open question.

**What it owns.** Its own identity to both parties — the fact that this crossing and not another is what the agreement is about. **What it does not own.** How either party reaches it, what it means to either party's own vocabulary, or how it is realized.

**Node.** It has an independent boundary — the crossing can be stated, reviewed, and ruled on once while every binding, every party, and every realization changes beneath it — and it enforces a rule no existing concern owns: that an agreement has exactly one subject, which is what makes the subject checkable.

**Collides with** nothing this repository declares, and **is not declared** by any `.kh` file.

#### Binding Declaration
The declaration one party writes stating its half of a binding.

Its distinguishing property is that **it is the only artifact this concept owns, and it is a declaration rather than a note.** A binding may be declared in prose beside a declaration, in a companion unit, in a manifest, or — under the widening — in whatever form each party already uses; what is not available is leaving it unstated and letting a coincidence of spelling stand in. This model's rule-level claim is exactly this and nothing more, because the language withdrew the stronger one: [Language Gaps → I-B](../../../bundles/khayyam/targets/js/language-gaps.md#i-b--whose-name-a-body-less-method-carries--withdrawn-by-the-owners-ruling) records that "there is no weaker version of the text this document can draft, because what is at issue is not how much the language should say but whether it says anything".

**What it owns.** The statement of one party's half, in that party's own vocabulary, at an address the other party can be given. **What it does not own.** The other party's half, what either statement means, and whether the other exists.

**Node.** It has an independent lifecycle — one party may be replaced without the other being touched — and it enforces the rule nothing else owns: that the correspondence is stated rather than inferred.

**Collides with** the previous shape's *Binding*, which was the same concept seen from one side only, and **is not declared**.

#### Counterpart Address
The key by which one party reaches the other party's side of a binding, as distinct from the address a call goes to.

This is the previous shape's *Facility Reference*, renamed because the reference it replaced named one instance's answer. The owner's example for it — "the path by which the intended function is reached" — cannot be a path in this language, and the three facts that decide it are language facts rather than preferences: there are **no primitive types** ([Khayyam → Type Principles Realized](../../../docs/khayyam/khayyam.md#type-principles-realized)), there is **no literal** ([Khayyam → Separation of Syntax and Governance](../../../docs/khayyam/khayyam.md#separation-of-syntax-and-governance-a-principle) at `:162`, with a `vr` carrying no inline initializer per [Variable in Khayyam → Variable Declaration Syntax](../../../docs/khayyam/variable.md#variable-declaration-syntax)), and there is **no construction form** ([The JavaScript target → Running a program](../../../bundles/khayyam/targets/js/target.md#running-a-program) records that every value a program handles was produced outside it). So nothing a program writes can be text, and a value in an influenced group can only have been put there by the supplied implementation.

What the key actually is, per instance, is this: for a foreign function it is the `(declaring URI, exported name)` pair the run request is keyed by ([`run.ts:32-34`](../../../bundles/khayyam/targets/js/src/run.ts)), with the loader asked for a URI and not told which it is ([`run.ts:6-9`](../../../bundles/khayyam/targets/js/src/run.ts)) and an implementation handed to the unit that declares it ([`run.ts:18-19`](../../../bundles/khayyam/targets/js/src/run.ts)); for a Web API it is a shape a program holds rather than writes; and **for a shared place the address is the exchange itself** — the memory address of the one capsule the application holds, produced outside the program and given to the driver, which is the owner's design and is worked out under [The sharpest instance](#the-sharpest-instance-one-module-on-both-sides). What holds for the place as for the other two is what this concept exists to say: the address is not a name in the language and no key is ever written down. It is a value the host produced, carried in a variable the call hands over, and it is the one thing in that design which crosses.

**What it owns.** Whatever requirement the supplying party places on the value or pair by which its side is reached. **What it does not own.** The other party, the declaration, the meaning, or any representation of an address.

**Node.** Tentative for the first instance, and for the third no longer withdrawn but not yet a node either: the address is exchanged rather than written, so this concept earns a node only if a ruling says a declaration must *write* it, which no document says today. The reason is the same in both cases.

**Collides with** `Path`, `Route`, `Handle`, and `Address` in this repository, and **is refused** those names — see [The names to use and the names to refuse](#the-names-to-use-and-the-names-to-refuse).

#### Binding Unit
The companion side file in which a party's binding declarations are written, and which holds nothing else.

Its distinguishing property is that **it is told apart by what it is called.** Nothing in the language, the compiler protocol, the display contract, or the link map reads a unit's other contents to classify its declarations — [the target](../../../bundles/khayyam/targets/js/target.md#the-three-kinds-of-body-less-method) records the classification this toolchain actually performs, by the owner's kind alone — so the name is the discriminator, and the owner's own principle is what it leans on: **a file should do one thing and not grow long carrying several.** The sources already write companions in this shape and nowhere else: 30 `.locale.<lang>.kh` files, 100 `.observers.kh`, and 9 `.mutators.kh`, with [Documentation → File Naming](../../../modules-plugable/knowledge/documentation/documentation.md#file-naming) stating the dot as the separator between a companion's facet key and its base name.

Two structural reasons keep the binding out of a unit that does other work. A provision's address is the URI of the unit that declares it, whatever unit imported it ([`run.ts:18-19`](../../../bundles/khayyam/targets/js/src/run.ts)), so a binding written in the reaching party's own unit would put that party's code and the other's provisions at one address; and [`link.ts:9-12`](../../../bundles/khayyam/targets/js/src/link.ts) says a link must restate what the unit declared or leave its contracts stated nowhere, so a unit that may be replaced must contain nothing that is not replaceable.

**What it owns.** Being the unit at which one party's binding declarations are addressed, and holding nothing that is not replaceable. **What it does not own.** The declaration's content, the crossing, the other party, or whether the file is required to exist.

**Node.** It has an independent lifecycle — one party can be replaced without touching the other's source — and it enforces the rule nothing else owns: that a binding is declared alone under an address of its own. It is a layout the model explains rather than a thing the language has.

**Collides with** nothing, and **is not declared**.

#### Provisioning
The arrival, from outside a program, of the implementation that makes an operation executable.

This is not a new concept and this model does not define it; it is attached, following the sibling [construction model](../../process/construction/construction.md), which names it at `:68` on the ground that in this repository every value a program handles is obtained by provisioning. What this model adds is the boundary and the limit: a Binding is *performed by* provisioning in the first instance, and the arrival supplies an *execution* rather than a value — one step past the construction model's wording, which is carried as an open question rather than settled here. In the second instance what arrives is data rather than an execution, and in the third instance nothing arrives at all, which is the sharpest statement of the "no third party" clause: the third instance is the one binding whose crossing already exists on both sides before either party runs. The address the application hands the driver in the owner's design is not an arrival either — it moves between the two parties themselves, and both of them were already holding the instance it names.

**Node.** It survives the challenge test as an existing concept this model attaches to, and it is **already declared** — by the language, not by a `.kh` file.

#### Foreign Function Interface
Not a concept of this model, and refused as a Memar term on the ground the owner gave.

The reason is the name's own reach. `ffi` refers only to a function, while this concept's crossings may be a route, a shape, or a place; and [Foreign function interface](https://en.wikipedia.org/wiki/Foreign_function_interface) places RPC, CORBA, SOAP, D-Bus and multi-lingual runtimes *outside* the term by its own statement, so the ecosystem's word covers one of this model's three crossings. Two further facts make it unusable here even for that one. It is one ecosystem's vocabulary for a host-independent concern, which [Documentation → File Naming](../../../modules-plugable/knowledge/documentation/documentation.md#file-naming) refuses and which [`bundles/khayyam/README.md:21`](../../../bundles/khayyam/README.md) makes concrete by planning `wasm`, `c`, and `asm` beside `js`. And it is the language's word for the *form*, not for what the form is used for: [Khayyam → Method](../../../docs/khayyam/khayyam.md#method) at `:91` and [Method in Khayyam](../../../docs/khayyam/method.md#body-less-methods-ffi-and-contracts) at `:80` both use it, and the sources' 51 arithmetic conversions are that form too, so a file named `ffi` would name the form rather than what the file holds.

**Node.** Refused: narrower than the subject, and one ecosystem's word for it.

#### Host Facility
Not a concept of this model, and refused because the widening made the name false rather than merely narrow.

The previous shape of this document named it, and the name was right for what that shape covered. Under the widening it is not a concept and not a name: a capability the host offers is one case of a **Party**'s side of a **Crossing**, and a Web API's shape and a driver-written buffer are not facilities anything offers a program. Keeping the name would keep the previous shape's boundary, which is what the owner's decision removes.

**Node.** Refused: an equivalent concept exists under a name that covers all three instances.

#### Mediator
Not a concept of this model, and refused in the strongest sense available: **this model's definition denies that it exists.**

That is the whole of its ground. A concept named for a third party that introduces the agreement would assert what the definition refuses, and [Modeling Practice → Single Responsibility Check](../../../docs/modeling.practice.md#single-responsibility-check) refuses a node whose definition is a negation. The mechanism is not absent by accident either — the reference's own mechanisms all have one (a dynamic linker resolving a symbol, a JVM, a resolver, a common substrate), so naming this thing would name the thing the widening removes. What replaces it is not nothing but a rule: the correspondence is recorded, and nothing else is required to be there.

**Node.** Refused: the definition's own negative.

#### Registrar
Not a concept of this model, and refused for the same reason as **Mediator**, on the added ground that it is this repository's word for a real thing elsewhere.

A registry is a relation between an instance and a set, and the sibling [construction model](../../process/construction/construction.md) already treats registries as owned by whoever owns registration and lookup rather than by the concern whose instances they hold — [`modules/process/services/protocol/services.kh:14`](../../process/services/protocol/services.kh) and [`modules/computer/mediatypes/protocol/media-types.kh:9`](../mediatypes/protocol/media-types.kh) are its witnesses in the sources. In the shared-place instance a registry is the natural third party and is precisely what the instance excludes.

**Node.** Refused: an equivalent concept exists, is owned elsewhere, and this model denies its role.

#### Adaptor, Wrapper, Shim, Marshal, Bridge
Not concepts of this model, and refused as a family with one reason: **each names a translation, and a binding performs none.**

An Adaptor *translates* — [`modules-plugable/computer/adaptors/adaptor.kh:14`](../../../modules-plugable/computer/adaptors/adaptor.kh) declares `type ReadAdaptor func(p []byte) (n int, err error)` and [`modules-plugable/computer/adaptors/String/stringer.kh:7`](../../../modules-plugable/computer/adaptors/String/stringer.kh) gives `Stringer_GO` the purpose "to prevent protocol package not couple to a implementation package(fmt)", which is the coupling a binding avoids by keeping the other party's name out of this repository's declarations. A wrapper *copies*, a shim *satisfies an interface it does not own*, a marshal *converts a representation*, a bridge *joins two things that were separate* — and the reference's own `extern "C"` case is a bridge in exactly that sense, a name-mangling barrier between two languages' symbol tables. None of them is what a declaration that stands for something another party provides does. A reader who met "wrapper" would look for a copy and find none.

**Collides with** `Adaptor`, which the sources already hold under that name with the opposite responsibility, and which is therefore a real collision this model records rather than resolves.

**Node.** Refused: a difference of kind from the concept, and one name already owned.

### What each concept owns, and what it does not own
**Binding** owns that the agreement exists, is stated once per side, and holds by being stated twice. It does not own what either party means, whether the other party exists at run time, what discharges it, or how either is delivered.

**Party** owns its own name, its own vocabulary, its own shape and rules, and whether it exists at all in a given environment. It does not own how a program asks for it, whether any program does, or what a program does with what it gets.

**Crossing** owns its own identity to both parties — which crossing, and not another, the agreement is about. It does not own how either party reaches it, what it means in either vocabulary, or how it is realized.

**Binding Declaration** owns the statement of one party's half, in that party's vocabulary, at an address the other can be given. It does not own the other half, what either statement means, or whether the other exists.

**Counterpart Address** owns whatever requirement the supplying party places on the value or pair by which its side is reached. It does not own the party, the declaration, the meaning, or any representation of an address.

**Binding Unit** owns being the unit at which one party's binding declarations are addressed, and holding nothing that is not replaceable. It does not own the content, the crossing, the other party, or whether it must exist.

**Provisioning** owns what arrives from outside a program and when it becomes reachable to it. It does not own what the arrived implementation means — [Method in Khayyam](../../../docs/khayyam/method.md#body-less-methods-ffi-and-contracts) says the implementation is "provided by" the external phase, not specified by it — and it does not own which parties exist or which names they carry.

Three concerns a reader will expect here are owned elsewhere, and this model does not absorb them: **what the environment is and what it guarantees**, which is [Runtime](../runtime/runtime.md)'s subject and which deliberately refuses to be narrowed to one language's virtual machine; **what a program may do with what it holds**, which is this repository's own libraries under [Compiler → The compiler recognizes language primitives, not library names](../compiler/compiler.md#the-compiler-recognizes-language-primitives-not-library-names); and **what the crossing's result means to the program**, which is the direction of travel the whole vocabulary separation establishes.

### The relations
**A Binding is held by exactly two Parties.** The direction runs from binding to party because the binding is what the parties hold; a third party holding it would be the Mediator this model refuses. This relation is the definition's first clause, and it is what makes the count checkable.

**A Binding is about exactly one Crossing, and a Crossing may be bound more than once.** The direction runs from binding to crossing because the crossing is the subject; the many-to-one is deliberate, because two bindings may agree about the same place — a driver writing a ring and an application reading it are two bindings about one crossing, which is the shared-buffer instance stated in the vocabulary the model now uses.

**A Binding Declaration states one party's half, and a Party states its half once per binding.** This is the relation the widening keeps intact across all three instances, and it is the one the rule over file layout rests on.

**A Party is reached by a Counterpart Address.** The direction runs from party to address because the address is what the other party holds. In the shared-place instance the address is the exchange rather than a handle to look up, and it is the one place where what the second party holds is a value rather than a name ([The sharpest instance](#the-sharpest-instance-one-module-on-both-sides)).

**A Party is admitted to a Crossing by that crossing's own declarations, and by nothing else.** The direction runs from the crossing to the party because what admits a party is the agreement it would be admitted to, not a party that vouches for it. A declaration states who may use what it declares — in this repository's sources that is [`Authorization`](../capsule/protocol/authorization.kh)'s `LimitToUseBy`, a term on the declaration rather than a party — and the two parties in the sharpest instance are admitted by the one module both of them include. This replaces the relation this document previously carried, which had an introducer holding the guarantees and introducing one party to another; the owner has refused that shape, and the refusal removes a party rather than adding a term. What the relation no longer rests on is equally worth stating: the guarantee is not claimed to be named three times over in any document, because no document names an introduction, and the nearest existing statement of the shape belonged to a network coordinator ([chapar.md:76](../../net/chapar/chapar.md); [networking.md:141](../../net/net.md)) — a different layer, a different party, and a different crossing. **Whether admission is a term of a crossing at all is open**, and it is carried below with the categories that could own it named rather than assumed. It is not the **Mediator** this model refuses, and the reason is now structural rather than a matter of emphasis: a mediator introduces the *agreement*, while this relation concerns only who may reach a crossing that two parties have already stated.

**A Crossing of kind *place* carries an agreed behaviour, and a Crossing of kind *route* inherits one.** This is the relation the owner's sixth fact adds, and it is what makes the execution method part of an agreement rather than an implementation detail: a region has no signature for either side to inherit a method from, so what each party may assume the other does to it must itself be stated — that a portion is released by an indivisible change of the ring's head or tail, and that the size may change when necessary ([The execution method](#the-execution-method-an-atomic-head-or-tail), [Resizing](#resizing-what-the-agreement-must-carry-about-the-places-size)). The behaviour is not a new concept: a crossing's kind is a classification and not a node, and a behaviour is a second requirement on the crossing rather than a third kind of it.

**A Binding Unit holds Binding Declarations and nothing else, and is addressed by its own URI.** A **reference** edge in [Modeling → Edge Types and Their Traditional Counterparts](../../../docs/modeling.md#edge-types-and-their-traditional-counterparts) — "a named pointer from one node to another that the referencing node depends on but does not own". The URI is a shortcut edge in that same sense: it is derived from the declaration and must never become the source of truth about which crossing a declaration stands for.

**A Crossing of kind *route* is performed by Provisioning.** A Crossing of kind *shape* is delivered by whatever carries data across the network, which this model does not name and does not own. **A Crossing of kind *place* is performed by neither** — it exists on both sides before either runs, which is the instance's whole content and the reason nothing arrives; what the owner's design adds is not an arrival but an **exchange of the address of one instance both sides then hold**, which is carriage rather than delivery and changes nothing about the crossing existing in advance.

**A Party may be absent, and no concern in this repository decides what follows.** Under [Modeling → Constraints Belong to the Constraining Concern](../../../docs/modeling.md#constraints-belong-to-the-constraining-concern) the constraint's state belongs to whoever constrains and is not duplicated onto each binding. No document states this rule; the finding is that it is unowned rather than misplaced, and [Language Gaps → I-J](../../../bundles/khayyam/targets/js/language-gaps.md#i-j--where-the-rule-about-a-facility-the-environment-does-not-offer-belongs) records where a drafted sentence for it would go.

**A Binding Unit may be stood in for by a link-map entry, and only where the module that stands in for it is in this repository.** [`link.ts:165`](../../../bundles/khayyam/targets/js/src/link.ts) keys the map by a `.kh` URI and [`link.ts:191`](../../../bundles/khayyam/targets/js/src/link.ts) refuses an entry whose module cannot be read, so an entry can replace a binding unit only when a conformant implementation of the declaration lives in this repository. For a party outside it, the implementation *is* that party, the map holds no entry — [`link_map.json`](../../../bundles/khayyam/targets/js/link_map.json) is `{}` — and the party answers at `EntryRequest.supplied` instead. The two routes are distinct and both are stated below.

### The two vocabularies, and why the separation is structural
This is the model's central claim, and it is not a naming preference. Under the widening it is a claim about *any* pair of parties, and its ground has changed: it is no longer carried by a language sentence — the owner's ruling withdrew the sentence — and it is carried by two keyspaces.

A name in a program is the only handle a reader, a reviewer, a tool, and a governance rule have on what a piece of source means. [Khayyam → Self-Documenting Code and Naming](../../../docs/khayyam/khayyam.md#self-documenting-code-and-naming) makes the name carry what a prose comment would otherwise carry, and [Modularity in Khayyam → Naming Without Package Context](../../../docs/khayyam/modularity.md#naming-without-package-context) makes a name "state its own domain meaning rather than relying on a package prefix to supply missing context". So when one name stands for the other party's capability and for this repository's own future method — `Beep` on both sides — every layer that consults the name is consulting two meanings at once and cannot tell them apart. The corruption is not only in the reader: a rule that governs one meaning cannot be written, because [Linter → A rule's home is its subject's document](../linter/linter.md#a-rules-home-is-its-subjects-document) requires the claim to have a subject, and a name claimed by two owners has none. And a replacement cannot be scoped, because when the other party changes or drops something there is no way to tell which of the two meanings moved.

**The structural reason is that the two names are not the same kind of thing.** The program's name is a name in the language: written at a declaration, resolved by `in`, spelled under [the qualified-names rule](../../../bundles/khayyam/rules/qualified-names/qualified-names.md). The other party's name is not a name in the language at all — for the first instance it is a pair of strings in a table the host supplies, keyed by the URI of the unit that declares the provision and then by the exported name ([`run.ts:32-34`](../../../bundles/khayyam/targets/js/src/run.ts)), and the compiler is told which unit stands at a URI rather than asked to resolve one ([`run.ts:6-9`](../../../bundles/khayyam/targets/js/src/run.ts)). So `HTMLAudioElement.Beep` is not a name this repository could write and mean, and no grammar admits it: the two live in different keyspaces with different resolvers, and a collision is not discouraged by a rule but **unexpressible**.

That generalizes to all three instances and the generalization is worth stating because it is what makes the concept host-independent. A Web API's other name is a URL, a verb, and a media type — all text, none writable in a source. A shared place's name is not a name at all but an agreement, which is why nothing introduces it. In each case the other party's key is outside the language's namespace and the program's key is inside it, and in no case is there a construct in which the two could meet. That is what makes the owner's correction achievable rather than merely desirable: there is no construct to be careful about.

The separation is also what makes each name answerable, and answerable to exactly one owner. The facility's name is the host's, in the host's own spelling and documentation; the declaration's name is this repository's, in this repository's qualified-name form, at a URI in this repository. That is the same guarantee-and-meaning split [OS → The OS responsibility boundary](../os/os.md#the-os-responsibility-boundary) draws at the layer below — "The OS provides guarantees; the architecture defines meaning" — applied at the boundary between any two parties.

And there is a second reason, which is that the alternative is forbidden rather than merely worse. [Runtime → A runtime does not establish structure](../runtime/runtime.md#a-runtime-does-not-establish-structure) states that "any mechanism whose operation *establishes* this system's structure at execution time is a violation of the default path", and the same paragraph blesses consuming another system's services through interfaces this system's definition already names. A capability reached under a name the language does not own would not be that: this system's own definition would be silent about where it came from, and the environment would be supplying part of the definition. Keeping the two vocabularies apart is therefore not tidiness; it is the condition under which reaching is consumption rather than structure acquisition at all. This holds for the second instance too and more sharply, since a service registry would otherwise be a runtime structure the program's definition never named.

What the withdrawal of the language sentence leaves is exactly one thing a rule may still require, and it is the half that does not depend on a sentence: **that the correspondence be recorded as a declaration rather than left as a coincidence of spelling.** [Language Gaps → I-B](../../../bundles/khayyam/targets/js/language-gaps.md#i-b--whose-name-a-body-less-method-carries--withdrawn-by-the-owners-ruling) says the gap "is closed from the other side, by the structure the toolchain already has", and the drafted rule in [Binding Declarations Live in a Side File](../../../bundles/khayyam/rules/binding-declarations/binding-declarations.md) is that half and nothing more.

### What the language states, what a library could provide, and what neither states
These three layers are kept apart because the difference between them is the difference between what a program may say today, what it may say once something is written, and what no document answers.

#### What the language documents already state
Nine things are stated, and each is usable without extending the grammar.

1. **A method is body-less when nothing follows its third group, so its line ends at the closing parenthesis of the influenced group, and a line ending with `{}` carries a body — an empty body being a body holding no command.** [Khayyam → Method](../../../docs/khayyam/khayyam.md#method) at `:89` and [Method in Khayyam → Body-less Methods](../../../docs/khayyam/method.md#body-less-methods-ffi-and-contracts) at `:77` both say it; [Abstraction in Khayyam → Defining an Abstraction](../../../docs/khayyam/abstraction.md#defining-an-abstraction) at `:59` and [Khayyam Practice](../../../docs/khayyam/khayyam.practice.md#abstraction-pure-behavioral-specification) at `:63` write the same shape. The parser reads it the same way — [`parseBlock`](../../../bundles/khayyam/core/src/parse.ts) at `:219` yields no body when no `{` follows the third group, and [`program.ts`](../../../bundles/khayyam/targets/js/src/program.ts) at `:289` reads that absence as the whole difference between a compiled method, a contract, and a supply.
2. **A body-less method on a concrete capsule asks for an externally provided implementation.** [Khayyam → Method](../../../docs/khayyam/khayyam.md#method) at `:91` and [Method in Khayyam](../../../docs/khayyam/method.md#body-less-methods-ffi-and-contracts) at `:80`. This is the whole of the first instance's mechanism.
3. **A method may be attached to any type, including a method, and a method implements an abstraction by defining methods whose owner is that method.** [Khayyam → Method](../../../docs/khayyam/khayyam.md#method) and [Method in Khayyam → A method implements an abstraction by methods of its own](../../../docs/khayyam/method.md#a-method-implements-an-abstraction-by-methods-of-its-own) at `:74`, presenting the intent to tooling through [`abstraction_p.Implements`](../abstraction/implements.md). The owner's design is built on the shape this states, and the sources have zero instances of it.
4. **An abstraction's signature may name only abstractions, and a signature owned by a capsule may name a capsule.** [Abstraction in Khayyam → What You Cannot Do](../../../docs/khayyam/abstraction.md#what-you-cannot-do) at `:100` and `:109`. This is what forbids a shared contract naming a place.
5. **Satisfaction of an abstraction is structural, and the receiver is the implementer rather than the abstraction.** [Abstraction in Khayyam → Satisfying an Abstraction](../../../docs/khayyam/abstraction.md#satisfying-an-abstraction) at `:136`.
6. **Every variable of a call is passed strictly by reference**, owner and both groups alike ([Method in Khayyam → Key Rules](../../../docs/khayyam/method.md#key-rules)); the artifact realizes it as one cell per variable, per [The JavaScript target → Running a program](../../../bundles/khayyam/targets/js/target.md#running-a-program) and [`run.ts:75-86`](../../../bundles/khayyam/targets/js/src/run.ts).
7. **The compiler recognizes language primitives, not library names**, and specifically not operations "imported from a privileged package" ([Compiler → The compiler recognizes language primitives, not library names](../compiler/compiler.md#the-compiler-recognizes-language-primitives-not-library-names)). This is what keeps a binding library a library rather than a grammar extension.
8. **A name collision is an architecture error** ([Khayyam → Import Mechanism (`in`)](../../../docs/khayyam/khayyam.md#import-mechanism-in) at `:62`, and **there are no primitive types, no literal, and no construction form** ([Khayyam → Type Principles Realized](../../../docs/khayyam/khayyam.md#type-principles-realized); [Khayyam → Separation of Syntax and Governance](../../../docs/khayyam/khayyam.md#separation-of-syntax-and-governance-a-principle) at `:162`; [The JavaScript target](../../../bundles/khayyam/targets/js/target.md#running-a-program)).
9. **The language is silent about how a foreign function is reached, by the owner's ruling.** [Language Gaps → I-B](../../../bundles/khayyam/targets/js/language-gaps.md#i-b--whose-name-a-body-less-method-carries--withdrawn-by-the-owners-ruling) at `:76-77`. This is stated as a decision, and its consequence for this model is that no rule may cite a sentence about a provision's name.

#### What a library over them could provide
Given the nine, the following is available today as a `.kh` library and is not a language change:

- **One abstraction stating the property a declaration has when it binds rather than merely being unbound.** Its signature may name only abstractions ([`abstraction.md:100`](../../../docs/khayyam/abstraction.md#what-you-cannot-do)), every binding method satisfies it structurally, and every such method presents it to tooling by composing [`abstraction_p.Implements`](../abstraction/implements.md). Its unit is a protocol unit, and the map can stand in for that unit with a module that provides the run-time side while the abstraction itself is declared without being provided ([`link.ts:41-44`](../../../bundles/khayyam/targets/js/src/link.ts)).
- **One companion unit per party's bindings**, holding those bindings and nothing else, at a URI of its own, so each declaration is addressed by a pair the other party can be given.
- **A provision for each first-instance binding**, arriving through the entry protocol the run already implements: the host is asked for "the implementation of each body-less method, keyed by the URI of the unit that declares it" ([`run.ts:32-34`](../../../bundles/khayyam/targets/js/src/run.ts)), so no facility's execution needs grammar, compiler knowledge, or a new runtime.
- **A text-owning library for the second instance**, which is the sources' own answer: [`modules/computer/buffer/string.kh`](../buffer/string.kh) and the error family's locale companions show how this repository owns text and the shapes it needs, given that no source may write it.
- **A link-map entry for a binding unit, wherever the implementation is a conformant module in this repository.** The entry's shape is stated at [The JavaScript target → The link phase](../../../bundles/khayyam/targets/js/target.md#the-link-phase) and enforced in [`link.ts:70-118`](../../../bundles/khayyam/targets/js/src/link.ts): an entry naming no module, no protocol document, no recorded check, no provided export, or no declaration is refused before anything is compiled. What the entry cannot name is a party outside this repository, because [`link.ts:191`](../../../bundles/khayyam/targets/js/src/link.ts) refuses a module that cannot be read from the repository.
- **A Test for each binding**, per [Test → A Test's Subject Is a Named Process](../../process/test/test.md#a-tests-subject-is-a-named-process): a binding is a named thing whose expectations can be written before anything arrives to discharge it.

#### What neither states
These are the gaps. Each is a place where a document is silent, and the silence is the finding.

**Whether a body-less method whose owner is a method is the provision form or the contract form.** Both language sentences scope the foreign-function case to a receiver that is a concrete capsule ([Khayyam → Method](../../../docs/khayyam/khayyam.md#method) at `:91`; [Method in Khayyam](../../../docs/khayyam/method.md#body-less-methods-ffi-and-contracts) at `:80`), and [the target](../../../bundles/khayyam/targets/js/target.md#the-three-kinds-of-body-less-method) sorts the two forms by the owner's kind. A method owner is neither. The language admits a method as an owner and makes a method the owner of its own methods, so the shape is grammatical; nothing says which meaning it carries. This is the largest gap the owner's design opens, and it is a gap in the documents — an earlier form of this entry also reported that the `.kh` sources hold no instance of the shape, which is a fact about the repository and not a reason the question is open, and which is dropped here.

**Whether a body-less method on a concrete capsule that nobody answers is a binding or an unfilled declaration.** Under the settled spelling the 51 arithmetic and duration conversions are exactly that: a provision awaiting an implementation this repository does not write. Nothing distinguishes them from a binding except the file they are written in, and the language does not read file names.

**What a provision writes into its influenced group.** Nothing states it, and the design's own vocabulary has depended on the answer. [Control Flow → Error Propagation](../../process/control-flow/control-flow.md#error-propagation) requires every fallible operation to expose its error path as an ordinary named part of the call contract, but that is a protocol's requirement over a library rather than a grammar obligation, since [Khayyam → The Grammar Refuses Protocol Semantics](../../../docs/khayyam/khayyam.md#the-grammar-refuses-protocol-semantics) declines protocol semantics entirely, and [Disregarded Error](../../process/error/rules/disregarded-error/disregarded-error.md) requires that the failure be accounted for where the operation can see it while prescribing no form of carriage at all. Nothing states that a provision's influenced group may be empty either, which the route-as-address reading requires. An earlier form of this entry answered the question by counting how the sources' body-less methods on a concrete capsule happen to be written; that count is withdrawn, because a declaration in the residue of the failed Go attempt is not evidence about what this language requires.

**How a shared place is named, and whether it can be.** No document states that a program may name an address, hold a region, or receive one. The three facts that bear on it are all negations — no primitive types, no literal, no construction form — and the fourth is the rule that forbids a shared contract naming a concrete instance. What the sources offer instead is a host-side answer: [`modules-plugable/computer/ui/gui/protocol/application.kh:8-10`](../../../modules-plugable/computer/ui/gui/protocol/application.kh) declares `vr GUI Application` and comments "You must assign to it by any object implement protocol.Application on your main.go file", and [Variable in Khayyam → Variable Scope and Visibility](../../../docs/khayyam/variable.md#variable-scope-and-visibility) states that a file-level variable's "initial state is established by the compiler and by source that code generation emits". That is a third party introducing the crossing, which is what the third instance excludes. The owner's design goes around three of the four negations rather than removing any of them: the address is never named and never written, only **exchanged**, as a value the host produced ([The sharpest instance](#the-sharpest-instance-one-module-on-both-sides)). What remains unstated after it is whether a program may *hold* a place at all, and what a capsule wrapping one may declare — which is why the question survives below in a narrower form than the one this document opened it under.

**What a program's own side of a binding looks like when the other party's crossing is a place.** A method that writes into a region the program was handed, or a declaration that says which region, is not a form any document provides; the sources' 33 `From*` declarations show this repository reaching for a declaration of that shape and not once discharging it. The owner's design answers the first half of this without a new form — the program obtains the instance and initializes it through the capsule's own method, which is the construction model's Construction and Initialization in that order — and leaves the second half, the handover of the address, to whatever a target's calls deliver.

**Whether a party that is absent is a failure.** Not at build time and not at run time, by anything in this repository. The link map's checks are about an entry's own record ([`link.ts:188-210`](../../../bundles/khayyam/targets/js/src/link.ts)) and none asks whether the party is there; the run asks only for the implementations the host chooses to supply ([`run.ts:32-34`](../../../bundles/khayyam/targets/js/src/run.ts)).

### What is language-level and what is per-target
The owner's ruling — "for **each language** we should say separately what the abstraction must be and what the developer declares" — is a structural claim, and this section is where the model makes it. The claim is that **the language fixes what a binding is made of and each target fixes how a party is reached**, and it needs a third place besides those two, which this revision names and tests at the end of the section: **protocol-level**, a claim owned by a module's document under [`modules/`](../../), which the language is silent about, each target realizes, and an organization may configure differently.

**The third bucket, and why it is not optional.** Two buckets were not enough, and this document already knew it: the initialisation's live question and the old introduction relation were each recorded as "neither", which is a third bucket wearing a refusal. Its test is not the coincidence test the two buckets use — a protocol-level claim is not made language-level or per-target by a second target stating it identically — but **who owns the statement**: if the claim's home is a protocol document, it is protocol-level whatever any target does with it, and only the realization varies. The corollary is that this bucket cannot be discharged by the language at all, which is exactly why a place crossing's release and its size are carried as terms rather than as guarantees ([The execution method](#the-execution-method-an-atomic-head-or-tail), [Resizing](#resizing-what-the-agreement-must-carry-about-the-places-size)).

**Language-level — what Khayyam states, once, for every target.** Six things, and every one is a statement about what a program may *mean* rather than about how it is delivered: the body-less form and its two documented uses ([`khayyam.md:89`](../../../docs/khayyam/khayyam.md#method), `:91`; [`method.md:77`](../../../docs/khayyam/method.md#body-less-methods-ffi-and-contracts), `:80`); that a method may be attached to any type including a method ([`method.md:74`](../../../docs/khayyam/method.md#a-method-implements-an-abstraction-by-methods-of-its-own)); that an abstraction's signature may name only abstractions and a capsule-owned one may name a capsule ([`abstraction.md:100`](../../../docs/khayyam/abstraction.md#what-you-cannot-do), `:109`); that satisfaction is structural with the receiver the implementer ([`abstraction.md:136`](../../../docs/khayyam/abstraction.md#satisfying-an-abstraction)); that every variable of a call passes strictly by reference ([`method.md:39`](../../../docs/khayyam/method.md#key-rules)); and that there are no primitive types, no literal, and no construction form ([`khayyam.md:203`](../../../docs/khayyam/khayyam.md#type-principles-realized) onward, `:162`). Add to those the one thing the language says *nothing* about — how a foreign function is reached — and the split is complete in the only way it can be: the language fixes the shape of what is declared and is silent on delivery.

**Per-target — what each realization states for itself, and what this model writes and does not write.** A target states five things. **How a party's side is keyed**: this target's run request carries it as a `(declaring URI, exported name)` pair ([`run.ts:32-34`](../../../bundles/khayyam/targets/js/src/run.ts)), the loader is given a URI and not told which it is ([`run.ts:6-9`](../../../bundles/khayyam/targets/js/src/run.ts)), and an implementation is handed to the unit that declares it ([`run.ts:18-19`](../../../bundles/khayyam/targets/js/src/run.ts)). **How a delivery arrives**: a `supply` function per unit ([`run.ts:43-48`](../../../bundles/khayyam/targets/js/src/run.ts); [the target](../../../bundles/khayyam/targets/js/target.md#the-three-kinds-of-body-less-method)). **How a variable is realized**: one cell per variable ([`run.ts:75-86`](../../../bundles/khayyam/targets/js/src/run.ts)). **Whether a binding unit is in the link map**: this target's map is keyed by `.kh` URI and refuses an unreadable module ([`link.ts:165`](../../../bundles/khayyam/targets/js/src/link.ts), `:191`), holds no entry ([`link_map.json`](../../../bundles/khayyam/targets/js/link_map.json) is `{}`), and records that state as the map's state rather than a gap ([the target at `:75`](../../../bundles/khayyam/targets/js/target.md#the-link-phase)). **What a body's absence is classified by**: this target reads a body-less declaration by the owner's kind alone ([`program.ts:289`](../../../bundles/khayyam/targets/js/src/program.ts)), which is why it has no case for a method owner.

What a target states is a shape, and this model deliberately writes no implementation of one. The run request, the `supply` hook, and the map are quoted as *evidence of what a target states*, never as a proposal for what one should be, and no second target's request is described — which is exactly the boundary the owner's ruling draws: "how a foreign function is reached depends on each organization's own modules".

**What would change if a second target filled the split.** Four things move and five do not, and the asymmetry is the test. What moves: the key's first half, which would become whatever that target's run request names in place of a URI; whether the host is told which unit stands at a URI or asked for one; the artifact's own export convention, since a linked module must match it; the classification of a declaration whose owner is a method, which would have to be re-decided per target unless the language decides it once; and whether a binding unit appears in that target's map. What does not move: every one of the six language-level statements, because none of them mentions a target; the two-keyspace separation, because it follows from having a namespace and a keyspace rather than from either one's shape; the companion-file convention, which is this repository's rather than a target's; and the refusal of `ffi` as the facet key, which is a naming matter. If the second target's key were *the same pair* rather than a different one, that would not make the statement language-level — it would make it a coincidence between two tools, and a coincidence is what [Khayyam → Minimal Legislation](../../../docs/khayyam/khayyam.md#minimal-legislation-a-principle) exists to refuse.

The owner's design adds its claims to be placed against that split, and each is placed under [The sharpest instance](#the-sharpest-instance-one-module-on-both-sides) where it is worked out. **One module** being admitted by the language and included by both parties is language-level, while the *identical artifact* being what each side receives is per-target and per-organization. **The place** being unnameable, unliteral, and unconstructible is language-level, while what the host's address is and how a handover is delivered is per-target. **The agreed behaviour** is language-level only in its negative half — that a size is not writable and that an indivisible update may be declared and never described — while the requirement itself is protocol-level and its realization per-target. **The initialisation** is language-level silence with a per-target driver, and the live part of it — which party may call it — is protocol-level. **Admission** is language-level only as far as `Authorization` is a declared abstraction; what a party is admitted to is protocol-level and has no owner today, and only the form an introduction takes would be per-target. A prior pass of this document recorded the introduction duty as belonging to neither bucket; the third bucket is that record, named.

### What the language must say first, what the toolchain must check
The language must state one thing before anything else, and under the ruling it is a smaller thing than the previous shape of this model asked for. **It must state that a body-less declaration asks of something outside, and stop there.** That sentence is already in both documents ([`khayyam.md:91`](../../../docs/khayyam/khayyam.md#method); [`method.md:80`](../../../docs/khayyam/method.md#body-less-methods-ffi-and-contracts)) and it is what the rest may cite. What may *not* be added to it is a sentence about whose name the declaration carries, because the owner ruled that the language states nothing about how a foreign function is reached and that the distinction is carried structurally instead ([Language Gaps → I-B](../../../bundles/khayyam/targets/js/language-gaps.md#i-b--whose-name-a-body-less-method-carries--withdrawn-by-the-owners-ruling) at `:76-83`).

The language must then state a second thing that no existing sentence covers and the owner's design makes unavoidable: **whether a body-less method whose owner is a method is the provision form.** The sentence is scoped to a concrete capsule receiver; a method owner is legal and is how a method implements an abstraction; nothing says which meaning a body-less method there carries. This is a language decision because which form a declaration is changes what it asks of the link phase, and a target's classification has no place to put a fourth case.

A third language decision follows from the first and is not settled: **whether a provision's execution can fail**, and therefore whether its influenced group carries an `Error`. No document in this repository answers it, and the protocol that requires the error path to be named is a protocol's requirement over a library, not a grammar obligation. An earlier form of this paragraph reported that the sources answer inconsistently, thirty-five of fifty-nine carrying one and twenty-four not; that is withdrawn, for the reason the previous entry gives.

A fourth, and the one the third instance forces: **whether a program may hold a place, and what a capsule wrapping one may declare.** The owner's design shows that a program need not be able to *name* one — the address is exchanged and never written — so the decision this document used to put as "may a program name a place" is now narrower and more answerable. What a ruling must decide is whether the wrapper capsule's operations are the only operations a place admits (the reading this model takes, and the only one the negations allow), and whether its declaration is per crossing kind or per crossing. The second of those collides with [`abstraction.md:100`](../../../docs/khayyam/abstraction.md#what-you-cannot-do) as recorded in the sibling model at [`construction/construction.md:154`](../../process/construction/construction.md) if anyone proposes to put the wrapper behind an abstraction instead.

A fifth follows from the owner's design and no document raises: **whether the two parties are required to hold the same artifact, and what checks it.** A target may link a separate build of the module to the driver and lose the design's central property with nothing objecting, and the check is a link- and build-time fact rather than anything a program says. This is a tool's condition under [`khayyam.md:177`](../../../docs/khayyam/khayyam.md#minimal-legislation-a-principle), and its home is a tool or an organization, not the language.

**What the owner's sixth fact adds to this list is nothing at all, and that is the finding rather than an omission.** Atomicity is not a language decision: the language embeds no concurrency model ([`agency.md:13`](../../../docs/khayyam/agency.md)), its own cost statement places concurrency safety with a rule or a tool's check rather than the grammar (`:44`), and the memory protocol places data races among relaxable governance (`memory.md:85`). Resizing is not a language decision either: a size is unwritable whatever a source may declare, and whether a crossing's size may change is a term of the agreement. Both are therefore **protocol-level and per-target**, and this document's language-level list is unchanged by them — which is the sharpest available evidence for the claim that the split is the right one, since the two largest new requirements of the design land outside the language without any effort to put them there.

Then, and only then, the toolchain. What a check would cover, and what already exists for it:

- **That a binding declaration is in a unit that says so, and that a unit which says so holds nothing else.** The rule exists as a draft at [Binding Declarations Live in a Side File](../../../bundles/khayyam/rules/binding-declarations/binding-declarations.md) and has no check; the enforcement is governance, not a compile gate, because whether a declaration was *expected* to be a binding changes how well-formed an instance is kept rather than what any program means ([Minimal Legislation](../../../docs/khayyam/khayyam.md#minimal-legislation-a-principle) at `:177`).
- **That a provision's declaring unit is the unit the map stands in for, wherever the implementation is in this repository.** Checkable by reading `link_map.json` today, with no new mechanism; what is missing is a provision to check.
- **That the display contract can tell a binding declaration from an ordinary body-less method.** [`display.json`](../../../bundles/khayyam/display/display.json) declares twenty-one roles, each naming what an identifier *is*, and every one is a role in a `.kh` source; none distinguishes a declaration whose execution arrives from outside. [Language Gaps → I-K](../../../bundles/khayyam/targets/js/language-gaps.md#i-k--a-display-role-for-a-provision) records that the withdrawn sentence leaves this role resting on the body-less spelling alone.
- **What the link map's `protocol` field points at.** An entry must name a protocol document and record each check at a section that document has ([`link.ts:35-38`](../../../bundles/khayyam/targets/js/src/link.ts), [`link.ts:200-206`](../../../bundles/khayyam/targets/js/src/link.ts)), so a binding unit's conformance record needs a home document that does not exist.

### What a program may express afterwards that it could not before
A model that only says what is gained is not a model, so this section states both sides, and it leads with what is not gained because the third instance is the one that breaks.

**Not gained, and the reasons are named.** **A shared place is not nameable after this model, and it is holdable only on the terms the owner's design sets.** The bindings a program may express are routes — a declared provision whose execution arrives — and, once a text-owning library exists, shapes it holds. A place is still not among them: there is no primitive type to be an address, no literal to be an offset, no construction form to produce the region, and no shared contract that may name a concrete instance ([`abstraction.md:100`](../../../docs/khayyam/abstraction.md#what-you-cannot-do); [`construction/construction.md:154`](../../process/construction/construction.md)). What the owner's design adds is not expression but **carriage**: the application holds the place as an instance the host produced, and what crosses to the driver is that instance's address ([The sharpest instance](#the-sharpest-instance-one-module-on-both-sides)). **The honest summary is that widening the concept to bindings widens what a program may *declare about* and *hold*, while what a program may *say about where a place is* stays inexpressible** — a place can be used and handed over and never mentioned. A facility that takes a callback cannot be reached faithfully either: the sources' own `Beep` takes one ([`element-status.kh:86`](../../../modules-plugable/computer/ui/gui/protocol/element-status.kh)), the language admits a method in an argument position and states no spelling for one ([Method in Khayyam → Type-level arguments](../../../docs/khayyam/method.md#type-level-arguments-for-sc-and-mt)), and the probe written against that silence is refused with `unbound-type-name` ([`bootstrap/behaviour.kh:15`](../../../bundles/khayyam/targets/js/bootstrap/behaviour.kh)). A facility whose arguments are values cannot be called, because nothing produces values yet. A provision whose owner is a method cannot be written until the language says what such a declaration asks for. And a party that is not there has no defined outcome, so the design gains the ability to ask and not yet the ability to be told no.

**Gained.** Five things become expressible that are not today. **A shared place becomes holdable and shareable without a single new grammatical form**, on the terms the owner's design sets — the host produces the instance, the application initializes it through the capsule's own method, and the address crosses as a value a call carries — which retires this document's own sharpest negative finding as it stood. **The dependence on the other party becomes part of this repository's definition** rather than a comment over archived source — the shape [`modules/computer/type/protocol/type.kh:41`](../type/protocol/type.kh) records and the sources mark as a thought the architect moved on from. **The dependence becomes scoped**: a party that renames or drops something is a change in one binding unit, and a reader can find which declaration it broke, because the correspondence is one declaration rather than a spelling coincidence across many. **The dependence becomes checkable**: a crossing with no recorded declaration, and a declaration with no crossing, are two states a tool can report, where today nothing here can report either. And **the concern becomes party-independent by construction**: the same shape serves a `wasm`, `c`, or `asm` host, a Web API, or a driver, because the other party's key is outside the language's namespace and no declaration changes when the party does.

The measurement that says the first instance is needed rather than optional is in this toolchain's own bootstrap: [`character.kh:19`](../../../bundles/khayyam/targets/js/bootstrap/character.kh) declares `tp CharacterAt mt (self Text) (at Count) (character Character)` with no body, so the probe compiles and the answer is that the only route to a character is a provision with no body. A self-hosting compiler reads the characters of its own input, so its single largest dependence on its environment is exactly a binding.

### The names to use and the names to refuse
**Use `Binding`** for the agreement. It is the owner's word, and it names a correspondence between two declared things without promising a copy or a conversion. **Record the collision `Binding` does have**, and carry it as a naming decision: [Type → Type and Relations](../../../docs/type.md#type-and-relations) at `:196` uses "receiver binding" for the relation by which a Method attaches to its owner, which is a different relation. Two referents for one word is the failure the owner's own rule names, so the model states it rather than resolving it by assertion.

**Use `Party`** for either side, and never `Host` for it. The three existing owners of `Host` in this repository are recorded under [Party](#party).

**Use `Crossing`** for what the agreement is about, and its three kinds as kinds rather than concepts: *route*, *shape*, *place*. **Refuse `Binding Kind`, `Crossing Type`, and `Binding Mode`** for the same reason the kinds are loop-edges: each would name a classification the model already carries and each would be a node without rules.

**Use `Binding Declaration`** for what one party writes, and use the repository's word *companion* when speaking of the file rather than the concept. **Refuse `Side file` as a term of art** — "side" appears nowhere in this repository's documentation or sources for this purpose, while "companion" is the repository's word twice over ([Documentation → File Naming](../../../modules-plugable/knowledge/documentation/documentation.md#file-naming) and [the file-layout rule](../../../bundles/khayyam/rules/file-layout/file-layout.md)).

**Refuse `Path`, `Route`, `Handle`, and `Address` for the Counterpart Address**, and use the compound. `Path` is already this repository's word for a different and heavily-owned thing — [`modules/computer/module/protocol/path.kh`](../module/protocol/path.kh) — and a path is text, which no program can write. `Route` is [Chapar's](../../net/chapar/chapar.md) word for a forwarding path through a network, and `Handle` is the sources' word for a capsule *field* ([`docs/khayyam/polymorphism.md:162`](../../../docs/khayyam/polymorphism.md) writes `tp FileReader cp { handle FileHandle }`), which is precisely the thing [Type → What Is Not a Type](../../../docs/type.md#what-is-not-a-type) at `:78` rules is not a Type. `Address` is refused on the relation it would duplicate, for the reason given under the concept.

**Refuse `FFI` as a Memar term and as the facet key**, on the ground in full under [Foreign Function Interface](#foreign-function-interface). The shape `<base>.<facet>.kh` is right and precedented twice; **the facet key is `bindings`**, plural, following the `observers`/`mutators` precedent the same sources write, and the drafted rule carries it.

**Refuse every party's own name as a Khayyam method name**, `Beep` being the owner's example. This is also the sources' problem: [`modules-plugable/computer/ui/gui/protocol/element.kh:166`](../../../modules-plugable/computer/ui/gui/protocol/element.kh) writes `//     HTMLAudioElement.Beep(400, 100, 5)` in a block marked archived memar-js JavaScript, and the same call appears again at `:214`, `:338`, `:386`, `:470`, and `:632`; [`modules/process/error/protocol/error.kh:116`](../../process/error/protocol/error.kh) and `:311` carry the owner's example verbatim. Nine occurrences, zero declarations. Since the language sentence was withdrawn, the rule that would forbid this is a governance question for this repository's rules catalog rather than a language claim, and it is carried as an open question.

**Refuse `Literal` for whatever a binding declaration is given** ([Khayyam → Separation of Syntax and Governance](../../../docs/khayyam/khayyam.md#separation-of-syntax-and-governance-a-principle) uses the word for the thing the language refuses) and **refuse `Slot`** as a concept name, because it belongs to one target's reading and the language's word is *variable*.

**Refuse `JS`** as a name for anything here, while keeping the owner's freedom to name a library as its author chooses; [Documentation → File Naming](../../../modules-plugable/knowledge/documentation/documentation.md#file-naming) requires a name to avoid implementation-specific vocabulary for a party-independent responsibility, and [`bundles/khayyam/README.md:21`](../../../bundles/khayyam/README.md) already plans four targets.

### Implications
- **The per-language split is not a documentation convenience; it is the only shape that survives the ruling.** Because the language is silent on reaching a foreign function, anything stated once for all languages would be a claim about one organization's modules written where it has no standing. The six language-level statements in this model are all statements about what a program may *mean*, and every one of them would still be true if the second target's key were a triple instead of a pair.
- **A shared place is the concept's real frontier, and it is a place-shaped hole rather than a missing binding — but the owner's design narrows the hole to one thing.** Two of the three instances need only what already exists — a provision, or a provision plus a text library. The third needs a value the language cannot make, under a rule that forbids a shared contract naming a concrete instance, and the design answers it by having the host make that value and by exchanging it rather than naming it. What remains open is not whether a program can *have* a place — on this design it can — but whether anything may be *said* about where one is, and whether a wrapper capsule's provisioned operations are the whole of what a place admits.
- **The owner's design is the first place this repository states that a crossing's two halves are one artifact rather than two statements, and that is a heavier obligation than the model's own vocabulary was built for.** A Binding holds because both parties stated it; the driver–application binding holds because both parties *include* the same unit and both then hold the same instance. The vocabulary separation survives it — one declaration included twice is not two claims on one spelling — and so does the model's sharpest exclusion, now for a structural reason rather than one of emphasis: with no umbrella, the guarantee that a party cannot appoint itself is a term on the declaration it would be appointed to, so admission is not a party and therefore not a **Mediator**. What the model no longer carries is the claim it used to close that topic with — that the guarantee is named three times over in the OS document and never once stated as an introduction ([Each party is a module of an existing category](#each-party-is-a-module-of-an-existing-category-and-there-is-no-umbrella)). That claim was true of the OS document and it was the wrong warrant, and the OS document had already said so itself at `os.md:41` and `:117`.
- **Widening the binding from an agreement about a subject to an agreement about a behaviour is the change that makes the sharpest instance writable at all.** A route crossing inherits its method from the far side's signature; a place crossing inherits nothing, so without an agreed behaviour there is nothing for the two sides to hold in common beyond which bytes are shared — and the design's concurrency requirement would then be a private choice of each party. The cost is that every requirement of a place crossing must now be *stated*, and the benefit is that each one can be placed: a declaration where a party can check it alone, a provision where only an arrival is evidence, a term where the other party must be told, and an open question where nothing owns it.
- **The two new requirements of the design are the two the language cannot help with, and one of them is the design's own undoing.** Atomicity is expressible as a declared method and guarantees nothing the language can see; and the resizing requirement collides with the design's central property, because a resize that moves the region invalidates the very address whose exchange makes the design worth having. The collision is the owner's own and needs no witness in this repository: the same account that hands the driver the capsule's address asks for a buffer that may be grown or shrunk. An earlier form of this bullet cited two `.kh` comments for it — one saying a zero-copy buffer "can't be resized", one describing a circular buffer as "a single, fixed-size buffer" — as though the sources had noticed the trade-off and settled it; that citation is withdrawn, because those two comments are about two different kinds of buffer and are not in tension, and because the code under `modules/**` is residue of an attempt that failed and the owner has ruled it neither evidence nor a premise. The owner has asked for both requirements; this model records that the second has to be answered before the first is worth anything, and does not answer it.
- **The obligation that leaves the language is the one that keeps the design honest.** "Both must have the same module" is what makes the driver's calls land on the capsule side of [abstraction.md:100](../../../docs/khayyam/abstraction.md#what-you-cannot-do) rather than the abstraction side, and nothing in any language document can hold a target to it: only a link- and build-time check can, and where that check lives is a tool's decision ([`khayyam.md:177`](../../../docs/khayyam/khayyam.md#minimal-legislation-a-principle)). A design whose sharpest requirement is unenforceable by the language is a design whose correctness is a property of the organization's build, and that should be said where the requirement is stated rather than discovered when a second target links it differently.
- **The vocabulary separation costs the other party a naming obligation it does not have today, and that is the price of the honesty.** A party that today offers `HTMLAudioElement.Beep` for free would have to, for every crossing a program may reach, publish a declaration under this repository's naming rules, state its arguments in this repository's types, say whether it can fail, and supply what arrives keyed by the declaring unit's URI. And a program, which today depends on nothing it can see, would depend on a named set — so a party that renames something becomes a change in this repository's source. The gain is that the dependence becomes a declaration and a checkable record; the price is that it is now visible and now binds.
- **One companion file per reaching party is what makes the correspondence recoverable at all.** The key is a pair and a pair's first half is the unit; a single shared unit would key every crossing at one URI and leave the correspondence to be recovered from exported names alone, which is a spelling coincidence of exactly the kind the separation exists to remove.
- **A binding unit is the one place in this repository where a unit may be replaced without touching this repository's own source, and the 51 conversions are the sources' proof that the boundary is currently nowhere.** A unit the map stands in for must contain nothing that is not replaceable; the conversions sit inside units whose own content matters, which is the same reason they cannot be links and the same reason their provisions go unfilled.
- **This repository has already tried the shape the widening rejects, and archived it.** [`modules/computer/type/protocol/type.kh:41`](../type/protocol/type.kh) carries the archived README's line "`Memar` as a `JS language library` is a repository wrapper to store all implementation", `:48` carries "call `Application.Start()`", and `:49` carries "Use `OS` and `Application` global object data any where like `window`" — a library named for the host's language whose globals a program reaches by name, held under the same "kept as a thought only" marker at `:34`. The widening is not a new direction in this repository; it is the correction of one this repository already tried.

### Open questions
Each question below names its kind, what it blocks, and what would close it. The full record of each — state, what a ruling must decide, and the path — is in the paired [handoff](./binding.handoff.md).

1. **Is a body-less method whose owner is a method the provision form or the contract form?** — *language decision.* Blocks: every binding under the owner's design, since the shape has a method owner and no sentence in the language says what such a declaration means. Closes: a sentence in [Khayyam → Method](../../../docs/khayyam/khayyam.md#method) and [Method in Khayyam](../../../docs/khayyam/method.md#body-less-methods-ffi-and-contracts), which the target's three-way classification would then have to gain a case for.
2. **What, if anything, may a provision write into its influenced group, and may its execution fail?** — *language decision.* Blocks: every binding signature and the answer to whether a Counterpart Address is a value. Closes: [Method in Khayyam → Influencing and Influenced Variables](../../../docs/khayyam/method.md#influencing-and-influenced-variables-not-inputs-and-outputs) or [Variable in Khayyam → Overview](../../../docs/khayyam/variable.md#overview), then [The Error](../../process/error/error.md) for the class.
3. **May a program hold a place, and what may a capsule wrapping one declare?** — *language decision.* Blocks: the third instance's library, and whether the wrapper is per crossing kind or per crossing. Narrowed by the owner's design, which shows a program need never *name* a place: what crosses is an address the host produced, carried by a call. Closes: a decision that the wrapper capsule's provisioned operations are the whole of what a place admits; putting the wrapper behind an abstraction instead collides with [Abstraction in Khayyam → What You Cannot Do](../../../docs/khayyam/abstraction.md#what-you-cannot-do) and the sibling model at [`construction/construction.md:154`](../../process/construction/construction.md).
4. **What is the criterion for a Crossing's kind?** — *language decision.* Blocks: any rule that would check a declaration against the kind of crossing it stands for, and any enumeration of kinds beyond the three this model names. Closes: a sentence stating what a crossing *is* such that the three kinds fall out of it.
5. **Who owns the rule that a party which is absent is a failure?** — *protocol decision.* Blocks: any claim that binding is safe to write. Closes: a topic in [Runtime](../runtime/runtime.md), which already owns the environment; [Language Gaps → I-J](../../../bundles/khayyam/targets/js/language-gaps.md#i-j--where-the-rule-about-a-facility-the-environment-does-not-offer-belongs) carries drafted text for it.
6. **Should Provisioning be restated to cover an arrival of execution and an arrival of data, not only of a value?** — *protocol decision.* Blocks: this model's use of the name across three instances where two of them arrive nothing. Closes: the owner of [`modules/process/construction/`](../../process/construction/), whose wording at `:68` is scoped to a construction.
7. **Is a Web API one binding or a binding per operation?** — *protocol decision.* Blocks: the second instance's model, and whether its declarations are per-operation or per-service. Closes: a topic in [Runtime](../runtime/runtime.md) or in the networking protocols, stating what a service is relative to a crossing.
8. **What document does a binding unit's link-map entry record its check against?** — *protocol decision.* Blocks: any entry for a binding unit, because an entry must name a protocol document and record each check at a section it has. Closes: a decision that this model's own document serves, or a protocol document written for the correspondence.
9. **Does the toolchain check that a binding declaration is in a unit that says so, and by what?** — *toolchain decision.* Blocks: nothing in the model; it decides whether the layout convention can ever become a check rather than a convention. Closes: an owner ruling on the drafted rule's enforcement, between governance and a compile gate.
10. **Does the link map hold an entry for a binding unit at all, given that the party is not a repository-readable module?** — *toolchain decision.* Blocks: the structural half of the discrimination between a binding and a conversion. Closes: either a conformant implementation in this repository, which is what [the target records at `:75`](../../../bundles/khayyam/targets/js/target.md#the-link-phase) as the map's reason to exist, or a decision that a party outside the repository is answered only at `EntryRequest.supplied`.
11. **Does the display contract gain a role for a binding declaration?** — *toolchain decision.* Blocks: nothing; it is a consequence. Closes: the owner of [`bundles/khayyam/display/`](../../../bundles/khayyam/display/), noting that the withdrawn sentence leaves the role resting on the body-less spelling alone.
12. **May a party's own name appear in a `.kh` source at all — in an identifier, a URI, or a comment?** — *naming decision.* Blocks: the first binding's record, which must state the correspondence and may need to name the far side to be checkable. Closes: a ruling in this repository's rules catalog, since the language sentence that would have settled it was withdrawn and the toolchain's classifier sorts declarations by the owner's kind rather than by a name's spelling.
13. **What is the binding abstraction's `.kh` spelling?** — *naming decision.* Blocks: the first abstraction declaration. Closes: the owner, under [Modularity in Khayyam → Naming Without Package Context](../../../docs/khayyam/modularity.md#naming-without-package-context) and [the qualified-names rule](../../../bundles/khayyam/rules/qualified-names/qualified-names.md).
14. **What is a binding method's name?** — *naming decision.* Blocks: the first binding. Closes: the owner, subject to three requirements: it must not be the party's own method name, it must not collide with a method this repository will write, and it must say that the call leaves this repository.
15. **Does `Binding` collide with `receiver binding`?** — *naming decision.* Blocks: nothing, and it is recorded because the owner's own rule forbids one name for two things. Closes: the owner of [`docs/type.md`](../../../docs/type.md), choosing between accepting the collision on the grounds that both uses are the ordinary sense of tying one declared thing to another, and renaming one of them — most likely the relation at [`type.md:196`](../../../docs/type.md), which is a cell in a table rather than a declared concept of its own.
16. **Who may call an instance's initialization, and may the holder of an instance be someone other than the party that obtained it?** — *language decision.* Blocks: the driver–application design's coherence, since the driver holds the application's instance and must not initialize it. Nothing states the rule and the sources' exclusion of `Init` from the shared lifecycle contract ([`life_cycle_contract.kh:6-9`](../capsule/protocol/life_cycle_contract.kh)) makes it *implied* rather than absent. Closes: a sentence in [Variable in Khayyam → Overview](../../../docs/khayyam/variable.md#overview) or the construction model, or a ruling that initialization is a method of the capsule and any holder may call it — in which case the driver's copy of the module is a hazard the design has to answer some other way.
17. **Is admission a term of a crossing, and whose declaration states it?** — *protocol decision.* Blocks: the relation this document now carries, which replaced an introducer with the crossing's own declarations and therefore assumes that admission is something a declaration can state. With the umbrella refused there is no document that owns the question, and the candidates are categories rather than one: `Authorization`'s `LimitToUseBy` in `modules/computer/capsule/`, `OnPresent`/`OnAbsent` in `modules/computer/adt/`, or a term of the crossing under [Memory → Copy and ownership semantics are contract members](../memory/memory.md#copy-and-ownership-semantics-are-contract-members). Closes: a document stating what admission conveys and where it is written.
18. **What follows where a party is admitted wrongly, or where the admitting declaration is gone?** — *protocol decision.* Blocks: any claim that a binding is safe to write. Whether an introducer is a **Mediator** is no longer the question — the owner's refusal of the umbrella removed the party, and the relation now concerns only who may reach a crossing two parties have already stated — so what is open is the failure case rather than the classification. Closes: the same document as 17, stating what a party does when it finds itself admitted to something it may not use, or holding an address to a region that is no longer the crossing.
19. **Is "the same module on both sides" checkable, and by what?** — *toolchain decision.* Blocks: the design's central property, which a target loses silently by linking a separate build to the driver, and the indivisibility of a release as well, since that guarantee rides on the same artifact. Closes: an owner ruling that a link or build step records which artifact each side received, and what a mismatch reports. The language has nothing to say: it admits the unit being included by both and admits a target linking what it likes ([compiler.md:33](../compiler/compiler.md#the-compiler-recognizes-language-primitives-not-library-names)).
20. **What is the wrapper capsule that carries a place called, and is its declaration shared by both parties?** — *naming decision.* Blocks: the first place-crossing library. Closes: the owner, under [Modularity in Khayyam → Naming Without Package Context](../../../docs/khayyam/modularity.md#naming-without-package-context) and [the qualified-names rule](../../../bundles/khayyam/rules/qualified-names/qualified-names.md); the sharing requirement follows from the module's, since the wrapper is one of its declarations. `Address`, `Handle`, and `Pointer` are each already refused or owned elsewhere in this document and this repository.
21. **Is a driver a party of the same kind as an application, and does `modules/computer/driver/` hold that kind?** — *naming decision.* Blocks: the vocabulary the design is written in, now that categories rather than an operating system carry the parties. Closes: the owner, and it is the owner's statement rather than this model's that the categories are not final — [`modules/README.md:11`](../../../README.md) says no folder here is final and that names may be merged, split, moved, or retired, so an answer given today is a reading and not a placement.
22. **May a place crossing's size change while the crossing is live, and what happens to the address the other side holds?** — *protocol decision.* Blocks: the third instance's library, and with it whether the design's central property and the owner's resizing requirement can both hold ([Resizing](#resizing-what-the-agreement-must-carry-about-the-places-size)). Closes: a term stating whether a resize may move the region, whether the other party is re-told, and what it may assume in the interval — the three answers this model sets out without choosing among them.
23. **Is the indivisibility of a release a term of the crossing, a provisioned method, or a configured posture?** — *protocol decision.* Blocks: whatever a crossing's terms say about the release, which is the one requirement of the design that nothing can check on behalf of the party that depends on it. The owner has ruled the second of the three: the indivisibility is a **provisioned method of the buffer module**, which obtains it from [Synchronization Model](../../process/sync/sync.md), per [The execution method](#the-execution-method-an-atomic-head-or-tail). Closes: a decision whether the crossing **also** states the requirement as a term of its own, and whether the guarantee is described as a property of the design or as a governance posture an organization configures ([`memory.md:85`](../memory/memory.md#safety-enforcement-is-governance)) — in which case the agreement may state it and never guarantee it.
24. **Which document owns a place crossing's contract terms?** — *protocol decision.* Blocks: where "the head is advanced atomically", "the portion is valid until the head is advanced", and "the size may change" are written, and therefore whether they are ever written at all. A fourth term is now owed beside the three: that the application's writes to a portion are visible to the driver before the driver observes the advanced head, which [Synchronization Model → Sequencing](../../process/sync/sync.md#sequencing) models as a second guarantee rather than a property of the first, and which no document states. Closes: a ruling assigning them, with [Memory → Copy and ownership semantics are contract members](../memory/memory.md#copy-and-ownership-semantics-are-contract-members) the obvious candidate and this model holding none of them.
25. **Do "atomic" in the language's syntactic sense and "atomic" as an indivisible operation need to be told apart in the language's own vocabulary?** — *naming decision.* Blocks: nothing structurally; [Khayyam → Syntactic Atomicity and Semantic Clarity](../../../docs/khayyam/khayyam.md#syntactic-atomicity-and-semantic-clarity) at `:234` uses the word of grammar while every concurrency document and the owner's own sentence use it of indivisibility, and a reader following one into the other finds a principle about syntax. Closes: the owner of [`docs/khayyam/`](../../../docs/khayyam/), which is outside this model's allowance.
