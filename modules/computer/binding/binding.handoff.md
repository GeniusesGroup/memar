# Binding Model Handoff
Open work for [binding.md](./binding.md). Entries are mutable current state — revised as each item moves, removed when it resolves or is dropped. Every open question below names the file and the section it can be read at, so a session that starts cold can go straight to it. See the repository's [documentation-handoff.md](../../../modules-plugable/knowledge/documentation/handoff/handoff.md) for what a handoff is.

## Topic & Purpose
The model of **binding** — an agreement two parties hold about something, with no third party introducing it — under the owner's widened decision: the concern is not a host interface but bindings generally, `ffi` is limiting because it refers only to a function, and for each language the abstraction and the developer's declaration must be stated separately. Since the last revision it also carries the owner's account of how the sharpest instance actually works — the driver and the application as two parties running **one module**, whose capsule's **address** is what crosses, whose initialization is the application's own named method — and the three decisions taken since: that what the two parties agree about is a **behaviour** rather than code, with an **execution method** beside the subject; that a head or tail is released **atomically** and the buffer's size may change; and that each party is a module of a category this repository already has, with **no umbrella** standing over them. The model names the concepts, their boundaries, their relations, the names, the three instances with what each costs the language, the seven points of that design with what each costs and which of the three levels each belongs to, and the split between what is language-level, what is per-target, and what is protocol-level. It settles no signature, no declaration form, and no per-target implementation, because each of those turns on a question carried below rather than on one this session answered.

## Decisions
- **What the two parties agree about is a behaviour, and never a code** — Decided, and the largest change this model has taken since the widening. The owner's words: "Both parties must agree on an **execution method**, because without an agreement concurrency cannot be implemented — both sides must know what the other side does … So the idea of the same library is **not that the code is literally the same, but that the behaviour is the same.** This sameness of behaviour can come with small changes, but not as **breaking changes.**" Two findings. **A route crossing inherits its method** from the far side's signature; **a place crossing inherits nothing**, because a region has no signature — so the method is part of what is agreed rather than a detail either party may choose, and the subject of a place agreement is no longer only *which* region is shared but *what each party may assume the other does to it*. And **"no breaking changes" cannot mean a commitment here**, because a commitment is enforced by somebody and this agreement has no third party: where both sides run the same artifact it is a fact of the deployment (both change at once, and a link step checks it), and where they do not it becomes a publish obligation the far party carries. The model adds one test to decide every term: **a term of a binding is worth stating only if one party can check it without the other's cooperation.**
- **The repository's concept for an agreement between parties is Contract, and it is close but not the same** — Decided. [Agency → Contracts](../../../docs/agency.md#contracts) at `:1006` defines a Contract as a structure "establishing expectations between participants … responsibility, authority, obligations, constraints, expected outcomes, acceptance criteria, failure conditions, and escalation procedures", glossary at `:2007`. Three distinctions on the evidence: a Contract has **escalation procedures** and this agreement has nobody to escalate to; a Contract sits inside an agentive relationship with a **Principal** ([Agency → Trust](../../../docs/agency.md#trust)), while two independent parties hold this between themselves; and a Contract may define **obligations**, which are duties one party may fail, while a binding's test admits no term one party cannot verify alone. The repository had already drawn the neighbouring line from the other side twice: [Protocol → Protocol vs Contract](../../../docs/protocol.md#protocol-vs-contract) and [`abstraction.md:45`](../../../docs/khayyam/abstraction.md#what-is-an-abstraction-in-khayyam) ("not a contract: it creates no parties, no reciprocal obligations, and no commitments"). **Rejected:** modelling this as a Protocol, which that document defines as one-sided and requiring no negotiation — the opposite of the property the owner stated; and treating Contract as the same concept, which would import a principal and an enforcement path the design has neither of.
- **An atomic release is expressible today as a declared method and as nothing else** — Decided. The language embeds no concurrency model ([`khayyam/agency.md:13`](../../../docs/khayyam/agency.md), `:39`), places concurrency safety with "a rule or a tool's check rather than by the grammar" (`:44`), and [Memory → Safety enforcement is governance](../memory/memory.md#safety-enforcement-is-governance) at `:85` puts data races among relaxable governance. [Concurrency Realization](../concurrency/concurrency.md) says nothing about atomicity and its one load-bearing rule — channels are signals, not stores (`:32`–`:39`) — bears on the ring directly. **What it costs:** the guarantee is the same on both sides only because both run the same module (nothing checks that), it fails the checkability test above, and it is relaxable by configuration — so an agreement can state it and never guarantee it. **Recorded collision:** [Khayyam → Syntactic Atomicity and Semantic Clarity](../../../docs/khayyam/khayyam.md#syntactic-atomicity-and-semantic-clarity) at `:233` uses *atomic* of syntax, so the word means two things across the documents this model reads. **Re-grounded 2026-10-03.** An earlier form of this entry also reported what the sources declare at [`atomic.kh:7`](../adt/hash_table/protocol/atomic.kh)–`:15` — `HashTable_AtomicAccessor` with `Load`/`Store`/`Swap`/`CompareAndSwap`, all body-less and unimplemented, with the realizations behind it in [`thread-status.kh`](../runtime/scheduler/thread-status.kh) and [`thread-yield.kh`](../runtime/scheduler/thread-yield.kh) — and cited that unimplementedness as the reason the answer is "a declared method and nothing else". The citation is withdrawn: an unimplemented declaration in the residue of the failed Go attempt shows what the sources do, not what the language admits. The answer now rests on the four documents named above, which is sufficient on their own, and the `.kh` lines are kept as a record of the repository's state.
- **The indivisibility of a release is a method of the buffer module, and the order is a second requirement the owner's sentence does not carry** — Decided, as the owner's ruling recorded and as this model's addition to it. The owner: atomicity is carried by "a method of the buffer module, using a module similar to Go's `sync`", and the synchronisation module itself may be generated. **Where the decision is recorded:** [binding.md → The execution method](./binding.md#the-execution-method-an-atomic-head-or-tail), the abstract, the categories list under [Each party is a module of an existing category](./binding.md#each-party-is-a-module-of-an-existing-category-and-there-is-no-umbrella), and question 23 below. **What the ruling settles:** the indivisibility is one of the three candidates question 23 named — a provisioned method rather than a term of the crossing or a configured posture — and its receiver is a capsule, which is what makes it writable at all, since [abstraction.md:100](../../../docs/khayyam/abstraction.md#what-you-cannot-do) would forbid an abstraction-owned signature to name the region. **What the model adds:** that indivisibility alone does not free the region. The driver must also observe the application's earlier writes to the portion, so a release that is indivisible and unordered lets the driver refill bytes the application was still writing. That is the second guarantee in [Synchronization Model → Sequencing](../../process/sync/sync.md#sequencing), and nothing in this repository states it — which adds a fourth term to the three question 24 already owes. **What it costs:** one more module both sides must include for the guarantee to be the same on both, so question 19's silent-loss risk now rides on two artifacts rather than one, and one more declaration outside this folder. **What it awaits:** the protocol that would state the guarantee — [concurrency.md:11](../concurrency/concurrency.md) claims to cover the synchronization primitives its body never names — and a ruling on question 24.
- **Resizing is expressible only as a declared capability, and it runs against the design's central property** — Decided, as a finding rather than as an answer. A size is not writable — no literal (`khayyam.md:162`), no primitive types (`:206`), no construction form — and what a source may therefore say is the declaration of a resize and nothing about how large. **The cost:** resizing and the design's central property are two names for what happens to the address the driver holds, and the collision is the owner's own rather than the sources': the account that hands the driver the capsule's address is the same account that requires the buffer to be grown or shrunk. Three answers are set out (the region never moves and the grant is renegotiated; the region moves and the driver is re-told; the address becomes an indirection) and **the model chooses none of them**, because the choice is the owner's. **Re-grounded 2026-10-03.** This entry previously read the trade-off out of two `.kh` comments — [`zero-copy/buffer.kh:7`](../buffer/zero-copy/buffer.kh) "it can't be resized!" against [`circular/buffer.kh:7`](../buffer/circular/buffer.kh) "a single, **fixed-size** buffer" — and treated the sources' declared resize shape at [`resize.kh:7`](../adt/container/protocol/resize.kh)–`:16` and its measure at [`length.kh:15`](../adt/container/protocol/length.kh) as where the language's answer came from. All three citations are withdrawn as grounds. The two comments are also not in tension with each other — one is about a buffer that is zero-copy, the other about the buffer a circular one is built on — so the entry's "against" was an artefact of reading two descriptions of different things as one position. The code under `modules/**` is residue of an attempt that failed, and the owner has ruled it neither evidence nor a premise; the sources' declarations are kept in the model as record only.
- **Each party is a module of an existing category, and there is no umbrella** — Decided, replacing this model's reliance on the OS document. The owner: "Each module should do one thing and do it properly … We no longer need a big umbrella concept like `os`". The categories named are [`modules/computer/driver/`](../driver) (named by the owner; empty, which [`modules/README.md:10`](../../../README.md) makes a decision made visible), [`modules/computer/adt/`](../adt) and [`modules/computer/buffer/`](../buffer) for the application side, [`modules/computer/capsule/`](../capsule) for what both sides rely on — its [`authorization.kh:5`](../capsule/protocol/authorization.kh)–`:7` `Authorization`/`LimitToUseBy` is where "who may use this" now lives — and [`modules/computer/runtime/`](../runtime) for scheduling. **The categories are not settled and are recorded as the owner's statement, not as a decision:** [`modules/README.md:11`](../../../README.md) says no folder here is final and names may be merged, split, moved, or retired. **What became of the old claim:** this document no longer claims the guarantee is "named three times over" in the OS document. The OS document had already de-privileged the driver (`os.md:41` on the kernel as a layer concept, `:117` on a router as an application, `:121` naming the driver and stating this design's central property as its own finding), so the three names — entitlement, arbitration, principal — were the wrong warrant rather than a false claim; they are replaced by three smaller owners, the largest of which (admission) is a term on the crossing rather than a party.
- **The split has three buckets, and the third is now named** — Decided. The model had been recording claims as "neither" — the introduction duty, the live part of initialization — which is a third bucket wearing a refusal. It is named **protocol-level**: a claim owned by a document under [`docs/modules/`](../../), which the language is silent about, each target realizes, and an organization may configure differently. **Its test is not the coincidence test** the two buckets use (an identical key in a second target would be a coincidence rather than language-level) — a protocol-level claim is not moved by a second target stating it identically; **it is identified by who owns the statement**, and only the realization varies. The consequence for the design is that its two largest new requirements — atomicity and resizing — are protocol-level and per-target, and neither adds anything the language must say, which this model records as the sharpest evidence that the split is the right one. **Still open:** whether the three-bucket form should be stated as the model's method rather than as this revision's device.
- **The concept is Binding, and the folder was renamed `modules/computer/binding/`** — Decided. The owner's decision replaced the central shape: the previous subject was "how a program reaches a facility its host provides", which is one of three crossings, and a folder whose name covers one of three is a defect under [Modeling Practice → Single Responsibility Check](../../../docs/modeling.practice.md#single-responsibility-check) and [Terminology drift](../../../docs/modeling.practice.md#common-modeling-anti-patterns). The rule requiring the rename is [modules/README.md:11](../../../README.md) — "No folder here is final. Names may be merged, split, moved, or retired whenever the responsibility they name is better served another way" — together with that document's `:12`, that a folder without a README carries its intent in its name until one is written. The name chosen is the owner's word, and it is not an ecosystem's: `bindings` for the facet key, `Binding` for the concept. **What this cost and what was done about it:** the two files moved with the folder, so every relative link inside them still resolves; the links *into* the folder from other documents were repaired in the session that made the rename, and `model.md` became `binding.md` on the same day under [Documentation → File Naming](../../../modules-plugable/knowledge/documentation/documentation.md#file-naming).
- **The owner's account of the sharpest instance is carried as stated** — Decided, and the revision that opened the model's sharpest section; what the owner's later facts added to it is stated in the decisions above and not repeated here. The design: both sides run **exactly the same code** — identical at the level of implementation, not merely at the level of abstraction; on the app side that module is initialized and **the memory address of that capsule is given to the driver**, which hands it to the same module; on every call that module writes the corresponding data into the corresponding buffer, so data goes from hardware into the app's own memory without passing through any other party's memory; with no operating system standing over the two sides, "correctly introducing a driver as an app to the others". Four findings came out of working it against the documents, and each is recorded with its evidence in the model's own section rather than here. **The one module contradicts nothing** in [`docs/khayyam/abstraction.md`](../../../docs/khayyam/abstraction.md): its two refusals — no body in an abstraction at `:99` and `:142`, no default implementations — are about *an abstraction supplying behavior*, and this module supplies none. **What the design actually leans on is the concept/instance asymmetry** at `:107`–`:109`: an abstraction-owned signature may name only abstractions, a capsule-owned one may name a capsule, so two separate realizations would put the driver's calls on the abstraction side of a wall it cannot pass, while one implementation does not. **The identity of implementation is therefore load-bearing for expressibility, not a preference.** **The design avoids needing the language to name a place** — the address is never named, literal, or constructed, only exchanged as a value the host produced ([`target.md:70`](../../../bundles/khayyam/targets/js/target.md#running-a-program)) and carried by a call ([`method.md:39`](../../../docs/khayyam/method.md#key-rules)) — and it needs **no shared construction contract**, so [`construction.md:154`](../../process/construction/construction.md)'s wall is not hit: there is one construction, on the app side, and the driver constructs nothing. **What it costs**, recorded without softening: a wrapper capsule rather than an address ([`type.md:78`](../../../docs/type.md#what-is-not-a-type)), every operation on the place being a provisioned method, and that wrapper's declaration being part of the module's — and *not* a copy, which is the point. **`init` is Initialization** in the construction model's sense ([`construction.md`'s concept](../../process/construction/construction.md#initialization)), ruled by the sources to be the capsule's own named method ([`life_cycle_contract.kh:6-9`](../capsule/protocol/life_cycle_contract.kh)) and outside the grammar ([`compiler.md:41`](../compiler/compiler.md#entry-and-lifecycle-are-not-grammar)), which is why the driver must not call it on an instance it does not own. **The OS's supervising role is not a concept this repository has**: the guarantee under it is named three times — entitlement ([`os.md:93`](../os/os.md#decomposing-the-os-without-presupposition)), exclusive-access arbitration (`:117`), and principal ([Identity](../os/os.md#identity-principals-not-users)) — the nearest existing *introduction* is a network coordinator's ([`chapar.md:76`](../../net/chapar/chapar.md), [`networking.md:141`](../../net/net.md)), and "supervision" is already Agency's word ([`agency.md:179`](../../../docs/agency.md), `:1200`). The model therefore adds **one relation and no node**: a Party is introduced to another by whoever holds the guarantees, never by itself. **Also found, and not this model's own**: [`os.md:121`](../os/os.md#networking-frame-delivery-not-communication-meaning) already states the owner's shape — packet data landing directly in the application's buffers from the NIC, "without the kernel copying it", and the kernel-mediated copy being "one implementation of the guarantee, not the guarantee itself". This repository had that conclusion at the guarantee layer before this model had it at the crossing layer.
- **Seven concepts named, seven refused, one attached** — Decided. **Binding** (the agreement), **Party** (either side, named by role rather than by what it is), **Crossing** (what the agreement is about), **Binding Declaration** (what one party writes), **Counterpart Address** (the key by which one party reaches the other, sometimes none), **Binding Unit** (the companion side file), and **Provisioning** (attached from the construction model). Refused: **Foreign Function Interface** (narrower than the subject, and one ecosystem's word); **Host Facility** (its name presumes the program/runtime asymmetry the widening removes); **Mediator** (the definition's own negative); **Registrar** (the same, and owned elsewhere); **Adaptor/Wrapper/Shim/Marshal/Bridge** (each names a translation and a binding performs none); **Path/Route/Handle/Address** (each already owned in this repository, and a path is text no program can write). The three crossings — route, shape, place — are carried as loop-edge classifications of Crossing, not nodes, because none of them carries rules no other concern owns.
- **The separation of the two vocabularies is structural, and its ground changed** — Decided, and this is the finding most changed by the owner's ruling. The previous shape rested the separation on a drafted language sentence and carried "who owns the name of a provision" as its first open question, blocking everything. That sentence was **withdrawn rather than deferred** ([Language Gaps → I-B](../../../bundles/khayyam/targets/js/language-gaps.md#i-b--whose-name-a-body-less-method-carries--withdrawn-by-the-owners-ruling) at `:76-83`), on the ground that how a foreign function is reached "depends on each organization's own modules". So the separation now rests on two keyspaces and nothing else: the program's name is a name in the language, while the other party's name is the `(declaring URI, exported name)` key of a supply table the host fills ([`run.ts:32-34`](../../../bundles/khayyam/targets/js/src/run.ts)), the loader is given a URI and not told which it is ([`run.ts:6-9`](../../../bundles/khayyam/targets/js/src/run.ts)), and an implementation is handed to the unit that declares it ([`run.ts:18-19`](../../../bundles/khayyam/targets/js/src/run.ts)). A collision between the two vocabularies is therefore unexpressible rather than forbidden, and that holds for all three crossings — a Web API's far name is a URL and a media type, neither writable in a source, and a shared place has no name at all. **What the withdrawal leaves:** a rule may require only that the correspondence be *recorded*, and the drafted [binding-declarations rule](../../../bundles/khayyam/rules/binding-declarations/binding-declarations.md) is exactly that half.
- **A shared place is not expressible in a source today, and the owner's design works around three of the four negations without removing any** — Decided, and narrowed by the design rather than overturned by it. Four language facts still decide it: no primitive types ([Khayyam → Type Principles Realized](../../../docs/khayyam/khayyam.md#type-principles-realized)), no literal ([Khayyam → Separation of Syntax and Governance](../../../docs/khayyam/khayyam.md#separation-of-syntax-and-governance-a-principle) at `:162`), no construction form ([The JavaScript target → Running a program](../../../bundles/khayyam/targets/js/target.md#running-a-program)), and an abstraction's signature may name only abstractions ([Abstraction in Khayyam → What You Cannot Do](../../../docs/khayyam/abstraction.md#what-you-cannot-do) at `:101`) while a construction's result is a concrete instance ([`construction/construction.md:154`](../../process/construction/construction.md)). **What changed:** the model used to record the place as neither holdable nor nameable and to call the shared place the concept's frontier on that ground. It is holdable on the terms the design sets — the host produces the instance, the application initializes it through the capsule's own method, and the address crosses as a value a call carries — and what remains inexpressible is any statement of *where* a place is. **What did not change:** every negation stands, no grammar grows, and the model's own vocabulary still refuses `Address`, `Handle`, and `Pointer` for the wrapper. Rejected: keeping the third instance out of the model because the language cannot express it, which is the narrowing the owner's decision forbids; and reporting the design as making a place expressible, which would be false — it makes a place *carriable*.
- **What is language-level and what is per-target is a real structural claim, with a stated test** — Decided. Language-level: six statements, none of which mentions a target — the body-less form and its two documented uses, that a method may be attached to any type including a method, that an abstraction's signature may name only abstractions while a capsule-owned one may name a capsule, that satisfaction is structural with the receiver the implementer, that every variable of a call passes by reference, and the absence of primitive types, literals, and construction forms. Per-target: the key by which a party is reached, how an implementation arrives, how a variable is realized, whether a binding unit is in the link map, and what a body's absence is classified by. The test: if a second target's key were the *same* pair rather than a different one, that would not make the statement language-level — it would make it a coincidence between two tools, and a coincidence is what [Khayyam → Minimal Legislation](../../../docs/khayyam/khayyam.md#minimal-legislation-a-principle) exists to refuse.
- **The supplied reference covers the first instance and the reference itself excludes the other two** — Decided, after reading [Foreign function interface](https://en.wikipedia.org/wiki/Foreign_function_interface) in full rather than from memory. The page defines a mechanism by which a program in one language calls routines in another — this model's first instance — and its concerns are all concerns about a call. It places RPC, CORBA, SOAP, D-Bus and multi-lingual runtimes *outside* the term by its own statement, which is this model's second instance, and its own *Naming* section records that Java 22 has a "Foreign Function and Memory API", the nearest it comes to the third. Every mechanism the page describes has a third party that introduces it — a dynamic linker, a JVM, a resolver, a common substrate — which is the clause this model removes. So the coverage is exactly the owner's: this concept is a kind of what the page describes for the first crossing and is not a kind of it for the other two.
- **The file-layout convention is a rule, and it is drafted** — Decided. The owner's ruling is that the discriminator is the side file's name, on the ground that "a file should do one thing and not grow long carrying several". [Language Gaps → I-P](../../../bundles/khayyam/targets/js/language-gaps.md#i-p--what-tells-a-binding-from-an-ordinary-conversion) drafted that sentence for `target.md` and recorded the placement as unsettled between that document and [the file-layout rule](../../../bundles/khayyam/rules/file-layout/file-layout.md). This session drafted it as a rule in this repository's catalog at [`binding-declarations`](../../../bundles/khayyam/rules/binding-declarations/binding-declarations.md), with the facet key `bindings` the owner agreed and the refusal half deliberately left to an organization's Linter configuration. **Rejected:** adding the sentence to `target.md`, which belongs to another owner this session, and editing the catalog index, which the brief forbids.
- **`ffi` is refused as a Memar term and as the facet key; `bindings` is used** — Decided as the owner's ruling, which the model now follows rather than proposes. `ffi` refers only to a function, while a crossing may be a route, a shape, or a place; the reference places RPC and multi-lingual runtimes outside the term; it is one ecosystem's vocabulary for a party-independent concern that [`bundles/khayyam/README.md:21`](../../../bundles/khayyam/README.md) plans four of; and it is the language's word for the *form* rather than for what a form is used for, which the sources' 51 arithmetic conversions also are.
- **No `README.md` was written in either folder** — Decided. [Documentation Practice → Folder READMEs](../../../modules-plugable/knowledge/documentation/documentation.practice.md#folder-readmes) requires the README of a folder that has a main document to be a symbolic link to it, recorded as git mode `120000`; no git operation is permitted this session. Both new folders are recorded here instead, and the rule's handoff says what the catalog index would need.
- **The model is conceptual; no declaration was written and no implementation designed** — Decided, unchanged. Reason: [Modeling → Modeling Produces Conceptual Abstractions, Not Implementation Structures](../../../docs/modeling.md#modeling-produces-conceptual-abstractions-not-implementation-structures). Where the model names a declaration it says what the declaration must mean.

## Ambiguities Resolved
- **Whether one module may be both the abstraction and its own implementation** — Answered: yes, and nothing in the repository contradicts it. [`abstraction.md:100`](../../../docs/khayyam/abstraction.md#what-you-cannot-do) and `:143` refuse a body inside an abstraction and refuse default implementations; both are about an abstraction *supplying* behavior, and a module whose abstraction-owned declarations stay body-less supplies none. What the design adds is a reason the identity of the implementation matters: an abstraction-owned signature may not name a capsule ([`:101`](../../../docs/khayyam/abstraction.md#what-you-cannot-do)), so two implementations would put the driver's calls where a place cannot be named, and one implementation does not. The abstraction still does not supply anything; it stops being a substitution point *between these two parties*, which is a fact about them rather than about the abstraction.
- **Whether the design needs the language to name a place** — Answered: no, and this is the sharpest reading of it. The address is never named, literal, or constructed; it is **exchanged**, as a value the host produced and a call carries. What the language cannot do is unchanged, and the cost is a wrapper capsule whose operations are the only operations a place admits.
- **Whether the concept kept the name `Binding` or took a new one for the widened subject** — Answered: `Binding`, the owner's word, on the ground that it names a correspondence between two declared things without promising a copy or a conversion. What it collides with is recorded rather than resolved.
- **Which spelling declares a method body-less** — Answered by the language documents, not by this session. [Khayyam → Method](../../../docs/khayyam/khayyam.md#method) at `:89` and [Method in Khayyam](../../../docs/khayyam/method.md#body-less-methods-ffi-and-contracts) at `:77` both read that a method is body-less when nothing follows its third group, that a line ending with `{}` carries a body, and that an empty body is a body holding no command; [Abstraction in Khayyam](../../../docs/khayyam/abstraction.md#defining-an-abstraction) at `:59` and [Khayyam Practice](../../../docs/khayyam/khayyam.practice.md#abstraction-pure-behavioral-specification) at `:63` write the same shape, and [`parseBlock`](../../../bundles/khayyam/core/src/parse.ts) at `:219` reads it that way. So [`modules-plugable/computer/ui/gui/initialize.kh:6`](../../../modules-plugable/computer/ui/gui/initialize.kh) and [`modules-plugable/computer/ui/gui/navigator.kh:13`](../../../modules-plugable/computer/ui/gui/navigator.kh), `:18` are methods with empty bodies rather than provisions.
- **Whether the model's central claim survives the withdrawal** — Answered: yes, and it changed shape rather than failing. It was a claim that a sentence should exist; it is now a claim that two keyspaces already keep the vocabularies apart. The sentence is gone; the structural claim is stronger for being carried by the toolchain's own address.
- **Whether `Host` or `Runtime` names a party** — Answered by reading: `Runtime` for the environment as such, and no word at all for a party. `Host` has three owners here — the process that loads and runs an artifact, the display contract's editor and CSS at [`display.json`](../../../bundles/khayyam/display/display.json), and a URL authority at [`modules-plugable/computer/ui/gui/protocol/navigator.kh:173`](../../../modules-plugable/computer/ui/gui/navigator.kh).
- **Whether `Adaptor` is this concept under another name** — Answered: no. `ReadAdaptor` and `Stringer_GO` exist to *translate* a foreign signature, `Stringer_GO`'s own stated reason at [`stringer.kh:7`](../../../modules-plugable/computer/adaptors/String/stringer.kh) being the coupling a binding avoids by keeping the other party's name out of the declarations.

## Open Questions
### Is a body-less method whose owner is a method the provision form or the contract form?
- State: [Khayyam → Method](../../../docs/khayyam/khayyam.md#method) at `:91` and [Method in Khayyam](../../../docs/khayyam/method.md#body-less-methods-ffi-and-contracts) at `:80` scope the foreign-function case to a receiver that is a concrete capsule, and [the target](../../../bundles/khayyam/targets/js/target.md#the-three-kinds-of-body-less-method) sorts the two forms by the owner's kind. A method owner is neither. The language admits a method as an owner and makes a method the owner of its own methods ([Method in Khayyam](../../../docs/khayyam/method.md#a-method-implements-an-abstraction-by-methods-of-its-own) at `:74`), so the shape is grammatical and nothing says which meaning it carries. Of the sources' 728 body-less declarations, **none** has an `mt` owner.
- What a ruling must decide: whether a body-less method on a method owner asks of the link phase, as its capsule-owned counterpart does, or of an implementing type, as its abstraction-owned counterpart does — and what a toolchain does with one nobody answers.
- Blocks continuation: yes, for every binding under the owner's design, and it gives [the target's classification](../../../bundles/khayyam/targets/js/target.md#the-three-kinds-of-body-less-method) a fourth case.
- Path: the same two language documents, with [`target.md`](../../../bundles/khayyam/targets/js/target.md) and its owner informed.

### May a program hold a place, and what may a capsule wrapping one declare?
- State: narrowed by the owner's design, which shows a program need never *name* a place. Nothing states that it may hold one either, and the three negations mean no source can write a place down: no primitive types ([khayyam.md:206](../../../docs/khayyam/khayyam.md#type-principles-realized)), no literal ([:162](../../../docs/khayyam/khayyam.md#separation-of-syntax-and-governance-a-principle)), no construction form ([target.md:70](../../../bundles/khayyam/targets/js/target.md#running-a-program)), and no shared contract over a concrete instance ([abstraction.md:101](../../../docs/khayyam/abstraction.md#what-you-cannot-do); [`construction/construction.md:154`](../../process/construction/construction.md)). What the design adds is a **wrapper capsule** whose instance is the address, produced by the host — the sources' own pattern at [`application.kh:8-10`](../../../modules-plugable/computer/ui/gui/protocol/application.kh) — and whose every operation is provisioned. The sources' alternative answer today is a host-side file-level assignment, which is a third party introducing the crossing and is what the third instance excludes.
- What a ruling must decide: whether the wrapper capsule's provisioned operations are the *whole* of what a place admits, and whether its declaration is per crossing kind or per crossing. Putting the wrapper behind an abstraction collides with [abstraction.md:101](../../../docs/khayyam/abstraction.md#what-you-cannot-do) and the sibling model.
- Blocks continuation: yes, for the third instance's library — not for the design, which the model now records as workable, but for any declaration of it.
- Path: [`docs/khayyam/variable.md`](../../../docs/khayyam/variable.md) or [`docs/khayyam/abstraction.md`](../../../docs/khayyam/abstraction.md), with the construction model's owner.

### Who may call an instance's initialization?
- State: the owner's design initializes the module on the application side and hands the driver the address of the same instance. Nothing states that the driver must not initialize it. The sources have ruled that initialization is the capsule's own behavior through its own named methods ([`life_cycle_contract.kh:6-9`](../capsule/protocol/life_cycle_contract.kh)), and [`construction.md:128`](../../process/construction/construction.md#the-names-to-use-and-the-names-to-refuse) refuses `Init` as a shared name — so the rule is *implied* by a decision about names rather than stated as one about authority. The sources' own `Init` declarations ([`hash-table.kh:24`](../adt/hash_table/protocol/hash-table.kh), [`timer.kh:20`](../../time/timer/protocol/timer.kh)) are domain-specific methods on the holder.
- What a ruling must decide: whether initialization is a method any holder of an instance may call — in which case the driver, holding the application's instance, may call it, and the design has an unstated hazard at the moment the hardware begins writing — or whether it belongs to the party that obtained the instance, which the design needs and no document states.
- Blocks continuation: no for the model; yes for anyone writing the driver–application pair and reasoning about who may reset the buffer.
- Path: [`docs/khayyam/variable.md`](../../../docs/khayyam/variable.md)'s Overview sentence, or the construction model's owner, whose concept this is.

## Assumptions
- **The owner's driver–application design is carried as stated, and not read as a decision about the language** — Stability: Unexamined. The account was given as prose in a conversation about viewpoint, and three of its load-bearing words — *module*, *capsule*, *supervision* — each have an owner in this repository that this model does not control. What changes it: a ruling on any of the seven questions below, or a second design that answers the same instance differently. Mitigation: every claim in the model's section is cited to the document that states it, and the three words are recorded where they collide rather than adopted.
- **A binding's terms can be checked by one party alone** — Stability: Unexamined. The test — a term is worth stating only if one party can check it without the other's cooperation — is this revision's, and it is what sorts the sharpest instance's requirements into a declaration, a provision, and an open question. What changes it: a ruling that a term may be checked cooperatively, which would move atomicity out of the provision column and back into a statement. Mitigation: each of the three requirements is classified in the model with its evidence, so a reader can see which column it sits in and why.
- **The categories the parties are placed in are the right ones, and are not settled** — Stability: Unexamined. [`modules/computer/driver/`](../driver), [`modules/computer/adt/`](../adt), [`modules/computer/buffer/`](../buffer), [`modules/computer/capsule/`](../capsule), and [`modules/computer/runtime/`](../runtime) are this model's reading of where the parties belong, and the owner named only the first. [`modules/README.md:11`](../../../README.md) says no folder here is final. What changes it: a restructure of `modules/`, which the same rule invites. Mitigation: none available; the model states the reading as a reading and names the guarantee each category would own.
- **Resizing is a requirement the owner will keep** — Stability: Unexamined. The owner's design asks for both zero-copy carriage and a size that changes, and the model's finding is that one of the three answers to that collision costs the design nothing. What changes it: an owner ruling on which of the model's three answers holds. Mitigation: the three answers are set out with their costs, so the ruling has something to rule on rather than a question. **Withdrawn 2026-10-03:** this entry's support was the sources' own sentence that a zero-copy buffer "can't be resized" ([`zero-copy/buffer.kh:7`](../buffer/zero-copy/buffer.kh)), which made the stability claim rest on a comment in the residue of the failed Go attempt. The claim stands or falls on the owner's own two sentences, and whether the owner will keep the requirement is not something this repository can verify from a file.
- **The design's central property survives a second target** — Stability: Weak. "Both sides run the same module" is checkable only by a build or link step, and none exists; a target that links a separate build to the driver loses the property with nothing objecting — and since this revision, the indivisibility of a release with it. What changes it: the toolchain question above being answered either way.
- **The JavaScript target's readings are a faithful measure of what the language admits** — Stability: Weak. The model rests citations on one target for the classification of the three forms, the cell-per-variable reading, the key's shape, and the supply hook. What changes it: a second target disagreeing on any of them, which would make those citations this realization's readings rather than the language's statements. Mitigation: each citation names the target document and section rather than a bare claim.
- **A body-less method on a concrete capsule is the form a binding is written over, and will stay that form** — Stability: Weak. Nothing forbids a new form; the owner's design already uses a case the language has not stated — a method owner — which could be settled as a new form rather than a widened reading of the existing one.
