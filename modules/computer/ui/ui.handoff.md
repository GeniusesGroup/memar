# UI Handoff
Open work for `modules/computer/ui/ui.md`. Entries are mutable current state — revised as each item moves, removed when it resolves or is dropped. See [documentation-handoff.md](../../knowledge/documentation/handoff/handoff.md) for what a handoff is.

## Decisions

### The ui design and the correction of this module's placement (Tentative, owner rulings of 2026-10-20 to 2026-10-22; session 20261020-T060223Z-17988)
The decisions below are Tentative; the moves they led to are listed at the end of this entry.

- **What this module is.** `modules/gui` was written as the base for developing the concept of an interface, not for one application, and it was placed as a main category by mistake. The concept is **ui**: how any agent (a person, a screen, a voice, a command line, a program) meets services. gui, vui and cli are realizations of it. *(owner)*
- **Placement.** The neutral protocols are core domains of `computer`: `modules/computer/ui`, not a top-level `modules/ui`, because ui has no identity apart from `computer` and does not hold enough modules of its own to be a category ([Category](../../knowledge/classification/primitive/category.md)). The realizations are pluggable: `modules-plugable/computer/ui/{gui,vui}` and, as modules of their own, `command` and later `cli`. *(owner leaned to `computer`; open whether `computer/ui` or `modules-plugable/computer/ui` for the neutral protocols, ruled for core below)*
- **Core versus pluggable, stated once.** Core domains must be able to build on the widget and page protocols, so those protocols cannot be pluggable. The dependency runs only from a domain to the ui protocols, never the reverse. In three layers: (1) the neutral protocols (Application, Page, Pages, PageState, Navigator, History, Event, Information, Page_Manifest, Widget) are core; (2) each domain's own widget contract (the conditions and services a widget offers, as in the present `gui-widget.kh` files) is realization-neutral and stays in the domain; (3) renderings, screen, DOM, Element, Scroll, WindowType, touch and keyboard events, and splash screen are pluggable; `page` and `widget` as concepts and `command` are modules of `computer/ui` (page and widget core, command pluggable). *(owner: "a realization is pluggable" accepted; a flat "protocols core, realizations pluggable" rejected as too simple, so this three-layer reading is Tentative)*
- **Widget and page.** A widget is a named, stateful aggregator that reaches services only through generated SDK functions. A page is an addressable composition of widgets with state and history. Domains do not know each other's work; aggregation happens only at these two concepts, and neither is bound to the screen (a vui composes services differently). These definitions are working ones, and are expected to be revised; they may not be complete or exclusive. *(owner)*
- **A domain's ui is one role folder.** Each domain gets one folder, `ui`, in place of the separate `widgets` and `pages` folders; a new main category is not created for it. It is a work-kind role like `protocol`, `services` and `rules` (every domain has it, once), and is different from the relational facets `edges`, `edges-loop`, `status` and `labels`, which belong to one domain's model. The categories session (q-categories) found no contradiction on 2026-10-22; the split is its option (b) of Q6. Its notes: the role set must come from a pluggable profile, not a kernel enum, so `ui` is added to the profile's roles (the `folders.py` list), not hard-coded in the kernel; whether roles are global or per domain (its Q8, Q10) is still open there; the pluggable realizations under `modules-plugable/computer/ui` must not be imported by the kernel. *(owner accepted the split)*
- **A page belongs to the one domain whose subject it is.** `page-invoice` goes to invoice. It composes the widgets of other domains only through their widget contracts. A page name that does not match a domain is a bad sign to be resolved, not hidden: it either points to a missing domain (market, store, summary) or the page belongs to the application bundle (`bundles/gui`). Revisable. *(owner: strongly agreed; he is himself unsure of the correct place)*
- **Command line.** `modules-plugable/computer/ui/command` is not a process concept: it is how a service is called, so it belongs to ui as a module `command` of its own; `cli` is later a separate module that uses `command` (as a future `bash` module would), not its folder. Its Python implementation was not developed with Memar's thinking and must not be carried into Khayyam as it stands; a note to say so is owed in its handoff. *(owner)*
- **The SDK rule.** "No part of a Memar GUI speaks the network; it calls generated SDK functions" is a rule of the service domain, not of ui: no agent that calls a service writes the call itself. It belongs in `modules/process/service/rules`, and `sdk.md` at the root of that module should move under it. ui cites it. *(owner)*

## Open Questions

### Page state and history have no protocol text yet
- State: the protocol's stances are stated — page identity and state are protocol-level structures so navigation, deep-linking, and state restoration are uniform across applications rather than invented per framework; one application performs routing in one place; the GUI never speaks the network — but the `Page` section stops at identity: a canonical page ID computed as the first 64 bits of the SHA3-256 hash of the page URN, zero reserved for "no page", and the URN form `urn:giti:{domain-name}:page:{page-name}`. Nothing states what a page's state is, what a history entry holds, how state survives a page's deactivation, or what a URL is in this model. The implementation is consistent with the gap rather than ahead of it: `modules-plugable/computer/ui/gui/protocol/navigator.kh` and `modules-plugable/computer/ui/gui/protocol/history.kh` declare abstract types with signature-only methods.
- The owner's position, recovered 2026-09-30 from an audit of Omid Hekayati's Go-community Telegram-group messages (gopherconf.ir, Gommunity), supplies the requirements rather than a design: state belongs to the protocol rather than to each GUI framework; a deactivated page's state must survive the deactivation; the browser's History API — built on the server-rendered-page assumption, accepting arbitrary state blobs with no structure — is the thing being replaced; and the same question was raised from the framework side, where each framework's own router would make routing a per-application invention.
- Question for the owner: what is a page's state — its shape, who may write it, and what a history entry refers to — and is a URL a projection of state (exportable into a link, restorable from one) or an independent input the state must be reconstructible from?
- Next: design jointly with the SDK, because a page reaches services only through generated SDK functions; a state shape that must survive a reload constrains what the generated client can hand a page and what it must be able to serialize.

### The GUI's half of the shared validation shape
- State: validation is stated as belonging to the business-logic layer and generated once for both the server and the GUI client, with the accessor/setter pattern realizing it per field — the protocol's changelog already records the claim as the owner's, so the stance is not in question. What is undesigned is the shape: how a rule is declared once, where that declaration lives, and how a generated accessor surfaces validity both to a decoder and to a widget.
- The owner's discussion of the pattern, in the same 2026-09-30 audit, gives the reasons it answers — validation sits with the service that owns the field rather than in a validation module; a decoder can stop at the offending field instead of failing the whole payload; a GUI input can tell the user whether the value is valid as it is entered — and one discipline of the pattern worth keeping: an aggregate initializer may call the per-field setters, which keeps each function single-purpose and the initialization logic reusable rather than reimplemented per aggregate.
- Question for the owner: is the declaration a rule artifact beside the service, part of the service's declaration consumed by the generator, or an annotation — and does the GUI receive validity as a value a widget can bind to, or only as a rejection at the boundary?
- Next: this entry and [SDK Handoff → The validation-sharing shape](../../process/service/rules/sdk/sdk.handoff.md#the-validation-sharing-shape) are one question that ended up with two homes; settle it once in a joint session and record the outcome in both, so the two cannot drift into different mechanisms.
