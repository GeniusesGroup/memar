# Implements Rule — Intent via Abstraction_Implements
Rules for [Implements](../../implements.md) live one rule per folder under [`rules/`](../README.md). This rule is the checkable condition for how a type declares the abstractions it intends to implement. The protocol is [`protocol/implements.kh`](../../protocol/implements.kh). Owner corrections of 2026-11-14 are recorded on task `20261114-T094324Z-22560`.

## The rule
- **Do not put a target abstraction's name in a capsule body to claim that the capsule implements it.** A bare line such as `Type_LifeCycle` inside `cp { … }` is not an intent declaration.
- **Do not compose `Abstraction_Implements` into a capsule body.** Intent is not declared by embedding that abstraction. A capsule satisfies `Abstraction_Implements` structurally by implementing `DeclaredAbstractions` with a matching signature ([Khayyam Abstraction → Satisfying an Abstraction](../../../../khayyam/abstraction/abstraction.md#satisfying-an-abstraction)).
- **`DeclaredAbstractions` fills its influenced `Abstractions` by `Push`.** [`Abstractions`](../../../protocol/abstractions.kh) composes [`Container_Push`](../../../../adt/container/protocol/push.kh). Each claimed target is `abstractions.Push(Target)(...)`. Do not invent a parallel add API, do not route through `Container_Add`, and do not introduce a realizing capsule in every caller only to call `Make` then `Add`.
- **An abstraction may carry owner-authorized intent metadata in a companion `<base>.implements.kh`.** The companion's DeclaredAbstractions names that abstraction as its receiver and lists intended targets by Push. For a service-specific request or response observer, the general observer is listed here; the specific observer declares GetRequest or GetResponse with its own service value type instead of composing that generic target. This companion is tooling metadata, not a default implementation of the abstraction's runtime behavior. Declared intent remains separate from structural conformance and establishes no general return-variance rule.
- **Opt-in and tooling-facing.** Implement `DeclaredAbstractions` only when a discoverable pre-completion signal is wanted. It is not a runtime seal and not a substitute for structural satisfaction of the claimed targets.
- **One method names every claimed target.** Domain-specific empty markers are not needed for disambiguation once `DeclaredAbstractions` returns the set. `Error` no longer carries `ImplementsError`/`ImplError`; other modules still holding a private marker migrate the same way when next changed.
- **The influenced `abstractions` slot is the caller's.** [`DeclaredAbstractions`](../../protocol/implements.kh) names `abstractions Abstractions` in the influenced group. Per [Method → Influencing and Influenced Variables](../../../../khayyam/method/method.md#influencing-and-influenced-variables-not-inputs-and-outputs) and [Variable → Overview](../../../../khayyam/variable/variable.md#overview), that group is a slot the caller declares and hands by reference; a `vr` does not create the instance. The method body does **not** construct `Abstractions`; it only `Push`es into the value already in that slot. Obtaining a usable `Abstractions` instance before the call is the caller's (or the tooling that drives the method) Construction obligation. Do not invent `Make`/`Add` scaffolding inside `DeclaredAbstractions` bodies to paper over that obligation.
- **Tooling-facing bodies type Error the same way; disregard is still disregard.** Fallibility is judged per operation ([Disregarded Error](../../../../../process/error/rules/disregarded-error/disregarded-error.md)). `Push` declares `(err Error)`; a body that elects not to act on that path hands [`VoidError`](../../../../../process/error/protocol/void-error.kh). There is no separate compile-time Error type and no lighter signature for methods whose bodies exist for tooling discovery. What differs from a live-process method is whether a failure must drive a caller decision: when the contract is disregard, the body needs no runtime refusal or propagation chain; when the method runs in a live process and the failure must decide the next step, the full Error discipline of that process applies.

## Why
Structural satisfaction cannot signal intent before a capsule is complete. Composing the target — or composing `Abstraction_Implements` itself — into the capsule body was read as that signal and is the wrong construct. `Push` appends to the end with a minimal signature; `Add` chooses location by container logic and returns a count, which this intent list does not need ([Type → Implementation intent](../../../../type/type.md#implementation-intent)). Leaving construction of the influenced slot and Error typing tacit produced ad-hoc `Make` capsules and invented compile-time Error contracts; both are settled above from Method, Variable, Construction, and Disregarded Error rather than from call-site scaffolding.

## Keep it or drop it
An organization may omit pre-completion intent signals and rely only on structural satisfaction; it then accepts that incomplete capsules are invisible to scaffolding tools.

## What this rule does not claim
- It does not change how structural satisfaction of the *claimed* targets is judged.
- It does not invent a Construction library for `Abstractions`; it only places the construction obligation on the caller of `DeclaredAbstractions`.
- It is enforced by no check this repository runs today; a linter or codegen service may adopt it later.
