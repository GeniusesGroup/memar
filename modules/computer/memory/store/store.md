# Memory Store

## Abstract
A **store** is anything that retains bytes under addresses: a block device, a page, a record store, a key-value store, a file system, the working memory of a process. The store contract is the one abstraction through which state kept in volatile or non-volatile memory is read and written: `get` and `list` read, the atomic `batch` under expectations writes, `state` and `changes` let a structure derived from the store keep itself current, and the guarantees say what every store keeps true. The contract is parametric in the kind of address ([Memory Address](../address/address.md)) and in three properties of the store (dense or sparse, fixed or any value length, compare-and-write or not). A capsule that realizes it for one kind of address adds no abstraction of its own, as a capsule that realizes an abstraction realizes no other ([Khayyam → Sovereign Encapsulation](../../../../docs/khayyam/encapsulation.md)). The medium is an adapter a project chooses, never a property of the services that read and write: a concern's authoritative data has one location, and a file in the working tree, a branch of version control and a database are ways an adapter keeps it, never a second place a service also writes ([Memory → The memory/storage dichotomy rejected](../memory.md#the-memorystorage-dichotomy-rejected)).

This document is the contract moved out of [Memory](../memory.md#retention-is-reached-through-one-contract) on 2026-10-26, because a category holds no contract ([Category → The rules](../../../knowledge/label/labels/category.md#the-rules)). The statements of [Memory Record](../../../../modules-plugable/computer/memory/store/record/record.md) that name no id, part or label (the operations' answers, the guarantees, the capabilities and limits, what an adapter's document states, the cases of the suite) were moved here, and the cases into [Memory Conformance](../conformance/conformance.md), on 2026-10-26 with the protocol, [`protocol/store.py`](protocol/store.py), which holds the signatures, the answers, the parameters, the limits and the capability names once; record keeps what it adds.

## Explanation

### The contract
- **Address.** A byte string with equality and a total order, the byte order; its kind and length are fixed by whoever instantiates the contract ([Memory Address](../address/address.md)). Volatile memory is an instance of the contract when its positions are given an order.
- **Parameters of an instantiation.** Whether the address space is *dense*, every address holding a value, so that nothing reads Absent and `list` answers the capacity range, or *sparse*; whether a value has a *fixed* length or any length; and whether the medium can *compare and write* one address atomically. The core cases of the suite are split by these three, so that a block device is not required to read Absent nor to take an expectation it cannot apply.
- **Operations.** Each is stated by what it answers for a given input, so that any party can decide whether an adapter does; the signatures are [`protocol/store.py`](protocol/store.py).
  - `get(addresses)` answers one result for each address, in the order given: Found with the value and its token; Absent; or Unavailable, when the adapter cannot decide between the two, as when the shared store it asks for an address it lacks cannot be reached. A call of many addresses does not cost a process or a file per address where the medium allows it, and an adapter reports the processes it starts and the files it opens through `stats`.
  - `list(from, to, after, limit, descending)` answers the first `min(limit, n)` addresses, `n` being the number of held addresses in `[from, to)` that come after `after`, in byte order, or, when descending is asked, the last `min(limit, n)` of the range that come before `after`, in descending order; or Unavailable when the adapter cannot answer the whole range. A page shorter than `limit` is the end of the range, and no adapter returns a short page for any other reason; with no bounds it answers every held address, which for a dense store is the capacity range. An adapter's shards and directories never show: the answer is the same for any adapter holding the same addresses.
  - `batch(expect, write)` applies the writes only if every expectation holds. An expectation is a token, which the value at its address must have, or `absent`. A write puts a value at an address and replaces whatever it held. The answer is the first of these that applies: Refused, the batch is malformed and nothing is applied (no write, an address written twice, two expectations on one address, an address or a value the instantiation does not take, a limit exceeded as TooLarge, an atomicity not declared as NotAtomic, which an expectation on a store that cannot compare and write needs too); Unavailable with its reason, NotHeld (an expectation of a value at, or a write to, an address outside the held ranges), Unreachable (the adapter cannot decide an expectation) or Failed (the adapter could not finish and has made sure the batch can no longer commit), nothing applied, and answered only once the batch's fate is settled; Conflict, the first failing expectation in the order given named and nothing applied; Committed.
  - A `get` with an address the instantiation does not take, or a `list` with a `limit` below one or a `from` after a `to`, is Refused as a whole and answers nothing.
  - `state()` answers a token of the committed state, which changes when a batch commits and at no other time, and `changes(since)` the addresses written by the batches committed between that state and now, each once, so that a structure derived from the store (an index, a view) is brought up to date without rescanning and a batch committed by another process shows in the next read. An adapter realizes them as the medium allows (for git, the hash of the reference and `diff-tree`).
- **Guarantees.** What every adapter keeps true; the capsule over it adds its own, as `record` does for its parts and labels.
  - *Atomic and isolated.* A committed batch is visible whole to every reader of the store and no reader sees part of it, whether the reader is a thread, another process, or the same process after a restart; a read answers from a state between two batches.
  - *Linear.* The batches of one store are in one order, and a call that begins after a batch has returned sees it.
  - *One place orders the writes.* A store has one writer location, where its batches are ordered, and every process that writes it goes through an adapter there. An adapter declares the ranges of addresses it holds, where it decides alone: one with no shared store holds every address; one that keeps a copy of what a shared store holds holds the ranges a fetch the user asked for gave it whole, and, for an address kind whose minting is monotone, every address after the last of them. An address outside the held ranges is read by asking the shared store through `get` and `list`, as fresh as the asking, and what is learned that way is not written into the adapter's own store. Inside a held range an `absent` expectation and a write are decided at the adapter; outside it, an expectation of a value and a write are Unavailable as NotHeld, and an `absent` expectation is Unavailable as Unreachable until the shared store has answered. Writing the same addresses from several places is a design the contract does not offer.
  - *Durable as declared.* An adapter that declares `durable` keeps a committed batch through the abrupt end of the process that wrote it; survival of the loss of power is not a capability of the contract, and an adapter that gives it says so in its own document.
  - *Absent is not unknown.* An `absent` expectation is never satisfied by an adapter that could not look, an address never written reads Absent only when the adapter has answered that nothing is there, and a `list` that could not look at part of its range answers Unavailable, never a shorter answer given as complete.
  - *Nothing is removed.* The contract has no operation that removes a value; a value is replaced by writing another. Erasure, which a legal purge or a secret requires, is not decided ([Memory Handoff](../memory.handoff.md#what-is-the-retention-and-erasure-rule-for-preserved-history-and-where-do-a-records-versions-live)), and until the owner rules, no adapter offers it.
  - *No file in the working tree, where declared.* An adapter that declares `leaves_working_tree_untouched` keeps whatever it needs outside the project's working tree, in the store's own medium or in the user's data area, and its writes never change a file the working tree tracks or shows; an adapter whose medium is the working tree declares it false.
  - *Derived structures are rebuildable and never stale.* A structure an adapter derives to answer fast is derived from the store alone, is never written into its medium, records the committed state it reflects and is brought up to date before it answers; deleting every derived structure changes no answer.
- **Token.** A value found is returned with its token, the SHA-256 of its bytes, and an expectation of a batch is either a token or `absent`; so an adapter that knows addresses only serves every capsule. The algorithm is the subject and not a choice: a token recorded outside the store must be equal in every adapter, which two organizations choosing two hashes would break.
- **Capabilities, limits, `stats`.** An adapter declares, in code and once, what it is, and the contract exposes it: the capabilities, the limits (writes per batch, bytes per batch as the sum of the lengths of the values written, bytes per value) and `stats`, each written once in [`protocol/store.py`](protocol/store.py) with its summary. An adapter that does not declare `atomic_batch` refuses a batch of more than one write, or with an expectation on another address than the one it writes, as NotAtomic. What a class needs of its adapter, the least limits and the capabilities, is stated by the service that opens it and checked when the class is opened; the contract fixes no floor. The optional operations are not here: `lockable` and `nonvolatile` are pluggable modules at `modules-plugable/computer/memory/store/` (below).
- **The seam.** Every adapter exposes to the suite a hook at the commit point, after a batch's expectations are checked and before it commits, by which a case pauses or fails it, and the deletion of its derived structures; both are in [`protocol/store.py`](protocol/store.py), and a case that reaches another process asks the adapter how to open it there ([Memory Conformance](../conformance/conformance.md)). An adapter that declares `fallback` also lets the suite make its shared store unreachable or hold given addresses, by a seam its own module declares with its group.
- **Adapters state themselves.** Each adapter's module has a document that says, once: its capabilities and limits; where it keeps anything outside the store's medium; the derived structures it keeps and what invalidates them; how it meets each case of the suite; and what it cannot do. The document of `git-store` also states its first configuration, one reference or several, with the consequence of each for a batch that touches two, and what it does with a lock a killed writer left; and the plumbing it uses and the constraints that follow from the owner's ruling that git is a sink to be left: only `hash-object`, `mktree`, `commit-tree`, `update-ref`, `fast-import`, `cat-file --batch`, the read-only `for-each-ref`, `ls-tree` and `diff-tree`, `repack` and `multi-pack-index` (or the host's `git maintenance`) to keep the number of packs bounded, and `fetch` with an explicit refspec; no worktree and no index; a batch written as objects and made visible by one compare-and-swap of a private reference, never a worktree commit; references under a private namespace, fetched only by explicit refspec and never checked out; and the shard rule private (a fixed-length prefix of the address).
- **Referring to an address.** The contract is the one abstraction other kernel modules use to refer to a thing retained: an identifier in a Task, a timeline or a Request names an address ([Memory Address](../address/address.md)) and, where the document reads or writes it, depends on this module, and on nothing of `record`, `file` or any adapter. How a thing is stored is the capsule's affair.

### What stands where
Put to each part, [Kernel Neutrality](../../../knowledge/modularity/rules/kernel-neutrality/kernel-neutrality.md#the-rule) and [Pluggable → The test](../../../knowledge/modularity/labels/pluggable.md#the-test) leave in the kernel the address, this contract, the reference adapter [Memory Volatile](../volatile/volatile.md) and the suite [Memory Conformance](../conformance/conformance.md). Every capsule that realizes the contract for one kind of address, and every optional operation, is optional and can be removed whole, so it is pluggable and stands at `modules-plugable/computer/memory/store/<capability>/`, the mirror of this module ([Category Depth](../../../knowledge/label/rules/category-depth/category-depth.md#the-rule)). What rests on another module places nothing.
| Capsule | Address | Rests on |
| --- | --- | --- |
| `lockable` | optional `Lock` and `Unlock` on the `Locker` of `modules/process/sync/`, with a lease (owner, 2026-10-25); the default control of writers is the expectation | the contract |
| `nonvolatile` | optional `Flush` for a medium that keeps a write only after a flush | the contract |
| `block` | position, fixed value size, dense | the contract |
| `page` | position, fixed value size, dense | the contract; the order of `block` and `page` is open |
| `record` | a 16-byte id and a domain key | the contract, and `index` for the labels |
| `key_value` | a variable-length key, listed in order | `page`, and `nonvolatile` as the barrier |
| `index` | derived | the contract's `changes` |
| `graph` | none of its own (it adds no address kind, operation or guarantee) | `key_value`; held while the review's question is open |
| `git-store`, `files` | addresses only | `git-store` the contract and the git module; `files` the contract and the `filesystem` module |
| `view` | a consumer of `record` | `record` (a pluggable that attaches to another stands beside it) |
| `cluster` | a replicated-store node; may have no responsibility of its own | see [Memory Handoff](../memory.handoff.md) |

Not at this mirror, because they realize no one store: `filesystem` (with `File` and `Directory`), the guest surface that realizes a whole family, `sql` while it is a foreign surface and not a query over one store, and `allocator`, which extends the subject of the category as a whole, each directly at `modules-plugable/computer/memory/` ([Category Depth](../../../knowledge/label/rules/category-depth/category-depth.md#the-rule), third bullet). The home of `sql` becomes `store/sql` if it proves to be a surface over `key_value` or `record`, and that of `allocator` is decided with the division of the rules of [Memory](../memory.md) that remain in the category.

A key-value store is not a record store: its key is not a fixed-length id and it lists keys, which `record` cannot and should not, and storing it in records would cost a hash of the key and the whole pair in a record's data; so it is a capsule of its own on `page` and not a layer on `record`. `record` is a capsule over any store that realizes the contract: the 16 bytes of an id followed by the bytes of a domain key form its address (`parts` of an id is a `list` over the addresses that begin with it, and a bound on existence instants is a range over the six-byte millisecond prefix), a part is a value, and the labels of a node and `scan` by label are answered from an `index` that `record` keeps current by `changes`, outside the store's medium. `files` and `git-store` know no id and no label: `git-store` shards by a fixed-length prefix of the address, which for an id of version 7 is a window of time without the adapter reading the id.

### The cases this module owes
The cases are code, one function each in [`conformance.py`](../conformance/conformance.py), whose docstring states the case: the cases of the first design's suite that can be stated for addresses, and those this contract adds for `state`, `changes` and the parameters. Which group each belongs to, and why a case naming an id, a part or a label is `record`'s, is [Memory Conformance](../conformance/conformance.md). The groups of an optional capability are owed by the module that declares it and run through the suite's runner: `lockable`'s in [`lockable.py`](../../../../modules-plugable/computer/memory/store/lockable/lockable.py), `fallback`'s and `working-tree`'s by the adapters that declare them, the first being [`git-store`](../../../../modules-plugable/computer/memory/store/git-store/git-store.md). A case whose capability no adapter yet declares is pending and carries `owed:memory.port.contract-suite`; the `durable` and `shared` groups run on `git-store` since 2026-10-26, and two of `lockable`'s wait for a lockable adapter.

Owed: memory.port.contract-suite
