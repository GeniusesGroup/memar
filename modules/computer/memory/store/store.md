# Memory Store

## Abstract
A **store** is anything that retains bytes under addresses: a block device, a page, a record store, a key-value store, a file system, the working memory of a process. The store contract is the one abstraction through which state kept in volatile or non-volatile memory is read and written; its operations and guarantees are [`protocol/store.kh`](protocol/store.kh). The contract is parametric in the kind of address ([Memory Address](../address/address.md)) and in three properties of the store (dense or sparse, fixed or any value length, compare-and-write or not). A capsule that realizes it for one kind of address adds no abstraction of its own, as a capsule that realizes an abstraction realizes no other ([Khayyam → Sovereign Encapsulation](../../../../docs/khayyam/encapsulation.md)). The medium is an adapter a project chooses, never a property of the services that read and write: a concern's authoritative data has one location, and a file in the working tree, a branch of version control and a database are ways an adapter keeps it, never a second place a service also writes ([Memory → The memory/storage dichotomy rejected](../memory.md#the-memorystorage-dichotomy-rejected)).

This document is the contract moved out of [Memory](../memory.md#retention-is-reached-through-one-contract) on 2026-10-26, because a category holds no contract ([Category → The rules](../../../knowledge/label/labels/category.md#the-rules)). The contract itself is Khayyam: the types and their operations are [`protocol/store.kh`](protocol/store.kh) and the files beside it, each type's human-facing text in its `*.eng.kh`, the two families of refusal in [`errors/errors.kh`](errors/errors.kh). This document holds what those cannot: the reasons, the trade-offs and the owner's rulings. The Python in this folder is a realization of the Khayyam and states nothing the Khayyam does not.

## Explanation

### The contract
Where each fact is: the operations, their answers, their parameters and the order in which a batch's outcomes apply are [`protocol/store.kh`](protocol/store.kh) and the types it names (`store-get-answer.kh`, `store-list-query.kh`, `store-batch-answer.kh`, `store-changes-answer.kh`); the capabilities, the limits and `stats` are `store-capabilities.kh`, `store-limits.kh` and `store-stats.kh`; the reasons an answer is Unavailable or Refused are `Unavailability` and `Refusal` in [`errors/errors.kh`](errors/errors.kh); the seam is `store-seam.kh`; that an adapter keeps the guarantees below is decided by the cases of [Memory Conformance](../conformance/conformance.md). The rest of this section says why.

- **Why the contract is parametric.** An address is a byte string with equality and a total order, the byte order; its kind and length are fixed by whoever instantiates the contract ([Memory Address](../address/address.md)). Volatile memory is an instance when its positions are given an order. A block device cannot read Absent and a medium that cannot compare and write cannot take an expectation; a contract that required both would exclude the media it is meant to cover. So whether the address space is dense or sparse, whether a value has a fixed length or any length, and whether the medium can compare and write one address atomically are parameters of an instantiation (`store-parameters.kh`), and the core cases are split by them.
- **Why writing is one atomic batch under expectations.** The only operation that writes is the batch, which applies every write only if every expectation holds, an expectation being a token or `absent`. This is the control of writers: a writer reads a token and writes under it, and no lock outlives a process, which is why `lockable` is an optional capability and not a core operation. A batch is answered by the first of its outcomes that applies, so a caller can tell a malformed batch, an unavailable store, a lost race and a commit apart.
- **Why `state` and `changes`.** A structure derived from a store (an index, a view) must be brought up to date without rescanning, and a batch committed by another process must show in the next read. `state` is a token of the committed state that changes when a batch commits and at no other time, and `changes` the addresses written between a state and now. An adapter realizes them as its medium allows. What `changes` answers for a state older than the store keeps, and what it counts as a change, are open (Memory Handoff, Memory Store Handoff).
- **Why the token is the SHA-256 of the value, and one algorithm.** A value found is returned with its token, and an expectation is a token, so an adapter that knows addresses only serves every capsule. The algorithm is the subject and not a choice: a token recorded outside the store must be equal in every adapter, which two organizations choosing two hashes would break.
- **Why Unavailable is not Absent.** An adapter that could not look must not say that nothing is there: an `absent` expectation is never satisfied by an adapter that could not look, an address never written reads Absent only when the adapter has answered that nothing is there, and a list that could not look at part of its range answers Unavailable, never a shorter answer given as complete. A page shorter than its limit is the end of the range for the same reason, so a caller that pages never mistakes a failure for an end.
- **Why one place orders the writes.** A store has one writer location, where its batches are ordered, and every process that writes it goes through an adapter there. Writing the same addresses from several places is a design the contract does not offer, because ordering them is a consensus problem it does not claim to solve. Where a shared store exists, a store that keeps a copy of it holds the ranges a fetch the user asked for gave it whole and, for an address kind whose minting is monotone, every address after the last of them; it can then decide alone inside them and ask the shared store outside them (what `git-store` holds by default is [`git-store-held.eng.kh`](../../../../modules-plugable/computer/memory/store/git-store/protocol/git-store-held.eng.kh)). An address outside them is read by asking the shared store and never copied into the adapter's own store, so a stale copy never competes with the shared store; a write there cannot be decided at the adapter, so it is Unavailable and never a guess.
- **Why atomic, isolated and linear.** A committed batch is visible whole to every reader, whether a thread, another process or the same process after a restart, and the batches of one store are in one order, so a read answers from a state between two batches and a call that begins after a batch has returned sees it. Without this a derived structure could be built from a state that never existed.
- **Why durability is declared and the loss of power is not asked.** An adapter that declares `durable` keeps a committed batch through the abrupt end of the process that wrote it. Survival of the loss of power is not a capability of the contract, because no case can decide it on every medium; an adapter that gives it says so in its own document.
- **Nothing is removed.** The contract has no operation that removes a value; a value is replaced by writing another. Erasure, which a legal purge or a secret requires, is not decided (Memory Handoff), and until the owner rules, no adapter offers it.
- **Why the working tree may be left alone.** Work records kept in the working tree are scanned at every edit, lost by a stash or a branch switch, and editable by any tool. An adapter that keeps whatever it needs outside the working tree declares `leaves_working_tree_untouched` and never changes a file the working tree tracks or shows; an adapter whose medium is the working tree declares it false, so a class can require the property when it is opened.
- **Why derived structures are rebuildable and never stale.** A structure an adapter derives to answer fast is derived from the store alone, is never written into the store's medium, records the committed state it reflects and is brought up to date before it answers. Deleting every derived structure then changes no answer, which lets an adapter drop one at any time and lets a case prove it.
- **Why the contract fixes no floor of limits.** An adapter declares, in code and once, what it is (its capabilities and its limits), and the contract exposes it. What a class needs of its adapter is stated by the service that opens it and checked when the class is opened; a floor set by the contract would be a choice the kernel makes for every organization. An adapter without an atomic batch refuses a batch it cannot apply whole rather than half-apply it ([`errors/errors.kh`](errors/errors.kh)). The optional operations are not here: `lockable` and `nonvolatile` are pluggable modules at `modules-plugable/computer/memory/store/` (below).
- **Why the caller closes the store.** A store holds what its medium needs open (a process, a file, a lock); the caller that opens a store closes it, so that a medium is released at a time the caller chooses and not when a process ends. The contract declares no `Close`, because a store of volatile memory has nothing to release: an adapter whose medium needs it declares its own ([`git-store`](../../../../modules-plugable/computer/memory/store/git-store/protocol/git-store.kh)), and a capsule over a store closes the store it opened when the store can be closed.
- **Why the suite has a seam.** To decide a requirement a case must pause or fail a batch at the commit point, delete an adapter's derived structures, and reach another process; every adapter therefore exposes that seam, and a case that needs another process asks the adapter how to open it there. An adapter that declares `fallback` also lets the suite make its shared store unreachable or hold given addresses, by a seam its own module declares with its group.
- **Adapters state themselves.** Each adapter's module has a document that says once where it keeps anything outside the store's medium, the derived structures it keeps and what invalidates them, and what it cannot do; its capabilities and limits are its Khayyam, and how it meets the suite is its cases. The constraints that follow from the owner's ruling that git is a sink to be left bind `git-store`, and are stated with their reasons in [Memory Git Store](../../../../modules-plugable/computer/memory/store/git-store/git-store.md).
- **Referring to an address.** The contract is the one abstraction other kernel modules use to refer to a thing retained: an identifier in a Task, a timeline or a Request names an address ([Memory Address](../address/address.md)) and, where the document reads or writes it, depends on this module, and on nothing of `record`, `file` or any adapter. How a thing is stored is the capsule's affair.

### What stands where
Put to each part, [Kernel Neutrality](../../../knowledge/modularity/rules/kernel-neutrality/kernel-neutrality.md#the-rule) and [Pluggable → The test](../../../knowledge/modularity/labels/pluggable.md#the-test) leave in the kernel the address, this contract, the reference adapter [Memory Volatile](../volatile/volatile.md) and the suite [Memory Conformance](../conformance/conformance.md). Every capsule that realizes the contract for one kind of address, and every optional operation, is optional and can be removed whole, so it is pluggable and stands at `modules-plugable/computer/memory/store/<capability>/`, the mirror of this module ([Category Depth](../../../knowledge/label/rules/category-depth/category-depth.md#the-rule)). What rests on another module places nothing.
| Capsule | Address | Rests on |
| --- | --- | --- |
| `lockable` | optional `Lock` and `Unlock` on the `Locker` of `modules/process/sync/`, with a lease (owner, 2026-10-25); the default control of writers is the expectation | the contract |
| `nonvolatile` | optional `Flush` for a medium that keeps a write only after a flush | the contract |
| `block` | position, fixed value size, dense | the contract |
| `page` | position, fixed value size, dense | the contract; the order of `block` and `page` is open |
| `record` | a 16-byte id and a domain key | the contract, and `index` for the labels |
| `key_value` | a variable-length key, listed in order | `page`, and `nonvolatile` as the barrier |
| `index` | derived | the contract's `changes` |
| `graph` | none of its own (it adds no address kind, operation or guarantee) | `key_value`; held while the review's question is open |
| `git-store`, `files` | addresses only | `git-store` the contract and the git module; `files` the contract and the `filesystem` module |
| `view` | a consumer of `record` | `record` (a pluggable that attaches to another stands beside it) |
| `cluster` | a replicated-store node; may have no responsibility of its own | see Memory Handoff |

Not at this mirror, because they realize no one store: `filesystem` (with `File` and `Directory`), the guest surface that realizes a whole family, `sql` while it is a foreign surface and not a query over one store, and `allocator`, which extends the subject of the category as a whole, each directly at `modules-plugable/computer/memory/` ([Category Depth](../../../knowledge/label/rules/category-depth/category-depth.md#the-rule), third bullet). The home of `sql` becomes `store/sql` if it proves to be a surface over `key_value` or `record`, and that of `allocator` is decided with the division of the rules of [Memory](../memory.md) that remain in the category.

A key-value store is not a record store: its key is not a fixed-length id and it lists keys, which `record` cannot and should not, and storing it in records would cost a hash of the key and the whole pair in a record's data; so it is a capsule of its own on `page` and not a layer on `record`. `record` is a capsule over any store that realizes the contract; its address, its parts and its labels are [`record-key.eng.kh`](../../../../modules-plugable/computer/memory/store/record/protocol/record-key.eng.kh) and the files beside it, and what it answers by label it answers from an `index` it keeps current by `changes`, outside the store's medium. `files` and `git-store` know no id and no label: `git-store` shards by a fixed-length prefix of the address, which for an id of version 7 is a window of time without the adapter reading the id.

### The cases this module owes
The cases are code, in the suite: the cases of the first design's suite that can be stated for addresses, and those this contract adds for `state`, `changes` and the parameters. Which group each belongs to, and why a case naming an id, a part or a label is `record`'s, is [Memory Conformance](../conformance/conformance.md). The groups of an optional capability are owed by the module that declares it and run through the suite's runner: `lockable`'s by [`lockable`](../../../../modules-plugable/computer/memory/store/lockable/lockable.py), `fallback`'s and `working-tree`'s by the adapters that declare them, the first being [`git-store`](../../../../modules-plugable/computer/memory/store/git-store/git-store.md). A case whose capability no adapter yet declares is pending and carries `owed:memory.port.contract-suite`; the `durable` and `shared` groups run on `git-store` since 2026-10-26, and two of `lockable`'s wait for a lockable adapter.

Owed: memory.port.contract-suite
