# Memory Handoff
Open work for `modules/computer/memory/memory.md`. Entries are mutable current state — revised as each item moves, removed when it resolves or is dropped. See [documentation-handoff.md](../../../modules-plugable/knowledge/documentation/handoff/handoff.md) for what a handoff is.

## Decisions

### Owner rulings of 2026-10-24 on the shape of the memory module (decided)
Given by the owner after reading the design of task `20261023-T074641Z-5420`; they supersede the Tentative entry below wherever the two differ, and the tasks queued from them settle the rest. The order is the owner's.
- **The adapters are independent modules.** `git` and `files` are modules of their own and do not stand under `modules-plugable/computer/memory/record/`: putting them there is like putting `record` under every domain because every domain's storage uses it. The model must be more exact: there is one common abstraction of retention that `record` itself uses down to the `block` layer, the base layer. The present categories of `modules/computer/memory/` were not accidental, and they are open to review.
- **File and Directory move to the filesystem module** (agreed). Whether the filesystem module itself should then move under `modules-plugable/computer/memory/` is the owner's own question, and the modelling task answers it.
- **`services/` is distributed.** The files of `modules/computer/memory/services/` are spread among the modules they belong to, or become a module of their own; a category that holds several modules does not keep the internal folders of a module (`services`, `error`).
- **The category rule changes.** The categories of `modules/` and of `modules-plugable/` correspond, and a flat pluggable side is a defect as the categories grow; the old categories are open to review too. `modules/storage` is wrong as a category and its modules belong under `memory`, since that word was chosen for the whole family.
- **A file that is developed is upgraded with care.** `record/protocol/model.kh` is the first example: `Record_Model_Lock` and `Record_Model_Unlock` become `Lock` and `Unlock`, since a capsule that realizes the abstraction realizes no other and needs no prefix on a method; `Storage_UUID` is a bad name for the key of the record module and is `RecordUUID`.
- **A key-value store is not a record store.** Its key is not a fixed-length id and it lists keys, which a record store cannot and should not; storing it in records would cost a hash of the key and the whole pair in the record's data. It is developed as a module of its own on `page` or even `block`.
- **Answers are given in the layers above this chat.** The owner will answer in the tasks queued below, not in the conversation that produced the design.

### The parts of the memory module: their state and where each belongs (2026-10-23)
**Tentative**, taken by task `20261023-T074641Z-5420` so that the record contract is built on a module whose shape is settled, and open to the owner's ruling. The state was read by listing the folders and counting the declarations that are not inside a `TODO(go-migrate)` comment; a part that is all comment is a Go-era draft and says so.
- **Memory proper, stays here:** `address` (`MemoryAddress`, `PTR`), `reference` (mutable, immutable, weak, counted), `page`, `block`, `protocol/nonvolatile.kh` (`Flush`) have declarations in Khayyam; `heap.kh` and `mem.kh` are comments only and wait on [Where do `heap.kh` and `mem.kh` belong?](#where-do-heapkh-and-memkh-belong).
- **`record` is the one abstraction of non-volatile retention.** Its Go-era `Record_Model` draft is replaced by the contract in [record.md](record/record.md), which says where each operation of the draft went. Its adapters are the pluggable modules under `modules-plugable/computer/memory/record/`: `git` over git plumbing and `files` over the file system module, and the view stands beside them as a consumer; the in-process reference adapter `volatile` is part of the contract's decision procedure and stays in `record/`. A new module `port` is not made: the record folder is where the abstraction stood. `modules/storage/key_value` declares the same shape as the Go-era `Record_Model` (Lock, Unlock, Length, Get, Set, Delete, Erase, Batch) as a database paradigm, and `modules/storage/graph` versioned storage services; whether they fold into `record` or stay a paradigm that consumes it is part of the question in [Modules Handoff](../../modules.handoff.md) on dissolving `storage` under `computer`, and until it is ruled `key_value` is read as a consumer (Tentative).
- **`file` and `directory` move to `modules-plugable/computer/filesystem/`.** They declare the File and Directory of the POSIX surface, which that guest module exists for. The consumers outside memory are one kernel declaration, `modules/computer/codec/compress/protocol/compress.kh`, which imports `Observer_Extension` from `file/`, and documents that link them; a kernel module may not import a pluggable one, so the move settles where the file extension observer lives (a mediatype or name concept the kernel keeps, or a local declaration in compress). The move is queued.
- **`index` and `index-one_one`** (the hash index of a database node, protocol declared and services commented) are a derived structure over records that can be removed whole, so they belong in `modules-plugable/computer/memory/record/index/` when converted; nothing outside memory uses them today.
- **`services/`** (`batch`, `cluster`, `errors`, `manifest`, `metrics-v0`, `transaction-manager`, all comments): `batch` and `transaction-manager` are superseded by the batch of the record contract; the rest is the node of a replicated store and belongs in `modules-plugable/computer/memory/record/cluster/` when converted.
- **`sql`** (one commented SDK file) is a foreign surface and belongs in `modules-plugable/computer/memory/sql/`, labelled `guest`, when converted.
- **`protocol/version.kh`** (`Versioned`, `MaxVersion`) stays until the record build decides it: the contract keeps no versions of a value, since the history of a value is its chain of Requests.
- **The pluggable side mirrors the kernel path**, as `modules-plugable/computer/codec/` already mirrors `modules/computer/codec/`: what is optional in `modules/computer/memory/record/` stands at `modules-plugable/computer/memory/record/`. This adds one folder to the floor of `modules-plugable/computer/` and none of the adapters, where the alternative adds one module there for each. The rule that would state it is the question in [Placements Handoff](../../knowledge/modularity/placements.handoff.md#how-a-pluggable-module-is-placed-under-a-kernel-module-that-has-children-and-the-floor-of-modules-plugablecomputer).

## Open Questions

### The contract-term notation
- State: the requirement is stated (copy/ownership semantics are contract members) but the notation is undecided — a capability interface, a naming convention, or a `Syllab`-level annotation.
- Next: design the notation after the abstraction syntax stabilizes.

### Copy semantics at process/network boundaries versus in-process call boundaries
- State: the [Error protocol](../../process/error/error.md)'s boundary rules suggest the default may differ across a network boundary; the interaction is not worked out. Next in that direction: work it out jointly with the error protocol's next revision.
- State: the adjacent, narrower question — whether an ordinary in-process argument or return value that stays inside one ownership domain is required to be passed by reference rather than copied — is also open. This document currently requires only that the copy/share choice be *stated* as a contract term, and states its default for values that *cross* ownership domains. Whether to also fix a protocol-level default for plain call-boundary passing was raised while dissolving a draft coding-style rule that asserted such a default as a MUST; it is deliberately not adopted here, since the neutrality above is this document's own position and a protocol-level MUST would have to be argued against it rather than past it. Where the claim is settled today it is settled at the realization layer: Khayyam's grammar passes arguments and returns strictly by reference and forbids implicit copying (Khayyam (`docs/khayyam/khayyam.md`)) — an instance of this protocol, not its authority.
- Next: decide in a dedicated chat, together with the tier the chosen position carries (protocol default, library contract term, or tooling-suggested).

### The copy convention's interaction with pooling
- State: a pooled buffer is shared across requests by definition; which of a pooled library's outputs are copies and which are views needs a worked-out taxonomy, not just the rule.
- Next: build the taxonomy against a concrete pooled implementation (the networking realization is the first candidate).

### Volatility vocabulary in the OS contract's storage topic
- State: settled by use, and both alternatives in the question are already in force. [OS → Storage](../os/os.md#storage-block-abstractions-not-filesystems) gives the block grant "the same kind of answer it provides for volatile memory" and says "Non-volatile storage deserves the same restraint", so the volatility vocabulary is applied there already and the block-grant framing is kept — the question is not which of the two to choose but what the two documents have not yet said to each other. Residue: the OS storage topic carries no cross-link to [Volatility: the real classifier](./memory.md#volatility-the-real-classifier), and it never states that the block grant is non-volatile memory under this document's definition rather than a separate class the two documents happen to name alike.
- Next: add that cross-link, and one sentence naming the block grant as non-volatile memory, during the next OS document revision; no choice of vocabulary remains to be made.

### Must every `Service` carry `Deinit`?
- State: raised 2026-09-28 by the lifecycle/process/storage pass of the memar-go port. [Teardown is explicit, and automation writes source](memory.md#teardown-is-explicit-and-automation-writes-source) and Khayyam → How Khayyam realizes Memory (`docs/khayyam/khayyam.md#how-khayyam-realizes-memory`) give `Deinit` to a capsule whose acquisition requires a release, and the lifecycle protocol `modules/computer/capsule/protocol/life_cycle_contract.kh` carries that teardown surface only. `modules/process/service/protocol/service.kh` composes `Capsule_LifeCycle` into `Service` unconditionally, so every service must declare `Deinit` even when it acquired nothing to release. No lifecycle or service document exists, so the mismatch is carried here, beside the teardown rule. Not edited.
- Question for the owner: does every service acquire something whose release is required, so the unconditional composition stands, or does `Service` drop `Capsule_LifeCycle` and leave `Deinit` to the services that need it?
- Next: owner ruling; then `service.kh` is edited or the reason is stated where the service contract is documented.

### Should storage capabilities be named as independent capabilities, against this document's rejection of named kinds?
- State: recovered 2026-09-30 from an audit of Omid Hekayati's Go-community Telegram-group messages. The owner's position is that a storage concern's needs are independent axes rather than one bundled kind — durable key/value retention, time-series retention, full-text search, vector search, transactions, and a faster derived tier are separately adoptable, and a framework that requires a system to carry a local store, a cache, and a distributed store together has turned one requirement into a package. The tension is with this document's own position, which is not a gap but a designed refusal: [Volatility: the real classifier](./memory.md#volatility-the-real-classifier) keeps retention as a *property* precisely so the field is not split into named kinds, and [The memory/storage dichotomy rejected](./memory.md#the-memorystorage-dichotomy-rejected) records that reifying a tier is what produces the shadow-tier pathology.
- Question for the owner: are these capabilities to be stated as properties a contract may require (in the spirit of [Copy and ownership semantics are contract members](./memory.md#copy-and-ownership-semantics-are-contract-members)), which preserves the refusal, or as a named capability vocabulary, which reifies the field a second time? No document enumerates them today; the closest existing statement is [OS](../os/os.md), where whether blocks become records, tables, logs, journals, or object stores is explicitly left as meaning owned by the system above the boundary.
- Next: answer this before any storage design chat opens, because a profile list adopted by default would be exactly the reification the two sections above reject, and the [Filesystem](../../../modules-plugable/computer/filesystem/filesystem.md) protocol's "a high-level library whose inclusion is a decision" stance is the precedent for the property-shaped answer.

### What is the retention and erasure rule for preserved history, and where do a record's versions live?
- State: the Modeling document fixes the modeling half — a concern's actual history of state changes is reality, a fix or reversal is a new fact referencing what it corrects, and no storage engine is prescribed ([Modeling → Modeling State Change as Events, Not Destructive Updates](../../../docs/modeling.md#modeling-state-change-as-events-not-destructive-updates)) — and the owner has stated the same position directly and repeatedly in the Go-group discussions recovered 2026-09-30: there is no logical reason to update or delete data, and a decision recorded at one time must not be erased by a later decision to change it. The same discussions carry the qualifications that keep this from being an absolute rule, and those qualifications are stated nowhere in `docs/`: secret erasure, legal purge, and bounded retention are not the same act as a state change, and "never delete" makes all three impossible.
- Question for the owner: what is the erasure rule that sits beside history preservation — is a removed value a tombstone that records the removal as a fact, a gap in the history, or an exception to the whole rule — and who states it, this protocol or the Modeling document? Related and equally unstated: whether the versions of one record must be co-located. The source argues both ways inside a single message — that the storage layer should not be made to understand the nature of the data, and that in a distributed store the temporal versions of a record must be kept on one node rather than spread across nodes.
- The record contract ([port](record/record.md#what-every-adapter-guarantees)) offers no removal until this is ruled, so no verb erases, and contents labelled `temp` are kept; the entry in [Memory Record Handoff](record/record.handoff.md#what-is-the-retention-and-erasure-rule-now-that-the-port-offers-none) carries the options.
- Next: owner ruling on the erasure rule first; the placement question then belongs to whichever storage design consumes the capability question above, and to [Time Handoff → Distributed ordering versus the Instant contract](../../time/time.handoff.md#distributed-ordering-versus-the-instant-contract) for what "co-located" would cost.

### Must teardown be idempotent, and which lifecycle names belong to which resource family?
- State: recovered 2026-09-30 from an audit of Omid Hekayati's Go-community Telegram-group messages, where the owner's stated house practice was three lifecycle members for most structures — initialize, re-initialize, de-initialize — with two disciplines attached: re-initialization is worth its cost only after being measured against release, and must not let information from the previous cycle leak into the new one; and initialization performed inside an external factory function was rejected outright, because it moves the capsule's own behavior outside its encapsulation. What survives of that practice in this repository is narrower than the source: `modules/computer/capsule/protocol/life_cycle_contract.kh` states that `Init` and `Reinit` are not members of the protocol, and this document gives `Deinit` only to a capsule whose acquisition requires a release ([Teardown is explicit, and automation writes source](./memory.md#teardown-is-explicit-and-automation-writes-source)). No document states whether releasing twice is defined, permitted, or an error — a rule the question immediately above this one needs before the composition in `service.kh` can be ruled on either way.
- Question for the owner: is idempotence a protocol requirement for teardown, and does the state sequence differ by resource family — a value with construction and validation, a resource with an open/running/closing/closed progression, a pooled object with reset and a separate lifecycle — or does one sequence serve every resource with the differences left to each protocol that owns one?
- Next: settle alongside [Must every `Service` carry `Deinit`?](#must-every-service-carry-deinit), which asks the same underlying question from the composition side; a ruling on idempotence alone does not answer it, and a ruling there alone leaves this one open. Initialization staying inside the capsule is already settled by Khayyam → Sovereign Encapsulation (`docs/khayyam/encapsulation.md`) and is recorded here only so the rejected factory alternative is not re-proposed.
