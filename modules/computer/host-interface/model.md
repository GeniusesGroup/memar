# Host Interface Model

## Abstract
This document is the model of how a program reaches a facility its host provides without the language naming that facility, derived from the language's own statement of its foreign-function-interface form, from the artifact the JavaScript target emits, from the link map that decides what is linked instead of compiled, and from the `.kh` corpus as it stands. It names two concepts — **Host Facility** and **Facility Interface** — attaches a third that another model in this repository already owns, **Provisioning**, and refuses three more: **Host Call** is a relation and a mechanism rather than a concern, **Facility Presence** is a rule the host owns rather than a responsibility this library holds, and **Host Interface Package** is a Module that [Modularity](../../../docs/modularity.md) already defines. It records one collision with a concept the corpus already owns, **Adaptor**, whose responsibility is translation and therefore the opposite of this one's. Its central claim is a vocabulary separation, stated as a first-class claim rather than a naming preference: a host's facility names and this repository's own names must not be one name, because the owner of a name is what makes every claim made with it checkable, and because a runtime that supplied a name the language owns would be establishing the system's structure at execution time, which [Runtime → A runtime does not establish structure](../../../docs/protocols/computer/runtime.md#a-runtime-does-not-establish-structure) forbids. It separates three layers no document in this repository has separated for this subject: what the language documents already state, what a library over them could provide, and what neither states. It states that the language must state one thing first — that a body-less method on a capsule names a provision whose name this repository owns and whose implementation the host does not — because the corpus's body-less methods on capsules are the port's own arithmetic and text conversions rather than anything a host supplies, and because the two language documents disagree with each other about which spelling declares one. And it names its dependency rather than working around it: the language has no literal, no primitive type, and no construction form, so the arguments of a host call can only be values the program already holds, which makes this concept wait on [`modules/process/construction/`](../../process/construction/model.md).

## Introduction

### Motivation
Six facts stand between this repository and a program that reaches a facility its host provides, and none of them is about JavaScript.

The first is that the language already has the form this concept needs, and states it in one sentence. [Khayyam → Method](../../../docs/khayyam/khayyam.md#method) says that when the receiver is a concrete capsule, "a body-less method signals to the compiler that the implementation will be provided externally during the linking phase"; [Method in Khayyam → Body-less Methods](../../../docs/khayyam/method.md#body-less-methods-ffi-and-contracts) repeats it at `:80`. What that sentence does not say is who owns the *name* such a method carries — and that is the whole of the owner's correction.

The second is that the artifact already performs one. [The JavaScript target → Running a program](../../khayyam/targets/js/target.md#running-a-program) states at `:70` that the language "has no primitive types, no literal, and no construction form … so every value a program handles was produced outside it — by a method whose implementation the host supplied". The target's host entry makes the same statement as an interface: [`src/run.ts:32`](../../khayyam/targets/js/src/run.ts) asks for "the implementation of each body-less method, keyed by the URI of the unit that declares it". Every mechanism a program needs in order to reach its host is therefore already present, and none of them is named by a document as a concern.

The third is that the three kinds of body-less method leave exactly one of them available. [The JavaScript target → The three kinds of body-less method](../../khayyam/targets/js/target.md#the-three-kinds-of-body-less-method) tells the three apart by their owner: the link form on a capsule, the contract form on an abstraction, and a body with commands, which is compiled. The contract form is closed here — "No artifact carries one, and a call whose receiver is typed as an abstraction is refused where it stands" (`:58`) — and the reason is a language rule rather than a toolchain limitation, because [Abstraction in Khayyam → What You Cannot Do](../../../docs/khayyam/abstraction.md#what-you-cannot-do) states at `:101` that a capsule type may not be an argument or return type in an abstraction's signature. A host facility's arguments are values of concrete types, so the surface this concept needs cannot be an Abstraction.

The fourth is that the link map is the right place for a facility whose implementation is not the host's, and the map holds no entry. [The JavaScript target → The link phase](../../khayyam/targets/js/target.md#the-link-phase) states the entry's shape at `:61` — a module, a protocol document, the checks read at sections of it, the unit's declarations, and the exports that provide them — and states at `:65` that "[t]he map holds no entry, and that is its state rather than a gap in the rule". [`link_map.json`](../../khayyam/targets/js/link_map.json) is `{}`. One constraint on any entry that would stand for a facility package is recorded as open: a link cannot stand in for a `.kh` file that is not there, because the frontend resolves every `in` URI before the target is asked anything ([target.handoff.md:62](../../khayyam/targets/js/target.handoff.md)). So a facility package must exist as source before it can be a link.

The fifth is that the arguments of a host call cannot be written. The language admits no literal ([Khayyam → Separation of Syntax and Governance](../../../docs/khayyam/khayyam.md#separation-of-syntax-and-governance-a-principle) uses the word for the thing the language refuses: "a bare numeric literal `41` may not appear as a value without a named capsule"), no primitive type ([Khayyam → Type Principles Realized](../../../docs/khayyam/khayyam.md#type-principles-realized)), and no construction form. A program therefore hands a host call only values it already holds, and a `vr` cannot carry an initializer inline ([Variable in Khayyam → Variable Declaration Syntax](../../../docs/khayyam/variable.md#variable-declaration-syntax)). The dependency this creates is named in [Implications](#implications).

The sixth is the owner's correction, and it is decisive rather than a preference. A method named `Beep` must not be introduced in Khayyam and linked to JavaScript, because this repository will later implement `Beep` itself in Khayyam, and one name must not stand for both the host's facility and the language's own future method. [Khayyam → Import Mechanism](../../../docs/khayyam/khayyam.md#import-mechanism-in) makes that a structural rule rather than a style: at `:62`, "Name collision is an architecture error, not a language disambiguation problem", with no `as` alias available and the stated remedy being "a root-cause redesign so that one abstraction is the single owner of that concept". A name that stands for two owners has no owner to point a rule at.

### Methodology
The model was derived by the procedure in [Modeling Practice](../../../docs/modeling.practice.md#challenging-a-proposed-concept): the candidate concepts were taken from the owner's own proposal, from the language's decomposition of the foreign-function-interface sentence that names the form, and from the corpus's existing uses of that form, and each was then run against the challenge questions — does an equivalent concept already exist, is it a contextual view of another, is it a new responsibility or only a new name, does it have an independent lifecycle, does it enforce rules no existing concern owns, would the system lose architectural clarity if it disappeared. Node-or-edge standing was then decided by the audit in the same practice, and every surviving candidate was searched against the whole `.kh` corpus for a declaration that already does its job under another name. The candidate set was measured rather than estimated: every `.kh` file outside `build/` was read for a body-less method on a concrete capsule, and every `.kh` file in the tree was searched for a use of the host's own facility names.

Three standing rules shape what follows. **A claim is recorded only where a document or a declaration states it**, with the section it comes from and, for a corpus unit, the file and line; where the corpus is the only witness it is named as such; where nothing answers, the silence is reported as the gap rather than smoothed. **Nothing here designs an implementation.** Where this document names a method it says what the method must mean, never how it is written; a signature, a declaration form, and a file layout are all downstream of questions the paired handoff carries. **The owner's shape is the shape modelled here.** The proposal of a package whose allowed interfaces are all named, with a capsule inside it that reconstructs the command, is kept as given; what this model settles is which of its parts is a concept and which is that concept's caller.

## Explanation

### What the host interface is for
A program runs inside an environment that offers capabilities the program did not write and cannot write down. [Runtime → What a runtime is](../../../docs/protocols/computer/runtime.md#what-a-runtime-is) names those environments as co-equal — "a WebAssembly host is a runtime for modules, a JavaScript engine is a runtime for scripts" — and states at `:31` the rule that makes reaching one legitimate rather than a violation: "Consuming another system's services through interfaces this system's definition already names is not structure acquisition." The host interface is what that sentence's "interfaces this system's definition already names" is made of, in a language that admits no literal and no ambient lookup.

Its reach is exactly one act: a program asks the environment to perform a capability it offers. It excludes three things a reader will expect here, each owned elsewhere. **What the program itself can do** belongs to this repository's own libraries, under the compiler's rule that no library name is an intrinsic ([Compiler → The compiler recognizes language primitives, not library names](../../../docs/protocols/computer/compiler.md#the-compiler-recognizes-language-primitives-not-library-names)). **What the environment is** is [Runtime's](../../../docs/protocols/computer/runtime.md) subject, and it deliberately refuses to be narrowed to a language's virtual machine (`:16`). **What a capability's result means** belongs to the program, which is the direction of travel the whole separation establishes.

### The concepts

#### Host Facility
A capability the host offers, named in the host's own vocabulary and shaped by the host's own rules.

Its distinguishing property is that **its name and its meaning are not this repository's to choose.** `HTMLAudioElement.Beep` is the working example and the corpus already holds it: [`modules/gui/protocol/element-status.kh:86`](../../gui/protocol/element-status.kh) carries `// HTMLAudioElement.Beep = function (duration, frequency, volume, type, callback) {` and `:75` carries the `AudioContext` it needs, both inside a block marked at `:71` "TODO(js-idea): archived memar-js source, not Khayyam and not a migration". The host decides the argument order, the optionality, whether the capability exists in this version of this host, and what it returns; none of that is a Khayyam decision and none of it may be restated as one.

**Node.** It has an independent lifecycle — the host's release cycle, which this repository does not participate in — and it enforces rules nothing else owns: that its name belongs to the host, that its arguments mean what the host says they mean, and that its presence or absence is not a fact about the program. It survives the challenge test as an existing concept this model attaches to rather than defines, the way [Provisioning](#provisioning) is.

**Collides with** nothing this repository declares, and is **not declared** by any `.kh` file. It is named in nine places in the corpus, and every one is a commented-out line of archived JavaScript.

#### Facility Interface
A capsule that stands for one Host Facility, holds what that facility's call needs, and declares one body-less method whose implementation the host supplies.

This is the concept the owner's proposal describes, and it is the one this model concludes is real. Its distinguishing property is that it is **the only thing in the design that must exist before any call can be written**, and that it is per-facility: one capsule per host facility, each carrying that facility's own arguments and each naming no host method in this repository's vocabulary.

Its shape follows from three language statements rather than from a preference. The receiver must be a concrete capsule, because the foreign-function-interface form is a body-less method on a capsule and the contract form is refused at the call site ([target.md:58](../../khayyam/targets/js/target.md)). The method must be body-less, because that is what [Khayyam → Method](../../../docs/khayyam/khayyam.md#method) says asks for an externally provided implementation. And its arguments must be values the program already holds, because the language admits no literal and a `vr` carries no initializer — which is the dependency named below, not a property of this concept.

**Node.** It has an independent behavioral boundary — a host can be replaced, or a program moved to a host that offers different facilities, without any method body that calls the interface changing — and it enforces rules no existing concern owns: that exactly one host facility stands behind it, and that the name it carries is this repository's name for that facility rather than the host's name for its method.

**Collides with** `Adaptor`, which this repository already holds and which is described under [The names to use and the names to refuse](#the-names-to-use-and-the-names-to-refuse), and it is **not declared** by any `.kh` file.

#### Provisioning
The arrival, from outside the program, of the implementation that makes an operation executable.

This is not a new concept and this model does not define it. [Khayyam → Method](../../../docs/khayyam/khayyam.md#method) names the form, and the sibling [Construction model](../../process/construction/model.md) named the responsibility at `:120`, on the ground that "in this repository, **every** value a program handles is obtained by provisioning". This model's reason for naming it is the boundary it draws and the limit it states: a Facility Interface is *performed by* provisioning, and what arrives is the execution of a capability rather than a value — which is one step past the wording the construction model uses, and that step is carried in the paired handoff rather than settled here.

**Node.** It survives the challenge test as an existing concept this model attaches to, and it is **already declared** — by the language, not by a `.kh` file.

#### Host Call
Not a concept of this model, and the answer to the question the owner's proposal raises about which of its two halves is the concept.

A host call is the operation by which a Facility Interface is performed. It has no responsibility of its own: it is one provisioned method plus the artifact's existing call convention, and it performs whatever interface it is handed. Two facts settle it. The first is that [Compiler → The compiler recognizes language primitives, not library names](../../../docs/protocols/computer/compiler.md#the-compiler-recognizes-language-primitives-not-library-names) forbids the compiler from treating the library-provided operation as an intrinsic "because they are common, useful, or imported from a privileged package" — so the owner's phrase "the compiler performs the same call in JavaScript" is not the compiler's act at all; it is provisioning supplying an implementation, which is what [target.md:57](../../khayyam/targets/js/target.md) and [`run.ts:32`](../../khayyam/targets/js/src/run.ts) already do. The second is that a concept which adds no responsibility is a new name, and under [Modeling Practice → Node Classification Audit](../../../docs/modeling.practice.md#node-classification-audit) a label earns a node only when it carries rules no other concern owns and opens a relation the model recognizes.

**Node.** Refused: it is a relation and a mechanism. Which of the two is the concept is settled in [The relations](#the-relations).

#### Facility Presence
Whether the host offers a named facility at all, and what follows for a program that asked for one that is absent.

Not a concept, and the finding here is sharper than a refusal. A facility may be missing — the corpus's own example needs an `AudioContext` ([element-status.kh:75](../../gui/protocol/element-status.kh)) that a host may not have — and nothing in the language, the compiler protocol, the runtime protocol, or the link map decides what happens then. That is not a responsibility waiting to be discovered; it is a **rule with no owner**, which is the shape [Modeling Practice → Premature Classification Check](../../../docs/modeling.practice.md#premature-classification-check) and [Modeling → Classification Emerges From Rules and Relations](../../../docs/modeling.md#classification-emerges-from-rules-and-relations-not-from-intrinsic-labels) both refuse as a node, because the node would represent a "must/should/cannot" statement. Under [Constraints Belong to the Constraining Concern](../../../docs/modeling.md#constraints-belong-to-the-constraining-concern) the rule belongs to whoever constrains, and here that is the host — with one consequence recorded below, that no check in this repository can reach it.

**Node.** Refused: a rule, not a responsibility. The three states a reader needs — the rule is unowned, the tooling check that would catch an absent facility does not exist, and the shape is currently indistinguishable in source from an accidentally empty body — are stated in [What neither states](#what-neither-states) and carried in the handoff.

#### Host Interface Package
A set of Facility Interfaces, one per facility its owner chooses to expose, gathered under one name so that a program may name the set rather than each member.

Not a concept of this model. [Modularity](../../../docs/modularity.md) defines a Module as a System under a modular boundary with a coherent responsibility, and this package is one. What the package needs beyond that existing concept is a boundary discipline, and it is stated in [The relations](#the-relations) rather than modelled as a thing. Its *name* is a separate question and is answered in [The names to use and the names to refuse](#the-names-to-use-and-the-names-to-refuse).

**Node.** Refused: an equivalent concept exists and is owned elsewhere.

### The vocabulary separation, and why it is what makes this concept honest
This is the model's central claim, and it is not a naming preference.

A name in a program is the only handle a reader, a reviewer, a tool, and a governance rule have on what a piece of source means. [Khayyam → Self-Documenting Code and Naming](../../../docs/khayyam/khayyam.md#self-documenting-code-and-naming) makes the name carry what a prose comment would otherwise carry, and [Modularity in Khayyam → Naming Without Package Context](../../../docs/khayyam/modularity.md#naming-without-package-context) makes a name "state its own domain meaning rather than relying on a package prefix to supply missing context". So when one name stands for a host's capability and for this repository's own future method — `Beep` on both sides — every layer that consults the name is consulting two meanings at once and cannot tell them apart. The corruption is not only in the reader. A rule that governs one meaning cannot be written, because [Linter → A rule's home is its subject's document](../../../docs/protocols/computer/linter.md#a-rules-home-is-its-subjects-document) requires the claim to have a subject, and a name claimed by two owners has none. A conformance record cannot be written, because the link map's per-entry check is recorded against a protocol document, and one document cannot be the standard for two unrelated facilities. And a replacement cannot be scoped: when the host changes or drops a facility, there is no way to tell which of the two meanings moved.

The separation is what makes each name answerable, and answerable to exactly one owner. The facility's name is the host's, in the host's own spelling, in the host's own documentation; the interface's name is this repository's, in this repository's qualified-name form, in a protocol document; and the correspondence between them is one declared, checkable, per-facility record rather than a coincidence of spelling. That is the same guarantee-and-meaning split [OS → The OS responsibility boundary](../../../docs/protocols/computer/os.md#the-os-responsibility-boundary) draws at the layer below — "The OS provides guarantees; the architecture defines meaning" — applied at the boundary between a program and the environment running it.

And there is a second, harder reason, which is that the alternative is forbidden rather than merely worse. [Runtime → A runtime does not establish structure](../../../docs/protocols/computer/runtime.md#a-runtime-does-not-establish-structure) states that "any mechanism whose operation *establishes* this system's structure at execution time is a violation of the default path", and the same paragraph blesses exactly what this concept does: consuming another system's services through interfaces this system's definition already names. A host facility reached under a name the language owns would not be that. The program's own definition would be silent about where the capability came from, and the environment would be supplying part of the definition — the failure [Runtime → Motivation](../../../docs/protocols/computer/runtime.md#motivation) calls a second place the definition is written. Keeping the two vocabularies apart is therefore not tidiness; it is the condition under which reaching a host facility is consumption rather than structure acquisition at all.

### What each concept owns, and what it does not own
**Host Facility** owns its own name, its own argument order and optionality, its own failure behaviour, and whether it exists in a given host. It does not own how a program asks for it, whether any program does, what a program does with what it returns, or whether this repository has heard of it.

**Facility Interface** owns the correspondence between one host facility and the way this repository's own code names it: the declaration, the argument types in this repository's own vocabulary, the shape of the call as this repository writes it, and the record of the provision that carries it. It does not own the host's meaning for any argument, the host's choice of name, whether the facility is present, the argument *values*, or what a caller does with the result.

**Provisioning** owns what arrives from outside a program and when it becomes reachable to it. It does not own what the arrived implementation means — [Method in Khayyam → Body-less Methods](../../../docs/khayyam/method.md#body-less-methods-ffi-and-contracts) says the implementation is "provided by" the external phase, not specified by it — and it does not own which facilities exist or which names they carry.

Three concerns a reader will expect here are owned elsewhere, and this model does not absorb them:

- **What the environment is, and what it guarantees.** [Runtime](../../../docs/protocols/computer/runtime.md) owns it, and it deliberately refuses to be narrowed to a language's virtual machine (`:16`). A Facility Interface says nothing about which host it will meet.
- **What a program is allowed to do with what it holds.** That is this repository's own libraries' subject, under the compiler's rule that no library name is an intrinsic.
- **How a facility's result is used.** Nothing in this concept constrains it; [Type → Structure Is Fixed by Definition](../../../docs/type.md#structure-is-fixed-by-definition) keeps provenance and capability questions out of the language's scope.

### The relations
**A Facility Interface stands for exactly one Host Facility.** One interface per facility, and a facility reached through exactly one interface, so that the correspondence is a bijection and can be re-derived from the declarations rather than inferred. The direction runs from interface to facility because the interface is what a program holds and the facility is what it stands for — [Modeling → Modeling Requires Explicit Relationship Analysis](../../../docs/modeling.md#modeling-requires-explicit-relationship-analysis) puts this on the node whose lifecycle the reference is bound to, and here the program's lifecycle governs. This relation already exists in this repository under another name and another purpose: a **reference** edge in [Modeling → Edge Types](../../../docs/modeling.md#edge-types-and-their-traditional-counterparts), which is "a named pointer from one node to another that the referencing node depends on but does not own".

**A Facility Interface is performed by Provisioning.** The arrival supplies what the call needs in order to run; the reverse is meaningless, since a provision with no interface to perform is a mechanism no program reaches. The language states the realization and not the relation: [target.md:70](../../khayyam/targets/js/target.md) records that in this repository every value was produced outside the program, and the same shape appears at [`bootstrap/construct.kh:26`](../../khayyam/targets/js/bootstrap/construct.kh) where `Make` is body-less and therefore provisioned.

**A Facility Interface names no method of a Host Facility.** This is the separation stated in the previous section, and it is recorded here as a relation because it is what makes the first two re-derivable: given the declarations, a reader can tell which names are this repository's and which belong to the host, and a tool can check the rule without knowing any facility's meaning. The language states no such rule; that silence is the model's sharpest finding and it is stated under [What neither states](#what-neither-states).

**A Host Interface Package is a Module of Facility Interfaces, and the compiler may not hold it by name.** One package per host family, replaceable per organization, with the compiler recognizing no name in it. The direction runs from package to interface because the package is a boundary over them. [Compiler → The compiler recognizes language primitives, not library names](../../../docs/protocols/computer/compiler.md#the-compiler-recognizes-language-primitives-not-library-names) states the second half — it "does not treat library-provided operations as intrinsics because they are common, useful, or imported from a privileged package" — and [Modeling → Extensible Behavior Belongs to Pluggable Modules](../../../docs/modeling.md#extensible-behavior-belongs-to-pluggable-modules) gives the general form for the first: a concern's model exposes attachment points rather than growing to absorb every variation. The corpus's precedent for how a *reader* is told a package is this repository's own is [the qualified names rule](../../khayyam/rules/qualified-names/qualified-names.md), and the evidence that this repository has already paid for a violated version of it is [`modules/gui/navigator.kh:20`](../../gui/navigator.kh), which records a numbered counter fallback `GUI_Navigator_2` "until a naming decision".

**A Facility Interface's arguments are values the program already holds.** The direction runs from the arguments to construction because nothing else produces them. This is the model's one dependency on a model that has not been written, and it is stated rather than designed around.

**A link-map entry may stand for the unit that declares Facility Interfaces, and only where that unit exists as source.** The direction runs from entry to interfaces because the entry's declarations stand in for the unit's ([target.md:61](../../khayyam/targets/js/target.md)), which is why a linked facility package must be a real `.kh` file at a real URI even when nothing compiles it. The measured constraint is [target.handoff.md:62](../../khayyam/targets/js/target.handoff.md): the frontend resolves every `in` URI before the map is asked anything, so a link can only replace a unit that is there.

**A Host Facility may be absent, and no concern in this repository decides what follows.** The direction runs from facility to host because the host is what constrains. Under [Constraints Belong to the Constraining Concern](../../../docs/modeling.md#constraints-belong-to-the-constraining-concern) the constraint's state — which facilities this host offers, and what a program does about one it does not — belongs to the host and is not duplicated onto each interface. No document in this repository states that rule, and the finding is that it is unowned rather than misplaced.

### The names to use and the names to refuse
**Use `Host Facility`** for what the host provides. The word is unreferenced anywhere in this repository's documentation, so under [Terminology → The Default Meaning of an Unreferenced Term](../../../docs/terminology.md#the-default-meaning-of-an-unreferenced-term) it carries its ordinary sense and nothing more, which is exactly the standing a name borrowed from a host needs.

**Refuse `Capability` for it.** [OS → The OS responsibility boundary](../../../docs/protocols/computer/os.md#the-os-responsibility-boundary) states each requirement area "as a capability and a constraint", and [OS → Identity: principals, not users](../../../docs/protocols/computer/os.md#identity-principals-not-users) uses the word in its privilege sense — "something that can hold exclusive access, be granted capabilities, and be held accountable for what it does with them" — beside the capability-based systems it cites. `HTMLAudioElement.Beep` grants no authority over anything, and a reader who met `Capability` in this repository's documents would read a security concept.

**Use `Facility Interface`** for the capsule, and always write the compound in full. **Refuse the bare `Interface`.** The word is already this repository's word for an abstraction: [Abstraction in Khayyam](../../../docs/khayyam/abstraction.md) states that an abstraction "does not contain logic, state, or even predefined method bodies", and the corpus uses it that way — [`modules/gui/protocol/application.kh:8`](../../gui/protocol/application.kh) telling the reader to "assign to it by any object implement protocol.Application", and [`modules/lib/adaptors/adaptor.kh`](../../lib/adaptors/adaptor.kh) carrying a `ReadAdaptor` that adapts an interface. A reader meeting "interface" expects an `ab`; what this model names is a `cp`, and the fact that it must be a `cp` is not negotiable here because of [`abstraction.md:101`](../../../docs/khayyam/abstraction.md#what-you-cannot-do). The compound's second half is therefore load-bearing and cannot be dropped.

**Refuse `Host` as a type name**, and use [`Runtime`](../../../docs/protocols/computer/runtime.md) for the environment. `Host` is the word this repository already uses for the process that loads and runs an artifact — [Compiler → Entry and lifecycle are not grammar](../../../docs/protocols/computer/compiler.md#entry-and-lifecycle-are-not-grammar) names "a JavaScript host" as a configuration choice, and [target.md:68](../../khayyam/targets/js/target.md) says "a host is asked for one entry" — which is the toolchain's word and keeps it. It is also the word the display contract uses for a different thing entirely: the `capsule` role in [`display.json`](../../khayyam/display/display.json) reads "A class, in the host's sense of a stateful declared type", where the host is the editor and CSS. And the corpus already uses it for a third: [`modules/gui/protocol/navigator.kh:173`](../../gui/protocol/navigator.kh) reads `window.location.host !== goUrl.host` inside a comment, where it is a URL authority.

**Use `Provisioning`** for what arrives, following the sibling model, and do not coin a second word for the host's case. **Refuse `Bind`, `Bridge`, `Shim`, `Wrapper`, and `Marshal`** for the correspondence. Each is an unreferenced word carrying a mechanism's ordinary sense — a wrapper *copies*, a bridge *joins two things that were separate*, a marshal *converts a representation* — and none of them is what a declared capsule standing for a named host capability does. A reader who met "wrapper" would look for a copy and find none, and "marshal" would promise a conversion this model explicitly refuses to perform.

**Refuse `Adaptor` for it, and record the collision.** The corpus already holds the neighbouring concept under that name, in the sense the archive's own Go wrote it: [`modules/lib/adaptors/adaptor.kh:14`](../../lib/adaptors/adaptor.kh) declares `type ReadAdaptor func(p []byte) (n int, err error)` and `:16` wraps it so the result is `err error_p.Error`, and [`modules/lib/adaptors/String/stringer.kh:8`](../../lib/adaptors/String/stringer.kh) declares `tp Stringer_GO ab` with `ToGoString` at `:10` and `FromGoString` at `:12`, whose entire stated purpose at `:7` is "to prevent protocol package not couple to a implementation package(fmt)". An Adaptor's responsibility is **translation**: it takes a foreign signature and restates it in this repository's vocabulary, including its error type. A Facility Interface's responsibility is the opposite — it holds the correspondence to a facility **without** translating the facility's name or its meaning, because translation is precisely what makes the host's vocabulary leak into the language's. Two concepts, one neighbourhood, opposite responsibilities. Under [Khayyam → Import Mechanism](../../../docs/khayyam/khayyam.md#import-mechanism-in) two declarations claiming one name would be an architecture error, so the names must not meet.

**Refuse every host facility's own method name as a Khayyam method name**, `Beep` being the owner's example. This is the owner's correction and it is also the corpus's problem: [`modules/gui/protocol/element.kh:166`](../../gui/protocol/element.kh) writes `//     HTMLAudioElement.Beep(400, 100, 5)` in a commented block marked at `:62` "TODO(js-idea): archived memar-js JavaScript, not Khayyam and not a migration", and the same call appears again at `:214`, `:338`, `:386`, `:470`, and `:632`; [`modules/process/error/protocol/error.kh:116`](../../process/error/protocol/error.kh) and `:311` carry the owner's own example verbatim, `HTMLAudioElement.Beep(500, 100, 5)`, in the same kind of block. Nine occurrences, zero declarations. Whatever this concept is finally called, it is not a method named after the host's method.

**Refuse `JS` as the package's name**, while keeping the package the owner proposed. Three grounds, in order of weight. [Documentation → File Naming](../../../docs/documentation.md#file-naming) requires a name to "communicate meaning, preserve conceptual boundaries, avoid implementation-specific vocabulary, and stay stable over time", and a name that is one host's language is implementation-specific vocabulary for a responsibility that is not: [modules/khayyam/README.md:21](../../khayyam/README.md) already plans `wasm`, `c`, and `asm` beside `js` as first-class targets. A package named after the host's language makes a host-independent concern look host-specific and guarantees a second package when the second host arrives. Second, the corpus already holds `JS` as a name for something else: [`modules/modules/gui/services/new-page/response.kh:8`](../../modules/gui/services/new-page/response.kh) writes `JS, HTML, CSS, JSON []byte` and [`logic.kh:26`](../../modules/gui/services/new-page/logic.kh) writes `JS: jsBuf.Bytes()`, where `JS` is the generated script of a page — a *different* thing under the same word, in the same repository. Third, [`modules/lib/process/command/cli.kh:120`](../../lib/process/command/cli.kh) already prints "Make Achaemenid service JS-SDK", so `JS` is a settled word for a generated SDK in this corpus. What the model uses instead is a name that carries the responsibility — the compound `Host_` prefix the qualified-names rule already produces — and the owner's shape is otherwise untouched.

**For the operation that performs an interface, use the language's own word for reaching a method's behaviour, and state the requirement the name must meet rather than fixing it here.** The name must not be a host method name, must not collide with a method this repository will write, and must say that the call leaves the program. `Perform` satisfies all three and is offered as this model's choice rather than as a ruling; `Call`, `Invoke`, `Execute`, and `Eval` are refused as *concept* names, being unreferenced words for mechanisms.

**Refuse `FFI` as a Memar term for this concept.** It is the language's word for the *form* — [Khayyam → Method](../../../docs/khayyam/khayyam.md#method) and [Method in Khayyam → Body-less Methods](../../../docs/khayyam/method.md#body-less-methods-ffi-and-contracts) both use it — and the form is not what this model is about: every `.kh` body-less method in the corpus is an instance of that form whether or not its host is JavaScript, and the contract form is the same spelling. Naming the concept by the spelling of one ecosystem's form would make a host-independent concern look like a JavaScript concern.

**Refuse `Literal`** for whatever a Facility Interface's call is given. [Khayyam → Separation of Syntax and Governance](../../../docs/khayyam/khayyam.md#separation-of-syntax-and-governance-a-principle) uses the word for the thing the language refuses, so calling the argument a literal would name the absence as the presence — the same refusal the sibling model records at [`modules/process/construction/model.md:126`](../../process/construction/model.md). **Refuse `Slot`** as a concept name, on the sibling model's ground that it belongs to one target's reading ("A variable is a cell", [target.md:50](../../khayyam/targets/js/target.md)) and not to the language, whose word is *variable*.

### What the language documents already state
Nine things are stated, and every one is usable without extending the grammar. Together they are the answer to whether a host interface can be declared today.

1. **A body-less method on a concrete capsule asks for an externally provided implementation.** [Khayyam → Method](../../../docs/khayyam/khayyam.md#method) states it for the receiver being a `cp`, and [Method in Khayyam → Body-less Methods](../../../docs/khayyam/method.md#body-less-methods-ffi-and-contracts) repeats it at `:80`. This is the whole mechanism.
2. **A call's receiver must be a concrete type for this form to be reachable.** The contract form carries no implementation and a call whose receiver is typed as an abstraction is refused where it stands, per [target.md:58](../../khayyam/targets/js/target.md); and [Abstraction in Khayyam → What You Cannot Do](../../../docs/khayyam/abstraction.md#what-you-cannot-do) forbids a capsule in an abstraction's signature at `:101`. A host interface therefore cannot be a contract, and this is a language fact rather than a toolchain limitation.
3. **A method may be attached to any type**, including a capsule — [Khayyam → Method](../../../docs/khayyam/khayyam.md#method) states the owner is not limited to capsules. A facility interface may therefore hang on a purpose-built capsule and need not be forced onto anything else.
4. **Every variable of a call is passed strictly by reference**, owner and both groups alike, per [Method in Khayyam → Key Rules](../../../docs/khayyam/method.md#key-rules); the artifact realizes it as one cell per variable, with an influencing variable handed over as the value the slot holds and the influenced group handed over as the slot itself, per [target.md:50](../../khayyam/targets/js/target.md). A facility's arguments are therefore influencing variables handed by value, and anything the host writes back arrives in a slot the caller declared.
5. **Both call groups are mandatory** and a call writes both — [Khayyam → Method Invocation Rules](../../../docs/khayyam/khayyam.md#method-invocation-rules). A facility call declares its influenced group even when it writes nothing.
6. **The compiler recognizes language primitives, not library names**, and specifically not operations "imported from a privileged package" — [Compiler → The compiler recognizes language primitives, not library names](../../../docs/protocols/computer/compiler.md#the-compiler-recognizes-language-primitives-not-library-names). This is what keeps a facility package a library rather than a grammar extension, and it is the rule that makes [Host Call](#host-call) not the compiler's act.
7. **Entry and lifecycle are configuration, not grammar** — [Compiler → Entry and lifecycle are not grammar](../../../docs/protocols/computer/compiler.md#entry-and-lifecycle-are-not-grammar). The host's entry request already carries "the implementation of each body-less method, keyed by the URI of the unit that declares it" ([`run.ts:32`](../../khayyam/targets/js/src/run.ts)), which is where a provision arrives and which also says that a program cannot be satisfied by an implementation keyed to a unit other than the one that declares the method.
8. **A name collision is an architecture error** — [Khayyam → Import Mechanism](../../../docs/khayyam/khayyam.md#import-mechanism-in) at `:62`. This is the structural form of the owner's correction.
9. **There are no primitive types, no literal, and no construction form** — [Khayyam → Type Principles Realized](../../../docs/khayyam/khayyam.md#type-principles-realized), [Khayyam → Separation of Syntax and Governance](../../../docs/khayyam/khayyam.md#separation-of-syntax-and-governance-a-principle), and [target.md:70](../../khayyam/targets/js/target.md). Every value a program handles was produced outside it, and [Variable in Khayyam → Overview](../../../docs/khayyam/variable.md#overview) assigns the producing act to "capsule behavior" without saying what discharging it consists of.

### What a library over them could provide
Given the nine, the following is available today as a `.kh` library and is not a language change:

- **A package whose members are Facility Interfaces**, one capsule per host facility, each declaring exactly one body-less method whose signature uses this repository's own argument types and whose influenced group names whatever the host writes back. The declaration needs no literal, no initializer, and no construction.
- **A provision for each interface**, arriving through the entry protocol the run already implements: the host is asked for "the implementation of each body-less method, keyed by the URI of the unit that declares it" ([`run.ts:32`](../../khayyam/targets/js/src/run.ts)), so a facility's execution needs no grammar, no compiler knowledge, and no new runtime.
- **A link-map entry for the package's unit**, where the implementation lives in a conformant module rather than in the host. The entry's shape is stated at [target.md:61](../../khayyam/targets/js/target.md) and enforced in [`src/link.ts:70`](../../khayyam/targets/js/src/link.ts): an entry naming no module, no protocol document, no recorded check, no provided export, or no declaration is refused before anything is compiled, and a recorded check standing at a section the document does not have is refused by [`checkLinks`](../../khayyam/targets/js/src/link.ts) — so a facility's conformance record is a checkable artifact rather than a claim.
- **A Test for each facility's contract**, per [Test → A Test's Subject Is a Named Process](../../../docs/protocols/process/test.md#a-tests-subject-is-a-named-process): a facility interface is a named thing whose expectations can be written before its provision exists, and a host that offers a facility it cannot honour fails a check that was about the contract.
- **A vocabulary that is inspectable.** The display contract's own principle — "A role names what an identifier IS, never where it appears" ([`display.json`](../../khayyam/display/display.json)) — is what a separated vocabulary makes possible, and the interface names it produces are ordinary declarations to every existing tool.

### What neither states
These are the gaps. Each is a place where a document is silent, and the silence is the finding.

**Who owns the name of a provision.** Nothing in the language, the compiler protocol, the runtime protocol, or the link map says that the name a body-less method carries belongs to the program rather than to whoever supplies the body. [Khayyam → Method](../../../docs/khayyam/khayyam.md#method) says the implementation "will be provided externally during the linking phase" and stops; it does not say whose name that is. This is the gap the owner's correction exposes and it is the one this model most needs closed, because the whole separation rests on it. What would close it is a sentence in [Khayyam → Method](../../../docs/khayyam/khayyam.md#method) or [Method in Khayyam → Body-less Methods](../../../docs/khayyam/method.md#body-less-methods-ffi-and-contracts) stating that a body-less method on a capsule is a *provision* — a declaration whose name and meaning this repository owns and whose execution the host supplies — as against the alternative, which is that a body-less method is a *hole* and the name it carries is the host's. Those two readings cannot both hold, and the corpus already contains a case where they cannot be told apart (below).

**That a body-less method is distinguishable from an empty one.** The language's own documents disagree with each other about which spelling declares one, and the parser sides with the second. `docs/khayyam/khayyam.md:89` and `docs/khayyam/method.md:77` both write the form as `{}` — "A method can be defined without a body (`{}`)" — while `docs/khayyam/abstraction.md:60` and `docs/khayyam/khayyam.practice.md:63` write it as a declaration that ends at its third group. The parser reads a method's body through `parseBlock()` ([`core/src/parse.ts:219`](../../khayyam/core/src/parse.ts)), which returns `null` when no `{` follows that group, and [`targets/js/src/program.ts:283`](../../khayyam/targets/js/src/program.ts) reads that `null` as the whole difference between an implemented method, a contract, and a supply. So a declaration carrying `{}` is a method with a body and an empty body, not a provision. The corpus is the witness on both sides: [`modules/gui/initialize.kh:6`](../../gui/initialize.kh) writes `tp Initialize mt (self GUI_Application_2) () () {}` and `:8` records "Go body is empty and is ported as an empty body `{}`; khayyam.md → Method writes 'without a body (`{}`)' for the FFI form, so confirm an empty body is not read as external"; [`modules/gui/navigator.kh:13`](../../gui/navigator.kh) and `:18` carry the same two declarations with the same worry recorded at `:21` and `:23`. Those three are the corpus's only doubtful readings, and under the parser's own reading none of them is body-less — the doubt is well founded and, resolved against the corpus, resolves in the corpus's favour. A facility interface's whole purpose is to be a body-less method, so this is the ambiguity the concept inherits and cannot escape, and the unremarked cases on the other side of it are counted under [What the corpus and the link map show](#what-the-corpus-and-the-link-map-show). What would close it is a governance rule — not a grammar change, by [Khayyam → Minimal Legislation](../../../docs/khayyam/khayyam.md#minimal-legislation-a-principle) — in the shape of [`modules/khayyam/rules/`](../../khayyam/rules/), stating that a body-less method on a capsule records the provision that supplies it. The rule's claim has no home document today, and [Linter → A rule's home is its subject's document](../../../docs/protocols/computer/linter.md#a-rules-home-is-its-subjects-document) says the claim must have one first.

**Whether a facility can fail, and what it returns.** Nothing states that a host call is fallible, so nothing states whether its influenced group carries an `Error`. [Control Flow → Error Propagation](../../../docs/protocols/process/control-flow.md#error-propagation) requires every fallible operation to expose its error path "as an ordinary, named part of the call contract", but that is a protocol's requirement over a library rather than a grammar obligation, since [Khayyam → The Grammar Refuses Protocol Semantics](../../../docs/khayyam/khayyam.md#the-grammar-refuses-protocol-semantics) declines protocol semantics entirely. The corpus disagrees with itself rather than offering no witness: of the 59 body-less methods on a concrete capsule, 35 declare an `err Error` output and 24 declare something else or nothing, and not one of the 59 was written as a host provision. What would close it is a statement in [`docs/khayyam/variable.md`](../../../docs/khayyam/variable.md) or [`docs/khayyam/method.md`](../../../docs/khayyam/method.md) about whether a provision's execution can fail, and [The Error](../../../docs/protocols/process/error.md) for which class a failure carries.

**Whether a facility that the host does not offer is caught anywhere.** Not at build time and not at run time, by anything in this repository. The link map's checks are about an entry's own record — module readable, protocol document readable, every recorded check standing at a section the document has ([`link.ts:201`](../../khayyam/targets/js/src/link.ts)) — and none of them asks whether the host offers the facility. The run asks only for implementations the host chooses to supply ([`run.ts:32`](../../khayyam/targets/js/src/run.ts)). Under [Constraints Belong to the Constraining Concern](../../../docs/modeling.md#constraints-belong-to-the-constraining-concern) the rule is the host's to state and no document in this repository states it.

**How a program obtains an interface value at all.** A program cannot write one: no literal, no construction form, and [Variable in Khayyam → Variable Declaration Syntax](../../../docs/khayyam/variable.md#variable-declaration-syntax) says a `vr` "cannot carry an initializer inline". The corpus's answer today is the host, in four places, none with a `.kh` form — recorded at [`modules/process/construction/model.md:165`](../../process/construction/model.md), of which [`modules/gui/protocol/application.kh:8`](../../gui/protocol/application.kh) is the clearest: "You must assign to it by any object implement protocol.Application on your main.go file", above `vr GUI Application` at `:10`. This is a dependency, not a question, and it is named in [Implications](#implications).

**Whether this concept needs a behaviour as a value.** It does not, and the condition is worth stating because the corpus's own example does. Nothing in this concept requires an `mt` in an argument position: the interface holds values and declares one method, and the provision is that method's implementation. A method-as-value becomes necessary only if reconstruction were held *as a value* rather than being the interface's own provisioned method — and that is exactly what the language cannot currently express. [Method in Khayyam → Type-level arguments for `sc` and `mt`](../../../docs/khayyam/method.md#type-level-arguments-for-sc-and-mt) admits an `mt` in an influencing group and states no spelling for writing one, and the probe written against that silence — [`modules/khayyam/targets/js/bootstrap/behaviour.kh:15`](../../khayyam/targets/js/bootstrap/behaviour.kh), `tp Emit mt (self Text) (body Method) ()` — is refused with `unbound-type-name`, recorded at [target.handoff.md:86](../../khayyam/targets/js/target.handoff.md) and at `:99`. The corpus's own `Beep` takes a callback ([element-status.kh:86](../../gui/protocol/element-status.kh), `@param {function} callback`), so a faithful interface for that one facility would need it. This model therefore does not need it and must not grow a need for it.

### What the corpus and the link map show
Six things are true of this repository's `.kh` corpus and of its link map, and of no document in it.

**The owner's example is already in the corpus nine times and declared zero times.** [`modules/gui/protocol/element-status.kh:86`](../../gui/protocol/element-status.kh) carries the facility's archived definition; [`element.kh:166`](../../gui/protocol/element.kh), `:214`, `:338`, `:386`, `:470`, `:632` carry calls to it; and [`modules/process/error/protocol/error.kh:116`](../../process/error/protocol/error.kh) and `:311` carry the owner's own example verbatim. Every one is inside a block marked as archived memar-js source and not Khayyam — [`element-status.kh:71`](../../gui/protocol/element-status.kh) says "TODO(js-idea): archived memar-js source, not Khayyam and not a migration" and `:72` adds "Kept as a thought only: the architect has moved on since, so this may contradict the current design". So the concept exists in this repository today as commented-out archived JavaScript in two modules, and as a declaration nowhere. The corpus's own verdict on it is recorded at [`element-status.kh:72`](../../gui/protocol/element-status.kh), and this model is that verdict made current.

**The archived design this model formalizes is quoted in the corpus, with its own shape.** [`modules/computer/datatype/protocol/data-type.kh:41`](../../computer/datatype/protocol/data-type.kh) carries the archived README's line "`Memar` as a `JS language library` is a repository wrapper to store all implementation", `:45` carries "Import `/gui/application.js` in main JS file of app", `:48` carries "call `Application.Start()`", and `:49` carries "Use `OS` and `Application` global object data any where like `window`". That is the owner's proposal already made once: a package named for the host's language, into which a host-side module is imported, whose globals a program reaches by name. The corpus holds it under the same "kept as a thought only" marker at `:34` and `:35`. The separation this model makes central is therefore not a new idea in this repository; it is the correction of one the repository already tried and archived.

**The corpus uses the language's host-facing form fifty-nine times, and not once as a host provision.** The method is to read every `.kh` file outside `build/`, match the declaration form `tp {name} mt (self {owner}) (…) (…)` with nothing after the third group, and keep the ones whose `{owner}` is a `cp` declared in the same file. That finds **59** of the **728** body-less declarations in the corpus; the other 664 are the contract form on an `ab` and are what that form should be. Of the 59, eight are under this toolchain's own `bootstrap/` and `demo/` — [`character.kh:19`](../../khayyam/targets/js/bootstrap/character.kh), [`compose.kh:13`](../../khayyam/targets/js/bootstrap/compose.kh), [`construct.kh:26`](../../khayyam/targets/js/bootstrap/construct.kh) and `:28`, [`state.kh:30`](../../khayyam/targets/js/bootstrap/state.kh) and `:32`, [`greeting.kh:15`](../../khayyam/targets/js/demo/greeting.kh) and `:21` — and those eight are the probes this target's handoff measures. The remaining 51 are in [`modules/math/`](../../math) and [`modules/time/duration/`](../../time/duration), and every one of them is the port's own arithmetic or text conversion: 14 `ToString`, 11 `FromString`, 4 `FromString_UnknownBase`, 4 `FromString_Base10`, 2 `Print`, and the `_Equal`, `_FromASCII`, `_ToASCII`, `FromSec`, `ToSecAndNano`, `FromSecAndNano`, `ToNanoSecond` and `FromNanoSecond` families on `W8`…`W64`, `I8`…`I64`, `R32`, `R64`, `Bool`, `Second`, `NanoSecond` and `NanoInSecond`. None of the 51 was meant to be supplied by a host, and under the parser's reading every one of them waits at run time for an implementation this repository does not write. Two corpus records show the form being reasoned about rather than inherited. [`modules/identifier/mediatypes/media-types.kh:13`](../../identifier/mediatypes/media-types.kh) notes that an implementation "uses if, &&, panic, map assignment, and a local var; none has a Khayyam form yet (control flow is a library, not grammar); a body-less mt on a cp means FFI, so the declaration stays commented". [`modules/hardware/cpu/core.kh:14`](../../hardware/cpu/core.kh) records the case the language's form cannot reach at all: "a body-less Khayyam method is the FFI form, but a method needs an owner type and this is a free function, so the owner is undecided", against the `CoreID cp` it already declares at `:3`. Between them: a facility the corpus can see and cannot name, fifty-one declarations the port made in the FFI spelling by inheritance rather than by decision, and one it could not declare at all. That is the shape of this concept's absence, measured rather than argued. The fifty-one are a problem for the owners of `modules/math/` and `modules/time/duration/` and not for this concept; what this concept inherits is the spelling disagreement that makes them count as provisions at all.

**The corpus already holds the neighbouring concept under another name, with the opposite responsibility.** [`modules/lib/adaptors/adaptor.kh:14`](../../lib/adaptors/adaptor.kh) and [`modules/lib/adaptors/String/stringer.kh:8`](../../lib/adaptors/String/stringer.kh) together are the archive's answer to reaching something outside: wrap it, and restate its signature in this repository's types including its error. The corpus names that `Adaptor`, this repository already owns it, and it is the one collision this concept creates. The distinction is in [The names to use and the names to refuse](#the-names-to-use-and-the-names-to-refuse), and the reason it matters here is that the corpus's `Adaptor` also documents the failure mode: `Stringer_GO`'s own stated reason for existing at `:7` is "to prevent protocol package not couple to a implementation package(fmt)", which is the coupling problem a facility interface avoids by keeping the host's name out of this repository's declarations entirely.

**The display contract has no role for a supplied declaration.** [`modules/khayyam/display/display.json`](../../khayyam/display/display.json) declares twenty-one roles, each naming what an identifier *is* — `capsule`, `abstraction`, `method`, `included-type`, `file-uri`, and the rest — and every one of them is a role in a `.kh` source unit. None distinguishes a declaration whose execution the host supplies from one this repository implements, because the host's declarations reach a reader through the link map's `declares` table rather than through source. That is not a defect in the contract; it is the separation this model argues for, visible as a gap in the tooling: a reader cannot be told which declarations are provisions, and the vocabulary that would let them be told does not exist yet.

**The link map holds no entry, and two of its own constraints decide where a facility package must live.** [`link_map.json`](../../khayyam/targets/js/link_map.json) is `{}`, which [target.md:65](../../khayyam/targets/js/target.md) records as the map's state rather than a gap in the rule, and [target.handoff.md:18](../../khayyam/targets/js/target.handoff.md) repeats it. The first constraint is that a link cannot stand in for a `.kh` file that is not there, because the frontend resolves every `in` URI before the map is asked anything ([target.handoff.md:62](../../khayyam/targets/js/target.handoff.md)), so the package's declarations must exist as source at a URI and the map is keyed by that URI's `.kh` form ([`link.ts:165`](../../khayyam/targets/js/src/link.ts)). The second is that a linked unit is never thinner than the unit it replaces, so an entry must declare every capsule, abstraction, and method signature the unit declared, including a method's owner, owner parameter, and both groups ([`link.ts:13`](../../khayyam/targets/js/src/link.ts)). Neither constraint is about host interfaces specifically; both bear on them entirely.

### Implications
- **The host interface's arguments are construction's subject, and this concept cannot be exercised until construction exists.** A host call can only be given values the program already holds, and in this repository every value a program holds was produced outside it ([target.md:70](../../khayyam/targets/js/target.md)). So the interface may be *declared* today and cannot be *called* until something produces a value of the interface's type. The sibling model records the same wall from the other side — an abstraction's signature may name only abstractions while a construction's result is a concrete instance, so no shared construction contract can exist ([`modules/process/construction/model.md:154`](../../process/construction/model.md)) — and this model inherits it rather than working around it. The dependency is named; it is not a question of judgment.
- **The language must state the ownership of a provision's name before the first facility interface is written, and the statement belongs in one of two places.** The claim is grammar-adjacent but not grammatical: [Khayyam → Minimal Legislation](../../../docs/khayyam/khayyam.md#minimal-legislation-a-principle) sends a condition that may differ between realizations to the tool's rules and keeps in the grammar only what a program's well-formedness turns on, and whether a provision's name is the program's or the host's does not change what any program means — it changes what a *reader and a rule* may assume. So the claim belongs to the language's documents as a stated position, and its enforcement belongs in [`modules/khayyam/rules/`](../../khayyam/rules/). The two places that could carry the position today are [Khayyam → Method](../../../docs/khayyam/khayyam.md#method) and [Method in Khayyam → Body-less Methods](../../../docs/khayyam/method.md#body-less-methods-ffi-and-contracts). Until one of them says it, this model's central claim is a modeling decision with no document behind it, and no rule may cite it.
- **A facility interface cannot be a contract, so this package's replaceability is governance rather than dispatch — the same trade the control-flow library makes for a different reason.** [Compiler → The compiler recognizes language primitives, not library names](../../../docs/protocols/computer/compiler.md#the-compiler-recognizes-language-primitives-not-library-names) forbids the compiler from holding the package, and the only remaining route to organizational replaceability is the one [Control Flow → Mechanism Summary](../../../docs/protocols/process/control-flow.md#mechanism-summary) names: an organization configures its Linter to mandate its own approved library. That route needs no language change, and the sibling [control-flow model](../../process/control-flow/model.md) shows what is lost without it — the one measured realization of a two-branch contract in this repository is reachable only by not going through the contract. A facility interface is further from a contract than a branch pair, because [`abstraction.md:101`](../../../docs/khayyam/abstraction.md#what-you-cannot-do) forbids the capsule its arguments are made of, so the trade here is real rather than hypothetical.
- **The vocabulary separation costs the host a naming obligation it does not have today, and that is the price of the honesty.** A host that today offers `HTMLAudioElement.Beep` for free would have to, for every facility a program may reach, publish a declaration under this repository's naming rules, state its arguments in this repository's types, state whether it can fail, and supply the provision keyed by the URI of the unit that declares it ([`run.ts:32`](../../khayyam/targets/js/src/run.ts)). And the program, which today depends on nothing it can see, would depend on a named set — so a host that renames a facility becomes a change in this repository's source. That is the cost the model states rather than omits: the gain is that a program's dependence on its environment becomes a declaration and a checkable record, and the price is that the dependency is now visible and now binds.
- **A compiler written in Khayyam reaches for exactly this concept and nothing else of it.** The target's own measurement puts it at item one: [`bootstrap/character.kh:19`](../../khayyam/targets/js/bootstrap/character.kh) declares `tp CharacterAt mt (self Text) (at Count) (character Character)` with no body, so the probe compiles and the answer is that the only route to a character is a method with no body ([target.handoff.md:82](../../khayyam/targets/js/target.handoff.md)). A self-hosting compiler reads the characters of its own input, so its single largest dependence on its environment is exactly a facility interface. What it does *not* need is the generic entry: it needs the capsule, because the capsule is what it can name.
