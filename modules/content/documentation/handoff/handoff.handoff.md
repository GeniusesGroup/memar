- State: a session plan (`.agents/scripts/services/session_record.py`) has two keys that classify its task, `Topic` (free text, one per plan, what `claims` batches by) and `Kind` (a closed list that says which model tier the task needs), each with its own file, flag and, for Topic, verbs `topic` and `topics`. ### Which plan keys stay keys rather than labels: Status, Priority, and the model a session runs on?
- State: the request names "Topic, TaskKind and future fields" as becoming labels. A label classifies the task: zero or more, and adding one changes nothing about the task's state. `Status` is state with transitions and a vocabulary shared by every Memar document; `Priority` is an order `claims` sorts by; `Title`, `Opened`, `Project`, `Parent`, `Conversation` are identity and links; the model a session is to run on is an assignment of the task to a worker named in `CONTRIBUTORS.md`. ### Do Effort and ReasoningLevel read as how much work the task needs and how hard its hardest judgment is?
- State: the owner named them "needed effort" and "needed level of reasoning" (2026-10-15). ### May a plan carry more than one Topic label, and is a claims batch bounded by model tier as well as by topic?
- State: today a plan has one topic, so that a batch's membership is a plain equality and a task with two subjects is two tasks; `claims` gives one sub-agent the first task's topic. With labels a plan could carry several. A sub-agent runs on one model, so a batch that mixes a design task with mechanical ones runs one of them on the wrong model; `claims` today does not look at `Kind`.
- Options: (1) at most one Topic per plan, and a batch takes only tasks of the first task's `TaskKind` tier (or none stated) as well as its topic, recommended: one context and one model per sub-agent; cost: fewer tasks per batch. (2) several topics per plan, batching by overlap; cost: membership becomes a judgment of overlap, and one task may pull two subjects into one context. (3) bound the batch by the same `AIModelName` instead of tier; cost: queued plans carry no `AIModelName` under the recommendation above.
- Ruling: owner (2026-10-15): no limit on labels, Topic among them, but none assigned needlessly. The revised design keeps membership a plain test: a batch's topic is `--label Topic=T` or the first task's first `Topic` label, and its members are the queued tasks that carry that label, so several topics on one plan do not turn membership into overlap. The model bound is still open, and is now asked against `AIModel`, tiers being gone: (1) a batch takes only tasks whose `AIModel` equals the first one's, an absent one counting as a value, recommended: one sub-agent, one model choice, no design task run on a model chosen for mechanical ones and no mechanical one on the expensive model; cost: fewer tasks per batch. (2) tasks whose `ReasoningLevel` is no higher than the first one's; cost: cheap tasks ride on the expensive model. (3) no model bound; cost: one of the batch runs on a model chosen for another.
- Anchor: `.agents/scripts/services/session_claims.py` (`take`, `batch_report`); `docs/labels-design.md` of session `20261015-T103826Z-16432`, Commands.
- Blocks: the `claims` change. Assumption meanwhile: ruling as above and bound (1) (Tentative).
