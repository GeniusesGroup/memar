# Construction Model

## Abstract
This document is the model of how a program obtains an instance of a capsule in Khayyam, derived from the language's own statements about what a variable declaration does not do, from the artifact one target emits for a capsule class, and from the `.kh` corpus as it stands. It names two concepts and refuses three — **Construction** (the responsibility by which a program obtains an instance) and **Initialization** (the responsibility by which an obtained instance reaches a usable state) are concepts; **Instance** is already a defined role rather than a concern, **Acquisition** is Memory's, and a **Route** is a way of performing construction rather than a thing — and it separates three layers that no document in this repository has separated before. The language states the substrate: a `vr` binds a name and a type and nothing more, a body holds four commands, every variable of a call is handed over by reference, and a body-less method on a concrete capsule is the foreign-function-interface form through which an implementation arrives from outside. It is silent on construction in three places that block any library over it: whether obtaining an instance can fail, whether a construction's influenced group is where the instance arrives, and whether construction is one responsibility or two — and it forecloses the one shape a shared contract could take, because an abstraction's signature may name only abstractions, so a construction contract over concrete capsules cannot be an abstraction. A `.kh` library over the substrate is writable today and the corpus shows its shape: thirty-three `From*` methods on the corpus's own capsules and abstractions, none of which declares a way to hand the instance back. The measurement under [`modules/khayyam/targets/js/bootstrap/construct.kh`](../../khayyam/targets/js/bootstrap/construct.kh) records the same fact from the other side: what fills the slot is the host's. The naming, the fallibility, the abstraction-signature gap, and the ordering of the very first instance are carried in the paired [handoff](./model.handoff.md).

## Introduction

### Motivation
Three failures stand between the language as it stands and any program that needs a value of its own.

The first is that **nothing fills the slot.** A method body may hold a variable declaration, a scope declaration, a method invocation, and the `return` marker — the four commands [the JavaScript target's own document](../../khayyam/targets/js/target.md#the-commands-a-body-may-hold) reads out of the grammar — and a variable declaration binds a slot and no more. [Variable in Khayyam → Overview](../../../docs/khayyam/variable.md#overview) states the consequence in one sentence: "Declaring a variable establishes a name and type relationship. It does not define how the underlying capsule is created or initialized — creation and initialization remain responsibilities of capsule behavior." That sentence names a responsibility and does not say what discharging it consists of. The probe written against it, [`bootstrap/construct.kh`](../../khayyam/targets/js/bootstrap/construct.kh), declares the slot at `:21`, calls a method that writes it at `:22`, and compiles; the test that holds it, [`bootstrap.test.ts`](../../khayyam/targets/js/test/bootstrap.test.ts), reads the finding at `:63` as "What fills the slot is still the host's."

The second is that **the artifact has a seam the source cannot name.** The emitted class takes an optional object of values in its constructor and gives each declared field one cell ([`emit.ts:518`](../../khayyam/targets/js/src/emit.ts) writes `constructor(values)`; [`target.md:43`](../../khayyam/targets/js/target.md#a-field-is-a-variable) states the shape), so a host can hand a capsule its fields. What no source can say is the sentence that asks for that. The same document draws the boundary at [`target.md:70`](../../khayyam/targets/js/target.md#running-a-program): the language "has no primitive types, no literal, and no construction form … so every value a program handles was produced outside it — by a method whose implementation the host supplied."

The third is that **the corpus already reached for construction and stopped.** Thirty-three declarations across the corpus are named `From*`, and each attaches to the type it produces rather than to an instance of it — [`modules/math/integer/unsigned-32.kh:16`](../../math/integer/unsigned-32.kh) reads `tp FromString mt (self W32) (str String) (err Error)`, and [`modules/codec/string/protocol/stringer.kh:16`](../../codec/string/protocol/stringer.kh) reads `tp FromString mt (self Stringer_From) (str String) (err Error)`. Not one of them carries an influenced variable of the type it produces. Under [Method in Khayyam → Key Rules](../../../docs/khayyam/method.md#key-rules) the influenced group is where a call's result arrives, and under [`target.md:50`](../../khayyam/targets/js/target.md#the-artifact-of-one-unit) that group is handed over as the slot itself. So the corpus holds thirty-three names for the responsibility and zero declarations that discharge it.

### Methodology
The model was derived by the procedure in [Modeling Practice](../../../docs/modeling.practice.md#challenging-a-proposed-concept): the candidate concepts were taken from the requirement as stated, from the language's own decomposition of the sentence that creates the responsibility, and from the corpus's thirty-three `From*` declarations, and each was then run against the challenge questions — does an equivalent concept already exist, is it a contextual view of another, does it introduce a responsibility or only a name, does it have an independent lifecycle, does it enforce rules no existing concern already owns, would the system lose architectural clarity if it disappeared. Node-or-edge standing was then decided by the audit in the same practice, and every surviving candidate was searched against the whole `.kh` corpus for a declaration that already does its job under another name.

Two standing rules shape what follows. **A claim is recorded only where a document or a declaration states it**, with the section it comes from and, for a corpus unit, the file and line; where the corpus is the only witness it is named as such; where nothing answers, the silence is reported as the gap rather than smoothed. **Nothing here designs an implementation.** Where this document names a method it says what the method must mean, never how it is written; a signature, a file layout, and a declaration form are all downstream of questions the paired handoff carries.

## Explanation

### What construction is for
Construction is the responsibility a program discharges when it needs a value of a named Type and does not hold one. That is its whole reach, and the reach is narrow for a reason the language states: [Khayyam → Separation of Syntax and Governance](../../../docs/khayyam/khayyam.md#separation-of-syntax-and-governance-a-principle) lists "a bare numeric literal `41` may not appear as a value without a named capsule" as an example of a decision that creates or denies existence and therefore belongs in syntax, and [Type Principles Realized](../../../docs/khayyam/khayyam.md#type-principles-realized) adds that there are no primitive types at all. A program cannot fall back on a literal, so wherever a value is needed, something must produce one. For a reader, a symbol table, or an output being built, that something is the first operation in the program, not an incidental detail of one call site.

The reach excludes three things that a reader will expect here, each owned elsewhere. **What an instance is made of** is [Memory](../../../docs/protocols/memory/memory.md)'s, which states that how a system acquires memory from its grant and hands it out "is a library choice inside the grant, not a language-mandated runtime" ([Allocators are libraries](../../../docs/protocols/memory/memory.md#allocators-are-libraries)). **What a type means** is [Type](../../../docs/type.md#categories-of-type)'s, whose four categories and the relations among them are settled there. **What a program boots as** is the compiler's configuration, not the language's, per [Compiler → Entry and lifecycle are not grammar](../../../docs/protocols/computer/compiler.md#entry-and-lifecycle-are-not-grammar).

### The concepts

#### Instance
A value of a defined Type, exercising capabilities the definition established; the thing a `vr` names and the thing a call writes into.

It is **not a concept of this model**, and the reason is that Type already defines it. [Type → Structure Is Fixed by Definition](../../../docs/type.md#structure-is-fixed-by-definition) states that "What a running instance holds are instances: values of defined Types, exercising capabilities the definition established", and [Type → Stateless Types](../../../docs/type.md#stateless-types) places instance state at runtime as one of the three roles a value serves. A concept already defined elsewhere is not redefined here; the boundary discipline [The Error holds](../../../docs/protocols/process/error.md) is what governs that choice, and construction inherits it rather than restating it. An instance is the **result** of construction, not a concern alongside it.

**Node.** Refused as an independent concept: it holds no responsibility of its own, only the data and the identity a Type already gives it.

#### Construction
The responsibility by which a program obtains an instance of a named Type.

This is the concept the requirement is about, and it is not owned anywhere in this repository. The language assigns it — [Variable in Khayyam → Overview](../../../docs/khayyam/variable.md#overview) makes "creation and initialization … responsibilities of capsule behavior" — and then says nothing about what discharging it consists of. The corpus assigns it nothing either: [`modules/computer/capsule/protocol/life_cycle_contract.kh:7`](../../computer/capsule/protocol/life_cycle_contract.kh) declares `Capsule_LifeCycle` with `Deinit` at `:8` and a comment at `:5-6` that says initialization "are each capsule's own named methods with its own domain arguments", so the one lifecycle contract in the corpus deliberately excludes the half of this responsibility that concerns the state after the instance exists, and says nothing about the half that concerns the instance itself.

Its distinguishing property is that it is **the only operation with no receiver**. Every other call in the language is made on something that already exists — a variable, or the parent type where the method's body does not invoke `self` ([Method in Khayyam → Method Invocation Rules](../../../docs/khayyam/method.md#method-invocation-rules)). A construction is made on a name that stands for a Type, and what it delivers arrives in a slot the caller declared. That is why the thirty-three `From*` declarations attach to the type rather than to an instance, and why the shape they need is legal: the language admits a call on the parent type, and admits a method on any Type including an abstraction ([Method Structure](../../../docs/khayyam/method.md#method-structure)).

**Node.** It has an independent behavioral boundary — a construction can be replaced by a library, a memory grant, or a host without any body that calls it changing — and it enforces rules nothing else owns: that no instance exists in a program without something having made it, and that the rules by which one is made belong to the Type being made rather than to the caller.

**Collides with** nothing declared in this repository, and is **not declared** by any `.kh` file.

#### Initialization
The responsibility by which an obtained instance reaches a state in which its methods mean what they promise.

The language names it as a second noun in the same sentence that names creation, and the corpus has already ruled on it: [`modules/computer/capsule/protocol/life_cycle.kh:6-9`](../../computer/capsule/protocol/life_cycle.kh) carries the comment "Init and Reinit are not members of this protocol. Initialization and re-initialization are the capsule's own behavior, through its own named methods carrying its own domain arguments", citing [Variable in Khayyam → Overview](../../../docs/khayyam/variable.md#overview) as its authority. That is a decision, made in the corpus, to keep initialization out of any shared contract — and it is the right one under [Modeling → One Authoritative Location per Concern's Data](../../../docs/modeling.md#one-authoritative-location-per-concerns-data), because what an instance is initialized *from* is domain-specific while the fact that it must be is not.

It is nonetheless a separate concept from Construction, and the separation is what the corpus's teardown half already demonstrates in the other direction: [`life_cycle_contract.kh:8`](../../computer/capsule/protocol/life_cycle_contract.kh) does carry `Deinit`, because teardown's arguments are not domain-specific. One responsibility, three lifecycle positions, and only the middle one is unclaimed.

**Node.** It has an independent boundary — it can be reasoned about, replaced, or ruled on without any construction changing, and [Process → State and Transition](../../../docs/process.md#state-and-transition) already gives "the conditions under which that state can change" its own modeling position — and it survives the challenge test.

**Collides with** two corpus declarations that do not own it, and **is not declared** by any `.kh` file: [`modules/computer/adt/hash_table/protocol/hash-table.kh:24`](../../computer/adt/hash_table/protocol/hash-table.kh) writes `tp ADT_HashTable_Init mt (self ADT_HashTable) (capacity NumberOfElement) (err Error)` and [`modules/time/timer/protocol/timer.kh:20`](../../time/timer/protocol/timer.kh) writes `tp Init mt (self Timer) (callback TimerListener) (err Error)`. Both are domain-specific initializations declared as a type's own method, which is exactly what the corpus's own lifecycle comment prescribes; neither is a construction, and neither is evidence that a shared initialization concept exists.

#### Provisioning
The arrival, from outside the program, of the implementation that makes a construction executable.

This is not a new concept; it is the language's own, and it is already settled. [Khayyam → Method, Body-less Methods](../../../docs/khayyam/khayyam.md#method) names the form: when the receiver is a concrete capsule, "a body-less method signals to the compiler that the implementation will be provided externally during the linking phase", and [Method in Khayyam → Body-less Methods](../../../docs/khayyam/method.md#body-less-methods-ffi-and-contracts) repeats it. This model's reason for naming it is the boundary it draws: in this repository, **every** value a program handles is obtained by provisioning. [`target.md:70`](../../khayyam/targets/js/target.md#running-a-program) states the consequence in one sentence — "so every value a program handles was produced outside it" — and the measurement at [`construct.kh:26`](../../khayyam/targets/js/bootstrap/construct.kh) is exactly that: `tp Make mt (self Holder) () (made Count)` is body-less, so it is provisioned, and the emitted artifact reaches it through the unit's `supply` function.

It is a distinct concern with a distinct owner, a distinct lifecycle, and a distinct boundary from Construction. A construction may be provisioned, or it may be written in Khayyam over something that is provisioned; the two are separate acts, and a reader who calls both "creation" cannot tell which half of a program is host-supplied. [Compiler → The compiler recognizes language primitives, not library names](../../../docs/protocols/computer/compiler.md#the-compiler-recognizes-language-primitives-not-library-names) fixes which of the two the compiler may own: neither, by name.

**Node.** It survives the challenge test as an existing concept this model attaches to, and it is **already declared** — by the language, not by a `.kh` file.

#### Acquisition
Not a concept of this model. [Memory → Allocators are libraries](../../../docs/protocols/memory/memory.md#allocators-are-libraries) owns it once and language-independently, and the corpus already uses the word in that sense: [`modules/computer/capsule/protocol/life_cycle.kh:12`](../../computer/capsule/protocol/life_cycle.kh) calls `Deinit` "the teardown surface for a capsule whose acquisition requires a release". Construction is not Acquisition; a construction may produce an instance backed by no acquired resource at all, and a claim that conflated them would make every construction look like an allocation.

**Node.** Refused: an equivalent concept exists and is owned elsewhere.

#### Route
A particular way of performing construction — from a literal, from another instance, from a file-level variable, from a registry, from the host.

Not a concept. A route is a choice of performer and of source, and under [Modeling → Classification Emerges From Rules and Relations](../../../docs/modeling.md#classification-emerges-from-rules-and-relations-not-from-intrinsic-labels) a label earns a node only when it carries rules no other concern owns and opens a relation the model recognizes. The corpus's `From*` family is one such route — "obtain this value by parsing that representation" — and it carries no rules of its own: what the parse means belongs to the Type. Routes are enumerated below because a reader choosing a `.kh` declaration needs them, not because any of them is a thing.

**Node.** Refused: a set of ways to perform one concept, which [Modeling → Domain Decomposition over Aggregate-Root Modeling](../../../docs/modeling.md#domain-decomposition-over-aggregate-root-modeling) treats as a consequence of modeling rather than a primitive.

### What each concept owns, and what it does not own

**Construction** owns that an instance exists, which Type may produce it, and what rules govern producing it. It does not own what the instance contains — a construction is not a container, and [Abstraction → A Concept Is an Abstraction; a Concrete Instance Is a Capsule](../../../docs/khayyam/abstraction.md#a-concept-is-an-abstraction-a-concrete-instance-is-a-capsule) fixes which of the two a signature names. It does not own the memory the instance occupies, which is Memory's. It does not own whether an instance of one Type may stand where an abstraction is expected; that is [Polymorphism](../../../docs/khayyam/polymorphism.md)'s dispatch question, and [Type → Structure Is Fixed by Definition](../../../docs/type.md#structure-is-fixed-by-definition) is what keeps the answer honest by requiring the set of realizable alternatives to be closed at definition time.

**Initialization** owns that an instance is in a state its own methods can act on, and the rules its own Type declares for reaching that state. It does not own what any particular field's value must be — that is the field's Type's contract. It does not own re-initialization for reuse through a pool, which [`life_cycle.kh:8-9`](../../computer/capsule/protocol/life_cycle.kh) already assigns to the pooling library as a contract term. It does not own teardown, which [`life_cycle_contract.kh:8`](../../computer/capsule/protocol/life_cycle_contract.kh) already owns under the language's own [lifecycle method names rule](../../khayyam/rules/lifecycle-method-names/lifecycle-method-names.md).

**Provisioning** owns what arrives from outside a program and when it becomes reachable to it. It does not own what the arrived implementation means — a body-less method on a capsule is FFI, and [Method in Khayyam → Body-less Methods](../../../docs/khayyam/method.md#body-less-methods-ffi-and-contracts) says the implementation is "provided by" the external phase, not specified by it. It does not own entry and lifecycle, which [Compiler → Entry and lifecycle are not grammar](../../../docs/protocols/computer/compiler.md#entry-and-lifecycle-are-not-grammar) places in configuration plus the Runtime. And it does not own construction: a provisioned implementation is what a construction reaches, not what a construction is.

Three concerns a reader will expect here are owned elsewhere, and this model does not absorb them:

- **Allocation and reclamation.** Memory owns them, once and language-independently; a construction that needs a grant asks an allocator for one.
- **Copying and cloning.** [Variable in Khayyam → Variable as Logical Reference](../../../docs/khayyam/variable.md#variable-as-logical-reference) and [Encapsulation → Sovereign Encapsulation](../../../docs/khayyam/encapsulation.md#sovereign-encapsulation) both name an explicit `Copy`/`Clone` abstraction as the route to an independent instance, and [Memory → Copy and ownership semantics are contract members](../../../docs/protocols/memory/memory.md#copy-and-ownership-semantics-are-contract-members) makes it a contract member rather than a language form. Under [Modeling → Acquired Data vs. Discovered Data](../../../docs/modeling.md#acquired-data-vs-discovered-data) a copied instance is discovered from an acquired one, which makes it a **source** of instances and not a way of producing them.
- **Registration and lookup.** The corpus's registries obtain instances the program never constructed — [`modules/process/services/protocol/services.kh:14`](../../process/services/protocol/services.kh) declares `Process_Services_Register`, and [`modules/identifier/mediatypes/protocol/media-types.kh:9`](../../identifier/mediatypes/protocol/media-types.kh) declares `Identifier_MediaTypes_Register` beside a `GetByMediaType` that returns one. A registry is a relation between an instance and a set; who put it there is Construction's question, not the registry's.

### The relations

**A Construction produces an Instance, and the instance arrives in a slot the caller declared.** The direction runs from construction to instance because the instance is what ends; the delivery into a caller-declared slot is not an addition of this model but a consequence of [Method in Khayyam → Key Rules](../../../docs/khayyam/method.md#key-rules), where every variable of a call is passed strictly by reference and the influenced group is where a call writes. This relation already exists in this repository under another name: [`Container_Iteration`](../../computer/adt/container/protocol/iteration.kh)'s `Iteration` writes into an influenced element index, and [`Marker_Clone_String_CloneFrom`](../../computer/adt/marker/protocol/clone.kh) writes the source's contents into the clone.

**A Construction may be realized by a Provisioning.** The direction runs from construction to provisioning because the arrival supplies what the construction needs in order to run; the reverse is meaningless, since a provisioned implementation with no construction to perform is a mechanism no program reaches. The language states the realization and not the relation: [`target.md:70`](../../khayyam/targets/js/target.md#running-a-program) records that in this repository every value was produced outside the program.

**An Initialization follows a Construction on one instance, and a Construction need not be followed by one.** The direction runs from initialization to construction because initialization acts on what construction produced. The corpus states the second half twice — [`life_cycle_contract.kh:5-6`](../../computer/capsule/protocol/life_cycle_contract.kh) and [`life_cycle.kh:6-7`](../../computer/capsule/protocol/life_cycle.kh) — and the first half is what [`bootstrap/construct.kh`](../../khayyam/targets/js/bootstrap/construct.kh) measures as two separate calls in one body, `Make` at `:26` writing the slot and `Fill` at `:28` receiving the instance.

**A Construction precedes every use of its instance, on every path.** This is not a rule any document states; it is forced by [Khayyam → How Khayyam realizes Memory](../../../docs/khayyam/khayyam.md#how-khayyam-realizes-memory), which names definite-assignment analysis — "an uninitialized `vr` is refused" — among the things correctness is obtained without lifetime syntax, and by [Memory → Uninitialized reads are refused](../../../docs/protocols/memory/memory.md#uninitialized-reads-are-refused), which prescribes the refusal without prescribing a keyword. A body that declares a slot and reaches a use without a construction on every path is therefore not well-formed, and *every path* is a control-flow question. That makes this relation the model's one dependency on another model that has not been written.

**A Construction is replaceable per organization; the compiler may not hold one by name.** [Compiler → The compiler recognizes language primitives, not library names](../../../docs/protocols/computer/compiler.md#the-compiler-recognizes-language-primitives-not-library-names) states that the compiler "does not treat library-provided operations as intrinsics because they are common, useful, or imported from a privileged package", and the same sentence names "lifecycle hooks" among them — which is a construction spelled in the ecosystem's terms. [Modeling → Extensible Behavior Belongs to Pluggable Modules](../../../docs/modeling.md#extensible-behavior-belongs-to-pluggable-modules) gives the general form: a concern's model should expose attachment points rather than absorb every variation. So a library over construction must be replaceable, which is the property that makes it worth modeling at all and the constraint every declaration in it is subject to.

One relation that looks adjacent is not one of these. **A Construction may not be given a field to write.** [Encapsulation → Capsule Structure and Privacy](../../../docs/khayyam/encapsulation.md#capsule-structure-and-privacy) states that fields are always private and that "the only way to read or modify a capsule's internal state is through methods attached to that capsule", and [`target.md:45`](../../khayyam/targets/js/target.md#a-field-is-a-variable) adds that "a call writes into a name the body binds, and a field is not one" — a rule of that toolchain rather than a claim about the language, measured by the refusal at [`bootstrap/write-field.kh:31`](../../khayyam/targets/js/bootstrap/write-field.kh). What the endorsed shape is, the same document states at `:45`: "a method that hands its field to the method that writes it". So a field's instance is filled by a call the capsule makes on itself, not by a construction the holder makes.

### The names to use and the names to refuse

**Use `Instance`** for the value a variable names and a call writes, and **use `Construction`** for the responsibility that produces one and **use `Initialization`** for the one that brings it to a usable state. The three are distinct, and the language's own sentence at [Variable in Khayyam → Overview](../../../docs/khayyam/variable.md#overview) is the reason: it names "creation and initialization" as two.

**Use `Provisioning`** for what arrives from outside the program, following the language's own two forms at [Khayyam → Method, Body-less Methods](../../../docs/khayyam/khayyam.md#method). The word carries its ordinary sense and the language has already fixed it, which is what makes it safe where the next words are not.

**Refuse `New` and `Create` and `Make` as this model's concept names, while keeping each as an available method name.** All three are ecosystem spellings of one responsibility, and the corpus holds all three under `TODO(go-migrate)` blocks that record where they came from: [`modules/crypto/aes-256.kh:17`](../../crypto/aes-256.kh) reads `func NewAES256(key [32]byte) *aes256` inside its commented Go source, [`modules/codec/compress/gzip/init.kh:12`](../../codec/compress/gzip/init.kh) reads `GZIP.Init()` inside `func init()`, and [`modules/khayyam/targets/js/bootstrap/construct.kh:26`](../../khayyam/targets/js/bootstrap/construct.kh) — the one live Khayyam declaration among them — reads `Make`. [Terminology → The Default Meaning of an Unreferenced Term](../../../docs/terminology.md#the-default-meaning-of-an-unreferenced-term) gives an unreferenced word "exactly its general meaning — the ordinary dictionary or established scientific sense", and for all three that is the Go spelling this repository is porting away from. Refusing them as *concept* names does not forbid them as *method* names: [Khayyam's receiver-method-names rule](../../khayyam/rules/receiver-method-names/receiver-method-names.md) is explicit that a method reached through its receiver keeps the bare name, and the corpus's thirty-three `From*` declarations are that rule working, not a violation of it.

**Refuse `Constructor` as a Memar term, and record why this document had to refuse the language's own.** [Encapsulation → Sovereign Encapsulation](../../../docs/khayyam/encapsulation.md#sovereign-encapsulation) states, at `:62`, that "Obtaining a *new* instance to rebind to … still requires going through that type's own constructor or an explicit copy/clone abstraction it chooses to implement — there is no ambient, type-independent way to conjure a value." That sentence is the only place in this repository's documentation where a word for this responsibility appears, and no document in this repository defines it; a search of the whole documentation set returns that line and nothing else. So the language document has already chosen a word for this responsibility without a Memar definition behind it, and under the rule above that word carries the ordinary dictionary sense — which in a language whose corpus is being ported from Go is Go's `new` and C++'s constructor, neither of which is what a Khayyam construction is. Refusing the word here does not correct [`encapsulation.md:62`](../../../docs/khayyam/encapsulation.md); it records that the word in it is unreferenced, and what would close that is carried in the handoff.

**Refuse `Literal` for what a construction produces.** [Khayyam → Separation of Syntax and Governance](../../../docs/khayyam/khayyam.md#separation-of-syntax-and-governance-a-principle) uses the word for the thing the language *refuses*: "a bare numeric literal `41` may not appear as a value without a named capsule". What stands in its place is an instance of a named capsule, and calling that instance a literal would name the absence as the presence.

**Refuse `Init` as a shared name across types**, while keeping the corpus's own `Init` declarations where they are. The corpus has already made this call and recorded its ground: [`modules/computer/capsule/protocol/life_cycle.kh:6-9`](../../computer/capsule/protocol/life_cycle.kh) excludes `Init` and `Reinit` from the shared contract precisely because "the capsule's own behavior … carrying its own domain arguments" is what differs. A shared `Init` would be the single name for every domain's own arguments, which is the collision [Khayyam → Import Mechanism](../../../docs/khayyam/khayyam.md#import-mechanism-in) calls an architecture error.

**Refuse `nil`, `null`, `unset`, and `None` as what an unconstructed slot holds.** [Khayyam → Variable](../../../docs/khayyam/khayyam.md#variable) states there is no universal nullability token and that "absence, when a type can represent it, is a method on that type's contract", and [Memory → Absence is a type's contract](../../../docs/protocols/memory/memory.md#absence-is-a-types-contract-not-a-universal-machine-condition) is the protocol-level claim. What a slot holds before a construction has written it is not a value; it is a refusal, per the definite-assignment rule below.

**Refuse `Slot` as a model concept, and keep it as the measurement's word.** The word belongs to one target's reading — [`target.md:50`](../../khayyam/targets/js/target.md#the-artifact-of-one-unit) says "A variable is a cell" and the handoff records "Every variable is a cell, and a field is a variable" as a decision of that target. The language's word is *variable*, and [Encapsulation → Sovereign Encapsulation](../../../docs/khayyam/encapsulation.md#sovereign-encapsulation) already generalizes it: "A field, like a variable, is simply a name bound to an instance of a type". A reader who learns "slot" from the artifact will look for it in the language and not find it.

### What the language states that a library may be written over
Seven things are stated, and every one of them is usable without extending the grammar. Together they are the answer to "can a `.kh` construction library be written today".

1. **A variable declaration binds a name and a type and nothing more.** [Variable in Khayyam → Variable Declaration Syntax](../../../docs/khayyam/variable.md#variable-declaration-syntax) states the grammar as `vr {name} {type}`, that "it cannot carry an initializer inline", and that of the four Type categories a `vr` names a capsule or an abstraction — "those are the categories with an instance for the name to reference".
2. **A body may hold four commands.** [The JavaScript target → The commands a body may hold](../../khayyam/targets/js/target.md#the-commands-a-body-may-hold) states the set with a citation for each: a declaration, a scope, an invocation, and the `return` marker. Declaring a slot and calling a method that writes it are two of the four.
3. **Every variable of a call is handed over by reference.** [Method in Khayyam → Key Rules](../../../docs/khayyam/method.md#key-rules) states it for the owner and both groups alike, and the target realizes it at [`target.md:50`](../../khayyam/targets/js/target.md#the-artifact-of-one-unit): the influenced group "is handed over as the slot itself".
4. **A method may be called on the parent type.** [Khayyam → Method Invocation Rules](../../../docs/khayyam/khayyam.md#method-invocation-rules) gives the shape `W32.Sum(a, b)(total, err)` and states that "the body does not invoke `self`", which is what makes a receiver-free call expressible.
5. **A method may be attached to any Type.** [Method Structure](../../../docs/khayyam/method.md#method-structure) admits a capsule, an abstraction, or another method, "wherever a receiver is genuinely warranted" — so a construction may hang on a purpose-built capsule, as [No Dedicated fn/func Keyword](../../../docs/khayyam/method.md#no-dedicated-fnfunc-keyword)'s `TimeHelper` case does, and does not have to be forced onto the constructed type.
6. **A body-less method on a concrete capsule is the foreign-function-interface form.** [Khayyam → Method, Body-less Methods](../../../docs/khayyam/khayyam.md#method) states it, and the target distinguishes it from the contract form at [`target.md:54`](../../khayyam/targets/js/target.md#the-three-kinds-of-body-less-method).
7. **An uninitialized `vr` is refused.** [Khayyam → How Khayyam realizes Memory](../../../docs/khayyam/khayyam.md#how-khayyam-realizes-memory) names definite-assignment analysis as the source of that correctness, and [Memory → Uninitialized reads are refused](../../../docs/protocols/memory/memory.md#uninitialized-reads-are-refused) prescribes the refusal without a keyword. This is the constraint a construction must satisfy on every path, and it is the only one that reaches outside this model.

### What neither states, and what a library is therefore blocked on
Three gaps block any construction library, and a fourth is recorded because it will block the first declaration rather than the design.

**Whether obtaining an instance can fail.** Nothing in the language says. [Variable in Khayyam → Domain-Driven Arithmetic](../../../docs/khayyam/variable.md#domain-driven-arithmetic) establishes the pattern that failure is visible in a method's signature rather than hidden in syntax, and [Domain-Driven Arithmetic → Mechanism Summary](../../../docs/khayyam/variable.md#mechanism-summary) makes arithmetic and comparison "always explicit capsule methods with explicit error outputs" — but that is a claim about operations *over* a value, not about the production of one. The corpus disagrees with itself on the question and is the only place either answer appears: thirty-three `From*` declarations carry `(err Error)` — [`modules/math/integer/unsigned-32.kh:16`](../../math/integer/unsigned-32.kh), [`modules/math/boolean/boolean.kh:23`](../../math/boolean/boolean.kh) — while the one measured construction, [`construct.kh:26`](../../khayyam/targets/js/bootstrap/construct.kh), carries none. If construction is fallible, then whether its error path is visible follows from [Control Flow → Error Propagation](../../../docs/protocols/process/control-flow.md#error-propagation)'s requirement that "every fallible operation exposes its error path as an ordinary, named part of the call contract" — which is a protocol's requirement over a library, not a grammar obligation, per [Khayyam → The Grammar Refuses Protocol Semantics](../../../docs/khayyam/khayyam.md#the-grammar-refuses-protocol-semantics).

**Whether the instance arrives in the influenced group or somewhere the language has not named.** Nothing states it. The corpus's thirty-three `From*` declarations are consistent with an instance that appears nowhere — a receiver the caller already holds, mutated in place, which is what their ported Go bodies do — and inconsistent with the by-reference rule the language does state. This is the sharpest single gap, because it decides every signature in a construction library and it is the one place where the corpus's thirty-three names and the language's one slot rule cannot both be right.

**Whether construction and initialization are one responsibility or two in the language, as opposed to in the corpus's comment.** The language's sentence at [Variable in Khayyam → Overview](../../../docs/khayyam/variable.md#overview) names both in one breath and does not say whether they may be one operation; the corpus's comment at [`life_cycle.kh:6-9`](../../computer/capsule/protocol/life_cycle.kh) treats them as separate and domain-specific; and the measurement at [`construct.kh`](../../khayyam/targets/js/bootstrap/construct.kh) writes them as two calls. This model treats them as two and says why; a ruling that fuses them would not contradict the language, which is precisely what makes it a ruling and not a reading.

**Whether a construction may be declared as a shared contract at all — the gap that decides the file layout.** [Abstraction → What You Cannot Do](../../../docs/khayyam/abstraction.md#what-you-cannot-do) states that a capsule type may not be an argument or return type in an abstraction's method signature, "only other abstractions are allowed". [Abstraction → A Concept Is an Abstraction](../../../docs/khayyam/abstraction.md#a-concept-is-an-abstraction-a-concrete-instance-is-a-capsule) then says which follows from who owns the signature: a signature owned by an abstraction names the concept, a signature owned by a capsule may name a capsule, including itself. A construction's result is a *concrete instance*, so under this model a construction contract that a program could call and receive an instance from cannot be an Abstraction over capsules. The corpus's one `Factory` is an Abstraction — [`docs/khayyam/polymorphism.md:202-206`](../../../docs/khayyam/polymorphism.md) writes `tp Factory ab {}` and `tp Create mt (self Factory) () (product Product)` — and its result is `Product`, an abstraction; it illustrates covariant return and never claims to hand over an instance. And a call whose receiver is typed as an abstraction is refused at the call site by this repository's one target, per [`target.md:58`](../../khayyam/targets/js/target.md#the-three-kinds-of-body-less-method). So a construction library can exist only as per-type declarations or as a contract the language has not yet admitted, and which way it goes is not a choice a library author makes.

### What the corpus states that neither does
Four things are true of the `.kh` corpus's construction surface and of no document in this repository.

**Thirty-three declarations name the responsibility and none discharges it.** The whole `From*` family was read: [`modules/math/integer/unsigned-8.kh:16-21`](../../math/integer/unsigned-8.kh), `unsigned-16`, `unsigned-32`, `unsigned-64`, `signed-8`, `signed-16`, `signed-32`, `signed-64`, [`modules/math/float/float-32.kh:16`](../../math/float/float-32.kh), `float-64`, [`modules/math/boolean/boolean.kh:23`](../../math/boolean/boolean.kh), [`modules/modules/app/protocol/dt-domain.kh:34`](../../modules/app/protocol/dt-domain.kh), [`dt-domain_name.kh:37`](../../modules/module/protocol/dt-domain_name.kh), [`dt-path.kh:41`](../../modules/module/protocol/dt-path.kh), [`modules/math/integer/protocol/signed.kh:15`](../../math/integer/protocol/signed.kh), [`modules/time/duration/second.kh:13`](../../time/duration/second.kh), [`nano-second.kh:14`](../../time/duration/nano-second.kh), [`nano-in-second.kh:10`](../../time/duration/nano-in-second.kh), and seven more under `codec/` and `lib/`. Every one attaches to the type it produces — `tp FromString mt (self W32)` — rather than to an instance of it, which is the correct receiver for a construction. Not one carries an influenced variable of the type it produces. Under [Method in Khayyam → Key Rules](../../../docs/khayyam/method.md#key-rules) that is where the result must arrive, and a whole-tree search for a declaration whose influenced group names its own owner's type finds only retrieval and comparison — `Container_Iteration` writing an element index, [`Marker_Clone_String_CloneFrom`](../../computer/adt/marker/protocol/clone.kh) writing a clone's contents, `GUI_Element_Clone` at [`modules/gui/protocol/element.kh:30`](../../gui/protocol/element.kh), `ParentCommand` and `SubCommand` at [`modules/lib/process/command/protocol/command.kh:28,31`](../../lib/process/command/protocol/command.kh), `Load` at [`modules/time/timer/protocol/timer-status.kh:10`](../../time/timer/protocol/timer-status.kh), `NextFrame` at [`modules/net/protocol/frame.kh:11`](../../net/protocol/frame.kh), `Module_Path_Get` at [`dt-path.kh:12`](../../modules/module/protocol/dt-path.kh), and `Equal` in every numeric width. So the corpus knows the name, knows the receiver, and has never written the delivery.

**One measurement is the same shape as those thirty-three and the opposite of their delivery.** [`bootstrap/construct.kh`](../../khayyam/targets/js/bootstrap/construct.kh) is a live `.kh` unit and it is the only construction-shaped declaration in the tree that compiles. `Make` at `:26` takes no influencing variable and writes `made Count`; `Fresh` at `:20-24` declares the slot at `:21` and calls it at `:22`; `Fill` at `:28` receives the instance and initializes it. That is construction and initialization as two operations, with the instance arriving in the influenced group — the shape the thirty-three lack. It is the same concept as this model's Construction, and it is not a coincidence: its own header at `:3-8` cites [Variable in Khayyam → Overview](../../../docs/khayyam/variable.md#overview) and [Khayyam → Type Principles Realized](../../../docs/khayyam/khayyam.md#type-principles-realized) by name. What it does *not* do is construct anything in Khayyam, because `Make` is body-less and therefore provisioned — which is exactly the boundary [The JavaScript target → Running a program](../../khayyam/targets/js/target.md#running-a-program) draws, and exactly why the test at [`bootstrap.test.ts:61`](../../khayyam/targets/js/test/bootstrap.test.ts) is named "a program cannot make the value a method was asked to produce".

**The corpus already decided that construction is not part of the shared lifecycle, and wrote the decision down as a comment.** [`modules/computer/capsule/protocol/life_cycle.kh`](../../computer/capsule/protocol/life_cycle.kh) declares `CapsuleLifeCycle` at `:5` with a block whose body at `:6-9` is only a comment, then `Deinit` at `:14`. [`modules/computer/capsule/protocol/life_cycle_contract.kh`](../../computer/capsule/protocol/life_cycle_contract.kh) declares `Capsule_LifeCycle` at `:7` and `Deinit` at `:8`, with the same exclusion stated at `:5-6`. Two declarations of one teardown contract, one word apart, and the first is imported by nothing in the tree while the second is imported by thirteen files — including [`modules/crypto/hash/protocol/hash.kh:3`](../../crypto/hash/protocol/hash.kh), [`modules/memory/reference/protocol/reference.kh:3`](../../memory/reference/protocol/reference.kh), and every OSI layer under `modules/net/protocol/`. Under [Khayyam → Import Mechanism](../../../docs/khayyam/khayyam.md#import-mechanism-in) that is a collision whether or not both are reachable, and it is recorded here rather than resolved: which of the two survives, and whether the survivor is where a construction belongs, are the owner's calls and not this model's.

**The corpus's answer to "how does a program get an instance" today is the host, and it says so in four places.** [`modules/gui/protocol/application.kh:10`](../../gui/protocol/application.kh) declares `vr GUI Application` and comments "You must assign to it by any object implement protocol.Application on your main.go file". [`modules/net/gp/init.kh:6`](../../net/gp/init.kh) declares `vr conns Gp_Connections` and comments "must assign before use the package". [`modules/identifier/mediatypes/media-types.kh:3`](../../identifier/mediatypes/media-types.kh) declares `vr mts mediaTypes` with no initializer anywhere in the file. And [`modules/codec/compress/gzip/init.kh:12-13`](../../codec/compress/gzip/init.kh) shows the ported Go shape of the same answer — `GZIP.Init()` then `cts.Register(&GZIP)`, inside a host-driven `func init()`. None of the four has any `.kh` form for the assignment, because [Variable in Khayyam → Variable Scope and Visibility](../../../docs/khayyam/variable.md#variable-scope-and-visibility) says who does it — "The variable's initial state is established by the compiler and by source that code generation emits" — and not where the author writes the statements that do it. That question is already open at [Variable in Khayyam Handoff → Where are the statements that build or bind a file-level `vr`'s initial state written?](../../../docs/khayyam/variable.handoff.md#where-are-the-statements-that-build-or-bind-a-file-level-vrs-initial-state-written), where it is recorded as blocking a port of 126 sites, and this model does not reopen it.

### Implications

- **Construction's soundness is a control-flow question, and the control-flow library does not exist.** [Khayyam → How Khayyam realizes Memory](../../../docs/khayyam/khayyam.md#how-khayyam-realizes-memory) makes an uninitialized `vr` a refusal, so a construction must be reachable on every path that reaches a use of its slot — and deciding which paths reach a use is what [`modules/process/control-flow/`](../control-flow/) exists to model, with the corpus's one measurement of it recorded at [`target.handoff.md:85`](../../khayyam/targets/js/target.handoff.md) as "the library which would supply it does not exist yet". Two sibling models, one dependency, and the dependent one cannot be written before the other.
- **A `.kh` construction library is writable today, and what it cannot do is be a contract.** Everything in [What the language states](#what-the-language-states-that-a-library-may-be-written-over) is sufficient to write per-type declarations: a caller binds a slot, a call writes it, the call's receiver is the type. What no document supplies is a shared abstraction over that, because [Abstraction → What You Cannot Do](../../../docs/khayyam/abstraction.md#what-you-cannot-do) forbids a capsule in an abstraction's signature. If a construction library is to be replaceable per organization — which [Control Flow → Mechanism Summary](../../../docs/protocols/process/control-flow.md#mechanism-summary) makes the reason a control-flow library is a Module rather than a fixed type — then a language change is required before the shape is settled, and no amount of declaration-writing substitutes for it.
- **If construction is ruled fallible, thirty-three corpus declarations become partly right for the wrong reason.** Their `(err Error)` would be correct, and their missing influenced group would remain a defect. Ruling the other way leaves the thirty-three correct on the error and still defective on delivery. Either way the delivery gap is independent of the fallibility gap, which is why this model treats them as two questions rather than one.
- **The first instance of a type is a construction the program cannot itself perform.** [Khayyam Handoff → Stdlib bootstrap ordering under the no-hidden-primitive rule](../../../docs/khayyam/khayyam.handoff.md#stdlib-bootstrap-ordering-under-the-no-hidden-primitive-rule) records the ordering problem as unstated, and [Variable in Khayyam Handoff → How does the compiler obtain the first instance's values from source?](../../../docs/khayyam/variable.handoff.md#how-does-the-compiler-obtain-the-first-instances-values-from-source) records the literal-to-instance half as open, with the two named as entangled. A model of construction that stops at "a program obtains an instance" does not cover that case, and this document says so rather than treating the bootstrap ordering as a separate problem.
