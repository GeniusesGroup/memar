# Construction Model Handoff
Open work for [model.md](./model.md). Entries are mutable current state — revised as each item moves, removed when it resolves or is dropped. See the repository's [documentation-handoff.md](../../../docs/documentation-handoff.md) for what a handoff is.

## Topic & Purpose
The model of how a Khayyam program obtains an instance of a capsule, and of what the language must state before a `.kh` library over it can be written. The model settles the concepts, their boundaries, their relations, and the names; it deliberately settles no signature, no owner type, and no file layout, because each of those turns on a question carried below rather than on one this session answered.

## Status
Active

## Decisions
- **Two concepts, and three refused** — Decided. **Construction** (the responsibility by which a program obtains an instance) and **Initialization** (the responsibility by which an obtained instance reaches a usable state) survive the challenge test in [Modeling Practice → Challenging a Proposed Concept](../../../docs/modeling.practice.md#challenging-a-proposed-concept) with independent behavioral boundaries and rules no existing concern owns. Refused: **Instance**, because [Type → Structure Is Fixed by Definition](../../../docs/type.md#structure-is-fixed-by-definition) already defines it and this model would be a second authority; **Acquisition**, because [Memory → Allocators are libraries](../../../docs/protocols/memory/memory.md#allocators-are-libraries) owns it once and language-independently; **Route**, because a route is a way of performing Construction and carries no rules of its own under [Modeling → Classification Emerges From Rules and Relations](../../../docs/modeling.md#classification-emerges-from-rules-and-relations-not-from-intrinsic-labels). Reason the refusals matter: each would otherwise become a declaration or an abstraction in the first `.kh` written here, and two of the three are already owned elsewhere.
- **Provisioning is named, and it is not Construction** — Decided. Provisioning is the arrival of an implementation from outside the program, which [Khayyam → Method, Body-less Methods](../../../docs/khayyam/khayyam.md#method) already settles as the foreign-function-interface form. Reason: in this repository every value a program handles is obtained this way, per [`target.md:70`](../../khayyam/targets/js/target.md#running-a-program), and a reader who has one word for both acts cannot tell which half of a program is host-supplied. Rejected: treating construction as a sub-case of provisioning, which would make the concept invisible in exactly the repository where the host does the work, and treating them as one node under a name like "Acquisition", which Memory already owns.
- **Construction and Initialization are two responsibilities, not one** — Decided. Reason: the corpus has already ruled on the middle of the lifecycle in both directions and can be read for it — [`modules/computer/capsule/protocol/life_cycle.kh:6-9`](../../computer/capsule/protocol/life_cycle.kh) excludes `Init` and `Reinit` from the shared contract "through its own named methods carrying its own domain arguments", while [`modules/computer/capsule/protocol/life_cycle_contract.kh:8`](../../computer/capsule/protocol/life_cycle_contract.kh) does carry `Deinit`; and [Process → State and Transition](../../../docs/process.md#state-and-transition) already gives "the conditions under which that state can change" its own position. Rejected: fusing them into one "creation" operation, which would put a capsule's domain arguments into a shared contract and so duplicate one boundary across every Type — the failure [Modeling → One Authoritative Location per Concern's Data](../../../docs/modeling.md#one-authoritative-location-per-concerns-data) names.
- **`Constructor` is refused as a Memar term, and the refusal is not a correction of the language** — Decided. [Encapsulation → Sovereign Encapsulation](../../../docs/khayyam/encapsulation.md#sovereign-encapsulation) states at `:62` that obtaining a new instance "still requires going through that type's own constructor", and a search of the whole documentation set returns that line as the only occurrence of the word. Reason: [Terminology → The Default Meaning of an Unreferenced Term](../../../docs/terminology.md#the-default-meaning-of-an-unreferenced-term) gives an unreferenced word "exactly its general meaning — the ordinary dictionary or established scientific sense", and for a corpus being ported from Go that sense is Go's `new` and C++'s constructor, neither of which is what a Khayyam construction is. This session does not own [`docs/khayyam/encapsulation.md`](../../../docs/khayyam/encapsulation.md) and did not edit it; the naming question is carried below.
- **`New`, `Create`, and `Make` are refused as concept names and kept as method names** — Decided. All three are ecosystem spellings of one responsibility, and the corpus holds each under a `TODO(go-migrate)` block recording where it came from — `NewAES256` at [`modules/crypto/aes-256.kh:17`](../../crypto/aes-256.kh), `GZIP.Init()` at [`modules/codec/compress/gzip/init.kh:12`](../../codec/compress/gzip/init.kh), `Make` at [`modules/khayyam/targets/js/bootstrap/construct.kh:26`](../../khayyam/targets/js/bootstrap/construct.kh). Reason: same unreferenced-term rule as above. What is kept is the corpus's thirty-three `From*` declarations, which [Khayyam's receiver-method-names rule](../../khayyam/rules/receiver-method-names/receiver-method-names.md) already licenses: a method reached through its receiver keeps the bare name, and `FromString` on `W32` is that rule working.
- **`Init` is refused as a shared name across types** — Decided, and the decision is the corpus's own, made before this session. [`modules/computer/capsule/protocol/life_cycle.kh:6-9`](../../computer/capsule/protocol/life_cycle.kh) states the ground. A single shared `Init` would carry every domain's own arguments under one name, which is the collision [Khayyam → Import Mechanism](../../../docs/khayyam/khayyam.md#import-mechanism-in) calls an architecture error. Rejected: a `Construction`-or-`Init`-named abstraction in this module, for the reason in the next entry.
- **The model is conceptual; no declaration was written and no implementation designed** — Decided. Reason: [Modeling → Modeling Produces Conceptual Abstractions, Not Implementation Structures](../../../docs/modeling.md#modeling-produces-conceptual-abstractions-not-implementation-structures), and the target handoff's standing decision at [`target.handoff.md:32`](../../khayyam/targets/js/target.handoff.md) that a library the compiler needs is modelled where the concept belongs before it is written anywhere. Where this document names a method it says what the method must mean.
- **The folder is `modules/process/construction/`, beside `control-flow/`** — Decided. Rules followed, in order: `modules/khayyam/README.md` places language-wide library source in the other module folders under `modules/` and excludes it from the toolchain folder, so nothing here goes under [`modules/khayyam/targets/`](../../khayyam/targets/); [`modules/README.md`](../../README.md) organizes this layer by responsibility and admits `process/` as one of them; and the precedent the toolchain set is the sibling model at [`modules/process/control-flow/`](../control-flow/), which exists because a library a Khayyam compiler needs is modelled under `modules/process/` before it is written. Rejected: `modules/khayyam/` — excluded by its own membership criterion, since this is a library concern and not the language's tooling; rejected `modules/computer/` — construction is not a compiler-internal mechanism and would acquire a language dependency it must not hold; rejected `docs/protocols/` — no protocol exists for this subject and the protocol layer states contracts, not the realization of one.
- **No `README.md` was written in the folder** — Decided. [`modules/process/control-flow/README.md`](../control-flow/README.md) and [`modules/process/test/README.md`](../test/README.md) both carry one, but [Documentation Practice → Folder READMEs](../../../docs/documentation.practice.md#folder-readmes) requires the README of a folder that has a main document to be a symbolic link to it, and creating that link requires a git operation this session may not perform. The two neighbouring READMEs are in fact real text files, which is the state this session leaves the question in rather than resolving.

## Ambiguities Resolved
- **Whether "construction" is one concern or three** — Answered by the challenge test, not by preference. The requirement names it as one; the language's own sentence at [Variable in Khayyam → Overview](../../../docs/khayyam/variable.md#overview) names two nouns in it; and the corpus's lifecycle comment splits them again, keeping initialization domain-specific. The model therefore names Construction and Initialization as two, and records that the corpus's split is a decision in a comment rather than in a document — which is why the fusion question below is still open.
- **Whether an instance is a concept of this model** — Answered: no. [Type → Structure Is Fixed by Definition](../../../docs/type.md#structure-is-fixed-by-definition) and [Type → Stateless Types](../../../docs/type.md#stateless-types) already use the word with a stated meaning, so naming it again here would create the second authority [The Error's boundary discipline](../../../docs/protocols/process/error.md) exists to prevent.
- **Whether a copy is a construction** — Answered: no. [Variable in Khayyam → Variable as Logical Reference](../../../docs/khayyam/variable.md#variable-as-logical-reference) and [Encapsulation → Sovereign Encapsulation](../../../docs/khayyam/encapsulation.md#sovereign-encapsulation) both name `Copy`/`Clone` as the route to an independent instance, and [Memory → Copy and ownership semantics are contract members](../../../docs/protocols/memory/memory.md#copy-and-ownership-semantics-are-contract-members) makes it a contract member rather than a language form. Under [Modeling → Acquired Data vs. Discovered Data](../../../docs/modeling.md#acquired-data-vs-discovered-data) a copied instance is discovered from an acquired one, which makes copy a source of instances and not a way of producing them.
- **Whether a registry is a construction concern** — Answered: no. [`modules/process/services/protocol/services.kh:14`](../../process/services/protocol/services.kh) and [`modules/identifier/mediatypes/protocol/media-types.kh:9`](../../identifier/mediatypes/protocol/media-types.kh) declare `Register` beside a `Get…` that returns what was registered, which is a relation between an instance and a set. Who put the instance there is Construction's question; where the set keeps it is the registry's.
- **Whether `bootstrap/construct.kh` is a coincidence of this model's subject** — Answered: it is the same concept, and it says so itself. Its header at `:3-8` cites [Variable in Khayyam → Overview](../../../docs/khayyam/variable.md#overview) and [Khayyam → Type Principles Realized](../../../docs/khayyam/khayyam.md#type-principles-realized) by name. What it does not do is construct in Khayyam: `Make` at `:26` is body-less, so it is provisioned, which is why the test at [`bootstrap.test.ts:61`](../../khayyam/targets/js/test/bootstrap.test.ts) is named "a program cannot make the value a method was asked to produce".
- **Whether `Factory` in `polymorphism.md` is a construction contract** — Answered: no, and it is recorded rather than resolved against the document. [`docs/khayyam/polymorphism.md:202-206`](../../../docs/khayyam/polymorphism.md) writes `tp Factory ab {}` and `tp Create mt (self Factory) () (product Product)`. Its result is `Product`, an abstraction; the example illustrates covariant return and never claims to hand over an instance. Under [Abstraction → What You Cannot Do](../../../docs/khayyam/abstraction.md#what-you-cannot-do) it could not return a capsule in any case. Not a coincidence and not the same concept: it is an example of a different rule, and it is the one place in the language's documents where the word "factory" appears at all.

## Open Questions
### Can obtaining an instance fail, and does the construction signature carry an influenced `err`?
- State: nothing in the language says. [Variable in Khayyam → Domain-Driven Arithmetic](../../../docs/khayyam/variable.md#domain-driven-arithmetic) establishes the pattern that failure is visible in a signature, and [Mechanism Summary](../../../docs/khayyam/variable.md#mechanism-summary) makes arithmetic and comparison "always explicit capsule methods with explicit error outputs" — but that is a claim about operations *over* a value. The corpus is the only witness and it disagrees with itself: thirty-three `From*` declarations carry `(err Error)` — [`modules/math/integer/unsigned-32.kh:16`](../../math/integer/unsigned-32.kh), [`modules/math/boolean/boolean.kh:23`](../../math/boolean/boolean.kh) — while the one measured construction, [`construct.kh:26`](../../khayyam/targets/js/bootstrap/construct.kh), carries none. A whole-corpus scan confirms the count and finds no exception either way.
- What a ruling must decide: whether producing a value is an operation that can fail, and therefore whether its error path is a named part of the call contract. If it is, [Control Flow → Error Propagation](../../../docs/protocols/process/control-flow.md#error-propagation)'s requirement that every fallible operation expose its error path applies to every construction signature in the library.
- Blocks continuation: yes, for every signature.
- Path: the language documents — `docs/khayyam/variable.md#overview` or `docs/khayyam/method.md#influencing-and-influenced-variables-not-inputs-and-outputs` — then the owner. If the answer is that a failure is possible, [The Error](../../../docs/protocols/process/error.md) would need to say which class a failed construction returns, because it currently distinguishes only the one-cause and multi-cause cases.

### Where does the instance arrive — in the influenced group, or somewhere the language has not named?
- State: this is the sharpest gap and the one that decides every signature. The language states that every variable of a call is passed strictly by reference ([Method in Khayyam → Key Rules](../../../docs/khayyam/method.md#key-rules)) and that the influenced group is where a call writes ([`target.md:50`](../../khayyam/targets/js/target.md#the-artifact-of-one-unit)). The corpus's thirty-three `From*` declarations are consistent with an instance that appears nowhere — a receiver the caller already holds, mutated in place, which is what their ported Go bodies do — and a whole-corpus scan finds none carrying an influenced variable of the type it produces. The one declaration that does carry it, [`construct.kh:26`](../../khayyam/targets/js/bootstrap/construct.kh), is a probe whose implementation is host-supplied, so it does not settle what a library would write.
- What a ruling must decide: whether a construction's result is an influenced variable the caller declares, and if so what it is called. This also decides whether a call on the parent type — `W32.Sum(a, b)(total, err)`, which [Method Invocation Rules](../../../docs/khayyam/method.md#method-invocation-rules) admits and where "the body does not invoke `self`" — can be a construction at all, since such a call has no receiver to write into and no instance to receive.
- Blocks continuation: yes, for every signature, and for whether this library exists in one file or one per Type.
- Path: the language documents. `docs/khayyam/method.md#influencing-and-influenced-variables-not-inputs-and-outputs` is where the two groups are named, and `docs/khayyam/variable.md#overview` is where the responsibility is assigned.

### May a construction be declared as a shared contract, and if not, what replaces it?
- State: the rule that decides it is [Abstraction → What You Cannot Do](../../../docs/khayyam/abstraction.md#what-you-cannot-do) — a capsule type may not be an argument or return type in an abstraction's signature, "only other abstractions are allowed" — combined with [Abstraction → A Concept Is an Abstraction](../../../docs/khayyam/abstraction.md#a-concept-is-an-abstraction-a-concrete-instance-is-a-capsule), which says a signature owned by an abstraction names the concept while one owned by a capsule may name a capsule including itself. A construction's result is a concrete instance, so under this model no Abstraction over capsules can carry it. The corpus's `Factory` returns an abstraction and so is not the shape; and [`target.md:58`](../../khayyam/targets/js/target.md#the-three-kinds-of-body-less-method) refuses at the call site any call whose receiver is typed as an abstraction in this repository's one target. The neighbouring model hit the same wall for a scope parameter, recorded in [`modules/process/control-flow/answers.md:157-161`](../control-flow/answers.md).
- What a ruling must decide: whether construction stays per-Type — each capsule's own method, no shared surface — or whether the language admits a form in which an Abstraction's method delivers a concrete instance. The first is available today and loses organizational replaceability; the second requires a change to `docs/khayyam/abstraction.md#what-you-cannot-do` and to the two documents that would follow from it.
- Blocks continuation: yes, for the file layout and for whether this module declares anything at all.
- Path: the owner of `docs/khayyam/abstraction.md`, together with the delivery question above, because the two are one signature. This is the single decision on the critical path.

### Is a Construction reachable on every path that reaches a use of its slot, and who checks that?
- State: the language makes an uninitialized `vr` a refusal — [Khayyam → How Khayyam realizes Memory](../../../docs/khayyam/khayyam.md#how-khayyam-realizes-memory) names definite-assignment analysis as the source of that correctness, and [Memory → Uninitialized reads are refused](../../../docs/protocols/memory/memory.md#uninitialized-reads-are-refused) prescribes the refusal without prescribing a keyword. Deciding which paths reach a use is a control-flow question, and [`modules/process/control-flow/`](../control-flow/) exists to model it, with the corpus's measurement at [`target.handoff.md:85`](../../khayyam/targets/js/target.handoff.md) recording that "the library which would supply it does not exist yet".
- What a ruling must decide: nothing — this is a dependency, not a question of judgment. What it decides is the order of work: a construction library cannot be validated until the control-flow library that a definite-assignment analysis would be built on exists.
- Blocks continuation: yes for any Test of a construction library, and no for writing the declarations.
- Path: [`modules/process/control-flow/`'s own handoff](../control-flow/model.handoff.md#open-questions), whose owner question and scope-parameter question must be settled before that model can be written.

### What is the first instance of a capsule, and who writes the statements that produce it?
- State: already open in the language's own records and not reopened here. [Variable in Khayyam Handoff → How does the compiler obtain the first instance's values from source?](../../../docs/khayyam/variable.handoff.md#how-does-the-compiler-obtain-the-first-instances-values-from-source) records the literal-to-instance half as undecided and entangled with [Khayyam Handoff → Stdlib bootstrap ordering under the no-hidden-primitive rule](../../../docs/khayyam/khayyam.handoff.md#stdlib-bootstrap-ordering-under-the-no-hidden-primitive-rule), which records the ordering problem as unstated; and [Variable in Khayyam Handoff → Where are the statements that build or bind a file-level `vr`'s initial state written?](../../../docs/khayyam/variable.handoff.md#where-are-the-statements-that-build-or-bind-a-file-level-vrs-initial-state-written) records the missing source form and what it blocks. The corpus's own answer is the host in four places, none of which has a `.kh` form: [`modules/gui/protocol/application.kh:10`](../../gui/protocol/application.kh), [`modules/net/gp/init.kh:6`](../../net/gp/init.kh), [`modules/identifier/mediatypes/media-types.kh:3`](../../identifier/mediatypes/media-types.kh), and [`modules/codec/compress/gzip/init.kh:12-13`](../../codec/compress/gzip/init.kh).
- What a ruling must decide: in which source, and under what form, an author writes the statements that construct or bind a file-level variable's initial state. The model's contribution is to name this as a construction question rather than a variable-syntax one, since what is missing is the producing step and not the declaration.
- Blocks continuation: yes for a program whose first value is a file-level variable; no for a library declaration, which has no first value.
- Path: with the two language handoff entries above, and jointly with whatever the bootstrap-ordering question produces. This session did not reopen either.

### Which declaration survives — `CapsuleLifeCycle` or `Capsule_LifeCycle`?
- State: two declarations of one teardown contract, one word apart, in the same folder. [`modules/computer/capsule/protocol/life_cycle.kh:5,14`](../../computer/capsule/protocol/life_cycle.kh) declares `CapsuleLifeCycle` with `Deinit`; [`modules/computer/capsule/protocol/life_cycle_contract.kh:7-8`](../../computer/capsule/protocol/life_cycle_contract.kh) declares `Capsule_LifeCycle` with `Deinit` and the same exclusion stated in prose. The first is imported by nothing in the tree; the second is imported by thirteen files, including [`modules/crypto/hash/protocol/hash.kh:3`](../../crypto/hash/protocol/hash.kh) and every OSI layer under `modules/net/protocol/`. Under [Khayyam → Import Mechanism](../../../docs/khayyam/khayyam.md#import-mechanism-in) that is a collision whether or not both are reachable.
- What a ruling must decide: which of the two survives, under what name, and whether the lifecycle contract's home is where construction belongs — that is, whether a construction declaration joins this contract or stays beside it. The two questions are one: a lifecycle contract that carried construction would be a contract over capsules, which the third open question above says the language currently forecloses.
- Blocks continuation: no for this model's concepts; yes for the first `.kh` file written here, and for any file that would import either declaration.
- Path: the owner of `modules/computer/capsule/`, which this session does not own. Recorded rather than resolved.

### Does the word `constructor` in the language's encapsulation document get a Memar definition or a different word?
- State: [`docs/khayyam/encapsulation.md:62`](../../../docs/khayyam/encapsulation.md) says obtaining a new instance "still requires going through that type's own constructor or an explicit copy/clone abstraction it chooses to implement — there is no ambient, type-independent way to conjure a value". A search of the whole documentation set returns that line as the only occurrence of the word; no document defines it. Under [Terminology → The Default Meaning of an Unreferenced Term](../../../docs/terminology.md#the-default-meaning-of-an-unreferenced-term) it therefore carries its ordinary sense, which in a corpus ported from Go is Go's and C++'s constructor — a fixed, type-declared special member, which is not what a Khayyam construction is, since the language has no constructor declaration form at all.
- What a ruling must decide: whether that sentence keeps the word and gains a definition pointing at whatever this model settles, or whether it is rewritten. Either way the sentence's *claim* — that there is no ambient type-independent way to conjure a value — is one this model affirms and rests on.
- Blocks continuation: no for any declaration; yes for the model's own names graduating into the language documents.
- Path: the owner of `docs/khayyam/encapsulation.md`. This session did not edit that file.

### Is a Construction replaceable per organization, and what replaces it if a contract is unavailable?
- State: [Compiler → The compiler recognizes language primitives, not library names](../../../docs/protocols/computer/compiler.md#the-compiler-recognizes-language-primitives-not-library-names) says the compiler "does not treat library-provided operations as intrinsics because they are common, useful, or imported from a privileged package", and names "lifecycle hooks" among them — a construction spelled in the ecosystem's terms. [Modeling → Extensible Behavior Belongs to Pluggable Modules](../../../docs/modeling.md#extensible-behavior-belongs-to-pluggable-modules) gives the general form. The neighbouring model made the same claim for flow forms and found it forces the owner question, at [`modules/process/control-flow/model.handoff.md:75`](../control-flow/model.handoff.md#open-questions).
- What a ruling must decide: whether a construction is per-Type-and-therefore-not-replaceable, or whether an organization can mandate its own — and if the former is forced by the abstraction-signature rule, whether that is acceptable. This is the question behind the contract question and should be answered with it.
- Blocks continuation: no for writing a per-Type declaration; yes for anything an organization is to be able to mandate.
- Path: the owner, jointly with the contract question above.

## Assumptions
- **The thirty-three `From*` declarations are the corpus's construction surface and not an accident of migration** — Stability: Weak. What changes it: a document stating that the port dropped the influenced group deliberately, or a corpus declaration outside the `From*` family that writes a freshly-obtained instance into an influenced variable. Mitigation: the whole-corpus scan behind the count was run over every `.kh` file in the tree, so a declaration of that shape would have been found; what it cannot rule out is a declaration the port never wrote.
- **`variables` in the corpus's `From*` family mean "parse this representation", so the family is one route and not the concept** — Stability: Weak. Each member's influencing group names a text, a buffer, or a duration component, which supports the reading, but no document states it. What changes it: a ruling that names the family. Mitigation: the model treats the family as evidence of a *route*, not as a concept, so a contrary ruling removes a claim and not a boundary.
- **The JavaScript target's reading of the artifact is a faithful measure of what the language admits** — Stability: Weak. The model rests several citations on one target: the four commands, the cell-per-variable reading, the constructor seam, and the refusal at the call site. What changes it: a second target disagreeing on any of the four, which would make those citations this realization's readings rather than the language's statements. Mitigation: each citation names the target document and section rather than a bare claim, and where the target itself records that a reading is its own — as at [`target.handoff.md:92`](../../khayyam/targets/js/target.handoff.md) for field access — the model says so.
- **A `.kh` construction library, once its signature is settled, will be per-Type rather than one file** — Stability: Unexamined. This follows from the abstraction-signature rule rather than from any decision, and no file has been written to test it. What changes it: a ruling admitting a capsule in an abstraction's signature, or a per-Type declaration that turns out to need a shared surface to be usable. Mitigation: the third open question names the decision, and this assumption should be revisited with it.
- **Nothing in `modules/process/control-flow/` will move to make a construction name fit** — Stability: Unexamined. What changes it: the control-flow owner ruling that a shared lifecycle contract grows a construction member. Mitigation: none available to this session; recorded as the neighbouring model's own unexamined assumption, which this one inherits rather than resolves.

## Anticipated Work
- A language topic on obtaining an instance, in `docs/khayyam/`, once the delivery and fallibility questions are settled. It would say what a construction must mean, where its result arrives, and whether it can fail — the three things this model shows a library cannot be written against without.
- An `answers.md` companion of the kind [`modules/process/control-flow/answers.md`](../control-flow/answers.md) is, if the questions above are put to the corpus rather than reasoned about. The measurement this session ran — a whole-tree scan for a `From*` declaration whose influenced group names its own owner's type — is repeatable and its result is reproducible.
- A joint statement with [Memory](../../../docs/protocols/memory/memory.md) on the boundary between Acquisition and Construction, since the corpus already uses the word "acquisition" at [`modules/computer/capsule/protocol/life_cycle.kh:12`](../../computer/capsule/protocol/life_cycle.kh) in the Memory sense while this model refuses it as a concept. The refusal is a modeling decision; whether the corpus's usage agrees is the owner of that folder's.
- A statement on whether a derived instance — from `Copy`, `Clone`, or a constant — counts toward a type's construction surface for any tooling that must check a value's provenance. [Type → Structure Is Fixed by Definition](../../../docs/type.md#structure-is-fixed-by-definition) keeps provenance out of the language's scope, so this would be governance under [Rule → Where Rules Live](../../../docs/rule.md#where-rules-live-rules-beside-protocol), not grammar.
