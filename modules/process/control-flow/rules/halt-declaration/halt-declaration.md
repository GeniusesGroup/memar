# Control Flow Rule — Halt Declaration
Control Flow's rules live one rule per folder under [`modules/process/control-flow/rules/`](../README.md), and this is the rule for an execution that ends without passing through the ordinary path of any decision before it — a **Halt**, which is the name the [Control Flow model](../../docs/control-flow.md#halt) gives the concept and the name [Control Flow → Error Propagation](../../control-flow.md#error-propagation) at `:144` gives the operations that perform it. It is a governance rule of this repository, held for the [Control Flow protocol](../../control-flow.md): that sentence states that abrupt execution halts are explicit operations in the realization's library or contract layer, and `:152` registers the halting semantics themselves — the contract of such an operation and its relationship to error propagation — as a subject the protocol has not yet designed. This Rule states what an organization does with that operation; it does not design its contract.

## The rule
- **A halt is an operation, and it is written where the caller reads it.** When an operation may end the execution, that possibility is stated in the surface the caller sees: in the operation's own declaration, or in the contract of the type that owns it. `:144` already requires the operation to be explicit in the realization's library or contract layer, and an operation nobody can see is not explicit in that layer but announced from inside it.
- **What leads to a halt is stated with the operation, not only in its body.** The conditions under which an execution ends are written where the caller of that operation reads them, so that a reader of the call site learns what may end the run without leaving the declaration. This is the same visibility the protocol requires of an error path (`:141`, `:143`), reached from the halt's side.
- **Governance over halting is the organization's.** Which halt operations a codebase may use — all of them, some of them, or none — is configured by that organization's own tooling, per [Control Flow → Structured and Unstructured Flow as Libraries](../../control-flow.md#structured-and-unstructured-flow-as-libraries) at `:134` and [Linter → Configuration and override](../../../../computer/linter/linter.md#configuration-and-override). Turning that configuration off changes which operations a codebase uses; it does not change what a halt is or whether one exists.
- **A failure reported by nothing but a halt is a disregarded failure, and one Rule governs that.** Where the failure could have been accounted for inside the call the operation was made through, the halt is the wrong report, and the [disregarded error Rule](../../../error/rules/disregarded-error/disregarded-error.md) is what governs the case — because its subject is the failure, not the halt. A halt that ends an execution over a condition no caller could have been told about is that Rule's instance, and a halt that ends one over a condition the caller was told about is this Rule's ordinary case.

## Why it exists
The concern has a module already, and this Rule is what was missing from it. `modules/process/control-flow/` holds the model that names Halt as one of four independent concepts ([control-flow.md](../../docs/control-flow.md#halt)), the two declarations that would realize it ([`protocol/panic.kh`](../../protocol/panic.kh) and [`protocol/panic-recovery.kh`](../../protocol/panic-recovery.kh)), and a README that says the folder's contract is the protocol's; what it held no `rules/` folder for, so the concern existed as a refusal inside a Rule about a different subject.

The protocol already draws the line this Rule states, and this Rule restates it imperatively rather than adding to it. [Control Flow → Error Propagation](../../control-flow.md#error-propagation) at `:143` requires every fallible operation to expose its error path "as an ordinary, named part of the call contract", and at `:144` requires abrupt execution halts to be explicit operations in the realization's library or contract layer; an operation nobody can see is explicit in neither, and a caller told only by a halt arriving has been told out of band. The protocol also declines to design the halt's contract — `:152` registers the halting semantics as a subject it does not yet hold — so the obligation this Rule states is the visibility of the operation and nothing about what the halt carries.

Two findings about this repository's `.kh` files are recorded as what they are, and no rule rests on either. [`modules/computer/runtime/thread/protocol/thread.kh:29`](../../../../computer/runtime/thread/protocol/thread.kh) carries a design note above its own commented `Execution_Exception` proposal — "Even when a package uses panic internally, its external API still presents explicit error return values" — and the ported bodies hold halts at `modules/computer/buffer/____ring.kh:333` and `:384`, `modules/net/____workerpool.kh:60` and [`modules/computer/runtime/scheduler/thread.kh:56`](../../../../computer/runtime/scheduler/thread.kh), every one of them inside archived Go source rather than a signature. Those files are the residue of an attempt to develop these ideas in another language that did not succeed, and the owner has ruled that they are neither evidence nor a premise; they are named here as a record of the repository's state, and neither line above was this Rule's ground.

The name follows the repository's own. [Control Flow Model → The names to use and the names to refuse](../../docs/control-flow.md#the-names-to-use-and-the-names-to-refuse) at `:129` says to use `Halt` following `:144` and the protocol's registered topic, and at `:131` refuses `panic` as a library concept name and `Recover` with it: an unreferenced `panic` carries Go's meaning rather than Memar's, and what the observation of a halt means is the protocol's own open topic. A Rule about the concern takes the name the model settled rather than the ecosystem's spelling.

## Keep it or drop it
An organization may configure its tooling to permit every halt operation, to require a stated error path in preference to one, or to forbid halting in a codebase it governs — all three are conformant here, and the third is what `:144` means by governance being supplied by tooling rather than by the grammar. What an organization may not do is change what a halt is while keeping the name: a codebase in which an operation ends the execution without saying so is not relaxing this Rule, it is running under a second meaning of the same source. Dropping the Rule is dropping the obligation to state the halt, and it costs the caller the only notice it had.

## What this rule does not claim
- It does not claim a halt may not exist, nor that halting is bad. `:144` treats halt operations as legitimate and explicit, and this Rule is about where that operation is written.
- It does not design the halt's contract. What a halt carries, what it reports, and whether it carries an `Error` and of which class are the protocol's registered topic at `:152` and [The Error](../../../error/error.md); this Rule states none of them.
- It does not claim the observation of a halt belongs here. What `RuntimePanicRecovery` in [`protocol/panic-recovery.kh`](../../protocol/panic-recovery.kh) and the handler in [`modules/process/log/panic_handler.kh`](../../../log/panic_handler.kh) are for is named as elsewhere-owned in the model at `:93`, and `Recover` is refused as a name at `:131`.
- It does not claim the two declarations named above become one contract, or that either survives; the model records the collision at `:78` and the declaration is not this Rule's to settle.
- It does not claim anything about what any `.kh` file in this repository does, in either direction. The code under `modules/**` is residue of an attempt to develop these ideas in another language that did not succeed, the owner has ruled that it is neither evidence nor a premise, and a rule's justification rests on the documents that own its subject — here the Control Flow protocol. Whether any declaration in this repository states a halt in its own signature was not measured, and the question is carried in the paired handoff.
- It does not restate the first Rule in this folder. A failure's carriage and a halt's declaration are two subjects, and each Rule speaks about its own.
