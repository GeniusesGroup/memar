## Topic & Purpose
What the documents and the `.kh` sources of this repository settle about the nine open questions the Control Flow model handoff carries, and what they leave open. The base document holds each answer with its citations; this file holds what a session needs that the base document deliberately does not — the state of each remaining question, the assumption each answer rests on, and the defects found outside this folder that no session has yet fixed. It is the working state that [control-flow.handoff.md](../control-flow.handoff.md) cannot be, because that file's questions were written before the evidence was gathered.

## Status
Active — nothing in the base document's answers has been ruled on, and the one disagreement between two of this repository's documents that the base document recorded has since been corrected in the document that made it.

## Decisions
- **Every question was answered by reading, and none was answered by choosing** — Decided. Each of the nine was put to the language documents first, then the protocol, then the `.kh` sources, then the toolchain's measurements, in that order, because that is the repository's own division of subjects. Reason: a question answered by argument would harden into a second authority over the same subject, and the one thing this chat can settle without the owner is which questions the evidence cannot settle at all. A question the evidence does not settle is carried below with the sentence that would have to be written, so the next chat can write that sentence rather than re-derive the search.
- **Silence is reported as a named absence, never smoothed into an answer** — Decided. Where no document states something, the base document names the document, the section, the sentence that would be needed, and the other document that would change with it. Reason: [Documentation → Content Rule](../../../knowledge/documentation/documentation.md#content-rule-no-fabricated-or-redundant-provenance) requires that an unknown be "stated as unknown or omitted, never glossed over with a confident-sounding filler", and a gap that reads as an answer is worse than a gap that reads as a gap — the first gets built on, the second gets closed.
- **A `.kh` witness is cited as a record, never as a ruling, and never as evidence** — Decided, 2026-10-03, replacing an earlier decision of this chat. The earlier decision said that where the only evidence for an answer is what some `.kh` file or some test fixture writes, the base document names the file and line and treats it as a declaration rather than a ruling. That was half a measure: it corrected the *authority* of a unit in the sources while continuing to use it as *evidence*, which is the same error at one remove. The code under `modules/**` is the residue of an attempt to develop these ideas in another language that did not succeed, and the owner has ruled it neither evidence nor a premise. So the rule is now: where the only witness is a `.kh` file, the answer is not available from it; the document names the witness as a record of the tree and reports the silence as the gap, and the answer waits for a sentence some document owes. Two earlier supports for the half-measure are withdrawn with it — that the one measured realization of a two-branch contract survives only as a compiled build product whose source is absent (still true, and still not the reason), and the [Compile cache](../../../../bundles/khayyam/khayyam.handoff.md#compile-cache) maxim about compiled JavaScript (still true, and about build products, not about source). This folder's own test fixtures are unaffected: they are this toolchain's measurements, written for the purpose, and not residue.
- **The nine questions are one decision wearing several hats, and one of them gates the rest** — Explored-but-unresolved. The first, the second, the third, the seventh, and the ninth questions cannot be answered independently: the owner of the forms, the type of its scope parameter, and the type that owns the two-branch contract are one signature. Reason: the pair's members have to reach the branch body, and `modules/process/control-flow/control-flow.md:59` requires the observable dependency boundary while permitting "named scopes, explicit closures, or another mechanism with the same observable dependency boundary" — so what is required is the boundary and not a named scope, and the protocol does not decide the spelling. In this language nothing an Abstraction may name reaches that boundary: a branch scope is the `sc` subtype (`docs/khayyam/khayyam.md:127`), an `sc` is a Scope rather than an Abstraction (`docs/type.md:181`), and an Abstraction's method signature may name only Abstractions (`docs/khayyam/abstraction.md:101`), which the owner's ruling of 2026-10-02 confirms on the ground that a code scope is an implementation rather than an abstraction. What is unresolved is therefore the owner's route to the scope: a language change admitting one in an Abstraction's signature — which that ruling refuses — or a library whose owner is a concrete capsule, which this repository's call rules make nominal. `modules/process/control-flow/control-flow.md:130` states that an organization may mandate its own control-flow library through its Linter, which is a claim about a library and not about type substitutability, so the capsule route does not contradict the protocol; it costs the organization's library the call sites that name the capsule. Rejected as a resolution path: declaring the forms on a capsule now and treating the protocol's Linter-governance claim as satisfied — that claim is about a library an organization can mandate, which is not what a capsule fixed in this repository is.
- **No question was carried forward from this chat's own reasoning** — Decided. Every sentence in the base document is cited to a document line or a declaration, and the four that have no such citation are marked as conflicts or as absences. Reason: the base document is an Explanation-facet document and [Relevance discipline](../../../knowledge/documentation/explanation/explanation.md#relevance-discipline) admits a claim into the body only where reading it changes the reader's understanding of the design as it stands; an unreferenced inference would be this chat's opinion wearing a document's clothes.

## Assumptions
- **A scope may be written in a signature if a document says so** — Stability: Strong. The grammar already admits an `sc` in an influencing group (`docs/khayyam/method.md:71`) and already admits a type-level argument for `sc` (`docs/khayyam/khayyam.md:131`), so nothing structural stands in the way; what is missing is the sentence. What changes it: a ruling that the position exists only as a type-level argument and not as a declared parameter type, which would move the question from a naming one to a grammar one — or the owner's ruling of 2026-10-02, which holds that a code scope is an implementation rather than an abstraction and so leaves the spelling to a signature that is not an abstraction's.
- **The absence of a scope parameter's type in the language documents is a gap and not a deliberate delegation** — Stability: Weak. `docs/khayyam/method.md:71` enumerates the three forms an influencing group may receive and then does not say how a scope's own is written, and `bundles/khayyam/targets/js/target.handoff.md:54` reads the same absence. A document could intend the realizing tool to decide, as it does with file layout. What changes it: a sentence in `docs/khayyam/khayyam.md#scope` or `docs/khayyam/method.md` delegating the spelling to the realization, which would make the toolchain's reading the standing one and this repository's answer to the question would be "whatever an organization states".
- **The JavaScript target's fixture is a faithful record of what `lib/control-flow.kh` declared** — Stability: Weak. It is the fixture a compiler test compiles, and the stored representation at `bundles/khayyam/targets/js/build/.cache/modules_khayyam_targets_js_lib_control-flow.kh.json` agrees with it declaration for declaration, so the two corroborate each other. What changes it: evidence that the fixture and the built artifact diverged from the source, or that the source changed after the last build.
- **A removed source's declarations are not an authority over the protocol** — Stability: Strong. `bundles/khayyam/khayyam.handoff.md` → Compile cache says compiled JavaScript is a build product and never a source of truth, and the removal at `bundles/khayyam/targets/js/target.changelog.md:87-88` carries a reason — "a library belongs with the rest of the library under `modules/`, and a model settles before code is written". What changes it: nothing in this repository; this assumption would change only if a later ruling adopts a target's fixture as a reference library, which the changelog entry argues against.
- **`Conditional` in `modules/math/logic/` is a Flow Decision outcome enumeration or an unrelated logic value, and not a third option** — Stability: Unexamined. Neither reading has been tested against `modules/math/math.md#realization-membership` or against what `modules/math/logic/conditional.observers.kh` would mean under each. What changes it: an owner ruling of `modules/math/logic/` — or a finding that a third reading exists, in which case the base document's fifth answer is incomplete rather than wrong.
- **The nine questions in `control-flow.handoff.md` are the complete set** — Stability: Strong as of this chat, and only as of it. The file carried nine `###` headings at the time of writing and no more. What changes it: another session appending a question to that file; nothing in this folder's own state would reveal it.
- **`modules/process/control-flow/protocol/` gains no declaration before the owner question is ruled** — Stability: Strong. `modules/process/control-flow/control-flow.handoff.md:10` states it, and `bundles/khayyam/targets/js/target.changelog.md:87-88` records that the model's settling preceded any code. What changes it: an owner ruling that permits a declaration whose owner is provisional.
