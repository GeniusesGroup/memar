# Event

## Abstract
`Event` is the framework's protocol for making an occurred fact available to participants the producer does not know, and for the capability through which such a fact reaches them. This document states what an Event is and is not, that an Event is a runtime occurrence rather than a stored record, that the capability is named `EventTarget` and belongs to the Type or Module that exposes it rather than to a parallel event data model, that the paired `EventListener` contract has exactly one mandatory member, that synchrony, capture order, once-only delivery, and listener options are properties of a dispatch and its registrations rather than members of either abstraction, and what a dispatch's `Error` does and does not carry. It consumes, and does not re-argue, the concept of an event as a Process owns it in [Process → Events](../../../docs/process.md#events), and it consumes the identity discipline [The Error](../error/error.md#identity-and-equality) states for itself rather than settling afresh what makes two occurrences of one kind the same occurrence.

## Introduction

### Motivation
The broader software ecosystem arrives with a settled-looking vocabulary for events — `EventTarget`, `addEventListener`, capture and bubble phases, `once`, `passive`, `cancelable`, `defaultPrevented` — and a reader arriving from it will assume those names carry their ecosystem's meaning. Four failures follow unless this protocol says otherwise, and each is a failure this repository has a document for elsewhere and cannot leave implicit here.

1. **The word doing three jobs at once.** An ecosystem's *event* names three different things: the fact, the value carrying it, and the channel it travels on. The concept document already separates the fact from its representation — a message, a record, a callback, a broker, or a log is an implementation concern unless the representation is itself part of the domain. A protocol that does not fix which of the three each of its own declarations names will have a reader inferring a wire format from a method signature.
2. **The mechanism's properties arriving as the concept's members.** Whether a dispatch returns before its handlers finish, whether a handler may see an event before one bound closer to the producer, whether a listener fires once — the concept assigns all of these to the rules of the mechanism that handles the event rather than to the event itself. The ecosystem nonetheless carries them as members of the listener and of the target, which is how a web page's propagation model becomes an assumption inside every type that has ever heard of a listener.
3. **A target that accepts any event, and therefore a listener that hears the wrong one.** Nothing in the ecosystem stops a listener for a keyboard event from being handed a storage record. The restriction that a target accepts only the kind of event it declared is the whole reason "which listeners hear this" is answerable, and it is lost the moment a target's event parameter widens to a base type that every event satisfies.
4. **A handler with no channel for its own failure.** A handler that returns nothing cannot report that it failed, and a dispatch that swallows that silently turns a broken listener into an invisible one — the class of defect the ecosystem's unhandled-rejection reporting exists to surface. [The Error → Boundary discipline](../error/error.md#boundary-discipline) already separates a contract addressed to a caller from a forensic record addressed to an operator, and that separation is what answers this; the protocol's job is to apply it rather than to leave each handler to invent a policy.

The naming is not a fifth question but a standing obligation. `EventTarget` is the name [Modularity → Event as a Module Capability](../../knowledge/modularity/modularity.md#event-as-a-module-capability) gives the capability, and it is the name the sources write. A bare `Target` says nothing about events in a body of source where `GUI_Event`, `Race_Event`, `ProcessLog_Event`, and `Net_PacketTarget` all say what they qualify, so it fails the qualified names rule (`bundles/khayyam/rules/qualified-names/qualified-names.md`) on collision grounds before any question of taste arises.

### Methodology
The contract was read out of the concept document first and the code second, and where the two disagreed the disagreement was recorded rather than resolved in the code's favor. That order decided the document's central question: the concept assigns handler behavior to the mechanism, so the five listener properties the ecosystem carries as members were examined as *properties of a registration* rather than of a listener, and all five failed the test — each is stated by the act of adding a listener to a target, none is stated by the listener itself, and a listener commonly has several registrations at once. What survived the same examination is the one member a listener cannot be without.

The narrowing question — how a target comes to answer one kind of event rather than every kind — was settled twice, and the first answer was wrong. The first draft read the language's composition and behavioural-satisfaction position and concluded that a target for one kind of event must be a specialization composing a narrower event abstraction and a narrower listener abstraction. The owner's objection, and the language's own text, correct it: Abstraction → Abstraction Realization (Implicit Satisfaction) (`docs/khayyam/abstraction.md#abstraction-realization-implicit-satisfaction`) holds that influencing-variable types must match **exactly**, with the receiver the one thing allowed to differ. A narrowed event parameter therefore satisfies nothing, and the declarations written on the strength of the first answer were removed rather than kept as a documented cost. What the language offers instead is Abstraction → Dispatch Strategy (`docs/khayyam/abstraction.md#dispatch-strategy`): the grammar names no resolution strategy and no syntax to choose one, so what arrives is settled at the call, and a target's own body is where a kind of event is recognized. What this document records from that is not a preference for composition over declarations — it is that a narrowing in an influencing position is not a way to narrow a capability at all, and that a rule now states it so no later session has to derive it.

## Explanation

### What an Event Is
An **Event** is an abstraction a Type composes to declare that an occurred fact of that kind exists. Composing it is what makes the fact dispatchable; it is not a claim that the fact is held anywhere.

An Event composes the two abstractions that give an occurrence its identity and its place in time, and nothing else the protocol requires. The declaration is [`protocol/event.kh`](./protocol/event.kh); what each composed abstraction is there for follows.

`Observer_Type` supplies the type-level identity machinery, so a receiver dispatches on the kind of event without the producing Type's whole method set in scope. `Observer_Time` supplies when the fact occurred, because two occurrences of one kind are otherwise indistinguishable and a listener that cannot tell them apart cannot answer "the second one" to anything. `Logic_Equivalence` is what lets a receiver compare two occurrences; what that comparison means is a question this protocol does not settle, and the reason it does not settle it is stated under [What this protocol does not claim](#what-this-protocol-does-not-claim).

**An Event is a runtime occurrence and is not a stored record.** An Event names a fact that happened; the composition says nothing about whether the fact survives the process that observed it. A Type that both dispatches an Event and keeps the record it came from keeps two different things, and the protocol requires only the first. This is the reason an Event's identity machinery is composed rather than a field: what is kept is a record, what is dispatched is an occurrence, and a protocol that let the second stand for the first would make retention a property of every dispatch.

**Every kind of event is its own abstraction.** A race report, a log entry, and a GUI touch are each declared as their own Event, following the identity principle [Type](../../../docs/type.md) states and [The Error → Enforcement of the "each Error is its own type" rule](../error/error.md#enforcement-of-the-each-error-is-its-own-type-rule) applies to errors. This is what makes the restriction in [A target accepts only the kind of event it declared](#how-a-target-narrows-to-one-kind-of-event) expressible at all: a target specialized to a narrower Event abstraction is stating which kind it takes, and that statement has somewhere to point.

**The data an occurrence carries belongs to its own kind.** The `Event` abstraction composes identity and time and nothing else, so a kind of event that carries a payload composes that payload on its own declaration rather than widening `Event` with a field every other kind would then have to answer for. The consequence is that the base contract cannot promise a listener access to the fact's content, only to which fact it is and when it occurred; a listener that needs the content depends on the kind's own abstraction, which is the direction the dependency runs everywhere else — on the abstraction, not on the instance.

### What an Event Is Not
Three separations carry most of the protocol's weight, and each is a place the ecosystem's word does not separate.

**An Event is not a command.** A command is addressed to a known participant and says what that participant must do; an event states a fact and does not name who acts on it. The producer of an event does not know its consumers, which is what makes an event usable by a participant the producer has never heard of. A capability that addresses a known participant with a known expectation is a request, and it belongs to the request and response protocols, not here — the two are consumed together wherever a system's boundary is an operation rather than an occurrence.

**An Event is not a continuation of the process that emitted it.** The concept states this directly: a process may emit an event and continue independently, and a receiving process does not become a participant, a sub-process, or a continuation merely by reacting. What follows for this protocol is that a listener is not a participant in the producer's Process, and the producer's expectations do not extend across the dispatch to cover what listeners do.

**An Event is not its representation.** Whether an occurrence travels as a message, a record, a callback, a broker entry, or a log line is the mechanism's business. The distinction is not academic here, because [The Error → Boundary discipline](../error/error.md#boundary-discipline) forbids the one representation that would otherwise be reached for: a single-locale human-readable string bound to the wire. An Event crossing a network boundary carries the identifier its `Type` supplies, and each side resolves that identifier into text for its own audience.

### The EventTarget capability
An **EventTarget** is a capability a Type or Module composes to declare that an occurred fact of some kind may be dispatched to participants that registered for it. The name is the one [Modularity → Event as a Module Capability](../../knowledge/modularity/modularity.md#event-as-a-module-capability) gives it, and the contract is three methods, declared in [`protocol/event-target.kh`](./protocol/event-target.kh).

The capability belongs to the Type or Module that exposes it. It does not require a separate conceptual model of events, and a system whose service request and response models already carry the relevant data does not acquire a parallel structure to notify anyone — the same conclusion [Modularity → Event as a Module Capability](../../knowledge/modularity/modularity.md#event-as-a-module-capability) reaches about the data model, applied here to the channel.

`AddEventListener` appends a listener to the target's own set, and `RemoveEventListener` removes one that is in it. Neither is keyed by a listener's name, a type parameter, or an option set: the listener value is the key, and what the set holds is listeners. A target that cannot accept a listener says so through its `Error` on `AddEventListener` rather than by refusing the dispatch later.

The `Error` these three methods return is the [Error](../error/error.md) abstraction, not a concrete error type, because each of the three may fail for more than one reason — a dispatch to a target that holds no listener for the event, an addition a target cannot hold, a removal of a listener it does not hold — and a caller that must branch on the reason needs the abstraction's type inspection rather than a single named type. This follows [The Error → Multi-cause returns](../error/error.md#multi-cause-returns) applied to the Event capability.

### The EventListener contract
An **EventListener** is the other half of that capability: the contract something satisfies to be handed an occurrence. It has exactly one mandatory member, declared in [`protocol/event-listener.kh`](./protocol/event-listener.kh).

`EventHandler` is mandatory because a listener that cannot be handed the occurrence is not a listener. That is the whole of it, and the restraint is the protocol's claim rather than an omission.

#### Why capture, once, passive, and synchrony are not members
The ecosystem carries five further members on its listener — `capture`, `once`, `passive`, a synchrony or blocking declaration, and an abort signal — and the sources' own residue carries the same five as open considerations. None of them is a member here, and the reason is the same for all five: **each is a property of a registration, not of a listener.**

A registration is the act of adding one listener to one target. A listener may hold several registrations at once, against the same target or against different ones, and each registration may differ from the others. A listener that is registered once may be registered again elsewhere and fire again there. A listener registered during the capture phase and the same listener registered during the bubble phase are one listener with two registrations, and only the registrations differ. Once the property belongs to the registration, the listener has no such property to carry, and an abstraction that declared it would be declaring a value that is true of one of its uses and false of another.

Two of the five fail a second test besides.

`capture` names a position in an ordered tree of targets — an event is delivered to a target's ancestors before the target itself, or after it, and the two orders are what the web's propagation model is built on. That tree is a property of one ecosystem's dispatch mechanism. This protocol has no target tree: a participant that reacts to an occurrence does not become part of the process that produced it, and a hierarchy in which a nearer ancestor intercepts an occurrence before the producer's own target sees it is a statement about the hierarchy, not about the fact. Where a system does have such a tree, the order is that system's dispatch rules.

`synchronous` names whether the caller waits. The concept assigns this to the mechanism explicitly: an event-handling mechanism may let the originating process continue independently, or may temporarily or conditionally affect its continuation. What the protocol can require is therefore not a synchrony but its consequence — that a listener may not assume the caller's state is unchanged by the dispatch, and that a caller may not assume its own continuation is unaffected. Both are obligations on the two parties rather than a member on either.

The corollary is where these five do belong. They are the dispatch mechanism's parameters and its registration's parameters, and a system that has them states them in its own dispatch contract and its own registration type. [Process → Mechanisms Are Not Obligations](../../../docs/process.md#mechanisms-are-not-obligations) is the principle: what a mechanism does is the mechanism's to state, and the concept does not oblige it.

### Dispatch
A **dispatch** is the act of handing one occurrence to the listeners a target holds for it. Three things about it are the protocol's to state, and each of them is a question a reader of a signature cannot answer.

#### A dispatch's listener set is the set the dispatch started with
A dispatch that iterates a live listener set lets a handler change what the rest of the dispatch sees: a handler that adds a listener may see it invoked in the same dispatch, and a handler that removes one may shift the positions the remaining handlers are visited at. Both make a dispatch's behavior a function of what its handlers do, which is the property that makes dispatch order unstateable and untestable.

The protocol requires that a dispatch sees the listener set as it stood when the dispatch began. A listener added during a dispatch is first seen by a later dispatch; a listener removed during a dispatch is still handed this one. This is decidable, and it is decidable from the outside: a handler that adds a listener and asserts on how many times it ran decides the question.

#### A dispatch does not carry its handlers' failures
`EventHandler` returns nothing, and a dispatch's `Error` carries the dispatch's own failures only. This is the [Error versus Log](../error/error.md#boundary-discipline) separation applied at the dispatch rather than at a layer crossing: the dispatch's contract is addressed to the caller and says whether the occurrence reached the target's listeners, and a handler's failure is that handler's own business, reported through its own layer's discipline — returned as that layer's `Error` to its own caller, or captured and persisted as a log event where that layer's boundary requires translation.

The alternative is stated so it can be refused deliberately: a dispatch whose `Error` also carries what its handlers returned would make one listener's failure indistinguishable from the dispatch having not happened, and would make a caller of the dispatch responsible for failures it has no vocabulary for. A target whose listeners routinely fail is a target whose dispatch is not the place that problem is visible.

#### What a listener may assume about the occurrence
A listener is handed one occurrence and may assume it is the one that was dispatched, with the identity and time its Event composes already answered. It may not assume the target holds no other listener, that it is the first or last to be called, that it is called at all for a dispatch that reached no listener, or that a dispatch it did not hear has not happened. None of these is promised by the contract, and each of them is the kind of assumption that survives a correct implementation and breaks the next one.

### How a target narrows to one kind of event
A target's `DispatchEvent` takes the `Event` abstraction, so a capability that says nothing more hands its listeners every kind of event. How a target narrows that to the kinds it answers is **the target's own business, and this protocol does not prescribe a shape for it.** What it requires is the outcome: a target does not hand a listener an occurrence of a kind the listener was not added for.

The language already has the two halves of that, and a rule records them. A module writes its own kind of event as its own abstraction — `Race_Event` composes `Event` and adds what a race report carries — and composes `EventTarget` where it needs the capability, which is all [Modularity → Event as a Module Capability](../../knowledge/modularity/modularity.md#event-as-a-module-capability) asks of it. What it does **not** write is a second abstraction beside `EventTarget` with the event parameter narrowed, for a reason that is not a matter of taste: Abstraction → Abstraction Realization (Implicit Satisfaction) (`docs/khayyam/abstraction.md#abstraction-realization-implicit-satisfaction`) holds that a capsule satisfies an abstraction "if and only if it implements every method declared by that abstraction", and that for each such method "the influencing-variable types must match exactly, the influenced-variable types must match exactly or via covariant return … and the receiver is the implementing capsule itself". `Event` and `Race_Event` are not the same type, so `DispatchEvent` taking `Race_Event` satisfies nothing — the receiver is the one thing that is allowed to differ, and the parameter is not.

What the language offers instead is where the narrowing actually happens. Abstraction → Dispatch Strategy (`docs/khayyam/abstraction.md#dispatch-strategy`) states that the grammar names no strategy for resolving a call through an abstraction and no syntax to choose one; what a compiler does at a given call site is [Compiler](../../computer/compiler/compiler.md)'s business. So a detector composes `EventTarget`, satisfies it with `DispatchEvent(self <the detector>)(event Event)`, and its body establishes whether the occurrence it was handed is a race report before it acts on it. That is Abstraction → Behavior Over Type Identity (`docs/khayyam/abstraction.md#behavior-over-type-identity`)'s general principle applied where it belongs: the contract names the behavior it requires, and what arrives is settled at the call rather than by a declaration that cannot be satisfied.

The cost that carries is the one a reader should have named for it, and it is not a multiplication of declarations. A target that answers one kind of event discovers at run time whether it was handed another, where a narrowed signature would have discovered it at the point of the call — and in exchange nothing has to be declared twice, nothing has to be kept in step with the general contract, and a new kind of event costs a target nothing to stop recognizing. Where a system wants the earlier discovery, a narrowing belongs in the *target's own* contract rather than in a second abstraction: a capsule may declare `DispatchEvent(self <itself>)(event Race_Event)` and check what it is given, and then it is that capsule's method rather than a capability the protocol composes.

### What this protocol does not claim
- **It does not claim an equivalence relation over occurrences.** `Logic_Equivalence` on `Event` is composed for a receiver that must compare two occurrences, and what the comparison answers is not settled by this protocol. [The Error → Identity and equality](../error/error.md#identity-and-equality) holds identity to be the type-level identifier alone and declines to declare an `Equivalence` method, on the grounds that a second identity source is a second thing to keep consistent. Whether an Event's case differs — whether two occurrences of one kind are distinguishable at all without an occurrence identity the `Type` does not supply — is a question this protocol leaves open rather than a claim it makes.
- **It does not claim a narrowing of the capability is expressed by narrowing its signature.** See [How a target narrows to one kind of event](#how-a-target-narrows-to-one-kind-of-event); the language's own satisfaction rule makes a narrowed influencing type unsatisfiable rather than merely narrow, and the composition-not-duplication rule (`bundles/khayyam/rules/composition-not-duplication/composition-not-duplication.md`) states the standing condition. Polymorphism in Khayyam (`docs/khayyam/polymorphism.md`) owns what a type parameter would mean, for every case rather than this one.
- **It does not prescribe a representation.** No broker, queue, callback registry, or log channel is named by this protocol, and none is required — [Process → Process Is Not a Mechanism](../../../docs/process.md#process-is-not-a-mechanism) holds that a process does not derive its identity from the mechanism enacting it, and the representation of an Event is the narrowest case of that.
- **It does not prescribe synchrony.** See [Why capture, once, passive, and synchrony are not members](#why-capture-once-passive-and-synchrony-are-not-members); the obligations it does place are on the two parties, not on the contract.
- **It does not claim a listener is a participant in the producing Process.** See [What an Event Is Not](#what-an-event-is-not).
- **It does not require a handler to be free of side effects on the caller.** What a handler may do to the dispatch is bounded by the dispatch's own listener-set rule and by whatever the dispatch mechanism states; the protocol does not add a sandbox claim it could not keep.

### Relationship to other concepts
**Process.** [Process → Events](../../../docs/process.md#events) owns what an event is at the concept layer; this protocol is what a system conforms to when it declares and dispatches one. The citation runs downward — the concept is not restated here and its document is not revised by this one.

**The Error.** [The Error](../error/error.md) is a consumed contract, not a base: this protocol's three methods return it, its dispatch boundary is an application of [The Error → Boundary discipline](../error/error.md#boundary-discipline), and its identity argument is why this protocol does not settle equivalence over occurrences.

**Modularity.** [Modularity → Event as a Module Capability](../../knowledge/modularity/modularity.md#event-as-a-module-capability) places the capability on the Type or Module that exposes it and refuses a separate event data model; the EventTarget contract is that capability's shape.

**Modeling.** [Modeling → Modeling State Change as Events, Not Destructive Updates](../../../docs/modeling.md#modeling-state-change-as-events-not-destructive-updates) is the modelling discipline an Event's declaration serves.

**Abstraction.** Abstraction → Abstraction Realization (Implicit Satisfaction) (`docs/khayyam/abstraction.md#abstraction-realization-implicit-satisfaction`), Abstraction → Dispatch Strategy (`docs/khayyam/abstraction.md#dispatch-strategy`), and Abstraction → Behavior Over Type Identity (`docs/khayyam/abstraction.md#behavior-over-type-identity`) are why a target composes the capability rather than narrowing a second copy of it, why what arrives is settled at the call, and why no declaration here states that it implements anything.

**Concurrency.** Whether a dispatch is delivered to a listener concurrently with, or after, the work that produced the occurrence is the dispatch mechanism's to state; this protocol places no ordering requirement between them, because [Process → Ordering](../../../docs/process.md#ordering) is a property of a process rather than of an occurrence.
