# Error Rule — Disregarded Error
Error's rules live one rule per folder under [`modules/process/error/rules/`](../README.md), and this is the Rule for a failure that the process meeting it may not disregard. It is a governance rule of this repository, held for [The Error](../../error.md), whose document owns the subject: it states at `:130` that an error is a contract addressed to the immediate caller whose sole purpose is to let that caller make a correct decision about what to do next, and at `:88` which class of failure a method carries. [Control Flow → Error Propagation](../../../control-flow/control-flow.md#error-propagation) at `:141` and `:143` states the same requirement from the execution side — every fallible operation exposes its error path as an ordinary, named part of the call contract — and `:139` is explicit that what an error *is* is not that document's subject. What the contract must contain is therefore stated upstream, in the document that owns it, and the form that carries it is the realization's — which is why this is a rule of this repository and not a sentence in [`modules/computer/khayyam/`](../../../../../modules/computer/khayyam/khayyam.md), per [Khayyam → Minimal Legislation](../../../../../modules/computer/khayyam/khayyam.md#minimal-legislation-a-principle) at `:177`. What this Rule adds is the refusal of the one way of reporting a failure that leaves the call contract with nothing in it.

## The rule
- **What triggers it.** An operation that can fail: an input that is legitimate for it may still leave it unable to produce what it was asked for. The judgment is the author's, made per method, and this Rule does not define it further. An operation that cannot fail is not touched by this Rule and gains nothing from it.
- **What it requires.** That the failure be **accounted for where the operation can see it** — inside the call the operation was made through, so that the code which performs the call is the code that learns what happened. That is the whole of the requirement, and it is deliberately stated at that height: a variable of an error type in the influenced group, a result type, or another explicit mechanism the realization already provides are equally conformant, and a designer who reports a failure some other legitimate way is writing a correct program. How a failure is carried is out of this Rule's scope by design, and the reason is given under [What this rule does not claim](#what-this-rule-does-not-claim).
- **What it refuses.** **Disregarding a failure.** That is proceeding as though it had not occurred, and reporting it by a signal that reaches past the point where it could have been handled — an announcement the signature does not state, of which a halt is the ordinary case. The caller has nothing to catch, and the reader of the call site has nothing to read: `x.Save(path)` looks the same whether `Save` can fail or not. Where the signature itself states a path for the failure and the body reaches past it anyway, that is this case with the path already drawn.
- **What it leaves alone.** Halting as a mechanism is not this Rule's subject, and halting has a Rule of its own in the flow-control module — [halt declaration](../../../control-flow/rules/halt-declaration/halt-declaration.md) — which says where a halt is written rather than what this one must not reach for. The objection here is to reaching for a signal where the failure could have been accounted for, not to halting; whether a halt may exist at all, and what class it carries, is a separate question that [Control Flow → Error Propagation](../../../control-flow/control-flow.md#error-propagation) at `:144` treats halt operations as explicit and legitimate, and which the same document registers as a topic to be developed there at `:152`. Which class a failure is, is likewise not this Rule's.

## Why it exists
A failure reported out of band adds magic in one specific way: the information exists nowhere a reader looks. [The Error → The two audiences, stated directly](../../error.md#the-two-audiences-stated-directly) at `:130` says what an error is for — a contract addressed to the immediate caller, whose sole purpose is to let that caller decide what to do next. A caller told through an announcement has to know the announcement exists before it can obey it, and nothing in the source it read tells it.

A contract addressed to the immediate caller is also what distinguishes an error from the two things it is easily confused with. The forensic record an operator reads is a Log event, and the defect in the author's reasoning is neither of them: an `Error` is an informational entity the system holds and reports, a named expected member of a method's contract, and it is found by being declared rather than by being investigated. A failure reported out of band borrows the one property those two have — that the reader must go looking for it — and keeps none of the contract that made it addressable. That is why this is a rule rather than a discovery: the contract is already stated upstream, and the refusal is of the one form that leaves it empty.

## Keep it or drop it
An organization may keep the Rule, state the form it prefers for carrying a failure, or drop it. Nothing in this repository's toolchain depends on it: the frontend reads a method's influenced group as a list of type references whatever is in it, so a signature that gains or loses an error-typed variable is a source change and not a compiler change.

What an organization does not get by dropping it is the check that a failure has been accounted for where the operation could see it. That half is mechanically visible in one case only, and a tool must say which case it means: a body that signals a failure where its own signature already states a path for one. The comparison a tool makes is between the body's signalling and the contract the signature states, never between the body and a variable this Rule does not require — which is why the check survives the Rule's refusal to prescribe a form, and why it is weaker than a check over a required slot would have been. The other half is not visible to any tool today, because nothing states which operations are fallible.

## What this rule does not claim
- **It does not prescribe how a failure is carried.** No variable, no name, no position in a group, no type, and no requirement that such a variable exist at all. An author may carry a failure in an influenced variable, in a result type, in a form another realization's language provides, or in whatever way the call contract already states one; every one of these is conformant, and a second realization may answer differently without either being wrong. Requiring a named slot is precisely the obligation this Rule declines, because it forces one shape on every declaration and so blocks a designer whose design reports failure some other legitimate way; the earlier framing that did require it, and what it would have foreclosed, are recorded in the paired handoff.
- **It does not rule out `panic`, halting, or any other mechanism as a thing a program may do.** It rules against reporting a failure through a signal that reaches past the point where it could have been accounted for. Whether a halt may exist at all, where one is written, and what class it carries are the [halt declaration Rule](../../../control-flow/rules/halt-declaration/halt-declaration.md)'s subject and [Control Flow → Topics to be developed here](../../../control-flow/control-flow.md#topics-to-be-developed-here)'s open question, and neither is settled here.
- **It does not say which class of failure is carried.** [The Error → Multi-cause returns](../../error.md#multi-cause-returns) at `:88` owns that: one possible cause returns the concrete type, several return the abstraction.
- **It does not oblige an operation that cannot fail of anything.** It does not ask such an operation to declare the absence of a failure, and it does not read a signature that carries nothing as a defect — the operation's own contract says what it can do, and a signature that states nothing about failing is a signature whose fallibility nobody has claimed.
- **It does not say how a caller reads a value the call did not write.** [Khayyam → Variable](../../../../../modules/computer/khayyam/khayyam.md#variable) sends absence to the type's contract and [The Error → ADT composition](../../error.md#adt-composition--the-full-adt-family-at-the-canonical-level) carries the family; what `IsNull` and `IsEmpty` mean for such a value is open in that document's handoff, and this Rule does not close it.
- **It does not claim the language requires any of it, and it does not claim a second toolchain must.** [Khayyam → Minimal Legislation](../../../../../modules/computer/khayyam/khayyam.md#minimal-legislation-a-principle) at `:177` puts the condition in the tool that applies it, and [Khayyam → The Grammar Refuses Protocol Semantics](../../../../../modules/computer/khayyam/khayyam.md#the-grammar-refuses-protocol-semantics) at `:170` says the need is met instead "through the language's generic mechanisms … ordinary values and explicit outputs".
- **It does not claim anything about what any body of Khayyam source does.** No declaration, count, or distribution in this repository's sources is evidence for or against this Rule, and none is cited here; the sources' standing as residue of an attempt that failed is the owner's, and a rule's justification rests on the documents that own its subject.
