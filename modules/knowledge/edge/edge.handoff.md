# Edge Handoff

## Topic & Purpose

State of converting the edge domain's own protocol — `modules/knowledge/edge/protocol/` — from Go to Khayyam under the seven governing rules in `____Chats/2026-09-23-go-khayyam-migration-map.md`: what `EdgeModel` is required to be, which of those requirements were judgment calls, what the identifier collapse means for the rest of the tree, and what is still undecided — including the question of whether this domain belongs where it sits.

## Status

Active — `protocol/dt-uuid.kh` and `protocol/model.kh` are converted and return `accept` from the Khayyam frontend against a root where both import roots resolve. Nothing in this domain refuses. This unblocks the `edge_p.Model` requirement that `modules/knowledge/label/` had to drop, and that `label/edges/table` and `taxon/edges/{gender,sexuality}` are downstream of.

The three folders under [`edges/`](edges) — `edge/`, `loop_edge/`, `preference/` — carry a document and a one-line `README.md` and nothing else; their Go was comment-only and was removed in Phase 0. They are **not** this domain and were not touched.

## Decisions

- **Decided: `EdgeModel` composes `ThingModel` and `Field_EdgeID`, so it is not an empty extension point.** The Go `Model` was `interface { thing_p.Model }` — empty — and rule 6 forbids translating an empty Go interface into an empty `ab`. The domain's own documents give the requirement to add: [`edge.md`](edges/edge/edge.md) says an edge connects two nodes, or one node to itself, and MAY hold data, so an edge is a stored record reached by its own identity, and `Field_EdgeID` is this domain's surface for exactly that. Composing it makes the second file of this protocol load-bearing — without it `dt-uuid.kh` would be a pair of surfaces no model in the tree requires — and it gives `LoopEdgeModel` and `PreferenceModel` a parent with real requirements.
- **Decided: no `EdgeUUID` is declared.** The Go `type UUID thing_p.UUID` restates the identifier `thing/protocol/dt-uuid.kh` already owns and states "MUST be unique ID in all domains". A second value abstraction over the same identifier is two abstractions claiming one concept, which rule 3 names as the architecture error. `time`, `uri`, `text`, `calendar`, `label` and `language-human` took this route; this domain joins them. Every `edge_p.UUID` in the tree — there are no external use sites today — would spell `ThingUUID`.
- **Decided: `Array_ThingUUID` is imported from the thing domain, not declared again.** The thing pilot already declares it, composing memar's `Array_Dynamic`. `label/protocol/dt-uuid.kh` declares its own copy of the same name over the same concept, which the qualified-names rule classes as "one concept declared twice" — its answer is one declaration the other module includes. This domain imports rather than making a third copy. **That duplicate in `label/protocol/dt-uuid.kh` should be removed by whoever owns the label domain; this domain did not touch it.** Note that the M1 frontend does **not** report the collision: a probe importing `Array_ThingUUID` from thing while also importing label's `dt-uuid.kh` returns `accept`. It is a governance finding, not a grammar one.
- **Decided: the singular surface keeps the Go name; the plural takes `…IDs`.** The Go already said `Field_EdgeID` / `EdgeID()`, not `…UUID`, so the in-flight `…ID` versus `…UUID` sweep has nothing to settle here and the name is carried over as written. The Go's plural was `Field_EdgesID` / `EdgesID()`; the accessor becomes `EdgesIDs`, matching `ThingsIDs` and `LabelsIDs` — the plural on the noun, `ID` last. The repository-wide sweep is still pending and is not started in this domain.
- **Decided: result parameter names follow the derived initial.** `EdgeID` returns `(t ThingUUID)` and `EdgesIDs` returns `(a Array_ThingUUID)` — the type's own first letter, lower-cased, which is what the result-parameter-names rule derives. `label/protocol/dt-uuid.kh` writes `(t ThingUUID)` for the same type and `(i Array_ThingUUID)` for the array; that divergence is cosmetic and was left alone, since the rule governs names the port generated, not names an author chose.
- **Decided: `model.kh` imports `Field_EdgeID` from this domain's own `dt-uuid.kh`.** Both files are in `protocol/`, so this is the local-directory extension the orphan-extension rule permits, not a cross-domain attachment.
- **Rule 5 extraction:** neither file carried a Go comment, so there was nothing to move out of the source. The statements the conversion settled went into [`edge.md`](edge.md), which did not exist before this pass and now states the identifier collapse and what `EdgeModel` requires. No `//` line was added above the Khayyam.

## Ambiguities Resolved

- **Whether `EdgeID` may differ from `ThingID`.** Both answer `ThingUUID` in the converted files, because an edge is stored as a record and the Go said so. The distinction kept is which question the accessor answers — the record's identity or the relation's — not a different value. If the tree ever needs an edge whose identity is not its record's, that is a second abstraction and a second decision, not a widening of this one.
- **Whether `Field_EdgesID` belongs in this protocol or in the thing/graph domain.** Here, because it names edge identities and the edge domain owns edge identities. It is the plural of `Field_EdgeID`, the pair reads as one family, and moving it would leave `storage/graph/protocol/data_model.kh` (`Edge() label_p.UUID`, `Edges() []label_p.UUID`) spelling the same requirement under a third name.

## Open Questions

- **Rule 6, recorded rather than papered over — what is still missing from `EdgeModel`.** It requires identification and nothing else. An edge is documented as holding data and joining two things, and neither is a requirement anywhere: no abstraction states what the two ends of an edge are or how they are read, no abstraction states what an edge's held data must satisfy, and no lifecycle of creating, retargeting, or removing an edge exists. `edge.md` says an edge MAY hold data, so the data is optional by the document, but the *ends* are not optional by any document and are simply absent. Whoever owns the edge's implementation layer has to write that down before `EdgeModel` can be more than identification.
- **Rule 6, second: `Field_EdgesID` has no consumer at all.** No Go source in the tree composes `edge_p.Field_EdgesID`, and none composes `edge_p.Field_EdgeID`. Both were declared and never used. `Field_EdgeID` is now required by `EdgeModel`, which gives it a reason to exist; `Field_EdgesID` still has none, and a record-level "the edges this thing holds" surface may belong to the thing domain or to `storage/graph` instead.
- **The domain's placement is contested and this conversion does not settle it.** `____Chats/core-vs-pluggable.wave2.md` lists `modules/knowledge/edge` under CONTESTED — "kernel relation type vs misplaced bundle-ish folder". Every other edge in the tree is held by a domain that owns the two nodes it joins; this folder owns none of them, and it is the only domain whose whole content is a relation. Nothing in the protocol layer depends on the answer: `EdgeModel` is the same contract wherever the folder sits, and the qualified name `EdgeModel` is not directory-derived. What the answer changes is every `in "org/modules/knowledge/edge/protocol/….kh"` path in the tree, so it should be decided before Phase 3 rather than during it.
- **The domain's own edges are self-referential, and nothing models that.** [`loop_edge.md`](edges/loop_edge/loop_edge.md) and [`preference.md`](edges/preference/preference.md) both state their Model as `(edge)-[:…]->(---)` — an edge whose *subject* is an edge, not a thing. That is what makes `EdgeModel` worth composing `Field_EdgeID`: whatever holds those edges has to be an edge itself. It is also the one place in the tree where an edge appears on both ends of a relation, and no abstraction in this domain says a relation may take an edge as an end. Whether `EdgeModel` should state that an edge is a valid subject, or whether the relation layer should, is open.
- **Whether `EdgeModel` belongs to the edges at all, or is the graph storage domain's.** `storage/graph/protocol/data_model.kh` is the only place in the tree that actually reads edges (`Edge() label_p.UUID`, `Edges() []label_p.UUID`, `Sides()`), and it reads them as labels, not as `edge_p` values. If edges-as-records live in the graph storage domain, `EdgeModel` may be a duplicate of something that belongs there. The one thing that argues against moving it is that `label` composes `edge_p.Model` and `storage/graph` does not, so today this domain is the one the tree reaches for when it means "this record is a relation".
- **`UserUUID` remains an open fork.** `user/protocol/dt-uuid.kh` declares its own `UserUUID` over the same identifier this domain collapsed. It was left untouched; this domain does not compose it and adds nothing beside it. Any resolution of that fork changes what an organization-shaped `EdgeModel` would say about a user edge.
- **The brief's clue pointer is stale.** `modules/knowledge/edge/edges/relation-content.kh` does not exist in this repository, tracked or on disk; the self-referential edge is `edges/loop_edge/`, and `edges/preference/` is a second one. Recorded so the next agent does not go looking.
- **What an edge is *for*.** Every edge document in the tree says "read graph theory to understand what this is", which is a pointer, not a decision. Nothing states which of the three Memar buckets — ordinary edge, loop-edge, shortcut — the domain's own concept sits in, and `edges/edge/`, `edges/loop_edge/` and `edges/preference/` are all filed under `edges/` while two of the three are loop-edges by the Phase 0 review's own definition. Those folder moves are the unapplied Phase 0 review, not this conversion.

## Assumptions

- **`ThingUUID` and `Array_ThingUUID` are the names the thing domain declares** — stability: Strong. `modules/identity/thing/protocol/dt-uuid.kh` is already converted and declares both.
- **`ThingModel` is the name the thing domain declares** — stability: Strong, same directory.
- **`EdgeModel` is the name this domain's consumers expect** — stability: Strong for this pass. `modules/knowledge/label/label.handoff.md` names it as the required declaration and rule 3 forbids an alias.
- **The `org/` and `memar/` import roots resolve through a manifest that does not exist in this repository** — stability: Strong, and named as the hard gate by rule 7 of the migration map. A plain run against the checkout reports `unresolved-import` everywhere; that is the missing-manifest condition, not a defect in these two files.
- **An edge is a record** — stability: Medium. It is read off the Go (`type UUID thing_p.UUID`, a `Model` embedding `thing_p.Model`) and off `edge.md`'s "MAY hold some data", and `storage/graph` stores edges as records. If edges turn out to be pure graph structure with no record of their own, `Field_EdgeID` in `EdgeModel` is the requirement to withdraw.

1. Add `EdgeModel` to `LabelModel` in `modules/knowledge/label/protocol/model.kh` — one import line and one line in the composition block. That domain's handoff already names this as its step 1, and `label/edges/table` and `taxon/edges/{gender,sexuality}` unblock behind it.
2. Remove the duplicate `Array_ThingUUID` from `modules/knowledge/label/protocol/dt-uuid.kh` and import the thing domain's, as this domain does. Owner: the label domain.
3. Decide the placement question in `core-vs-pluggable.wave2.md` before Phase 3, so the `in` paths are settled once.
4. Decide whether an edge's two ends, and the data an edge MAY hold, are requirements of `EdgeModel` or of the graph storage layer — this is the rule 6 work that would give `EdgeModel` a second requirement.
5. Give `Field_EdgesID` a consumer or move it; as it stands it is the one declaration in this domain with no reason to exist.
6. Apply the Phase 0 review's bucket moves to `edges/loop_edge/` and `edges/preference/` — both are loop-edges by the `(edge)-[:…]` Model line — and rename the folders to the relation (`loop`, `preference`) once the owning-domain name is settled. Out of scope here.
