# Documentation
This document defines what a Facet is, says where the facets in use are specified and how one is added, and carries the cross-cutting conventions that span facets (file naming, documentation language, written surface, results routing, citations, URI). It does not itself specify the structure of any facet — that is each facet's own document's job. One further specification sits beside the facets rather than among them: [Documentation — Comparison](./comparison/comparison.md), which governs a kind of document that belongs to no facet.

## Abstract
Documentation in this project is organized into **Facets** — distinct kinds of documentation content, each with its own governing structure and its own specification document. A facet is defined by the reader's relationship to the content: what the reader is expected to do with it. The facets in use are the specifications in this folder's subfolders, each subfolder named for its facet; listing that folder is how they are found, so that placing a specification there is the whole of registering one. What defines each facet — the reader relationship that makes it distinct — is stated in that facet's own specification and nowhere here, so a facet added later needs nothing written in this document; [Extensibility](#extensibility) says what a new specification must state and how a facet is added. Cross-cutting conventions that apply regardless of facet — how a document's name encodes its category, concept, and facet; the language the written record is kept in; written surface (no blank line between a section title and its body; linear form for load-bearing logic); where a result of each type is recorded; that a fact written in code is written only there, while an illustrative example stays in its document; the one Status vocabulary every document kind draws on; that recording waits for no one's permission while removal is the act that takes care; citation practice, and the direction a citation runs between the layers of the written content; URI form — are defined here as well. The followable writing procedures live in [documentation.practice.md](./documentation.practice.md). These surface rules are about *writing*, not about any one markup protocol. One document kind answers to none of the facets: the comparison essay, governed by [comparison.md](./comparison/comparison.md), whose reader examines a comparative argument and which therefore gets no companion changelog, no handoff, and no status ladder ([Comparison: a document kind outside the facets](#comparison-a-document-kind-outside-the-facets)).
## Introduction

### Motivation
A single documentation structure cannot serve two categorically different reader needs without compromising both. Content meant to be *studied* (specifications, analyses, definitions) demands rich front matter, structured argumentation, citation trails, and contributor attribution. Content meant to be *followed* step by step (procedures, agent instructions, Skill files) demands brevity, imperativeness, and minimal context overhead — every field that is not the procedure itself is pure cost to the agent reading it mid-task. Forcing both kinds of content into one shared schema means either overburdening the procedural content with apparatus it does not need, or under-equipping the analytical content with structure it does. The Facet concept resolves this by acknowledging, upfront, that "documentation" is not one thing — it is a family of related but structurally distinct kinds of content, each deserving its own specification. A third need surfaced after that decision was taken, and each facet's own specification says how it arose; none of them is restated here.

### Methodology
The decision to adopt a facet-based architecture was not made in the abstract. It arose from observing a real problem: the earlier version of this specification (then a single `documentation.md`) attempted to govern both analytical specifications *and* procedural Skill files with the same schema. That produced a concrete tension — the same document's thirteenth revision explicitly moved procedural walkthrough content into a separate Skill file, on the principle that procedural and analytical content are categorically different. The facet concept crystallized that instinct into a named, extensible architectural decision. How each facet itself arrived — what was adopted from an existing convention, what was named from an accumulated practice, and what was designed ahead of accumulation — is stated in that facet's own [Methodology](#methodology), for the same reason this document holds no facet definition.

## Explanation

### Content Rule: No Fabricated or Redundant Provenance
Documentation content must be current truth, not archaeology. Five rules apply to every Explanation- and Practice-facet document (and to pointer files such as directory READMEs that guide readers into those documents):

- **No fabricated information.** Never invent facts, history, usage evidence, or attribution — including plausible-looking reconstruction of things nobody recorded. If something is unknown, it is stated as unknown or omitted, never glossed over with a confident-sounding filler. This project is under active development; presenting a guess as an established fact poisons every downstream decision built on it.
- **Historical notes live in exactly one place.** How a document, a convention, or the documentation method itself came to be — including what an older approach looked like and when it was replaced — belongs in the paired changelog, once. Base documents state current rules and their reasons, without narrating what used to be written where, which revision introduced which sentence, or how a migration was executed. A reader needing that history consults the one home it has; a reader who does not is never taxed by it.
- **No redundant restatement.** When content exists in its authoritative home, other documents link to it instead of repeating it — repetition is where documents go to drift apart. A fact written in code is held to the stricter rule [A Fact in Code Is Written Once](#a-fact-in-code-is-written-once).
- **No derivative inventories.** Do not write a membership list, index, or table that merely mirrors a live collection (a directory's files, a script folder's commands, a set of comparison essays) when that membership is discoverable from the collection itself. Such prose is a cache: the next addition invalidates it and forces a second edit for no new judgment. Point the reader at the authoritative location (list the directory; invoke the tool's `--help`) instead. A list that carries *selection judgment* absent from the source (why these few of many matter) is content, not a cache — and must state the selection criterion rather than pretend to be an inventory.

- **Owed or planned capability is marked in all three places.** Where material describes capability not yet enacted — owed rows, prototypes, planned phases, externally hosted versions — the prose claim, the quiescent default in code, and the pointer at the entry point must agree. A claim implied by one surface and absent from the others is a fabrication in the first sense of this rule. The mark is a line `Owed: <id>` in the document, where `<id>` is an opaque identifier: a lowercase dotted slug of letters, digits, hyphens, and dots, such as `khayyam.js-backend-runs`, never a path, a heading, or a line number, so that moving or rewording anything leaves the mark true. The same identifier is carried in the title of a pending Test (`modules/process/test/test.practice.md#the-cycle`), which is how the claim and the work it waits for are found from each other; an identifier found on one side only is an inconsistency, and a pending Test that passes while the mark remains is a hint that the mark is stale, not an error. Owed capability that no Test can execute is marked by the same `Owed: <id>` line and judged by a reader, with no Test to carry it.
### Facet
A **Facet** is a named category of documentation content, defined by the reader's relationship to it: what the reader is expected to *do* with the content. Each facet has its own governing specification — a separate document that defines what structure, fields, and conventions documents of that facet must follow. What a facet is called and what makes it distinct are stated in its own governing specification, so that a facet added later needs nothing written here; this document states the concept, where each facet in use is specified, and how one is added.

The core observation is that documentation content is not homogeneous: a reader studying a specification to understand a design, a reader following a procedure to accomplish a task, a reader consulting a history to audit changes, a reader reading a record to resume a paused discussion, and a reader examining an inquiry to evaluate it are doing categorically different things, and the structure that serves each best is not the same. Forcing every kind of content into one shared schema means either overburdening the simpler kinds with apparatus they don't need, or under-equipping the richer kinds with structure they do. The Facet concept resolves this by naming each kind upfront and giving it its own governing specification.

### Which facet does a document belong to?
The decision is made by the document's author, guided by the document's *primary purpose*: what its reader is expected to do with it. Those relationships are not enumerated here; each facet's own specification states the one that defines it, and the specifications are the subfolders of this folder, found by listing it. What an author does is compare the document's purpose against each of them. Most documents are unambiguous. When the boundary is unclear — for example, a document that contains both analytical content and a step-by-step procedure — the author should ask which purpose dominates: if the procedure is the document's reason for existing and the analysis exists only to support it, the document is followed to accomplish something (with the analytical portion treated as context-setting within the procedure). If the analysis is the document's reason for existing and a brief procedure is included only as an illustrative example, the document is studied to understand a subject. A document kind whose reader relationship none of those specifications answers is the case [Extensibility](#extensibility) covers, not a document that belongs to no facet.

### Extensibility
The facet system is designed to be extensible without structural upheaval. A facet is added by writing its governing specification — itself an Explanation-facet document — into a subfolder of this one named for the facet, and by nothing else: no entry is added to this document, no section of it grows, and no count of the facets in use is held here for the next addition to falsify. What the new specification must state is what every facet's specification states: the reader relationship that makes it distinct — its own, stated in full in the new document rather than here — the structure the documents of that facet follow, and which values of the shared [Status](#status) vocabulary it draws on. A document type that needs a reader relationship none of the specifications in this folder's subfolders answers is what this section exists for, and adding the facet for it changes the facet concept itself and no existing facet specification.

### Relationship between this document and its facet specifications
This document (`documentation.md`) is the entry point and meta-layer. It defines what a facet is, where each facet in use is specified, and how one is added. It does not itself specify the structure of any facet — that is each facet's own governing document's job, and each of those is an Explanation-facet document, being a specification to be studied rather than a procedure to be followed.

A facet's specification is also the facet's address: a subfolder of this one named for the facet, holding the specification under that same name beside its changelog, handoff and other companions. Listing this folder is therefore how the facets in use, their specifications and their companions are found, and each specification states its own reader relationship and what its documents follow; no table of them is kept here, since one would mirror that listing and be wrong the next time a facet is added.

Every facet's governing specification is an Explanation-facet document while the documents it governs belong to the facet it names: the documents *produced with the help of* `practice.md` (such as a `write-a-document/SKILL.md`) are Practice-facet documents, those produced with the help of `changelog.md` (such as `explanation.changelog.md`) are Changelog-facet documents, and so on for each facet. The governing specifications and the documents they govern belong to different facets by design.

### Comparison: a document kind outside the facets
One more governing document sits beside the facet specifications rather than among them: [Documentation — Comparison](./comparison/comparison.md), which specifies the fair-comparison essay — the method a project follows when it examines a neighbouring project people treat as its substitute. It is an Explanation-facet specification like the facet specifications beside it, but the documents it produces belong to no facet, and that is deliberate: a reader examining a comparative argument is not studying a design, auditing a change, resuming a discussion, or evaluating an inquiry, and forcing the essay into a facet would give it a companion changelog and a status ladder it must not have. A comparison is corrected in place with its reasons stated inside, and whatever it concludes about its own project graduates into the documents that own it.

The consequence for discovery is the one a reader of this document most needs: a comparison is found by listing the folder the project keeps its essays in, never through an index, and the method's own rules are reached by reading that specification rather than by having them restated in each essay.

### Citations
A citation is a structured reference to another document or external source, recording the relationship between this document and the cited work. Citations are currently used in [Changelog-facet](./changelog/changelog.md) entries (in the `Cited` bullet field); they may also appear in other facets that need provenance tracking in the future. The rules below apply wherever a citation appears, regardless of which facet the citing document belongs to.

**Source-selection criteria.** A citation should only be added when the relationship is substantive, not decorative — not a passing or general-sounding mention. When judging whether an external source is worth citing, prefer:
- Peer-reviewed or standards-body sources (published research, IETF/W3C/ISO-style documents) over a vendor's own product documentation, where both are available.
- Structure as a quality signal: a source that shows its reasoning or evidence rather than only asserting a conclusion is more trustworthy than one that reads well but argues nothing — polished prose is not itself evidence of rigor.
- A clear distinction between two different kinds of claims from the same source: a claim about *observable, testable behavior* (e.g. "this software does X under condition Y") is generally reliable regardless of the source's other qualities; a claim about that same source's *own design philosophy or motives* is a self-assessment and should be treated with more skepticism, since the source is not a neutral party about itself.

**Source standing.** Whether a source may be recorded at all is settled before whether it is worth recording, and the two questions are independent. A work whose terms of use or license do not permit the use being made of it — quotation, reproduction, redistribution — is not cited, however sound it is; where permission is unclear, the citation is withheld and the record says the material was observed without naming it. Naming a source can also create an attribution obligation the project has not agreed to, which is a second reason the default is not to record one: an unrecorded observation costs a later reader nothing, while a recorded one the project has no right to record becomes a claim it cannot defend.

Among works that may be recorded, standing decides what a citation may support. A personal site or blog, a social-media or network post, a chat channel, a conference-hallway or corridor remark, a vendor's marketing or "best practices" page, an AI-generated summary of any of these, and a tertiary compilation such as an encyclopedia article carry no standing: none may be cited with `Evidence`, `Depends_on`, or `Extends`, and no proposition in a Memar document rests on one. A tertiary compilation is a pointer toward the primary sources behind it, used to find them, never the support for a claim. Two reasons, either sufficient. Naming a source confers a standing it has not earned, whatever words are borrowed from it — a borrowed sentence carries the borrower's authority, not the author's. And the citation tells the reader that a proposition was reached by that source when the reasoning is Memar's own, which is a claim about provenance this project does not make.

Sources that pass both tests: standards bodies and formal specifications; peer-reviewed work; a published book of record; primary technical documentation of an artifact, for claims about that artifact's observable behavior; and this project's own published record. A vendor's own technical documentation or engineering report of a product it ships is primary documentation of that product: it supports claims about what the product does, what it ships, and what the vendor reports measuring, each measurement stated as the vendor's report and never as a general result. Whatever its standing, a citation supports a claim about what its source itself shows or did and never presents Memar's reasoning as reached by that source: Memar's positions are stated as Memar's, and an outside source that agrees with one is never framed as its origin.

**An origin may be recorded without being cited.** Any source may prompt a question, including one of no standing, and the record of that origin is legitimate: it belongs in a research's record of how the inquiry was conducted ([Research → Methodology](./research/research.md)) or in the paired [handoff](./handoff/handoff.md), because attributing a question is not citing a claim. What an origin of no standing may never do is carry a conclusion. The document that records it states the reasoning in its own words and supports the conclusion from a source that passes both tests — or states that the conclusion is its own reasoning and marks it as its own, per [Cognition → Discourse Norms](../../../docs/cognition.md#discourse-norms-derived-from-this-model).

**Relation vocabulary.** Each citation specifies a `Relation` describing how the cited work relates to the citing document:
- `Reference`: cites for context, no structural dependency.
- `Depends_on`: cannot be implemented or understood without the cited work.
- `Depends_for`: inverse of `Depends_on` — the cited work depends on this document.
- `Extends`: builds on top of the cited work.
- `Extends_by`: inverse of `Extends` — the cited work extends this document.
- `Conflicts`: a real, unresolved tension between this document and the cited work.
- `Superseded`: this document obsoletes the cited work. When a document is superseded, both sides update: the older document's `Status` becomes `Superseded` with a `Superseded_by` entry pointing forward; the newer document adds a `Superseded` entry pointing back.
- `Superseded_by`: the inverse — this document is obsoleted by the cited work.
- `Evidence`: the cited work is what supports a proposition made in this document. Distinct from `Reference` (cited for context only) and `Depends_on` (a structural dependency). Use `Evidence` when the source is the empirical or argumentative basis for a claim, but the claim does not structurally depend on the source existing.

### Citation Direction
Memar's written content has two layers, and a reference runs down them.
0. **The base** — the documents in `docs/` and their companions, `docs/khayyam/` and `docs/comparisons/` among them. They hold Memar's concepts, the framework's own rules, and the language Memar's code is written in: what a type is is defined here ([Type](../../../docs/type.md)), and Khayyam declares one with `tp` ([Khayyam → Type](../../../docs/khayyam/khayyam.md#type)). The language belongs to the base because the modules are written in it and its grammar adopts no module's semantics ([Khayyam → The Grammar Refuses Protocol Semantics](../../../docs/khayyam/khayyam.md#the-grammar-refuses-protocol-semantics)).
1. **The modules** — each module's documents and code together under `modules/`, and the bundles under `bundles/`, which run or aggregate modules.

A document links to a document or file of its own layer or of the base; a link to a higher layer runs against the direction. The direction the base travels in is that a base document refers to a module only as a concept: it names the concept in its own words — the Error module, the Linter — and derives nothing from it, and it names one only where its subject needs it. A base claim that holds without reading any module is what lets a document leave the base, as Documentation does for its module, without the base losing anything it stands on.

**A link is never removed to comply.** Where a text needs a reference, its link stays, whatever the reason given for removing it: a link deleted while the text still leans on the module leaves the reference implicit — still there, and no longer followable or counted. An existing upward link is a debt, repaid when its subject can be restated conceptually and the text upgraded, and a new one may be written where the text needs it. The direction holds for every relative link, not only for a `Cited` entry: a link in prose, in a `Propagates to` line, and in a changelog entry, whose links are repaired as [Links in recorded entries](./changelog/changelog.md#links-in-recorded-entries) says; and for every relation, the inverse ones (`Depends_for`, `Extends_by`) included. A base document's changelog and handoff record work done on files, and may name a module's file by a code span holding its path where the record needs it; so may a comparison essay in `docs/comparisons/`, which sets systems side by side and would lose its readability without their paths. Their links take the same direction.

A module applying a base definition is citing down and needs no exception: a module's declarations are written in Khayyam and take what a type is from the base. A module's document links to the module's own code, which is how it refers to the code it is about ([A Fact in Code Is Written Once](#a-fact-in-code-is-written-once)).

Files outside the two layers — the repository's own README and CONTRIBUTORS, and `.agents/` — are not in the order, and a link to or from one is not judged by it. A folder's README may link anywhere inside its own folder, since pointing into its contents is what it is for ([A README Points](#a-readme-points-content-gets-a-document)); a link out of its folder follows the rule. `memar content check` reports an upward relative link as a warning, apart from its problems: a debt to repay, never a link to delete.

### URI
A URI is a string identifier as defined by [RFC 3986](https://datatracker.ietf.org/doc/html/rfc3986). Two forms are used throughout this project's documentation:
- **Absolute URI**: carries a scheme, e.g. `mailto:omid@geniuses.group`, `https://claude.ai`. Used when the URI must resolve independently of this repository.
- **Relative reference**: a scheme-less reference resolved against a base URI ([RFC 3986, Section 5](https://datatracker.ietf.org/doc/html/rfc3986#section-5)), e.g. `./chat-logs/x.md`. Used for resources local to this repository. This is a first-class, standards-compliant form, not a workaround.

The `file:` scheme ([RFC 8089](https://datatracker.ietf.org/doc/html/rfc8089)) specifically requires an absolute path, which breaks portability across different clones of the same repository; a scheme-less relative reference is used for local paths instead of `file:` for that reason. This rule applies wherever a URI appears — internal hyperlinks, citation entries, contributor identity, examples, and any other reference to a local resource, in any facet.

### File Naming
A name is a [label](../label/label.md) attached to the document, and what a label is and is not is that module's; the rule below is how documents apply it. A file name carries structure, not only an identifier: it states which category a document belongs to, which concept it addresses, and — for a companion record — which facet it follows. Three separators divide that labor, and each carries exactly one kind of boundary; a name is legible when no separator is asked to carry two.

- **Folder, or hyphen (`-`)** — the structural boundary between category and topic. The folder carries it where a category has enough documents to own a directory (`modules/computer/identifier/media-type.md`, `khayyam/variable.md`); the hyphen carries it where documents sit beside one another in one directory (`abstraction-implements.md`, `networking-osi_1-Asb.md`). The left side names the namespace, the right side the subject.
- **Underscore (`_`)** — joins the words of a single conceptual term so the term reads as one unit rather than as separate parts (`immutable_infrastructure.md`, `osi_1`).
- **Dot (`.`)** — separates a companion record's facet key from its base name (`<base>.changelog.md`, `<base>.handoff.md`, `<base>.practice.md`, `<base>.research.<NNN>.md`), which is how the companion pairing is stated instead of inferred.

The distinction is load-bearing: `type-explicit_behavior_ownership.md` says *category* `type`, *term* `Explicit Behavior Ownership`, while a name whose parts all wear the same separator states no boundary at all and leaves the reader to guess where the category stops and the topic starts.

A name is chosen by the criteria that govern the term it encodes — it communicates meaning, preserves conceptual boundaries, avoids implementation-specific vocabulary, and stays stable over time, since a rename changes how the concept is addressed rather than how it is written. The human-readable form of a document's name is its front-matter `Title`, which is the slug's source; see [explanation.md → Title](./explanation/explanation.md#title).

A document that states a model is named after the concept the model is about. A folder holding that document is named for the responsibility whose model it is, and the document takes that same name beside it — `modules/computer/binding/binding.md`, `modules/process/construction/construction.md`, `modules/process/control-flow/control-flow.md` — and every companion record takes the same base name (`binding.handoff.md`). Nothing in such a name carries the kind of document it is: the dot already carries the facet key and the base name already carries the subject, so a general word standing where the subject belongs is the one misplacement this system exists to prevent.

The rule is for addressing, and its purpose is that the smallest mistake in addressing a model — the wrong folder segment, or a path rebuilt from memory — reaches nothing rather than reaching a real document about a different concept. A fixed name removes that safeguard: one file name shared by every model folder leaves a wrong folder segment resolving to a real document, two paths differing only in the segment a mistake gets wrong. A subject name carries the mirror risk instead, that a path mistake lands in a neighbouring folder, and in this repository that is the cheaper of the two costs — a document's kind and its subject are easiest to confuse for the one artifact where they are, 41 of this repository's 115 base documents already carry their own folder's name (a base document being any document that is neither a `README.md` nor a `.handoff.md`, `.changelog.md`, `.practice.md`, or `.research.<NNN>.md` companion, and none under `.agents/`), every one of the 26 folders under `bundles/khayyam/rules/` (`bundles/khayyam/rules/README.md`) does because that catalog states the rule for its own case ("Each rule has its own folder, holding a main document named after the rule"), and two pairs of base documents share a base name across folders (`docs/agency.md` with `docs/khayyam/agency.md`, `docs/modularity.md` with `docs/khayyam/modularity.md`), so a wrong subject path there resolves to no file rather than to a neighbour. The repository states the same rule from the other side under [Folder READMEs](./documentation.practice.md#folder-readmes), which makes a folder's main document the target of that folder's `README.md` — a path a reader types and a tool resolves.

The rule reaches a document that is a folder's main model. It does not reach a model a session leaves beside the documents it read rather than in a folder of its own, which is working state and takes `<base>.handoff.md` as a [Handoff](./handoff/handoff.md); and it does not bind the front-matter `Title`, which stays free to read as the model *of* the concept.

### Documentation Language
The project's written record is kept in English. The reason is the record's audience rather than a preference about which language reads better: documentation is read by agents of every kind — human, IDE, CLI, AI — across sessions, shifts, and projects, and one language is what lets all of them read the same text instead of a version of it. A proposal to change documentation states its replacement text in English, ready to substitute, so accepting a proposal never requires a translation pass. Conversation is outside this rule: it follows whoever is speaking, and the language a discussion happened in is no reason to write the record in it.

### Written surface
Cross-cutting mechanics of how written documentation is laid out — independent of facet and **independent of any particular markup protocol**. Today's files may use Markdown; tomorrow's may not. These rules govern the *writing*, not a syntax. The followable steps live in [documentation.practice.md](./documentation.practice.md).

- **No blank line between a section title and its body.** The body of a section begins on the line immediately after the section title. A blank line after a title falsely signals a paragraph break and detaches the body from the section it belongs to. One blank line *between* successive blocks inside a section (paragraphs, lists, quotations) remains ordinary paragraph separation; that is not the same as a blank line after the title itself.
- **No run of two or more blank lines** anywhere in the document. Double blanks are decorative noise.
- **Load-bearing logic is linear.** Normative rules, decision procedures, and conditionals are written as sentences or numbered steps under section titles. Do not encode norms in grid layouts or diagram blocks that only make sense when rendered as two-dimensional graphics — those forms are hostile to linear readers (including models) when they carry rules. Short non-normative lookup grids remain allowed where no rule lives in cell adjacency. The knowledge-side rationale is [Knowledge → Write for the Structure of the Subject](../knowledge.md#write-for-the-structure-of-the-subject-not-for-todays-reader-limits).
- **Present-state writing when no prior snapshot is available to the reader.** Until a durable prior snapshot of the document exists that the reader can open (a committed revision, a published release, a frozen research), the body states current findings and decisions as present content. Do not narrate "revised," "updated after review," or "formerly said X" when that former text is not available to the reader — that forces them to ask what changed when they cannot see it. Diff and changelog exist for that job once a prior snapshot exists.
- **The body affirms what holds.** A body sentence states the current rule, definition, or claim in the form a reader applies. The wording that was replaced, the label that was dropped, and the alternative that was rejected are changelog content: the outcome in `What changed`, the rejected alternative in `Considered and not done`. A sentence whose job is to warn the reader off a previous formulation — "X is retired," "Y is not the rule," "this document once said Z" — is that changelog content sitting in the body. A reader who loads the body without the changelog, including an AI-assisted reader, treats the negation as a live claim; [Relevance discipline](./explanation/explanation.md#relevance-discipline) names the same hazard for considered-and-not-done. A prior snapshot does not move that sentence into the body: the snapshot changes whether the old text can be opened, and the changelog is still where the removal is recorded.
- **An empty result leaves the medium unchanged.** A report, review, check, or convergence whose result is nothing to report produces no artifact: no empty section, no placeholder heading, no empty changelog entry, no file created to hold a result that is not there. This is the same economy [Trivial changes](./changelog/changelog.md#trivial-changes) applies to a session's edits, carried up from the changelog entry to every artifact a check might write, and it has a second reason beyond tidiness. A loop whose success condition is "nothing was found" needs the nothing to be *observable*, or the party running it cannot tell a completed check from one that has not run and keeps producing work to fill the gap; the observable form of finding nothing is that the shared medium is exactly as it was.

### Results routing
Documentation work constantly produces results, and the type of the result — not the writer's preference — determines where it is recorded. This routing is cross-cutting: its homes span several facets, while each home's structure is defined by that facet's own governing specification, not repeated here.

- **Anticipated results** — what a decision is expected to achieve, stated while writing: the document's own claim, in its [Abstract](./explanation/explanation.md#abstract).
- **Derived results** — consequences that adopting the decision forces, whether or not anyone wants them: the [Implications](./explanation/explanation.md#implications) entry of the Explanation facet's Optional Sections.
- **Observed results** — what real use actually produced: an observation that changed the design belongs to the [Changelog](./changelog/changelog.md) entry that made the change; one that supports a specific claim is cited inline at that claim, as Evidence ([Relevance discipline](./explanation/explanation.md#relevance-discipline)); one that warrants deliberate study is a [Research](./research/research.md) record; one awaiting action is working state in the paired [handoff](./handoff/handoff.md).

An Explanation-facet document carries no `Results` section; the boundary is defined in [explanation.md → Body sections](./explanation/explanation.md#body-sections).

### A Fact in Code Is Written Once
Where a fact is written in code, no other place keeps a copy of it. Code is any text a machine reads: a declaration or a statement in an executable language, and any block a program parses. In Memar that language is Khayyam, its official language ([Framework → Khayyam and Other Languages](../../../docs/framework.md#khayyam-and-other-languages)); code in another language, such as the Python of Memar's scripts today, is held to the same rule. A document names the code, and a help text, a message or a generated listing asks it; neither retypes it. A retyped fact is a derived copy with no re-derivation path ([One Authoritative Location per Concern's Data](../../../docs/modeling.md#one-authoritative-location-per-concerns-data)): a cache of information, which the next change to the code leaves wrong while nothing fails.

Five questions are asked of a fact, in this order:
0. **Presumption.** Everything is code unless shown otherwise, and in Memar that code is Khayyam. A fact is written in code first; the burden of showing that it is not falls on the text, never on the code.
1. Does a program, tool or service read it, compare it, branch on it, or validate against it? Then it is code.
2. Is it a closed set (values, fields, transitions) or a fixed shape? Then it is code; a prose table of a closed set is a copy.
3. Is it stated in two places? Then it is code, once, and every other place refers to it.
4. Must a reader be persuaded, warned or shown why, so that what is written is a reason, a trade-off, a history, an example or an audience and not a fact? Then it is text. Only this answer shows otherwise.

A fact that answers no to every question stays code, by the presumption. A statement that holds both a fact and its reason is split: the fact goes into code, and the reason into text that refers to it.

**Real code lives in its own file; an example is not banned from any text.** Real code is a definition a machine reads and the one source of a fact: what a compiler, a tool or a test takes as the fact itself. It is written in the file of the module whose subject it is, and a document of any layer refers to it and says only what the code cannot: the reason, the trade-off, the audience, and the history its changelog keeps. A document that retypes real code holds a copy no compiler checks, by question 3; and reading the file costs a reader, and the toolchain that carries it into another language, less than a document long enough to restate it. An example is another thing, and two kinds are told apart by who reads them:
- **An illustrative example** is written for a reader, to show how something is used or what it looks like, and no program takes it as the source of anything. It stays in the document it illustrates, in whatever language it is written: a Khayyam snippet, a data format, a diagram, a tree, a sketch, quoted prose, a template.
- **A real example** is one a tool or a test runs or reads. It is code, and lives in a folder of examples where the toolchain reads it — for Khayyam, a folder such as `bundles/khayyam/examples/` — and a document may refer to it.

What makes a fragment real code is that a program takes it as a source, not its tag and not that a program could parse it. An illustrative example that restates a real definition, so that the two can drift apart, is replaced by a pointer to that definition; one that shows what no definition holds stays.

How text refers to code:
- **A help text, a message or a generated listing** calls the methods of the type when it is shown (its name, its summary, its overview), so the words are produced from the one definition and kept nowhere else.
- **A module's document** links to the code or names it by a code span holding its path, and states the concept, the reason and examples in prose. It lists no value, field or transition of the type. **A base document** names the concept the code declares rather than the code, the direction [Citation Direction](#citation-direction) states.
- **A description in a human language** of a code fact belongs to the type's own detail methods, not to a document, and each human language has a file of its own. How those files work is a rule beyond this document and beyond any one language, kept by the organization's own rules; this rule says only that the description is the type's.

Three examples:
- **Status.** The closed set of values, with each value's kinds and safety to depend on, is code (questions 2 and 3): a type with one value per Status. The prose keeps what a writer decides by it and why one vocabulary serves every kind: a report states its Status as its plan does, and an error is never `Complete`.
- **Session records.** A plan and a report are records of a fixed set of fields, so the field names and the Status they carry are declared once as types, and `memar task ensure --help` prints the shape by calling them. A report has no field of its own for how the run ended: that is its Status with the Result part. The prose keeps why a plan and its report agree.
- **Service inputs and outputs.** A service is itself a type, and its inputs and outputs are types, not bare strings: a session id, a project name and a project path are three, and a name is never taken for a path. What each is, is said in the type once; a service's help and a document refer to it by calling it and by naming it.

### Status
Status names where a document, or a piece of work, stands in its life. One vocabulary serves every kind that carries a Status, and its rules and reasons are stated here; each kind's governing specification links to this section and states only what is specific to it: where the Status is written, which of the vocabulary's values it may take, and what moves it.
- A Status is exactly one value of the vocabulary, taken from the values the kind may use. A kind never adds a value of its own; a value a kind needs is added to the type that declares the vocabulary, with the kinds that may use it.
- A Status reports the item's own lifecycle, never informal or practical usage of what it holds.
- Where the Status is written is the kind's own rule: the front-matter `Status` field of an Explanation-facet document ([explanation.md → Status](./explanation/explanation.md#status)), a body section of a handoff or a research (which carry no front matter), and the head of a session's plan and report.
- The shape of a session's plan.md and report.md is stated by `memar task ensure --help`; this section states the rules for the values those files draw on. A session's report states its Status as the plan does and how the run ended is that Status with the report's Result part: a run that ended unmet because its budget ran out or it made no progress leaves the report `Active`, one that stopped at an act needing a human's approval leaves it `Blocked`, and the report's Result part says which. A value used by the report alone would be added to the type with `Session report` as its only kind; none is needed now.
- A session's plan and its report agree when their Statuses are equal; a plan left `Active` beside a report that states `Complete` is the disagreement a reader acts on.
- An error or an exhausted budget is never reported `Complete` ([Acceptance Criteria](../../../docs/agency.md#acceptance-criteria)).
- The vocabulary is a closed set, so it is code and nowhere else ([A Fact in Code Is Written Once](#a-fact-in-code-is-written-once)): `modules/knowledge/documentation/primitive/status.py` declares every value, its meaning, the kinds that may use it and whether it is safe to depend on, and `modules/knowledge/documentation/record.py` declares the shape of a session's plan and report. This section lists none of them; a value is read, added or changed in the type alone. The type is a Python class for now and becomes a Khayyam capsule later; its place under `.agents/scripts` is not settled.

### A README Points; Content Gets a Document
A folder's README orients a reader into the folder: what the folder is for and the criterion its contents meet. It carries no changelog and no handoff, and that is a test as much as a convention: content whose changes matter to someone — a rule, a definition, a decision, a layout other work depends on — needs a history and open questions, which a README cannot hold. When such content is found in a README, that is the signal to make it a document of its own (or move it into the document that owns its subject) and leave the README pointing at it. A rule kept in a README is also a rule the agents it binds rarely read, since they open the documents their work governs, not the folder's front page.

The converse holds for documents: one that has no changelog yet may be given one by any agent that changes it; nothing reserves its creation to the document's author.

### Recording Is Not Gated; Removal Is
Nothing the work learns goes unrecorded. A rule, an open question, a finding, or a note the work produced is written into the document that owns its subject when the work reaches it, and writing it waits for no one's permission — not a counterpart's, not an owner's, not a reviewer's — because a record held back for permission is a finding the next session cannot see. Open questions above all are recorded along the path of reasoning, at the moment they arise, in the open questions of the owning document's handoff, not collected for the end of the work, where the reasoning that raised them is no longer at hand; an ambiguity set aside is recorded as [Ask rather than assume](../../../docs/cognition.md#ask-rather-than-assume) says. An addition is still a claim under the owning document's rules: it is placed by [Results routing](#results-routing) and marked unratified where it decides nothing, and what is judged is its placement and its content, not whether it was permitted.

Removal is the act that loses information, and it is the one that takes care. Text is not deleted, shortened, or rewritten away because it seems superseded, redundant, or out of place: what it said is moved to the home it belongs in, or kept beside what replaces it, or its removal is recorded in the changelog entry that made it with the removed content stated, so that nothing it carried is lost. A removal that reaches beyond the instance under discussion is proposed before it is applied ([Confirm before large-scope changes](../../../docs/cognition.md#confirm-before-large-scope-changes)).
