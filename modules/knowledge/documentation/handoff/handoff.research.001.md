## Question and Goals
- **Question 1:** Should Memar identify a working session, so that every artifact it produces is traceable to it and a later session can resume from the repository alone? — **Answered**
- **Question 2:** If so, is a Unix-epoch timestamp at minute or nanosecond granularity a sound identifier? — **Answered**
- **Goal 1:** settle session identity on a defensible basis, consulting the standards and the published record rather than the nearest convenient scheme — **Met**
- **Scope:** what may identify a working session, and where that identity is recorded. Excludes the content of any feature pipeline, task-tracking tooling, estimation and scheduling, and any change to how a tool resolves the repository it reads. This is the half of [Process Research 001](../../../process/process.research.001.md) that concerns the record rather than the concept: a session is an exchange between cognitive systems, and what outlives it here is a Handoff, so the question belongs to the facet that owns the record and not to the one that owns the concept.

## Methodology
A pass over the primary sources on 2026-10-04: RFC 9562 (UUID versions 1, 6, 7, 8 and §6 on distributed generation), the ULID specification, the KSUID README, the W3C Trace Context recommendation, Anthropic's published context-engineering article, the Claude Code session and architecture documentation, LangGraph's checkpointer and persistence documentation, tmux(1), `git interpret-trailers`(1), the Conventional Commits specification, GitHub's issue-linking documentation, the Twelve-Factor App's disposability section, and the specification project's own PowerShell sources. GitHub Spec Kit's sources were read directly.

## Findings
### Answering Question 1: a session is retrievable, not a concept
**A Memar session already exists as a thing, and it is the handoff set.** [Handoff → Reader relationship](./handoff.md#reader-relationship) defines the Handoff facet as a companion record "carrying a discussion's current state across a session boundary — decisions with their confidence, resolved ambiguities, open questions, assumptions, and proposed next steps". A session that ends mid-thought leaves exactly that. What is missing is not the record and not the practice; it is the **address**.

**The gap the owner described is real and is not the one the artifact set was invented for.** A session that hits a context limit and is continued by a different model must find the previous session's state from the repository, not from the losing session's context. [Cognition → Declare unverified reading and context limits](../../../../docs/cognition.md#what-implementation-asymmetry-obliges) already makes a participant say when prior context may have been lost, and [Cognition → What Implementation Asymmetry Obliges](../../../../docs/cognition.md#what-implementation-asymmetry-obliges) makes externalizing session state an obligation — but neither says *where to look*, so the obligation is discharged by writing into whichever handoff is at hand and the next session reads whichever handoff it finds first (Space Bunny Alpha — argued).

**The published record says the same thing, from the other direction, and its two halves carry different weight.** Anthropic's context-engineering article names structured note-taking as one of three techniques for long-horizon work and states the survivability claim plainly: "After context resets, the agent reads its own notes and continues multi-hour training sequences" ([anthropic.com](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents) — **Reference**: a vendor's own account of a technique it shipped, admitted as the claim being weighed and not as support, per [Documentation → Citations → Source standing](../documentation.md#citations)). The mechanism they shipped is a file-based memory tool, and the stated benefit is that it lets an agent "maintain project state across sessions, and reference previous work without keeping everything in context". What this finding rests on is the other half: Claude Code's own documentation states the failure this research addresses: "**Sessions are independent.** Each new session starts with a fresh context window, without the conversation history from previous sessions" ([docs](https://docs.claude.com/en/docs/claude-code/how-claude-code-works) — **Evidence**), and separately that "instructions from early in the conversation can get lost. Put persistent rules in `CLAUDE.md`".

**What must not survive, and why a scratch directory is the wrong answer.** Claude Code's durable artifact is a plaintext transcript under `~/.claude/projects/`, one file per session ID, with a 30-day default retention — and its documentation states flatly that "The entry format is internal to Claude Code and changes between versions, so scripts that parse these files directly can break on any release" ([sessions](https://code.claude.com/docs/en/sessions) — **Evidence**). A resume path that depends on a vendor's private format, or on a directory the operating system is entitled to empty, is not a resume path. The Twelve-Factor App's disposability section states the condition under which ephemeral state is acceptable at all: "Implicit in this model is that all jobs are reentrant, which typically is achieved by wrapping the results in a transaction, or making the operation idempotent" ([12factor.net](https://12factor.net/disposability) — **Evidence**). A session's decisions are neither reentrant nor idempotent, so the condition does not hold and the state must be written where the repository keeps it.

**The strongest single piece of prior art is the project this repository already compared itself against.** GitHub Spec Kit keeps its current-feature pointer in `.specify/feature.json`, a single mutable slot holding `{"feature_directory": "..."}` and nothing else, and it has had to defend that slot twice by issue number: its own PowerShell sources document `-NoPersist` because "pure path resolution never writes .specify/feature.json, **which would dirty the working tree**", and `SPECIFY_FEATURE_NO_PERSIST` "letting an orchestrator (multi-agent runner, CI matrix) guarantee that no script invocation in the process tree writes" it ([common.ps1](https://raw.githubusercontent.com/github/spec-kit/main/scripts/powershell/common.ps1) — **Evidence**). A framework whose session pointer is a mutable file inside the working tree spends two issues and two environment variables keeping its own state out of version control. Memar's answer must not be that shape (Space Bunny Alpha — argued).

**Therefore: a session is identified, not modeled.** It is a retrieval label over records Memar already keeps, and the only new thing is a field. It is not a Process, not a facet, and not a document — [Documentation → Extensibility](../documentation.md) makes a new facet a deliberate act, and nothing here needs one.

### Answering Question 2: a timestamp is not an identifier, and no granularity makes it one
**A bare Unix-epoch timestamp guarantees uniqueness at no granularity, on one machine or many.** The reason is stated in one sentence of RFC 9562 §6.1: "system clocks themselves have an underlying granularity, which is frequently less than the precision offered by the operating system" ([RFC 9562](https://www.rfc-editor.org/rfc/rfc9562.html) — **Evidence**). A nineteen-digit field therefore carries a value that may be constant across a far wider real interval than one nanosecond, and the width of the integer says nothing about the resolution of the reading in it.

**Within one machine, across concurrent processes, nothing coordinates the two readings.** RFC 9562 §6.4 names the only two ways to make time-based identifiers safe across hosts — an embedded node identifier, or a central registry, which it then rules out: "Shared knowledge schemes with central/global registries are outside the scope of this specification and are NOT RECOMMENDED" — and closes with the sentence a design must answer to: "**Distributed applications generating UUIDs at a variety of hosts MUST be willing to rely on the random number source at all hosts.**" Across machines the position is worse, because the clocks are independent and RFC 9562 §6.1 names backwards movement as a live case: "if it is possible for the system clock to move backward due to either manual adjustment or corrections from a time synchronization protocol, implementations need to determine how to handle such cases" (all **Evidence**: RFC 9562).

**Every scheme that is an identifier keeps the timestamp as a prefix and appends something that is not time.** ULID is 48 bits of Unix milliseconds plus 80 bits "Cryptographically secure source of randomness", and its specification's own guarantee is deliberately weak: "Within the same millisecond, sort order is not guaranteed" — monotonicity is an opt-in factory whose guarantee is scoped to that factory's state and which hard-fails past roughly 280 ULIDs in one millisecond ([ulid/spec](https://github.com/ulid/spec) — **Evidence**). KSUID is a 32-bit timestamp plus 128 random bits, and concedes the timestamp is not an invariant: "This is not a strong guarantee (an invariant) as it depends on wall clocks" ([segmentio/ksuid](https://github.com/segmentio/ksuid) — **Evidence**). UUIDv7 is 48 bits of Unix milliseconds plus 74, and RFC 9562's guidance is probabilistic rather than absolute: using extra clock precision "provides values that are **more likely to be** unique", which is why it caps the sub-millisecond fraction at 12 bits (§5.7, §6.2 — **Evidence**). UUIDv1 and v6 carry a 14-bit clock sequence and a node field precisely because a timestamp alone is insufficient (§5.1 — **Evidence**).

**The most mature traceability standard chose randomness over a timestamp for the top-level identity.** W3C Trace Context states that "The value of trace-id SHOULD be globally unique… global uniqueness of trace-id is important, even when local uniqueness might seem like a good solution", and that a "**Randomly generated value of trace-id SHOULD be preferred over other algorithms of generating a globally unique identifiers**" ([W3C Trace Context](https://www.w3.org/TR/trace-context/) §§8.1, 8.2 — **Evidence**). Where one span cannot parent another, OpenTelemetry does not widen the identifier; it adds a side-channel: "In response to some of these operations, an additional operation is queued to be executed, but its execution is asynchronous… We cannot predict when the subsequent operations will start. We need to associate these two traces, so we will use a span link" ([opentelemetry.io](https://opentelemetry.io/docs/concepts/signals/traces/) — **Evidence**).

**Two systems that do keep a timestamp do not use it as the identity.** LangGraph's `checkpoint_id` is a ULID, chosen for ordering — "Because `checkpoint_id` is a ULID, it sorts lexicographically — larger values are newer" — while `thread_id`, the key a caller looks work up by, is an arbitrary caller-supplied string whose documented examples are `"1"` and `"thread-1"` ([docs](https://docs.langchain.com/oss/python/langgraph/checkpointers) — **Evidence**). Spec Kit itself uses a monotonic counter scanned from the directory tree for machine-managed units, a human-supplied slug for human-managed ones, and a date only as documentation — `**Created**: [DATE]` on the spec template — and has never used a timestamp as an identity ([create-new-feature.ps1](https://raw.githubusercontent.com/github/spec-kit/main/scripts/powershell/create-new-feature.ps1) — **Evidence**).

**The conclusion, and it is the answer to Question 5: the timestamp may be the *sort key*, never the *name*.** What a session identifier buys is retrieval, ordering, and a legible creation instant. Ordering and legibility come from the timestamp. Uniqueness — the third requirement, and the one that makes two same-instant sessions distinguishable — comes from somewhere else, and every scheme surveyed gets it from randomness or from a node identity. A design that wants a legible, sortable session label and provable uniqueness must therefore be two fields, and the second field may be short (Space Bunny Alpha — argued).

**What Memar's existing identifier already teaches here.** [Documentation Explanation → ID](../explanation/explanation.md) mints an Explanation document's `ID` from `unix seconds / 3600` and states precisely what it is and is not: "A UTC unix-time-derived integer, generated once when the file is first drafted, never reused or reassigned. It carries no meaning beyond relative creation order — generating it does not imply approval; that is `Status`'s job." An hourly counter that two drafts in the same hour would share is acceptable *there* precisely because uniqueness is not what that field is for — a filename is the identity there. Applying the same reasoning to a session is the error: a session's identity **is** its name, so the collision case is the one that matters (Space Bunny Alpha — argued).

**A resolution that satisfies all three requirements, and is narrower than expected.** A session label of the form `<unixtime-nanoseconds>-<short-random>` is legible, sorts by creation, and cannot collide with another session on this machine or another. But the owner may reasonably want less: for sessions that are minutes to hours long, a **minute-resolution timestamp plus a two-character suffix** is enough, and the suffix is short enough to type. The decision belongs to the owner; what this research settles is that the timestamp alone is not available as an answer, and by what it would have to be replaced.

### What the identifier must not become
**Traceability by convention is documented to be unreliable, and the documentation is the argument.** `git interpret-trailers` specifies the trailer block, and Conventional Commits builds its `Refs:` examples on it ([git-scm](https://git-scm.com/docs/git-interpret-trailers), [spec](https://raw.githubusercontent.com/conventional-commits/conventionalcommits.org/master/content/v1.0.0/index.md) — **Evidence**) — but Conventional Commits also treats the whole convention as advisory: "if a commit lands that does not meet the Conventional Commits specification… that commit will be missed by tools that are based on the spec". GitHub's own documentation records three concessions in the same page: keyword links "are interpreted only when the pull request targets the repository's *default* branch. If the pull request targets *any other branch*, then these keywords are ignored, no links are created"; keyword-derived links cannot be unlinked through the interface, "you must edit the pull request description to remove the keyword"; and a commit-message keyword closes the issue while leaving the pull request unlisted as a linked one ([docs](https://docs.github.com/en/issues/tracking-your-work-with-issues/using-issues/linking-a-pull-request-to-an-issue) — **Evidence**). A framework that depends on a person remembering to type a keyword into a commit message has, by the platform's own documentation, an incomplete and partly unmaintainable link set (Space Bunny Alpha — argued).

**So the session label belongs in the artifact's own front matter, where the facet already requires a field.** Every Memar companion already carries structured metadata a tool can read — a Handoff's open questions and anticipated work, a Changelog entry's `Propagates to` states — and `memar-documentation.py` already parses front matter and reads fields by name. A session field in the front matter of the artifacts a session produces is machine-readable without any new convention, is not gitignored, and is inside the artifact rather than beside it. The multi-handoff problem the owner raised is answered by the field rather than by a directory: one session id, repeated in each handoff that session produced, and a search across the doc set finds all of them (Space Bunny Alpha — argued).

**What this research does not decide.** Whether a session id appears in *every* artifact or only in handoffs and researches; whether it is one field or a small block; whether a continuation session gets a new id or reuses the previous one with a new `Continues` line; and the exact width of the random component. Each is a small decision with a defensible answer either way, and none of them changes the finding above (Space Bunny Alpha — raised).

## Open Questions
- **Should the field be required on every artifact or only on handoffs and researches?** Requiring it everywhere makes the search total; requiring it only where state crosses a boundary keeps front matter light and makes a query return a subset by design.
- **Does a continuation session take a new label?** A new label with a `Continues:` line keeps each session's own artifacts separable, at the cost of a reader having to follow a chain; reusing the label makes the whole development one unit, at the cost that no artifact says which session wrote it.
- **What width should the non-temporal component have?** Nanosecond timestamp plus a short random suffix is the shape; how short is the owner's call, and the tradeoff is legibility against a guarantee that is probabilistic rather than absolute.

## Notes
This research was split out of [Process Research 001](../../../process/process.research.001.md) after its first two questions were answered. A research is paired to the base artifact whose subject it is, and the two halves of the original inquiry did not share one: decomposition is a question about the Process concept, while identifying a session is a question about the record that survives one. Keeping both under `process.md` would have made a concept document answer for a records mechanism it does not own.

The original proposal → a Unix-epoch timestamp at finer granularity than Memar's hourly document `ID` → is answered by the standards rather than adopted. A timestamp is a sort key and never a name: clock resolution is independent of the field's width, nothing coordinates two concurrent processes or two machines reading the clock at once, and every scheme surveyed appends a non-temporal component for exactly that reason. What survives the proposal is the part that was right, because it sorts and because it is legible.
