# Protocol Rule — A Protocol Is Written in a `protocol/` Folder
The owner's ruling of 2026-10-31, while designing the title module, clarified 2026-11-06 for service Request/Response, realization naming, and the test that keeps service contracts out of a module's main `protocol/`. It is the rule for where an abstraction is written, held for every module of every project built with Memar, and it applies [Protocol](../../protocol.md) to the file system: an abstraction is the code-level form of a protocol, and a protocol has one place to be read.

## The rule
- **Every abstraction is written in a `protocol/` folder.** No abstraction stands in a module's root, in `primitive/`, in `errors/`, or in a service's or widget's folder beside its realization. What realizes an abstraction stands elsewhere; what states it stands in `protocol/`.
- **The module's main `protocol/` holds what the module as a whole states.** It is the one folder a reader opens to learn what the module requires, and it stays small: it holds the concepts of the module and nothing that belongs to a single service or widget.
- **Each service and each widget has a `protocol/` folder of its own** (`services/<name>/protocol/`, `widgets/<name>/protocol/`), holding the abstractions of that service or widget: what it takes and what it gives back — including that service's separate **Request** and **Response** abstractions, as [Service Contract](../../../../process/service/rules/service-contract.md#the-rule) requires. The main `protocol/` does not repeat them. [Title](../../../../../modules-plugable/uri/title/title.md) is the applied example for service-local protocol/.
- **A `protocol/` folder is one protocol surface of its owner, however many files it holds.** A service's `protocol/` is its owner's, not a second protocol of the module, and no `protocol/` stands inside another `protocol/`.
- **A `.kh` file in `protocol/` is named for the concept it states, with no `dt-` prefix.** The kind of a thing is a label it takes, never a prefix of its file name ([Label Rule → A Folder Is a Label](../../../label/rules/folder-label/folder-label.md)). Request and Response files are named `request.kh` and `response.kh` under that service's `protocol/` (the folder already names the service).
- **Realization does not live in `protocol/`.** A capsule or other language unit that satisfies an abstraction of a service or widget sits in that service's or widget's folder **beside** `protocol/` (the service/widget root). It does not sit in the parent `services/` or `widgets/` root when that service or widget folder exists. The example that was wrong: `modules/management/timeline/services/timeline-place/timeline_place.py` beside `services/timeline-place/`. It never shares a file with the abstraction it satisfies: an abstraction file holds no method body ([Khayyam → What You Cannot Do](../../../../../modules/computer/khayyam/abstraction/abstraction.md#what-you-cannot-do)).
- **The realization file is named for the same concept as the abstraction file it satisfies, without a marker that restates "realization".** Example: abstraction `services/query-text-index/protocol/query-text-index.kh`; realization `services/query-text-index/query-text-index.kh` or `services/query-text-index/query-text-index.py`. The **folder** (`protocol/` vs its parent) is what distinguishes contract from realization — the same form [Test Naming](../../../../process/test/rules/test-naming/test-naming.md) uses so a Test needs no `test_` marker. A Request or Response realization, when separate from the service capsule, is likewise `request.<ext>` / `response.<ext>` beside `protocol/`, matching the base names in `protocol/`.
- **A capsule's type name is not the abstraction type's name.** Satisfaction needs no `implements` keyword ([Khayyam → Satisfying an Abstraction](../../../../../modules/computer/khayyam/abstraction/abstraction.md#satisfying-an-abstraction)), but two declarations of the same type name cannot share a module; the capsule chooses a distinct type name that states the bind or the realization (for example an in-memory bind), never reuses `Text_Index_Query_Request` as the capsule's own type name.
- **The label `protocol` is independent of the other kinds a content has.** One content may carry the label `protocol`, be a widget, and be a member of a module at once: the kinds combine and do not nest ([Label Rule → A Folder Is a Label](../../../label/rules/folder-label/folder-label.md#the-rule)).

## Placement test (refuse the main folder)
Before writing any `.kh` under a module's **main** `protocol/`, answer these. A **yes** to any means the file belongs under `services/<name>/protocol/` or `widgets/<name>/protocol/`, not in the main folder — create the service or widget folder if it does not exist yet.

1. **Does the type extend `Service` or compose as a widget?** → service/widget `protocol/`. Becoming a service is a **move into** `services/<name>/protocol/`, never a reason to keep the type in the main folder.
2. **Is the type that service's Request, Response, or the named service/widget abstraction itself?** → that owner's `protocol/`.
3. **Is the type a Hit, Hits, Field bag, or other return/value surface produced or consumed only by one service or widget?** → that owner's `protocol/` (example that was wrong: `Text_Find_Hits` in the retrieval module's main `protocol/` instead of under `widgets/text-find-holders/protocol/`). Shared filter values used by several services (for example field preds) may stay in the main folder.
4. **Would only one service (or one widget) import this type if the module were split?** A port, lock, or stamp taken only by one service belongs beside that service. A codec several services share may stay in the main `protocol/`. A repository may not: see the next test that refuses it.
5. **Are you writing it in the main folder "for now" because the service folder is not ready?** → refuse. Create `services/<name>/protocol/` first; the main folder is not a staging area.
6. **Is the type a store, a repository, or any face whose methods are the domain's own add, read, remove, rank, or find?** → refuse it in the main folder and beside the service. Those acts are the services ([Service Contract](../../../../process/service/rules/service-contract.md#the-rule)). Keeping a thinner `*_Store` that still adds and reads the same records is the same face. The example that was wrong: `Group_Membership_Store` in the group module's main `protocol/`. What several services share of a graph is imported from the graph module; it is not redeclared here.
7. **Is the parent only a pluggable mirror of a kernel module** (siblings are capabilities; the folder itself has no module contract)? → refuse any `protocol/` there. Shared fields belong in the **kernel** module (or in one capability others import). Example that was wrong: `modules-plugable/knowledge/text/protocol/` beside `likeness/` and `retrieval/`.

Shared **values**, **events**, and **structure** of the module's subject stay in the main `protocol/` when more than one service or widget needs them. The test is ownership, not file count: a large structure model in the main folder can still be correct; a single `Service` there is never correct.

## Common mistakes
- Declaring `tp X ab { Service }` in the module's main `protocol/` (example that was wrong: `Text_Place` under `modules/knowledge/text/protocol/`).
- Leaving Hit/Hits (or only-one-service field bags) in the module main `protocol/` because they "are not Service" — ownership still follows the service or widget that returns them.
- Putting `request.kh` / `response.kh`, or the service abstraction itself, at the service folder root beside where realization must later sit. They belong in that service's `protocol/`.
- Leaving the service's realization at the `services/` root, outside the service folder.
- Growing the main `protocol/` with every new act of the module until an agent must open the whole folder to learn one service — that growth is the failure this rule exists to stop.
- Inventing a second vocabulary for realization files (`impl`, `capsule`, `default`) instead of the same base name beside `protocol/`.
- Stopping after moving only the examples the owner named, without applying the placement test to the rest of that module's main `protocol/`.
- Asking the owner again for the same ruling already given by example (apply the pattern; queue missing math abstractions as their own task).
- Treating this placement test as a substitute for [Challenging Proposed Concepts](../../../../../modules/knowledge/modeling/modeling.md#challenging-proposed-concepts) and the [Attribute-or-Edge Test](../../../../../modules/knowledge/modeling/modeling.md#the-attribute-or-edge-test): a correctly placed type can still be a false concept (capsule width in an ab signature, a service contract filed as a domain root protocol). Challenge **each** proposed concept before it enters any `protocol/`.
- Wrapping another module’s concept under a local name (`Text_Term` for [Label](/modules/knowledge/label/label.md), “Term” for word-or-phrase). [One Owner](/modules/knowledge/modularity/rules/one-owner/one-owner.md): search the owner of the **role**, import it, declare none of your own.
- Putting a `protocol/` under a pluggable **mirror** folder that is not itself a module (item 7 of the placement test).

## Why it exists
A module's contract is read first, and by an agent often only. When every service's types stand in one folder, the folder grows with the module and a reader must open all of it to learn about one service; when an abstraction stands in the root beside its realization, a reader cannot tell what a party is held to from what happens to be implemented. One `protocol/` per owner keeps each surface small and tells the reader at the path whose surface it is. Naming the realization with the same base name as the abstraction, distinguished only by folder, avoids inventing a second vocabulary that would drift from the contract name. The placement test exists so the next agent does not re-learn the mistake by reading a crowded main folder and treating it as the place for the next `Service`.

## What this rule does not claim
- It does not decide what a protocol is, or when a text is one: that is [Protocol](../../protocol.md).
- It does not forbid a service from using the main `protocol/`'s concepts; it forbids writing them again, and forbids writing service-owned types into the main folder.
- It does not say how a document slug is formed beyond the `dt-` prefix: that is [Documentation → File Naming](../../../../../modules-plugable/knowledge/documentation/documentation.md#file-naming).
- Service shape is governed by [Service Contract](../../../../process/service/rules/service-contract.md#the-rule); this rule owns its placement.
- It does not forbid a large main `protocol/` of shared structure; it forbids that folder holding what a single service owns.
