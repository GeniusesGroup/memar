# Label Rule — Category Depth
Label's rules live one rule per directory under [`modules/knowledge/label/rules/`](../README.md), and this is the rule for how many levels stand between a placement and a module, and for where a pluggable module stands. It is a governance rule of this repository, held for [Category](../../labels/category.md).

## The rule
- **Between a placement and a module there are any number of categories.** The path of a kernel or pluggable module is its placement, zero or more categories, and the module (`modules-plugable/computer/memory/store/record`, `memory` being a category). Each category earns its level by [Category → The rules](../../labels/category.md#the-rules): a subject, several members with reason to grow, not a mechanism.
- **A pluggable module stands at the mirror of the module it attaches to.** Its path is `modules-plugable/`, then the path of the module it attaches to, then its own capability name. The module it attaches to is the one whose contract it realizes or extends, which is the module that exposes the explicit relationship its [Pluggable](../../../modularity/labels/pluggable.md#the-test) test asks for. What a module rests on or imports places nothing, so `key_value`, which rests on `page`, stands at the mirror of the module whose contract it realizes. This holds for every such module, whether it has other capabilities or not, so that one test places it ([Pluggable → Operational rules](../../../modularity/labels/pluggable.md#operational-rules)). Owner's ruling, 2026-10-24. A pluggable module that attaches to another pluggable module stands beside it, in the same folder, and declares the relationship; no pluggable module holds another.
- **When a capability extends the subject of a category as a whole and no one module of it, it stands directly in that category's pluggable folder.** It attaches through the protocols of the modules of the category that it reads, which it names, so the relationship [Pluggable](../../../modularity/labels/pluggable.md#the-test) asks for is exposed by those modules and not by the category. A cross-domain analytics namespace of a category and a guest protocol that realizes a whole family are such capabilities. What stands directly in a category's pluggable folder is these, the mirror folders and the nested categories, and no capability that attaches to one module.
- **A mirror folder is neither a category nor a module** ([Category → The rules](../../labels/category.md#the-rules)). The kernel module's existence earns it and the few-members test does not apply to it. The folder holds the capabilities, or, when the kernel module has no other capability, the one module that holds its optional parts, and never both.
- **A module holds its own facets and no modules.** The documentation module holds its facets (changelog, comparison, plan and the rest) because each is a part of what documentation is. A part is never a sibling of its module, and a module whose parts could stand alone in another module's work is not holding parts but a category by another name, which then holds no contract.
- **A category is not created for a handful of modules.** A subject too small to hold several modules with a reason to grow is a module of the category it serves.
- **A module's folder name is unique among the folders that hold a `<name>.py`, across the three roots.** The router (`bundles/memar/memar`, `catalog`) keys a module by its leaf folder name and stops at a repeat, so a module that holds a kernel module's optional parts and has its own `<name>.py` under the kernel module's name, or a capability named as another module that has one (`git`), collides today. That is a defect of the router, which is to key by path; the rule does not wait for it, and the move that meets a collision names it.

## Why it exists
Every added level is another place for two modelers to disagree about where a module goes, and a deeper tree does not make a model more accurate. The first reorganization (2026-10-17) answered that by refusing every level above the module's own, and the cost came due in the memory family: the adapters of one contract either crowded a floor or stood under a module they do not belong to. The owner ruled on 2026-10-24 that the limit was the defect, that the two roots correspond, and that a flat pluggable side is a defect as the categories grow (`modules-plugable/computer/` holds fourteen entries on its floor). The rule keeps what the limit protected, a short reason to put a level in, and moves the test from the depth of the path to the reason for each level.

## What it changes in the tools
Almost no tool counts a module path's depth; the module-graph test names a module by its dotted path and matches the longest, and the router keys by the leaf folder name. The router's key by leaf name is the one change the rule makes necessary. The files that reach the checkout by counting parents from their own location (`parents[N]`), and the Go port's same-category rank by the first segment, change when a module moves, and are the moves task's to repair.
