# Calendar Handoff

## Topic & Purpose
Converting the Khayyam protocol layer of `modules/management/calendar`: the identity surface the domain owns (`protocol/dt-uuid.kh`), under the governing rules in [`../../../Khayyam.practice.md`](../../../Khayyam.practice.md). `git ls-files modules/management/calendar` returns five files; `protocol/dt-uuid.kh` is the only source, and it was the only one converted.

## Status
Protocol layer converted (2026-10-03). `protocol/dt-uuid.kh` accepts against the Khayyam frontend as written, against a root where both `org/…` and `memar/…` resolve.

**The domain is not modelled.** What converted is identity only. The calendar's reason — its substance, the time-stamped entry — has no declaration anywhere in the tree, and the time concept it would be stated against does not exist in this repository either. See Open Questions.

## Decisions

- **A calendar's identity is the thing domain's identity — the same concept, not a new one.** *(Decided.)* The Go source wrote `type UUID thing_p.UUID`, a Go named-type re-declaration of one concept; the thing domain's own comment calls its UUID the base identifier for every domain and says it "can be same with any other UUID domains e.g. user". Khayyam has no alias form, so carrying the same concept here under a second name would be two abstractions claiming one thing — the architecture error [`khayyam.md` → Import Mechanism (`in`)](https://github.com/GeniusesGroup/memar/blob/main/docs/khayyam/khayyam.md) names, which [`qualified-names`](https://github.com/GeniusesGroup/memar/blob/main/modules/khayyam/rules/qualified-names/qualified-names.md) answers with one declaration the other module includes. So the file includes `ThingUUID` from `modules/identity/thing/protocol/dt-uuid.kh` and declares no `CalendarUUID`.
  - This is the fourth domain to reach that conclusion (`user`, `time`, `uri`, and now `calendar`). The repository-wide fact it records: roughly ninety `dt-uuid.kh` files each re-declare one UUID concept, and `thing` is its owner.
  - **Rejected alternative:** declaring `CalendarUUID ab` and composing it. It would have been locally coherent and globally wrong; the collision would surface at the first import site that needed both a thing's and a calendar's identity.
- **`Field_CalendarID` + accessor `CalendarID` matches the corpus and is left as the Go source had it.** *(Decided.)* Every converted `dt-uuid.kh` in this repository takes the shape `tp Field_X ab` / `tp XID mt (self Field_X) () (id ThingUUID)` — `user`, `time`, `uri`, `text` all do. `receiver-method-names` keeps a method bare when the receiver supplies the context, and `Field_CalendarID` already says which field is asked; `result-parameter-names` derives the parameter from the type, and `id` is what the three sibling `dt-uuid.kh` files write. Rule 2's generator produces the body from the field's name.
- **The Go comment moved to the domain document, not the source.** *(Decided.)* Rule 5. `// Usually it is some other domains UUID / e.g. invoice, form, department, role, task, user, production, batch, …` is the reason this domain imports its identity rather than minting it, so it is now [`calendar.md` → Identity](calendar.md#identity). No `//` line was written above the Khayyam.
- **No `CalendarModel` was written, though the corpus convention would have one.** *(Decided, and this is the domain's central finding.)* `user`, `uri`, `text` and `thing` each have a `protocol/model.kh` declaring `ThingModel` / `UserModel` / `URIModel` / `TextModel`, and rule 3 expects a calendar to state `CalendarModel`. Writing it needs a second requirement beyond identity — the entry's time — and there is nothing to name it against: `modules/identity/time` declares no `Time`, no `Field_Time`, no `Field_Epoch`, and `memar`'s `Time` is not the concept either (it is an instant measured from an epoch, with no calendar system and no civil date). A `CalendarModel` composed of `ThingModel` + `Field_CalendarID` alone would be the empty extension point rule 6 names. It was left unwritten rather than written hollow.
- **The domain's edges were not touched.** *(Decided.)* `edges-loop/type/` (calendar system: Gregorian, Persian, …) has no `.kh` file and no Go source — it is a one-line model sketch plus a list of calendars. `type.md` itself is marked `(calendar)-[:type]->(label(??))` with an undecided far end, so there is no contract to convert. The reason vocabulary is not this domain's: [`calendar.md` → Idea backlog](calendar.md#idea-backlog) resolves it to the pluggable [`calendar-reason`](../../../modules-plugable/management/calendar-reason/calendar-reason.md) module.

## Open Questions

- **The calendar has no time-stamped entry.** *(Blocking. The central problem of this domain.)* The domain document's first line — "Calendar records time-stamped entries (events, work periods) for persons and organizations" — has no declaration behind it anywhere in the tree. `Field_CalendarID` names a record; nothing states when it happened. Nothing composes `Field_CalendarID` either: `git grep Calendar -- '*.kh'` returns only this file, so the accessor has no consumer and no record is known to carry it. Finishing the domain means designing the entry — its time, its reason, its span — and the first of those has no type to name.
- **What the calendar needs from the time domain, stated as a requirement on whoever owns time.** The calendar does not need `identity/time` to grow a `UUID`; it needs an instant. Concretely, four things, in dependency order:
  1. **An instant a record can carry.** `memar`'s `modules/time/protocol/time.kh` declares `Time` (`Epoch`, `SecondElapsed`, `NanoInSecondElapsed`) and `time.observers.kh` declares `Observer_Time` / `GetTime`. That is an instant from an epoch with no civil date and no calendar system, so it is the wrong concept for "3 p.m. on 4 Tir" and the right one for "the moment the record was written". The calendar needs to say which of the two it means; the answer is probably both, in different roles, and it is the owner's call.
  2. **A civil reading in a named calendar system.** `edges-loop/type/` says the node is classified Gregorian / Persian / Islamic / … — a calendar system changes what a date *means*, and no type in the tree carries one. `type.md`'s far end is written `label(??)`: undecided between a label vocabulary, an enumeration of systems, and a calendar-system abstraction with its own conversions. Until that is decided, no calendar entry can state a date that is not silently UTC.
  3. **A span.** [`management.md` → Calendar event labels](../management.md#calendar-event-labels) lists `Start`, `End`, `TemporaryEnd`, `ManualStart`, `ManualEnd`, `Deadline`, `ExpectedTime`, `Validity` — all of which are pairs of instants or a span from an instant. `memar`'s `Duration` caps at roughly 290 earth years (its own comment) and is a nanosecond count, so a validity window stated in calendar years is asking for a different concept than the one memar declares. The calendar is the first domain in the tree to need this, and it is why the question cannot be deferred as "TTL can have it later".
  4. **Repetition.** [`time.md`](../../identity/time/time.md) says a time may carry a repetitive epoch like `DayInWeek`, and the same document's motivating examples are the calendar's own: Friday as an organizational holiday, 8 a.m. to 5 p.m. as a daily service window, and `staff-timing-utc.kh`'s `Day() utc.DayElapsed` / `DayHours() earth.DayHours`. `memar` has `modules/time/utc/epoch/day-in-week.kh` and `modules/time/utc/weekday.kh` (`Weekdays`); whether a recurring calendar entry is a repetition rule in the time domain or a repetition attribute on the entry is undecided, and it decides whether the calendar's record is one row or many.
- **The multi-typing question is unanswered and it decides the model.** *(Blocking for `CalendarModel`.)* [`calendar.md` → Idea backlog](calendar.md#idea-backlog) carries it from the cooking comment: "usually a calendar is a `product`, but it can also be other ones like a `task`". A record that is sometimes a product and sometimes a task cannot be given one `Model` abstraction without answering this. The vocabulary discipline the backlog cites ([`../vocabulary-discipline.handoff.md`](../vocabulary-discipline.handoff.md)) asks for the conceptual definition before the term is kept, and "calendar" has not had one — the same handoff's open question 3 names `meeting` and `shift` as audit candidates and has not been run.
- **Whether the calendar node is a thing at all, or a reading on one.** The Go comment's own claim — the ID is *usually another domain's UUID* — describes a calendar record as an attribute-time-stamp attached to an invoice, a form, a department. If that is the whole of it, the calendar may not be an independent node, and the domain's `edges-loop/type` classification would classify the reading rather than a thing. This reading competes with `calendar.md`'s own "the core keeps only the calendar node", and nothing in the tree settles it. It is the same question as the multi-typing one, one level down.
- **`Field_CalendarID` may not be wanted at all.** *(Minor, but it decides whether the file survives.)* Nothing composes or calls it. If a calendar record's identity is always the identity of the thing it timestamps, then the record needs no identity of its own and the correct conversion is to delete this file — the same conclusion `time.handoff.md` reached for `Field_TimeID`. It was converted rather than deleted because the Go source declared it and deleting a declared contract is the owner's call, not the converter's.
- **Whether `CalendarID` collides under `qualified-names`.** A method whose plain name is also a declaration elsewhere must be qualified; nothing in the corpus declares `CalendarID`, so the bare name stands today. If a `CalendarUUID` ever appears, the method side must not move.

## Notes

- **Frontend result.** `modules/management/calendar/protocol/dt-uuid.kh` — **accept**. Nothing was suppressed and nothing was refused.
- **How it was verified.** The frontend resolves one root, and neither `org/…` nor `memar/…` exists in this repository, so a plain run from here would report `unresolved-import` for any importing file. Every `.kh` in the organization repository was copied to `…\khroot_copy\org\` and every `.kh` in the memar repository to `…\khroot_copy\memar\`, preserving relative paths, and the check ran against that root. (Files were copied physically: a Windows junction is not followed by Node.) The same run included the ten already-converted identity and model files this one composes or sits beside — `thing`, `user`, `uri`, `time`, `text` — and all eleven accepted, so the calendar file was checked in company, not alone.
- **The tooling defect reported by the previous wave is confirmed and was avoided.** `memar-documentation.py write`/`edit` with `--newline` passes the literal string `"lf"`/`"crlf"` to the writer in place of `"\n"`/`"\r\n"`. All text here went through the file-write and edit tools.
- **Line endings.** `protocol/dt-uuid.kh` is CRLF, matching every other `.kh` in the repository; `calendar.md` is LF, matching the Markdown. No BOM in either. Both verified by reading the bytes, not by trusting the editor.
- **`TextModel` was needed and was present.** `modules/knowledge/text/protocol/model.kh` was mid-conversion by another agent; it now declares `TextModel ab { ThingModel Field_TextID Field_Text }` and accepted in the same run. The calendar does not compose it today — the Go source composed nothing — but if a calendar entry is ever given a human-readable name, that is the abstraction it composes, and not a second text concept here.
- **No empty abstraction was written without recording it.** Rule 6 is satisfied by argument rather than by omission: `Field_CalendarID ab` is empty because the requirement it carries is the accessor beside it and the body is generated (rule 2), the same shape as `Field_TimeID` / `Field_URIID` / `Field_TextID`; and the abstraction that *would* have been hollow — `CalendarModel` — was not written at all, for the reason given in Decisions.
