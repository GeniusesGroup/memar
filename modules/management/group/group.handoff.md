# Group Handoff

## Topic & Purpose
Converting the Khayyam protocol layer of `modules/management/group`: the identity surface (`protocol/dt-uuid.kh`), the node model (`protocol/model.kh`), the record contract (`protocol/data_model.kh`), and the one edge that carried a record (`edges/membership-term-member_limit/protocol/data_model.kh`), under the governing rules in [`../../../Khayyam.practice.md`](../../../Khayyam.practice.md). `git ls-files modules/management/group` returns 28 files; four were sources with declarations and were converted.

## Status
Protocol layer converted (2026-10-03). All four files accept against the Khayyam frontend, against a root where both `org/…` and `memar/…` resolve.

**The domain is not modelled.** What converted is identity, one node model, one record contract, and one edge record. The membership decomposition the domain document settles as "the resolved direction" — membership, role, and term as separate small edges — has no declaration anywhere in the tree. See Open Questions.

## Decisions

- **A group's identity is the thing domain's identity — the same concept, not a new one.** *(Decided.)* The Go source wrote `type UUID user_p.UUID`, a Go named-type re-declaration. `user_p.UUID` is itself `thing_p.UUID`, and the thing domain's own comment calls its UUID the base identifier for every domain. Khayyam has no alias form, so carrying the concept under a second name would be two abstractions claiming one thing. The file includes `ThingUUID` and `Array_ThingUUID` from `modules/identity/thing/protocol/dt-uuid.kh` and declares no `GroupUUID`. This is the fifth domain to reach that conclusion (`user`, `time`, `uri`, `calendar`, now `group`); `task`, `department`, `staff` and `shift` reach it in the same wave, and the repository-wide fact it records is that every `dt-uuid.kh` in the tree re-declares one UUID concept and `thing` owns it.
- **`GroupModel` composes `ThingModel`, `UserModel` and memar's `Target`.** *(Decided, with a reservation.)* `UserModel` already composes `ThingModel`, so `GroupModel` composing both states twice what one of them already carries. Both were kept because the Go interface embedded both and the embedding is a claim — a group *is* a user. Nothing in [`group.md`](group.md) explains why a group would be a user, and no consumer of `GroupModel` exists in the tree. See Open Questions.
- **`event_p.Target[DataModel]` became memar's unqualified `Target`, and the type restriction was lost.** *(Decided, and recorded as a real loss.)* Khayyam has no generic syntax, and memar's `Target` is already converted as `tp Target ab` with `DispatchEvent(event Event)`, `AddEventListener`, `RemoveEventListener` — accepting *any* `Event`. The Go parameter `DataModel` carried the domain's own guarantee, stated in memar's own comment on `Target`: "It MUST implement for each data-type in each domain that need to dispatch, It means method only accept that data-type event not any other one." That guarantee has no Khayyam expression and is now unenforced. memar shows the shape that would restore it — `Target_Race_Event` in `memar/modules/process/event/protocol/target-race-event.kh` declares the three methods with `Race_Event` and does not compose `Target` — but the declaration would have to be written by whoever owns the event model, because the method set is memar's, not this domain's. A `Group_Event_Target` declared here with three body-less methods would have been an empty abstraction (rule 6) with a duplicate of memar's contract.
- **`GroupDataModel`, not a bare `DataModel`.** *(Decided.)* Rule 3 and the converted corpus: `TextDurationDataModel`, `AuditLogDataModel`, `NodeAddressDataModel`. `event_p.Event` was imported as memar's bare `Event`.
- **The three member counts became qualified observers returning `W32`.** *(Decided, with a collision recorded.)* `Minimum() int32`, `Expected() int32`, `Maximum() int32` are inline accessors on the record, the shape `NodeAddressDataModel` handled by extracting observers (`Observer_Node_Address` + `GetAddress`). So:
  - `Observer_GroupMemberLimit_Minimum` / `GetMinimum`
  - `Observer_GroupMemberLimit_Expected` / `GetExpected`
  - `Observer_GroupMemberLimit_Maximum` / `GetMaximum`

  The qualifier is required, not decorative: the identical triple is declared a second time in `modules/knowledge/knowledge_unit/edges/duration/protocol/data_model.kh` (`Minimum() duration.Second` / `Expected()` / `Maximum()`, unconverted), so the bare names `Minimum`, `Expected`, `Maximum` are already ambiguous in the corpus. `int32` became `W32` (`memar/modules/math/integer/unsigned-32.kh`) rather than a new `GroupMemberLimit` abstraction: unlike `criterion`'s `Point`, where a domain concept existed behind the Go `int64`, here the Go said a primitive and inventing three abstractions for three integers would be modelling the storage, not the domain.
- **`GroupMemberLimitDataModel` is the edge's record name; `membership-term-member_limit` was not repeated whole.** *(Decided.)* The corpus writes `TextDurationDataModel` for `text/edges/duration`, i.e. owner + the relation word. Owner + `MemberLimit` says the same thing without a 22-character name.
- **`_import/group.kh` was left unconverted.** *(Decided.)* It declares `type GroupUUID = protocol.UUID` — a Go type *alias* of the thing domain's UUID, under a `package org` that imports the deleted `libgo/protocol`. Converting it would mint a rival `GroupUUID`, the exact architecture error `qualified-names` answers against. No `_import` file has been converted in any wave of this migration, and the convention holds here. Its content is already carried by `protocol/dt-uuid.kh`.
- **The Go comment `// register group` moved to the document, not the source.** *(Decided.)* Rule 5. It is a note about the module's purpose and is now in this handoff's Topic; it names no contract.

## Open Questions

- **The membership decomposition has no declarations.** *(Blocking for the domain, not for the conversion.)* [`group.md`](group.md) resolves the direction — "proper modeling decomposes relationships into several small, single-purpose edges (e.g., membership + role as separate edges) rather than overloading one generic edge" — and names `edges/`, `edges-loop/` members accordingly: [`edges/joined`](edges/joined/joined.md) (membership, with `Member`/`Honorary Members`/`Supporter` labels and a `JoinWay`), [`edges/invite`](edges/invite/invite.md), [`edges/request_to_join`](edges/request_to_join/request_to_join.md), [`edges/blocked`](edges/blocked/blocked.md), [`edges/membership-term-skill`](edges/membership-term-skill/membership-term-skill.md), [`edges/parent`](edges/parent/parent.md). Seven edges, one record contract between them. What exists in the tree is the direction and no code.
- **`(group)-[:membership_term_member_limit]->(---)` has an undecided far end, and the Go comments point somewhere else.** *(`membership-term-member_limit.md` writes the far end as `---`.)* The three Go comments say "Minimum number of employees **for this job position**" — a per-position reading, not a per-group one. The document puts the edge on the group. The two disagree, and the disagreement decides whether `Field_GroupID` belongs on this record at all. A member limit that is per *position* belongs to the staff side ([`../staff/edges/group/group.md`](../staff/edges/group/group.md) already holds staff↔group hiring), not to the group.
- **The parent edge has no contract, and `parent.md`'s GUI citation crosses domains.** [`edges/parent/parent.md`](edges/parent/parent.md) cites `../../../../knowledge/question/widgets/question/gui.kh` as the source of "Show in SameLevel, UpperLevel, LowerLevel" and drag-and-drop reparenting. The path resolves correctly from the document — the file exists at `modules/knowledge/question/widgets/question/gui.kh` (checked 2026-10-08) — but it is `knowledge/question`'s widget, not the group's; the citation crosses two domains and the document itself calls it a *view* behaviour over the stored parent. Its open questions — one edge or two (`parent_of` / `parent_is`), and whether the department organizational chart reads the same edge — are unanswered, and the second decides whether `edges-loop/department/department.md` (`(group)-[:department]->(---)`, "used to show organizational chart") is a second hierarchy or a reading of this one.
- **Whether `GroupModel` should compose `UserModel` at all.** `(group)` and `(user)` are different concepts in this repository — `group.md`'s own test cases include "a sole proprietorship (one person acting as an organization)", which is precisely the case the Go embedding cannot express. Nothing consumes `GroupModel`. Until someone states what "a group is a user" buys, the composition is an unexplained claim carried forward from Go.
- **Label-granting authority (unresolved #5) is still open and it is what would make `DepartmentModel` a runtime upgrade rather than a static composition.** The structural reading (Department *is* a Group, now `DepartmentModel` composing `GroupModel`) and the discussion reading (a Department is a Group an authorized role has *labelled*) are different mechanisms, and [`../department/edges-loop/department/department.md`](../department/edges-loop/department/department.md) holds the label edge with an undecided far end. `group.md` unresolved #1 (static embedding vs runtime type upgrade) is unresolved; `calendar.handoff.md` reaches the same question for its own model and does not settle it.
- **Oversight membership (unresolved #2) and org-to-org business relations (unresolved #3) have no home.** Both are described only as questions; neither has an edge folder, so nothing can be converted for them and nothing is lost by leaving them.
- **Cycle guards (unresolved #4) are unaddressed anywhere.** With `edges/parent`, `edges/joined` and an org-as-external-member reading, cycles are structurally possible; [`group.md`](group.md) → Idea backlog → Group deletion depends on the ancestor chain being walkable. No cycle-detection concept exists in the tree.

### Open Questions raised by the research
Each carries a recommended default and what it blocks; the full text is in the research's [Open Questions](group.research.001.md#open-questions). Ordered by what they change.

1. **Is a group a kind of user, or a thing with members that is classified as an actor only when it acts as one?** Default: the second. Blocks: `GroupModel` composing `UserModel`, the `(user)`/`(group)` pairs in the ownership and status edges, the sole-proprietorship case, the base of the `group` loop-edge.
2. **Can any thing take members (a task, a case, a contract), or is a team always a separate group node?** Default: any thing can. Blocks: [group.md](group.md#unresolved-questions) unresolved 1, Task question 2 and `TaskModel`, the case premise, the contract question, the product default chat.
3. **Does a membership have an identity of its own?** Default: yes. Blocks: the shape of `joined`, the three pair-keyed records (content `group-user`, user `GroupUserDisplayName`, access-control `GroupUserAccessControl`), any `MembershipDataModel`.
4. **When a group is a member of another, do its members count?** Default: no for unit membership, yes for `parent_is`; two relations. Blocks: the committee case, the department chart, effective membership, whether containment is one relation with task's `part_of`.
5. **May membership cycles exist?** Default: `parent_is` acyclic and guarded; unit membership may cycle and derivations are cycle-safe. Blocks: unresolved 4, the ancestor-deletion backlog.
6. **May membership arise without the member's consent?** Default: yes (authority, rule, law, event); consent is admission's default. Blocks: admission, the household and municipality cases.
7. **Does leaving end the membership or delete it; is a return a new membership?** Default: ends it, never deletes; a return is new and refers back. Blocks: history, erasure.
8. **Where does a role in a group live: a label on the membership, a role-group, or a position owned by role and staff?** Default: a position; the membership carries only its kind. Blocks: the `joined` labels, `role/edges/group`, `staff/edges/group`, Task question 7, the member-limit far end.
9. **Is oversight a seat or an inspection right?** Default: a seat without a vote is a membership of a kind; an inspection right is a delegation. Blocks: unresolved 2.
10. **Do business relationships between organizations belong here?** Default: no; they stay with `identity/organization` and contract. Blocks: unresolved 3.
11. **Who may classify a group as a department, squad, tribe or guild; one mechanism for all kinds?** Default: an authority over the group, recorded; one mechanism; the kinds are data. Blocks: unresolved 5, `department/edges-loop/department`.
12. **Is a rule-defined group (a cohort) a different capability from a group people joined?** Default: yes, a pluggable. Blocks: the form, pos, sell-limit, discount, voucher and buyers links.
13. **Is a group a place for contents or the audience of a timeline?** Default: the audience. Blocks: the content widgets `group` and `group-user`, the case premise, `timeline/edges/chat`, the "same group" reply rule.
14. **What is a group's identity across rename, member replacement, merge, split, annual intake and reopening?** Default: rename, replacement and reparenting keep it; merge and split create groups that supersede; an annual intake is a new group unless named otherwise. Blocks: the `supersedes` shape, the reorganization and class cases.
15. **Who may see a member list, and how does it meet erasure?** Default: nobody by default; sensitivity labels on a group and a membership. Blocks: authorization and access-control, the sensitive-membership case.
16. **May a group be deleted or only dissolved; what happens to children, owned things and the timeline?** Default: dissolved with an end instant. Blocks: the group-deletion backlog item, the lifecycle.
17. **When the last authority leaves, who acts for the group?** Default: an organization rule decides succession; nothing is granted silently; acting for a collective is a delegation. Blocks: representation, the actor classification.
18. **One shared offer-and-acceptance (admission, task acceptance, contract signature) or one per domain?** Default: one, defined once. Blocks: admission, Task question 6, the `invite` pluggable.
19. **Is the MUST/SHOULD/MAY level vocabulary shared with the Task `requires` edge?** Default: shared, defined once. Blocks: `membership-term-skill`.
20. **Is a member limit a property of the group or of a position?** Default: the group; a per-position limit belongs to the position. Blocks: the far end of `membership-term-member_limit` and its `.kh` record.
21. **Is the org group listing with offset and limit a modeling matter?** Default: no; service layer. Blocks: nothing.

## Notes

- **The `rights` alias concern is already resolved, and it was resolved before this wave.** Both `rights/contract` and `rights/case` declared `type UUID group_p.UUID`, which would have made this domain's identity load-bearing for them. Both files now import `ThingUUID` directly from `modules/identity/thing/protocol/dt-uuid.kh` and declare no group import at all, so no domain reaches this one through an alias. Nothing here needed to change for them, and nothing should be changed in those domains to "restore" the dependency.
- **Frontend result.** `modules/management/group/protocol/dt-uuid.kh`, `modules/management/group/protocol/model.kh`, `modules/management/group/protocol/data_model.kh`, `modules/management/group/edges/membership-term-member_limit/protocol/data_model.kh` — **accept**, four of four. Nothing was suppressed and nothing was refused.
- **One real refusal was found and fixed.** `protocol/model.kh` and `protocol/data_model.kh` first imported memar's `Target` and `Event` under the local spellings `Event_Target` and `Process_Event`, on the strength of the `ProcessLog_Event` precedent. That is wrong: `in` resolves the name *declared* in the target file, not a local alias, and the frontend refused both with `name-not-declared`. `ProcessLog_Event` looks like a local spelling but is declared *in memar itself* (`memar/modules/process/log/protocol/log-event.kh`), which is why it worked. Both files now import the bare `Target` and `Event`, and both accept. The general lesson for the next wave: qualification belongs at the declaration site, and an `org/` domain cannot rename a `memar/` one.
- **How it was verified.** The frontend resolves one root, and neither `org/…` nor `memar/…` exists in this repository, so a plain run from here would report `unresolved-import` for any importing file. Every `.kh` in the organization repository was copied to `…\khroot_copy\org\` and every `.kh` in the memar repository to `…\khroot_copy\memar\`, preserving relative paths, and the check ran against that root. The final run included all eight files this wave wrote across `group`, `task`, `staff` and `department`, together — eight of eight accepted, so the files were checked in company, not alone.
- **Line endings.** All four `.kh` files are CRLF, matching the converted `.kh` files in the repository; this file is LF, matching the Markdown. No BOM in any. Verified by reading the bytes.
- **The `Minimum`/`Expected`/`Maximum` triple is a cross-domain collision waiting to happen.** `modules/knowledge/knowledge_unit/edges/duration/protocol/data_model.kh` declares the same three methods over `duration.Second`. That file is unconverted. When its wave arrives it must either take the qualified spellings or the two records must be recognised as one abstraction — they are the same shape (a planned/actual count for a bounded population) applied to a different population, and the group edge's Go comments are about employees while the knowledge_unit edge's are about learning time.
- **No empty abstraction was written without recording it.** Rule 6 is satisfied by argument, not by omission. `Field_GroupID ab`, `Field_GroupsID ab` and `Target`'s use are empty because the requirement they carry is the accessor beside it and the body is generated (rule 2) — the same shape as `Field_TextID` / `Field_CalendarID` / `Field_EdgeID`. No `GroupModel` requirement was invented to fill a block.
- **Read with the rest of the wave.** `task`, `staff`, `department` and `shift` were converted in the same run and the same root; see [`../task/task.handoff.md`](../task/task.handoff.md), [`../staff/staff.handoff.md`](../staff/staff.handoff.md), [`../department/department.handoff.md`](../department/department.handoff.md), [`../shift/shift.handoff.md`](../shift/shift.handoff.md).
