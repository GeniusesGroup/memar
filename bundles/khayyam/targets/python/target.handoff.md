# Khayyam Python Target Handoff
Open state for [target.md](./target.md). See [documentation-handoff.md](../../../../modules-plugable/knowledge/documentation/handoff/handoff.md) for what a handoff is.

## Decisions
### The profile and its place (Tentative, 2026-10-24)
- The profile of Python written to be carried into Khayyam is stated in this target's document, beside the Go and JavaScript targets, because the converter that applies it is this toolchain's and a rule's home is its subject's document. The rules stay Tentative while the owner's ratification is a working answer (decision below).
- A module's Python is split into domain code, which is translated, and host bindings, which realize an abstraction the domain declares and are rewritten per host as body-less methods are.
- A conversion is accepted by the module's contract suite passing on both realizations.

### Which host runs a converted module first is decided when the conversion is planned (Tentative, 2026-10-24)
- Decided: the host is chosen when the conversion of a delivered system is planned, not now. The Khayyam toolchain's first working target is JavaScript, on a JavaScript host and in a browser ([Khayyam toolchain → The goals](../../khayyam.md#the-goals-in-the-order-they-come)), and the host chosen decides which host bindings are rewritten.
- Reason: nothing before the conversion depends on the choice, and the profile keeps host bindings small, one file per foreign capability, for every host ([target.md → Domain code and host bindings](./target.md#domain-code-and-host-bindings)). The independent critique of 2026-10-24 (task 20261024-T161344Z-16944) found the material settles it, so it is not brought to the owner.
- Rejected: deciding now for the JavaScript host, which would shape host bindings for one host before any conversion is planned.

### What the checker assumes (Tentative, 2026-10-24; owner's working answers of 2026-10-25)
- The checker is built on the four working answers below: the profile as written, loops and jumps admitted and marked, integer arithmetic and formatted text in width-naming domain capsules, and a pluggable module imported as `modules_plugable`. Each is replaced if its deeper task changes it.
- Reason: the checker and the first modules of a Memar-built system can be written without waiting, and every use of a form not yet mapped stays findable by its label.

### The Python profile is ratified in its place under the Khayyam toolchain (Tentative, owner's working answer, 2026-10-25; deeper task 20261025-T140522Z-16944)
- Decided: the profile in [target.md → The rules](./target.md#the-rules) is ratified where it stands, beside the Go and JavaScript targets, and its checker is built first (task 20261024-T161020Z-20560). The rules bind from the first module of a Memar-built system, and some Python idioms, comprehensions, lambdas, operators and exceptions, are given up in domain code.
- Reasons: the owner ruled on 2026-10-24 that a Memar-built system is written in Python following Memar's framework and that Khayyam replaces the Python later, so the Python must be written for a conversion that is a translation and not a redesign; the profile is that design. Its evidence was corrected on 2026-10-24 after an independent critique: the Go residue is the work the Go bridge never attempted, not a list of forms that cannot cross, and what the profile does not yet cover is stated ([What the profile does not yet cover](./target.md#what-the-profile-does-not-yet-cover)).
- Rejected: ratifying a narrower profile, only imports, typing, errors as values and host bindings, which leaves more of every body to be carried by hand at conversion; placing the profile in a document of its own outside the toolchain, which puts the converter's rules apart from the converter.
- Standing: the owner accepted the recommended option on 2026-10-25 as a working answer, to be studied in depth in task 20261025-T140522Z-16944, which may change it. It replaces the open entry "Does the owner ratify the Python profile, and its place under the Khayyam toolchain?".

### Loops and jumps are admitted in the profile, marked, until the flow library declares their forms (Tentative, owner's working answer, 2026-10-25; deeper task 20261025-T140523Z-16944)
- Decided: the profile admits `for` over a domain container, `while`, and `break`, `continue` and an early `return` as the last command of a branch; the checker marks each use under its own label, and the conversion of those bodies waits for the flow library's declarations, which [Control Flow](../../../../modules/process/control-flow/control-flow.md) owns. The conversion of loop bodies is not mechanical until then, and the marks show how much waits.
- Reasons: [target.md → The rules](./target.md#the-rules) maps a conditional to the flow library's `IF`, declared in draft in `modules/process/control-flow/protocol/if.kh`, while the files of the same folder for loops and jumps, `for.kh`, `while.kh`, `loop.kh`, `break.kh` and `continue.kh`, hold only the licence line or a comment; almost every method body has a loop, so refusing loops or waiting for their forms would hold up every module of a Memar-built system.
- Rejected: refusing loops in domain code and writing iteration as a method of the container that takes a named capsule as its body, which costs a capsule per loop body in every module; waiting for the flow library's loop and jump forms before any module of a Memar-built system is written, which makes the delivery wait on a language design.
- Standing: the owner accepted the recommended option on 2026-10-25 as a working answer, to be studied in depth in task 20261025-T140523Z-16944, which may change it. It replaces the open entry "What Khayyam form does a profiled loop or jump convert to, while the flow library declares none?".

### A quantity is a domain capsule naming its width, and text built from values is a method of the capsule that owns the text (Tentative, owner's working answer, 2026-10-25; deeper task 20261025-T140524Z-16944)
- Decided: every quantity in domain code is a domain capsule that names its width once (`Count` over `W64`), its arithmetic in a host binding that refuses overflow with a returned error, so the Python and the Khayyam realization fail at the same bound; text built from values is a method of the capsule that owns the text, taking each value's own text method's result. Cost: a width chosen per quantity, and overflow checks Python never needed.
- Reasons: a Python `int` has no bound, while the number tower names only widths, `I`, `W` and `R` with a bit count ([Math → The number tower](../../../../modules/math/math.md#the-number-tower)), and each width capsule chooses its own overflow behaviour ([Encapsulation → Primitive Capsule Specification](../../../../docs/khayyam/encapsulation.md#primitive-capsule-specification)), so converting an integer to a width changes what overflows unless the width is named from the start; no document states an unbounded integer capsule, and an f-string or `str.format` has no stated Khayyam form.
- Rejected: declaring an unbounded integer capsule for Khayyam and mapping Python `int` to it, a new kind beside the widths that [Math](../../../../modules/math/math.md) owns; leaving both to the converter, so that each use is designed at conversion.
- Standing: the owner accepted the recommended option on 2026-10-25 as a working answer, to be studied in depth in task 20261025-T140524Z-16944, which may change it. It replaces the open entry "What capsule does a Python integer holding a quantity become, and what form has text built from values?".

### A pluggable module is imported through the alias `modules_plugable` (Tentative, owner's working answer, 2026-10-25; deeper task 20261025-T140525Z-16944)
- Decided: domain code spells the folder `modules_plugable`, an alias the serving image installs once on the import path for `modules-plugable`, and the converter maps the one spelling back. Cost: one mapping rule in the converter and one in the image, and a Python path that differs from the repository path in one segment.
- Reasons: the profile's import rule is `from a.b.c import X` with the repository path ([target.md → The rules](./target.md#the-rules), row `import`), and Khayyam's form `tp X in "path"` can name `modules-plugable/...`, but Python cannot, because `modules-plugable` is not an identifier; Memar's own code reaches it with `import_module('modules-plugable.computer.memory.filesystem.services.fs_memar')` (`bundles/memar/tests/module_graph.py`), a dynamic import the profile does not admit, so without the alias a module of a Memar-built system that uses a pluggable module, such as the GUI realization under `modules-plugable/computer/ui/gui/`, has no admitted import.
- Rejected: renaming the folder to a Python identifier across the repository, a repository-wide move and every link to it; admitting `import_module` with a literal path in domain code, a dynamic import the checker must parse as a static one.
- Standing: the owner accepted the recommended option on 2026-10-25 as a working answer, to be studied in depth in task 20261025-T140525Z-16944, which may change it. It replaces the open entry "How does profiled Python import a module under `modules-plugable/`?".
