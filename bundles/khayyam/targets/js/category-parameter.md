# Category Parameter
## Abstract
The owner has asked whether a signature may name a *category* — `sc`, `ab`, `cp` — as well as a concrete type, so that a parameter can stand for "any of that kind", and has said that what they want underneath is a rule that a category may be declared in that position generally, so that "(abstract `ab`) may also be permitted" and an abstraction may be passed between layers whatever it is. This document establishes what the repository already says, what the sources already assume, and what each of four options costs; it drafts the text each would need and applies none of it. Seven findings carry the rest. **One:** a signature may name nothing but a declared type's name today, in every position, and not by omission — the parser refuses every subtype keyword in every type position with the label `keyword-as-identifier`, which is the same label a mistyped keyword earns, so a category is unspeakable rather than merely unstated. **Two:** the semantic representation carries a parameter's type as a bare `string`, so admitting a category is a change to the representation and not a parser fix; the smallest option costs three files in `core/`, the option that costs the frontend nothing is the one that names a declared abstraction, and the option that costs nothing in code is the one the base layer cannot hold. **Three:** the sources neither use nor contradicts a category position — zero of 739 method declarations under `modules/` name one — but it does carry fifty-four retained Go generic declarations and eight retained *union* constraints, which is this repository's own evidence that a parameter standing for a kind is a real need the port answered by naming one abstraction per concrete type. **Four:** the deeper question is not new and not old either: the spelling half is already carried in [`target.handoff.md`](./target.handoff.md) under two different headings, the vocabulary for the generalization is already drafted as a term, and the answer for `sc` is already ruled; what is new is the owner's re-reading of a spelling question as a rule about categories. **Five:** a parameter typed "any abstraction" receives an artifact that carries a name and nothing else — the emitted marker is `{ type: "IF" }` — so no variance question arises, because there is no contract for a callee to use; the power the callee would have is the qualified call on methods the abstraction itself declares, which the language admits and this toolchain refuses. **Six:** the documents' own vocabulary is emphatic that a category is not a type and not a hierarchy, which is strong evidence against the option that makes categories types and moderate evidence for the one that names a declared abstraction; the grammar's vocabulary is mildly the other way, since the same keyword already names the category in a declaration. **Seven:** the cheapest option in this document is the one already preferred — a declared abstraction — and it is the only one that costs the frontend, the sources and the base layer nothing at all.

## Introduction
### Motivation
Three positions have now been written down about the same subject, and the owner has found each of them hard to read. [`language-gaps.md`](./language-gaps.md) at [I-E](./language-gaps.md#i-e--what-a-scope-parameter-is-written-as-and-what-an-sc-position-carries) drafts a keyword written where a signature writes a type, and names the position *Category Name*; [`sc-in-signature.md`](./sc-in-signature.md) works through ten drafts of what a signature may write for a scope after the ruling that an abstraction has no need of one; and [`docs/khayyam/khayyam.research.001.md`](../../../../docs/khayyam/khayyam.research.001.md) scored five options for keeping the construct. The owner's question is larger than all three. It is not "what does a signature write for a branch body" — that has an answer, a preferred one, and a ruling behind it — but "may a signature name a category at all, so that the question has a general answer and a value of *whatever kind* may be handed between layers". No document in this repository carries that question in that form, and no handoff frames it as a rule about categories rather than as a spelling. This document puts the general question next to the three partial answers and says what each general answer would cost.

### Methodology
Every claim below about this repository carries the file and line it was read at. Two words mark the two kinds of claim, as [`docs/khayyam/khayyam.research.001.md`](../../../../docs/khayyam/khayyam.research.001.md) uses them: **evidence** is a quotation or a line of code or a measured scan result, and **inference** is my reading across two or more of those. Claims about the frontend were measured, not assumed: twelve units were written for the purpose and passed to `analyze` from [`core/src/frontend.ts`](../../core/src/frontend.ts) and to `readCommands` from [`core/src/body.ts`](../../core/src/body.ts) in a throwaway harness outside this repository, each one varying one thing — whether the position names a declared type, a scope a body declared, or a category keyword — and each result is reported with the label the toolchain actually returned. The claims in the sources come from scans over every `.kh` file under `modules/`, excluding `build/`, and each scan's shape is stated so a reader can repeat it; the counts are this document's own and differ from the counts other records give, which is recorded rather than reconciled. Two things a reader should carry in: the documents this document overlaps — [`sc-in-signature.md`](./sc-in-signature.md) and [`language-gaps.md`](./language-gaps.md) — are other sessions' artifacts and are cited here, not edited, and where a draft below repeats a draft one of them already carries, this document says so and drafts only what is new. And nothing under `docs/` is edited; every draft below is text for the owner.

## Explanation
### Every place a signature may name something
The question as asked has a short answer: **no place a signature names a category.** What follows is the whole of what a signature may name, position by position, so the reader can see that the absence is uniform rather than accidental.

1. **The owner group** names the method's parent type — "The owner group names the method's parent type" ([`docs/khayyam/method.md`](../../../../docs/khayyam/method.md) at `:38`, `:34`) — and what it may name is bounded by two sentences: a signature owned by an abstraction names the concept and may name abstractions only ([`docs/khayyam/abstraction.md`](../../../../docs/khayyam/abstraction.md) at `:109`, `:101`), while a signature owned by a capsule may name a capsule, including itself (`:110`). A method may be attached to *any* type, an abstraction or another method included ([`method.md`](../../../../docs/khayyam/method.md) at `:29`, [`docs/khayyam/khayyam.md`](../../../../docs/khayyam/khayyam.md) at `:80`) — so a third owner exists and neither sentence describes what its signature may name. **Evidence.** Whether a *scope* may own a method is unaddressed: the language states no placement for a `sc` at all ([`bundles/khayyam/rules/scope-placement/scope-placement.md`](../../rules/scope-placement/scope-placement.md) at `:21`), so "any type" includes one by the documents' own words while this repository's rule forbids it (`:12`).
2. **The influencing group** is the only position with a sentence about what may *arrive* rather than what may be *written*: "A method's influencing group may receive a `vr`, an `sc`, or an `mt`. The compiler distinguishes the three from the callee's signature" ([`method.md`](../../../../docs/khayyam/method.md) at `:71`). Three things may arrive — an instance, a code scope, a method. **Evidence:** what the parameter's *type* is written as is nowhere stated, which is the gap [`language-gaps.md`](./language-gaps.md) at `:134` records. **Inference:** "the compiler distinguishes the three from the callee's signature" is a claim about the signature doing the distinguishing, and the signature has one slot per parameter; either the slot can hold three kinds of thing or the sentence describes something else.
3. **The influenced group** has no statement of any kind, and [`docs/khayyam/variable.md`](../../../../docs/khayyam/variable.md) is what the sources and the target treat as its subject.
4. **The position, restated from the grammar's side**, is the only sentence that names a *spelling*: "An argument position may be satisfied by a `vr` of the declared type or, for `sc` and `mt`, by the type itself passed as a type-level argument" ([`khayyam.md`](../../../../docs/khayyam/khayyam.md) at `:131`). "The type itself" is the one place the documents reach for a value that is a type rather than an instance, and it is used for exactly two categories.
5. **Elsewhere**, where a signature is not the subject: a capsule field's type ([`khayyam.md`](../../../../docs/khayyam/khayyam.md) at `:76`), a `vr`'s type (`:135`), and an abstraction's composition block, which holds abstraction *names* and nothing else (`:102`).

**Every one of these names a declared type.** Not one names a category, and not one names a kind.

### What the grammar and the frontend do with what a signature names
**Evidence — the grammar refuses a category in every type position, and the refusal it uses is the one a typo earns.** [`core/src/parse.ts`](../../core/src/parse.ts) reads a parameter list as a name followed by a type reference (`:197-217`), and a type reference as a name plus any names a dot joins (`:169-176`). The name it starts from is [`expectName`](../../core/src/parse.ts) at `:159-167`, which refuses any of the seven keywords with `keyword-as-identifier` and any non-identifier with `declaration-form`. So a keyword standing in a type position is refused before any question of what it means arises. Measured, one unit per line, through `analyze`:

| Unit (the only line that varies) | Result |
| --- | --- |
| `tp Drive mt (self Text) (branch Branch) () { tp Branch sc { } }` | refused `unbound-type-name` |
| `tp Drive mt (self Text) (branch sc) () {}` | refused `keyword-as-identifier` |
| `tp Drive mt (self Text) (branch ab) () {}` | refused `keyword-as-identifier` |
| `tp Drive mt (self Text) (branch mt) () {}` | refused `keyword-as-identifier` |
| `tp Drive mt (self Text) (branch cp) () {}` | refused `keyword-as-identifier` |
| `tp Drive mt (self Text) (branch in) () {}` | refused `keyword-as-identifier` |
| `tp Drive mt (self Text) (branch tp) () {}` | refused `keyword-as-identifier` |
| `tp Drive mt (self sc) () () {}` | refused `keyword-as-identifier` |
| `tp Text cp { field sc }` | refused `keyword-as-identifier` |
| `vr b sc` | refused `keyword-as-identifier` |
| `tp Drive mt (self Text) () () { vr b sc }` | accepted; body refused `keyword-as-identifier` |
| `tp Body cp {}` + `tp Run mt (self Text) (branch Body) () {}` + a body declaring `tp Branch sc {}` and calling `self.Run(Branch)()` | accepted |

Two of those rows carry the weight. **The last one is the shape the repository's only measurement writes** ([`emit.test.ts`](./tests/emit.test.ts) at `:11-45`), and it is accepted with nothing changed: a declared capsule in the signature, a body-declared scope passed at the call site, and the backend already emitting the scope as a function and handing the call its name ([`emit.ts`](./src/emit.ts) at `:423-429`, `:76`, `:342-357`). **The first one is the finding the sources have never had**: a signature cannot name the very thing the language says this position receives. A body-declared scope is not a declaration of the unit — it is a command of a body ([`core/src/body.ts`](../../core/src/body.ts) at `:179-195`, dispatched from `:200`; [`program.ts`](./src/program.ts) at `:230-231`) — and a parameter's type must be a name the unit or one it includes declares ([`core/src/frontend.ts`](../../core/src/frontend.ts) at `:68-75`, the label at `:72`). So `(branch Branch)` is refused for the same reason `(body Method)` is ([`language-gaps.md`](./language-gaps.md) at `:27`): **there is no declaration a signature may write for a branch body.** A declared capsule is the only spelling that survives, and [`sc-in-signature.md`](./sc-in-signature.md) at `:88` records that the tree's only measurement takes it.

**Evidence — the representation is why this is not a parser fix.** [`core/src/sr.ts`](../../core/src/sr.ts) carries a parameter as `{ name, type: string }` (`:66-69`) and collects the three groups' types into one flat list (`:135-153`, `:144-149`). A category and a type are the same string in it. **Inference:** admitting a category means giving a parameter's type somewhere to say which of the two it is, and every reader downstream treats the string as a name — the analyzer's visible-name table ([`frontend.ts`](../../core/src/frontend.ts) at `:38-75`), the emitter's owner lookup for a call's receiver ([`emit.ts`](./src/emit.ts) at `:232-233` into `:93-99`), and the classification of a body-less method by its owner group's type ([`program.ts`](./src/program.ts) at `:289-294`, which reads `unit.types[owner.type]`). A category string reaching any of those three is looked up as a name and missed. **Evidence:** the body reader has the same shape and the same refusal ([`body.ts`](../../core/src/body.ts) at `:105-112` on `:93-101`, reached from `readDeclare` at `:168-174`), so a position that may hold a category has two readers, not one.

**Evidence — this toolchain does not in fact distinguish the three the document says it distinguishes.** [`method.md`](../../../../docs/khayyam/method.md) at `:71` says the compiler tells a `vr`, an `sc` and an `mt` apart from the callee's signature. The backend tells them apart from the *argument's binding* instead: a local of kind `scope` is found by [`findLocal`](./src/emit.ts) at `:166-172` and emitted as `$Name$`, a cell as `local$`, and an unbound name as a type marker ([`emit.ts`](./src/emit.ts) at `:234-242`, `:354-358`, `:442-456`). The signature contributes nothing to that decision. **Inference:** the sentence at `:71` describes an intent the representation does not yet realize, which is one more reason the spelling question is open rather than settled.

### What the sources already assume, and what they work around
Scans over every `.kh` file under `modules/`, excluding `build/`.

**Nothing in this repository's `.kh` files uses a category, and that is a fact about the tree only.** Zero of the **739** `tp {name} mt …` declarations across **315** files write a subtype keyword in any of the three parameter positions; the scan pattern matches any group entry whose type is `sc`, `ab`, `cp`, `mt`, `in` or `tp` and returns nothing. Zero `vr` declarations type a variable with a category, and zero capsule fields are typed with one. **2** `tp {name} sc` declarations exist under `modules/`, both inside a method body and both in this folder's own probes ([`bootstrap/repeat.kh`](./bootstrap/repeat.kh) at `:25`, [`bootstrap/compose.kh`](./bootstrap/compose.kh) at `:20`). The tree also holds **654** `ab` and **45** `cp` declarations. **Withdrawn 2026-10-03:** the sentence that headed this finding, "Nothing assumes the capability, and nothing contradicts it". It made an absence in the residue of a failed attempt read as a position taken — as though the tree could assume or contradict something — and the owner has ruled the code under `modules/**` neither evidence nor a premise. Sources never written in this language's final syntax would return the same result for every construct. The counts stay, as a description; no option below rests on them.

**The witnesses to the shape are comments, and one of them spells the category as an English word.** [`modules/computer/adt/protocol/listeners.kh`](../../../../modules/computer/adt/protocol/listeners.kh) at `:3` and `:6` writes `// OnAbsent(call scope) (err Error)` and `// OnPresent(call scope) (err Error)` above `tp OnAbsent ab` at `:4` and `tp OnPresent ab` at `:7` — a parameter typed `scope`, a word the grammar does not have, above two abstractions. [`modules/process/operation/protocol/listeners.kh`](../../../../modules/process/operation/protocol/listeners.kh) at `:8` and `:12` carries the same two signatures inside the retained Go block. The one declaration anywhere in the tree that puts a branch body in a type-level argument is a test fixture, and it names a capsule in every signature including the two whose owner is an abstraction ([`emit.test.ts`](./tests/emit.test.ts) at `:15`, `:23`, `:29`, `:33`, `:35`, `:39`) — which [`docs/khayyam/abstraction.md`](../../../../docs/khayyam/abstraction.md) at `:101` refuses, as [`sc-in-signature.md`](./sc-in-signature.md) at `:88` and `:102` record.

**What the tree retains of the Go it was ported from: fifty-four declarations of a parameter that stands for a kind.** `54` generic `type …[…]` declarations survive in the migration comment blocks of `45` `.kh` files, and **8** of those are *union* constraints, which is the Go form for "any type of one of these kinds": [`modules/math/protocol/number.kh`](../../../../modules/math/protocol/number.kh) at `:9-11` (`type Number interface { Integer | Float }`), [`modules/math/protocol/ordered.kh`](../../../../modules/math/protocol/ordered.kh) at `:9-11` (`Integer | Float | ~string`), [`modules/math/integer/protocol/integer.kh`](../../../../modules/math/integer/protocol/integer.kh) at `:9-11` (`Signed | Unsigned`), and five more under [`modules/math/`](../../../../modules/math/) and [`modules/math/integer/protocol/unsigned.kh`](../../../../modules/math/integer/protocol/unsigned.kh) at `:10`. Those files carry no Khayyam declaration at all beyond the comment. Around them the tree holds a nominal answer — [`modules/math/protocol/operations.kh`](../../../../modules/math/protocol/operations.kh) declares `tp Operations ab` at `:13` and then `tp Operations_Math_Decimal ab` at `:15` with four methods at `:16-22`, and **320** distinct abstractions carry such a monomorphised-pair name — which is [`docs/khayyam/polymorphism.md`](../../../../docs/khayyam/polymorphism.md)'s own answer stated as sources (`polymorphism.md` at `:98`, `:229-233`). **What is withdrawn from this finding, and it is the whole of its argumentative half:** the inference, previously labelled as such, that the port's answer is "evidence that the need for one is real and has been paid for in declarations". Go generics left behind in a comment are the residue of an attempt to develop these ideas in another language that did not succeed, and the owner has ruled them neither evidence nor a premise; the monomorphised naming is likewise not evidence about what this repository needs. **What remains is a description of the tree, and the finding that survives it is the one above this paragraph:** a category position is unspeakable today because the frontend refuses every subtype keyword in every type position with `keyword-as-identifier`, and that is a fact about this toolchain's own code, measured with programs written for the purpose. Whether a parameter standing for a kind is wanted is the owner's question, and this document does not answer it from the tree.

### The options
Each is stated with what it costs in the grammar and the frontend, what it costs a reader, what it forecloses, what it makes expressible that nothing does today, and what it says about whether categories are kinds of things or merely grammar. None is recommended; the owner decides.

**(α) The category written directly — `(branch sc)`, `(abstract ab)`.**
*Grammar:* one slot of one construct gains a second accepted form, and the seven keywords stop being reserved words in that slot alone — `in` and `tp` are declaration keywords rather than categories, so the rule must say *which* subtype keywords the position admits, which is a sentence nothing carries.
*Frontend:* `core/src/sr.ts` (a parameter's type must be able to say it is a category), `core/src/parse.ts` (accept it), `core/src/frontend.ts` (a category is not to be looked up in the visible-name table), `core/src/body.ts` if the position may also appear in a body's `vr`; then in this target `emit.ts` and `program.ts`, because both look a parameter's `type` string up as an owner name; then the display contract, whose `subtype` role states that a subtype keyword "names a position, not a kind" ([`display.json`](../../display/display.json) at `:150`) and whose `type-reference` role is defined as "A Type in a type position whose category and origin this file does not state" ([`display.md`](../../display/display.md) at `:63`) — a category in a type position is a type position whose category *is* stated, so one of the two role statements has to move.
*Reader:* one construct more; a reader learns that a signature may name a kind as well as a type, and that `(branch sc)` and `(branch BranchBody)` differ in kind rather than in what they hold.
*Forecloses:* nothing that exists; it adds a form. It does, however, make `(self sc)` and `(branch cp)` writable unless the rule excludes them, and each is a decision.
*Expressible:* a parameter that stands for every value of a category, including values no declaration names — which is the one thing the sources' shape cannot currently say.
*Says:* that a category is a kind of thing a signature may name. That is a second-order claim the base layer has never made.

**(β) A named abstraction the language declares — `(branch BranchBody)`.**
*Grammar:* nothing. A capsule or an abstraction is nameable where a capsule is expected ([`abstraction.md`](../../../../docs/khayyam/abstraction.md) at `:110`), and the sources' one working measurement is written this way.
*Frontend:* **nothing.** Measured: the accepted row above, which is this shape with no change to any file.
*Reader:* a reader must know that a declared abstraction stands for "any branch body" and that a named capsule per site satisfies it — which [`encapsulation.md`](../../../../docs/khayyam/encapsulation.md) at `:95` already requires of every callback-shaped requirement, so the shape is one the reader meets elsewhere.
*Forecloses:* the declared type is satisfied by nothing but itself where substitutability is the point — a position naming a capsule forfeits [`abstraction.md`](../../../../docs/khayyam/abstraction.md) at `:48` and `:137`. A position naming a *declared abstraction* keeps both, which is the difference between this option and naming a capsule.
*Expressible:* substitutable branch bodies, a library an organization may mandate, and nothing that is not expressible today by declaring the abstraction. **Inference:** this option's whole gain over "do nothing and declare a capsule" is the one missing sentence — what relates a declared abstraction to the `sc` the grammar produces, which [`sc-in-signature.md`](./sc-in-signature.md) at `:169-183` names as D4 and drafts as the base layer declining to relate them.
*Says:* nothing about categories at all. It is the option that leaves that question exactly where it is.

**(γ) The category is nameable as an ordinary type — `sc` and `ab` become types the language declares.**
*Grammar:* a new declaration would have to exist, or the existing keywords would have to be declared types by fiat, and both are additions rather than acceptances.
*Frontend:* nothing, and that is the trap. Because a parameter's type is a bare string looked up as a name ([`core/src/sr.ts`](../../core/src/sr.ts) at `:66-69`, [`core/src/frontend.ts`](../../core/src/frontend.ts) at `:68-75`), a *declared* `ab` would flow through every existing check without a change.
*Reader:* a reader must hold that a category is also a type, that `ab` in a type position is a type and in a declaration is a keyword, and that a value of it exists.
*Forecloses:* the base layer's sharpest sentence. [`docs/type.md`](../../../../docs/type.md) at `:126` says the categories "are not subtypes of each other — they are different ways a Type can fulfill its role", at `:129-137` refuses to read them as a hierarchy, at `:191` puts all four "on one level with none nested inside another as a subtype", and at `:209` repeats it. Declaring a category as a type with instances makes it a fifth thing that *is* a Type, and the relations table at `:193-198` — which already relates the categories only by `satisfies`, `attaches to`, `extends` and "commonly used within" — would need a row saying that a declaration is an instance of its category. The document's own answer to "why only four categories" (`:211-216`) is about categories, not about kinds, and does not survive being read as a claim about kinds.
*Says:* that categories are things. **Inference:** this is the only option here that the base layer must be *rewritten* for rather than extended.

**(δ) The category is read from the argument, and the signature keeps naming a type.**
This is not among the options the brief lists; it is what the repository's own code already does, and the documents half-claim. [`method.md`](../../../../docs/khayyam/method.md) at `:71` says the compiler "distinguishes the three from the callee's signature", and [`khayyam.md`](../../../../docs/khayyam/khayyam.md) at `:131` says the position is satisfied "by a type itself passed as a type-level argument" — which, read strictly, is a *call-site* claim: what arrives is a scope or a method, and the declaration that admits it is the callee's own. The backend already works that way ([`emit.ts`](./src/emit.ts) at `:222-242`, `:234-242`), and no signature change is involved.
*Grammar:* nothing. *Frontend:* nothing new; a check that what a parameter declares matches what a body's binding can be at that argument is a check this target can make today and has not been asked to.
*Reader:* nothing new to learn, which is the option's whole appeal.
*Forecloses:* it leaves the position's meaning dependent on the callee's *body*, and [`khayyam.md`](../../../../docs/khayyam/khayyam.md) at `:177` says a construct earns a place in the grammar when a program's well-formedness turns on it — which here it does, so the sentence is owed to the language even under this option rather than left to a linter.
*Expressible:* what (α) expresses, less legibly — the reader of `(branch BranchBody)` cannot tell whether a scope may be passed without reading the callee's body, whereas the reader of `(branch sc)` can.
*Says:* that a category is a property of a *value*, read where the value appears, and need never be named. **Inference:** this is the reading most consistent with [`type.md`](../../../../docs/type.md) at `:186`, which places a realization's choices with the realization rather than with the category, and with [`display.json`](../../display/display.json) at `:150`.

**Which the documents' vocabulary favours, and how strongly.** Strongly against (γ): three sentences in the base layer state the contrary in categorical terms, and one sentence in the toolchain's own display contract says a subtype keyword names a position rather than a kind. Moderately for (β): two sentences already grant it ([`abstraction.md`](../../../../docs/khayyam/abstraction.md) at `:109-110`), and the owner's preference of 2026-10-02 is recorded in [`target.md`](./target.md) at `:98`. Mildly for (α): the grammar already names each category with a keyword in the declaration slot ([`khayyam.md`](../../../../docs/khayyam/khayyam.md) at `:70`, `:208`), and a second slot for the same word is a smaller conceptual step than it looks — but the counterweight is that [`khayyam.md`](../../../../docs/khayyam/khayyam.md) at `:47` says the seven words "name the declaration forms rather than names", which is a claim about *where* they are allowed that (α) would have to rewrite. Weakly for (δ), on the ground that it is the only option whose premise (`type.md` at `:186`) a document already asserts; weakly against it, because it makes a program's meaning depend on a body a reader may not open.

### The question behind the owner's sentence
The owner's stated want is broader than the branch body: *"later we want to make this an official rule in Khayyam so that, for example, `(abstract ab)` may also be permitted to be declared"* and *"can we pass an abstraction around between layers regardless of what it is?"*. Three things follow, and only the third is a surprise.

**A parameter whose type is "any abstraction" has no usable contract, so no variance rule is needed.** **Evidence:** an abstraction reaches an artifact as a marker carrying its own name and nothing else — [`program.ts`](./src/program.ts) at `:207-208` records it in `composition` and `exports`, and [`emit.ts`](./src/emit.ts) at `:529-531` writes `export const IF = { type: "IF" }`. No methods, no requirements, no signature. So what the callee holds is a name. The only power that name carries in the language is the qualified call on methods the abstraction itself declares — `IF.OnTrue(…)()` — which the language admits, since a method attaches to any type including an abstraction ([`method.md`](../../../../docs/khayyam/method.md) at `:29`, `:73-74`, [`khayyam.md`](../../../../docs/khayyam/khayyam.md) at `:80`), and which this target refuses, because a contract emits nothing ([`program.ts`](./src/program.ts) at `:308`) and the emitter has no dispatch over capsules it did not see ([`emit.ts`](./src/emit.ts) at `:117-121`, recorded at [`target.md`](./target.md) at `:60`). **Inference:** a callee handed an abstraction can do exactly two things with it — compare its identity, and call methods whose names it must already know. There is no contract to be a subtype of and therefore nothing for a variance rule to constrain. Variance would be needed only if the parameter's type were a *set* of abstractions rather than one, and the model has no such set: the categories are refused a hierarchy ([`type.md`](../../../../docs/type.md) at `:129-137`) and subtyping in Khayyam runs one way only, from a satisfying capsule to an abstraction ([`polymorphism.md`](../../../../docs/khayyam/polymorphism.md) at `:157-191`, `:142`).

**What "an abstraction passed between layers" actually needs is two things the model already has and no new syntax.** The abstraction as a named value is what [`khayyam.md`](../../../../docs/khayyam/khayyam.md) at `:131` already calls a type-level argument and what [`emit.ts`](./src/emit.ts) at `:128-139` already resolves as a marker; the qualified call on it is what a method on an abstraction already is. **Inference:** the owner's wish is not blocked by the absence of a category position — it is blocked by the absence of a *spelling* for passing a type, and that is a smaller question than the one the brief poses. And the base layer already underwrites the wish on its own terms: a parameter has an identity distinct from the method that declares it, and is reasoned about on its own terms ([`type.md`](../../../../docs/type.md) at `:47`) — which is the whole of what "a value of whatever abstraction" would mean.

**Is this question new?** **Evidence:** searching the open questions, it is a known question under a name the brief did not expect, twice over, plus a third under a fourth. [`target.handoff.md`](./target.handoff.md) at `:146` carries "What a signature writes for a scope, and whose signature may write it" — the `sc` half — and its `Path` at `:150` says in so many words that "writing the category keyword also needs the frontend to accept it where it reads a name, which is a new accept row in `core/` and possibly a new refusal label", which is (α) already costed. [`target.handoff.md`](./target.handoff.md) at `:164` carries "A method in an argument position has no type" — the `mt` half, whose `Anchor` at `:166` is the very line the measurement above returns. [`language-gaps.md`](./language-gaps.md) at `:150` carries the *vocabulary* for the generalization already drafted: a term defined as "a name of one of the four Type categories written where a signature writes a type" — every category, not the two the `sc` case needs. And the general question itself — whether a category may be declared in a signature position *at all*, `ab` included — is in no document and no handoff. **Inference:** the question is new as a question about categories and known as a question about a spelling; the answer for `sc` is already ruled ([`sc-in-signature.md`](./sc-in-signature.md) at `:26-33`), the answer for `ab` is the owner's recorded preference, and the answer for `cp` nobody has asked. The repository's nearest existing name for the whole subject is *Category Name*, and it is a term drafted for two categories' sake in a document whose subject is one of them.

### The drafts
One set per option. Where a draft already exists elsewhere in this folder, this document says so and drafts only what is new, so that no two documents become authorities over one sentence. **None of this text is applied, and nothing under `docs/` is edited.**

**A1 — (α): which subtype keywords a type position admits, and what a category there means.**
*Document and section:* [`docs/khayyam/khayyam.md`](../../../../docs/khayyam/khayyam.md), section **Type** — a bullet added after the one at `:70`, which is where the subtype slot is defined.
*Proposed text:*
```
- The subtype keyword names the declaration's category and is otherwise a keyword rather than a name. Where a signature writes a type, it may write a category instead: the position then admits every value of that category rather than the instances of one declared type, and the category is written as the keyword itself — `(branch sc)`, `(handler mt)`. `in` and `tp` are declaration keywords rather than categories and are never admitted there. What a category admits is what the category is: a code scope is inert until a method drives it, and a category a signature names is not a declaration of anything.
```
*Why this text and not a weaker or stronger one.* It makes the two claims (α) needs and no others: which keywords qualify, and what the slot then means. It excludes `in` and `tp` because they are not categories — [`type.md`](../../../../docs/type.md) at `:212` says a fifth category needs a burden of proof, and `in` would be a sixth thing in that namespace on no evidence. Its last sentence is what keeps (α) from smuggling in (γ): a category in a position admits values, it does not declare one. A weaker text — "a signature may name a category" — leaves `in` in by accident and leaves the reader unsure whether the category is a type. A stronger one, admitting `cp`, makes `(branch cp)` writable and every capsule an argument to every position, which is a decision nobody has taken.
*What it unblocks:* `(abstract ab)`, the case the owner names, and the whole of [`language-gaps.md`](./language-gaps.md)'s I-E — whose text at `:141` and `:147` covers `sc` and `mt` and would need this sentence beside it rather than instead of it.
*What it changes elsewhere:* [`method.md`](../../../../docs/khayyam/method.md) at `:71` gains the `cp` and `ab` cases; [`type.md`](../../../../docs/type.md) gains the sentence the base layer currently lacks about a category being nameable — the same relation question [`sc-in-signature.md`](./sc-in-signature.md) at `:99` records as unaddressed; [`khayyam.practice.md`](../../../../docs/khayyam/khayyam.practice.md) at `:57` gains a row; the display contract needs a role or a redrawn one, as [`display.json`](../../display/display.json) at `:150` and [`display.md`](../../display/display.md) at `:63` show.
*Language, toolchain, or naming:* the **language** for the bullet, and the **toolchain** for everything downstream of it.

**A2 — (α): the term.** Already drafted at [`language-gaps.md`](./language-gaps.md) at `:150`. **Inference:** it needs one amendment rather than a new draft — "one of the four Type categories" must survive the decision to admit `cp` and `ab`, and the term must say *what it is written as*, which that sentence does not. **Naming.** The owner, since a term in a rules-adjacent position names the position for every document that later uses it.

**B1 — (β): what a declared abstraction means in a position, and what the compiler checks.**
*Document and section:* [`docs/khayyam/abstraction.md`](../../../../docs/khayyam/abstraction.md), section **A Concept Is an Abstraction; a Concrete Instance Is a Capsule** — a third item after the two at `:108-110`, which enumerate the owners and their admissible types.
*Proposed text:*
```
3. A signature may also name a category of the language, as a declared abstraction of the language stands for one — a branch body handed to a method is written with a named abstraction, and the code scope a body declares is a value of it. What the abstraction requires is what the compiler checks: the body a caller passes must provide what the abstraction names, and nothing about how it is written reaches the signature.
```
*Why this text and not a weaker or stronger one.* It is the sentence that does not exist and that every other sentence in this option leans on: [`sc-in-signature.md`](./sc-in-signature.md) at `:47-51` shows that naming a capsule produces a type with no stated relation to the `sc` the grammar produces, and its D4 at `:169-183` drafts the base layer declining to add that relation. This text adds the relation from the other side — the language's, in the document that already owns "which of the two a signature names". A weaker text restates `:110` and leaves the relation unstated; a stronger one would say a scope *is* an instance of that abstraction, which is a claim about conformance no document supports and which would make the abstraction's satisfaction structural over a construct the compiler reads as body text.
*What it unblocks:* the owner's preferred spelling, the control-flow library's first signature ([`target.md`](./target.md) at `:98`, [`target.handoff.md`](./target.handoff.md) at `:149`), and the sources' commented witnesses becoming declarations ([`listeners.kh`](../../../../modules/computer/adt/protocol/listeners.kh) at `:3`).
*What it changes elsewhere:* [`method.md`](../../../../docs/khayyam/method.md) at `:71` — the sentence D2 at [`sc-in-signature.md`](./sc-in-signature.md) at `:126-141` already drafts is the edit there, and this text must be drafted with it or the two contradict; [`docs/type.md`](../../../../docs/type.md) at `:193-198` gains the relation row D4 declines, or the two documents will disagree about whether the model relates a scope to anything.
*Language, toolchain, or naming:* the **language**, and a drafter's.

**G1 — (γ): the sentence that would have to become true.**
*Document and section:* [`docs/type.md`](../../../../docs/type.md), section **Type Categories Are Not a Hierarchy** — the first sentence at `:129` amended.
*Proposed text, stated as what it must say rather than as a recommendation:*
```
The categories are the kinds a Type may take, each named by a keyword the grammar declares, and each a Type in its own right whose instances are the declarations that take it.
```
*Why this text and not a weaker or stronger one.* **Inference:** this is the weakest form that makes (γ) work, and it is already stronger than the paragraph it would sit in. It contradicts `:126` ("they are not subtypes of each other"), `:191` ("none is nested inside another as a subtype") and `:209`, and it makes `ab` a value whose type is `ab`, at which point [`khayyam.md`](../../../../docs/khayyam/khayyam.md) at `:62`'s rule — one concept, one name, two declarations an architecture error — has `ab` claimed by the language for two things at once. A weaker text that said only "a category may be written in a type position" is (α), not (γ), and would leave the base layer untouched; the difference between (α) and (γ) is exactly this sentence. **This is why (γ) costs nothing in code and everything in the base layer, and the cost is not a phrasing.**
*What it unblocks:* `(abstract ab)` and `(branch cp)` with no further decision, and nothing the needs in the sources.
*What it changes elsewhere:* [`display.json`](../../display/display.json) at `:150` (a subtype keyword would then name a kind), the relations table at [`type.md`](../../../../docs/type.md) at `:193-198`, and every sentence that reads a category as a position.
*Language, toolchain, or naming:* the **language**, and squarely the **owner's**: it is a claim about what a category *is*, and no phrasing makes it smaller.

**D1 — (δ): whose job it is to tell the three apart.**
*Document and section:* [`docs/khayyam/method.md`](../../../../docs/khayyam/method.md), section **Type-level arguments for `sc` and `mt`** — the first two sentences of `:71` replaced.
*Proposed text:*
```
A method's influencing group may receive a `vr`, an `sc`, or an `mt`. What each position admits is decided by the declaration that occupies it and by the method that writes it: a variable of the declared type is an instance, a scope is a branch body, and a method is a method, and a compiler distinguishes the three where the argument is read rather than where it is declared. What the position is written as is a named type, and what fills it is what the callee's declaration admits.
```
*Why this text and not a weaker or stronger one.* It is the only draft here that changes no spelling, and it is the only one that makes [`khayyam.md`](../../../../docs/khayyam/khayyam.md) at `:177` do its work explicitly: a construct earns a place in the grammar when a program's well-formedness turns on it, and here it turns on whether the argument's category matches what the callee does with it. A weaker text would leave `:71`'s claim — that the *signature* tells the compiler — standing while the backend tells it from the argument ([`emit.ts`](./src/emit.ts) at `:234-242`), and the two would go on disagreeing. A stronger one would name the categories in the position, which is (α).
*What it unblocks:* the mismatch between [`method.md`](../../../../docs/khayyam/method.md) at `:71` and what this toolchain implements — the measurement above found the signature contributes nothing to the decision, so under this option the language states what the code already does and the sentence stops being owed.
*What it changes elsewhere:* [`khayyam.md`](../../../../docs/khayyam/khayyam.md) at `:131`'s "by the type itself" is the sentence this text makes consistent; the check that a category matches the declaration becomes a rule of this toolchain's level, and [`bundles/khayyam/rules/type-as-argument/type-as-argument.md`](../../rules/type-as-argument/type-as-argument.md) at `:15` and `:24` — which already disclaim the grammar's subject — is where it would sit.
*Language, toolchain, or naming:* the **language** for the sentence and the **toolchain** for the check.

### Open questions each option leaves
Per option, the questions that survive it, and which of them only the owner can settle.

**(α) leaves:** which subtype keywords the position admits — `cp` in particular, and the answer decides whether `(branch cp)` is a way of writing "any capsule" or a hole; whether a category-typed parameter may also appear in a *field*, a *`vr`*, or an abstraction's composition block, all three of which the frontend shares one reader with ([`core/src/parse.ts`](../../core/src/parse.ts) at `:169-176`, [`core/src/body.ts`](../../core/src/body.ts) at `:105-112`) and all three of which are one decision rather than three; and whether the base layer gains a sentence about a category being nameable ([`type.md`](../../../../docs/type.md) has none, and its relations table at `:193-198` has no row for it). **Owner-only:** the first two — each is a statement about what the language admits, and each forecloses a spelling. The third is the owner's too, because it is a claim about the category.

**(β) leaves:** whether a declared abstraction is a *closed* set of branch bodies or an open one — whether a method may be passed where a branch body is expected — which the language's own position already answers three different ways (`sc` and `mt` at [`method.md`](../../../../docs/khayyam/method.md) at `:71`, a `vr` of a capsule or abstraction at the same line); whether the branch body's abstraction composes with the intent abstraction a method presents itself through — [`Abstraction_Implements`](../../../../modules/computer/abstraction/protocol/implements.kh) at `:3` — and how it is documented, which [`docs/khayyam/khayyam.practice.md`](../../../../docs/khayyam/khayyam.practice.md) at `:57` does not say; and whether a *scope* satisfies it structurally, given that a scope is body text and not a unit declaration. **Owner-only:** the last, and the first where it bears on the control-flow library's owner.

**(γ) leaves:** everything (α) leaves, and in addition whether a category may be both a keyword and a declared type, what `docs/type.md`'s hierarchy paragraph becomes, and whether `ab` as a type collides with a program that wants to name a concept `ab` — which [`khayyam.md`](../../../../docs/khayyam/khayyam.md) at `:62` makes an architecture error rather than a rename. **Owner-only:** all of it. This option has no drafting that is not a ruling first.

**(δ) leaves:** how a compiler is to check that an argument's category matches what the callee's declaration admits, when the callee's declaration is prose in its own words rather than a rule — which is a check no tool in this repository performs, and which [`target.md`](./target.md) at `:60` records as this target's boundary for the `ab` case; and whether a reader who has only the signature is expected to know what the callee accepts. **Owner-only:** the second, because it is a claim about what a program means, which is the grammar's subject.

**Across all four, one question is the owner's and nobody else's:** whether a signature is a place where a program states what a value *is*, or a place where it states what a caller may hand over. Everything the sources and the compiler do says the second is what the position has always been ([`khayyam.md`](../../../../docs/khayyam/khayyam.md) at `:131`, [`emit.ts`](./src/emit.ts) at `:234-242`), and the owner's sentence — a category that "may be declared in that position" — says the first. That is a different language, and the difference is worth settling before a spelling is chosen.

### Implications
Adopting (β) as the owner's preference states would change nothing in [`core/`](../../core/) and nothing in the sources, and would add one sentence to [`docs/khayyam/abstraction.md`](../../../../docs/khayyam/abstraction.md) and one relation question to the base layer. That is the cheapest set of consequences in this document, and it is cheap for a reason worth naming: the language already has the construct that carries the branch body and already has a mechanism that makes one declared type stand for many — abstraction conformance, structural, checked where the abstraction is expected ([`abstraction.md`](../../../../docs/khayyam/abstraction.md) at `:81`, `:137`). The only thing missing is that nothing relates it to the `sc` the grammar produces, and that relation is a sentence.

Adopting (α) would change the semantic representation, three files in [`core/`](../../core/), two in this target, and one role statement in the display contract; and it would still leave the branch body's abstraction undeclared for anyone who prefers (β), because the two are not exclusive — which is worth noticing, because the owner's question is phrased as if they were. Adopting (γ) would change no code at all and would require [`docs/type.md`](../../../../docs/type.md) to be rewritten at its most quoted sentence. That asymmetry — the option that is cheapest to implement is the one the base layer can least hold — is the most useful thing this measurement has found, and it is the same asymmetry the research addendum found about `sc` itself: the repository's cost is not evidence about the language ([`docs/khayyam/khayyam.research.001.md`](../../../../docs/khayyam/khayyam.research.001.md) at `:250`).

What this document does not do is choose. It states that a signature names a declared type today and cannot name a category in any form the grammar admits; that the needs in the sources none of the four and has already paid for the need a fourth way; that the owner's larger question is known in two halves and drafted in one term; and that the deeper question behind it — an abstraction passed between layers — turns out not to be a variance question at all but a missing spelling for passing a *type*, which is a smaller thing than the one asked and is the one I would put in front of the owner first.
