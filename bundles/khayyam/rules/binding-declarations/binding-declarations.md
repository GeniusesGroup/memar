# Khayyam Rule — Binding Declarations Live in a Side File
Khayyam's rules live one rule per folder under [`bundles/khayyam/rules/`](../README.md), and this is the rule for where a binding's declarations are written and what such a file may hold. It is a governance rule of this repository, not a grammar requirement: [Khayyam → Minimal Legislation](../../../../docs/khayyam/khayyam.md#minimal-legislation-a-principle) at `:177` puts "which prose a file carries" and "where a declaration may be written" in the tool's own rules, on the ground that one realization may treat them differently from the next.

## The rule
A **binding** is an agreement two parties hold about something, with no third party introducing it. What crosses the agreement may be a route to a capability in another language, a shape of data and behaviour reached over a network, or a place in memory that one party writes and another reads. The concept and its three crossings are modelled at [`modules/computer/binding/binding.md`](../../../../modules/computer/binding/binding.md); this rule states only where such declarations are written and what else may be beside them.

- **The declarations live in a side file whose name carries the fact.** A binding's declarations are written in a companion unit named `<base>.bindings.kh` — the facet key `bindings`, plural, following the `observers`/`mutators` precedent the sources already write — beside the unit whose method reaches the crossing. The name is a discriminator, not a label: the run already addresses a supplied implementation by the URI of the unit that declares it and then by the name the artifact exports it under ([`run.ts:32-34`](../../targets/js/src/run.ts)), so a unit holding only bindings is answerable by its name alone, where a unit holding a type's own behaviour is not.
- **The file holds nothing else.** A unit so named carries binding declarations and no other content: no capsule of its own, no abstraction a caller composes, no arithmetic or text conversion belonging to the type it sits beside. The obligation is [the file-layout rule's](../file-layout/file-layout.md) first bullet — each `.kh` file expresses one coherent responsibility — and the binding's responsibility is the agreement, so a second thing in the file is by definition a second responsibility.
- **A file not so named may not hold a binding.** A body-less method on a concrete capsule written in a unit that is not named `<base>.bindings.kh` is not a binding. It is a provision awaiting an implementation, and the repository holds 59 of them — 51 the port's own arithmetic and duration conversions under [`modules/math/`](../../../../modules/math) and [`modules/time/duration/`](../../../../modules/time), 8 this toolchain's own probes — none of which was meant to be supplied by another party. The remedy for one of those is a companion unit that says so, not a section of the unit the type already has.
- **The stronger half is not this rule.** Refusing a body-less method on a concrete capsule anywhere but in a companion unit so named is a decision about how firmly a tool insists on a given form, and its first application would be 59 findings in the sources rather than one file. This rule states what the name means; an organization that wants the refusal configures its own Linter for it, per [Linter → Configuration and override](../../../../modules/computer/linter/linter.md#configuration-and-override).

## Why it exists
One file does one thing, and the toolchain reads a unit's identity to answer what a declaration is for. The classification this repository actually performs is by **the owner's kind**, not by a unit's contents: [`parseBlock`](../../core/src/parse.ts) at `:219` yields no body when no `{` follows the third group, and [`program.ts`](../../targets/js/src/program.ts) at `:289` reads that absence as the whole difference between a compiled method, a contract, and a supply. So a body-less method on a concrete capsule is the provision form whether or not another party supplies it — which is why the port's own conversions read as provisions nobody made, and why the owner's archived `Beep` would be classified the same way as `FromString`. The name is the one discriminator available that the compiler's classifier and the run's address already agree with.

Two structural reasons keep a binding out of a unit that does other work, and neither is taste. An implementation is handed to the unit that declares it "whatever unit imported it" ([`run.ts:18-19`](../../targets/js/src/run.ts)), so a binding written in the reaching party's own unit would put that party's code and the other's provisions at one address. And [`link.ts:9-12`](../../targets/js/src/link.ts) says a link must restate what the unit declared or leave its contracts stated nowhere, so a unit that may be replaced must contain nothing that is not replaceable.

The precedent is the repository's own: 30 `<base>.locale.<lang>.kh` files (23 `.locale.eng.kh`, 5 `.locale.per.kh`, 1 `.locale.en.kh`, 1 `.locale.fa.kh`), 100 `<base>.observers.kh`, and 9 `<base>.mutators.kh`, with [Documentation → File Naming](../../../../modules-plugable/knowledge/documentation/documentation.md#file-naming) stating the dot as the separator between a companion's facet key and its base name, and [file-layout.md:14](../file-layout/file-layout.md) already naming `<base>.observers.kh` beside the base it belongs to.

## Keep it or drop it
An organization may name its companion whatever it likes and keep every declaration in one unit per program, and dropping this rule costs only the recoverability of the correspondence: with one shared unit, every crossing is keyed at one URI and the correspondence has to be recovered from exported names alone, which is a spelling coincidence of exactly the kind the separation of the two vocabularies exists to remove. The rule is a layout convention and changes nothing a program means; the refusal half, which this rule deliberately does not state, is an organization's to configure.

## What this rule does not claim
- It does not claim the language reads a file's name. Nothing in [Khayyam → Method](../../../../docs/khayyam/khayyam.md#method) or the compiler protocol consults it, and a second toolchain need not.
- It does not claim a body-less declaration's name, signature, or meaning belongs to the declaring party. The language states nothing about how a foreign function is reached, by the owner's ruling, and the drafted intervention that would have said it was withdrawn rather than deferred — see [Language Gaps → I-B](../../targets/js/language-gaps.md#i-b--whose-name-a-body-less-method-carries--withdrawn-by-the-owners-ruling). This rule does not restate it.
- It does not claim that the correspondence is recorded by this rule's name. What the name buys is that a unit is *findable* as a place where bindings are declared; how the correspondence between one party's declaration and the other party's side is recorded is unowned, and that gap is real.
- It does not claim a unit so named must exist. The rule names what such a unit holds and does not require it, so an owner may write one before the crossing it will carry is known.
- It does not claim anything about the file-layout rule's other subjects — file size, declaration order, or one abstraction per protocol file — which it cites and does not restate.
- It does not claim the sources' 59 unmeant provisions are a defect of this rule. They are a consequence of the body-less spelling the language states ([Khayyam → Method](../../../../docs/khayyam/khayyam.md#method) at `:89`), and applying this rule to them is a decision for the folders that own them.
