# Khayyam Rule — Scope Visibility Handoff
Open state for [scope-visibility.md](./scope-visibility.md). See the repository's [documentation-handoff.md](../../../../modules-plugable/knowledge/documentation/handoff/handoff.md) for what a handoff is.

## Status
Active — drafted 2026-10-03 on the owner's ruling of the same date: a scope's block may refer to any name visible where it was declared; its own variables are not visible outside, because that scope may never execute; and Khayyam does not permit a name to change even at `in` level, two identical names meaning faulty development that the language does not participate in.

## Placement
The Rule is in this catalog rather than in a concept's module because its subject is name resolution in the language, and a program may satisfy every other Rule in this catalog and still violate it — a program that reads a variable declared in a scope outside that scope is a different program, not a differently written one. That is the test [Rule → Which Module a Rule Belongs To](../../../../modules/process/rule/rule.md#which-module-a-rule-belongs-to) states, and it is the answer to [Khayyam → Minimal Legislation](../../../../docs/khayyam/khayyam.md#minimal-legislation-a-principle) at `:177` and `:181`. The category is named at [Type → Scope — Type as Semantic Boundary](../../../../docs/type.md#scope--type-as-semantic-boundary) at `:181`, which is the concept document that would own the claim if a concept owned it.

## Withheld, and why
- **The claim was not written into `docs/khayyam/`.** The language documents do not state a `sc` block's reach, and the research companion records the statement as owed: [`khayyam.research.001.md:444`](../../../../docs/khayyam/khayyam.research.001.md) names "the reach **and its edges** — read, write, sibling invisibility, and the fate of `return`" beside the inertness at [`khayyam.md:129`](../../../../docs/khayyam/khayyam.md#scope). That folder is not this session's to write. The Rule therefore cites the Scope topic and the research record for the debt rather than pretending the language already says it.
- **Nothing contrary was found in `docs/khayyam/`.** The audit that preceded this session removed the statements that would have conflicted, and what remains supports the ruling: [`variable.md:159`](../../../../docs/khayyam/variable.md#variable-scope-and-visibility) says a method-body variable is not accessible outside the method, [`variable.md:167`](../../../../docs/khayyam/variable.md#variable-scope-and-visibility) says an imported name is the name the declaring file gave it, and [`encapsulation.md:95`](../../../../docs/khayyam/encapsulation.md#closures-as-implicit-capsule-syntax) is about closure *syntax*, which the same research record at `:392-393` says must not be read as a prohibition on a `sc`'s reach. Reported rather than edited, per the constraint that `docs/khayyam/` is not this session's.
- **The fate of `return` was not stated.** The research record lists it as one of the four edges, and a `return` inside a `sc` is a claim about mid-scope exit that `docs/modules/process/control-flow.md` holds as ordinary control flow and that no language document states. The Rule leaves it open rather than deciding it.

## Open Questions
- **The fate of `return` inside a scope.** Whether a `return` written in a `sc` block leaves the enclosing method and what a halt does with a scope's own bindings are the two edges of the owed statement this Rule does not make. The protocol's registered topic at [`control-flow.md:152`](../../../../modules/process/control-flow/control-flow.md#topics-to-be-developed-here) is halting semantics, and the language document that owes the reach statement is the language's owner's.
- **Whether the language document's statement lands, and what this Rule then is.** If the claim is written into `docs/khayyam/` at `:129`, the Rule becomes its executable form and the citation tightens from the research record to the Scope topic itself. If it is not written, this Rule is the only statement of the condition in the repository, which is a worse place for it to be and is recorded here rather than presented as a solution.
- **Whether the frontend resolves a body's declarations.** [`frontend.ts:38-77`](../../core/src/frontend.ts) resolves at unit level only, and [`body.ts:13-23`](../../core/src/body.ts) carries a body's commands without positions or any scope structure, so a visibility check over a body would need the frontend to walk commands rather than declarations. That is code work in [`bundles/khayyam/core/`](../../core/), which is not this session's, and whether the check is wanted is the toolchain owner's.
- **Whether the duplicate-name case is one check or two.** The Rule states that a name is declared once, which covers a repeat inside one block and a nested block's name against the name around it. Whether a tool refuses both as one condition or reports the first and leaves the second is a check's design, and the language makes no distinction between them.
- **Whether `in` is the only other edge.** The Rule says a name does not change "at `in` level or anywhere else", which covers the file-level case `variable.md` already owns for imports. Whether a method's own signature parameters are visible to a `sc` block inside its body is settled by construction — they are the enclosing method's — and is recorded here only because the Rule's wording reaches it.
