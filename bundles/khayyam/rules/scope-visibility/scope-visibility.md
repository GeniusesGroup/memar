# Khayyam Rule — Scope Visibility
Khayyam's rules live one rule per folder under [`bundles/khayyam/rules/`](../README.md), and this is the Rule for the names a `sc` block may use and the names it takes with it when it ends. It is a rule about the language rather than about this repository's toolchain or its conventions: whether a name resolves is what decides what a program means, so [Khayyam → Minimal Legislation](../../../../docs/khayyam/khayyam.md#minimal-legislation-a-principle) at `:177` places a condition of this kind in the grammar — a construct earns a place there "when its existence, its resolution, or its observable behavior turns on it" — and `:181` makes the test the one this Rule answers, whether turning the condition off would change what a program means rather than how well a codebase is kept. It is a governance rule reported per declaration and enforced by no tool today; what the frontend does and does not check is under [What this rule does not claim](#what-this-rule-does-not-claim).

## The rule
- **A scope's block uses the names that were visible where the scope was declared.** A name a `sc` block refers to is one the place that declares that scope already supplies — its own declarations and what its `in` declarations bring in. This is the whole of the block's reach outward, and it is the same reach the enclosing method has. Reaching *inward* is the block's own: a nested block's names are its own.
- **What a scope's block declares ends with that block.** A `vr` declared inside a `sc` block is not visible after it, because the block may never execute — [Khayyam → Scope](../../../../docs/khayyam/khayyam.md#scope) states that a code scope is inert until a library-provided method drives it — and a value read where its declaration did not run is a value no line of the program wrote on the path that reached the read. Nothing outside the block reads such a name, and nothing outside the block's own nested blocks does either.
- **A name is declared once.** Two identical names in one block are a fault in the development rather than a shadowing the language permits, and the same holds for a nested block's name against the name around it and for a name an `in` declaration carries against a local declaration of the same name. Khayyam does not permit a name to change, at `in` level or anywhere else: [Variable in Khayyam → Variable Scope and Visibility](../../../../docs/khayyam/variable.md#variable-scope-and-visibility) states that an imported name is the name the declaring file gave it, and this Rule says the same of a name the source itself writes.

## Why it exists
The owner's ruling is the whole of it, with three reasons that travel with it. In several other languages a variable created inside an `if` scope may share its name with an unrelated variable outside, which the owner does not approve of; Khayyam does not permit a name to change even at `in` level; and two identical names mean the development is faulty, and the language does not participate in faulty development. The Rule is written as three instructions rather than as that reasoning because the reasoning is the owner's and the conditions are the language's, and a catalog Rule states what holds.

The category already says where such a condition lives. [Type → Scope — Type as Semantic Boundary](../../../../docs/type.md#scope--type-as-semantic-boundary) at `:181` defines a Scope as "a Type that delimits a semantic boundary within which names, relationships, ownership rules, and visibility constraints are established", and names "a local algorithmic block (as used by `if`, `loop`, `goto`)" among the category's realizations. Visibility is therefore not an incidental property of a code scope in this language; it is what the category is for, and a condition about it is a condition about Khayyam's Scope. [Type → Scope](../../../../docs/type.md#scope--type-as-semantic-boundary) also says the realizations sit at different levels, which is why the Rule speaks of a `sc` block and not of every boundary a program may draw.

The inertness makes the second bullet an argument rather than a preference. A scope is inert until a library-provided method drives it (`khayyam.md:129`), so the block's declarations are the declarations of a region whose execution is conditional, and a name that outlived the region would be a name whose value is undefined on every path that did not run it. That is the same reason [The Error → ADT composition](../../../../modules/process/error/error.md#adt-composition--the-full-adt-family-at-the-canonical-level) cannot be read past its contract: what a value means on a path that did not produce it is a question for the type that owns it, not for the source.

This repository's own JavaScript target already realizes the reach this Rule states, which is the evidence that the shape is the language's and not one backend's invention. [`emit.ts:47-50`](../../targets/js/src/emit.ts) says it in its own words — "a `vr` and a scope come from the commands themselves; a nested scope's names are its own" — and [`emit.ts:64-78`](../../targets/js/src/emit.ts) builds one `Block` per scope and writes each `declare` into the block that encloses it. A `sc` block's names are already its own at the point of emission; what is missing is that nothing checks it before that point.

## Keep it or drop it
An organization does not keep or drop this Rule, because its subject is the language's and a second organization writing Khayyam meets it without ever reading this catalog — that is what makes it a condition of the language rather than a governance Rule, and the difference is the one [Rule → Which Module a Rule Belongs To](../../../../modules/process/rule/rule.md#which-module-a-rule-belongs-to) draws. What an organization configures is how firmly a tool refuses it, whether the refusal is an error or a report, and whether it extends the same condition to a case the language leaves open. What no organization may do is accept a program that reads a name outside the scope that declares it while keeping the language the same: that is not a relaxed Rule, it is a second meaning for one source.

## What this rule does not claim
- **It does not claim the toolchain enforces any of it.** [`frontend.ts:38-77`](../../core/src/frontend.ts) builds its visible set from a unit's own declarations and what its `in` declarations bring in, and checks nothing inside a method body; a body's commands are read by [`body.ts:13-23`](../../core/src/body.ts) and never examined for visibility at all. A second declaration of one name in one block is written by [`emit.ts:67`](../../targets/js/src/emit.ts) with `set`, which replaces the earlier cell rather than refusing, so today the duplicate case is silent. Turning this Rule into a check is code work in the frontend and is not this session's.
- **It does not restate a language document, because none states it.** The language documents carry the inertness of a code scope (`khayyam.md:129`) and the two scopes a `vr` may be declared at ([`variable.md:155-159`](../../../../docs/khayyam/variable.md#variable-scope-and-visibility)), and say nothing about a block's reach. [`docs/khayyam/khayyam.research.001.md:444`](../../../../docs/khayyam/khayyam.research.001.md) records that the statement of "the reach **and its edges** — read, write, sibling invisibility, and the fate of `return`" is owed beside that inertness. This Rule states the read, write, and sibling edges; the fate of `return` inside a scope it leaves to the document that owes the statement, and no document in `docs/khayyam/` was edited to carry any of this.
- **It does not say what a name declared in a block is initialized to, or how it obtains its instance.** [`variable.md:157`](../../../../docs/khayyam/variable.md#variable-scope-and-visibility) sends initialization to the type's own behavior for a file-level variable and the same holds here; the Rule is about which names are visible, not about what a visible name holds.
- **It does not claim a `sc` may be written only in a method body.** That is the [code scope placement rule](../scope-placement/scope-placement.md), which is a rule of this toolchain, and this Rule does not move it.
- **It does not claim the sources comply, and the sources were not measured for it.** Every `.kh` file under `modules/` was searched for a `sc` declaration and two were found, both this toolchain's own probes — [`bootstrap/compose.kh:20`](../../targets/js/bootstrap/compose.kh) and [`bootstrap/repeat.kh:25`](../../targets/js/bootstrap/repeat.kh) — so the library sources exercise this Rule nowhere today. That is a measurement of where `sc` blocks are written, not a finding about names.
