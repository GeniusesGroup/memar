# Khayyam Rule — Declaration Rename Handoff
Open state for [declaration-rename.md](./declaration-rename.md), the rule that renames one declared type everywhere the language binds its name. It is applied by [`bundles/khayyam/rename/rename.ts`](../../rename/rename.ts) as `node rename/rename.ts --name OLD --to NEW [--declaration PATH:LINE] [--residue] [--samples N] [--report PATH] [--root PATH] [--exclude PREFIX] [--language NAME] [paths…]`, and that file is now wiring only: it registers the Khayyam binding and hands it to the declaration-rename service at [`modules/computer/identifier/services/rename/`](../../../../modules/computer/identifier/services/rename/), which owns the corpus, the plan, the report, the write, the gate, the command and the exit codes. What is Khayyam's stayed here — [`khayyam-binding.ts`](../../rename/khayyam-binding.ts), which reads `core/` and nothing else. The mechanism has therefore moved twice, both times for the same reason: out of `targets/go/` because the four rules the Go bridge applies rewrite Go residue and this one rewrites Khayyam, and out of this module because the service is not any language's ([the module's README](../../../../modules/computer/identifier/README.md#the-seam-what-a-language-hands-the-service)). A run is dry unless it is given `--write`, and the report names every place it would rewrite and every place it would not, so what is left open here is what that report cannot answer about a name. See the repository's [documentation-handoff.md](../../../../docs/documentation-handoff.md) for what a handoff is.

## Open Questions

### Does the seam hold for a second language, and what does it cost the first?
- State: the split is made and one binding exists. `Binding` in [`occurrences.ts`](../../../../modules/computer/identifier/services/rename/occurrences.ts) is the whole of what the service knows about a language: the places that bind a name, the reader for text the language does not itself read, and the check that says whether a rewrite still means anything. A run with no binding registered is refused, and so is a `--language` nothing answers for and a process with two registered bindings and no `--language` — deliberately, because two definitions of what a token is are two languages. The costs paid so far: a language's reader is reached through an interface rather than called directly, so its Test lives beside the reader rather than beside the service, and a change to either side's shape is a change to both. Nothing yet has been shown to need the seam's second user, and one binding is not evidence that the interface is the right shape.
- Next: a second language, or an owner's ruling that the service is premature. The first would settle the interface by use; the second is a legitimate answer and would put the mechanism back beside the one language that has it.
- Question for the owner: is this module's abstraction settled enough to invite a second binding, or should it stand as one service until a second language asks for it?

### What does a Go-block occurrence mean when the name is only a substring there?
- State: in the default mode the Go residue entries are raw-text occurrences, because the Khayyam scanner reads no token inside a `/* */` block, so an entry may be a substring of a longer Go identifier — `PacketTarget` is reported alongside a bare `Target` rename. `--residue`'s `residue_sites` is matched on whole identifier tokens rather than on raw text, which is what keeps the substring out of it; the reader that supplies those tokens is the subject of the next question. Both sets appear in the report, and the rule states the distinction rather than leaving a reader to infer it from the mode. The two names the mode and the report section carry were `--go-residue`, `go_sites` and `go_left` until the mechanism moved: the service may not name a port's language or a compiler's stage, so they are `--residue`, `residue_sites` and `residue_left` now, and the binding supplies `go-residue` as the name the mode is reported under.
- Next: the ruling named below. Until it is given, the two modes stand as the rule states them, and a reader who needs a site rather than an entry reads `residue_sites`.
- Question for the owner: should the default mode report raw-text occurrences at all, or report nothing and leave a Go block entirely to the opt-in mode? The first costs a reader who has to know which entries are substrings; the second costs the reader who never asks for `--residue` and so never learns that the residue still spells the old name.

### How far is the residue mode from the Go lexer it no longer has?
- State: the mechanism stood inside `targets/go/` and read the residue with the Go lexer, over the Python tool's own reader of block extents. Moved out of the target for the reason [khayyam.handoff.md → Decisions](../../khayyam.handoff.md) carries, both of those imports went with it: block extents now come from `core/src/scan.ts`'s own block-comment handling, and tokens inside a block are the identifier shape `scan.ts` already applies. Measured on the pre-rename sources, that is the same ten Go sites the Go lexer found, on the same lines, columns and lengths, and the move out of this module did not change it — the second move put that reader in the binding rather than in the service, and a reader that moved unchanged cannot have changed its answer. It is narrower in three corners: a Go rune literal and a backquoted raw string are read as their characters rather than as literals, and a comment marker inside a raw string costs that whole block — eleven blocks over nine files, none of which names a declaration in the sources, so no site is hidden here. Two mechanisms make the identifier case exact rather than lucky, and both are in the binding's header: a block's extent is the smallest tail the scanner reads whole, and the part of a line the scanner skips at a character it does not read is read again from where it stopped.
- Next: a body of source that leans on the three corners. The rule reports every block it could not read whole rather than guessing at it, so what is needed is a decision about whether a corner that cannot be read should be a refusal rather than a skip — the same question the walk mismatch below raises, and it deserves one answer for both.
- Question for the owner: is a block the reader cannot account for reported-and-skipped the right shape, or should the rule refuse the file the way it refuses an already-refused one?

### Why does one declaration's tokens not walk?
- State: [`modules/memory/reference/weak.kh`](../../../../modules/memory/reference/weak.kh)'s line 16 is reported as a walk mismatch and nothing in it is planned, rather than guessed at. The rule refuses to plan a declaration whose token walk disagrees with `referencedTypes`, which is the safe direction — a rename planned from a walk the representation does not confirm is a rename the language never bound — but the cause is undiagnosed. The [module handoff](../../khayyam.handoff.md) records `weak.kh` as a pre-final-syntax artifact, which may or may not be the whole story. The report's field is `walk_mismatches` and its printed line says `walk mismatch`, both of which are the binding's words rather than the service's; the shared contract describes the field as the places where the binding's own reader disagrees with itself, and kept the names so that a report written before the move still reads.
- Next: the diagnosis itself — what the walk finds at that line that `referencedTypes` does not — since the refusal stands either way and only the cause decides what repairs it.
- Question for the owner: whether `weak.kh` is what the module handoff says it is, a file carried over from before the syntax was final, because that is the difference between a source file to curate and one to leave.

### Should a file named after a declaration be renamed with it?
- State: the rule reports the mismatch (`target-race-event.kh` against `Target_Race_Event`) and never renames. The folding it compares is the declaration name against the file's own base name, so a directory named after its concept does not match every file beneath it — which is why this is a report rather than a plan.
- Next: a ruling on whether the rule offers the rename. Which spelling a repository gives a file belongs to the [import address rule](../import-address/import-address.md), so a tool that renamed files would be choosing a convention rather than applying one.
- Question for the owner: is a file rename deliberately left to a person and to `git mv`, or should the rule carry it as an opt-in second step?

### What is the tool's answer when two declarations share a name?
- State: today it reports both owners and plans nothing, and `--declaration PATH:LINE` picks one, which the run then checks against the sources.
- Next: the ruling named below. Until it is given the selector stands, and either answer leaves the remedy with the [qualified names rule](../qualified-names/qualified-names.handoff.md) rather than here.
- Question for the owner: should a collision instead be refused outright, as the architecture error the language calls it, so that the qualified-names rule owns the remedy rather than this rule offering a selector?

## Anticipated Work
- **Every place the rule leaves alone is another subject, and the enumeration is already built.** The report names each occurrence it did not rewrite — a comment, a name inside a longer identifier, a parameter spelled like the declaration, a method body, a qualified reference, a file name — so a later chat does not hunt for them; what is anticipated is a rule or an owner ruling taking one of them, and this rule staying a rename of one declaration rather than widening into each.
- **A qualified reference stays a report until a qualifier means something.** `pkg.Type` is reported and not rewritten because what a qualifier denotes is undecided; when that ruling lands — the open question the [unbound type name rule](../unbound-type-name/unbound-type-name.handoff.md) carries — this rule has a case to revisit rather than a gap to fill, and the case is already written into the report.
- **The general rule engine, which this rule's second move is an argument for.** Now that the mechanism is shared rather than one language's, an engine that applies rules by each rule's stated condition would put back the one thing both moves cost: the check for whether a rename would be refused beside `commented-generic-bindings` or `go-clue-residue`, which was visible only through an invocation the two shared. The separation is structural rather than checked — nothing is refused beside anything any more, because nothing is applied together — and both [`rules/README.md`](../README.md) and [khayyam.handoff.md → Decisions](../../khayyam.handoff.md) carry the engine as the arrangement that would settle all five rules at once.
