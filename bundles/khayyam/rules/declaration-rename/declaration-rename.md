# Khayyam Rule — Declaration Rename
Khayyam's rules live one rule per folder under [`bundles/khayyam/rules/`](../README.md), and this is the rule for renaming one declared type everywhere the language binds its name. It rewrites source; it is applied by `node services/rename/rename.ts --name OLD --to NEW [--write]`, which is [`bundles/khayyam/services/rename/rename.ts`](../../services/rename/rename.ts) — this rule's own invocation, in this module. The mechanism that invocation reaches is [`declaration-rename.ts`](../../services/rename/declaration-rename.ts) beside it, and the binding that answers for Khayyam is ([How the run decides that an occurrence names *this* declaration](#how-the-run-decides-that-an-occurrence-names-this-declaration)).

## The rule
The rule is one run about one declaration. Given the name of a declared type, it writes the new name at every place in the repository where the language binds *that* name to *that* declaration, and at no other place.

Its members, in the rule model's terms:

| Member | What this rule declares |
| --- | --- |
| Identity | `declaration-rename` |
| Subject | One declaration — a `tp` or `vr` that owns its name, named by `--name` and, where the sources hold two, by `--declaration PATH:LINE` |
| Condition | The name's binding at a place is the declaration this run is about, as the language's scanner and reader say it |
| Consumes | The `.kh` units of a repository, read whole |
| Produces | The same units with the places rewritten, and a plan a reader can review before anything is written |
| Enforcement | `source-rewrite` |
| Scope | `repository` — a name is bound across files, so no unit's rewrite is knowable alone |

A run is dry. It prints, per file, how many occurrences it would change and shows sample old→new pairs; `--report` writes the whole plan as JSON. `--write` is what writes anything, and a write that would make any file newly refused by `analyze()` ([`core/src/frontend.ts`](../../core/src/frontend.ts)) is refused and nothing is written: a rename that breaks the build is worse than no rename.

### What counts as a place that binds the name
Five, and the report names which one each site is:

- **`declaration`** — the name at the declaration itself.
- **`inclusion`** — the name in a `tp {name} in "{path}"` or `vr {name} in "{path}"` line. The path is a URI and is never rewritten ([Khayyam → Import Mechanism (`in`) → The path is a URI](../../../../docs/khayyam/khayyam.md#import-mechanism-in)).
- **`signature`** — the name as the owner type or as a parameter type of a method's three groups ([Method in Khayyam](../../../../docs/khayyam/method.md#method-structure)).
- **`field`** and **`composition`** — the name as a capsule field's type, or as a bare member of a `cp` or `ab` block ([Capsule → Capsule Structure and Privacy](../../../../docs/khayyam/encapsulation.md#capsule-structure-and-privacy), [Abstraction → Abstraction Composition](../../../../docs/khayyam/abstraction.md)).
- **`vr-type`** — the name as the type of a `vr` declaration.

### What the run leaves alone, and says so
The report's `left_alone` and `unread` sections carry every occurrence of the name that is not rewritten, each with what it is, because "not rewritten" is only useful next to "why not":

- **A comment.** A `//` line, a `/* */` block, and a string literal are not tokens ([Khayyam → Comment Forms](../comment-forms/comment-forms.md)), so the scanner reads no token there and the run rewrites nothing. Prose naming a type is documentation, and the [comment policy rule](../comment-policy/comment-policy.md) is where this repository keeps it — an author's sentence, not a binding. Every such place is reported so that the prose needing an edit is visible in one list.
- **A name inside a longer name.** An identifier is a whole token ([Khayyam → Keywords → Language Keyword in a Glance](../../../../docs/khayyam/khayyam.md#language-keyword-in-a-glance)), so `Target_Race_Event` is a token that is not `Target`, and `Net_PacketTarget_2` is not `PacketTarget`. Both are reported as `part-of-longer-identifier`, and every declaration whose own name carries this name is listed under its own heading, because such a declaration is a separate rename and its own run.
- **A parameter spelled like the declaration.** A parameter names a value; it is reported as `parameter-name` and not rewritten.
- **A method body.** The reader reads a method body as opaque text ([The module handoff → M1 scope boundaries](../../khayyam.handoff.md)), so what an identifier inside one binds is undecided. It is reported as `method-body` and not rewritten.
- **A qualified reference.** `pkg.Type` is accepted without a binding check and its resolution is undecided ([Unbound Type Name → Open questions](../unbound-type-name/unbound-type-name.md)), so it is reported as `qualified-reference` and not rewritten.
- **A file name.** A file whose own name is the declaration's name, spelled with any case and separators, is reported. No file is ever renamed: which spelling a repository gives a file is the [import address rule](../import-address/import-address.md)'s owner, and a tool that renamed files would be choosing a convention rather than applying one.

### The two modes, and what each covers
Both are named in the run's output and in the JSON report, and the mode is never stamped into the source: a comment recording which run wrote a file is prose that drifts from the file. Each mode's label is handed to the mechanism together with the pass that fills it — `khayyam` with the binding, `khayyam+go-residue` with the residue pass — and the mechanism composes no name out of languages it does not hold. Those two are what this language and its second reader call themselves, written in [`khayyam-binding.ts`](../../services/rename/khayyam-binding.ts), and the run reports whatever it was handed.

- **`khayyam`** (the default) — the five places above. An end-of-file Go clue block is left as its own source, which is what [`renames.py`](../../targets/go/renames.py) does and what [Go Clue Residue](../../targets/go/rules/go-clue-residue/go-clue-residue.md) expects of a block that is later re-emitted.
- **`khayyam+go-residue`** (`--residue`) — the above, and the Go clue blocks too. A block's extent is the Khayyam scanner's own: `scan` reads a `/* */` comment as one run and refuses an unterminated one, so the block is where that reading says it is, and inside that extent the pass rewrites only what `scan` reads as a **whole identifier** equal to the name. For the identifier shapes the sources' residue uses — letters, digits, underscore — that is the Go-lexer-exact answer, and it is what keeps `PacketTarget` from matching a `Target` rename. **Resolves no Go binding**: a Go identifier that happens to spell the name inside a block is rewritten, because that is the spelling the residue carries and a stale spelling in the residue is read back out of it later. Every site is listed in `residue_sites` so a reader can accept each one. A block sealed by its sha256 is left whole and reported, the same discipline `go-clue-residue` holds for one; a block the scanner cannot read whole is left and reported.

  **What the mode therefore does not cover.** The block is Go text read with Khayyam's lexics, and the two languages disagree at the corners, so the report distinguishes what was read from what was not rather than letting the difference disappear in the move:

  - A Go **rune literal** is read as its characters and a **backquoted raw string** is read as Go text, where the Go lexer read each as one literal: a name inside either is rewritten here and would not have been there.
  - A **comment marker inside a raw string** is an opener to this scanner, so a block holding one is read as a comment to its end — left whole and reported rather than half-read. Across the sources, that is eleven blocks over nine files, and it costs no site, because none of them names the declaration; a body of source that did would be reported rather than guessed at.
  - A double-quoted string and a `//` or `/* */` comment are the scanner's own already, so a name inside either is *not* rewritten — the same answer the Go lexer gave.
  - The scanner takes the rest of a line with it when it meets a character it does not read, and a Go body is full of them (`*` alone is enough), so the block is read again from where the scanner stopped. A region it refuses even then is reported as unread.

  These are the costs of not re-implementing Go's lexical rules inside Khayyam's toolchain, and they are stated here because the Python version this moved from did have the Go lexer and its report carried no such gap.

The reason `renames.py`'s default is wrong here and right there is the caller: `renames.py` rewrites every source mechanically and leaves the residue alone because the residue is compared to the Khayyam side by name; a deliberate rename is about one declaration, and a residue that still spells the old name is a fact the repository will be read against. Hence a mode rather than a change of that rule's default.

### How the run decides that an occurrence names *this* declaration
Through the language's own machinery, in [`khayyam-binding.ts`](../../services/rename/khayyam-binding.ts) beside this rule's folder, asked in process by the service:

1. `scan` ([`core/src/scan.ts`](../../core/src/scan.ts)) says what a token is, so a comment, a block, and a string literal are not tokens and an identifier is a whole token.
2. `readUnit` ([`core/src/reader.ts`](../../core/src/reader.ts)) with `declaredName` and `referencedTypes` ([`core/src/sr.ts`](../../core/src/sr.ts)) says what each declaration declares and which type names it references, and [`referencePlaces`](../../core/src/references.ts) says where inside a declaration each of those names stands — for every form the reader produces a type for, the `vr` and `in` forms included, which `referencedTypes` itself carries no entry for. There is no second walk beside it that could disagree with the reader: the one that places a name is `core/`'s own, over the scanner's tokens and nothing else, and it decides placement and never binding. This run and the language server filter that one answer rather than each keeping a copy of it.
3. The binding: a name in a file is bound to a local declaration, or to the file behind the `in` that brings it, exactly as `analyzeImports` binds it ([`core/src/frontend.ts`](../../core/src/frontend.ts)) — because that is the analyser the write is checked against. An occurrence is planned only when that binding resolves to the file this run's declaration stands in.

There is no second definition of what a token is. Whether a place holds a name is the scanner's answer and the reader's, and both are asked in process rather than through a subprocess or a fallback path, so nothing this rule does can disagree with the toolchain it rewrites. The Go clue block is the one place two readers read the same source, and what each of them does not cover is stated under [the two modes](#the-two-modes-and-what-each-covers).

Where the reader lives and where the mechanism lives is this rule's own boundary, and it is stated once here: the **mechanism** owns the corpus, the plan, the report, the write, the gate, the command and the exit codes, and it asks rather than reads; the **binding** owns what a name means in Khayyam and hands the mechanism its places. That mechanism is the engine the [Revision contract](../../../../docs/modules/computer/revision.md) states once for every language toolchain; what that contract leaves to the shared contract it settles in its own *What Narrowed Elsewhere* section rather than restating here. Two consequences are visible from this rule's side. Every place the mechanism reports is a place the binding named, so `signature`, `comment` and `go-identifier` are that file's words and this one repeats them without knowing one. And what one unit of the sources is called, and which of them a run leaves alone, are the caller's facts: `node services/rename/rename.ts` supplies `.kh` and `bundles/khayyam/`, so the documented invocation reads exactly as it always has. Which of the mechanism's claims are the language's and which are this port's is classified in [`rename-management.md`](../../services/rename/rename-management.md), beside the mechanism.

### When the sources hold the name twice
The run **reports every owner and plans nothing.** `tp` and `vr` declarations own their name; an `in` only routes one, so a name brought into twenty files by `in` is still one declaration and the run names it. Two owners is a different matter: the [qualified names rule](../qualified-names/qualified-names.md) records that a collision is an architecture error the language names rather than a disambiguation problem ([Import Mechanism (`in`)](../../../../docs/khayyam/khayyam.md#import-mechanism-in)), so the rule refuses to pick one and asks for `--declaration PATH:LINE`, which it then checks against the sources. The `in` lines that carry the name are reported as `carried` in every run, because a route is a consumer too.

A name the sources already use for something else is refused before any plan: `--to EventTarget` against a body of source that declares `EventTarget` is the collision the [qualified names rule](../qualified-names/qualified-names.md) is about, and the run says where the name is taken rather than creating it.

## Why it exists
An abstraction is renamed by its owner's judgment, and every consumer of the name is a fact about the repository that no declaration records. Finding them by hand is the whole cost, and it does not scale past one abstraction: the worked case is `Target` in [`modules/process/event/protocol/event-target.kh`](../../../../modules/process/event/protocol/event-target.kh), whose rename to `EventTarget` reached three method signatures, a second declaration and its three methods, an importer's `in` line and its composition member, a file rename, and the Go residue of five further files — fourteen places across nine files, none of which the declaration site points at.

The name is what the language uses to bind a type across files ([Import Mechanism (`in`) → A name an `in` declaration includes is the name it declares](../../../../docs/khayyam/khayyam.md#import-mechanism-in)), so a rename is a language-level change and its consumers are enumerable by the same machinery that resolves them. This rule is where that enumeration is a rule rather than a habit, and it is a `source-rewrite` rule because a formatter is a rule that rewrites source ([The module handoff → Khayyam's rules live in `bundles/khayyam/rules/`](../../khayyam.handoff.md)) rather than a tool of its own.

## Keep it or drop it
An organization may keep the four unconditional rules and do renames by hand, may require a second reader to sign off on every `--write`, may forbid `--residue` so a residue is only ever rewritten by the port that produced it, or may replace the rule with the IDE's own rename refactoring and keep this one as the check that says how many places a rename would reach. Dropping it loses the enumeration, not the language.

### Why this is invoked over argv, and why it is invoked at all
A rule that rewrites source is a rule ([The module handoff → Khayyam's rules live in `bundles/khayyam/rules/`](../../khayyam.handoff.md)), and this one is invoked over argv because that is what the [no CLI or TUI decision](../../khayyam.handoff.md) carves out: build tooling is developer-side and is not the product's interaction surface, so a developer's one-off rename is a command and not an app. Were this rule's subject the product's own interaction — renaming a declaration in a reader's session — it would owe an app, and [`lsp/src/`](../../lsp/src) is where that would live. That much is unchanged by where the rule lives.

What has changed is **where the mechanism sits**, and the reason is the subject rather than the tool. The four source-rewrite rules the Go bridge applies rewrite **Go residue**: the clue block a ported file ends with, the Go member matched to its Khayyam counterpart, a Go method's generic binding. Their material is the port's and their reader is the port's, so `abstraction_bridge.py tidy --rule …` is how they are applied and where they die with the target, while the Rule documents that state them are filed by the module that owns their subject at [`targets/go/rules/`](../../targets/go/rules/README.md) — the tool owns the check, and the check's home is not the Rule's. **This** rule rewrites **Khayyam** — a declaration's name, at every place the language binds it — and the need to rename one outlives the port, the port's tooling, and the Go target folder that is scheduled for deletion. A rule that rewrites source is still a rule; a mechanism's home follows its subject. So the rule document stays in this catalog, which is not a target.

The mechanism has moved twice, and the second move is the one this rule now rests on. Out of the Go target first, because a need that outlives the port cannot live inside it. Then out of this module and back again: it was moved out on the claim that **at the level of tokens and identifiers a name has meaning that does not depend on any programming language** — the argument [Lexer → Domain and consumers](../../../../docs/modules/computer/lexer.md#domain-and-consumers) settles for the neighbouring mechanism — and a shared module was built for it at `modules/computer/identifier/`. That module was removed on 2026-10-04. The reason is not that the claim is false but that it was carried out one step further than the requirement reaches: every question this rule asks is a question about a **Khayyam declaration** — a `tp` or a `vr` that owns its name, routed by an `in`, colliding the way the language's import mechanism says it collides — and each of those is answered by `core/` already. A mechanism that must ask this language's own reader for every place it reports is not thereby language-neutral; it is this language's, with an interface drawn around it, and the interface bought a second copy of the walk that places a name rather than the one that already exists. So the mechanism is [`declaration-rename.ts`](../../services/rename/declaration-rename.ts), beside [`khayyam-binding.ts`](../../services/rename/khayyam-binding.ts) and the command [`rename.ts`](../../services/rename/rename.ts), and the invocation never changed: `node services/rename/rename.ts --name OLD --to NEW` reads the same in every one of these three homes.

What the moves cost is the one thing the four rules share and this one does not: a common invocation. `tidy --rule` remains how the residue rules are applied, `node services/rename/rename.ts --name OLD --to NEW` is how this one is, and there is no command that runs both. That is the honest price, and the alternative was worse in the other direction: a rule whose mechanism dies with the Go target, applied through a script that is on its way out. **Everything this project has developed as a script is provisional and is eventually to become real code in modules** — which includes the Go target's own tooling, and which is the standing reason a mechanism that has outlived two homes gets a third. The arrangement that would settle all five at once — a general rule engine that applies any rule of the catalog by its stated condition, beside `rules/` — is still unwritten; [`rules/README.md`](../README.md) and [the placement decision](../../khayyam.handoff.md) both carry that, and this rule is the second thing that has now had to be moved for want of it.

## What this rule does not claim
- It does not claim a new name is a good name. It moves one; whether `EventTarget` says what the abstraction means is the [qualified names rule](../qualified-names/qualified-names.md), the [identifier naming rule](../identifier-naming/identifier-naming.md), and the owner's call.
- It does not claim a name is one declaration's alone. It reports every other declaration that carries the name and refuses a body of source that holds two owners; deciding which module owns a concept is not naming.
- It does not claim that what it leaves alone needs no change. Comments, file names, URIs, method names, and qualified references are all reported with their places, and each is another rule's subject or the owner's.
- It does not claim the Go-residue mode resolves Go. It rewrites whole Go identifiers of that spelling over a known block extent and lists every one.
- It does not claim the four unconditional source-rewrite rules run beside it. `commented-generic-bindings` writes declarations that reference names no plan has seen, and `go-clue-residue` matches a Go member to its Khayyam counterpart by name, so neither can share a run with this one. That is now structural rather than a check: the two have no invocation in common, so there is no run that selects both.
