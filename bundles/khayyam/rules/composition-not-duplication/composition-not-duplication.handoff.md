# Khayyam Rule — Composition Not Duplication Handoff
Open state for [composition-not-duplication.md](./composition-not-duplication.md), the rule that a refinement of an abstraction is written as composition and never as a second declaration beside the abstraction it narrows. See the repository's [documentation-handoff.md](../../../../docs/documentation-handoff.md) for what a handoff is.

## Status
Active — drafted 2026-10-04 from two per-event-kind abstractions that a session wrote beside the general event contracts and that the working tree now carries as deleted: `Target_Race_Event` in `modules/process/event/protocol/target-race-event.kh` (beside `tp EventTarget ab`) and `EventListener_Race_Event` in `modules/process/event/protocol/event-listener-race-event.kh` (beside `tp EventListener ab`), each narrowing one influencing type of the general contract's methods. Both were committed and are removed in the working tree; neither is removed on this branch's history yet. The rule's normative claims are already in the language documents and in the toolchain's port-review decision; nothing in this folder states a claim the language has not made, and no decision about the rule's own placement has been recorded in [`khayyam.handoff.md`](../../khayyam.handoff.md), which is the owner's to write.

## Vocabulary
The name follows the catalog's own practice of naming a subject rather than a verdict: `composition-not-duplication` says what is compared — a refinement and a copy of it — and leaves the document free to say which is which. `abstraction-scaffolding` and `type-as-argument`, the two nearest siblings, are both named for what the Rule is about rather than for what it forbids, and this name does the same. Three alternatives were considered and refused: `narrowed-parameter` names one clause and not the other, and is a phrase from the language documents rather than a subject; `per-kind-abstraction` borrows a kind the corpus does not declare and would send a reader to a taxonomy; `abstraction-refinement` is the concept the rule governs, which makes it the language's term and not this folder's — and if the Rule were the language's, [Rule → Which Module a Rule Belongs To](../../../../docs/rule.md#which-module-a-rule-belongs-to) would put it in `docs/khayyam/` rather than here. No spelling of the concept is settled beyond this.

The corpus already had terms for the two halves and the Rule says so in its own body rather than claiming new names: the port review's second check ("a refinement is written as abstraction composition … rather than as a second interface beside the general one", [khayyam.handoff.md](../../khayyam.handoff.md)) is the condition, and the [qualified names rule](../qualified-names/qualified-names.md) carries the same claim for the naming case. The Rule is those claims applied as a standing condition; what it adds is the second half — that the narrowed declaration satisfies nothing — and the measurement.

## Measurement
Taken on 2026-10-04 over every `.kh` file under `modules/`, excluding `node_modules` and `build`: **1279 files, 747 `mt` declarations, 150 abstractions** (147 carrying a composition block, 62 of those composing exactly one abstraction, 3 carrying none). The command was a scan kept outside the repository:

```
python C:\Users\omid\AppData\Local\Temp\opencode\kh_shadow_scan.py .
```

It reads every declaration line with comments stripped, pairs method declarations by the segment of the name after its last `_` (so an owner-prefixed spelling still meets the bare one the [receiver method names rule](../receiver-method-names/receiver-method-names.md) gives it), and decides narrowing by composition alone: `S` narrows `T` when some `tp S ab { … T … }` exists in the corpus, transitively. **(B) Abstractions composed by exactly one other abstraction and differing from it only in narrowed influencing types — 0.** All 62 single-composition abstractions were examined; each either adds methods of its own (`Detector_Static ab { Detector }` at `modules/process/race/protocol/detector.kh:15` adds `AnalyzeVariable`; `Detector_Dynamic ab { Detector }` at `:23` adds `Enable` and `Disable`) or states a different set. The composition form is what the corpus already uses, which is why this count is zero and the Rule is a statement about a mistake the sources have made once rather than a description of a habit.

**(C) An abstraction re-declaring an inherited method with other types — 0.** For every `ab` composing another, no method name it declares exists on the abstraction it composes with a different signature. The composition blocks in the corpus add requirements rather than restate them.

**(D) Same operation on different receivers with differing influencing types, no relation required — 211 pairs.** This is the over-approximation a linter would face, and it is why the Rule's second clause is not a report. Beyond the `Register` registries: the numeric width families (`modules/math/integer/signed-16.kh:10` `I16_Equal` against `modules/math/integer/signed-32.kh:11` `I32_Equal`, and every pair among the ten width files under `modules/math/`), the per-type `Marker_Copy_*_CopyFrom` and `Marker_Clone_*_CloneTo` families at `modules/computer/adt/marker/protocol/copy.kh` and `clone.kh`, the `Container_*_String_Character_*` families under `modules/computer/adt/container/protocol/`, and one pair the [qualified names rule](../qualified-names/qualified-names.md) already records as one source declaration emitted twice — `modules/net/protocol/packet-target-2.kh:9` against `modules/net/protocol/packet-target.kh:9`. Each of these names one capability, not two, and a checker reading signatures has nothing in the signatures that says so.

**Validation against the state where the defect existed.** The same scan was run over a five-file reconstruction of the pre-deletion sources (the two deleted files beside the current `event-target.kh`, `event-listener.kh`, and `race/protocol/event.kh`). Count (A) returned **2** — the `EventTarget`/`DispatchEvent` pair and the `EventListener`/`EventHandler` pair — and count (D) returned **4**, the two `AddEventListener`/`RemoveEventListener` pairs included. The gap is the Rule's honest limit in one measurement: `EventListener_Race_Event ab` carried no composition block, so nothing in the corpus related it to `EventListener`, and a scan that decides narrowing only by composition edges cannot see that half of the mistake. The narrowed type was the wrong declaration's own claim, and a wrong declaration states nothing a checker can lean on.

## Placement and tier
Governance, scope repository, and the Rule is this repository's own: a program violating it is a program whose narrowed declaration satisfies nothing, which no other Rule in this catalog refuses, so turning the condition off changes no program's meaning — the test at [docs/rule.md:77](../../../../docs/rule.md#which-module-a-rule-belongs-to). It is filed here because its subject is Khayyam source read for what its declarations reach, which is the subject [comment-forms](../comment-forms/comment-forms.md) is the precedent for. The catalog's verdict table at [Which rules here are the language's own](../README.md#which-rules-here-are-the-languages-own) has no row for this Rule; this session was permitted one row in that index and did not edit the table. The verdict the Rule would receive there is **The repository's**.

**What a linter could check.** That a method declaration's influencing types differ from those of a same-named method on another receiver, and that the narrower side is related to the wider by a composition edge — count (A), which is cheap once declarations are parsed and the composition graph is built. That an abstraction's composition block lists a type whose methods it re-declares with other types — count (C), zero today. That a `tp X ab` has no methods, no importer, and no body where a same-named method elsewhere carries a narrowed type — the shape both deleted abstractions had, and the check the port review's first and third items ([khayyam.handoff.md](../../khayyam.handoff.md)) perform by hand.

**What it could not.** Deciding, from signatures alone, that the two declarations are one capability rather than two: 211 pairs to judge by hand against 4 to report. Distinguishing a deliberate per-kind contract from an accident — nothing in the source distinguishes them, and the `Register` registries show the false-positive rate of any signature-only test. Reaching a shadow written under a wholly different method name, which the pairing by name cannot see. And telling a reader that the declaration is inert: the diagnostic would have to say what the language has in place of the thing refused, which is the toolchain's own wording and not this Rule's.

## Open questions
- **Does this Rule reach a realization whose signature misses exact match, or is that the abstraction scaffolding rule's?** `Bool_FromASCII` at `modules/math/boolean/boolean.kh:28` takes `String` where `ASCII_Stringer_From` at `modules/codec/string/ascii/protocol/ascii.kh:25` requires `String_ASCII`, under a `//memar:impl` comment that names the protocol. It is the same exact-match clause and the opposite direction of difference, but it is not a second declaration beside anything. [Abstraction scaffolding](../abstraction-scaffolding/abstraction-scaffolding.md) already owns what tooling may do about a capsule that partially or wrongly implements an abstraction; whether the wrong-signature half belongs there, here, or in both is undecided.
- **Should a shadow with no same-named method be in scope at all?** Count (A) pairs by the segment after the last `_`. A per-kind contract whose methods were renamed along with it is invisible to it, and the corpus's own port produces such names. Whether the Rule says anything about a declaration that no other declaration's method name reaches is unstated.
- **Should anything report a violation, and at what tier?** Nothing does today, and the honest answer may be that the Rule's whole enforcement is a reader who finds it in this index — the position the [declaration order rule](../declaration-order/declaration-order.md) records for its own unanswered report. A report at governance tier is available at the cost of the 211-to-4 judgment above; a rewrite is not, since what to write instead depends on whether the second declaration was meant as a refinement at all.
- **Does the Rule say anything where no composition can express the refinement?** A composition block may name abstractions only ([What You Cannot Do](../../../../docs/khayyam/abstraction.md#what-you-cannot-do)), so a refinement whose narrower side is a capsule has no composition form. The Rule currently stops at the boundary and points at the [qualified names rule](../qualified-names/qualified-names.md); whether it should carry the case itself is undecided.
- **The port review's stale anchor.** [khayyam.handoff.md](../../khayyam.handoff.md) links `docs/khayyam/polymorphism.md#what-you-will-not-do-in-khayyam` for "the Go type parameters it carried have no Khayyam form". That section is now [What the Grammar Does Not Admit](../../../../docs/khayyam/polymorphism.md#what-the-grammar-does-not-admit), and the anchor resolves to nothing. The file is the owner's and was not touched.
- **The two removed declarations are named here as their files named them.** The deleted files declare `Target_Race_Event` and `EventListener_Race_Event`; `EventTarget_Race_Event` appears nowhere in the committed tree or in the deleted files themselves. The Rule cites the names the sources carry.

## Anticipated Work
- **Re-measuring is cheap and the scan is not kept.** Counts (A) through (D) are a parse of every declaration line plus a transitive closure over composition blocks; the script was written outside the repository and is not part of any module. Keeping it — as a test fixture, or as a governance check beside the [declaration order rule](../declaration-order/declaration-order.md)'s unkept measurement — would make these numbers reproducible after the next change rather than a claim in a handoff.
- **A view that showed every type beside the abstractions it composes would satisfy this Rule without any source changing.** Companion tooling already presents structure first, and the same question the [file layout rule](../file-layout/file-layout.md) raises for its own clause is open here: whether the Rule still says anything once a reader can see the composition graph without reading the blocks.
