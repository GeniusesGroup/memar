# Khayyam Rule — Composition Not Duplication
Khayyam's rules live one rule per folder under [`bundles/khayyam/rules/`](../README.md), and this is the rule for how a refinement of an abstraction is written. It is a governance rule of this repository, and it stands on claims the language documents already make: [Polymorphism in Khayyam → Subtyping Through Abstraction Extension](../../../../docs/khayyam/polymorphism.md#subtyping-through-abstraction-extension) holds that when abstraction `B` includes abstraction `A`, `B` is a subtype of `A` and any capsule conforming to `B` is automatically a subtype of `A` as well — the relation a refinement states is a relation between types, and composition is the form that states it; [Abstraction in Khayyam → Defining an Abstraction](../../../../docs/khayyam/abstraction.md#defining-an-abstraction) shows the form (`tp Error ab { DataType; Field_MediaType; ADT }`), which [What You Cannot Do](../../../../docs/khayyam/abstraction.md#what-you-cannot-do) makes legal precisely because a composition block may name abstractions and nothing else (`:100`). What is new here is neither claim: it is their consequence as a standing condition over the corpus, and the reason a reader needs it stated once. The port's own review already carries the same check as the second of its four ([toolchain handoff → *A transferred abstraction is reviewed and cleaned before it is committed*](../../khayyam.handoff.md)), where it governs one pass over transferred abstractions; this rule states it as a condition on every `.kh` file in this repository, in either direction of authorship.

## The rule
- **A narrowing of an abstraction is written as composition, never as a second declaration beside the one it narrows.** A race report is an event, and the language already says so at `modules/process/race/protocol/event.kh:8`:

  ```khayyam
  tp Race_Event ab {
      Observer_ThreadID
      Stack
      Event
  }
  ```

  The capability that dispatches events is stated once, with the general parameter, at `modules/process/event/protocol/event-target.kh`:

  ```khayyam
  tp EventTarget ab
  tp DispatchEvent mt (self EventTarget) (event Event) (err Error)
  ```

  What is not to be written beside it is a second contract whose only difference is the narrower parameter — `tp DispatchEvent mt (self Target_Race_Event) (event Race_Event) (err Error)`, together with the two listener methods beside it. That form states the same relation twice and gets less from it, because of the second clause.

- **A declaration whose only difference from an abstraction in the same corpus is a narrowed influencing type satisfies nothing.** [Abstraction Realization (Implicit Satisfaction)](../../../../docs/khayyam/abstraction.md#abstraction-realization-implicit-satisfaction) is explicit: a capsule satisfies an `ab` "if and only if it implements every method declared by that abstraction. For each such method, **the influencing-variable types must match exactly**, the influenced-variable types must match exactly or via covariant return …, and the receiver is the implementing capsule itself" (`:136`). Influenced types have a documented relaxation and influencing types have none; `Event` and `Race_Event` are not the same type, and no composition edge makes them interchangeable at a signature. The per-kind contract is therefore satisfied by no capsule, and it requires nothing of any, and the failure surfaces far from where it was written: satisfaction "is judged wherever an abstraction type is required — a `vr` declared as one, or a value passed to a position declared with one" (`:137`). The concrete cost is that `modules/process/race/protocol/detector.kh:8` composes `EventTarget` into `Detector`, so a capsule declaring only the per-kind methods can never be a `Detector`, and the reader is told so at a `vr` or a call, not at the declaration.

- **The narrower requirement is expressed by what the body does with the event, not by a second signature.** The general contract names the concept; the dispatch decides what an arriving event is. `modules/process/race/race-event-target.kh` is the form this rule asks for: `tp DispatchEvent mt (self Race_EventTarget) (event Event) (err Error)`, with the body's own answer to "is this a race report at all?" inside it. Nothing in the grammar states how a call through an abstraction is resolved and no syntax chooses a strategy ([Dispatch Strategy](../../../../docs/khayyam/abstraction.md#dispatch-strategy)); what a compiler does at a call site is the compiler's business, so a body that tests its argument needs no declaration to authorize it.

- **A refinement is a composition block on the narrowing abstraction, not a renamed copy of the general one.** Where the reference language instantiated a generic, the instantiated contract is not written; the general one is composed where the capability is needed. This is the same condition the [qualified names rule](../qualified-names/qualified-names.md) states for the naming case at [When qualification cannot separate two declarations](../qualified-names/qualified-names.md#when-qualification-cannot-separate-two-declarations), where one concept declared twice has one declaration that the other includes rather than a second name.

## Why this exists
Khayyam admits no type parameter to write — "no generic syntax … and no type parameter to write, so a reusable behavior is written as an ordinary method taking the abstraction it requires" ([What the Grammar Does Not Admit](../../../../docs/khayyam/polymorphism.md#what-the-grammar-does-not-admit)) — so a source that instantiates a generic leaves nothing in the language to write, and the nearest form an author can reach for is a contract per instantiation. That is what the port's review list names as its second check ([toolchain handoff](../../khayyam.handoff.md)), against the worked example of `Timer_Time_Timer_Status` written beside `Timer` and repeating `Init`, `Start`, `Reset`, and `Stop` under a second owner. The two abstractions removed from `modules/process/event/protocol/` in October 2026 were the same move on the event capability: `Target_Race_Event` beside `EventTarget`, and `EventListener_Race_Event` beside `EventListener`, each narrowing one influencing type of the general contract's methods.

What makes the mistake expensive is that it is silent. A per-kind contract is a well-formed declaration, the scanner reads it, nothing refuses it, and it is inert — the reader who trusts it believes a capability exists that no capsule can be passed as. The language's own argument is against it in the abstract: a signature owned by an abstraction names the concept, and "a contract that fixed a unit or a width would make every implementation of it exactly that resolution, for no gain in meaning" ([A Concept Is an Abstraction; a Concrete Instance Is a Capsule](../../../../docs/khayyam/abstraction.md#a-concept-is-an-abstraction-a-concrete-instance-is-a-capsule), `:108`–`:111`). The per-kind contract buys the resolution and loses the capability.

The corpus is a small-count claim, not a large one, and the numbers are this rule's evidence rather than its warrant. Over the 1279 `.kh` files under `modules/` (excluding `node_modules` and `build`), 747 `mt` declarations and 150 abstractions were scanned on 2026-10-04: **four** declaration pairs narrow an influencing type of a same-named method declared on another receiver, and **none** of the 62 abstractions that compose exactly one other abstraction differs from it only in narrowed influencing types. Every candidate, with file and line, and the method by which each was found and judged, are in this rule's [handoff](./composition-not-duplication.handoff.md) → [Measurement](./composition-not-duplication.handoff.md#measurement). One of the four is a real mismatch of this family (`Bool_FromASCII` at `modules/math/boolean/boolean.kh:28` against `ASCII_Stringer_From_FromASCII` at `modules/codec/string/ascii/protocol/ascii.kh:25`); the other three are pairs drawn from five registries across the corpus that share the trailing word `Register`. The sources are close to clean, which is why the rule is stated rather than described.

## Keep it or drop it
An organization may write a per-kind contract wherever it likes and remain conformant to the language — nothing in the grammar reads this rule's condition, and the second clause is a statement about what such a contract *reaches*, not a prohibition on writing it. What an organization may not do is read the language as requiring composition here, and this rule is what keeps that from being read here. An organization that drops it keeps its meaning intact and its cost: a duplicate contract still satisfies nothing, and the capsule that declares only the duplicate still cannot be passed where the general abstraction is required. This repository keeps the rule because that cost is invisible at the declaration and visible only where a value is refused.

## What this rule does not claim
- **It does not claim the language requires it.** Turning the condition off changes no program's meaning: a program violating it is a legal program that satisfies an abstraction nothing asked it to satisfy. That is this repository's own test — a Rule belongs to a language exactly when no program satisfies every Rule of that language's catalog and still violates this one ([Rule → Which Module a Rule Belongs To](../../../../docs/rule.md#which-module-a-rule-belongs-to)) — so the Rule belongs to this catalog and not to `docs/khayyam/`. Read literally the test's first half says the opposite here — a program violating this Rule violates no other Rule in the catalog necessarily, which is the form that calls a Rule the language's — and the catalog records that disagreement as unsettled ([catalog README → Which rules here are the language's own](../README.md#which-rules-here-are-the-languages-own)). This Rule does not claim to settle it; the second half is the one it rests on.
- **It does not claim anything checks it.** Nothing implements this condition; the duplicate declarations this session removed were found by reading, not by a tool. A linter could report a declaration that narrows a same-named method's influencing type relative to another receiver, and it could report an abstraction whose composition block is missing where a same-named method elsewhere carries a narrower type — what it cannot do is decide, from signatures alone, whether the two declarations name one capability or two. See the [handoff](./composition-not-duplication.handoff.md) → [Placement and tier](./composition-not-duplication.handoff.md#placement-and-tier) for the boundary as measured: the same scan that found four candidates over the whole corpus found 211 same-operation pairs with differing influencing types, of which the `I16_Equal`/`I32_Equal` width family, the `Marker_Copy_*_CopyFrom` per-type family, and the four `Register` registries are all distinct concepts that a report would have to leave alone. A checker could look at method name, receiver, the influencing types on each side, whether one type composes the other, whether one declaration's method set is a subset of the other's, and whether an `in` edge or a `//memar:impl` comment ties the two files; what it would have to ask a human is whether the second declaration is a refinement of the first or a second concept that happens to reuse the method's name.
- **It does not claim a capsule may not narrow for its own body's convenience.** A signature owned by a capsule may name a capsule, including itself ([A Concept Is an Abstraction](../../../../docs/khayyam/abstraction.md#a-concept-is-an-abstraction-a-concrete-instance-is-a-capsule), `:109`), and an implementation may be more precise than what it is asked for (`:111`). The narrowing this rule forbids is the narrowing of the *contract*, in a second contract.
- **It does not claim composition is available for every refinement.** A composition block may name abstractions only ([What You Cannot Do](../../../../docs/khayyam/abstraction.md#what-you-cannot-do), `:100`), so where the narrower thing is a capsule there is no composition to write, and whether the two declarations are one concept or two is the [qualified names rule](../qualified-names/qualified-names.md)'s question rather than this one's.
- **It does not restate the port review's other three checks** — a contract stated once in the file that owns it, a declaration that exists only because the reference instantiated a generic, and a name that repeats its owner ([toolchain handoff](../../khayyam.handoff.md)). This Rule is the second of them as a standing condition; where the third applies — the instantiated contract has no expressible refinement — that check removes what composition cannot state.
