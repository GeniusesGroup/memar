## Direction (owner, 2026-10-07)
- **A server, not a command line.** The command-line tool is set aside as the way to reach Memar's operations; the direction is a server. `main.kh` already carried the question as `TODO::: act as a server??`, and this is its answer. The command files the port carried — `init-cmd.kh` and `cmd.kh` here, and `module-cmd.kh` in [`computer/module/`](../../modules/computer/module/) and [`gui/`](../../modules-plugable/computer/ui/gui/) — are registration for that command line, and are to be replaced by the server's surface rather than ported as they are.
- **The files here become independent modules on a plan, not by porting.** What the files say may look useful, but each is to be reshaped into a good independent module in an order this handoff records as it is decided; until then a file here is a record of what `memar-go` did, not a commitment to do it the same way.
- **A bundle, not a module.** The server runs operations that modules own and owns none itself, so it sits under [`bundles/`](../README.md), the layer for what runs or aggregates modules, and `modules/` keeps only reusable modules. This answers where it goes in the layout: it has no counterpart under [`docs/modules/`](../../modules/knowledge/modularity/modularity.changelog.md#the-one-layout-for-both-trees-argument-is-dropped-with-the-specification-folder), and a part of it that a second bundle or project comes to need leaves for `modules/`.
- **`.agents/scripts/` rewritten in Khayyam, and soon.** The scripts are to move into modules as Khayyam realizations. Where each one lands follows its responsibility; this module receives only what only the server does.

## The MCP adapter is the server's first face (owner, 2026-10-18)
The owner chose option B of the study of a server (task 20261016-T095101Z-14276) with its recommended answers (task 20261018-T133019Z-4704): a thin local MCP server over stdio, importing the services `memar` already routes to, is the first face of this server, built before the server itself. The `memar` command and every path it is called by stay exactly as they are until the server's interface is final, because other chats and agents call it. Built in task 20261019-T111413Z-21136, provisionally under [`.agents/scripts/mcp/`](../../.agents/scripts/mcp/), run as `memar mcp serve`; it moves to `modules-plugable/net/mcp/` with the [guest adapter](../../modules/knowledge/modularity/placements.handoff.md#mcp-as-a-guest-adapter).

The design, which the files there carry in their own words:
- **Two processes.** `memar mcp serve` is a relay that reads and writes MCP's newline-delimited JSON-RPC and owns nothing else; a worker it starts holds the services, the tools and the content index. Before every message the relay compares a fingerprint of the Python under `modules/`, `bundles/` and `.agents/scripts/` (path, size, modification time); a change replaces the worker, which replays the client's `initialize`, and tells the client the tool list changed. The relay's own file is in the fingerprint, so a change to it is reported, but it takes effect only at the next start.
- **One tool per verb, generated.** The worker assembles the command line as `memar` does and makes each leaf verb a tool: its name the verb's words joined by `_`, its description the verb's own overview, its input schema from the verb's arguments. A call is turned back into the arguments the CLI would get and run through the same parser and runs, its stdout and stderr captured at the descriptor, so the answer is the CLI's byte for byte. `mcp` itself is not a tool. One input is not the CLI's: a tool's `stdin` is text, handed to the verb as UTF-8, while the CLI on Windows decodes its stdin in the console's code page, so a verb reading non-ASCII text from stdin (`content write`) gets it right through the server and garbled through the CLI (found by the review, task 20261019-T115931Z-16236); the CLI is left as it is, by the binding above.
- **Stateless per call** apart from what is asked to be kept: after each call the worker clears every `functools` cache of the checkout's modules and restores the scalar module globals they had when loaded.
- **The index kept, checked by stat.** `memar content find`'s index is kept in the worker per file, keyed by its size and modification time and checked on every call; a file modified within the last two seconds is re-read and compared by SHA-256, since a second write in the same tick leaves its stat unchanged. The corpus listing is re-read every call, so an added or deleted document is seen. A CLI call keeps nothing, as before. The sessions' files, read only with `--from sessions` (task 20261019-T170853Z-4740), are kept apart from the checkout's: a live one by its stat as a document is, an archived one by its blob id on the records branch, which changes whenever its bytes do; the branch is listed again on every call.
- **Registration at user level** in the agent apps `memar install` knows that have an MCP setting, never a project `.mcp.json`.

Task 20261016-T090123Z-23220's Q1 and Q2 are answered with it: the index is held in memory by the worker, persisted nowhere (Q1), and no write refreshes it; the reader checks by stat on every call (Q2).

## Open Questions
- **How the Memar server holds the services and its caches and serves overlapping calls.** The first version (a small process with up to four workers, each loading every service, behind the `memar` command) lowered the cost of a light call but not of `content search` and `content find`, and spends memory in proportion to the callers, so it does not reach the goal of cheaper answers and fewer resources. The task is task 20261020-T074539Z-16108; it reads the measurements and the design of the first version in tasks 20261020-T061848Z-22132 and 20261019-T111413Z-21136. Task 20261020-T063351Z-18380 met the first version from a sub-agent: `memar ai get-task-init-context` run from PowerShell printed nothing for over 120 s and answered from Bash with stdin from /dev/null, and one `--part 3` call failed with "the resident process stopped before it answered" and worked on retry (its report's Left open).
- **Whether the Khayyam toolchain's operations are served here.** The owner's leaning is one Memar server that also performs Khayyam's operations, so that there is no server specific to Khayyam. [`khayyam.handoff.md`](../khayyam/khayyam.handoff.md) already asks to "extend the Memar server" with a capability that generates a service from its name and path, and says no document defines that server; whether the language server under [`khayyam/lsp/`](../khayyam/lsp/) is one of this server's faces or stays its own program is undecided.
- **Where `app/` belongs.** Building, initializing, updating and deploying an application is a lifecycle, and [immutable infrastructure](../../modules/computer/runtime/immutable_infrastructure/immutable_infrastructure.md) specifies deployment; `app/` is parked here because the category that would own it is itself under review (see [Modularity Handoff → The category layout](../../modules/knowledge/modularity/modularity.handoff.md#the-category-layout-of-this-repository)).
- **Whether localization is a module.** `locale/services/details/` is a command printing a locale's details, and every module carries `locale.*.kh` files of its own. Whether a locale is a responsibility with its own module, or only a per-module concern, is not stated anywhere.
