# Compiler

## Abstract
A **compiler** is a system that consumes a language's specification and produces a target representation of a well-formed program. It is not identified with any one language, and it is not identified with any one target — native machine code, JavaScript, WebAssembly, and further backends are equally legitimate products of the same concept. The compiler is a separate system from the language it consumes: it is not part of what that language *is*. This document is Memar's protocol for that system: what a compiler may recognize (the language's own primitives, never a library's names as intrinsics), that it emits analysis events rather than special-casing libraries, that entry and lifecycle are configuration plus [Runtime](runtime.md) libraries rather than grammar, that where a declaration standing outside any operation's body receives its first instance is a freedom of the realization rather than a form of the grammar, that designated pure operations may be evaluated at compile time without privileging types, that a language's branch-grouping primitive is served to the flow-management modules built over it under stated guarantees about the body such a module receives — what it is, what driving it does, what it may see of its enclosing method, when two drivings differ, and when it stops meaning anything — while the mechanism that serves it is left to the realization, that how a call written against a declared specification is served is likewise a freedom — the closed/open distinction, inlining a concrete implementation, a generated dispatch structure, devirtualization, and the absence of any promise about cost — with the rationales a language's discipline gives and costs a compiler recorded as rationales rather than as obligations, and that it consumes the [Lexer](lexer.md) under that protocol's contract. A Khayyam-to-JavaScript compiler and a C compiler that honors the same rules are two realizations, not two concepts.

## Introduction

### Motivation
Once a language project owns compiler implementation, every convenience request becomes pressure to add syntax, special cases, or built-in magic — because the team that controls the language spec is the same team that feels the pain of not having the convenience. The failure is documented across language projects; [Khayyam Is Not Its Own Compiler or Runtime](../../khayyam/khayyam.md#khayyam-is-not-its-own-compiler-or-runtime) records it for one language. This protocol states the same boundary as a contract any compiler realization must satisfy, so the safeguard does not have to be re-derived per language.

The second failure is identifying "compiler" with "Khayyam to machine code." A compiler that lowers Khayyam to JavaScript, or that lowers C to an intermediate representation, is still a compiler. If the protocol is shaped by one language and one target, every later backend has to fight the definition.

The third failure is the compiler quietly adopting protocol semantics by recognizing a library by name — treating a framework's `IF` as an intrinsic, a numeric type as a builtin, a `main` as grammar. Each shortcut reintroduces magic the language's specification refused.

### Methodology
The positions below were first exercised as directives to a Khayyam compiler, then lifted: what survives without naming that language's constructs is the protocol; what names those constructs is a realization fact and lives in [Khayyam](../../khayyam/khayyam.md). The Lexer was split out of the same discussion into its own protocol because a lexer serves many consumers, of which a compiler is only one. Compile-time evaluation is stated as a designation-and-purity rule, not as a catalogue of privileged types; C's `const` folding and similar toolchain features are evidence the requirement is not language-unique. The directives are stated so that a party that did not write them can decide each against a named input; that no suite runs today is a gap in this project's checking, not a limit on what the protocol decides.

The obligation to flow management was derived from its consumers rather than from any compiler: each need was read from the module that has it and nothing else, and each guarantee was then checked to hold under every mechanism the topic names as an option. A claim that failed that check was not written as a guarantee. No mechanism is selected, and what the compiler in this repository does is recorded under [The implementation in this repository is not this protocol](#the-implementation-in-this-repository-is-not-this-protocol) as what that compiler does rather than as what a compiler must do.

## Explanation

### What a compiler is
A compiler is a system whose process is compilation: given a source and a language specification, it accepts or refuses the source as a program of that language, and, on acceptance, produces a target representation. The language specification is an input, not a component of the compiler. The target is an output chosen by configuration — it is not part of the compiler's definition. Multiple compilers may consume one language; one compiler may produce several targets behind one semantic representation. The semantic representation, not any one backend, is the source of truth both targets realize.

A compiler is not the language. Folding compiler implementation into the language's own scope is the failure mode the Motivation names.

### The compiler recognizes language primitives, not library names
The compiler's front end accepts the constructs the language specification actually defines. It does not treat library-provided operations as intrinsics because they are common, useful, or imported from a privileged package. Framework control-flow methods, numeric helpers, and lifecycle hooks are ordinary library code. Special-casing any of them by name couples the compiler to one library and forces every other library through that one library's shape.

What a given language's primitives *are* is stated in that language's documents. For Khayyam, the grammar's control-flow primitive is the inert code scope `sc`, which is inert until a library-provided method drives it — see [Khayyam → Scope](../../khayyam/khayyam.md#scope). Which operations may drive such a primitive, and by what mechanism a compiler serves a drive, are settled by the realization and by the flow-management module, not by this topic. What every realization must keep true about the primitive it is handed is stated as meaning, under [The compiler's obligation to flow management](#the-compilers-obligation-to-flow-management); that a flow-management operation is ordinary library code over a language primitive, and not a name the compiler privileges, is this topic's rule.

### The compiler emits analysis events
The compiler, as an independent application, emits events that analysis tools subscribe to — entering and leaving a scope, taking or skipping a branch — rather than requiring those tools to recognize a library's constructs by name. The [Linter](linter.md) and definite-assignment / path-coverage analyses consume this surface. Once tools depend on it, changing event shape or ordering is a breaking change for consumers the compiler does not control. The versioned event schema is not yet specified; see the paired handoff.

### How a call against a declared specification may be served
A language may let a call be written against a declared specification rather than against one concrete kind of thing — an abstraction, an interface, a protocol, a type parameter. Where it does, the compiler must still produce a call that reaches some implementation satisfying that specification, and **how** it does so at any given call site is a freedom: this document names no preference among the options, states none as a default, and obliges no module to anything about it. Three things follow from that status, and each is stated because a language that leaves the choice to its compiler can otherwise say nothing at all about it.

1. **What a compiler reasons over at a site.** The implementations a call site could reach form a **closed** set when every one of them is identified where the call is compiled, and an **open** set when at least one is not. Both terms are this document's rather than any language's, and they are stated here because they are criteria a compiler applies when it decides how to perform a call. [Structure Is Fixed by Definition](../../type.md#structure-is-fixed-by-definition) already speaks of a closed set of conforming implementations in its own account of what deferring the choice to execution does not change; what that topic does not state, and what is missing without this one, is the criterion a compiler applies at a call site and the two terms' reach as a pair. One boundary is not this document's to draw: whether an implementation can arrive after the call was compiled is a question for the language, and a language that fixes its structure by definition has already answered it. An open set defers the *selection* among candidates the program already establishes; it never defers the *identification* of a concept.
2. **What serving a site may cost.** A compiler may serve a closed site by inlining the concrete implementation — a specialized copy for the candidate actually reached, with no indirection left in the target — which is what *monomorphization* names. A compiler may serve an open site by generating a dispatch structure for the candidates and emitting one indirection per call, which is what a virtual method table names. A compiler may equally serve a site it could have resolved statically through an indirection it did not need. And a compiler free to choose at each site may choose again later in its own process: converting a dispatched call into a direct one once the concrete candidate can be established — *devirtualization*, common in the toolchains of several established runtimes — is a further step of the same freedom, not a second decision the language defers and not a separate mechanism. None of these is prescribed; none is forbidden.
3. **What no module may rely on.** Nothing about cost or mechanism is guaranteed. **Zero-cost abstraction is available where a compiler chooses to make it available and is promised by nothing**: the claim that "when the compiler knows the concrete type behind an abstraction, it should be able to inline the call — eliminating VTable overhead entirely — without the developer writing different code" states one compiler's freedom and one language's expectation, not a property a module can be written against. What a module may rely on is the meaning and not the mechanism: a call reaches an implementation satisfying the specification its call site declared, and which implementation that is may be settled by the target's execution rather than by the source.

One reason the distinction above is worth stating precisely rather than as "the compiler works it out" is that a compiler's target may itself be a language. Translating a program whose calls are written against declared specifications requires deciding, at each such site, which of the target's own mechanisms to emit — an interface or protocol the target resolves itself, a generic instantiation, an inline expansion, a table of function pointers — and without a classification of what a site looks like, that decision is ambiguous. The closed/open distinction is the classification that makes it answerable. This is a **rationale** for stating the freedom carefully rather than an obligation on any module, and which target mechanism corresponds to which case is a realization's own mapping, stated by that realization and not here.

### What a Language's Discipline Gives and Costs
The three claims below are rationales and observations, not obligations. None binds a compiler, none is a promise to a module, and each is recorded because a reader weighing what a language's rules buy has to see both sides; a compiler that does none of what they describe is not thereby nonconforming.

1. **A language that refuses to let a declaration acquire behavior it does not state keeps a compiler's account of a call's target single.** Where the set of methods a type answers to is exactly what its own source declares plus what a specification it composes requires, a compiler identifies a call's target from one place and never walks a chain of ancestors to discover what answers a name. The other side of that coin is the cost: letting a declaration acquire an implementation it does not state **clouds compile-time optimization, because the compiler can no longer assume the call target is a single entry it identified or a specialized copy it generated** — what a name may reach is no longer knowable at the point of declaration, and every guarantee that rested on knowing it weakens with it.
2. **Code whose state is always a named, explicitly declared thing is more consistently analyzable than code whose state is captured implicitly.** A compiler reasoning over named types has a concrete shape to work from at every use; an implicitly captured environment has a shape that varies from one use to the next, and what can be done with the first cannot be done with the second by the same argument. The two models are equivalent in the worst case — this is a claim about how often the favorable case is reached, not about what one model can express and the other cannot — and it is an observation about compilers in practice rather than a result any of them is required to reproduce.
3. **A language that reaches a value only through a declared operation never hands a compiler a chain to resolve.** This is the first claim seen from the language's own side, and it is what keeps an analysis of where a value's storage is decided within the region it can see. The failure it excludes is specific: a method acquired from elsewhere that reaches back into state the analysis did not see creates non-local references and breaks the analysis's linearity, so a compiler that relies on such an analysis is entitled to the language's rule and not to a promise about the analysis's result.

### The compiler's obligation to flow management
Three kinds of module are blocked on something only a compiler can supply, and each states its own need in its own words. The control-flow module needs a branch body it can hand to an operation and drive, with the operation's effect being the running of that body, while the choice of what that operation is stays its own. [Control Flow → Library-Defined Control Flow](../process/control-flow.md#library-defined-control-flow) is what separates the two halves: a code scope names *what* would run, an explicit operation decides *when*, and the common denominator across realizations is the branch-grouping primitive rather than any library's way of driving it.

The construction module needs the compiler to be able to say which paths reach a use of a variable. Refusing an uninitialized read is required of a compiler and not of a linter ([Memory → Uninitialized reads are refused](../memory/memory.md#uninitialized-reads-are-refused); [Linter → Linter versus compiler](linter.md#linter-versus-compiler)), and deciding which paths reach a use is a question about the driven bodies, not about the library that drives them.

The binding module needs a declaration whose implementation is supplied rather than written in source to stay a *request*: the compiler must not resolve it by name, and the correspondence between the declaration and what fills it must be recorded rather than inferred from a coincidence of spelling. That is the same refusal [The compiler recognizes language primitives, not library names](#the-compiler-recognizes-language-primitives-not-library-names) states, applied to a name the compiler never learns; [Entry and lifecycle are not grammar](#entry-and-lifecycle-are-not-grammar) states the same placement for boot and teardown.

Each of these is a **guarantee** — something a compiler must keep true — because a module cannot be written at all without it, and because a rule the compiler may vary at will is not a rule a module can be written against. What the compiler is **not** bound is the mechanism, because [Control Flow → Structured and Unstructured Flow as Libraries](../process/control-flow.md#structured-and-unstructured-flow-as-libraries) requires that a jump form be exactly as valid and exactly as unprivileged as a branch pair and that the choice between them belong to a tool and an organization, and an obligation stated as a mechanism would decide that choice once, here, for every realization. This document therefore states both kinds, and the line between them is drawn at one test: **a guarantee is a property of what a drive means; a freedom is a property of how it is served.** A claim about the meaning that cannot be restated for every mechanism named in [What this obligation does not decide](#what-this-obligation-does-not-decide) is not a guarantee but a mechanism in a guarantee's clothes, and it is not written here.

### The branch body a flow-control module receives
A language that groups a branch body in a construct of its own hands a flow-management module an object, and this protocol states what that object must be to the module. Every item below is a guarantee.

1. **What it is.** A value the compiler materializes and hands over wherever the language admits a scope in an argument position; not a name, and not a region of an emitted artifact. A module may bind it, pass it on, and keep it. This is what [Control Flow → The Generic Form: IF/ELSE](../process/control-flow.md#the-generic-form-ifelse) assumes when it writes the body as an argument of the operation that decides whether it runs.
2. **What driving it does.** The body's commands run, inside the execution that declared it, and the driving operation does not return until they have run. A module may therefore treat a drive as having happened by the time the call returns, and may rely on the writes the body performed being visible when it returns.
3. **What happens when it is driven twice.** The body runs again, from its first command. Nothing the compiler holds about a body survives from one driving to the next, so a repetition is a repetition and not an accumulation, and a module need not reset a body before driving it again.
4. **What it returns.** Open; it is named in [What this obligation does not decide](#what-this-obligation-does-not-decide). What a module may rely on is only this: a drive completes before the driving call returns, and whatever the body produced reaches the driver through the variables the driver handed it. Whether a body may hand a value back by any other channel is a question for the language, and no such channel is guaranteed here.
5. **Whether it is the same object across calls.** Within one execution, the same declared scope hands over the same body every time. A module may therefore capture a body during one driving and drive it again from within another, which is what the [control-flow model](../../../modules/process/control-flow/control-flow.md) relies on when it separates a scope that any number of decisions may drive from a decision that drives one scope per call. Across separate executions the value may or may not be the same object; nothing here depends on it being so.
6. **What it may see of its enclosing method.** A body may refer to every name visible where it was declared — the enclosing method's owner, its influencing and influenced variables, and what is reachable through them. Nothing a body declares is visible outside it, because a body may never execute: a name whose only declaration is inside a body may not be read where that body is not being driven. [Type → Scope — Type as Semantic Boundary](../../type.md#scope--type-as-semantic-boundary) makes visibility a property of the Scope's own rules rather than of whatever construct contains it; those rules are this protocol's, and no language document states them. The two halves are one rule: a body sees outward and is not seen outward.
7. **What happens to it when the enclosing method returns.** A body's meaning ends with the execution that declared it. A module that keeps one past that point and drives it has left this protocol; the compiler need not diagnose that, and is free to. Where a retained body names something that no longer exists, the compiler may do anything observable — including refusing, including doing nothing — and a module may rely on none of it.

None of the seven says what the body becomes in the target; that is the freedom named next. What the compiler must additionally keep true about the *analysis* of driven bodies is already stated, under [The compiler emits analysis events](#the-compiler-emits-analysis-events) and [Linter → Analysis consumes compiler events, not library names](linter.md#analysis-consumes-compiler-events-not-library-names), which is where taking and skipping a branch becomes observable to a tool that knows no library's names. This topic adds one constraint on top of those: the events must be derivable from whatever serves the drive, so the mechanism is answerable to the analysis and not only to execution.

### What this obligation does not decide
The mechanism by which a compiler serves a drive is not decided here, and this document names no preference among the options. What follows are the options a module may rely on being served by, and what choosing each would commit the compiler to.

- **A call.** The drive is an ordinary call whose callee the compiler already knows. This commits the compiler to the body's commands being reachable as a callable unit at the point of declaration; to the language's ordinary call contract applying to the drive, arguments handed over by reference and the receiver not among them; and to the callee being known where the drive is written, which is what makes inlining a drive an ordinary optimization available to any language with known callees rather than a library special case this protocol forbids.
- **A jump.** The drive becomes a transfer of control. This commits the compiler to control transfers that are not calls; to the body's commands being emitted as part of the enclosing method's own body rather than as a separate unit; and to a static account of where control can land, which is what makes the derived-target decisions — past an enclosing scope, the next iteration, past the call — expressible at all. [Control Flow → Error Propagation](../process/control-flow.md#error-propagation) names a mid-scope return as ordinary control flow, and [Structured and Unstructured Flow as Libraries](../process/control-flow.md#structured-and-unstructured-flow-as-libraries) requires that a jump form be no less a library construct than a branch pair.
- **A step of a state machine.** The drive becomes one step in a per-body progression. This commits the compiler to representing a body's position, to a suspension and resumption model for a body that is not finished, and to analysis that reasons over positions rather than over paths — which moves the cost of definite-assignment and path coverage onto the same representation the drive itself uses.
- **A returned continuation.** The body, or a position within it, is a value the module holds and re-enters. This commits the compiler to first-class re-entry: one declared scope entered at several points and resumed where it stopped. No other option delivers that, and it is what a repetition driven from two different decisions would need.

Two further questions belong to the same family and are equally left open: what a body hands back to its driver; and whether a body may be re-entered at a point other than its start.

### What no option delivers
A finding about this obligation, and it is a statement about the compiler rather than a proposal.

**The deciding half of a conditional is unimplemented, and none of the four options covers it.** Every option above describes what happens once a drive is granted. None says where the *decision* comes from. In this repository that decision is a method: [`modules/process/control-flow/protocol/if.kh:6`](../../../modules/process/control-flow/protocol/if.kh) declares `tp IF mt (self CF) (condition Condition, execute labelType) (err Error) {}` — body-less, which is the language's own signal that the implementation will be provided externally during the linking phase ([Khayyam → Method, Body-less Methods](../../khayyam/khayyam.md#method)) — and [`bundles/khayyam/targets/js/link_map.json`](../../../bundles/khayyam/targets/js/link_map.json) holds no entry for it, while a link entry that provides nothing is refused outright (`link.ts:93-96` of that target's link phase). The operation that decides whether a body runs is therefore both provisioned and unsupplied, and [the control-flow model's handoff records the same gap](../../../modules/process/control-flow/control-flow.handoff.md) as the question of whether a branch's own driver is a jump the library must declare or the compiler's.

This obligation does not dissolve that dilemma; it states it. [The compiler recognizes language primitives, not library names](#the-compiler-recognizes-language-primitives-not-library-names) forbids the compiler from owning the decision by name, so the decision belongs to a library — and the library's decision needs an implementation the link phase has no entry for. Three things would close it: a way for source to express a condition without naming a library, a link entry that supplies the one this repository has declared, or a compiler able to serve a decision without recognizing a library's name. Which of them it is belongs to the owner. What this protocol states regardless is that the obligation is unmet today, and that meeting it is not something any of the four mechanisms delivers.

**What leaves a method early is a library's business, and no option states it.** [Control Flow → Library-Defined Control Flow](../process/control-flow.md#library-defined-control-flow) calls a mid-scope return an ordinary control-flow operation. A language may realize it as a command of the grammar, and the language this repository develops does not: what ends an execution before the last command of a body is there a method on some type, which makes the question one a library answers by declaring it ([Khayyam → Scope](../../khayyam/khayyam.md#scope)). No option above states it, and none needs to — what it would state is a fact about a construct rather than about how a drive is served.

Two further facts belong beside this one, recorded because a reader checking conformance meets them at once. A scope used as the receiver of a call is refused by the toolchain in this repository with the words "a scope is a branch body, not a receiver" (`emit.ts:223-228` of that target's emitter), which is consistent with the first guarantee and is a realization's refusal rather than a protocol rule. And the compiler in this repository emits no analysis events at all, so the half of this obligation the construction module needs — deciding which paths reach a use — is undischarged for the same reason; that obligation is already stated under [The compiler emits analysis events](#the-compiler-emits-analysis-events), and its schema is an open item in the paired handoff.

### The implementation in this repository is not this protocol
Every mechanism claim about this repository's JavaScript target describes that target and nothing else. That target lowers a scope to a function declared inside the method holding it (`emit.ts:423-428`), lowers a call to a call (`emit.ts:464`), refuses a scope used as a receiver, and has an empty link map. Its frontend's semantic representation carries three commands for a body — declare, scope, invoke — with no jump among them ([`core/src/body.ts:15-24`](../../../bundles/khayyam/core/src/body.ts)). How it serves a call written against a declared specification is stated by the target itself rather than here: it resolves a call by the receiver's declared type, has no dispatch over capsules it did not see, and refuses a call whose receiver is typed as an abstraction ([`target.md:60`](../../../bundles/khayyam/targets/js/target.md)). That is a realization's mechanism on a freedom this document leaves open, and this repository's realization happens to exercise none of the options the freedom names. None of that is a requirement, and a protocol is neither defined nor satisfied by an implementation matching it: conformance is a checkable property of an implementation against the protocol's own rules and is never inferred from a label ([Protocol → Protocols and External Observers](../../protocol.md#protocols-and-external-observers)).

Three disciplines keep an implementation from becoming the specification, and this document holds itself to all three:

1. **A guarantee is stated as meaning.** Each of the seven items above holds under all four options; that is the test a claim must pass, and one that fails it is a mechanism claim that does not belong here.
2. **A mechanism claim lives in the realization.** The target's own documents, and the toolchain plan that carries the compiler's obligation toward flow management as one of its own steps ([`bundles/khayyam/khayyam.handoff.md`](../../../bundles/khayyam/khayyam.handoff.md)), are where this repository's mechanism is stated. This protocol states what must hold whatever that mechanism turns out to be.
3. **The rule is stated before the implementation is read against it.** A document revised until it matches the code in front of it has stopped being a protocol, whatever else it still is; the check runs in the other order or it is not a check.

### A protocol may be written for an obligation nothing discharges
Yes. A protocol states what must happen within a process and prescribes no mechanism for it ([Protocol → What is a Protocol?](../../protocol.md#what-is-a-protocol)), and whether any implementation yet conforms is a separate question asked later, measured against the protocol's own rules rather than inferred from a label ([Protocol → Protocols and External Observers](../../protocol.md#protocols-and-external-observers)). A document enters this folder at whatever maturity it carries and is developed here toward its full protocol form ([Protocols → Membership criterion](../README.md#membership-criterion)), so an undischarged obligation is the ordinary condition of a protocol at this stage rather than an anomaly in it.

Three commitments follow, and a reader is entitled to all three of them:

1. **The rules bind a conforming compiler whether or not one exists.** Every compiler of a language that has a branch-grouping primitive is obliged to the seven guarantees. The compiler in this repository discharges none of them today — it serves a drive by a call, emits no analysis events, and holds an empty link map — and that is a gap in an implementation measured against rules written without reference to it.
2. **A module written against them is not wrong when it does not run.** A flow-management module that is correct against these guarantees and fails to run has found a compiler-side gap rather than made a mistake of its own. The [construction model](../../../modules/process/construction/construction.md) records a shape that rhymes from the other side: the sources' thirty-three `From*` declarations attach to the type they produce, and not one carries an influenced variable of it — which that model labels a record of this repository and not proof that nothing fills the slot.
3. **What is stated as a guarantee is this protocol's claim; what is listed as undecided is not.** A reader may rely on every item in [The branch body a flow-control module receives](#the-branch-body-a-flow-control-module-receives) and on none of the options in [What this obligation does not decide](#what-this-obligation-does-not-decide). Under [Protocol → Protocol Properties](../../protocol.md#protocol-properties) an idea that has not passed a protocol's structured refinement does not yet carry Protocol status, which is what this document's own Status says about the parts it has not yet settled.

### Entry and lifecycle are not grammar
A compiler does not hardcode a syntax-level entry point or lifecycle (`main`, `init`, `deinit`, or equivalents) into the language it consumes. How a program boots and tears down is compiler configuration plus the selected [Runtime](runtime.md). Changing target environment — a Unix process, a unikernel, WebAssembly, a serverless handler, a JavaScript host — is a configuration change, not a language change.

The cost of the rule is real: a newcomer cannot discover where execution starts from the language alone. That cost is accepted so the language does not have to grow a new entry-point syntax each time the execution environment changes.

The same freedom covers where a declaration that stands outside any operation's body receives its first instance, and from what source. A compiler may establish it from the program's own source, from source the program includes, from a companion the build generates, or by refusing it; this protocol guarantees none of these, forbids none, and requires no program to name which it gets. What it does settle is that the answer is not a language feature: a grammar that made the establishing of such an instance part of a declaration would be legislating what a compiler, a link phase, and a [Runtime](runtime.md) do between them. Which of them establishes it, and what that first instance therefore contains, belongs to the realization.

### Designated pure operations may run at compile time
An operation that does not depend on runtime state, and that is *explicitly designated* as pure, may be evaluated during compilation and replaced in the target by its result. Qualification is designation plus purity, never a privileged type the compiler "knows." Languages that fold constants implicitly still owe an equivalent honesty about *which* operations ran at compile time; this protocol's default is explicit designation so a reader can see the boundary.

Compile-time evaluation is a second interpreter that must stay semantically identical to runtime evaluation of the same operation. Divergence is a real bug class. Designation adds an authoring obligation that implicit const-evaluation does not have; the protocol accepts that cost for visibility.

### The compiler consumes the Lexer; it is not the Lexer
Lexical processing is owned by the [Lexer](lexer.md). A compiler is one consumer of that protocol. Tokenization strategy, token shape, and whether a lexer exists at all for a given source are not compiler-definitional. A compiler that parses characters directly remains a valid architecture under the Lexer protocol's own terms.

### Runtime mutation of the artifact is `unsafe`
A compiler may support emitting or linking code that patches a running module's binary — adding or removing modules the way a WASM host replaces a module. The capability is dangerous and MUST be tagged `unsafe`. It is an opt-in escape hatch from [Structure Is Fixed by Definition](../../type.md#structure-is-fixed-by-definition), not the normal path. The [Runtime](runtime.md) states the same hatch on the execution side; [immutable infrastructure](../runtime/immutable_infrastructure.md) owns the deployment-side working-out. The two sides do not contradict: default is the base principle; the hatch is explicit, audited, and never used for normal capability evolution.
