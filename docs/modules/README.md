# Modules (`/docs/modules/`)
This directory holds the specifications of **Memar's modules** — each a bounded responsibility of the systems Memar builds, in the sense of [Modularity → Module as a System](../modularity.md#module-as-a-system) — stated independently of any programming language and of any implementation. What a module's specification chiefly states is the module's protocol: the declarative rules Memar owns for the process that module is responsible for, and expects systems built with it to conform to. See [Protocol](../protocol.md) for the general concept; a document here answers "what does *Memar's* module for X require?", not "what is X?".

## Membership criterion
A document belongs here when its subject is one of Memar's own modules and it specifies, or is expected to grow into the specification of, that module's protocol — requirements whose conformance a party that did not write them can decide from a stated input ([Protocol → Protocol Properties](../protocol.md#protocol-properties)), whether they take the form of a contract, a wire or encoding format, or a rule set any language or stack can realize. Documents enter at whatever [Status](../documentation-explanation.md#status) they carry, including Draft, and are developed here toward their full protocol form: a Draft that currently records the *why* and the open questions is expected to mature in place until it states the protocol itself. What an organization may hold a different view on, and what the OS leaves to the system above it, are stated in the documents themselves as parts of the protocols, not decided here.

A document stating **Memar's position on something whose authority lies outside Memar** — a protocol surface Memar conforms to and may realize, or a design name that circulates with senses Memar does not inherit — belongs in [`lib/`](./lib/README.md), which states its own criterion.

What does **not** belong here:
- **Concept documents** (System, Type, Process, [Protocol](../protocol.md), Modeling, ...) — these model general concepts and lenses; they stay at `docs/` root.
- **Khayyam language documents** — the language's own design and specification lives in `../khayyam/` (`docs/khayyam/README.md`); the modules here are what Khayyam conforms to, not the language itself.
- **Realizations** — declarations, sources, and tools live under `modules/` (`modules/README.md`); see [Where implementations live](#where-implementations-live).

**Citation direction.** A citation runs down the layers of the written content, never up, as [Documentation → Citation Direction](../documentation.md#citation-direction) states once for every layer.

The documents themselves are not listed here — the folder listing is the index. This file only states the folder's role and criterion, which do not change when documents are added.

## One layout for both trees
The category folders of this directory are the layout of the repository's modules, and `modules/` (`modules/README.md`) follows it: a module specified at `docs/modules/<category>/<name>.md` is realized at `modules/<category>/<name>/`, and [`lib/`](./lib/README.md) here stands opposite `modules/lib/`. No category is final; a category is created, renamed, merged, or retired here first and then in `modules/`, so a responsibility has one address in both trees and the two are never reconciled by hand. A folder in `modules/` that precedes its first document keeps its path when that document is written here. What runs or aggregates modules rather than being one — the language toolchain and the Memar server — lives under `bundles/` (`bundles/README.md`), outside this layout, and has no counterpart here. The port's residue is a record rather than a module and no longer sits in `modules/`; it is the Go target's research record (`bundles/khayyam/targets/go/target.research.001.md`).

## Where implementations live
This folder is each module's specification and source of truth — **not executable code**. Implementation modules live under `modules/` in this repository — for example, the Control Flow module under `modules/process/control-flow/`. What runs or aggregates those modules — the Khayyam toolchain, the Memar server — lives under `bundles/` (`bundles/README.md`). An agent that needs running code for one of these modules should go there instead of reading these documents as an implementation specification; open a document here only when the contract itself is the subject.

The specifications here remain language-independent, and that is why specification and realization are two trees rather than one document beside each realization: a folder holding both could not show which of its files binds every realization and which is one language's. The repository hosts the current Khayyam toolchain plan and module material as one local realization, alongside any implementation modules a project needs for its own realization. The language used by a realization is chosen where that system is implemented; the module's meaning remains stable across realizations.
