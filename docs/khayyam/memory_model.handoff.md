# Khayyam Memory Model Handoff

Open work for `memory_model.md`. Entries are mutable current state — revised as each item moves, removed when it resolves or is dropped. See [documentation-handoff.md](../documentation-handoff.md) for what a handoff is.

## Open Questions

### Which of this document's content is Khayyam's?
The folder's membership criterion is "how does Khayyam realize X?", but parts of this document read as Memar-level positions rather than one language's realization of them: that memory layout and reclamation are a toolchain responsibility instead of a developer's syntax problem, that a variable's identity is separate from its instance's lifecycle, and that reclamation analysis belongs in tooling. Each already has a language-independent home — [Memory → Copy and ownership semantics are contract members](../protocols/memory.md#copy-and-ownership-semantics-are-contract-members) and the topics around it. What is unambiguously Khayyam's is the mechanism: `vr`/`Deinit()` surfaces, the static escape-analysis pass, PGO shipped as an orchestration library, generated files named `file_name.generated_by_gc1.kh`. Whether a reader can currently tell the two apart from the shelf this document sits on is the question this item exists to settle.

### How much of this document is settled design and how much is aspiration?
Mechanisms at very different maturities are stated in one voice: a static escape-analysis ruleset, a PGO orchestration library, linter-required execution-path analysis, and a compile-time binary-mutation idea for dynamically-valued constants. The document's own `Drawbacks` says plainly that the PGO approach "should currently be read as a long-term architectural goal rather than an already-solved engineering problem", and its `Unresolved questions` says the binary-mutation idea is undecided in the source material itself — but both statements live under headings the current skeleton no longer uses, so nothing in the body marks the maturity of any individual claim. A document-level `Status: Proposed` cannot carry that distinction claim by claim.

## Anticipated Work

- State: the proposal is to move this document's general memory positions into [protocols/memory.md](../protocols/memory.md), which already owns the memory/storage dichotomy, the reclamation-mechanism taxonomy, copy semantics as contract members, and the boundary-copy default, leaving here only Khayyam's realization of them (Omid Hekayati — raised 2026-09-14). Leaving them where they stand makes Memar's position on memory read as a Khayyam commitment, which is the misreading that motivated the move.
- Next: a dedicated session, with two dependencies to settle on the way in. First, each relocated statement needs its enforcement tier decided as it lands: `memory.md`'s copy-semantics topic deliberately leaves the copy/share choice to the contract ("both directions are viable; what is not viable is leaving the choice discoverable only by reading the implementation"), so a reference-by-default style claim cannot arrive there as an unqualified MUST — it becomes either a stated protocol default with its deviation path, or an open question in `memory.handoff.md`. Second, [Memory → Methodology](../protocols/memory.md#methodology) currently hands reclamation-mechanism choice *to this document*, so that pointer must be re-decided once the split lands rather than left pointing at a half-relocated file.
