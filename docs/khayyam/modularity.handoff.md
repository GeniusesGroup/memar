# Modularity in Khayyam Handoff
Open work for `modularity.md`. Entries are mutable current state — revised as each item moves, removed when it resolves or is dropped. See [documentation-handoff.md](../documentation-handoff.md) for what a handoff is.

## Open Questions

### Naming Without Package Context
1. Is a whole-file inclusion form beyond `in` genuinely needed? Earlier design material mentioned a hypothetical `im` keyword (`tp {name} im {address}`) for including an entire file under one local name, such as `jsonEncode.Encoder`; it was exploratory, not a commitment to a second import mechanism. Whether `in` alone can cover both inclusion of a named entity and any future whole-file inclusion need remains unresolved.

### Dependency Resolution and Companion Manifest
1. **This section is not where the manifest is designed, and holding it here was the mistake that moved it.** The manifest, what a module claims, how one reaches it, and how one module's use of another is declared are [dependency management](../protocols/modules/dependency-management.md), and on 2026-09-30 they were taken out of this handoff and taken there — a session had put a module's four manifest obligations, its file name, and a regex claim in a Khayyam document, which is the wrong layer twice over: dependency management is not a language subject, and a later session reading it here would have concluded the language had examined it.
2. **What the language owns here is one sentence**, ruled 2026-09-26 and recorded under *What is the exact `in` path shape?* below: the value of an `in` declaration is a URI, and the grammar fixes neither its scheme nor its shape. Everything else — the manifest's format, the resolution algorithm, multi-version conflict policy, integrity mechanisms, what a module claims — belongs to the protocol document, and a rule or a resolver owns it rather than the grammar.
3. **Nothing is open in this section for the language.** Whether an address is path-shaped, whether a manifest exists, and what a manifest says are all questions whose answer changes no sentence of the language. If one of them ever does change a sentence of the language, that sentence belongs in [`modularity.md`](./modularity.md) and the question returns here — the test is whether the grammar is affected, not whether the topic is adjacent.

### What is the exact `in` path shape?
- Ruled (2026-09-26, owner): **the language does not fix the shape.** An `in` value is an *address*; the scheme it is written in, and how it is resolved, is declared by the module manifest — which is itself a requirement and must provide dependency management. A UUID-based scheme is acceptable; a repository-root-relative filesystem path is acceptable and is what this repository uses, because it is readable and deterministic. Nothing is forced at the language level. **This is the whole of what the language says about the shape of an address, and it is why this entry is one line.**
- **Everything after that sentence is dependency management's, and it was moved there on 2026-09-30.** The rulings of 2026-09-29 — that the base an address is resolved from is the manifest of the module that wrote it rather than a repository root; that a manifest says everything about its own module, in four obligations; that its file name is `memar.manifest.{format}`; that a module claims an address by a pattern such as `memar/*` and that a whole may be a module as well as each of its parts — are recorded in [dependency management's handoff](../protocols/modules/dependency-management.handoff.md). One of them **collides with that document's stated position**, which names the version-control repository as the dependency mechanism and a manifest as machinery this project does not require; the collision is recorded there as an open question for the owner rather than resolved here, because resolving it is a statement about Memar's dependency position and not about Khayyam.
- **What the language still owes, and it is small:** nothing about the shape. A stricter requirement — that an address carry a file name, a path separator, or a particular form — would be a rule an organization holds rather than something the grammar says, and the place for it is a rule ([`modules/khayyam/rules/import-address/`](../../modules/khayyam/rules/import-address/import-address.md)), which is where this repository's own permissive default already lives.

### Cyclic Module Dependencies
Khayyam has not settled whether and how its grammar or tooling restrict cycles among module inclusions. Go forbids cyclic package imports outright, and the ban behaves like a compilation-speed measure rather than a modeling truth: developers satisfy it by dropping type information across package boundaries (for example, passing an account identifier as a plain string where a real identifier Type exists), losing exactly the nominal distinction the type model is for. The conceptual layer has already ruled that mutual conceptual dependence between Modules is not, by itself, a defect and that language cycle restrictions must not be forced onto the model ([Modularity → Conceptual Relationships Are Not Runtime Coupling](../modularity.md#conceptual-relationships-are-not-runtime-coupling)); the language layer still owes the positive decision — no restriction, a restriction with an escape hatch, or an out-of-band tooling rule — and its rationale.
