## 1. What each project is
### context-mode (self-definition)
context-mode calls itself "The other half of the context problem" (`README.md:3`). The problem it states is concrete: every tool call dumps raw data into the window — "A Playwright snapshot costs 56 KB. Twenty GitHub issues cost 59 KB" — and when the agent compacts, it forgets which files it was editing and what the user last asked (`README.md:34`). It answers on four sides (`README.md:38-51`): sandboxed tools keep raw data out of the window ("315 KB becomes 5.4 KB. 98% reduction"); session events are kept in SQLite and re-served by search after compaction; the model is told to write code that analyses data and prints only the answer ("Think in Code"); and it deliberately does not dictate the model's prose style, citing a report that aggressive brevity prompts degrade benchmarks (`README.md:51`).

What it ships toward that purpose is an MCP server with 11 tools (`server.ts` registers eleven; `README.md:86`), a set of per-host hook scripts that intercept `Bash`, `WebFetch`, `Read` and `Grep` calls (`hooks/hooks.json:28-64`): `curl` and `WebFetch` are redirected, `Read` only above 50,000 bytes (`routing.mjs:846-848`), `Grep` gets one-shot guidance (`:870-872`) (`README.md:1404`), a SQLite FTS5 store with BM25 and trigram search fused by reciprocal-rank fusion (`README.md:1192-1199`), a per-project event log built by the hooks, and 18 host adapters (`configs/` holds 18 directories). It is licensed under the Elastic License 2.0, which is source-available and forbids offering it as a hosted service (`LICENSE`, `README.md:1619`).

### Memar (self-definition)
Memar is a framework for developing any system — software, hardware, buildings, organizations — conducted through one continuous mental model held in documents and tools ([Framework](../framework.md)). Of its own context work it says three things that matter here. A session exists "so that a task's decisions outlive the context" (`.agents/skills/memar/SKILL.md:28`). The agent's context is a budget to be spent on purpose: after any compaction the skill and the session's plan are re-read and the act's passages are printed again, and past about half the window the remainder goes to a new session or a delegate (`SKILL.md:38-42`). And a task is sized by "weighing the load of a session against the work it holds", with no numeric threshold "until a real session's cost, load and re-reads both counted, has been measured" ([Handoff Practice → The size of a task](../../modules-plugable/knowledge/documentation/handoff/handoff.practice.md#the-size-of-a-task), lines 94 and 102).

Memar ships no sandbox, no hook, and no index of its own beyond what its content verbs build. What it ships toward context economy and recall is `memar content get-act-context`, which prints in ordered parts under a runtime's output cut (`SKILL.md:65`) and, with `--after`, omits what the session's record already shows printed (`SKILL.md:20`); `memar content find`, whose ranking is informative only (`SKILL.md:22`), and `memar content search`, a regex search; both read documents and code by default and, with `--from sessions`, the archived session records and the live session folders (section 6); and a session's plan, report and handoff, kept per task and archived on the branch `dev-knowledge`. Asking for "the least output that answers" is an instruction to the agent (`SKILL.md:40`), not a property of the commands.

### Category distinction and layers
The two projects overlap on two surfaces and differ on the rest. The cut is by the job a reader would hire each for ([Documentation — Comparison → Fairness rules](../../modules-plugable/knowledge/documentation/comparison/comparison.md#fairness-rules), rule 2), and here the jobs are four, not one.

- **Window hygiene** — keeping tool output out of the context. context-mode's whole first half; Memar has only part-splitting, `--after` and an instruction to the agent. Not Memar's job so far, and context-mode is the specialist.
- **Resuming after a cut** — continuing the same work after compaction, `--resume` or a new chat. Both do it. context-mode rebuilds a snapshot from captured events; Memar's plan, report, `Next` and handoff carry the state, and a new chat for a session starts from `memar ai get-task-init-context`. This is a direct rival pair.
- **Recalling earlier work to answer a later question** — a chat or session that meets a question similar to one met before, and finds the earlier answer. context-mode does it across the current session, prior sessions of the same project and the host's memory files, in `sort: "timeline"` mode only, and for as long as its retention keeps them — seven days for session events, fourteen for indexed content (`src/search/unified.ts`, `src/session/db.ts:1089`, `:1696`; section 3, item 10). Memar's stated aim is the same (the owner's, 2026-10-19): what a chat or a session learned must be findable by a later one. Its mechanism is `memar content find` and `search` with `--from sessions`, which read the archived records and the live session folders, each hit naming its session and file and being a session's claim, never a ruling; it is reached on request, nothing yet tells an agent when to ask, and a chat that opens no session leaves nothing to find (section 6). This is the surface where the two are rivals in purpose.
- **Deciding what the work is and recording what was decided** — rulings, rules, models, with named parties and reasons. This is Memar's job and not one context-mode attempts; its closest thing is a pattern-selected "decision" event (section 4, item 2).

On the second and third jobs the two compete, and the honest reading is that Memar holds the deeper record on both, while context-mode's retrieval is wired into its instruction to search before asking and Memar's is a command an agent has to choose to run.

## 2. Source status of the inspected checkout
The checkout is a single-commit snapshot of an actively developed repository. The version number (1.0.169) and the ADR history show a project that ships a patch release often; the source tree is substantial — `src/server.ts` alone is 4,991 lines, `src/store.ts` 2,071, `hooks/core/routing.mjs` 1,017 — and the test directory holds 210 `*.test.ts` files with roughly 4,500 `it(`/`test(` occurrences (a loose count). `BENCHMARK.md:120-128` still states 125 tests.

Because the history is collapsed, the project cannot be asked why a given line is what it is from inside the checkout. That is a finding about the source ([Documentation — Comparison → Method requirements added by practice](../../modules-plugable/knowledge/documentation/comparison/comparison.md#method-requirements-added-by-practice), item 2). It is partly offset by something the project does well: it writes its reversals down. ADR 0001 records that v1.0.128 shipped a single-writer lock, that multi-window users then could not work, and that the guard was withdrawn in v1.0.130 after a root-cause re-analysis (`docs/adr/0001-sessiondb-multi-writer.md`). ADR 0004 records that a stats formula drifted from "compression ratio" into "infrastructure-size accounting" across two unrelated fixes and was restored (`docs/adr/0004-stats-strict-compression-formula.md`). A project that can say that about its own metric is a different kind of source than one that cannot.

Several of the project's headline claims resolve outside the checkout: the user count and the "Used across teams at …" row are badges (`README.md:5-30`, the company badges link to `#`), the Hacker News badge points to an external thread, and the Insight dashboard is hosted (`README.md:96`, `src/cli.ts:1224`). None of them is a claim about code, and none is checked here.

## 3. What context-mode has that Memar does not
Stated as strengths with the evidence for each. This is an inventory, not a shopping list — the filter is in section 7.

1. **It names a failure Memar's tools can also cause, and measures it.** "One unrouted command dumps 56 KB into context" (`CLAUDE.md:3`). The failure — tool output flooding a window — is real, ordinary, and costly, and the project counts it: `ctx_stats` reports bytes kept out per tool and per session, and ADR 0004 shows the count being argued over and corrected. Memar's own text says the window is a budget (`SKILL.md:40`) and asks for "the least output that answers", but holds no instrument that says how much a session spent.
2. **Enforcement by the host's own event, not by the model's compliance.** "Instruction files guide the model via prompt instructions but cannot block anything. **Always enable hooks where supported**" (`README.md:1404`). A `PreToolUse` hook denies or rewrites the call before it runs. This is the opposite choice to Memar's, whose skill records the problem openly — "telling the agent to read does not work", and "whether every part is run … still rests on the agent following the skill" ([Skills README → Known Problems of the Current Skill](../../.agents/skills/README.md), line 17).
3. **Compaction is detected by an event, not by the agent noticing.** `PreCompact` builds a snapshot and `SessionStart` with source `compact` re-injects it (`README.md:1291-1303`, `hooks/precompact.mjs`). Memar's rule is "announced or not; a context that opens with a summary has been compacted" (`SKILL.md:39`): the agent must recognise the summary in its own context. Where a host emits the event, that recognition is not needed.
4. **Guidance that is re-fired because it is forgotten.** `CONTEXT_MODE_EXTERNAL_MCP_NUDGE_EVERY` (default 10) re-injects the routing guidance every tenth matching call, because the original once-per-session reminder "got lost after context compaction in MCP-heavy sessions" (`README.md:1606`). It is a measured admission that one-time instruction decays — the same phenomenon Memar's re-read-after-compaction rule answers by hand.
5. **A refusal text treated as an instruction to the model.** ADR 0003 records that the word "blocked" in a redirect message made Opus 4.6 "capitulate to training data" instead of using the redirected tool, and fixes the rule: a redirect names the alternative by tool, affirms it works, and ends with a retry hint, while real security denials keep restriction vocabulary (`docs/adr/0003-routing-deny-reasons.md`). The distinction — redirect is not restriction — is a durable claim about agent-facing text, supported by a reproduced failure.
6. **A single routing block, many adapters.** `hooks/routing-block.mjs:3` calls itself the "single source of truth", with a tool-namer function producing each platform's names. Eighteen adapters do not become eighteen mental models; the platform grids carry honest `--` and "Partial" cells (`README.md:1243-1251`, `1373-1384`) and state which hosts reject which hook (Cursor's `sessionStart`, Kiro's `agentSpawn`). That is the shape of Memar's own principle that adapters may multiply but the model must not ([Knowledge → A project carries one continuous mental model](../../modules/knowledge/knowledge.md)).
7. **Security reuses the host's own rules rather than adding a second configuration.** `permissions.deny` and `allow` from the host's settings are enforced inside the sandbox tools too; an out-of-project read is opted back in with the same `Read(...)` allow rule — "there is no context-mode-specific env flag" (`README.md:1530-1573`). The same section states its limit: `ctx_execute` "still inherit[s] the process's filesystem access … not a full OS sandbox" (`README.md:1575`). One place for a grant, and an honest ceiling.
8. **Fetch and persistence hardening with reasons.** Scheme allow-list, cloud-metadata and link-local ranges blocked even after DNS resolution, loopback and RFC1918 allowed by default with a strict switch (`README.md:1577-1592`); credentials in MCP tool inputs redacted before persistence (`README.md:1594`).
9. **A "do not enforce prose style" stance.** The routing block "stays focused on *where data goes*, not on *how the model talks*" (`README.md:51`). A small, correct separation of a harness's concern from the author's.
10. **Recall across sessions and sources, with a coarse origin on each hit.** `ctx_search(sort: "timeline")` merges the content store, prior sessions' events and the host's own memory files (`CLAUDE.md`, `AGENTS.md` and the platform's memory directory) into one chronological list in which every hit carries `origin: current-session | prior-session | auto-memory` (coarse: the origin is fixed per store — content-store hits are always `current-session`, even when indexed in an earlier session, `unified.ts:87-89`, `:120`, and session-event hits are always `prior-session`, `:143`) (`src/search/unified.ts:15-26`, `:60-66`; `src/search/auto-memory.ts:1-6`). Events carry typed labels the model can search by (`source: "decision"`, `"rejected-approach"`, `"constraint"`; the table in `CLAUDE.md`, "Memory"), and a per-project scope keeps one project's recall out of another's (`unified.ts:44-54`, issue #737). Prior sessions are reached only in `timeline` mode; the default `relevance` mode searches the content store alone (`unified.ts:64`, `:133`), and session events are stored there under the label `session-events` (`server.ts:516`), so the `source: "rejected-approach"` and `"constraint"` examples in `CLAUDE.md:76-77`, given without `timeline`, appear not to reach them (read from the code, not run). The scope is the same project and the retention window above (`db.ts:1089`). The agent is told to search before asking the user what it was doing (`CLAUDE.md:67-80`, "Memory"). Whatever one thinks of what is stored (section 4, item 2), this is a working answer to the question Memar poses as its own aim, and Memar's answer, `--from sessions` on `memar content`, is in section 6.
11. **A visible decision record with amendments.** The four ADRs state status, version, what they supersede, and, for ADR 0003, two amendments, the first dropping a previously prescribed phrase. Section 2 names the value of this.

## 4. Where Memar is stronger
1. **Decisions outlive the context; here they are ephemeral by design.** The README says "If you don't `--continue`, previous session data is deleted immediately" (`README.md:41`), but the code deletes only what is older than seven days (`hooks/sessionstart.mjs:306`, `src/session/db.ts:1696`), and indexed content is removed after 14 days (`README.md:1221`); the README sentence is stale prose, as in section 5, item 4, and the retention is what makes prior-session recall work. Short retention, not immediate deletion, is the actual design. That is a coherent product choice for continuity, and it is the opposite of what Memar means by a decision: one claimed by a named party, recorded in the home that owns it, and kept with its reasons (`SKILL.md:28`; [Documentation — Comparison](../../modules-plugable/knowledge/documentation/comparison/comparison.md) on corrected-in-place records). context-mode restores working state; it does not accumulate knowledge, and does not claim to. The advantage is in what is kept and by whom, not in being able to find it again: section 6 records that Memar keeps more and retrieves it on request, with limits.
2. **A decision is recorded by someone who made it; here it is a shape.** The "Decisions" event is any user message that is not a question, 15 to 500 characters long, and contains a clause separator (`src/session/extract.ts:2199-2230`). The comment states honestly that this is "a coarse 'looks like a correction' filter" and leaves interpretation to the next model. A "constraint" is a tool error response containing "Error" and matching `/cannot/i`, `/FAIL/i`, `/refused/i` and similar (`extract.ts:871-875`). These are reasonable heuristics for resuming work and say nothing about whether the thing recorded was decided. Memar's decisions are rulings: the owner's, dated, and cited where they apply (for example the owner's note of 2026-10-13 in [the preferences file as it then stood](https://github.com/GeniusesGroup/memar/blob/6833d19b/.agents/memar/preferences.md)).
3. **The duplication problem is solved at the source.** ADR 0004's field report: 84% of one user's event data was "496 duplicate copies of the same CLAUDE.md captured by SessionStart hooks across resume cycles", and the schema's `data_hash` dedup column "is populated but unused by the formula". Memar's `memar content get-act-context --after` records what a session has printed by hash and omits it the next time, so a changed section is printed again and an unchanged one is not (`memar content get-act-context --help`; `SKILL.md:20`). The same problem, handled in the design rather than discovered in a statistic.
4. **A claim of savings is not a claim about the work.** context-mode's headline is bytes kept out of the window on captured fixtures (`BENCHMARK.md:1-17`, `README.md:1459-1472`). It does not measure whether the agent's answer was right, or what the code that produced the small output cost to write and what happened when that code was wrong (section 5, item 1). Memar makes no savings claim and therefore cannot be wrong in this way; this is a strength of reticence, not of measurement, and section 6 says what Memar lacks in return.
5. **Reviewers who did not do the work.** The ADRs list their reviewers — ADR 0001: "10 parallel grill verdicts (UX, SQLite, Security, Perf, Architect, Test, SRE, PM, Data, DevEx)"; ADR 0004: "7-agent EM ops audit". ADR 0001 and ADR 0004 read as roles played in one agent session (inference — they do not say what ran them); ADR 0003 names a human reviewer, the owner, who caught a flaw in its first rubric (`:8`, `:79-81`), which is the stronger kind. Memar's rule is that an approval comes from a party that did not do the work, on a different model where the runtime offers one ([Documentation — Changelog → Approval Requires a Reviewer Who Did Not Do the Work](../../modules-plugable/knowledge/documentation/changelog/changelog.md)). Role-played reviewers share their author's blind spots by construction; the point is not that the ADRs are wrong but that their review does not carry the same evidential weight a Memar record's does.
6. **Software specified without hidden inputs.** context-mode's behavior depends on a thick layer of environment variables, host-directory probing and platform auto-detection by `clientInfo.name`, or by whichever of `~/.claude/` or `~/.codex/` is found (`README.md:1600`, `1606`; ADR 0001's #561 misdetection). Memar's rule for the software its documents specify is that every input is a name or a path ([Software → No Hidden Inputs](../../modules/process/software/software.md)). The trade is real: detection is what makes 18 hosts work without configuration. It is also where ADR 0001's regression came from.

## 5. Limits and failure modes in context-mode
Each item says whether it is read from the files or is inference.

1. **The headline measures bytes on fixtures, not outcomes (read, then inference).** `BENCHMARK.md` states 96% across 21 scenarios and 98% for the `ctx_execute_file` subtotal (`BENCHMARK.md:51`); the timings (15-32 ms) are of scripts run over stored fixtures. The measure leaves out the model's output tokens spent writing the script, and the case where the script is wrong and returns a confident small answer (inference: no wrong-script scenario appears in `BENCHMARK.md`). The project's own ADR 0003 (`:15-17`) and ADR 0002 (`:21-22`) admit adjacent fragility elsewhere: Opus 4.6 misread one deny word.
2. **The headline mixes two modes the project itself separates (read).** `BENCHMARK.md:72-75` says `ctx_execute_file` on React docs returns "5 code blocks, 3 sections about cleanup" which is "useless for coding", and that exact retrieval through `ctx_index`/`ctx_search` is what documentation needs, at 44-93% savings (`BENCHMARK.md:57-66`). The README's benchmark table nonetheless lists "Context7 React docs 5.9 KB → 261 B, 96%" (`README.md:1466`, copied from `BENCHMARK.md:36`) — the summary mode's figure, for the content the benchmark file says the summary mode should not be used for.
3. **Counts that disagree inside the repository (read).** "5 hooks working together" (`README.md:1241`, also `:1336`) against six named in the same section and at `README.md:86`; a Tools table of ten (`README.md:1163-1174`) against eleven registered tools (`README.md:86`); 125 tests (`BENCHMARK.md:128`) against hundreds of test files.
4. **Documentation and code disagree on the snapshot (read).** The README says the snapshot is built within a 2 KB budget and "lower-priority events … are dropped first" (`README.md:1294`, `1305`; `hooks/precompact.mjs:7`). `src/session/snapshot.ts` opens with "Zero truncation. Zero information loss", and its option `maxBytes` is marked "KEPT for backward compat but IGNORED" (`snapshot.ts:12`, `:30`). The code is explicit that no budget applies: `snapshot.ts:470` reads "Assemble ALL non-empty sections — no priority dropping, no byte budget", and `hooks/precompact.mjs:49-51` calls the builder without `maxBytes`; the only limits are per section (`MAX_ACTIVE_FILES = 10`, `snapshot.ts:37`; three recent messages, `:428`). The README's 2 KB budget and tier dropping, and the `precompact.mjs:7` header, are stale prose; the code is authoritative.
5. **A number with no source: "~60% compliance" (read; the weight put on it is inference).** Instruction-file-only hosts are described as getting ~60% compliance (`README.md:864`, `:995`, `docs/platform-support.md:367`, `:818`; the `~60% saved` column at `README.md:1410` is the savings counterpart). No measurement of it appears anywhere in the checkout. The sentence is the basis of the strongest design claim in the project — that hooks are necessary — and it stands unmeasured. The claim may be true; the checkout does not show it.
6. **"Rejected approaches" appear to include the product's own redirects (read).** The README lists them as "Tool calls denied by user" (`README.md:1273`). In `hooks/pretooluse.mjs:186-196` the marker is written whenever the hook's own decision is `deny` or `modify`, with the reason "Redirected to context-mode sandbox" for the second case, and `hooks/posttooluse.mjs:82` emits a `rejected-approach` event from it. Traced further, on Claude Code, `routing.mjs:938-940` and `:993-994` return `modify` to pin a working directory for the product's own `ctx_*` calls, which `hooks.json:73-91` routes through `PreToolUse`, so ordinary calls to its own sandbox tools are logged as rejected approaches. A refusal at the host's interactive permission prompt passes through no hook; denials from the user's own `permissions.deny` rules do write markers (`routing.mjs:716,932,953,964,985`), and plan rejections go to a separate category (`extract.ts:762-766`). A denied tool never reaches `PostToolUse`, so its marker is picked up at the next call of any tool, and the single marker file is overwritten, so only the last survives. What a resumed model reads under "Rejected Approaches" may therefore be dominated by the product's own activity.
7. **Privacy is stated without a sentence about the hosted part (read).** "Nothing leaves your machine. No telemetry … no account required" (`README.md:1524`) sits beside `ctx_insight`, which opens a hosted dashboard for "org analytics for AI-assisted engineering teams" (`README.md:96`). The local code does only open a URL (`src/cli.ts:1224`); what the hosted site receives, and from where, is outside the checkout. This essay makes no claim that data is sent; it notes that the reader of the privacy paragraph cannot tell from the repository.
8. **A coupling to each host's hook API is a standing maintenance cost (inference from the project's own record).** Eighteen adapters, several marked partial because a host rejects or lacks an event, and ADR 0001's story — two consecutive patch releases of a guard that locked out legitimate multi-window use — show a surface that moves under the project. The `~/.claude/context-mode/` misdetection on Pi (#561, ADR 0001) is the same class: guessing the host from the filesystem.
9. **The instruction layer is loud (read).** The project's own `CLAUDE.md` and skill use "MANDATORY", "BLOCKED — do NOT attempt", and a skill description that lists 39 quoted trigger phrases (`CLAUDE.md:1`, `skills/context-mode/SKILL.md:3-19`). ADR 0003 shows that this register failed once in a reproduced case, and its response was substantial — a CASE A/CASE B rubric banning bare negations (`:36-74`), with two amendments, and ADR 0002 a description-style rubric. The fair finding is narrower: the project's own `CLAUDE.md:10-13` ("BLOCKED — do NOT attempt … Do NOT retry") still breaks ADR 0003's rubric.
10. **Licence and attribution (read).** Elastic License 2.0 is source-available, not open source in the usual sense; the README says so (`README.md:1619`). A project built on this one under Memar's own licensing choices would need to hold that in mind. This essay takes no further position.
11. **A very large central file (read).** `src/server.ts` is 4,991 lines and registers all eleven tools in one module. This is a description, not an argument; Memar's own script-size test is set against its scripts ([`bundles/memar/tests/script_size.py`](../../bundles/memar/tests/script_size.py)) and says nothing about someone else's.

## 6. Costs and limits on both sides
### context-mode
- It pays for its enforcement in adapters, and for its detection in guesses (section 5, items 8 and 9). Both costs are visible in its own ADRs and neither is concealed.
- It makes the agent a code generator for analysis. That is cheap when the script is right and costly in a way no benchmark here counts when it is wrong.
- Its memory is working state, not knowledge. A team that wants durable decisions will need a second system; the project does not say otherwise.
- Its savings claims are, so far as the checkout shows, unreproduced off the project's own fixtures and not re-derivable from a live session.

### Memar
Each item below is a statement that Memar has not reached the subject, or has reached it only in part, not a claim that it chose not to. Where a document or an open question already covers it, it is named. The first two items concern the third job of section 1, recall, and are the main finding of this essay.
- **Archived session records are searchable by content on request, with limits.** `memar session archive` keeps a finished session's folder on the branch `dev-knowledge`; the branch holds 1,537 files in 240 sessions (`git ls-tree -r dev-knowledge`). The archive's stated purpose is "to cite with the task's work" (the verb's summary in `memar session --help`; [Handoff → Where a finished session's records are kept](../../modules-plugable/knowledge/documentation/handoff/handoff.handoff.md)), and `memar session show` prints a session by its id. `memar session list TEXT` still matches only a session's id, title and project. What reaches the content is `memar content find` and `search` with `--from documents|code|sessions` (repeatable; the default, documents and code, is what they read without the flag): `sessions` reads the archived records through read-only git calls (`git ls-tree -r -z`, `git cat-file --batch`; HEAD, the index and the working tree do not move) and the live session folders under `.agents/tasks/`, a session's live folder being read in place of its archived copy, as `memar session show` does. Each hit names its origin — `dev-knowledge:.agents/tasks/<id>/<file>` or `.agents/tasks/<id>/<file>` — and both verbs' help says a hit from a session is that session's record, "never a ruling" (`memar content find --help`, `memar content search --help`). The value set and what each value reads are declared once, in `modules/knowledge/text/primitive/corpus_source.py`; the git reads are in `.agents/scripts/modules-plugable/computer/git/services/_git_records.py`; the MCP tools carry the filter as an enumerated array without extra code. The owner's ruling of 2026-10-19 was that the reach belongs to `memar content` as a filter by which the agent says where to read from, not to a new verb. Checks run for this essay: `git grep -l -i compaction dev-knowledge -- .agents/tasks` lists 25 files, and `memar content search compaction --from sessions` lists the same 25 (compared file by file) plus hits in 8 live folders; `memar content search "T124124Z-3000-0" --from sessions` finds the archived session's records, while without the flag it finds no session record; the fix's own tests, `python modules/knowledge/content/tests/session_records.py`, ran 18 tests, OK. A project whose preferences say `records: off` or give `records` a value it may not take, a folder that is not a repository's top, and a repository without the branch each produce a note on standard error rather than a silent empty answer (`modules/knowledge/content/services/session_records.py`, `archive_note`). Its limits, as they stand: with `--from sessions` every live folder under `.agents/tasks/` is read, other sessions' and the asking session's own included, and only the id in each hit tells them apart; a hit is a session's claim, to be checked, never a ruling; it is reached only when an agent asks for it, and the skill names no point at which to ask (`SKILL.md` has no `--from`), where context-mode's instruction file tells its agent to search before asking the user; `find` ranks by word similarity and `search` by pattern, and neither has been measured on a later question; the corpus reads documents and code as it always did, so `.py` and `.ts` files are not in the `code` source; and the lessons of a chat that opens no session are not there to be found (next item).
- **A chat that opens no session leaves no record of what it learned.** [Memar's skill](../../.agents/skills/memar/SKILL.md) says "a question answered in chat opens none" and that a request to investigate and apply nothing "opens no session" (`SKILL.md:29-30`). That is a considered rule against the cost of sessions, and it also means that the lessons of an ordinary chat have no place unless the owner or the agent routes them to a document by hand ([Documentation → Results routing](../../modules-plugable/knowledge/documentation/documentation.md#results-routing) names the homes for results of documentation work, not for the lessons of a conversation). The owner's stated aim — that the lessons of every chat and session be stored so that a later chat can answer a similar question — is not met by this rule alone, and searching sessions does not touch it: a chat without a session writes nothing there. The agent runtime's own memory is not the answer either: the owner's standing note there says rulings and learnings go into Memar's documents, not into the runtime's memory. The owner has ruled the principle (2026-10-19): a chat's lesson either appears in the documents and code or a session is opened for it, with no third way. The rule that says so is not yet written in the skill or the Documentation practice, so the gap stands until it is.
- **No instrument measures a session's context cost.** [The size of a task](../../modules-plugable/knowledge/documentation/handoff/handoff.practice.md#the-size-of-a-task) says so itself: "No numeric threshold for merging is set until a real session's cost, load and re-reads both counted, has been measured; this rule is provisional until then." context-mode shows what such an instrument looks like and, through ADR 0004, how its ratio drifts.
- **Reading before acting rests on the agent.** Known and recorded (Skills README, line 17). Memar's reading arrives as command output now, which is stronger than a pointer; there is still no check that the act's kind was read before the first edit.
- **Compaction is recognised by the agent.** The skill's rule depends on the agent seeing a summary at the head of its context (`SKILL.md:39`). A host event would settle it where one exists. This is runtime behavior; whether it belongs in Memar's skill or in the Organization project, which the owner's note of 2026-10-13 names for "how agents are run" ([Preferences](https://github.com/GeniusesGroup/memar/blob/6833d19b/.agents/memar/preferences.md)), is not settled here.
- **A command's output is policed by prose.** `SKILL.md:40` says to ask for the least output that answers; the commands split long output into ordered parts, but no command refuses to print more than a stated ceiling by default. The part-splitting and `--after` are the answer so far.
- **Memar reaches a few runtimes through one skill.** It has no adapter layer of the kind in section 3, item 6, and the comparison method's standing principle is that a consuming project installs a pointer, not a plugin ([README → Using Memar in another project](../../README.md#using-memar-in-another-project)). That is a position, not a gap.
- **The hand-back is a reference by convention.** Memar's research already records the shape ("sub-agents … return condensed summaries"; "pass references, not copies, back" — [Task Research 002, section 2](../../modules/management/task/task.research.002.md)), and context-mode's snapshot is the same shape in code: "the snapshot is a table of contents", with runnable retrieval calls (`src/session/snapshot.ts:12-13`, `toolCall()`). The two agree; neither adds to the other.

## 7. The adoption filter
The method writes toward absorbing what is durable into Memar's homes (rule 1). The owner's ruling of 2026-10-12, recorded in the [Context7 essay](context7.001.md#7-the-adoption-filter), applies here: no candidate becomes a rule written from a neighbouring product, and a candidate is placed as an open question only where there is a home whose subject it is. The owner's note of 2026-10-13 adds a second filter: an idea that needs concepts Memar does not define — a model, how a model is chosen, how agents are run — most likely belongs in the Organization repository ([Preferences](https://github.com/GeniusesGroup/memar/blob/6833d19b/.agents/memar/preferences.md)). Both filters are applied below. The questions are held by one queued task, `20261019-T155821Z-13024`, whose plan records the owner's rulings.

### Candidates considered for absorption
- **Recall of earlier work by question, with the origin of each hit stated.** The obligation is the owner's, stated for Memar's own purpose: what a chat or a session learned must be findable by a later one that meets a similar question. It has three durable parts: a retrieval reaches the archived session records and not only the live documents; each hit says where it came from (a document, a session's report, a chat's note) so that it is read as a claim to check, not as a settled fact — the rule Memar's own [Terminology → AI Implications](../terminology.md#ai-implications) gives for weighing a source; and a hit from a session is not mistaken for a ruling. context-mode shows that the retrieval part is a small, finished piece of work (FTS5 over events and memory files; its origin labels are coarse, section 3, item 10); it also shows the cost of letting heuristic capture decide what is stored (section 4, item 2). Disposition: done in `memar content` as a filter (section 6, first item), carrying the first two parts by the archive being reached and each hit naming its session and file, and the third by the verbs' help. Left with the queued session: when an agent should ask — a question about the skill, not about the verbs — and whether the marking of a session's hit (its path, and the verbs' help) is enough.
- **A routine that turns a chat's lesson into a record without opening a task.** The durable part is the gap itself (section 6, second item), not any capture mechanism. Disposition: the owner has ruled the principle — the lesson appears in the documents and code, or a session is opened for it; the queued session writes that rule and weighs what opening a session for a lesson costs against the skill's rule that a chat answer opens none.
- **A refusal or redirect text that an agent will read must state what happened, say that the task is possible, and name the next call.** The obligation is durable: it stays true as models change, because it concerns what an instruction that arrives at the moment of refusal does to a reader that acts on it, and it has a reproduced counter-instance (ADR 0003). It is not context-mode's mechanism; it is a property of agent-facing text, which Memar places under Communication ([Agency → Prompt Engineering and Harness Engineering](../agency.md#prompt-engineering-and-harness-engineering)). Memar's own scripts speak to agents (`--after is refused without it`, `refused` in `memar content get-act-context`). Disposition: question 1 of the queued session. It is not written as a rule here.
- **Enforcement by the host's event rather than by compliance.** The durable part is the claim that a one-time instruction decays after compaction and that a re-fired or enforced one does not (`README.md:1606`; ADR 0003). The mechanism — hooks per host — is packaging. Disposition: question 3 of the queued session, because it is a question about the skill's own method ("Partly solved" in the Skills README); and an item for the Organization project, because how a host runs an agent is that project's subject. Not taken into Memar as a rule.
- **A measure of context spent per session, with its formula stated.** The durable part is not the number but ADR 0004's lesson: a ratio that has two denominators drifts when two fixes touch it. Memar cannot write a threshold without a measurement ([The size of a task](../../modules-plugable/knowledge/documentation/handoff/handoff.practice.md#the-size-of-a-task)). Disposition: question 2 of the queued session, framed as what to measure and how its formula would be stated, not as adopting `ctx_stats`.
- **Re-fire cadence for guidance, as a measured value.** Packaging of the enforcement item; not taken.
- **Reuse the host's own permission rules instead of a parallel configuration.** Memar's rule is no hidden inputs ([Software → No Hidden Inputs](../../modules/process/software/software.md)); the same value stated from the other side. Disposition: already present in spirit; no new text.
- **Honest per-host capability grids with explicit absences.** Memar's triple-marking requirement already asks that capability not enacted be marked wherever a reader reaches it ([Documentation — Comparison → Method requirements added by practice](../../modules-plugable/knowledge/documentation/comparison/comparison.md#method-requirements-added-by-practice), item 4); context-mode's platform grids are a worked example of a project doing it, and it is cited as that, nothing more.

### Reject
- **Automatic extraction of decisions and constraints by pattern from user prompts and tool output** as a source of recorded decisions. A heuristic that records "looks like a correction" does not record a decision (section 4, item 2); as continuity for a working state it is sound, as a record it is not. Disposition: stays in this essay only; Memar already holds that a decision is claimed by a party.
- **Ephemeral memory as the default.** Short retention of prior-session data — seven days for events by code, 14 for content, whatever `README.md:41` says — is right for what the project is and contrary to the point of a Memar session. Disposition: stays in this essay only.
- **Prose commands as the primary instrument** ("MANDATORY", "BLOCKED — do NOT attempt"). Memar's [MCP essay](mcp.001.md) already concluded that an interface the model must obey as prose, not read as a type, is the weaker delivery; ADR 0003 is further evidence of the same failure inside a product that chose the other way. Disposition: already present; no new text.
- **A bytes-saved headline as the measure of the benefit.** Section 5, items 1 and 2. Stays in this essay only.
- **Guessing the host from the filesystem.** Section 5, item 8. Already covered by the no-hidden-inputs rule.

## 8. Possible relationship
1. **On window hygiene context-mode is a companion; on resuming and recall it is a rival in purpose.** A Memar session on a host with context-mode gets a cleaner window; the two can run together without contradiction. But both claim the same ground in "continue where we left off" and in "find what we did before". context-mode's recall is prompted by its instruction file and served from its FTS5 store; Memar's is reached on request over its records, matched by word similarity or pattern, and neither has been measured against the other. Two readings are open to the owner: treat context-mode as what Memar's aim must exceed (curated, attributed, durable) with a retrieval at least as capable — `--from sessions` is a first step on this reading, not proof of the capability; or treat it as a place where a Memar-built system may use a neighbour's retrieval over Memar's records. The second would need the records to be readable by something other than `memar`, which they are (plain files on a branch), and would bring the question of what a third party may read.
2. **Its code-execution sandbox is the thing Memar's own "mechanical" kind already points at.** Memar's skill says a step that counts or searches by a given rule is mechanical, and the knowledge module separates prose recipes from executable generative services ([Knowledge → Knowledge and Code](../../modules/knowledge/knowledge.md#knowledge-and-code)). "Think in Code" is the runtime-side statement of the same split; there is nothing to import.
3. **The fixtures link it to the Context7 essay.** `BENCHMARK.md:36-39,57-62` uses Context7 outputs as inputs. context-mode is the consumer-side answer to a cost that [Context7](context7.001.md) creates (retrieved documents are large) and the [spec-kit essay](spec-kit.001.md) names as the binding constraint (context-window exhaustion, item 9). The three essays together describe one stack from the corpus down to the window; Memar's place in it is above, as the model that decides what is worth retrieving at all.
4. **The ADR practice is a better neighbour than the product.** A project that writes down a reversal, with the number that exposed it, is doing what Memar's comparison method asks of its own essays. That is worth saying to the people who build it, whatever the licence.

## 9. Decision
context-mode is not a substitute for Memar: it does not decide what the work is, or record who decided it. It is, however, a working rival on two surfaces Memar names as its own aims — resuming after a cut, and recalling earlier work to answer a later question. On the second, Memar's records are the deeper and its retrieval is the younger: `memar content find` and `search` with `--from sessions` reach the archived records and the live session folders on request, each hit marked as a session's claim (section 6), while context-mode's agent is told to search before asking and, on hosts with its hooks, its capture covers every conversation it runs in, where a Memar chat that opens no session leaves no lesson to find (ruled in principle, rule not yet written).

Measured against its own purpose, context-mode is a serious, honestly documented tool with real engineering in it — enforcement by host event, a measured account of why instruction decays, a cross-source recall with origin labels, hardening with reasons, an unusually candid ADR record — and with limits (section 5): a headline that counts bytes, counts and descriptions that disagree with the code, one number with no source, heuristic capture, and a memory that is deliberately short-lived.

Memar takes five questions from the examination and no machinery. Recall over archived records is answered by the owner's ruling and built in Memar's own verbs, not borrowed; the capture of a chat's lessons is ruled in principle and awaits its rule; what a refusal text must say, what a session's context cost would be measured by, and whether compaction recovery is Memar's or a host's are the queued session's questions 1 to 3, each placed with the home whose subject it is. Nothing is written into Memar as a rule from this essay, in keeping with the owner's ruling of 2026-10-12.

Two readings the examination corrects. That Memar "ships no hooks and no measure" is true and already recorded as a silence (Skills README, line 17; Handoff Practice, line 102), but it is not the largest gap; the largest is that a record which cannot be asked a question is not yet knowledge anyone can use, which is why the reach of `memar content` into the records matters more than a hook. And that context-mode's way of storing (events by pattern, short retention) is a worse answer than Memar's is true about what is stored and not yet shown about whether it works: now that both can be searched, the comparison that remains is of answers to later questions, which neither project has measured.
