## 1. What each project is
### Tensorus (self-definition)
Tensorus calls itself an "Agentic Tensor Database/Data Lake" (`README.md:11`). Its own summary: "a specialized data platform focused on the native management and manipulation of tensor data. Unlike traditional databases that treat tensors as opaque blobs, Tensorus understands tensor structure and enables tensor-native queries and operations. It provides the foundation for AI and machine learning workflows where tensors are first-class citizens" (`README.md:21`). Its stated core purpose is "tensor-native data management where tensors are stored, queried, and operated on based on their mathematical properties — not just as raw bytes" (`README.md:34`).

What it ships toward that purpose: native tensor storage with tensor-operation-based similarity queries, a library of 40+ tensor operations (decompositions, linear algebra, transformations) integrated with storage, full computational lineage and operation-history tracking, and a production-oriented service surface (`README.md:27-30`). Agents and natural-language queries are explicitly marked as planned and conceptual, not shipped (`README.md:31-32`, and at length `README.md:258-270`).

### Memar (self-definition)
Memar is a domain-agnostic framework for developing systems, not only software — "a framework for developing any system, including software, hardware, buildings, and organizations" ([Framework](../framework.md) — **Evidence**). It states its own purpose as a chain, Knowledge → Thinking → Intelligence → Agency → Goals ([Framework → Memar's Purpose Space](../framework.md#memars-purpose-space-from-knowledge-to-agency) — **Evidence**), and its own model of work as: the model is the primary architectural artifact, contracts live in documents, and generative work lives in callable modules ([Knowledge → Knowledge and Code](../knowledge.md#knowledge-and-code) — **Evidence**).

Memar's knowledge principles are "intentionally principle-level; implementation belongs to domain-specific projects" ([Knowledge](../knowledge.md) — **Evidence**, `knowledge.md:12`). Memar ships no storage engine, no math library, and no running service.

### Category distinction
The two projects answer different questions, and the questions are not adjacent.

- Tensorus's question: **given tensors as the working material of AI/ML, where do we keep them so their mathematics stays queryable, and what operations run against that store?**
- Memar's question: **what shared model of systems and knowledge is this work conducted inside, and how does that model stay coherent as the system changes?**

In Memar's own vocabulary this is the framework/sub-framework distinction: Tensorus is a bounded slice of the kind Memar names as examples of sub-frameworks — a valuable, incomplete guide to full-system work — while Memar claims the complete-framework job. A team can develop a tensor-backed system inside Memar and use Tensorus as that system's store. Neither replaces the other.

Correction of reading, on the owner's note of 2026-10-13: "the questions are not adjacent" and "not in the same category" are claims about Memar the framework and Tensorus the platform, and they were read in this essay's first form as a claim that Tensorus has no bearing on the owner's work. They do not say that. A large part of the work Tensorus makes doable is being done in the owner's private organization project, because it is tied to many matters Memar has no home for; the distinction is why that work lives there and not in Memar, not a statement that the two are unrelated.

## 2. Source status and maturity
The inspected checkout presents a single squashed commit ("Move tensorus-v1 codebase"), so no history is reviewable and no per-change rationale exists in version control. Two small drifts were verified directly: the README badge advertises `v0.0.5` (`README.md:15`) while `pyproject.toml` declares `version = "0.1.0"`; and `README.md:185` points to a `QUICKSTART.md` migration guide whose file is absent from the checkout. The Streamlit page filenames described in the README (`01_dashboard.py`-style) do not match the shipped `1_Dashboard.py` / `*_v2.py` names. None of these affects the architecture; all are noted because a data platform's documentation is part of its trust surface.

A second pass, run by a different method (a claim-by-claim evidence audit rather than a survey), found the material that bears most directly on maturity: the repository root carries a four-file self-investigation dated 7 January 2026 — `INVESTIGATION_README.md`, `INVESTIGATION_REPORT.md`, `PRACTICAL_FIXES_REQUIRED.md`, `EXECUTIVE_SUMMARY.md` — whose verdict is "Partially — Good for prototyping, NOT ready for production" (`EXECUTIVE_SUMMARY.md:13`), an overall score of 6.5/10 (`INVESTIGATION_REPORT.md:9`), and a prioritized P0/P1 fix list whose first items are a vector-database SDK parameter mismatch, embedding-agent initialization, and examples that do not run out of the box (`PRACTICAL_FIXES_REQUIRED.md:15-86`). The set names Tensorus v0.1.0, which corroborates the badge drift above. The four files cross-link each other and nothing else in the repository links them: the README never mentions them, and the `docs/executive_overview.md` it does link is a different document. This is the sharpest single fact in the comparison, because the project's own audit contradicts the adjective on its own front door while remaining invisible from it.

Maturity is honestly disclosed where it matters most: agent orchestration, NQL, distributed storage, and the external models package are all marked conceptual or future, and the SDK disables NQL and embeddings by default. This candor is credited in section 3 rather than held against the project — with the qualification section 2's second paragraph records, that the candor reaches the code and the README's feature lists but not the repository's own front door or its maturity adjective.

## 3. What Tensorus has that Memar does not
Stated as genuine strengths, each with the evidence that supports it. This is an inventory, not a shopping list — the filter is in section 7.

1. **Math-aware storage as a real mechanism.** Tensors are stored with per-dataset schemas, pluggable compression, chunking for oversized tensors, and three coexisting index families: metadata indexes (hash/range/property), precomputed mathematical descriptors (`TensorDescriptor`: norms, sparsity, rank/trace/determinant/condition summaries), and a partitioned vector index for text embeddings. Memar's knowledge principles prescribe "storage model is not content model" and "identity independent of location" without supplying any store; Tensorus supplies one for its domain.
2. **Compatibility and property queries, not just similarity.** Beyond nearest-neighbor search, the SDK answers `by_shape`, `by_norm`, `by_property`, `matmul_compatible`, and `decomposition_candidates` — questions about whether two tensors can legally meet in an operation. This is a domain-specific query vocabulary Memar has no counterpart for and should not invent one for.
3. **Lineage as an audit trail.** Every operation is recorded with its type, operands, and result, exportable (including DOT graph form) and queryable per tensor. This is the executable instance of a principle Memar states abstractly (explicit context recovery); Tensorus shows what it costs to actually keep.
4. **A candid conceptual/future boundary.** Planned work (agents, NQL, distributed storage, streaming, external models) is labeled conceptual in the README, in code comments, and in SDK defaults (disabled until opted in), and the repository carries a dated self-audit that scores the project 6.5/10 and rules it "NOT ready for production" (section 2). Of all projects compared in this folder so far, Tensorus is the clearest about which claims are shipped and which are drawn — and the only one that has written its own unfavorable findings down. That disclosure discipline is the single most transferable lesson in this comparison, with the boundary condition section 5 records: the disclosure is real, and its placement is not — nothing a reader arrives at leads to it.
5. **A complete runnable service surface.** FastAPI application with typed endpoints, a unified Python SDK, a CLI, Docker and Compose packaging, Postgres-backed metadata, audit logging, API-key authentication, and a Streamlit operations dashboard. Memar deliberately supplies none of this; the contrast shows what "implementation belongs to domain-specific projects" looks like when a project actually carries it.

## 4. Where Memar is stronger
1. **Framework against sub-framework.** Tensorus covers one slice — tensor CRUD, math, and embedding search for AI/ML workloads — and is silent on everything outside it: modeling, language, substrate, organization, and any non-software system. Memar's framework/sub-framework distinction predicts exactly this shape: a bounded slice that needs glue the moment the work leaves its slice.
2. **Documents against knowledge.** Memar's standing claim is that "a document is a frozen projection of knowledge" and a system storing documents while losing context, relationships, and rationale "has lost knowledge while keeping its artifacts intact" ([Knowledge](../knowledge.md) — **Evidence**, `knowledge.md:12`). Tensorus stores tensors with operation provenance — it records *what was computed from what*, not *why it mattered, what was rejected, or what decision it served*. Op lineage and decision rationale are different things, and only Memar's apparatus (changelog provenance, handoff records, research companions) keeps the second.
3. **One continuous mental model against a demo-console sprawl.** Tensorus teaches itself through a 1,486-line README, twelve docs pages, eight examples, thirteen Streamlit pages, and three spellings of the server invocation — with the drifts recorded in section 2. Memar's Content Rule ("repetition is where documents go to drift apart") diagnoses this precisely: every restated surface is a future inconsistency.
4. **Design space against deployment checklist.** Memar's Framework question — *what kinds of solutions are allowed?* ([Framework](../framework.md) — **Evidence**, `framework.md:59`) — has no counterpart in Tensorus: there is no modeling gate, no terminology authority, and no statement of which solutions are out of bounds. Two teams can mean different things by `dataset`, `embedding`, `agent`, and `workflow` with no arbiter; in Memar's vocabulary `agent` names the exercise of intelligence toward objectives, while in Tensorus it names a runtime class — a conflation with no one assigned to resolve it.

## 5. Limits and failure modes in Tensorus
Stated without calling the project worthless — these are failure modes when it is treated as a development framework.

1. **Demo-grade defaults behind production-grade language.** The README claims "Production-Grade Architecture" and "Enterprise security, scaling" while shipping `in_memory` as the default backend, open CORS, manually provisioned keys, a local audit log, and Compose Postgres on a nonstandard port — with TLS, reverse proxying, secrets management, and multi-node operation delegated to the operator. The repository's own audit reaches the same verdict and then names the gaps the README does not: a P0 list of SDK parameter mismatches, agent initialization defects, and non-running examples (`PRACTICAL_FIXES_REQUIRED.md:15-86`), judged "NOT ready for production" (`EXECUTIVE_SUMMARY.md:13`). The hardening list being documented is good; the adjective being ahead of the default, and the audit of that gap being unreachable from the front door, is not.
2. **A self-audit that no entry point reaches.** Four files in the repository root carry a dated, scored, prioritized verdict on the project, and nothing in the repository links them from anywhere a reader arrives. Two consequences, and they point opposite ways: the material is honest and specific — a project that scores itself 6.5/10 has earned a credit no marketing claim could buy — and it is simultaneously unowned, its provenance (a four-hour investigation, per its own README) unverifiable, and its conclusions contradicted by the README that never mentions it. This is the concrete instance of what [Knowledge Research 002 — Material With No Producing Decision](../knowledge.changelog.md) asks about: material that exists in the medium without any decision having produced it, sitting next to material whose producing decision is a marketing adjective.
3. **The SDK facade is narrower than the library.** "40+ tensor operations" exist in the operations library and behind typed API routes, but the unified `Tensorus` facade exposes a handful (matmul, stack, SVD, reshape, transpose). A reader judging the project by its front door undercounts it; a team adopting it must go around the facade for its headline feature.
4. **Agent scaffolding that can be mistaken for an orchestrator.** `WorkflowTask` carries dependency fields and the README names DAG-based execution, but the agent classes are self-described as conceptual and the SDK's agent factories reference globals still set to `None`. Nothing here is misrepresented in isolation — the marks are all present — but the parts compose, at a glance, into something that looks production-ready and is not.
5. **Regex NQL as a query story.** The natural-language path is keyword-pattern matching with documented limits (no AND/OR, counts only) and an opt-in LLM rewrite behind an external key. As a discovery aid over tensor metadata this is proportionate; as "natural language queries" in the headline sense it is a placeholder wearing the feature's name.
6. **Single hierarchy, math properties, no rationale.** Containment is `dataset/record_id`; knowledge distinctions Memar treats as load-bearing (data vs information vs knowledge vs document, relationships as first-class, classification beyond one hierarchy, units finer than documents) have no counterpart. This is a correct scoping decision for a tensor store — and exactly why the store cannot serve as the development framework.

## 6. Costs and limits on both sides
### Tensorus
- A tensor-shaped answer to every question: anything that is not a tensor, an embedding, or an operation over them is outside the model.
- Durability, scale, and hardening are operator work; the defaults optimize for trying, not for running.
- Documentation sprawl with verified drift (version badge, missing QUICKSTART, page names) in a 1,486-line front door.
- Agent/NQL claims that require careful reading to price correctly — the labels are honest, the composition flatters.

### Memar
- **No executable anything in the compared layer.** Memar states the lineage principle; Tensorus keeps lineage. Memar states context recovery; Tensorus ships the audit log. Every concrete mechanism in section 3 is something Memar points at but does not provide — by design, and still a cost to anyone who must build it.
- **No disclosure convention as explicit as Tensorus's.** Memar has document `Status` and changelogs, but no single stated rule that planned/conceptual material must be labeled as such wherever it appears, including code defaults. The project that needs the lesson most here is Memar, not Tensorus.
- **No adoption surface.** There is no SDK, no service, no dashboard — nothing to try in three minutes. That is the correct price of being a framework rather than a product, and it is still the reason a team reaches for Tensorus first.

## 7. What Memar can learn
### Absorb
1. **A disclosure rule for the conceptual.** Wherever Memar material describes planned, prototype, or externally-hosted capability — research companions, handoff anticipations, "no home yet; owed" rows — it should carry the same label in prose, in code defaults, and in entry points, all three. Tensorus does this (README marks, code comments, disabled-by-default flags); Memar's `Status` ladder plus changelog provenance already gives it the homes, but nothing currently *requires* the triple marking. Home: [Documentation → Content Rule](../documentation.md#content-rule-no-fabricated-or-redundant-provenance) and the script-level `check`. (Since absorbed: the Content Rule's fifth rule now states it; the script-level check half is deferred.)
2. **Lineage-shaped changelog discipline as the worked example.** Tensorus's operation history (typed operation, operands, result, queryable per artifact) is a concrete image of what Memar's propagation ledger aspires to for documents. No change is proposed to the ledger; the proposal is to cite the shape as the bar — every `Propagates to` entry should be answerable to "which operation, over which inputs, produced which result," or state why it cannot be.

### Adapt
3. **Compatibility queries as a modeling question.** `matmul_compatible` and `decomposition_candidates` ask "can these two things legally meet?" Memar's modeling practice could ask the same of concepts: stated once, domain-generally — what must hold for two models, two protocols, or two documents to compose — without importing any tensor vocabulary. Candidate home: the modeling practice, as a review question rather than a mechanism.
4. **The three-spellings lesson for entry points.** Tensorus documents three invocations for one server. Memar's discovery scripts already hold the cleaner position (the script declares its interface; prose does not reduplicate it). The adaptation is negative: keep it, and cite this comparison the next time prose is tempted to restate an entry point.

### Reject
- A tensor store, an operations library, an SDK facade, a service surface, or any domain runtime as Memar doctrine. Implementation belongs to domain-specific projects; the principle already says so, and this comparison is evidence for it, not an occasion to revisit it.
- Dataset/record containment, math-descriptor indexes, or op-lineage schemas as knowledge-model content. They answer a domain's questions, not the framework's.
- The 1,486-line front door, the Streamlit-card packaging, and the `tsr_`-key ritual as distribution shapes. Memar's pointer-based consumption stands.
- "Production-grade" as an adjective for documented-but-operator-owed hardening. If Memar ever needs the corresponding rule, it is: adjectives of maturity must be true of defaults, not of documented delegate lists.

### Separate research
5. **Whether Memar's "owed" rows need Tensorus-style disclosure.** `Software → The software life cycle` records requirements, project management, and quality assurance as owed or prior art. Is that record sufficient under the disclosure rule proposed in item 1, or does each owed row need the triple marking (prose label, default behavior, entry-point visibility)? Research, not a change — the rows may already satisfy the rule, and the question is worth answering explicitly. (Status since: the rule in item 1 is stated and the software rows were checked against it in the same pass — each carries a prose label and none promises a default behavior or an entry point, because none is enacted. The question survives as "is prose marking alone sufficient for a row with no code surface?", which is a smaller question than the one opened here.)
6. **Rationale lineage.** Tensorus keeps operation lineage; Memar keeps decision provenance in changelogs and handoffs. Is there a named, minimal record for "which rejected alternative this decision closed over" that survives across documents — distinct from `Considered and not done` lines that live and die inside one entry? The spec-kit comparison asked a sibling question about unrequested material; this one asks about undecided-against material. Research, not a change. (Since investigated, and held open with its sibling: the hindsight comparison's separate-research item 6 asks the same question about supersession mechanics, and the two were investigated together rather than tracked as threads that would drift apart — [Knowledge Handoff → Supersession](../knowledge.handoff.md#supersession-which-home-owns-the-obligation-and-is-it-a-norm-or-a-check).)

## 8. Possible relationship
1. **Memar remains the authority** for concepts, terminology, model, protocol contracts, knowledge discipline, and change provenance.
2. **Tensorus is a domain store that may run inside a Memar development.** A project whose domain is tensor-heavy (ML systems, signal processing, scientific computing) may adopt Tensorus as its persistence and compute substrate without adopting its README as doctrine, its agent scaffolding as agency, or its Streamlit console as process.
3. **The tensors it stores are evidence, not knowledge.** A stored tensor with full op lineage is an artifact with provenance; what it means, why it was produced, and what decision it serves live in the project's model and records, not in the store.
4. **Compatibility requires one explicit contract:** which document owns a claim about a tensor (the store's schema or the project's model), whether governing statements are read at runtime or copied into artifacts, and what makes a lineage entry evidence rather than exhaust.
5. **Where the adoption work lives.** The owner's note of 2026-10-13: a large part of the doable Tensorus work is being done in the private organization project, which is where the explicit contract of item 4 belongs, and Memar's part is only the framework statements it can already make (the disclosure rule, the lineage question). The consequence for this essay is that its rejections (a tensor store, an operations library, a service surface as Memar doctrine) are rejections for Memar and say nothing about whether the organization project adopts the platform; a session for the contract was queued on that project's side (20261013-T072632Z-2072).

## 9. Decision
Tensorus is not a substitute for Memar and is not in the same category (a statement about Memar as a framework, not about whether the owner's wider work uses Tensorus: section 1, "Correction of reading", and section 8, item 5). It is a genuinely useful tensor-native data platform with unusually honest disclosure of its own conceptual boundary — and that honesty is both its most Memar-compatible trait and the mechanism this comparison proposes Memar adopt. The comparison justifies no change to Memar's governing method. It identifies two absorptions that strengthen mechanisms Memar already owns — triple-marked disclosure of the conceptual, now a Content Rule, and lineage as the bar for propagation entries, still an open question — two adaptations stated as questions rather than imports, and two research threads Memar deferred to itself, one of which was later merged with the hindsight comparison's sibling into a single inquiry.

The strongest argument Memar has here is not against Tensorus but with it: a domain project that labels its own unfinished work in three places at once — and then writes itself a 6.5/10 — demonstrates, in running code, a discipline the framework prescribes but does not itself fully practice. The finding that sharpened it came from the second pass and cuts the same way twice: Tensorus's disclosure lives where a reader arrives, except for the one file where it would have mattered most, and its P0 list is the proof that a written-down failure is only half a disclosure until an entry point carries it. That is an argument from a stated principle meeting observed evidence, which is the only kind worth making.

## 10. Open for critique
- Whether the credit in section 3 is sufficient, and whether any of the five items is stronger than stated.
- Whether the disclosure rule (item 1) is correctly scoped, or whether triple marking is ceremony that will rot like the README drifts it is meant to prevent.
- Whether the lineage-as-bar proposal (item 2) asks more of `Propagates to` entries than document provenance can bear.
- Whether the rationale-lineage question (item 6) duplicates `Considered and not done` rather than extending it. The investigation behind it found that `Considered and not done` already holds the dropped reasoning, and that the missing piece is that nothing *requires* a superseding entry to use it — which is the norm-versus-check decision held at [Knowledge Handoff → Supersession](../knowledge.handoff.md#supersession-which-home-owns-the-obligation-and-is-it-a-norm-or-a-check).
- Whether section 5 item 2 (the unlinked self-audit) is fair to material a contributor may have added deliberately as an appendix. Nothing suggests a decision produced it and nothing suggests one removed it, which is exactly the condition that record describes; the comparison's claim is about reachability, not about intent.
- Any unfair characterization of Tensorus. Every claim here is pinned to a file and line so it can be checked; the ones that should be re-read first are the self-audit verdict, the version drift, the missing QUICKSTART, and the SDK facade breadth.
