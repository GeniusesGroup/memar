## 1. What each project is

### LangChain (self-definition)
The root README gives LangChain two names for itself in two places. Its tagline is "The agent engineering platform." (**Evidence**, `README.md:12`), and its body says "LangChain is a framework for building agents and LLM-powered applications." (**Evidence**, `README.md:24`). It addresses "developers" and "your engineering team" (**Evidence**, `README.md:61`, `README.md:64`), and it lists five products of an ecosystem — Deep Agents, LangGraph, Integrations, LangSmith and LangSmith Deployment — of which only the framework is in this repository (**Evidence**, `README.md:53-57`). The core package states a narrower job: "the base abstractions that power the LangChain ecosystem", with "any provider can implement the required interface" (**Evidence**, `libs/core/README.md:21`, `libs/core/README.md:25`), and says of itself that "No third-party integrations are defined here" (**Evidence**, `libs/core/langchain_core/__init__.py:7`). The current top-level package describes its job as the easiest way to start building agents, "built on top of LangGraph" (**Evidence**, `libs/langchain_v1/README.md:21`, `libs/langchain_v1/README.md:25`).

The three packages that carry the name share one description string, "Building applications with LLMs through composability" (**Evidence**, `libs/core/pyproject.toml:7`, `libs/langchain/pyproject.toml:7`, `libs/langchain_v1/pyproject.toml:7`), yet the current package contains no chain-composition code at all: its modules are agents, chat models, embeddings, MCP, messages, rate limiters and tools (**Evidence**, the directory listing of `libs/langchain_v1/langchain/`). The word "composability" survived the thing it described, and the project says so itself by marking the directory that still holds composition as "legacy, no new features" (**Evidence**, `AGENTS.md:23`).

### Memar (self-definition)
Memar is "a system development **framework** as **structure** document that gives you a structuralism mental model to understand the development model" (**Evidence**, `README.md:2`), and it refuses the role of an oracle: "Memar is not an authority that decides reality. Memar is a framework for constructing, examining, and refining mental models about systems." (**Evidence**, `README.md:4`) Its governing statements about delivery are boundaries rather than capabilities: the built system, the generated modules and the deployment are Enterprise work; the performed service over a live corpus is built in the Organization project; and a subject no Memar document governs is reported as an absence that becomes a question with an owner (**Evidence**, `README.md:30-31`).

### Category distinction and layers
The cut applied here is by the job a reader would hire each project for ([Documentation — Comparison → Fairness rules](../documentation-comparison.md#fairness-rules), rule 2), not by the layer names a stack diagram uses. Both projects say "framework", and the word hides four different jobs.

1. **Running an LLM application.** LangChain's job. The question: *how does a program call a model, give it tools, loop until it is done, and survive providers that differ?* The thing built is a runtime; the code is executed in production, and its correctness is the behaviour of calls.
2. **Building and keeping one model's truth.** Memar's job. The question: *how does a project build the model of its own system and keep it true as the system changes?* The thing built is a set of documents, and its correctness is whether the model is consistent and the system realizes it.
3. **Delivering a typed interface to a consumer.** Both touch it. Memar holds that the party that knows the service delivers its client, derived from the service's declaration, and that an AI agent is a consumer like any other (SDK → Working positions (`docs/modules/process/service-sdk.md#working-positions`), position 13 — **Evidence**, `docs/modules/process/service-sdk.md:46,65`). LangChain delivers the tool and the model as Python objects in one process and has no declaration of effect, and none apart from the object (a tool does carry an argument schema).
4. **Holding implementations to a contract.** Both touch it. LangChain ships the contract as an inheritable test suite; Memar holds that conformance is a decidable question settled from outside the author, and that a Test is a part of the system that owes it (Test → A Test Is Part of the System That Owes It (`docs/modules/process/test.md#a-test-is-part-of-the-system-that-owes-it`)).

The false rival appears when job 1 is read as an answer to job 2. A runtime that composes calls does not tell a project what its system is, and a model of a system does not call a provider. They meet at jobs 3 and 4, and at those two the comparison is a real one: the question is what each says about an interface and about a contract, not which one a team should install. LangChain is also several of its own layers at once, and they should not be judged as one: the abstractions package (`libs/core`), the agent runtime (`libs/langchain_v1`), the integration packages (`libs/partners`), the contract suite (`libs/standard-tests`), the capability data (`libs/model-profiles`), the legacy package (`libs/langchain`), and a generated orientation index (`openwiki/`). Several of those are strong at what they set out to do; the weaknesses below belong to particular layers and are named with them.

## 2. Source status of the inspected checkout
The checkout holds one commit, "release(langchain): 1.4.5 (#41226)" (**Evidence**, `git rev-list --count HEAD` = 1). The history is collapsed by the clone and not by the project: the repository is shallow (**Evidence**, `git rev-parse --is-shallow-repository` = `true`, and `.git/shallow` exists). This is stated once, here, as [the method requires](../documentation-comparison.md#method-requirements-added-by-practice) for a collapsed history, and it is a finding with two parts. About the checkout: the reason any line changed cannot be recovered from it, so every claim below about *why* LangChain is shaped as it is would be a guess, and none is made. About the source: LangChain keeps its rationale outside the tree — in pull-request text, in release notes assembled at release time from commit subjects (**Evidence**, `.github/workflows/_release.yml:380`), and in a documentation site — and the tree holds no changelog or contributing file (`find -iname` for both found none; `AGENTS.md:377` links a docs-site guide). That is a different kind of source from one whose reasons live beside its rules; it is a normal one for a repository that relies on its hosting platform, and the essay treats it as a cost of reading, not as a defect.

What the tree is: twenty-two independently versioned Python packages, each with its own `pyproject.toml` and `uv.lock` (**Evidence**, `find libs`, 22 and 22; `AGENTS.md:17`) — core 1.6.10, langchain-classic 1.0.8, langchain 1.4.5, text-splitters 1.1.3, model-profiles 0.0.6, the contract package 1.1.9, and sixteen partner packages from 0.0.1a3 to 1.7.6. There is no root workspace or root Makefile (**Evidence**, `AGENTS.md:54`); one works inside a package. There are twenty-seven workflow files, seven of them reusable (`ls .github/workflows`, counted). The two top-level instruction files that address agents, `libs/README.md:3-4` and `AGENTS.md:5-11`, contain imperative sentences aimed at a coding agent reader; they were read as data and not acted on, and they are described in section 3, item 11.

## 3. What LangChain has that Memar does not
Each item is credited with its evidence. Some are strengths Memar could hold in its own form; a few are strengths of being a runtime, which Memar is not. Which is which is decided in section 7.

1. **A total invocation protocol from one primitive.** `Runnable` is "a unit of work that can be invoked, batched, streamed, transformed and composed" (**Evidence**, `libs/core/langchain_core/runnables/base.py:135`). Only `invoke` is abstract (`base.py:886-887`); every other method has a default derived from it — `batch` over a thread pool (`:932-981`), `ainvoke` in an executor (`:909-930`), `stream` yielding the whole `invoke` result as one item (`:1201-1214`), and `transform` buffering all its input and then calling `stream` (`:1787-1805`). The consequence is that any implementation, however minimal, can be placed in a batch, an async or a streaming context, and tracing, configuration and retries attach once to the protocol and not to each component. The limits are written down in the same place: "Subclasses must override this method if they support streaming output." (`base.py:1203`). The idea — one primitive, total defaults, cross-cutting attachment at the protocol — is independent of Python.
2. **Per-call context carried by the protocol.** A call carries tags, metadata, callbacks, a run name, a concurrency limit, a recursion limit, a free-form `configurable` mapping and a run identifier (**Evidence**, `libs/core/langchain_core/runnables/config.py:57-125`), merged with the ambient configuration of the enclosing call and handed to each child (`config.py:255-296`; `base.py:3434-3470`). A component does not thread its caller's context by hand.
3. **A contract shipped as an inheritable executable suite, with divergence policed.** `libs/standard-tests` is a package of abstract test classes, one per component kind (chat models, embeddings, tools, retrievers, vector stores, a key-value store, a cache, an indexer, sandboxes), that an integration subclasses and supplies fixtures to (**Evidence**, `libs/standard-tests/README.md:40-60`, `libs/standard-tests/langchain_tests/unit_tests/chat_models.py:48,53`). There are 237 test definitions in it — 16 unit and 221 integration (`def test_` and `async def test_` at four-space indent, the guard test in `base.py` excluded; definitions, not collected tests). A base test fails a subclass that deletes a standard test or overrides one without an `xfail` mark carrying a reason (**Evidence**, `libs/standard-tests/langchain_tests/base.py:7-70`). Capabilities that an implementation may lack are declared as properties on the subclass — `has_tool_calling`, `has_structured_output`, `supports_image_inputs` and others (`unit_tests/chat_models.py:95-255`) — so "not offered" becomes a declared skip and not a silent pass. Twelve of the sixteen in-repo partners use it (counted by the pass).
4. **Interception at both ends and around a call.** Middleware has node hooks (`before_agent`, `before_model`, `after_model`, `after_agent`) that return a state update, and wrap hooks (`wrap_model_call`, `wrap_tool_call`) that receive a handler and may call it zero, one or many times (**Evidence**, `libs/langchain_v1/langchain/agents/middleware/types.py:431-823`). What a middleware can change is closed and named: the model request through an immutable `override` of a fixed set of fields, state through returned updates, and control flow through a `jump_to` allowed only where the hook declares it (`types.py:74-85,203-269,879-931`). Two shipped middlewares draw a line worth crediting by itself: `SummarizationMiddleware` replaces the stored history, and `ContextEditingMiddleware` edits only the copy the model sees, leaving the record whole (**Evidence**, `middleware/summarization.py:507-523`, `middleware/context_editing.py:270-274,296-300`).
5. **State with named durability.** Which agent state is checkpointed is decided field by field: messages and the to-do list persist; the per-run call counters and the live shell session are declared untracked; the control-flow jump is ephemeral (**Evidence**, `middleware/todo.py:42`, `middleware/tool_call_limit.py:48-49`, `middleware/model_call_limit.py:34`, `middleware/shell_tool.py:107-109`, `types.py:353`). Limits come in two scopes — thread (persisted) and run (not). The runtime that stores the checkpoint is outside the checkout; the *declaration of what is kept* is inside it.
6. **A closed set of human decisions, batched.** After the model proposes tool calls, the human-in-the-loop middleware raises one interrupt listing every pending action with the decisions allowed for it — approve, edit, reject, or respond for the tool (**Evidence**, `middleware/human_in_the_loop.py:65,344-392,456-481`). A decision outside the allowed set, or a count that does not match the pending calls, raises (`:384-392,483-489`); a misspelled or empty allowed set is rejected at construction because it "would otherwise be silently dropped" (`:279-304`); an edited call is substituted at execution while the history keeps what the model actually proposed, with a notice prepended to the result (`:31-38,541-661`).
7. **A typed result requested from a model and repaired by conversation.** A caller states a schema (a class, a dataclass, a typed dictionary, or a JSON schema, which is returned unvalidated so that the repair handler is inert for it — `structured_output.py:223-230`) and the library selects, per model call, between the provider's native structured output and a forced tool call, by the model's declared capability (**Evidence**, `libs/langchain_v1/langchain/agents/structured_output.py:195-315`, `libs/langchain_v1/langchain/agents/factory.py:1407-1422`). When validation fails, the error goes back to the model as a tool result and the model tries again, under a handler the caller configures (`factory.py:646-673`; `structured_output.py:210-231`).
8. **A capability record per model, with harvested data kept apart from hand overrides.** A profile is a typed record of a model's limits, modalities, reasoning and tool-calling support, attached to the chat model (**Evidence**, `libs/core/langchain_core/language_models/model_profile.py:12-170`). It is produced by a command that downloads a public model catalogue, merges per-provider overrides from a hand-kept file, and writes a generated module per partner (**Evidence**, `libs/model-profiles/langchain_model_profiles/cli.py:111-157,350-376`); a daily workflow refreshes it and opens a pull request whose body is a deterministic summary of the data change, not a model's prose (**Evidence**, `.github/workflows/refresh_model_profiles.yml:1-16`, `libs/model-profiles/langchain_model_profiles/_summary.py:1-9`). The record is marked beta and its fields are optional, which the type says (`model_profile.py:25-28`).
9. **A release that refuses what it can detect.** The release workflow fails if the requested version differs from the package's or already exists on the index, and fails closed if the index cannot be reached (**Evidence**, `.github/workflows/_release.yml`, the "Check version" step at about `:196-262`); for a core release it checks out each of the anthropic and openai partners and the contract package at their latest non-yanked published tag, installs the new core, and runs their tests before it publishes (`:664-692,740-745`, `partner: [ anthropic, openai ]` at `:603`) — unless the release input `skip-prior-published-package-checks` skips the job (`:648-657`), in which case publishing goes ahead; and 87 of the 89 external action references carry a full commit hash (counted by the pass; the other two are comment text). A separate check demands that each release pull request resolves its dependencies against the index before it merges (**Evidence**, `.github/workflows/check_release_deps.yml`).
10. **A deprecation record with a shape.** `@deprecated` takes `since`, `alternative`, `removal` and a `pending` level, and a parallel `@beta` marks unfinished surface (**Evidence**, `libs/core/langchain_core/_api/deprecation.py:119-130`, `_api/beta_decorator.py:32`). The legacy package is named as legacy in the directory table and in the agents file (`AGENTS.md:23`), and it is used at scale: 94 uses in the classic package, 14 in core (counted by the reviewer; the pass counted 15 including a docstring example).
11. **A generated orientation index that says what it is.** `openwiki/` is a set of Markdown pages generated from the code by a tool on a daily schedule. Each page carries front matter naming the source files it was written from, the tool, the time and a `verified` field; sidecar files record the commit and a source fingerprint per page (**Evidence**, `openwiki/architecture.md:37-40`, `openwiki/.page-manifest.json`, `openwiki/.last-update.json`). The agents file labels it "optional" and "not required startup reading", and tells an agent that source and tests are authoritative, that a brief's unknowns are "verification gaps", and that pages are not hand-edited (**Evidence**, `AGENTS.md:35,379-390`). The provenance discipline is the same one Memar asks of its own derived material; section 4, item 4 reports how the instance fared.
12. **Caveats written where the reader will meet them.** The limits of the protocol, of caching and of the validator machinery are stated in the docstrings of the code that has them (**Evidence**, `base.py:1203,3108`, `libs/core/langchain_core/language_models/base.py:198,222-240`). A reader of the code is warned before being surprised.

## 4. Where Memar is stronger
Each of these is a claim about what Memar states, not about what it has built; where Memar's own documents are silent on a point LangChain handles, section 6 and section 7 say so.

1. **LangChain's tool has no declared effect, so approval is keyed by the tool's name.** A search of the core tools package and the agent package for a read-only, destructive, idempotent or side-effect declaration found only a container option that mounts a filesystem read-only (**Evidence**, `libs/langchain_v1/langchain/agents/middleware/_execution.py:292`). The human-in-the-loop gate selects calls whose names are keys of a mapping and skips the rest, which are approved by default; within a named tool a caller may supply a `when` predicate over the call and its arguments (**Evidence**, `human_in_the_loop.py:209-227,256-258,394-425,456-465`) — a hook the caller writes, not a declaration the tool makes. The retry middleware retries every tool unless it is narrowed by name, and a search of its file for idempotency or side effects found nothing (**Evidence**, `middleware/tool_retry.py:137-156`). The MCP adapter copies a server's tool annotations — the destructive and read-only hints — into the tool's metadata and nothing in the library reads them; the one consumer is an example script, which treats a missing hint as not destructive (**Evidence**, `libs/langchain_v1/langchain/mcp/tools.py:186-206`, `libs/langchain_v1/examples/mcp/destructive_interrupt.py:34-37,52-62`). Memar states the ground on which the absence reads as a gap (session analysis; the judgment is this essay's, not Memar's): "Capability ≠ Authority ≠ Responsibility", authority bounded by domain, time and limits, "may still require verification for high-impact actions", and "failure and escalation behavior" among the important dimensions of interacting with an agent (**Evidence**, `docs/agency.md:743`, `docs/agency.md:715-724`, `docs/agency.md:1220`, `docs/agency.md:1575`). The owner's ruling of 2026-10-13 reframes what this finding shows about Memar: an SDK call is a way of calling, it does not itself act on the world; the effect lies in what the caller does with the answer, under the caller's own authority (his example: a greenhouse system calls a weather service of another organization, is told heavy rain is 90% likely in the coming hours, and itself decides to close its windows and slow its fans). Under that reading the comparison is between a runtime in which the tool is the actor, so its name is what a gate can key on, and a model in which the call informs and the consumer acts; the gate Memar's model implies sits on the consumer's act, which is the consumer's own matter (section 7, candidate 3). The finding about LangChain stands; the claim that Memar is stronger here does not extend beyond the statement of authority.
2. **Composition that is visible in the call.** LangChain's `|` builds a sequence by coercing its right operand by type: a function becomes a lambda runnable, a dictionary becomes a parallel one, anything else raises, so a bare dictionary literal changes meaning by its position in the expression (**Evidence**, `libs/core/langchain_core/runnables/base.py:674,6644-6670`). Extra keyword arguments to a sequence reach the first step only (`:3457-3460`, read by the drafter: `if i == 0:` passes `**kwargs`, the else branch does not). `RunnableLambda.deps` finds a function's dependencies by inspecting its closure (`:5071-5094`), and a retriever base class rewrites a subclass's async method at class creation when its signature lacks a parameter (**Evidence**, `libs/core/langchain_core/retrievers.py:146-160`). Middleware order is asymmetric: wrap hooks nest first-outermost, before-hooks run in list order and after-hooks in reverse (**Evidence**, `factory.py:281-298,1855-1895`). Memar's position is the opposite and it is a position, not an omission: Khayyam has no decorator syntax, and cross-cutting behaviour "is expressed as explicit, visible composition" because a decorator "silently alters what a method actually does at the call site" (**Evidence**, `docs/khayyam/metaprogramming.md:41-43`). Fairness: LangChain's costs are the costs of Python idioms at scale and Khayyam has not been run at that scale; the argument is about direction, and it is shown by LangChain's own maintainers writing docstrings that warn about several of these (middleware order, `factory.py:281-298`; lambda runnables and `transform`, `base.py:3105-3110`).
3. **A contract that is stated apart from the tests that check it** (a comparison of what Memar states with what LangChain built, as section 10 says). LangChain has no separate specification: the interface is a set of Python base classes in core and the behavioural contract is the test classes and their docstrings, which instruct implementers on how to mark a divergence (**Evidence**, `libs/standard-tests/langchain_tests/integration_tests/chat_models.py:1675-1678`, and the pass's finding that no specification file exists). Memar states that a Test names the Process whose expectations it holds, that its authority is derived from the document defining that Process, and that "a Test that contradicts that document is asserting a different Process than the one the system claims to realize" (**Evidence**, `docs/modules/process/test.md:54-62`); and that conformance is "a decidable question, not a judgment", settled by a party that did not write the rules (**Evidence**, `docs/protocol.md:225-232`). The consequence in LangChain is visible: the capability a test presumes is declared in two places — a property on the test subclass and a field in the model profile — with one point of contact (**Evidence**, `unit_tests/chat_models.py:95-255`, `integration_tests/chat_models.py:1705,1784`), and the library itself holds a third, a hand-kept list of model-name patterns, that can disagree with the profile (section 5, item 6). Memar's silence on a *shared* suite is stated in section 6.
4. **A derived orientation aid is never allowed to be the authority, and its drift is the evidence.** The generated wiki's own rule is sound (section 3, item 11); the instance shows what the rule is for. Fourteen claims were checked against the code by the pass: four held; seven were contradicted or stale; three were unsupported, incomplete or qualified (**Evidence**, the pass's section 4.5, recounted in the second-opinion record). Examples read by the drafter: the CI page says the lint pipeline includes "Markdown linting (via .markdownlint.json)" (`openwiki/ci-workflows.md:71`) while the lint workflow runs two `make` targets and a case-insensitive search for "markdownlint" outside the wiki finds only two editor configuration files; the partner-pattern page says the standard suite validates "Model profile: Presence and validity" (`openwiki/partner-pattern.md:748`) while no standard test does. Fairness, stated before the finding is used: the recorded commit is absent from the clone, so a contradiction may be drift after generation and not an error at generation (the two cannot be told apart here); the generator is a small model run by a daily job whose step is `continue-on-error` (**Evidence**, `.github/workflows/openwiki-update.yml`); and the project does what it can short of a check — the pages carry provenance and the agents file tells a reader to prefer the code. Memar's rule is that a mirror of a live collection "is a cache" and is not written ([Documentation → Content Rule](../documentation.md#content-rule-no-fabricated-or-redundant-provenance) — **Evidence**, `docs/documentation.md:31`), and its earlier essays rejected the generated report as the model's authority ([Graphify → Reject for Memar](graphify.001.md)). LangChain's instance is the first in this folder where the generated artifact is *measured* against its source. The owner's observation of 2026-10-13 is the principle underneath: a document must not state what is a cache of the code, because the code can speak for itself and changes easily while the document stays behind; and a document that has to exist belongs beside the code.
5. **Foreign things stay visibly foreign.** Core says "No third-party integrations are defined here" (**Evidence**, `langchain_core/__init__.py:7`) and its README says its dependencies are "not tied to any specific model provider" (`libs/core/README.md:31`). Its contents include provider block translators for seven modules covering five vendors (`libs/core/langchain_core/messages/block_translators/`), output parsers named for one provider's function-calling formats (`libs/core/langchain_core/output_parsers/openai_functions.py`, `openai_tools.py`), a deserialization allow-list in which eleven of fourteen namespaces are provider packages (`libs/core/langchain_core/load/load.py`, about `:134-148`), thirty-one of its 182 source files that contain the words "openai" or "anthropic" (case-sensitive; forty case-insensitive), and docstrings that import from the higher package (`libs/core/langchain_core/stores.py:51,252,275`). Memar's placement rule is that "a protocol that is not Memar's own belongs" in the library module, kept apart from Memar's model, with the standing of a guest adapter (the standing the MCP ruling gives that protocol — `modules/lib/lib.handoff.md:9`) (Lib (`modules/lib/lib.md`) — **Evidence**, `modules/lib/lib.md:10,18`; `modules/lib/lib.handoff.md:9`). Fairness: Memar's rule does not say who maintains a vendor-specific adapter or where it lives (section 6, Memar, item 6), and LangChain's drift is the ordinary pressure of shipping to providers that change monthly.
6. **State that must survive is externalized for the next reader, with its decisions.** The tree holds no changelog, and the project's rationale sits in pull-request text outside it (section 2). Memar's handoffs, changelogs and the session plan and report preserve decisions and open questions beside the rules they affect ([Cognition → What Implementation Asymmetry Obliges](../cognition.md#what-implementation-asymmetry-obliges) — **Evidence**, `docs/cognition.md:156`). Fairness: GitHub's pull-request record is a real record, and LangChain's machine-readable pull-request titles feed its release notes; the difference is where the record lives, and a reader offline from the platform has less.

## 5. Failure modes in LangChain
Stated without calling the project worthless; most of them are the cost of a decade of compatibility with a field that moved faster than any interface could.
1. **Overlapping surfaces for one function.** Streaming alone has `stream`, `astream`, `astream_log`, `astream_events` in two versions, `stream_events` and a third protocol mode that raises `NotImplementedError` on runnables that do not implement it (**Evidence**, `libs/core/langchain_core/runnables/base.py:1195,1216,1238,1344-1374,1601-1613,1675-1760`); the chat model base class adds private methods for protocol-version streaming (**Evidence**, `libs/core/langchain_core/language_models/chat_models.py:525-645,995`). Three event-protocol generations coexist in one method set.
2. **A guarantee that holds as a callable surface and not as a behaviour.** The Runnable docstring says any chain "will automatically have sync, async, batch, and streaming support" (**Evidence**, `base.py:167-168`); the sequence documents that streaming begins only after the last non-streaming step and that lambda runnables "do not support `transform` by default" (`base.py:3108`). Nothing at construction time tells an author which they have. Also, the schema a runnable derives for its input "can be used to validate input" (`base.py:380-420`), and a search of the file for a validating call found none, so the input type is descriptive (pass A, reported with the limit that other files were not searched).
3. **Aliasing and duplicated names.** There are two `ToolCall` typed dictionaries and two `ToolCallChunk` (**Evidence**, `libs/core/langchain_core/messages/content.py:247,291`, `libs/core/langchain_core/messages/tool.py:206,261`); `RunnableMap` is an alias of `RunnableParallel` (`base.py:4400`); two binding classes carry `type: ignore[no-redef]` (`base.py:5855,6382`).
4. **Four copies of the call lifecycle.** The retriever, the tool, the sequence and the base helper `_call_with_config` each carry their own start / child-configuration / error / end sequence, though the helper's docstring says to use it to implement `invoke` (**Evidence**, `libs/core/langchain_core/retrievers.py:179-296`, `libs/core/langchain_core/tools/base.py:1009,1137`, `base.py:2272-2320,3434-3500`).
5. **Legacy kept alongside, with removal tied to a release that has not been cut.** The directory named `libs/langchain` is the legacy package and `libs/langchain_v1` is the package now named `langchain`, and the release workflow carries a mapping for it (**Evidence**, `.github/workflows/_release.yml:13-19`). The legacy package holds 1,321 Python files against 40 in the current one, and about 870 of them mention the community package (866 for the package name, 871 for the word, depending on the method). Ninety-six deprecation markers in it and seventeen in core say removal is at "2.0.0" (counted); the package is at 1.0.8, and a method on the chat model base class was deprecated at 1.4.2 inside the 1.x series with removal 2.0.0 (**Evidence**, `libs/core/langchain_core/language_models/chat_models.py:2334`). Two markers read `removal="0.0.305"` in a package at 1.0.8 (**Evidence**, `libs/langchain/langchain_classic/smith/evaluation/runner_utils.py:1547,1722`; whether they are stale was not checked). The policy is delegated to two documentation-site pages (`libs/core/README.md:41`).
6. **Two hand-kept statements of one capability that can disagree.** The structured-output strategy is chosen by the model's profile when the profile says the model supports it, and otherwise by a regular-expression list of model names kept in the library (**Evidence**, `libs/langchain_v1/langchain/agents/factory.py:182-203,601-623`, read by the drafter: the profile test returns early only on true, so a profile that says false still falls through to the name list). The list names specific model versions and needs a hand edit when models appear; the profile has its own hand-kept override file (**Evidence**, `libs/partners/anthropic/langchain_anthropic/data/profile_augmentations.toml:1-35`). A derived record that is not authoritative over the thing that consults it is a second copy.
7. **Silent defaults whose names promise more.** A summarization middleware with no trigger never summarizes (**Evidence**, `middleware/summarization.py:706-707`); the PII middleware scans the last user message and by default neither model output nor tool results (`middleware/pii.py:564-566,733-735`), while the generated wiki says it covers prompts, responses and tool outputs (`openwiki/middleware.md:231`); the fallback middleware catches any exception, not only retryable ones (`middleware/model_fallback.py:413-426`); the tool-call limit defaults to `continue`, so a blocked call yields an error message and the model may keep going (`middleware/tool_call_limit.py:141-150`).
8. **A contract change is tested against a fixed subset of its consumers.** A change to the contract package runs lint and tests for the package and five hard-coded partners, with a TODO in the script saying the list should include every package that depends on it and that it "won't run on external repo partners" (**Evidence**, `.github/scripts/check_diff.py:334-343`); a core release is checked against two of sixteen partners, and the check can be skipped by a release input (**Evidence**, `_release.yml:603,648-657`); four of the sixteen in-repo partners have no tests that use the contract package at all (counted by the pass: exa, nomic, qdrant, typesafe). Divergence is recorded, and its reasons are undifferentiated: of 31 `xfail` marks in the partners, some state a missing capability (`libs/partners/openai/tests/unit_tests/chat_models/test_azure_standard.py:24`), some flakiness (`libs/partners/groq/tests/integration_tests/test_standard.py:37-52`), some run time ("Takes > 30s to run.", `libs/partners/deepseek/tests/integration_tests/test_chat_models.py:47,65`) and one a to-do ("TODO: handle in integration.", `libs/partners/perplexity/tests/integration_tests/test_chat_models_standard.py:29`). A reader of the marks cannot map which implementation lacks what.
9. **Two truths for one rule.** The agents file says a commit-title scope is required "with no exceptions" (`AGENTS.md:106`) and the title check is configured with `requireScope: false` (**Evidence**, `.github/workflows/pr_lint.yml:124`). A rule addressed to agents and a rule enforced against them are different artifacts, and here they disagree.
10. **Global mutable state with a warning label.** The verbose, debug and cache switches are module variables beside the comment "DO NOT USE THESE VALUES DIRECTLY!" (**Evidence**, `libs/core/langchain_core/globals.py:9-15`); a documented limit is that caching "is not currently supported for streaming methods of models" (`libs/core/langchain_core/language_models/base.py:198`).

## 6. Costs and limits on both sides

### LangChain
- A hard runtime dependency chain: the agent package pins a narrow range of LangGraph (`langgraph>=1.2.11,<1.3.0`, **Evidence**, `libs/langchain_v1/pyproject.toml:28`), the interrupt and checkpoint semantics that the middleware relies on live there (outside the checkout), and core depends on the hosted-tracing vendor's client (`libs/core/pyproject.toml:27`).
- The provider treadmill is carried in library code: a cache-marker strip so a fallback provider accepts a request (`middleware/model_fallback.py:1-10,98-130`), a special case for one provider's model generation (`factory.py:605-612`), an Anthropic characters-per-token ratio from an "offline experiment" (`middleware/summarization.py:251-259`), tool-search identifiers that "can go stale" (`middleware/provider_tool_search.py:41-49`).
- Size: the Runnable module is 6,729 lines in one file (counted); the callback manager module has seventeen classes (counted by the reviewer; the pass counted sixteen manager classes); a reader meets the whole of it to find one rule.
- Unfinished surface: the MCP namespace warns "in beta" on import, supports elicitation but raises for sampling and roots, and its interrupt-and-resume re-issues a server call from its first round so that work done before asking "repeats" (**Evidence**, `libs/langchain_v1/langchain/mcp/__init__.py:21-26`, `libs/langchain_v1/langchain/mcp/elicitation.py:13-14,318-321,333-355`); the capability record is marked beta (`model_profile.py:25-28`).
- Triple-marking, as [the method asks](../documentation-comparison.md#method-requirements-added-by-practice): the MCP namespace is marked in prose and by an import-time warning; the capability record is marked in prose and by its optional-field typing. Whether any default flag or advertised version contradicts a mark was not checked (section 10).

### Memar
1. Memar has no runtime. There is no provider adapter, no agent loop, no tool node, no model catalogue, and no integration; a project that needs those today buys or builds them, which is the sentence Memar already writes about the finished delivery (**Evidence**, `README.md:30`). The comparison does not measure this as a gap: it is the boundary.
2. Streaming and batching of a *result* are not stated at the SDK call surface. sRPC carries stream frames at the wire (**Evidence**, `docs/modules/net/sRPC.md:65-110,126-130`), and the owner of the call surface, the SDK document, has no occurrence of "stream", while "batch" appears in `docs/` outside the comparisons only in senses unrelated to a call (pass D's search, checked by the reviewer). What a consumer receives from a service whose result is incremental or composite is unstated (pass D, silence after reading the SDK document; a search is bounded by its terms — [Cognition → Report absence rather than supplying it](../cognition.md#report-absence-rather-than-supplying-it)).
3. Memar names that high-impact actions require verification and that an agent's authority is bounded. It states no mechanism by which a call is marked effectful, and by the owner's ruling of 2026-10-13 it needs none at the SDK: a call informs, and the effect is the consumer's act under the consumer's authority (section 7, candidate 3). Its method grammar declares per call the variables that influence it and the variables it influences (**Evidence**, `docs/khayyam/method.md:87-92`), which names the data a call touches and is not an approval gate.
4. Memar states that conformance is decidable and that a Test is part of what owes it, and it states no *shared* body of Tests that several realizations of one abstraction all run, nor a record of a known divergence from one (pass D, silence after reading the Test documents and the Protocol and Rule documents; the nearest place for an unmet expectation is a handoff open question, which is a different artifact). The Test handoff holds the mechanism of the Test module open (Test Handoff (`docs/modules/process/test.handoff.md`)).
5. Memar has no position on a machine-readable record of what a model can do. Its Agency document declines to define "LLM implementation details" and "model architectures" (**Evidence**, `docs/agency.md:63-72`), and a type describes itself (SDK → What an SDK is (`docs/modules/process/service-sdk.md#what-an-sdk-is`) — **Evidence**, `docs/modules/process/service-sdk.md:48`); a catalogue of external models is neither.
6. Memar's library placement rule puts a vendor's interface under the library module and does not say who maintains the adapter or where it lives (Lib (`modules/lib/lib.md`)); the MCP adapter there is a guest with nothing realized (Lib Handoff (`modules/lib/lib.handoff.md`)).
7. Memar's documents state no policy for retiring a part alongside its replacement, and by the owner's statement of 2026-10-13 the policy is not a deprecation window keyed to a version but a life cycle with no versions (section 7, candidate 6). The documents hold only fragments: the Type document names four life-cycle positions that Error relies on (`Experimental`, `Stable`, `Deprecated`, `EndOfLife`) while stating that the set is not yet stated and that no list of positions is normative; a superseded document keeps a forward link; an SDK declaration change is "a new revision … never a silent mutation"; and the protocol document for GP says that a fundamentally different protocol is a new protocol and not a new version (**Evidence**, `docs/modules/computer/type.md:44-48`, `docs/documentation.md:125-126`, `docs/modules/process/service-sdk.md:59`, `docs/modules/net/giti.md:77`). The life-cycle source itself, `modules/computer/type/protocol/life-cycle.kh`, is a migration stub whose live content is a commented list of positions from PreAlpha to EndOfLife (read by the drafter), and the question what positions a Type's life cycle may hold is open (`docs/modules/computer/type.handoff.md:7`). LangChain's section 5, item 5 is what a version-keyed removal looks like after a few years.
8. Memar has no stated position on fallback chains or on rate limiting as a policy of a call; it holds retry as a strategy any participant may request and caching as the service developer's choice, and leaves the policy abstraction open (**Evidence**, `docs/process.md:172-178`, `docs/modules/process/service-sdk.md:124`; `docs/modules/process/error.handoff.md`). On messages as typed content blocks and on structured output from a model, the pass found no stated position; the owner's view of 2026-10-13 is that information has two forms only, human language and mathematical language, that Memar supports both, and that abstractions such as a Stringer can convert anything in the second into whatever form a model needs, with a codec concept already worked on, including a character encoding more economical than UTF-8 (`docs/modules/codec/characters-codec.md`, read by the drafter only as to its existence and opening lines). That is a position held in the owner's design and not yet stated in one document for models as consumers; this essay records it as his and places nothing. The silences were read in the owning documents by the pass; none was derived line by line by the drafter.

### Both
- Neither can promise what a provider's model will do next month. LangChain carries the cost as library code that changes monthly; Memar carries it by declining to define model behaviour at all.
- Neither removes the need to pin what is depended on: LangChain's cap on its runtime is `<1.3.0`, and Memar's dependencies are declared as references to other projects' repositories pinned to specific revisions (**Evidence**, `docs/modules/computer/module-dependency.md:27-30`).

## 7. The adoption filter
The method writes toward absorbing what is durable into Memar's homes ([Documentation — Comparison → Fairness rules](../documentation-comparison.md#fairness-rules), rule 1). What is durable here is a small set of obligations, and every one of them is a statement a project could follow without LangChain's machinery. No machinery, no surface and no shape of LangChain's travels.

The owner's ruling of 2026-10-12 applies and is not re-litigated: no candidate becomes a rule; a candidate becomes an open question only where Memar holds no position on the subject, and then the question is stated from Memar's own vocabulary, with no governing document naming LangChain as its source; the examination and its evidence stay here. Each item states which disposition it has: queued to be placed as an open question (with where), put to the owner as a question below, stays in this essay only, or already present in Memar (with where).

### Candidates considered for absorption
1. **A divergence from a contract is a reasoned, recorded exception whose reason says what kind of exception it is.** LangChain makes the first half mechanical — a subclass cannot delete or weaken a standard test without a reason — and fails the second half: capability, flakiness, run time and a to-do share one field (section 5, item 8). The durable obligation is the pair: a known divergence is recorded where the realization is, and the record distinguishes *the realization lacks what the expectation presumes* from *the realization has not yet met it* from *the expectation is wrong for this realization*, which are three different facts about the system, from facts about the test run. Memar holds that conformance is decidable and a Test is part of what owes it (`docs/modules/process/test.md:54-62`, `docs/protocol.md:225-232`) and holds no statement on a shared body of Tests or a record of divergence (section 6, Memar, item 4). Disposition: queued to be placed as an open question in Test Handoff (`docs/modules/process/test.handoff.md`), session 20261013T035748Z-8848-0, under the owner's ruling; the session verifies the silence itself and places nothing if Memar already answers. If the owner thinks the subject is premature (no module yet has a second realization), the session can be deleted.
2. **A uniform call surface that answers whole is not an incremental one, and a declaration should say which.** LangChain's `stream` default yields the whole result as one item, so "can be streamed" is a property of the callable surface and not of the behaviour; whether an implementation streams is discovered at run time (section 3, item 1; section 5, item 2). The obligation, from Memar's side, is a question about its own unfinished surface: the SDK is the only thing a consumer calls and is derived from a declaration, so it could declare which calls are incremental, what a consumer receives, and what partial failure means mid-stream — and the owning document is silent (section 6, Memar, item 2). Disposition: queued to be placed as an open question in SDK Handoff (`docs/modules/process/service-sdk.handoff.md`), session 20261013T035748Z-1516-0. The question is Memar's own; LangChain supplies only the failure the question prevents.
3. **Approval belongs to a declared effect, not to a name.** LangChain's approval gate, retry and limits all work from tool names because nothing declares what a tool does to the world, and the one place the information exists — the MCP annotations — is copied and never read (section 4, item 1). Offered as an obligation of the SDK declaration, it was put to the owner, who ruled on 2026-10-13 that it is not one: the SDK is a method of calling and does nothing special by itself; whether something acts on the world depends on what the caller does with the answer, as in the greenhouse example of section 4, item 1. The effect, and any approval before it, belongs to the consumer's own act under its own authority. Disposition: answered by the owner; nothing is placed, and the SDK handoff's agent-as-consumer entry is not extended. The candidate stays in this essay as an instance of the difference between a runtime whose tool is the actor and a model whose call informs.
4. **A derived capability record is a second copy, and a consumer must either trust it or not consult a second.** LangChain keeps a profile (harvested data plus hand overrides) *and* a name-pattern list that decides when the profile says no (section 5, item 6), and its contract suite keeps a third declaration as test-class properties (section 4, item 3). The obligation is a statement about derived records of what a dependency can do: one source, with its overrides in a layer that is visibly a layer, consulted by everything that depends on the answer. Memar declines to define model behaviour (section 6, Memar, item 5), so this may not be Memar's subject at all. Disposition: stays in this essay only, unless the owner rules the capability record of a dependency a Memar subject, question 2.
5. **A release is tested against the last released consumers, and a version already published cannot be republished.** The mechanism is CI, which is delivery and not Memar's model (`README.md:30`). The obligation underneath it is about versioning of module dependencies, which is open in Memar: semver is "available, not mandatory", a version is "a claim by the producer", and a dependency pins a revision (`docs/modules/computer/module-dependency.md:27-38`, as cited by pass D), with a standing question on the manifest against the VCS pin. Disposition: stays in this essay only. The owner's statement of 2026-10-13 (item 6) goes further than the open versioning questions: there are no versions at all, so a release gate keyed to version numbers has no subject; what remains is that a change to a part already at stable release is a new part, which every consumer of the old part is free to keep using.
6. **A deprecation names what replaces the old thing and when the old thing ends, in a form that survives the release it was written in.** LangChain's record format is good (section 3, item 10) and its removal discipline shows the failure: removal tied to a release that is not scheduled, so the markers wait and a method deprecated in 1.4.2 is promised for 2.0.0 (section 5, item 5). The owner's position of 2026-10-13 removes the failure at its root, not by a better window: he does not hold the concept of a version. A part — a type, a module, an application — accompanies one life cycle from PreAlpha to EndOfLife (`modules/computer/type/protocol/life-cycle.kh`, citing the public software release life cycle); a change after StableRelease does not make a new version of the part but a new part, and calling the new part by the old name with a suffix such as "v1" is itself the error, since names are most often chosen wrongly: a module named for a concept that will not change (his example: a username module, not a user module that gains things each time) keeps its name for life, and what an organization allows in a username is a Rule that organization writes. This is the same position the GP protocol document already states for its own protocol (`docs/modules/net/giti.md:77`). The documents hold no text that states it generally (a search of `docs/` for stable release, versionless and "new version" found none outside that line and the module-dependency pin). Disposition: not placed by this essay. The position is the owner's and it reaches several documents (Type, Module dependency, SDK delivery and versioning), so it is queued as a session that drafts the proposed text and the files it would touch for the owner's approval before anything is applied ([Cognition → Confirm before large-scope changes](../cognition.md#confirm-before-large-scope-changes)), session 20261013T045637Z-27308-0.
7. **A repeat is safe only if the owner of the process says so.** LangChain's retry middleware retries every tool unless narrowed by name and has nowhere to read whether a repeat is safe (section 4, item 1; section 5, item 7). Memar holds that a retry is a strategy any participant may request (`docs/process.md:172-178`) and holds idempotence only as a question about teardown (`docs/modules/memory/memory.handoff.md:65`). Disposition: queued to be placed as an open question in the Error handoff, session 20261013T052605Z-29756-0, verify-first.
8. **Which failures qualify a call for an alternative path.** LangChain's fallback middleware catches any exception (section 5, item 7). Memar holds that a failure may lead to an alternative path (`docs/process.md:154-156`) and maps errors across the boundary as codes (`docs/modules/process/service-sdk.md:58`), and states no rule for which failures qualify. Disposition: queued, session 20261013T052605Z-13940-0, verify-first.
9. **The dependents of a module are derived from declarations, not listed by hand.** LangChain checks a contract change against a hard-coded list of five partners, with a TODO in the script saying the list should include every dependent, and a core release against two of sixteen (section 5, item 8). Memar's Content Rule forbids hand-kept inventories (`docs/documentation.md:31`) and its module dependencies are declared (`docs/modules/computer/module-dependency.md:27-38`); the reverse index (who depends on this module) is stated for documents only (`docs/documentation.md:121`). Disposition: queued, Module Dependency handoff, session 20261013T052605Z-15036-0, verify-first.
10. **A derived artifact carries what lets a check, not a reader, say it is stale.** LangChain's generated wiki records sources, generator, time and a per-page source fingerprint, and no check compares a page with its sources (section 4, item 4). Memar rejects the generated page as authority; whether a derived artifact that is allowed to exist must carry the revision it came from, and who checks it, is not stated. Disposition: queued, Knowledge handoff, session 20261013T052606Z-17388-0, verify-first.
11. **What a value that arrives from outside may select.** LangChain's tool-server adapter accepts a string only as a web address and needs an explicit path or transport object to launch a local process, and its loader accepts only listed namespaces (**Evidence**, `libs/langchain_v1/langchain/mcp/adapter.py:92-142`, `libs/core/langchain_core/load/load.py`, about `:134-148`). Memar holds open questions on untrusted lexing, on exposing a protocol and on a delegated credential, and none states that a value from outside does not by itself select what runs. Disposition: queued, session 20261013T052606Z-5004-0, verify-first; the lowest priority of the set because the evidence from LangChain is thin.

The provenance fields it carries are the idea; the pipeline is the packaging.

## 8. Possible relationship
1. **Session analysis: a Memar-built system that needs an LLM application runtime depends on one, and the question is only whether it is this one.** Under the Enterprise boundary the built system is delivered work (`README.md:30`); if that system is a Python agent application, a library of this kind is a dependency declared at a revision, like any other. Nothing in Memar says which. This essay takes no position on LangChain over another runtime.
2. **LangChain is the standing instance of the other side of the SDK boundary.** Memar holds that the party that knows delivers the typed client; LangChain delivers its tool and its model as objects in one process and has no declaration of effect, and none apart from the object (a tool does carry an argument schema). That is a different delivery by design, and under the owner's ruling of 2026-10-13 (section 7, candidate 3) it is not a gap an SDK declaration should close: the call informs and the consumer acts. The comparison supports the SDK position on who delivers the client and takes nothing from LangChain on who acts.
3. **The contract-suite idea is the closest thing in this examination to a technique Memar could host inside its own Test module, and its failure is the instruction.** If a second realization of a module appears, the shared body and the record of divergence become real questions; the queued session asks them before they are urgent.
4. **A generated index with measured drift is useful to Memar as evidence, not as a tool.** It supports a sentence Memar already holds (a mirror is a cache) with a figure from a shipped product, which is the kind of support the earlier essays in this folder were asked not to move into a governing document. The figure stays here.

## 9. Decision
LangChain is not a substitute for Memar and is not in its category. Its job is running an LLM application — calling models, giving them tools, looping, and surviving the differences between providers — and in that job it is strong where it has been strongest longest: a total call protocol with documented limits, per-call context carried by the protocol, a contract shipped as executable tests with divergence policed, a closed set of human decisions, and a release process that refuses what it can detect. Memar's job is the truth of a system the project owns, and measured on that job LangChain does not compete; it is an instance of what a runtime looks like when someone builds it.

Memar takes seven questions from this examination (candidates 1, 2 and 7 to 11), each stated from its own vocabulary and queued for placement as an open question after the session has verified the silence itself, and one position of the owner's, stated in answer to the comparison, queued for a drafting session that asks his approval: that there are no versions and a change after stable release is a new part. No machinery of LangChain enters Memar: not its `Runnable`, not its middleware, not its callbacks, not its profile pipeline, not its wiki, not its instruction file.

The examination also supports two things Memar already holds with evidence from a shipped product: visible composition over invisible wrapping, and the refusal to let a generated projection be the authority. In both cases the LangChain instance stays in this essay.
