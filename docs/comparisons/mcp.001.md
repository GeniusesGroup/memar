# Comparison: Memar and the Model Context Protocol
**Compared project:** [Model Context Protocol (MCP)](https://modelcontextprotocol.io), through its [architecture overview](https://modelcontextprotocol.io/docs/2026-07-28/learn/architecture).
**Inspected at:** protocol version `2026-07-28`, as the architecture overview for that version states it, read on 2026-10-10. No repository was checked out: the specification proper, the SDKs, the MCP Inspector, and the reference servers that the overview lists under its *Scope* were not inspected.
**Method:** one read of the overview's architecture sections, with its worked JSON examples consulted by search for the fields named below; two vendor posts from MCP's own side, read in the session that commissioned this essay and stated here as vendor reports — each its vendor's engineering report of its own shipped product, which [Documentation → Source standing](../documentation.md#citations) admits as that product's primary documentation, and so supporting only claims about what that vendor built and what it reports having measured, never a general result; all cross-checked against Memar's live `docs/` and the one Khayyam source cited. Nothing was executed: no host, client, server, or SDK was run, and nothing was measured. A claim about MCP below is a claim about what the overview says, cited as *Overview → heading*.
**Framing:** ruled by the owner ([Omid Hekayati](../../CONTRIBUTORS.md#omid-hekayati), 2026-10-10): this is a comparison, not a source of lessons. Memar takes nothing from MCP into its model; a Memar document names MCP only as evidence, as a counter-example, or as a guest protocol Memar adapts to, and says what it says about MCP from Memar's own positions. Positions marked below as the owner's are his. Positions marked as session analysis were reached in the session that commissioned this essay and agreed by him.

## 1. What each project is
### MCP (self-definition)
MCP defines its own boundary: it "focuses solely on the protocol for context exchange—it does not dictate how AI applications use LLMs or manage the provided context" (*Overview → Scope*). Under that name it groups four projects: a specification, "SDKs for different programming languages that implement MCP", development tools including the MCP Inspector, and reference server implementations (*Overview → Scope*).

Its participants are a host — "The AI application that coordinates and manages one or multiple MCP clients" — one client per server, each holding a dedicated connection, and servers, each "A program that provides context to MCP clients" (*Overview → Participants*). It has two layers. The data layer is a JSON-RPC 2.0 exchange covering discovery, server features, client features, and utilities such as notifications and progress tracking; the transport layer is stdio for local processes or Streamable HTTP for remote servers, with standard HTTP authentication and OAuth recommended for obtaining tokens (*Overview → Layers*). As of `2026-07-28` the protocol is stateless: every request carries the protocol version and the capabilities relevant to it in its `_meta` field, clients identify themselves there unless configured not to, and servers advertise versions and capabilities through a mandatory `server/discover` request (*Overview → Statelessness and discovery*).

Servers expose three primitives — Tools ("Executable functions that AI applications can invoke"), Resources ("Data sources that provide contextual information"), and Prompts ("Reusable templates that help structure interactions with language models") — each with `*/list` and `*/get`, and `tools/call` for execution; listings are dynamic (*Overview → Primitives*). Clients expose Elicitation, delivered through the Multi Round-Trip Requests pattern; Sampling and Logging are deprecated as of `2026-07-28`; optional extensions build on the core, the Tasks extension giving long-running requests a durable handle (*Overview → Primitives*). Change notifications are opt-in through a long-lived `subscriptions/listen` stream (*Overview → Notifications*).

### Memar (self-definition)
Memar "is domain-agnostic — it is a framework for developing any system, including software, hardware, buildings, and organizations" ([Framework → Abstract](../framework.md) — **Evidence**, `framework.md:19`). The parts of it this essay measures MCP against are three:
- **The SDK protocol** — "**service client delivery**: a service's own developer produces, alongside the service, the client-side realization of the service's declared interface, produced per consumer language — not a document other parties must implement from" ([SDK → Abstract](../modules/process/service-sdk.md) — **Evidence**, `service-sdk.md:12`). Its question: "what does a service owe its consumers, and in what form is that debt paid?" ([SDK → What an SDK is](../modules/process/service-sdk.md#what-an-sdk-is), `service-sdk.md:33`).
- **sRPC**, Memar's application protocol, which keeps routing, service, operation, and request as independent identities and states that "Human readability of the wire is not a goal" ([sRPC → Motivation](../modules/net/sRPC.md) — **Evidence**, `sRPC.md:16`).
- **Type self-description** — the `Details` abstraction, whose `Domain`, `Summary`, `Overview`, `UserActionNote`, and `DevActionNote` methods each return locale text a type gives about itself ([`detail.kh:19-41`](../../modules/computer/type/protocol/detail.kh) — **Evidence**).

### Category distinction and layers
The two answer different questions.
- MCP's question: **how does an AI application obtain context and actions from many independently written servers through one protocol?**
- Memar's question in the part compared: **what does a service owe each of its consumers — an agent among them — and in what form is that delivered?**

The layers have to be separated before anything is compared, because MCP bundles under one name what Memar treats as different jobs. MCP's wire — its data layer and transport layer — is the counterpart of sRPC. MCP's "SDKs" are per-language implementations of the protocol, which in Memar's terms are protocol machinery: "a general-purpose client library for a protocol (an HTTP client, a [Chapar](../modules/net/chapar.md) implementation) is a different concept — reusable machinery, not one service's delivered interface" ([SDK → What an SDK is not](../modules/process/service-sdk.md#what-an-sdk-is-not) — **Evidence**, `service-sdk.md:72`). What Memar calls an SDK — one service's own delivered interface — has no counterpart in MCP (session analysis, agreed by the owner). Not compared: Memar as a whole framework, since MCP claims no framework layer, and what a host does with context, which MCP's scope excludes.

## 2. Source status of the inspected source
- **One page, not a repository.** Every claim about MCP rests on the architecture overview, which describes itself as an overview with "an example demonstrating each core concept" (*Overview*, opening). Where it defers to the specification ("Detailed information can be found in the specification", *Overview → Statelessness and discovery*), this essay goes no further. The specification may carry rules the overview simplifies.
- **History.** The overview is versioned by protocol revision in its address and carries no change history of its own beyond its deprecation notes. The condition is the one a collapsed checkout presents ([Documentation — Comparison → Method requirements added by practice](../documentation-comparison.md#method-requirements-added-by-practice), item 2), and it is recorded as a finding about the source: a reader learns what changed in `2026-07-28` — Sampling and Logging deprecated, the protocol stated as stateless — and what replaces the deprecated features, but not why they entered the protocol or why they leave it.
- **Marking of what is not current.** The overview marks deprecated material in prose at both places a reader meets it (*Overview → Data layer*; the "Deprecated:" paragraph under *Overview → Primitives*) and marks extensions as optional (*Overview → Primitives*). The SDKs' code comments and defaults were not inspected, so whether they carry the same marks is unchecked, not found absent.
- **Memar's side.** The SDK protocol is a Draft and says so in its opening prose: "a dedicated design session will turn these positions into the protocol's actual specification" (`service-sdk.md:9`). Its declaration artifact and its delivery and versioning are open ([SDK Handoff → What the declaration artifact is](../modules/process/service-sdk.handoff.md#what-the-declaration-artifact-is); [→ Delivery and versioning](../modules/process/service-sdk.handoff.md#delivery-and-versioning)). The reserved SDK-delivery service and the MCP guest adapter named in section 7 are open entries in their handoffs and nothing more: no code exists for either, so no default can claim them.

## 3. What MCP has that Memar does not
An inventory of genuine strengths, each with its evidence; the disposition of each is in section 7.

1. **One protocol many AI applications already speak.** The overview names Claude Code, Claude Desktop, and Visual Studio Code as hosts (*Overview → Participants*); a server written once is reachable from each. No host consumes Memar's SDK protocol. Reach is the one thing here MCP holds in full and Memar does not hold at all.
2. **A mandatory, cacheable discovery request.** `server/discover` returns supported versions, capabilities, and identity (*Overview → Statelessness and discovery*), and list responses carry a `ttlMs` freshness hint (*Example → Understanding the Tool Discovery Response*). sRPC's frames select a service by Service ID and define no discovery exchange ([sRPC → Frames](../modules/net/sRPC.md#frames)), and how a consumer obtains a service's SDK is open ([SDK Handoff → Delivery and versioning](../modules/process/service-sdk.handoff.md#delivery-and-versioning)).
3. **Requests that stand on their own.** Since `2026-07-28` each request carries what the server needs "so the server can process each request on its own" (*Overview → Statelessness and discovery*).
4. **Two shipped transports matched to where a server runs.** stdio for a local process, Streamable HTTP for a remote one (*Overview → Transport layer*). Memar holds the position that local and network invocation sit behind one call surface ([SDK → Working positions](../modules/process/service-sdk.md#working-positions), item 10), while who decides the realization per call is open ([SDK Handoff → The local/network realization decision surface](../modules/process/service-sdk.handoff.md#the-localnetwork-realization-decision-surface)).
5. **A user-in-the-loop request.** Elicitation lets a server ask the user for more information or for confirmation of an action through `elicitation/create` (*Overview → Primitives*).
6. **A durable handle for long-running work.** The Tasks extension lets a server return a handle the client polls for status and result (*Overview → Primitives*).
7. **Deprecation marked where readers arrive, with the replacement named.** Sampling: "New implementations should integrate directly with LLM provider APIs"; Logging: "New implementations should log to `stderr` (stdio transport) or use OpenTelemetry" (*Overview → Primitives*). What the deprecation says about the protocol's design is in section 5; the candor of marking it is credited here.

## 4. Where Memar is stronger
1. **The service delivers its interface; no consumer re-derives it.** Memar's SDK is "the service's own deliverable" ([SDK → Working positions](../modules/process/service-sdk.md#working-positions) — **Evidence**, `service-sdk.md:53`); a textual or intermediate specification "is not a deliverable of this kind" (`service-sdk.md:54`); the SDK "carries the service's operational decisions, not just its message shapes" (`service-sdk.md:55`); and every call a consumer makes to the service is an SDK call (`service-sdk.md:56`). MCP is the specification-first default that this document rejects, re-done with the model as the consumer that re-derives each call from text on every call (session analysis, agreed by the owner): its server publishes for each tool a `description` and an `inputSchema` that is "A JSON Schema that defines the expected input parameters" (*Example → Understanding the Tool Discovery Response*), and the host merges every server's tools into "a unified tool registry that the language model can access", from which the model "automatically generates the appropriate tool calls" (*Example → How This Works in AI Applications*, under Tool Discovery). Memar records this in its own home, [SDK → What an SDK is not](../modules/process/service-sdk.md#what-an-sdk-is-not), and the agent as a consumer of a delivered SDK in [SDK → Working positions](../modules/process/service-sdk.md#working-positions), position 13.
2. **What an agent reads as text is the declaration, not the wire.** A wire carrying text because its consumer reads text is a category error: the model never reads the wire — the host translates it into the registry quoted above — so what an agent must read as text is the service's declaration, not the bytes in transit (session analysis, agreed by the owner). sRPC holds the matching stance as goals — minimum overhead to find a service, minimum data exchange forced by the protocol, and "Easy understanding by a human is not a goal" ([sRPC → Goals and non-goals](../modules/net/sRPC.md#goals-and-non-goals) — **Evidence**, `sRPC.md:27-29`) — with [Syllab](../modules/codec/syllab.md) as the default codec and JSON possible but "not suggested" ([sRPC → Payload](../modules/net/sRPC.md#payload-request-or-response) — **Evidence**, `sRPC.md:142`).
3. **A protocol is designed for all its participants, not one** (the owner's position). Binary on the wire is not a side benefit: it saves the resources of the whole network — bandwidth, and serialization and parse work at both ends of every exchange — and at scale that cost is not small. MCP optimizes for one participant, the model's context, and charges the network for it; the industry's own move from REST to gRPC is the precedent that wire cost matters. The SDK route delivers both savings at once: the agent reads the SDK as text locally, and everything on the wire is binary (sRPC, Syllab).
4. **Delivered once, against parsing on every exchange** (the owner's position). The SDK can be delivered as a digitally signed WASM bundle, downloaded once and cached, which is set against parsing JSON billions of times, once per request and once per response. WASM is itself an execution sandbox and the signature gives integrity, so running such downloaded code is not the risk it is for native code. Plain source code is not a critical risk either (the owner's position): what a consumer expects of a connection is a specific domain fixed outside the SDK, which the consumer itself — the agent application, for one — checks at a layer such as TLS, blocking any connection the SDK's code attempts to another domain, so WASM is his preferred form, not a precondition. How this delivery form relates to [SDK → Working positions](../modules/process/service-sdk.md#working-positions) item 7 — deliverables "produced per consumer language where the module provides them" (`service-sdk.md:59`) — is open: the bundle may be the delivery form for every consumer with per-language bindings, or one form beside per-language source (section 7).
5. **Every type describes itself, so resources and prompts need no primitive of their own** (the owner's position). A resource is a typed value reached through an SDK call. Treating Resources as a primitive apart from calls is a symptom of frameworks and protocols whose types do not describe themselves. In Memar every type must describe itself: `Details` declares `Domain`, `Summary`, `Overview`, `UserActionNote`, and `DevActionNote`, each a locale text the type returns about itself ([`detail.kh:19-41`](../../modules/computer/type/protocol/detail.kh) — **Evidence**), so no type in the system is ambiguous, and the text an agent needs about a service comes from the types the SDK carries. Prompts — instructions to the model on using the service — fall under the same self-description; this last sentence extends the owner's position in the commissioning session, and the owner may overrule it.
6. **A declaration change is a new revision, never a silent mutation.** Two deliverables derived from one declaration revision are substitutable, and "a declaration change is a new revision and new deliverables, never a silent mutation of delivered code" ([SDK → Working positions](../modules/process/service-sdk.md#working-positions) — **Evidence**, `service-sdk.md:59`). MCP's counterpart is in section 5, item 4.
7. **The call is a delegation under an agreement already held.** "A delegation is only trustworthy when the process has actually been agreed beforehand — the two parties hold the same declared process, and neither can redefine it during execution. The SDK is how that agreement travels: not as a promise in a document, but as the generated code both sides already conform to" ([SDK → The call as delegation](../modules/process/service-sdk.md#the-call-as-delegation) — **Evidence**, `service-sdk.md:119`; [Agency → Delegation](../agency.md#delegation)). MCP's counterpart is in section 5, item 5.

## 5. Failure modes in MCP
MCP does what its scope says it does, and many hosts run on it. What follows are the failures its own design shows, stated from Memar's positions.

1. **Text on the wire for a reader who never reads the wire.** Both transports carry "the same JSON-RPC 2.0 message format" (*Overview → Transport layer*), and since `2026-07-28` every request also carries version and capabilities in `_meta`, and client identity there unless the client is configured not to send it (*Overview → Statelessness and discovery*). The reader the text is for is the model, and the model receives the host's registry, not the messages (section 4, item 2).
2. **The interface is re-derived by the consumer on every call.** The description and schema the server publishes are what the model reasons from each time it generates a call (section 4, item 1). The cost is visible from MCP's own side, in two vendor reports about their own engineering, stated as vendor reports and not as general results. Anthropic, in ["Code execution with MCP"](https://www.anthropic.com/engineering/code-execution-with-mcp), presents MCP servers to the agent as a generated TypeScript file tree the agent imports, and reports one example falling from about 150,000 tokens to about 2,000 (98.7%). Cloudflare, in ["Code Mode: the better way to use MCP"](https://blog.cloudflare.com/code-mode/), converts MCP tools into a TypeScript API with doc comments and has the model write code against it. Both rebuild, as a patch over MCP, the service-delivered SDK the owner's position calls for (the owner's position).
3. **Features placed in the protocol that belonged elsewhere.** `2026-07-28` deprecates Sampling, directing new implementations to "integrate directly with LLM provider APIs", and Logging, directing them to `stderr` or OpenTelemetry (*Overview → Primitives*), and in the same revision moves the protocol to stateless (*Overview → Statelessness and discovery*) (session analysis, agreed by the owner).
4. **A tool set that can change after it was approved.** Tools "may come and go based on server state, external dependencies, or user permissions", and on a change notification the host "immediately refreshes its tool registry and updates the LLM's available capabilities" (*Example → Why Notifications Matter*; *→ How This Works in AI Applications*, under Real-time Updates). Where Memar makes any declaration change a new revision with new deliverables (section 4, item 6), MCP lets the set the model acts from change under it (session analysis, agreed by the owner).
5. **Instructions with no prior agreement.** A tool's `description` is a "Detailed explanation of what the tool does and when to use it" (*Example → Understanding the Tool Discovery Response*), and it reaches the model as text the model acts on as instruction — the surface of tool-poisoning attacks — while nothing precedes the call as an agreement both sides already conform to (section 4, item 7) (session analysis, agreed by the owner).
6. **Resources and Prompts as primitives apart from calls.** The overview's own example has one server expose "tools for querying the database, a resource that contains the schema of the database, and a prompt that includes few-shot examples for interacting with the tools" (*Overview → Primitives*): three primitives to say what one self-describing service would carry in its types (section 4, item 5).

## 6. Costs and limits on both sides
### MCP
- Every exchange is serialized to and parsed from JSON text at both ends, with per-request metadata added by the stateless revision (section 5, item 1).
- The tools of every connected server enter one registry the model reasons from (*Example → How This Works in AI Applications*); the two vendor reports in section 5 are MCP's own side reporting that cost and building around it.
- A revision that deprecates two client primitives and changes the protocol's state model obliges every implementation to follow it.

### Memar
- **No reach.** No host speaks Memar's SDK protocol, and Memar cannot fight the whole ecosystem (the owner's position) — the reason for the guest adapter in section 7.
- **The SDK protocol is a Draft.** Its declaration artifact, generation mechanics, and delivery and versioning are open ([SDK Handoff → Open Questions](../modules/process/service-sdk.handoff.md#open-questions)); what this essay says the SDK route delivers is the protocol's settled position, not a shipped mechanism.
- **The agent's delivery path is a proposal.** The reserved SDK-delivery service and the signed WASM bundle (section 7) are positions and an open question, not built.
- **The service owner carries the work.** Deliverables are produced per consumer language where the module provides them, and a consumer in another language reaches the same interface through FFI, a port, or another consumption path (`service-sdk.md:59`): responsibility the specification-first default spreads over consumers is concentrated on the service's developer, by design.

## 7. The adoption filter
The method writes toward absorbing what is durable into Memar's homes ([Documentation — Comparison → Fairness rules](../documentation-comparison.md#fairness-rules), rule 1). Under the owner's ruling nothing durable here comes from MCP: the filter's result is that nothing is absorbed or adapted, and what this examination does carry home is Memar's own positions, restated against MCP as a counter-example.

### Absorb
None. Each item of section 3 is disposed of as follows.
- Reach (item 1) is a property of MCP's ecosystem, not a design Memar lacks, and adoption is not a technical argument (the owner's position): it is met by the guest adapter below.
- Discovery and delivery (item 2) are Memar's own open question, answered from Memar's own position — the reserved SDK-delivery service below — not from `server/discover`.
- Self-contained requests (item 3) and shipped transports (item 4) are not taken: sRPC keeps request identity as its own field ([sRPC → Independent identities](../modules/net/sRPC.md#independent-identities)), and the local and network realization is Memar's own open decision ([SDK Handoff → The local/network realization decision surface](../modules/process/service-sdk.handoff.md#the-localnetwork-realization-decision-surface)).
- Elicitation (item 5) and the Tasks extension (item 6) are not taken. This essay holds no Memar position on either need and opens none.
- Marked deprecation (item 7) is credited; Memar's own marking rule is the Content Rule's ([Documentation → Content Rule](../documentation.md#content-rule-no-fabricated-or-redundant-provenance)).

### Reject
- JSON-RPC text as the wire for Memar's services (section 4, items 2–3). Home: [sRPC → Goals and non-goals](../modules/net/sRPC.md#goals-and-non-goals) and [→ Payload](../modules/net/sRPC.md#payload-request-or-response).
- The model as the party that re-derives a service's interface from a published description (section 4, item 1). Home: [SDK → What an SDK is not](../modules/process/service-sdk.md#what-an-sdk-is-not).
- Resources and Prompts as primitives apart from calls (section 4, item 5). Home: Resources at [SDK → Working positions](../modules/process/service-sdk.md#working-positions), position 14, and [→ What an SDK is](../modules/process/service-sdk.md#what-an-sdk-is); Prompts, tentatively, at [SDK Handoff → The agent as an SDK consumer](../modules/process/service-sdk.handoff.md#the-agent-as-an-sdk-consumer).
- Tool sets that change under a consumer without a new declaration revision (section 4, item 6). Home: [SDK → Working positions](../modules/process/service-sdk.md#working-positions), position 7.
- MCP as Memar's model, its addressing, or a channel Memar's own server is built on (the owner's position). Home: [Lib Handoff → Decisions](../../modules/lib/lib.handoff.md#decisions).

### Guest adaptation
MCP is supported as a guest adapter under [`modules/lib`](../../modules/lib/lib.md), the module whose placement rule is "**a protocol that is not Memar's own belongs here.**" (`lib.md:10`), in the same standing HTTP has toward sRPC: "That form is guest interoperability, not this protocol's addressing model" ([sRPC → Service ID](../modules/net/sRPC.md#service-id) — **Evidence**, `sRPC.md:136`) (the owner's position). Home: [Lib Handoff → MCP as a guest adapter](../../modules/lib/lib.handoff.md#mcp-as-a-guest-adapter). Nothing of the adapter is built.

### Memar's own positions, routed to their homes
1. **MCP as the specification-first default with the model as re-deriving consumer** (section 4, item 1). Home: [SDK → What an SDK is not](../modules/process/service-sdk.md#what-an-sdk-is-not).
2. **The agent as an SDK consumer.** Home: [SDK → Working positions](../modules/process/service-sdk.md#working-positions), positions 13 and 14; the WASM delivery form and the Prompts line stay in [SDK Handoff → The agent as an SDK consumer](../modules/process/service-sdk.handoff.md#the-agent-as-an-sdk-consumer).
3. **A reserved sRPC service that delivers a service's SDK** (the owner's proposal). One reserved Service ID that any agent or consumer calls to obtain an application's SDK in its own language, or as the signed WASM bundle, so the consumer understands the service locally as text while every exchange on the wire stays binary; whether "reserved" means a number set aside or one well-known service media type is undecided in its home. Since a Service ID is the MediaTypeID of the service media type (`sRPC.md:136`), the request is keyed by the service's media type, the consumer's language or form, and the declaration revision. It ties to [SDK Handoff → What the declaration artifact is](../modules/process/service-sdk.handoff.md#what-the-declaration-artifact-is) and [→ The local/network realization decision surface](../modules/process/service-sdk.handoff.md#the-localnetwork-realization-decision-surface). Home: [sRPC Handoff → A reserved service that delivers a service's SDK](../modules/net/sRPC.handoff.md#a-reserved-service-that-delivers-a-services-sdk).
4. **The signed WASM bundle against working position 7** (section 4, item 4): whether it is the delivery form for every consumer with per-language bindings, or one form beside per-language source. Home: the question for the owner under [SDK Handoff → The agent as an SDK consumer](../modules/process/service-sdk.handoff.md#the-agent-as-an-sdk-consumer), which blocks the rules under [→ Delivery and versioning](../modules/process/service-sdk.handoff.md#delivery-and-versioning).

## 8. Possible relationship
1. **Memar remains the authority** for its model, its addressing, its wire, and the form in which a service's interface reaches a consumer.
2. **MCP is a guest protocol at Memar's boundary**, reached through an adapter under `modules/lib`, so that an MCP host can reach what a Memar-built system offers in the way an HTTP client reaches sRPC through its multiplexer form. The adapter conforms to MCP; Memar's model does not.
3. **The direction on MCP's own side runs toward the SDK route.** The vendor reports in section 5 rebuild a delivered, typed interface as a patch over the wire; Memar's answer is to have the service deliver it, through the reserved SDK-delivery service when that is designed.
4. **Adoption by large companies is not a technical argument** (the owner's position). Memar states its critique on its merits, and "do you know better than the big companies?" is not an answer to it.

## 9. Decision
MCP is not a substitute for Memar and is not in its category: it is a wire protocol and its tooling for one exchange, between AI applications and the servers that give them context, while the part of Memar it meets is the question of what a service owes each consumer and in what form. Memar takes nothing from MCP into its model. MCP is supported as a guest adapter in the standing HTTP holds toward sRPC, and never as Memar's model, addressing, or a channel Memar's own server is built on.

The comparison changes no governing method. It gives [SDK → What an SDK is not](../modules/process/service-sdk.md#what-an-sdk-is-not) a new instance of the default that document rejects — specification-first delivery, with the consumer that re-derives the interface now a language model — and it places three open questions of Memar's own where they belong: the agent as an SDK consumer, the reserved SDK-delivery service, and the signed WASM bundle as a delivery form.

The strongest argument here comes from MCP's own side. Two vendors that build on MCP met what re-deriving an interface from text costs a model — one of them reporting a measured example of it — and both answered by generating a typed interface for the model to import. That is the SDK, rebuilt after the fact on top of a wire that still carries text; delivered by the service instead, it costs the consumer one download and leaves every exchange on the wire binary.

## 10. Open for critique
- Whether section 3 credits MCP fully, in particular whether discovery (item 2) and Elicitation (item 5) are stronger than stated.
- Whether section 5, item 3 is fair: the overview names the replacements for Sampling and Logging but not the reasons for deprecating them, so "features that belonged elsewhere" is Memar's reading of the replacements, not MCP's stated reason.
- Whether the extension of the owner's position to Prompts (section 4, item 5) holds; it is the commissioning session's, and the owner may overrule it.
- Whether the specification proper, which this essay did not read, carries rules that answer section 5, items 4 and 5 — for example on approval of changed tool sets or on the trust given to tool descriptions.

Claims this essay could not verify from what it inspected, named so a reader can tell them from verified ones:
- Every claim about MCP rests on the architecture overview of `2026-07-28`, not on the specification, the SDKs, or a running host.
- The two vendor reports in section 5, including the 150,000-to-2,000-token example and its 98.7%, were read in the commissioning session and carried into this essay; the drafter did not re-read either post.
- "Tool-poisoning" names a class of attack the session analysis derives from the description-as-instruction design; the overview does not mention it.
