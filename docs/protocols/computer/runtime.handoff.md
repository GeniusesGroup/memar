# Runtime Handoff
Open work for `runtime.md`. Entries are mutable current state — revised as each item moves, removed when it resolves or is dropped. See [documentation-handoff.md](../../documentation-handoff.md) for what a handoff is.

## Open Questions

### How do pinned user-space tasks block on kernel boundaries without stalling their core's run queue?
The interaction model between user-space scheduling and unavoidable kernel boundaries — how a pinned task blocks on file I/O without stalling its core's run queue — is not yet specified. Core-pinning itself is not a Runtime protocol requirement; if it is a MUST, it belongs in a [Concurrency](../computer/concurrency.md) extension. The leak, when pinning is chosen, still appears at the runtime-host boundary.

### What does the `unsafe` tag gate at the runtime layer, and how is a module replacement audited?
What the `unsafe` tag concretely gates — an API surface requiring explicit enablement, a linter/compiler cooperation, or both — and how a module replacement is audited, are not yet specified. Shared with [Compiler](../computer/compiler.handoff.md).

### Which host kinds are in the first conformance floor?
The protocol names OS, unikernel, WASM host, language library, and JavaScript engine as equally legitimate runtimes. Which of those, if any, a first conformance suite must include — versus remaining examples — is not decided.

### Where do shared mechanisms come from — a composition root, or a lookup?
- State: this document defines the runtime as the environment that exercises an artifact's structure and hosts the concurrency substrate; it does not say where a running system obtains the mechanisms every part of it needs (a logger, a clock, a registry, an authenticator, a store handle, a bus). The owner's position, recovered 2026-09-30 from an audit of Omid Hekayati's Go-community Telegram-group messages, draws the line explicitly: one application-level object that holds the shared mechanisms and hands them to what declares it needs is legitimate composition, but a part that reaches into a global to obtain what it needs is a service locator, and it replaces a declared contract with a hidden one. The framework already rejects the neighbouring mechanism on the same ground — silent forwarding of a call to an embedded or wrapped object is listed among the ways behavior hides ([Type → How Behavior Hides](../../type.md#how-behavior-hides)) — and [Module](../../modularity.md) already owns the idea of a bounded part carrying capabilities, so the open part is narrower than it looks: whether the composition root is a framework concept with a stated contract, a library convention, or left to each application.
- Question for the owner: does Memar name the composition root, and if so does a part receive its dependencies as declared parameters (as [SDK → Local and network invocation](../modules/sdk.md#local-and-network-invocation) already implies for the one call surface it owns) or as a handle it holds from the root? Related and unanswered by either: who owns teardown of a shared mechanism when the last holder releases it, which [Memory Handoff → Must teardown be idempotent, and which lifecycle names belong to which resource family?](../memory/memory.handoff.md#must-teardown-be-idempotent-and-which-lifecycle-names-belong-to-which-resource-family) currently leaves open.
- Next: decide with the Module document's capability treatment; nothing in the corpus depends on the answer yet, and no contract in the implementation tree currently receives a shared mechanism, so this is a design question to answer before the first service, not a migration.
