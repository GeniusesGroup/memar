# Memory

## Abstract
This document defines memory as a framework concern and records Memar's position on it, in two movements. The first is definitional: memory is every bounded capacity that retains state over an interval, classified not by what it is made of but by its retention property — **volatile, semi-volatile, non-volatile** — and the ecosystem's two-name split of the field into "memory" versus "storage" is rejected as a historical convention that pulled everything non-volatile out of the concept and made one substance look like two kinds of thing. The second movement is managerial: with the concept intact, memory management is shown to be inescapable — no language with dynamic allocation escapes the reclamation question — and the ecosystem's placement of that question is corrected: the mechanisms marketed as "GC versus no GC" are one subcategory (runtime GC mechanisms) under a broader spread of reclamation mechanisms, of which compile-time ownership-derived reclamation — the kind languages like Rust use — is another. On top of both movements sit the framework's contract rules: which values are copied, which are shared, who may retain a view into a buffer, and how long — because memory semantics are part of a contract, and contracts that leave them implicit are underspecified, not simpler.

## Introduction

### Motivation
Five recurring failure patterns motivate this document:
1. **The two-name split doing conceptual damage.** The ecosystem inherits a vocabulary that divides the field into "memory" (fast, volatile, close to the processor) and "storage" (slow, durable, distant) — a split commonly attributed to the von Neumann architecture tradition. The split trains architects to treat non-volatile retention as a different *kind of thing*, which is the root of the shadow-tier pattern: a second system introduced to hold a domain's data "for persistence" and a third to hold it "for speed", each with its own ownership and invalidation story (worked out below; stated as a modeling rule in [Modeling → One Authoritative Location per Concern's Data](../modeling.md#one-authoritative-location-per-concerns-data)).
2. **The GC concept misplaced.** The ecosystem's languages are marketed as "GC" and "non-GC" as if garbage collection were a property some languages escape. In reality garbage exists the moment memory is dynamically allocated, and every such language must answer who reclaims it — the marketed difference is distance from one *mechanism family* (runtime GC), not absence of the concept.
3. **Invisible structural copies.** In Go, a slice or string value is a small header structure (pointer, length, capacity); passing it copies the header — and the header alone determines whether the underlying buffer is shared. Developers routinely reason about these values as if the data itself moved. The ecosystem's HTTP libraries make the opposite choices from each other — one copies header values before handing them out so callers may retain them freely, another hands out views into a shared request buffer and documents "things will go wrong here" if the buffer is reused — and callers who never learned the distinction write both kinds of bug.
4. **The unwritten copy convention.** The ecosystem operates on an undocumented consensus about who copies what at a return boundary; libraries that deviate are "unsafe" and libraries that follow it pay a copy cost nobody asked them for explicitly. A convention this load-bearing should be a stated rule, not folklore.
5. **Folklore-based performance claims.** Claims like "zero allocation" or "the GC handles it" circulate without measurement; when measured, they frequently fail (a library advertising zero allocation performing more allocations than the default for realistic requests). The project's own practice — benchmark before defending an allocation claim — is recorded here as a rule, because the failure mode was observed repeatedly, including by the project's own members before correcting course.

### Methodology
The definitional movement uses the volatility classification recorded on [Wikipedia's Computer memory page](https://en.wikipedia.org/wiki/Computer_memory#Volatility_categories) as its reference taxonomy, and examines the ecosystem's memory/storage organization as presented on [Wikipedia's Computer data storage page](https://en.wikipedia.org/wiki/Computer_data_storage). Every empirical claim this document carries about a specific library's behavior was checked against its source or measured before being recorded. This document deliberately does not re-litigate reclamation-mechanism choice as a language-design question — that belongs to [Khayyam's memory model](../khayyam-memory_model.md) — and does not prescribe an implementation for any backend. It states the definitional positions and the contract-level requirements any realization must satisfy.

## Explanation

### What memory is
Memory is every bounded capacity of a system that retains state over an interval — so that state set at one time can be read at a later time. Under this definition, memory is not one component in a machine diagram; it is the class of all such capacities: processor registers, cache levels, main memory, flash cells, magnetic surfaces, battery-backed units, and everything else that holds state for later. A domain's database is memory; a file on disk is memory; a register is memory. What distinguishes members of the class is not *what they are* but *the properties they carry* — and the property this document treats as primary is retention.

The definition is deliberately broad because the narrow alternatives all fail the same way: any definition that names a technology ("memory is RAM") expires with the technology and re-creates the two-name split discussed below.

### Volatility: the real classifier
Members of the memory class are classified by their **retention property** — what happens to the held state when ordinary support (power, refresh) is withdrawn:

- **Volatile memory** loses its held state when support is withdrawn.
- **Non-volatile memory** retains its held state without support.
- **Semi-volatile memory** sits genuinely between: retention without support is partial or time-limited — whether through a non-volatile assist (a battery, a periodic refresh) or through slow intrinsic decay of the stored physical state.

The three-way classification is this document's adopted vocabulary (per the reference taxonomy above), and its value is exactly what makes it worth stating: **volatility is a property, not a taxonomy of different kinds of thing.** The semi-volatile middle case is the proof that no hard boundary exists between the two popular classes — retention without support is a continuum from microseconds to decades — so any two-name division of the field must draw an arbitrary line on that continuum and then defend the line as if it were a difference in essence.

### The memory/storage dichotomy rejected
The ecosystem's dominant vocabulary splits the field into two named domains: "memory" for the fast, support-dependent tier, and "storage" for the durable tier — an organization presented in references like [Wikipedia's Computer data storage page](https://en.wikipedia.org/wiki/Computer_data_storage), where primary memory and secondary storage form different levels of one hierarchy. This document's position: the two-name split is a **historical convention layered on hardware economics, not a conceptual division** — and it is rejected here as a classification principle.

Two arguments carry the rejection:

1. **The continuum argues against two essences.** As established above, retention without support is a spectrum, with genuinely populated middle cases. A two-name split draws one arbitrary line across that spectrum — fast-and-lost versus slow-and-kept — and then trains architects to think the line marks two different *kinds of thing*, requiring different ownership models, different layers, different engineering instincts. The semi-volatile case (and every technology that later moved across the line — flash was once exotic storage, then became the substrate of main memory class devices) shows the line is drawn for convenience and redrawn by history.
2. **The attribution itself does not survive scrutiny.** The split is commonly attributed to the von Neumann architecture tradition — yet the architecture's own central idea, the stored-program concept, is a *unification*: one memory holds both instructions and data. The two-name division is a later industry convention consolidated by the cost-driven tiering of hardware, not a principle of the architecture it is named after. Rejecting the split therefore rejects a convention, not a foundational design.

What survives the rejection: the real needs the old names wrapped — fast working retention and durable retention — are genuine, and are expressed here as *properties* (volatility, latency, capacity, access contract) rather than as two kinds of thing. The word "storage" survives in this framework only as the common name for non-volatile memory serving long-term retention — a description, not a separate concept.

The dichotomy's most damaging practical product is the **shadow-tier pattern**: a second, faster memory introduced in front of a concern's authoritative location, treated as infrastructure ("a caching layer") rather than as what it is — a derived copy whose ownership and re-derivation discipline must be owned by someone. Once non-volatile retention is reified as a different *kind of thing* — "storage" — a system bridging the two reified kinds looks like architecture rather than like one concern's data held twice. The rule this document records, and which [Modeling → One Authoritative Location per Concern's Data](../modeling.md#one-authoritative-location-per-concerns-data) states at the modeling level: **a concern's authoritative data has one location; a faster tier standing in front of it is a derived copy — if the owning location provides the access capability, or the data is re-modeled so its access pattern matches one location, the shadow tier disappears along with its invalidation problem.** Invalidation is hard precisely because two owners were introduced for one concern; removing the second owner removes the problem class rather than solving its instances. A parallel failure mode is recorded in [Type → Concepts Outlive Their Labels](../type.md#concepts-outlive-their-labels): rejecting a vocabulary bundle wholesale risks discarding the real concepts wrapped in its names — the functional-programming communities' rejection of object-oriented vocabulary discards encapsulation, without which even a primitive type cannot be defined. The dichotomy rejected here is the same disease in reverse: two names pretending to be two essences, where one concept with properties is the truth.

### Memory management is inescapable
With the concept intact, the management question comes into focus. State placed in memory must eventually be reclaimed — the capacity is bounded, and state whose purpose has ended must yield its space. Every system that allocates dynamically must therefore answer: **who reclaims, when, and how is that reclamation kept correct?**

The framework's own architecture answers the framing first, per [OS](./os.md): the founding layers grant memory in bounded entitlements — a system receives, say, a megabyte, and the management inside that grant is its own business. No component at the guarantee layer receives a grant per variable, and none should ask for one: allocation and reclamation inside the grant are *meaning*, defined by the system above the boundary, exactly as [OS → The OS responsibility boundary](./os.md#the-os-responsibility-boundary) prescribes. The traditional arrangement — a host offering per-allocation services (an allocator, a collector) to everything running on it — is the same down-pushed-meaning pattern that document rejects; even there, the per-allocation service is not the guarantee layer's work but a library running inside each process on top of its grant.

This framing yields the position this document records on the ecosystem's "GC or no GC" framing:

- **Garbage exists wherever dynamic allocation exists.** Memory allocated and later unreachable by the program's logic is garbage, in every language that allocates dynamically — including every language marketed as "no GC". The honest difference between languages is not the *existence* of the reclamation question but *where its policy is decided and who executes it*.
- **The manager is inescapable; the collector is optional.** Every language carries a memory manager — some component that acquires memory from the grant and hands it out (an allocator library, a runtime, a compiler-inserted scheme). What varies is only whether *reclamation* is performed by a runtime service (a garbage collector), by reference counts maintained at runtime, by reclamation code the compiler derives from ownership rules and inserts statically, or by the programmer's own hands. A language claiming to have "no GC" has, precisely, *no runtime collector* — its memory manager is fully intact.
- **The cost never disappears; it moves.** In a manually-managed language the human performs the collector's bookkeeping — deciding when state is dead and freeing it — at the price of human time and human error. In a runtime-collected language the cost is paid in throughput and pause behavior. In an ownership-derived language the cost is paid at compile time (proving ownership) and in restricted sharing patterns. No arrangement is free; the ecosystem's habit of marketing one arrangement as having "no cost" is the same folklore this document's measurement rule (below) exists to correct.

### The reclamation mechanisms, classified
Putting the above in one taxonomy, using "garbage collection" in its *function* sense — any reclamation performed automatically on the program's behalf:

- **Manual reclamation** — the programmer decides and executes (C's `malloc`/`free`). The concept of garbage is fully present; the mechanism is human.
- **Scope-discipline reclamation** — reclamation bound to lexical scope, executed deterministically at scope exit (stack discipline; RAII in its resource form). No runtime collector; no garbage survives scope exit by construction, at the price of limiting lifetimes to scopes.
- **Ownership-derived reclamation** — the compiler *proves* for each value when its useful life ends and inserts the reclamation statically (Rust's ownership system). This is automatic reclamation in the full function sense — the programmer neither frees nor counts — and it depends on its own tooling: the allocator library that acquires memory in the first place, and the borrow analysis that keeps reclamation correct. A language can honestly claim "no runtime GC mechanism" this way; it cannot honestly claim to have escaped reclamation.
- **Runtime reference counting** — reclamation when a value's live-reference count reaches zero, maintained at runtime (Swift's ARC, and every `Rc`-style type). The literature classifies counting as a GC family; languages marketing it as "no GC" are demonstrating the concept misplacement this topic exists to correct.
- **Runtime tracing GC** — periodic or concurrent reachability analysis with reclamation of unreachable state (Go, the JVM, C#). The mechanism the ecosystem's "GC" label actually refers to.

The position this taxonomy records: **the mechanisms the ecosystem attributes to "GC" are one subcategory — runtime GC mechanisms — under the broader spread of reclamation mechanisms**, and the concept itself (the reclamation question, and its automatic answers) is present in every language that allocates dynamically. The ecosystem's "GC versus non-GC" division is a division between mechanism families, marketed as a division between languages that need the concept and languages that do not — and the second half of that marketing is false.

A definitional note is recorded deliberately: the mainstream literature often reserves "garbage collection" for *runtime* reclamation, under which reading the taxonomy above would rename its automatic entries rather than gather them under one term. This document adopts the function-based reading — reclamation performed automatically on the program's behalf, by whatever means — because the load-bearing claim here is conceptual (the question is inescapable; only mechanisms differ), and because the function-based reading exposes the marketing error the mechanism-based reading shelters: under it, "no GC" claims survive by defining their own counter-example out of the word.

### Copy and ownership semantics are contract members
A method's contract includes the memory semantics of its inputs and outputs: for every value that is passed in or out, the contract states whether the caller retains ownership, whether the callee may retain a view, and how long a returned view remains valid. "Treat any returned buffer as valid only until the next call" is a legitimate contract term — but it must be *written*, because it is exactly the term callers otherwise assume to be the opposite. The ecosystem's own experience proves both directions are viable; what is not viable is leaving the choice discoverable only by reading the implementation.

This rule binds Memar's own libraries doubly: every buffer-reuse, pooling, or zero-copy optimization they perform must be paired with an explicit, documented contract term, and an optimization whose contract term cannot be stated simply is an optimization the library does not get to make.

### The boundary copy convention, stated
Where a value crosses from one ownership domain to another — a return from a call whose underlying buffer the callee may still touch, a value handed to a different execution unit — the framework's default is: **the producing side prepares a copy the receiving side may retain without coordinating with the producer.** This matches the (unwritten) convention the broader ecosystem already runs on; the change this document makes is not the convention but its status: it is now a stated default that implementations may deviate from only by an explicit, documented contract term. Two consequences follow:

- A library that hands out retained views into shared buffers is not "more optimized" — it has chosen a different contract, and must present it as prominently as its performance numbers.
- A library that defensively copies everything "for safety" without stating so is hiding a per-call cost inside its API's apparent simplicity. Both directions of silence are treated as contract violations, not style choices.

### Allocation claims are measurement claims
Statements about allocation behavior — "zero allocation", "no copying", "the runtime optimizes this" — are empirical claims and carry the discipline of empirical claims: they are stated with the measurement that supports them, at a specified scale (an allocation profile differs between small and large requests), and they expire when the implementation changes. The project's benchmark-first rule for memory discussions exists because the failure it prevents was observed repeatedly: performance folklore defended by appeals to the runtime's internals, contradicted the first time someone measured.

### Memory knowledge is not backend-specific
A developer's obligation to understand memory — what allocates, what copies, what retains — does not dissolve in a garbage-collected language. The collector changes *who* reclaims; it does not change *what the program causes*. Leaks in collector-equipped systems (unbounded buffers, retained views, accidental root references) are caused by the same acts that leak manual systems, merely discovered later. Memar's expectations for developers are therefore language-uniform: the memory model of the realization is additional knowledge, not a replacement for the general discipline.

The arena-allocation experiments in collector-equipped languages — including one language's own, later shelved, arena proposal — are evidence that allocation placement is a real, felt cost even under tracing collection; the contract rules above generalize that felt cost into a stated discipline.
