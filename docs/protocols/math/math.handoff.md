## Open Questions

### Is `int32` → `W32` in Primitive Capsule Specification a slip?
- State: raised 2026-09-28 by the numeric-primitives pass of the memar-go port. [Encapsulation in Khayyam → Primitive Capsule Specification](../khayyam/encapsulation.md#primitive-capsule-specification) speaks of replacing `int32` with `W32`, twice. `W` is the whole (unsigned) width, and `int32` is signed; the numeric widths map a signed 32-bit integer to `I32`. The document's own gloss, "A `W32` (whole 32-bit) capsule", agrees with the tower.
- Question for the owner: is the example a slip that should read `I32` (or `uint32` → `W32`), or is the pairing deliberate?
- Blocks: nothing in the toolchain; a reader porting from Go can take the wrong width from the example.
- Answered (owner, 2026-09-28): a slip. `int32` maps to `I32`. The section now reads `I32` throughout, and its gloss reads "signed 32-bit". The owner added that an Integer module may exist, its names taken from the scientific protocols; none is declared, and what it would hold is not decided here. The other numeric answers of the same ruling are recorded under [Does the tower hold widths the reference does not declare?](#does-the-tower-hold-widths-the-reference-does-not-declare).

### Is there a common abstraction over all numeric kinds?
- State: the widths are capsules and the concept names are abstractions ([Math → The number tower](../math/math.md#the-number-tower); [Abstraction in Khayyam → A Concept Is an Abstraction; a Concrete Instance Is a Capsule](../khayyam/abstraction.md#a-concept-is-an-abstraction-a-concrete-instance-is-a-capsule)), so a contract can name a concept only where one exists. `Signed` exists; nothing in the corpus names the concept behind a whole number or behind a real number. Four abstraction-owned signatures therefore still name a capsule, and are the recorded exception: `Hash16_Sum16`, `Hash32_Sum32`, and `Hash64_Sum64` ([`modules/crypto/hash/protocol/hash.kh`](../../modules/crypto/hash/protocol/hash.kh)) name `W16`, `W32`, `W64`, and `Math_Decimal_Decimal` ([`modules/math/decimal/protocol/decimal.kh`](../../modules/math/decimal/protocol/decimal.kh)) names `W64`. Every other contract that took a width or a duration now names the concept (`Signed`, `Duration`).
- The question, for the owner: is there one abstraction over all numeric kinds (a name like `Number`), or one per kind (`Whole`, `Real`, `Signed`), and which methods does it require? Two things any answer settles first. (a) A shared method set can hold only methods whose types are abstractions, so equivalence cannot be among them as the widths state it — `W32_Equal` takes `W32`, and an abstraction requiring `Equal (with Whole)` is one no width satisfies. A contract needing comparison across kinds is left with nothing to name, which is the concrete cost of leaving this open. (b) What a width itself guarantees is itself unanswered ([Encapsulation in Khayyam Handoff → What behavioral guarantees do primitive capsules provide?](../khayyam/encapsulation.handoff.md#what-behavioral-guarantees-do-primitive-capsules-provide)), so a shared method set would require behavior no document has settled yet.
- Also waiting on the answer: its counterpart at duration resolution, carried in [Time Handoff → Is there a common concept over the duration units?](../time/time.handoff.md#is-there-a-common-concept-over-the-duration-units). `Duration` is the concept the units share and what every contract names today, so nothing here blocks on that answer either.
- Blocks continuation: nothing in the toolchain — the M1 frontend does not check satisfaction, and no semantic checker exists yet. It blocks closing the abstraction layer of the numeric capsules: the four signatures above.
- Path: owner ruling, then the concept declarations beside the widths under `modules/math/integer/` and `modules/math/float/`, then the four signatures retargeted. Until then the widths stand as capsules and those four signatures stand as the exception.

### Does the tower hold widths the reference does not declare?
- State: the numeric widths were `I8`, `I32`, `I64`, `W8`–`W64`, `R32`, `R64`, exactly what `memar-go/math/integer/` and `memar-go/math/float/` declare, and the port added nothing on the strength of a pattern. Reference code outside those packages uses kinds the widths did not hold: a 16-bit signed integer (`memar-go/codec/syllab/decode.go` `GetInt16`, `memar-go/computer/buffer/byteslice/convert/signed-integer-slice-unsafe.go`), complex numbers (`GetComplex64`, `GetComplex128` in the same codec, `complex-slice-unsafe.go`), integers whose width the platform chooses (Go `int` and `uint`, throughout), and an address-sized integer (Go `uintptr`: `memar-go/storage/memory/pointer.go` `type PTR uintptr`, and a race context in `memar-go/computer/runtime/scheduler/thread.go`). Two more reference types are the same values as widths under other names: a byte is an unsigned 8-bit integer and a rune a signed 32-bit one.
- The question, for the owner: (a) is there a 16-bit signed width beside `W16`? (b) are complex numbers a kind the tower holds — the owner's earlier notes name the number system `C` ([The owner's earlier notes on library-implemented types](#the-owners-earlier-notes-on-library-implemented-types)) — and if so, what is the concept and what are the widths? (c) does Memar have a width whose size the platform chooses, or does every value name its width, so that a translation must pick one? (d) is an address-sized integer a number at all, or the memory module's pointer concept? (e) is a byte the width `W8` and a rune the width `I32`, or does each carry a concept of its own — an octet, and the codec's character — which the principle that different meanings are different types ([Khayyam → Type Principles Realized](../khayyam/khayyam.md#type-principles-realized)) would suggest?
- What waits on the answer: nothing in the toolchain. What waits is every declaration in the corpus whose reference type is one of these; until each is answered it has no capsule to name, and a translation reports it rather than choosing one. A contract owned by an abstraction is not blocked for (a) and (c): a signed integer of any width is `Signed` there ([Abstraction in Khayyam → A Concept Is an Abstraction; a Concrete Instance Is a Capsule](../khayyam/abstraction.md#a-concept-is-an-abstraction-a-concrete-instance-is-a-capsule)).
- Path: owner ruling per item, then the widths or concepts declared under `modules/math/integer/`, `modules/math/float/`, or the owning module, then the translation told where each goes.
- Answered (owner, 2026-09-28), item by item; the question stays above as it was asked, and the rules are stated at their protocol homes:
  - (a) Yes. `I16` is declared the way `I8`, `I32`, and `I64` are: a capsule outside `protocol/`, in [`modules/math/integer/signed-16.kh`](../../modules/math/integer/signed-16.kh), with `Equal`, `ToString`, and `FromString` and no other method. Built.
  - (b) Complex numbers are an algebraic concept, not a width. A module for them may come later; the tower gains no complex width. Recorded in [Math → The number tower](../math/math.md#the-number-tower); not built.
  - (c) A platform-sized integer (signed and unsigned) may exist, but its declaration must carry an explicit warning that its size is the platform's and that it is error-prone. Go `int` and `uint` are not mapped onto it silently: a translation still reports them. `Signed` and the widths stay as they are. Recorded in [Math → The number tower](../math/math.md#the-number-tower); not built.
  - (d) An address-sized integer belongs to the memory domain, not to the numeric widths; no math capsule is declared for it. Carried in [Memory Handoff → Where does an address-sized integer (`uintptr`) go?](../memory/memory.handoff.md#where-does-an-address-sized-integer-uintptr-go) and [Memory → Address-sized integers are not numeric widths](../memory/memory.md#address-sized-integers-are-not-numeric-widths). Recorded, not built.
  - (e) Distinct concepts are distinguished by their abstractions. There is no `rune` container capsule: each encoding implements its own character abstraction — the concept is `String_Character` in [`modules/codec/string/protocol/character.kh`](../../modules/codec/string/protocol/character.kh), and the encodings declare `UTF8_Char` and `ASCII_Char`. A byte is not silently `W8`: an octet, an encoding unit, is a different concept from an unsigned 8-bit width, even where the bits are the same. Recorded in [Characters Codec → Characters and octets are not numeric widths](../codec/characters-codec.md#characters-and-octets-are-not-numeric-widths); not built. No corpus-wide rewrite of existing `W8` uses follows from this.
  - What an Integer module may be is answered under [Is `int32` → `W32` in Primitive Capsule Specification a slip?](#is-int32--w32-in-primitive-capsule-specification-a-slip): it may exist, with names taken from the scientific protocols; none is declared.

### Does `Bool` satisfy `Boolean`?
- State: `Bool`'s contract is the reference value type's — `Equal (with Bool) (Bool)`, `ToString`, `FromString`, `ToASCII`, `FromASCII` — and `Boolean` requires the logic module's `Conjunction`, `Disjunction`, `Equivalence`, and `Negation`, each over `Boolean` ([`modules/math/boolean/protocol/boolean.kh`](../../modules/math/boolean/protocol/boolean.kh)). Satisfaction is structural and influencing types must match exactly ([Abstraction in Khayyam → Abstraction Realization](../khayyam/abstraction.md#abstraction-realization-implicit-satisfaction)), so `Bool` does not satisfy `Boolean`. The reference expects it to: `memar-go/libgo/process/command/flag.go` asserts a value to `boolean_p.Boolean[boolean.Boolean]`. A second mismatch sits under it: `Bool` and every width mark `Equal` as their realization of the logic module's `Equivalence`, while that protocol names its method `Equivalence` and carries its own unresolved note on the name (`Equal()`, `Equals()`, `Equivalence()`, or `EQV()`).
- The question, for the owner: (a) does `Bool`'s contract carry conjunction, disjunction, negation, and equivalence taking `Boolean`, so that the one concrete truth value satisfies its own concept? (b) is the operation of equivalence named `Equal`, as `Bool` and the widths declare it, or `Equivalence`, as the logic protocol requires it?
- Whichever way (a) is answered, `Bool` is a capsule and does not belong in the protocol file: its methods are written with the capsule in [`modules/math/boolean/boolean.kh`](../../modules/math/boolean/boolean.kh), and `modules/math/boolean/protocol/boolean.kh` holds `Boolean`.
- What waits on the answer: nothing in the toolchain — the M1 frontend does not check satisfaction. What waits is any contract that receives a `Bool` where a `Boolean` is expected, and a capsule method returning `Bool` against an abstraction returning `Boolean`, which covariant return admits only once `Bool` satisfies `Boolean`. Answer (b) reaches every width's `Equal`.
- Path: owner ruling, then `Bool`'s methods in the capsule's file and, for (b), the one name applied to the widths and the logic protocol together.
- Answered (owner, 2026-09-28), for (b); the question stays above as it was asked: equal is not equivalence. `Bool`'s operation is the logic protocol's, and is named `Equivalence` — `Bool_Equivalence` in [`modules/math/boolean/boolean.kh`](../../modules/math/boolean/boolean.kh). The widths' `Equal` is value equality, a different operation, and keeps its name; the answer does not reach the widths. Built; the rule is stated in [Encapsulation in Khayyam → Primitive Capsule Specification](../khayyam/encapsulation.md#primitive-capsule-specification).
- Still open: (a). `Bool` carries no conjunction, disjunction, or negation over `Boolean`, and its `Equivalence` takes `Bool` where the logic protocol takes `Boolean`, so `Bool` does not satisfy `Boolean` yet.
