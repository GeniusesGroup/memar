# Token

## Abstract
The Token protocol governs the vocabulary by which classified things reach a reader who sees them: what a producer must publish so that an editor, a Markdown preview, a code-hosting page, or any other renderer can colour a file it is not told the contents of, and what that renderer then decides for itself. A token is a named class, and it is never a value, never a piece of text, and never an occurrence: a producer publishes names, kinds, and the statement of which mechanism can answer each name, while every consumer decides every value — colour, weight, size, style, contrast — for itself, against the theme its own reader chose. A token names what a thing **is**, never where it stands, so one identity carries one token wherever it appears in every file; a name published to be matched is published to a parser, not to a human; and a token no rule resolves is discarded rather than defaulted, so a fault anywhere in the chain reads as an absence rather than as a visible nothing. The protocol fixes what a producer owes a consumer, what a consumer is not owed, and the standing costs of the alternatives — and it states no colour, no classification, and no classification's correctness. Whether a token is identified by a standard class the consumer already knows, by a symbolic label the producer publishes, by both, or by nothing the producer publishes is the one question the evidence does not close; the four answers, what each makes possible and impossible, what each costs, and what would settle it are set out as the owner's decision.

## Introduction

### Motivation
A consumer that colours source is handed classified things and has to decide what each looks like. Three failures recur when the vocabulary those classifications come from is left to each side's improvisation, and each of them is expensive in the same way: the reader cannot see that anything went wrong.

**Every producer invents its own vocabulary, and every consumer re-derives it.** One producer's published list of twenty-one names had to be built from scratch against a consumer that already published a classification of its own, because nothing said the two were the same kind of thing; the re-derivation spread three separate questions into one column, because the consumer's existing classification has room for only the first of them ([display.research.002.md → F4](../../modules/khayyam/display/display.research.002.md#f4--the-twenty-one-roles-against-the-hosts-classification)). A consumer that styles by one mechanism and knows nothing of the producer's names then gives part of a published vocabulary a colour and silently leaves the rest uncoloured, and nothing in the producer's statement says which part or that the split exists ([display.research.002.md → F5](../../modules/khayyam/display/display.research.002.md#f5--the-boundary-and-what-is-missing-for-a-consumer-that-never-sees-the-code)).

**An unresolved classification is not a visible nothing; it is a discarded token.** Where a consumer resolves no style for a token, the token is dropped before it is drawn, so the line keeps whatever a second mechanism said and the producer's own silence and the consumer's own fault produce the same picture ([display.research.002.md → F3](../../modules/khayyam/display/display.research.002.md#f3--what-the-host-does-with-a-type-nothing-matches)). The same picture is what a name the consumer's parser cannot read produces: the request succeeds, the tokens arrive, and nothing is drawn.

**A value can reach a reader by a mechanism nobody declared.** A realization given a second mechanism that can also resolve a token's value decides that value for every reader whose theme has never heard of the producer, and no reader can tell that the substitution happened ([display.handoff.md → Decisions](../../modules/khayyam/display/display.handoff.md#decisions)).

The requirement these three failures defeat is narrow and general: a consumer must be able to colour a file it is not told the contents of, consistently, against the theme the reader chose, without each language inventing its own vocabulary. The answer to it cannot depend on which language the file is written in, which consumer is drawing it, or which technology carries the tokens.

### Methodology
Every claim about a mechanism was read out of the mechanism's own implementation rather than from its documentation about itself, and is cited to the artifact that holds it. Those claims establish a requirement and a failure shape; they are one consumer's behaviour, not a taxonomy of consumers, and no consumer's own classification is proposed here as the vocabulary this protocol governs ([display.research.002.md → Methodology](../../modules/khayyam/display/display.research.002.md#methodology), [Content → What a Host's Own Mechanism Costs a Realization](../content.md#what-a-hosts-own-mechanism-costs-a-realization)).

The evidence is one producer's vocabulary carried end to end — the contract, the grammar, the language server, two theme files, the manifest, and the check that keeps them from drifting ([display.md](../../modules/khayyam/display/display.md), [verify-roles.mjs](../../.agents/vscode/extensions/khayyam-language/scripts/verify-roles.mjs)) — examined as a test case and not as the definition. What is generalized from it is the requirement and the failure modes; what stays local to it is every name, every value, and every list.

The protocol states no value and asserts no classification's correctness. Where the evidence settles a question this document rules and says why; where it does not, the options are given with their costs and what would settle each, and the decision is left where it belongs.

## Explanation

### What a Token Is
A **token** is a named class of thing a consumer may render. It carries a name, a statement of what the class applies to, and a kind — and nothing else. Two occurrences of one token are one token, and one occurrence is not a token of its own: an occurrence is a rendering event, and a token is what a renderer is given to decide about.

A token is not:

- **A value.** No colour, no weight, no size, no style, no floor, no default, and no suggested value. A producer that states a value has left this protocol and entered the consumer's.
- **A piece of text, or an extent.** Where a token's name applies to a piece of a source is a realization's business, settled by that realization and by whatever decomposes the source — not by this protocol.
- **An occurrence,** and not a lexical unit. See [The Boundary with the Lexer](#the-boundary-with-the-lexer).
- **A term the producer's own language uses.** A token's name is the producer's name for the class, reached from the producer's own vocabulary. Whether the language itself draws that distinction, and calls it that, is a separate claim about the language and belongs to the language's own documents ([display.json → `classification.authority`](../../modules/khayyam/display/display.json) records which names in that realization are the owner's and which are the toolchain's).
- **A claim of correctness.** No token is right because this protocol states it. See [What Conformance Means](#what-conformance-means).

The word is used here for one thing only, and two other concepts in this repository carry words a reader may confuse with it. The Lexer protocol's output is a **lexical unit**, and the name for that concept is deliberately unsettled ([Lexer → Lexical Unit and naming](./computer/lexer.md#lexical-unit-and-naming)). [Content → Lexical Token vs. Sense](../content.md#lexical-token-vs-sense--handling-ambiguity)'s **Lexical Token** is a third thing again — a unique lexical string that carries sense edges and is disambiguated by composition. Three concepts, three meanings; this document is about the first, and a reader arriving from either of the others should know they are not looking at the same thing.

### The Boundary with the Lexer
The two protocols answer different questions, and each rule belongs to the document whose subject it is.

The [Lexer](./computer/lexer.md) protocol owns **how a source is decomposed**: what a lexical unit is, where boundaries fall and what determines them, the lexical model that drives recognition, trivia, lexical error, delivery, the change contract, and the lifecycle capsule. Each of those is a property of a source and of the model reading it, settled without reference to any renderer, and the protocol's own boundary principles are stated on that ground.

This protocol owns **how a classified thing reaches a reader who sees it**: what a token names, how it is identified, who decides its value, what happens when one cannot be resolved, and what a producer must publish for a consumer to work with.

The seam is the occurrence. This protocol does not decide how text is divided; the Lexer does not decide what a renderer calls a unit. A renderer may be handed the Lexer's units, a host's own tokens, a parser's annotations, or nothing it can classify at all, and the token names hold across whichever of those it is given. The two failure owners are different as well — the Lexer's is a unit not grounded in an observable extent of the source, this one's is a value not decided by the consumer — and a rule stated in both documents is a rule that drifts apart.

### What a Producer Publishes
A producer — a language, or any source of text a consumer may render — publishes a set of tokens. For each token it publishes exactly four things:

1. **A name,** spelled so that a consumer can key a rule by it.
2. **What the token applies to,** in terms a reader can check against a source.
3. **Its kind:** which standard class already published by the consumer it is a kind of, or that it is this producer's own root together with the reason it has no counterpart.
4. **Which mechanism can answer it** — one that decides from the syntax alone, or one that must see the whole document. This is a property of what the token is rather than of any realization, and it is the one thing a consumer must know before it can tell whether it is able to answer the token at all. The standing case for it is a matcher that sees one line at a time and holds no symbol table: a name whose whole distinction is the block it was declared in has no per-line form to be carried by, and the producer says so on the token rather than leaving a consumer to discover it ([display.json → `conformance.howARoleIsImplemented`](../../modules/khayyam/display/display.json)).

A kind has exactly three answers, and a producer that gives a fourth has not stated one ([display.research.002.md → F1](../../modules/khayyam/display/display.research.002.md#f1--the-hosts-own-classification-twenty-four-token-types-and-eight-modifiers), [→ F2](../../modules/khayyam/display/display.research.002.md#f2--the-super-type-mechanism-and-what-a-type-with-no-super-type-is)):

- **A standard class the token is a kind of.** The consumer matches a rule's key against a token's whole type hierarchy, and that hierarchy is built only from declarations someone made, so a token that declares no class is a hierarchy of exactly itself and no rule keyed on a standard class ever reaches it. A declaration is therefore what makes a producer's tokens reachable by a rule a consumer's reader already has, whether or not that reader's theme has ever heard of the producer.
- **The producer's own root,** with the reason there is no counterpart. A root is a real result rather than a failure: it is what the producer adds to the vocabulary a consumer already has, and it is visible in the published statement and in any verdict a consumer's check prints.
- **A standard class under the token's own name,** which is therefore declared nowhere. A consumer that already registers that name for that kind must not be told about it again: the registration overwrites the consumer's own entry, its number and its styling property included, and declaring a class to be a kind of itself makes the hierarchy walk a cycle that never ends.

What a producer is **not** owed, and what it therefore does not publish:

- **No value on any channel.** Not a default, not a suggestion, not a floor. A consumer that receives one has been given another party's decision.
- **No promise that a theme which has never heard of the producer will style its tokens.** Where a kind was declared, a rule keyed on the standard class reaches the token; that is a permission the declaration earns, not a guarantee this protocol makes, and it does not hold for a root.
- **No scope names, no grammar, no theme, and no registration with any consumer.** Those are one realization's own files. A scope name published as part of the vocabulary is read by a portable consumer as though it were the vocabulary's, and a scope matches by prefix on its segments, so a producer's scope reaches a consumer's published classification only when it nests under what that class probes — some do and some do not, and the difference is invisible in the file ([display.research.002.md → F5](../../modules/khayyam/display/display.research.002.md#f5--the-boundary-and-what-is-missing-for-a-consumer-that-never-sees-the-code)).
- **No obligation on a consumer to render a token, or to render two distinct tokens differently.** A producer may state that two tokens are distinct and what a reader must be able to tell apart — that is a claim about what must be legible, and it is the most a producer may state about a consumer's own values. Distinctness is not a floor, and a consumer that gives two tokens one value has not broken a rule of this protocol.

### What a Consumer Decides
- **Every value, for every token, on every channel the consumer has.** A token with no value is a token the consumer has not resolved, and there is no fallback standing in for one.
- **One decision, one mechanism.** A token's value is resolved by exactly one mechanism, and a realization that adds a second mechanism able to resolve the same value carries a defect whatever that mechanism decides. A second mechanism cannot displace a value a rule already set; the cost is not that it overrides, it is that it decides the value for every reader whose theme has never heard of the producer, and no reader can see that the substitution occurred ([display.handoff.md → Decisions](../../modules/khayyam/display/display.handoff.md#decisions)).
- **An unresolved token is discarded, not defaulted.** A consumer that resolves no style for a token does not draw it unstyled; it does not draw it, and whatever a second mechanism said about that text stands in its place with no error anywhere ([display.research.002.md → F3](../../modules/khayyam/display/display.research.002.md#f3--what-the-host-does-with-a-type-nothing-matches)).
- **A consumer names the tokens it cannot answer.** Since an unresolved token is an absence rather than a visible nothing, the published vocabulary is where a consumer states which of its tokens it leaves to a mechanism that can answer them, and a consumer that cannot answer a token is expected to name it rather than guess a substitute for it. This is also what a partial realization owes, and naming what it cannot answer discharges the obligation: a consumer that answers only what syntax determines conforms by saying so.
- **The consumer's own rules over the consumer's own values** — a floor it declares for itself, a contrast measured against the background that same sheet declares, two tokens given one value, a channel the producer never named. A producer's statement carries no floor and no palette; a realization's own sheet states a floor for itself and holds its own values to it, and the protocol takes no position on any value ([display.research.001.md → F3](../../modules/khayyam/display/display.research.001.md#f3--a-proposed-value-per-role-per-theme-with-its-measured-contrast) is one realization's measurement of one sheet, not a claim about values).

### How a Token Is Identified
Six things the evidence settles, and one it does not.

**Settled, and ruled here:**

1. **A token is identified by a name, and a name published to be matched is published to a parser.** A consumer parses a rule's key, matches what it finds against a token's type hierarchy, and refuses identifiers that do not fit its own grammar for them. A name chosen to read as `role.language` can never be matched by a rule keyed the same way, and a name outside the consumer's identifier grammar cannot be registered at all. The constraint is a property of the parser and not of the name, so a producer chooses its spelling knowing that a consumer's grammar constrains it. This settles what identity is made of and rules out every alternative that is not a name: a token cannot be identified by an extent, a position, a structure, or any property a rule cannot be written against ([display.research.002.md → F2, F6](../../modules/khayyam/display/display.research.002.md#f6--principles-with-what-each-cost), [display.handoff.md → What a Host's Own Mechanism Costs a Realization](../../modules/khayyam/display/display.handoff.md#what-a-hosts-own-mechanism-costs-a-realization)).
2. **A kind is a separate statement from a name, and a token with no declared kind is a root.** A hierarchy built from no declaration contains the token's own name and nothing else, so a root is styled by nothing a consumer's reader already has. That is what makes a sheet's value for a root a requirement rather than a formality, and it is the standing price of introducing a class the consumer's vocabulary does not contain.
3. **A token names what a thing is, never where it stands.** One identity carries one token wherever it appears in every file, at a declaration and at each use, and this is measurable over a wire rather than asserted: a parameter carries the parameter's token in a signature and in the body it is used in ([display.md → The roles](../../modules/khayyam/display/display.md#the-roles)).
4. **A token carries no value, and a producer that publishes one has left the protocol.**
5. **One mechanism decides a token's value.** See [What a Consumer Decides](#what-a-consumer-decides).
6. **An unresolved token is an absence, and naming the unanswerable is part of the published vocabulary.**

**Not settled, and left as the owner's decision:** what form a token's identity takes. A consumer's own published classification may or may not be a vocabulary this protocol builds on; that is a question about how much authority a consumer's vocabulary has over a producer's own distinctions, and the evidence constrains every answer without closing any. The four answers below are the live ones, each with what it makes possible, what it makes impossible, what it costs, what the evidence does and does not say about it, and what would settle it.

**A — A standard class only.** A token is a member of a classification the consumer already publishes, and a producer may not introduce a class.
- *Possible:* a theme that has never heard of the producer styles every one of its tokens, with nothing to extend and no per-token rule to write.
- *Impossible:* any distinction the classification has no room for — a category of thing where the classification offers only a generic class, a form the language refuses, a use a resolver could not resolve. Those are not kinds of anything, so under this answer they leave the vocabulary entirely and the reader is told nothing about them.
- *Costs:* the vocabulary is the consumer's, so the protocol is shaped by whichever consumer was measured; a second consumer with a different classification forces the producer to publish again, and the producer's own questions get re-derived against each consumer's axes — which is the re-derivation this document exists to stop.
- *What the evidence says:* it works, and its working was measured, but the measured case carried four tokens that did not fit as roots anyway. That is the contradiction rather than a solution, and the owner's ruling on those four is the same question this answer poses.
- *What would settle it:* whether a producer's own distinctions can be expressed in a foreign classification at all, which the first producer to declare a category the consumer has no counterpart for would show.

**B — A symbolic label the producer publishes.** A token is a name the producer publishes, and the consumer maps it to its own rendering.
- *Possible:* the producer's distinctions are stated once, in the producer's own vocabulary, and every consumer works from the same list.
- *Impossible:* nothing at the vocabulary level. A consumer has no rule of its own to fall back on, so every consumer writes a rule per token, and a consumer that misses one draws nothing for that token and reports nothing.
- *Costs:* measured. A published vocabulary reached this way produced a file that drew as though the producer had said nothing, across several rounds, with every automated check green throughout — the request succeeded, the tokens arrived, and the line carried only the other mechanism's answer. Every consumer that is not the one the producer tested against repeats that.
- *What the evidence says:* this is the only mechanism that reaches a consumer with no classification of its own, and the only one where a single typo in a name is fatal with no error.
- *What would settle it:* the spelling decision below, and whether a consumer may style by a name it did not read from the producer.

**C — A published label plus a declared kind.** A token is the producer's own name, and it also declares which standard class it is a kind of, or declares itself a root with the reason.
- *Possible:* the producer's own vocabulary and a foreign theme's existing rules at the same time. A rule keyed on the declared class reaches the token through the declaration, and the producer's own value still wins where both apply, because a consumer's matching arithmetic places a rule keyed on the token's own name nearer in the hierarchy than one keyed on the class — the realization states that arithmetic in its own check, in the consumer's own numbers, rather than asserting it ([verify-roles.mjs](../../.agents/vscode/extensions/khayyam-language/scripts/verify-roles.mjs)).
- *Impossible:* a token whose only identity is positional or structural, and any claim that the class it is declared under is the right class.
- *Costs:* the kind statement is a claim about the producer that the producer may never have made, and the declaration is a per-consumer contribution, so one vocabulary is declared once per consumer rather than once.
- *What the evidence says:* this is the only form measured end to end, and the measurement is the evidence that a declaration works. It does not show that a declaration should be required, and it was measured against one consumer.
- *What would settle it:* who owns the kind claim, and whether a consumer's classification is a vocabulary this protocol may build on at all.

**D — No published vocabulary.** The consumer classifies the source itself, from its own model, and the producer publishes nothing for it to match.
- *Possible:* a renderer with no dependency on the producer's tooling, and a producer that publishes no names and therefore no names for a consumer to get wrong.
- *Impossible:* ruling 3. A consumer that cannot tell what a thing is cannot state what a thing is, so a producer's identity rules become unenforceable — nothing checks them, and the reader is told a thing's identity by a consumer's guess.
- *Costs:* the consumer becomes a second implementation of the producer's semantics, and the failure is a *partial* silence. A consumer styling by one mechanism alone gives part of a vocabulary a colour and leaves the rest uncoloured, and nothing says which part or that the split exists.
- *What the evidence says:* this is what a code-hosting page and most documentation engines do today, and what it costs is a failure no reader can see: nothing announces which part of a vocabulary was honoured and which part was not.
- *What would settle it:* whether a token is required to be named at all — whether this protocol governs a vocabulary or a rendering.

**Two consequences follow whichever answer is chosen, and are the owner's as well.**

- **The portable spelling.** Either this protocol fixes one spelling a consumer may key a rule by and each stricter consumer translates in its own files, or the producer's spelling is authoritative and a consumer that cannot parse it is given an alias. The cost of the first is a parser's grammar imported into a protocol; the cost of the second is that two consumers can disagree about a token's name and neither is wrong. *What would settle it:* the second consumer — the first one unable to read the first one's spelling is the whole of the argument ([display.research.002.md → F5](../../modules/khayyam/display/display.research.002.md#f5--the-boundary-and-what-is-missing-for-a-consumer-that-never-sees-the-code)).
- **Who owns the kind claim.** The cost of a display contract owning it is that the contract holds a claim about the language that the language has not made, and a later reader cannot tell a claim about the language from a claim about how it is read. The cost of the language owning it is that a consumer's classification enters the language's own specification, and the language must be re-read to learn which classes a consumer happens to have. *What would settle it:* whether the producer's own documents will state which of its categories are kinds of which, and the first consumer that is not the one measured.

### Standing Costs
These are the faults this class of work hits, as principles with what each one cost. Each is a rule a later realization can apply, not an account of what happened.

1. **A consumer's mechanism is read out of the consumer,** and out of its code where its documentation names a field but not a rule. *Cost:* rounds in which every check was green, the extension was installed, and the reader saw no colour from the producer at all, with the two rules deciding the outcome unknown until the implementation was read.
2. **A realization must not reshape the published vocabulary.** A realization names its own entries, its own scope names, and its own diagnostic codes; a consumer that reads another form carries the translation in its own files. *Cost:* a name the consumer could not match, discovered only because a file drew as though nothing had been said — and a spelling then had to be changed in the producer, its tests, and its diagnostics at once.
3. **One mechanism per decision, and one decision per mechanism.** What kind of thing a token is is decided in one place, what a consumer is able to answer in another, and what the token looks like in the consumer's own — and no two of these are ever answered by the same mechanism. *Cost:* two delivery mechanisms carried at once with no run that showed which one a reader saw, and a token list answering three questions in one column, so a rule about one of them had to be derived from the other two.
4. **A name published to be matched is published to a parser.** *Cost:* a published vocabulary a consumer could not read, and no portable spelling in the contract — so every consumer would have invented its own.
5. **Check what the reader sees, not what the checker reads.** A check proves that files agree; no run of it proves a value reached a screen, and a discarded token leaves a line that looks properly coloured. *Cost:* an unmeasured sheet, and a working feature whose own log lines had to be marked as self-tests so they would not read as a fault.
6. **A bridge between two mechanisms is the consumer's to publish, not the producer's to add.** Where a consumer already publishes a probe that reaches a producer's classifications, a producer that writes its own is writing a second copy. *Cost:* a contribution written, measured, and removed.
7. **A token no mechanism can answer is named as such, with its reason where a reader will see it.** *Cost:* the published vocabulary came to owe a realization something it had not owed before — a consumer that can only match syntax must read the reason before it starts rather than after it has guessed.

### What Conformance Means
A consumer conforms when, for every token the producer publishes, it either renders the token with a value it decided for itself or names the token among those it cannot answer. A producer does not conform by supplying a value, and a consumer does not conform by rendering one the producer supplied. Conformance here is a property of the exchange and not of the outcome: nothing in this protocol makes a colour correct, a classification right, or a reader better served, and a consumer that renders every token in colours its own reader dislikes conforms ([Protocol → Conformance](../protocol.md#conformance)). Conformance is checked, never inferred from a label, and the check a producer runs against one consumer is that consumer's business rather than part of this protocol.
