# Test Practice
> **Purpose:** This practice operationalizes [test.md](./test.md). It turns the protocol's claim — that a Test is a named Process's written expectations, produced before the work and kept afterwards — into the followable procedure, in two parts. **The cycle** is what one development step does: state the expectations, enact the smallest increment that could satisfy them, check the instance against them, and record the disposition. **The artifact** is what one Test is: which Process it names, what it states, what it may assume, where it is recorded, and the fact that it outlives the run. The reasons live in the protocol document and are not restated here; each step links to the topic that argues it.

## What Each Part Covers
This procedure has two units and two scopes, and they are not the same size. **The Cycle** covers one **development step** — work whose expectations can be stated in one pass and checked after. **The Artifact** covers one **Test** — the written expectations of one **named Process**. A Test may hold many expectations of that Process and may exercise as much of it as those expectations reach; it may not hold expectations of a second Process, because a Test whose subject is not nameable cannot be reviewed against anything ([test.md → A Test's Subject Is a Named Process](./test.md#a-tests-subject-is-a-named-process)). Where a second Process's expectations belong, that is a second Test.

## The Cycle
The unit of this part is **one development step** — a piece of work whose expectations can be stated in one pass and whose enactment can then be checked: a function, a defect fix, a document section, a feature, a protocol contract, a piece of store equipment being designed. A larger development is decomposed into steps and each runs the cycle below. Scale changes how much the expectation states, never whether it is stated first ([test.md → The Expectation Is Written Before the Work](./test.md#the-expectation-is-written-before-the-work)).

For each development step:

1. **Name the process being developed and its intent.** What entity or behavior is being advanced, for what end — who or what brings what in, what must come out, under which conditions, with which outcomes ([test.md → A Test's Subject Is a Named Process](./test.md#a-tests-subject-is-a-named-process)). A step whose developed process cannot be named is not ready for its expectations; discover that process first.

2. **Write the expectations, in checkable form, before the work** — following **The Artifact** below, which is the procedure for one Test. The expectations are of the developed process, not of the developers' procedure ([test.md → The Expectation Is Written Before the Work](./test.md#the-expectation-is-written-before-the-work)). Establish two facts as you go: that the expectation is genuinely checkable, and that it is not already satisfied. Running the check before the work is the usual way to establish both; the obligation is the two facts, not the run.

3. **Enact the smallest increment that could satisfy the expectation.** The work is judged against the written expectation only. Enlarging the step's intent mid-flight is not enactment; it is a new expectation — return to step 2 and record it.

4. **Run the check and record the disposition.**
   - **Satisfied** — the step is done; the Test stays as the step's record.
   - **Not satisfied, expectation sound** — fix the work; re-run the check.
   - **Expectation itself wrong or incomplete** — revise the expectation *first*, as a recorded change, then continue. An expectation revised after the instance to match what was built, without the revision recorded, has silently converted the discipline into description ([Process → Expectations and Checks](../../process.md#expectations-and-checks)).

5. **Keep the Test.** It stays in the tree, is re-checked whenever the Process's defining document changes, and is retired only when the Process it names no longer exists ([test.md → What a Test Is](./test.md#what-a-test-is)).

## The Artifact
The unit of this part is **one Test**nt that defines it.** Write the name the defining document uses, and cite it. A Process with no defining document has no stated expectations to test, and the correct outcome of this step is to go and state that document, not to write the Test from the code ([test.md → A Test's Subject Is a Named Process](./test.md#a-tests-subject-is-a-named-process)).
1. **Name the Process, and find the document that defines it.** Write the name the defining document uses, and cite it. A Process with no defining document has no stated expectations to test, and the correct outcome of this step is to go and state that document, not to write the Test from the code ([test.md → A Test's Subject Is a Named Process](./test.md#a-tests-subject-is-a-named-process)).
2. **Enumerate the decidable expectations of that Process.** Go through the defining document's own claims: the inputs it promises to accept, the outputs it promises to produce, the conditions each applies under, the outcomes that count as which, and the errors it names. Expectation by expectation, ask whether it is decidable before enactment; each one that is becomes a candidate assertion, and each one that is not is recorded in the Test in whatever form its domain applies, per the second boundary in [test.md → A Test Is Part of the System That Owes It](./test.md#a-test-is-part-of-the-system-that-owes-it).
3. **Write each expectation so another participant could check it without asking you.** This is the another-agent test, and it is where most writing fails. If a reader would have to ask what is meant, the expectation has not been stated yet. Where the developed process is software and the expectation can be executed by a machine, write it in the form that can be executed — the ordinary realization, not an optional extra ([TDD → Test Is Not Its Implementation](./test.md#the-expectation-is-written-before-the-work)).
4. **Assert the contract, not the implementation.** Before each assertion, check that the defining document promises what you are about to assert. If it does not, stop: either the assertion is about an accident and is dropped, or the document needs a claim added and the Test is written against that ([test.md → What a Test May Assume](./test.md#what-a-test-may-assume)).
5. **Establish that the expectation is checkable and not already satisfied.** Running the check before the work is the usual way to establish both, and for software this is the red of the cycle [The Cycle](#the-cycle) names. The obligation is the two facts, not the run.
6. **Record it where the owning project's Rules require.** Locate the Rules that govern placement and naming for the project that owns the Process — in this repository they are stated in the `rules/` folder of the module realizing [test.md](./test.md), and a project that has stated none is free to choose. The Test follows the project's Rule, not the other way round ([test.md → What a Test Is Not](./test.md#what-a-test-is-not)).
7. **Leave it in place when the run is over.** The Test stays in the tree, is re-checked whenever the Process's defining document changes, and is retired only when the Process it names no longer exists. A Test deleted with the branch that introduced it has not been kept, which is the standing [test.md → What a Test Is](./test.md#what-a-test-is) exists to establish.

## Where the Expectation Lives
The Test is recorded in whatever form the checks can be applied and wherever the owning project's Rules put it; the protocol fixes neither. What the protocol does fix is stated in [test.md → What a Test Is](./test.md#what-a-test-is) and is worth restating as the reason the placement is left to a Rule: a system's Test is a standing part of the system, and a layout that scatters it, hides it under a naming scheme a reader cannot guess, or omits it from the tree makes the standing unenforceable — which is a property of the layout, and therefore the layout's owner's subject rather than this protocol's.

## Failure Modes
- **A Test with no named subject.** It exercises code without saying which Process's expectations it holds, so it cannot be reviewed, shown redundant, or shown missing. Return to step 1.
- **Assertions about the implementation.** Asserting an internal name, an allocation count, an incidental ordering, or a helper's return binds the system to an accident, and the next conforming implementation fails a check that was never about the contract. Return to step 4.
- **A Test quietly contradicting the defining document.** The Test has become the authority over the Process it was written from. Fix the document or the Test at the concept layer, as a recorded change; never edit the Test alone to match the code ([TDD → Relationship to Other Concepts](./test.md#relationship-to-other-concepts)).
- **An expectation edited to match what was built.** The expectation no longer states what was intended, only what happened, and the next check has lost its subject. Revise the expectation first, as a recorded change ([Process → Expectations and Checks](../../process.md#expectations-and-checks)).
- **A Test deleted with its branch.** The expectation leaves the system, and the defect it was written for is free to return. Keep it, per step 7.
- **Tests ordered so that one decides the next's outcome.** The suite's verdict becomes a property of the order rather than of the system. Give each Test its own state ([test.md → What a Test May Assume](./test.md#what-a-test-may-assume)).
- **A coverage number standing in for the obligation.** A number says which parts were reached; it cannot say whether every decidable expectation is stated. Enumerate the surface instead ([test.md → What a Passing Suite Establishes](./test.md#what-a-passing-suite-establishes)).
- **A green run reported as conformance.** The run answered whether the checks passed, not whether the system conforms; the second question is broader and the run does not reach it.
- **A test file with no Process behind it.** A script kept around "to check that one thing" is not a Test under this protocol. Either name the Process whose expectations it holds and bring it under the procedure, or let it go.

## Boundary: When a Test Is Not the Artifact
- **The subject is not yet defined.** When the Process is still an inquiry, its expectations are not the subject; state the inquiry's expectations — what evidence it must produce, what decision it must return, what record it must leave — and let the finding become a Test when the Process's definition exists ([test.md → Test, Verification, and Inquiry](./test.md#test-verification-and-inquiry)).
- **The work is already enacted.** Writing expectations to check existing work is verification. The artifact is a Test and carries the same obligations, but the check no longer establishes anything about intent, because the ordering cannot be recovered afterward ([Process → Expectations and Checks](../../process.md#expectations-and-checks)).
- **The expectations cannot be executed.** A checkout counter's ergonomics, an organization's process, a document's acceptance condition. The Test is then the written record of what must hold and by what observation, which satisfies the standing and fails only a runner, which was never the obligation.

## Scaling
- **Function scale** — the expected inputs, outputs, and failure behavior of one Process, stated before the function and checked against it.
- **Feature scale** — the umbrella requirements concept read as the developed Process's expectations ([test.md → An Umbrella Requirement Is a Developed Process's Expectations](./test.md#an-umbrella-requirement-is-a-developed-processs-expectations)); the mechanically checkable subset is this procedure's artifact.
- **System scale** — the expected interfaces and contracts of the system's protocol surface, one Test per named Process within it, the surface enumerated so that absence is visible ([test.md → A Test Is Part of the System That Owes It](./test.md#a-test-is-part-of-the-system-that-owes-it)). In Memar's own production the surface is the protocol documents, and the Tests are the checks run against this repository.
