# Event Handoff
Open work for [event.md](./event.md). Entries are mutable current state, revised as each item moves and removed when it resolves or is dropped. See [documentation-handoff.md](../../documentation-handoff.md) for what a handoff is.

## Open Questions

### Can the target capsule's two fields be realized at all?
- State: `modules/process/race/race-event-target.kh` holds a `Locker` and an `ADT_List`, and **nothing in the sources implement either**. `tp Locker ab` at `modules/process/sync/protocol/locker.kh:7` with `Sync_Locker_Lock`/`Unlock` has exactly one consumer, `modules/memory/page/protocol/page.kh:15,30`, which composes the abstraction and implements nothing. `tp ADT_List ab` at `modules/computer/adt/list/protocol/list.kh:18` has **no consumer at all** — it is the only hit for its own name in the sources. Worse, `ADT_List` composes `Computer_Container`, which reaches iteration and containment but **no append**: `Container_Append` at `modules/computer/adt/container/protocol/append.kh:12` is composed by nothing, and `ADT_List` does not reach it. So `AddEventListener` has no declared operation to call and `RemoveEventListener` has no remove-by-value. The alternative reading is `Array_Dynamic` at `modules/computer/adt/array/protocol/dynamic.kh:12`, whose own comment says a domain value holding such a run "is its own named type" — which would mean inventing a `Listener_List` abstraction, and an invented abstraction looks current in a way a residue block does not.
- Next: decide whether a domain list of listeners is a container the sources should declare, or whether the listener set is small and bounded enough that the target declares its own named type over a fixed capacity — which is also where the ported `CNF_InitialListenersLength = 8` in `modules/process/event/const.kh` would land. The Go's alternative (`// TODO::: Change to use atomic operation instead of sync.`) has no Khayyam contract either: `modules/process/sync/protocol/atomic.kh:3` declares `Sync_AtomicAccessor` with no methods. That alternative was not carried into the capsule and is recorded here rather than in a comment, per [Test → A Test Is Documentation, and Comment Is the Last Place to Look](./test.md#a-test-is-documentation-and-comment-is-the-last-place-to-look).
- Question for the owner: do the sources owe a concrete list and a concrete lock, or does the target declare a domain type of its own?

### What is the target capsule called?
- State: the specialization is `EventTarget_Race_Event` and the capsule realizing it is `Race_EventTarget`. It cannot take the abstraction's own name: [the qualified names rule's open case](../../../modules/khayyam/rules/qualified-names/qualified-names.handoff.md) is explicit that between an abstraction and a capsule one module path names alike the abstraction keeps the name and "a capsule is named where a realization is chosen. What the capsule is called is its author's choice; this rule supplies no suffix for it" — and `Bool` realizing `Boolean`, and `GUI_History_2` beside `GUI_History`, are the sources' instances. `Race_EventTarget` is that choice and nothing more: it is not derived from a rule, and the sources now holds three spellings of one concept (`EventTarget`, `EventTarget_Race_Event`, `Race_EventTarget`) that no document relates.
- Next: the ruling the qualified-names handoff already asks for — what a capsule that gives up its name to an abstraction is called, per capsule or by a stated convention. Until it is given, the next target this module writes will pick a third spelling by the same coin flip.
- Question for the owner: one convention for a capsule that yields its name to an abstraction, or a ruling per capsule?

### A handler that registers against the target it is being dispatched to deadlocks
- State: the ported dispatch holds the mutual exclusion across every listener invocation, so a handler that calls `AddEventListener` or `RemoveEventListener` on the same target from inside its own dispatch waits for that dispatch to end. [Dispatch → A dispatch's listener set is the set the dispatch started with](./event.md#a-dispatchs-listener-set-is-the-set-the-dispatch-started-with) is satisfied by that lock trivially and at that price; a target that copies the set and releases the lock before iterating satisfies the same rule without the hazard, and the copy is a decision about the dispatch mechanism, which [Dispatch → What this protocol does not claim](./event.md#what-this-protocol-does-not-claim) assigns elsewhere rather than to this abstraction.
- Next: whichever way the dispatch mechanism is eventually specified, the copy belongs to it and this capsule follows. What is not settled is whether the protocol should say anything today about a handler re-entering its own target — the protocol's current obligations do not forbid it, and a reader could reasonably infer from the snapshot rule that it is safe.
- Question for the owner: does the protocol owe an explicit statement that a handler must not re-enter its own target, or is that the dispatch mechanism's rule to state?

### What does `Logic_Equivalence` over two Event occurrences answer?
- State: `Event` composes `Logic_Equivalence`, and the live sources declare it. [The Error → Identity and equality](./error.md#identity-and-equality) holds identity to be the type-level identifier alone and declines to declare an `Equivalence` method at all, on the grounds that a second identity source is a second thing to keep consistent. Applied literally, that argument reaches `Event`: absent an occurrence identity the `DataType` does not supply, two occurrences of one kind are equal exactly when their types are, so the composed method compares kinds and is already available from `DataTypeID()`. The case that differs is that an Event is an occurrence rather than an identity — two occurrences of `Race_Event` really are two things, and a listener asking "is this the one I already handled" has a question the type identifier cannot answer. Whether that question needs an answer at all is what is undecided, and `Event`'s `Time` is the only thing currently distinguishing two occurrences. **What writing the capsule turned up**: `Logic_Equivalence` in `modules/math/logic/protocol/equivalence.kh` declares the abstraction and **no method at all** — the `Equivalence(with T) bool` it stands for is still inside that file's own Go block, along with its four alternative spellings (`Equal`, `Equals`, `Equivalence`, `EQV`) left as a `TODO:::`. So `Event`'s composition of it is currently inert: there is nothing for a realization to implement, which is why `modules/process/event/event.kh` declares `GetDataType` and `GetTime` and no equivalence method. The question below is therefore two questions, and the first one is smaller than the second.
- Next: first settle which spelling the method takes, since the abstraction cannot be satisfied until it has one and the four candidates are the Go residue's own indecision, not a Khayyam choice. Then settle what it compares. Two answers are available for the second and they are not equivalent — either it compares kind and the composition is dropped as redundant, or occurrences carry an identity of their own and the method compares that. The latter is a change to what `Event` composes, so it reaches [Abstraction → Behavior Over Type Identity](../../khayyam/abstraction.md#behavior-over-type-identity) before it reaches this document.
- Question for the owner: is "have I already seen this occurrence" a question Memar asks, and if so what distinguishes two occurrences of one kind? And separately, is that question worth an abstraction whose method every realization of every Event must then declare?

### In what order does a target visit its listeners, and is that order promised?
- State: this protocol requires that a dispatch sees the listener set as it stood when it began, so a handler cannot change what the rest of the dispatch sees. It deliberately says nothing about the order the set is visited in, and correspondingly tells a listener it may not assume it is first or last. A protocol that refuses to state the order leaves a system's dispatch behavior unspecified, and a listener written against "registration order" is written against an incident rather than a contract.
- Next: decide whether order is part of the contract or incidental to a target's realization. Registration order is the obvious candidate and is cheap to promise; listener priority is the same question with more surface. What would falsify promising registration order: a target whose realization serves listeners concurrently, where order is not a fact the target has.
- Question for the owner: does a dispatch promise an order, and if so which?

### Should `Event`'s Time be the occurrence's or the dispatch's?
- State: `Observer_Time` is composed so a listener can tell two occurrences apart. Which time it is was not settled. For an occurrence produced and dispatched at once they are the same fact, and the sources' residue treats them as one. They diverge the moment an occurrence is retained and dispatched again — replay after a restart, redelivery, a queue — and then a listener comparing against a time it recorded earlier sees a different answer for what it thought was the same occurrence. That interacts directly with the equivalence question above: two occurrences are distinguishable by time, and if the time moves on redelivery they are not the same occurrence by the only measure the base contract has.
- Next: settle whether the composed time is fixed at occurrence or set at dispatch, and state which in this document. If it is fixed at occurrence, redelivery becomes something the dispatch mechanism must preserve rather than something it may restamp.
- Question for the owner: does an Event's time belong to the fact or to the notification?

### What does the specialization cost, and does the language owe a type-parameter form?
- State: specialization is written out, so a module exposing *M* targets over *N* kinds of event writes *N*×*M* declarations where one parameterized `EventTarget[E]` would be one declaration and *M* uses. **That cost is the exposing module's and not this protocol's**, which is what [A target accepts only the kind of event it declared](./event.md#how-a-target-narrows-to-one-kind-of-event) now states: this protocol declares `Event`, `EventListener`, and `EventTarget` and no specialization of any of them, and a module that wants a target for its own kind writes the specialization in its own `protocol/`. The sources' one live specialization is therefore `Race_EventTarget` in `modules/process/race/protocol/event-target-race-event.kh`, owned by the race module, with its capsule beside it in `modules/process/race/race-event-target.kh`; the memory ADTs at `modules/memory/record/protocol/model.kh:81`, `modules/memory/page/protocol/page.kh:82`, and `modules/memory/block/protocol/block.kh:51` each carry an `EventTarget[]` composition note, so the multiplication is already visible in modules that have no live target yet.
- Next: nothing here can settle it, and nothing here should try. The requirement is named so that the polymorphism discussion meets a concrete case rather than an abstract one.
- Question for the owner: none from this document — the question belongs to the language, and this protocol's only obligation was to price the requirement.

### Does the protocol owe a registration type, and do any of the five belong on one?
- State: [The EventListener contract](./event.md#the-eventlistener-contract) rejects capture, once, passive, synchrony, and an abort signal as members of `EventListener`, on the ground that each is a property of one registration rather than of a listener. That is the whole of the argument as it stands, and it does not say what happens to them. The sources' shape for an optional capability is a separate abstraction a concrete type may compose — `ErrStorageUnavailable` composes `Internal` and `Temporary` at `modules/process/error/protocol/error-internal.kh` — so even a kept one would not be a member on `EventListener`: a listener is not a capsule with its own composition, and the thing that composes a capability would be the registration, which this protocol does not declare at all. `AddEventListener` takes a bare `EventListener` and returns nothing about what it recorded, so a registration in this protocol is a fact a target keeps and nothing states it.
- Next: decide whether a registration is a thing this protocol declares. If it is not, the five stay out and the answer to "once" and "passive" becomes "not in this protocol; a dispatch mechanism states them on its own registration type" — which the current text already implies and nowhere states. If it is, `AddEventListener`/`RemoveEventListener` take and return something, and the questions a registration must answer (`Does it fire at most once?`, `Is it passive?`, `Which phase of the dispatch does it observe?`) become a contract with its own Test.
- Question for the owner: is a registration a concept this protocol owns, or is every one of the five permanently out and the sentence saying so written into [The EventListener contract](./event.md#the-eventlistener-contract) rather than left to the reader to infer?

The second is likelier now that `EventListener` carries `EventHandler` and nothing else, since a GUI needing more of its own would have more than one member.
- Next: read the GUI abstraction's own methods and decide which reading holds; if the second, the two residue comments name the wrong path and say nothing about this protocol.
- Question for the owner: none — this is a fact to be read, not a judgment to be made.

### Should `Event` carry its module's path?
- State: this module's declarations are qualified — `EventTarget`, `EventTarget_Race_Event` — while the base `Event` is bare, beside `GUI_Event`, `Race_Event`, and `ProcessLog_Event` in the modules that specialize it. The [qualified names rule](../../../modules/khayyam/rules/qualified-names/qualified-names.md) keeps a module prefix only where the sources make the plain name ambiguous, and records at [its handoff](../../../modules/khayyam/rules/qualified-names/qualified-names.handoff.md) that which side of a collision keeps the plain name is undecided — naming `Event` staying bare as one of the two instances of the open case. `Event` is the general abstraction every other event composes, which is the criterion that handoff offers for the side that keeps the plain name, so the bare name is defensible on the rule as it currently stands and inconsistent with the directory's other declarations.
- Next: the owner's ruling on the handoff's open question decides this. Nothing in this protocol depends on the spelling.
- Question for the owner: none from this document.

### Does the protocol owe anything about a handler that blocks or misbehaves?
- State: this protocol places no obligation on a handler beyond receiving the occurrence. [Process → Events](../../process.md#events) explicitly permits a handler to block the caller, and the concept assigns the whole question to the dispatch mechanism's rules, so declining to state it is a consequence rather than a gap. What is unexamined is the aggregate: a listener that blocks every dispatch is a target that has stopped working, and nothing in the Event contract or the Error contract makes that visible to anyone but the blocked caller. Whether that needs an answer here, or belongs to the dispatch mechanism's own contract, is open.
- Next: raise it where a dispatch mechanism is actually specified; a protocol-level answer now would be a claim about a mechanism this document does not name.
- Question for the owner: none.

### What is `EventMainType`, and should the ecosystem's event taxonomy be carried at all?
- State: `modules/process/event/____events.kh` carries 53 `EventMainType_*` identifiers taken from the web's event list, mixed with a handful of Memar's own (`Log`, `System`, `Navigation`, `Storage_Record`), under a filename of four underscores. No file declares `EventMainType`; the whole block is residue, and the residue in `modules/process/event/target.kh` names it as the type a target dispatches "on desire" event types — a dispatch-by-type-string model this protocol does not adopt, since [A target accepts only the kind of event it declared](./event.md#how-a-target-narrows-to-one-kind-of-event) makes the kind a type rather than a value. Importing the ecosystem's taxonomy wholesale also runs against [Cognition → Resist defaults that arrive with the medium](../../cognition.md).
- Next: either delete the block, or replace it with Memar's own taxonomy stated for a reason. What would settle it: whether a dispatch keyed by a runtime type *value* is wanted anywhere — that is a capability question, and this protocol currently answers no.
- Question for the owner: is a runtime-keyed event type wanted, and if not the block goes?
