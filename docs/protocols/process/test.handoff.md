# Test Handoff
Open work for [test.md](./test.md). Entries are mutable current state, revised as each item moves and removed when it resolves or is dropped. See [documentation-handoff.md](../../documentation-handoff.md) for what a handoff is.

## Open Questions

### The module's own protocol surface
1. What the Test module under `modules/process/test/` exposes — whether a runner, a discovery service, a report format, or only Rules — is undesigned, and the folder is a carrier of thinking rather than a container awaiting code ([modules → Why a folder may exist before it holds code](../../../modules/README.md#why-a-folder-may-exist-before-it-holds-code)). Deciding it needs a design session the way [SDK](../modules/sdk.md) records its own.

### The Rules and their enforcement
1. Whether [test-placement](../../../modules/process/test/rules/test-placement/test-placement.md) and [test-naming](../../../modules/process/test/rules/test-naming/test-naming.md) are checkable by anything this repository runs, or are governance-tier Rules an organization adopts by choice. The toolchain enforces governance Rules for Khayyam source ([Khayyam rules → The rules](../../../modules/khayyam/rules/README.md#the-rules)); a condition over a folder tree is a different check, and no such check exists yet.
2. Whether the plural form `tests/` is a repository-wide convention about role folders, or a local choice. The reasoning that produced it is in the placement Rule; the general case, being that a role folder is singular when it holds one thing of its kind and plural when it holds many, has no document of its own, and this repository's two role folders in Khayyam's toolchain are singular (`core/test/`, `targets/*/test/`).

### The mechanism this protocol declines to state
1. No runner exists for the language this repository's modules are written in, and the test artifacts currently present are archived from a previous language under a migration marker. Nothing in this protocol requires one, per [test.md → Test, Check, and Runner](./test.md#test-check-and-runner), but a system cannot check the Tests this protocol obliges it to carry without one. Whether the runner belongs to the module here or to a general tool is a separate decision this document does not make.

### Graduated from the researches
1. **Whether a Test's completeness can ever be made checkable.** [test.md ? What Would Take This Further](./test.md#what-would-take-this-further-and-what-would-not) establishes that the literature's "a test can be a proof" result is licensed by a proved property of the selection, which this protocol does not require and does not claim. That leaves an open possibility rather than a closed door: a Test set could in principle carry enough structure for its completeness to be argued, and the ecosystem survey found no language whose tools make that structure expressible today. Whether a future realization should carry it, and what obligation would follow, is undecided — and it is the one place where a stronger Test would change what this protocol asks for rather than only how much it says.
2. **Whether the internal-structure limit should be stated more strongly.** [test.md ? What Would Take This Further](./test.md#what-would-take-this-further-and-what-would-not) records Dijkstra's position that what can be established about a program depends on its structure and not on its specification alone. The protocol states that as a boundary it does not itself address. Whether the coverage obligation should route toward a structural claim as well — that is, whether a protocol about Test should also govern what a Test can be expected to reach given the structure it is run against — is a question about scope that this document leaves open rather than answered.

## Anticipated Work
- The Rules this document points to may grow a third, for what a Test may assume of its own subject's internals once a real case forces the question [test.md → What a Test May Assume](./test.md#what-a-test-may-assume) cannot answer.
- If a second system adopts this protocol, the placement and naming Rules will have an adopter other than this repository, at which point [Rule → This set is a floor, not a ceiling](../../../modules/khayyam/rules/README.md#this-set-is-a-floor-not-a-ceiling)'s reasoning applies to them and they should say so themselves.

### Carried over from the absorbed TDD document
1. **Whether a fuller vocabulary is warranted for the four roles that share overloaded domain words** ? the written expectation artifact, the comparison procedure, the enacted comparison, and the disposition or result. [Process ? Expectations and Checks](../../process.md#expectations-and-checks) and this document between them use a two-word base plus *Test* for the artifact. A fuller vocabulary is open only if recurring confusion returns; it is not blocking for applying this protocol, and it is the one question the absorbed document left open that its absorption does not answer.
2. **Whether the boundary between "expectations stated for the inquiry process" and "expectations for the inquiry's subject" needs its own worked treatment.** This document routes on it under [Test, Verification, and Inquiry](./test.md#test-verification-and-inquiry), inheriting the routing rather than settling the boundary. Whether an agent still re-derives it on each defect inquiry is the live test, and this document is the first protocol to depend on it.
3. **Whether development of a uniquely enacted system needs anything beyond the ordering stated here.** A foundation pour, a public launch, a one-time organizational restructure. The ordering binds and the check may be unavailable afterward; nothing here substitutes for that, and whether a rule should is open only if a real case shows the absence is a defect.
