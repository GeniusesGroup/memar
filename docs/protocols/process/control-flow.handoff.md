## Open Questions

### Which type owns the control-flow forms, and what category is it?
- State: Khayyam's method rules require every method to name its parent type in its owner group and every call to write the receiver and both variable groups ([Method → Method Invocation Rules](../khayyam/method.md#method-invocation-rules)), and the owner-less global form is closed as rejected in favor of type-level invocation (paired changelog, 2026-09-23). No document requires one type per form or one form per file: Khayyam asks for short, single-responsibility files ([Khayyam → Import Mechanism](../khayyam/khayyam.md#import-mechanism-in)), which bounds a file's size, not how many forms one owner carries. The repository holds four spellings, none decided: this document's examples (`tp IF in "…/if.kh"` and an owner-less `IF(cond, scope)`); the corpus draft `modules/process/control-flow/protocol/if.kh` (`tp IF mt () (condition Condition, execute labelType) (err Error)` — owner-less, two unbound types, and an `Error` import from a file that does not declare it), beside per-form files that carry only a licence header; the JS target's own library (`modules/khayyam/targets/js/lib/branch.kh`, where `IF` and `ELSE` are each an `ab` owning `OnTrue`/`OnFalse`); and one owner for the whole family — `CF.IF` in [execution.md](../../modules/khayyam/execution.md) step 4 and the untracked root scratch `main.kh`, and `CF.Return` in the owner's words ([Method changelog, 2026-08-27 entry](../khayyam/method.changelog.md)). One owner with bare method names is consistent with the language and with the toolchain's [receiver method names rule](../../modules/khayyam/rules/receiver-method-names/receiver-method-names.md). The owner raised on 2026-09-28, without deciding, that the forms may sit under `tp CF sc`. For it: [Type → Scope](../type.md#scope--type-as-semantic-boundary) counts a namespace or module-visibility boundary as a Scope, and a method may attach to any type ([Method → Method Structure](../khayyam/method.md#method-structure)). Against it as written today: [Khayyam → Scope](../khayyam/khayyam.md#scope) describes `sc` as a code scope that is inert until a library method drives it, this toolchain refuses a top-level `sc` ([scope placement rule](../../modules/khayyam/rules/scope-placement/scope-placement.md), owner ruling 2026-09-26), and no document says what a file-level scope is — driven by whom, entered how ([its handoff](../../modules/khayyam/rules/scope-placement/scope-placement.handoff.md)).
- Question for the owner: is the owner of the forms (a) a Scope in Type's namespace sense — and then is Khayyam's `sc` the declaration of that kind of Scope as well as of the inert code scope, and what does entering it mean; (b) the protocol's contract, an `ab` that each organization's control-flow library realizes (the library choice being the Linter's, per the Mechanism Summary); or (c) something else? The answer fixes the declaration, the file layout, and whether the scope placement rule changes.
- Downstream of the answer, also open: the type of the condition variable (the examples use `Status` and `Bool`; the boolean protocol is not final), how a signature writes the type of a scope parameter ([Method → Type-level arguments for `sc` and `mt`](../khayyam/method.md#type-level-arguments-for-sc-and-mt) says an `sc` is received, not what the parameter's type is written as), and whether a form has an influenced `err`.
- Next: the owner answers; the declarations are then written once under `modules/process/control-flow/protocol/` and this document's examples are rewritten to the settled call. Until then no module depends on a declaration under that folder, and no form declaration is added there.

### Which error class is declared as an abrupt halt (panic)?
- State: recovered 2026-09-17 from an audit of Omid Hekayati's Telegram-group messages (Go Engineers, 2024). A position reached in a panic-vs-error discussion, offered by the owner as a general doctrine: errors **temporary and outside the program's control** (e.g. momentary memory unavailability) warrant abrupt halting (panic-class behavior), while input-validation failures return errors addressed to the caller — with the owner noting the answer depends on how the return/halt distinction is modeled, not merely on which is conventional in Go. This document anticipates halting semantics ([Topics to be developed here](../process/control-flow.md#topics-to-be-developed-here)) and [The Error](../process/error.md) carries an `Internal`/`Temporary`/`Timeout` class model (the optional capability interfaces of [Composition](../process/error.md#composition)) without yet connecting the two: which class conditions justify a `PANIC()`-family halt versus an ordinary propagated error is undecided.- Next: settle jointly with the halting-semantics topic when that topic is developed; the temporary/uncontrollable criterion is the owner's working position to evaluate, not a decided rule.

### Should the success/failure pair live on the Error abstraction or on a shared abstraction?
- State: asking an `Error` — whose identity already represents failure — "what to do on success" may be semantically backwards; the pair may belong one level up, on the shared abstraction `IsNull()` already belongs to, with `Error` only inheriting it. Not yet decided.
- Next: resolve before finalizing the pair naming.

### No final naming choice between the candidate pairs
- State: `OnFailure`/`OnSuccess` versus `OnPresent`/`OnAbsent`, or another candidate — none confirmed as final.
- Next: decide alongside the shared-abstraction question above.

### Interaction with the rejection of default implementations
- State: if the shared-abstraction approach is chosen, how does it interact with [Abstraction in Khayyam](../khayyam/abstraction.md#rejection-of-default-implementations)'s rejection of default implementations? Each implementing capsule would need its own Explicit Delegation Verification line to a shared internal implementation, to avoid duplicating the same check logic across every implementer without resorting to inheritance.
- Next: design the delegation-verification mechanism if the shared abstraction is chosen.
