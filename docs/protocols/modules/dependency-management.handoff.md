### The manifest, its four obligations, and its name
- State: ruled 2026-09-29 (owner) and built toward on 2026-09-30, all of it in this document rather than in a Khayyam one — a session had put it in `docs/khayyam/modularity.handoff.md`, which is the wrong layer, and it was moved here.
  - **The base is the writing module's manifest.** An address is resolved through the manifest of the module whose file wrote it — not a repository root, not a folder a client states, not a version-control directory. The reason is that a Module is not a directory ([Modularity → Modularity Is Not Deployment](../../../modularity.md#modularity-is-not-deployment)): one repository holds a hundred modules, so there is no one place every address resolves from.
  - **A manifest says everything about its own module, and it is declarative, so it is complete.** Four obligations: which part of the address space is its own; how one reaches it; which other modules it uses, held in the referring module's own manifest as every dependency manager does; and what documents belong to it with how to reach each — a Reference and zero or more Locators, which are two different things ([Content → Reference as a Relation, Not a Property](../../../content.md#reference-as-a-relation-not-a-property)).
  - **A fault in a manifest is a fault in that module.** It makes the whole module unusable rather than one claim in one file, so it is reported once against the module and every dependent `in` is a consequence of it. This last reading is the toolchain's and not the ruling's.
  - **The name is `memar.manifest.{format}`** — one fixed stem, the realization in the suffix, spelled the same everywhere, and kept apart from the ecosystem's bare `manifest.*`. Because the suffix varies, the fixed name is `memar.manifest.*`, so which formats a reader tries is a fact the protocol owes, and two in one directory is an error rather than a choice.
- **A manifest is found by stem and read by a registry, and a format this reader does not have is a different answer from no manifest.** Ruled 2026-09-30 (owner): the code must not be hardwired to one format, because the objection "YAML would have been better" is one a reader is entitled to make and the answer has to be *true* rather than promised — adding a format is one entry in the server's list. And a reader that finds a manifest it cannot read says so, names the format, and says that opening an issue to add it is the whole of the work; it does not read it approximately. The two answers are told apart because the remedies differ: one wants a manifest written, the other an issue opened. **Built on 2026-09-30** in [`lsp/src/manifest.ts`](../../../modules/khayyam/lsp/src/manifest.ts), with the registry, the stem, the two-manifests-in-one-directory fault, and the unreadable-format sentence each under a test.
- Open: the format set to register beyond JSON; the fields; the algorithm. **The fields are what now blocks the Khayyam toolchain**: its server walks up, opens a manifest, reads it, and then says it does not yet know how to ask it anything — so the remaining unknown is a schema, which is a question about the document and not about plumbing. **Where a manifest is looked for is ruled (2026-09-30, owner), in two steps.** First: upward from the file's own directory, one directory at a time, and the manifest in the directory where the walk ends is the one that answers — no walk continues past a manifest it found, because a manifest that added to a higher one rather than replacing it would leave "which claim answers" undecidable. Then, the same day, the owner struck the ending out: **the walk must not stop at a directory name**, and the earlier version of this entry said it stops at the directory containing `.agents`. Naming a directory makes the walk's end depend on a spelling, and the owner's reason is the standing one — a filesystem realization is not what a protocol is built on, and finding these directories is not the right method, only the one a filesystem-based dependency management has. **And then struck out again, the same day, for the same reason one step further**: the boundary had been implemented as this repository's `$MEMAR_ROOT`, and the owner's objection is that a framework is not its own use — `MEMAR_ROOT` says where *Memar's source* sits on a machine, so in a project that merely **uses** Memar it says nothing about that project at all, and a criterion that answers for the framework and not for the project is the storage engine's mistake in a project's clothes. So the criterion is **a statement the project being worked on makes about where it ends**, `MEMAR_ROOT` being this repository's one instance of it and the only such statement that exists yet; a foreign project states its own somewhere this repository does not know where, and designing that statement is not something a Khayyam rule folder should invent. Until it exists, such a project gets the filesystem's own root and a warning with it: **a manifest found while no boundary was stated was found by walking out of the project**, and on a machine holding several projects that is another project's module — so the answer says so rather than reporting it as found. The two endings are named apart because they are different facts with different remedies, and a walk with no boundary is the third and worst case. The walk finds the *writing* module's manifest and is not itself a claim about which module a file belongs to; what that manifest then declares about the modules it uses is a separate relation, and the two being apart is what lets a module that claims `memar/*` and a part of it that claims `memar/error` both be modules.

### A module claims an address by a pattern, and a whole may be a module as well as each of its parts
- State: ruled 2026-09-29 (owner). A module declares a claim over a pattern rather than a row per declaration — the example given being every reference matching `memar/*` — and either the whole framework or each part may be a module, with the levels themselves open to discussion.
- This is the one design decision here that is load-bearing for everything else, and it is not yet a protocol, so the following is analysis rather than a position. **Precedence is not a detail under it.** If a whole claims `memar/*` and a part claims `memar/error`, one address is covered by two claims, and something must say which answers. Most-specific-wins is the only rule that lets a whole and its parts both be modules, and it is the one that makes the owner's "a whole can be a module too" work at all rather than being a special case. The cost is that it also silently swallows a mistake: a module that wrote `memar/.*` intending itself takes every other module's space and nothing complains, so most-specific-wins is defensible for the *answer* only if overlapping claims are also *reported*.
- **A claim should be a path-shaped pattern, not a regular expression.** A claim is a namespace, and a namespace that can match any string is not one; a regular expression in a claim can cover addresses its author never considered, and a module cannot know at writing time which those are. A glob over segments is checkable at the moment it is written. If a regular expression is wanted, it belongs in the "how one reaches me" half, which is a procedure rather than a claim. **Ruled 2026-09-30 (owner, accepting the receiver's reading): a claim is a path-shaped pattern with a wildcard in it, and a regular expression is not admitted in a claim.**
- **The claim tree is not the module tree, and keeping them apart is what stops this sliding back into the error a walk made.** Two modules may nest because their *addresses* nest, and nothing follows about responsibility: a Module is a bounded Responsibility and a shared prefix is not one. A claim hierarchy is a resolution structure; a module hierarchy is a design one, and the protocol owns only the first.

### The collision with this document's stated position
- State: open, and it is the largest thing here. This document's [position](../dependency-management.md) is that **the version-control repository is the dependency mechanism** — dependencies are references into other repositories, pinned by the VCS, addressed as local relative paths — and it names the manifest-plus-lockfile layer as machinery Memar's default does not require. The 2026-09-29 ruling needs a manifest, and says its file is `memar.manifest.{format}`.
- These can be reconciled without either position giving way, and the division is sharp: **a manifest declares identity and reachability; the VCS pins revisions.** One addressing scheme (the manifest's claim) and one pinning mechanism (the VCS's own), which is what this document already argues for against the package manager — the package manager is a *second* addressing scheme and a *second* source of truth, and a manifest that declares what a module is and how to reach it is neither a lockfile nor a second pinning mechanism. What it costs is a file the VCS does not pin, so its own version is a question: either the manifest is tracked and pinned like any other file in the repository, or it is generated and then it is a build artifact and the position here is unchanged.
- **This has not been ruled and is not decided here.** Recorded as a question because a later session reading only the 2026-09-29 rulings would not know that they contradict this document's Abstract.
